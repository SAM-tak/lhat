# Lua との速度差を2倍以下にする最適化

比較基盤のコミットは `4525e7a`。既存の6ケース、入力サイズ、seed、反復の意味、期待結果を維持した。
L^ / Luau は Visual Studio 付属 Clang 22.1.3、Lua 5.5.1 は MSVC 19.51.36260.0。
Release、PGO / JIT / デバッガ無効、GC は通常設定。比較対象の Lua / Luau の実行ファイルは最適化前と同じ SHA-256。

標準設定の各5プロセス・3ウォームアップ・10サンプルで、全6ケースの `L^ 時間 / Lua 時間` が2以下になった。
代表値はプロセス中央値の中央値。各ケースの「最も遅い L^ のプロセス中央値 / 最も速い Lua のプロセス中央値」も2未満。
後者は分布の範囲の確認であり、将来の測定に対する信頼区間ではない。

単位は µs / round。最適化前は保存した基準測定の値であり、同時測定の対照実験ではない。
目標判定の比率は最適化後の L^ と Lua を同じセッションで測った値を使用する。

## 変更内容

- 通常のテーブルが自身に持つ文字列フィールドと整数添字の配列要素は、VM 内で直接読み取る。継承・委譲・組み込みメンバ・未充填の予約フィールドなどは既存経路に戻す。
- 既存の配列要素と文字列フィールドの更新も直接行う。共有・読み取り専用テーブルの制約と、GC の黒オブジェクトから白オブジェクトへの書き込みバリアは維持する。新規キー・削除は既存経路を使う。
- フィールドや添字への複合代入でも、数値リテラルの右辺には既存の定数演算命令を使い、不要なロードと一時レジスタを減らす。評価順と nil 安全な代入の短絡を維持する。
- コンパイル時にローカル変数が捕捉されたか記録し、捕捉されないスコープの CLOSE 命令を省く。残る CLOSE も、開いた upvalue がなければ外部関数を呼ばない。

## 検証

- Clang Release のコア・型検査・VM・標準ライブラリ・LSP・DAP・インストール確認を含む90テストがすべて成功。
- tombstone をまたぐ文字列検索、内容が等しい別文字列での更新、配列の nil 穴、ループ内で捕捉した変数の寿命を追加検証。
- 既存のハッシュスロットと配列スロットそれぞれに対し、黒い親への白い子の書き込みで親が再走査対象になることを決定的に検証。
- 3 VM とも、標準入力と境界入力2種類の正解を検証。全ウォームアップ・測定でも期待結果を確認。
- ベンチマークのケースと manifest は基盤コミットから変更していない。

結果はこのマシン（AMD Ryzen 5 2600 / Windows x64）と固定ケースに対するもの。任意のプログラムで2倍以下という保証ではない。
生データ・バイトコード・ビルド条件・測定時点の差分は、ローカルの `results/optimized-selected-clang-msvc/` に保存した。生データは通常どおり Git 管理外。
