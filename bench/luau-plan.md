# L^ と Luau の比較ベンチマーク計画

目的は、組み込み用途で L^ と Luau の実行時間・起動コスト・メモリ使用量を比較し、L^ の改善対象を特定すること。最初は Windows x64 の同一マシンで再現可能な比較を作り、後から Linux に展開する。

初期版の実装と実行手順は [compare/README.md](compare/README.md) を参照。拡張項目を含む全体計画は以下に残す。

比較対象には本家 Lua 5.5.1 も追加。公式ソースを固定し、同じ 6 ケース・入力・検証・測定方法で 3 VM を比較する。以下は当初の L^ / Luau 比較計画。

Windows の標準比較は配布構成に合わせ、Visual Studio 付属の `clang-cl` を C/C++ の両方に指定する。初期の MSVC 測定結果は別条件として保存する。

## 1. 既存コードとの関係

- `bench/main.c` はメンバ参照・ホスト呼び出しなどの内部コストを測るもの。現在はミリ秒時計と 5 回の最小値を使用している。
- `bench/checkbench.c` はホスト型と委譲の型検査コストを測るもの。
- 両方を残し、言語間比較は `bench/compare/` に追加する。既存の差分計測の数値をそのまま言語間ランキングに使わない。
- `DesignDocuments/12-specialization.md` の PGO 方針を踏まえ、通常の Release 比較に加えて PGO の測定を用意する。L^ の JIT は試作なので追加実験とする。

## 2. 比較条件を固定する

最初の比較は L^ VM と Luau VM。両方を同一コンパイラ系列・アーキテクチャの Release ビルドにし、サニタイザとデバッガの実行時フックを無効にする。L^ は `LHAT_WITH_DEBUGGER=OFF` と、それに必要な `LHAT_BUILD_DAP=OFF` を使う。ビルド設定・実際のコンパイルオプションは結果に保存する。

Luau はコミット SHA を固定し、バイトコードの最適化レベルを明示する。まず O2 を主比較、既定設定を補助比較とする。C/C++ コンパイラの最適化と Luau のバイトコード最適化は別々に記録する。

追加の比較は次の順序で行う。

1. 両方の PGO ビルド。訓練用ワークロードと測定用入力を分け、同等の訓練条件を記録する。片側だけ成功した結果は非対称な条件として表示する。
2. L^ の JIT と Luau の native code generation。対応環境・対応ケースを確認し、コンパイル時間とフォールバックの有無を記録する。VM の結果とは別表にする。

依存ソースの取得は明示的な準備コマンドで行い、通常ビルド時の自動ダウンロードは行わない。

## 3. ケースを段階的に増やす

| 段階 | ケース | 調べること |
| --- | --- | --- |
| 最初 | 数値ループ・分岐 | 算術、比較、命令ディスパッチ |
| 最初 | 関数呼び出し・再帰 | スクリプト内の呼び出しコスト |
| 最初 | 配列の走査・更新 | 添字アクセスと集計 |
| 最初 | 固定フィールドの読み書き | テーブルアクセスとキャッシュ |
| 最初 | テーブルの生成・破棄 | アロケーションと通常の GC を含む負荷 |
| 最初 | 複数フレームのエンティティ更新 | ゲームに近い混合負荷 |
| 追加 | 文字列処理、クロージャ | 文字列管理、捕捉変数の扱い |
| 追加 | ホスト関数・ホストメソッド | API 境界のコスト |
| 追加 | ベクトル演算 | 共通のスカラー実装と各言語の値型実装 |

各ケースに入力サイズ、固定 seed、反復回数、期待結果を定義する。まず各分類 1 ケースずつ実装し、細分化は結果を見て行う。

数値は共通の計算意味を優先する。L^ の整数と Luau の number を無条件に同一視せず、整数計算は倍精度で正確に表現できる範囲に制限し、浮動小数点ケースは L^ 側も浮動小数点入力で実行する。浮動小数点の誤差許容はケースごとに定義する。

配列の 0/1 ベースの違いは移植時に吸収し、要素数と処理回数を一致させる。同一アルゴリズム・同一データ構造による比較と、各言語固有の機能を使う比較を分ける。特に L^ の値型と Luau のベクトルは精度・成分数を確認し、同等条件が作れなければ参考値にする。

## 4. 測定ハーネス

CMake で独立した 2 つの実行ファイルを作る。L^ は C API、Luau は C++ の薄いアダプタから実行し、共通の結果形式を出力する。L^ 本体のビルドに Luau や C++ の依存を持ち込まない。

各アダプタはケースの読み込み、準備、実行、結果検証、破棄の境界をそろえる。外側の Python ランナーで両方の起動、実行順、反復、集計を管理する。

| 指標 | 計測範囲 |
| --- | --- |
| 定常実行 | コンパイル・ロード・初期化を除いたカーネル実行。処理中の割り当てと GC は含む |
| フロントエンド | 型検査とコンパイルを分けて計測。分離できない経路は合算と明記 |
| 初回実行 | 新規プロセスの起動から計算結果を得るまで。型検査を含むか明示 |
| メモリ | 別の計測パスで VM 管理ヒープのピークとプロセスのピーク使用量を記録 |

型検査は実行速度とは分ける。Luau 側は解析用 API または解析ツールを明示的に呼び出し、通常の実行経路に型検査が含まれるとは仮定しない。言語の検査内容が違うため、型検査速度だけで単純な優劣を付けない。

定常実行の具体的な手順：

1. 両実装の期待結果を検証する。不一致・実行失敗は集計対象外として失敗を報告する。
2. 単調増加の高分解能時計を使用する。Windows では `QueryPerformanceCounter` を使う。
3. 予備測定で遅い側の 1 サンプルが約 250 ms になる共通反復回数を決め、両実装に同じ回数を適用する。速い側のサンプルは短くなるため、実時間も生データに残す。
4. 新規プロセスを各実装 5 回起動し、それぞれ 3 回のウォームアップ後、10 サンプル採る。遅いケースは明示的な時間上限を適用する。
5. 実装の実行順を交互または固定 seed のランダム順にする。ウォームアップ後も状態が変わるケースは初期状態を復元し、そのコストを含むかケース仕様に記載する。
6. 結果は各プロセスの中央値と、その中央値の分布を集計する。全サンプルを独立した測定として扱わない。初回実行はウォームアップせず別途測定する。

GC は通常設定で有効にする。強制 GC が必要な診断実験は別枠とし、メイン結果で都合よく GC を停止しない。計測区間内のログ出力を避け、計算結果をホスト側で読み取って検証する。入力を実行時に渡し、定数式だけに縮退していないか代表ケースのバイトコードも確認する。

## 5. 成果物

追加する構成の案：

```text
bench/compare/
  CMakeLists.txt
  README.md
  manifest.json          # ケース、入力、期待値、誤差許容
  lhat_runner.c
  luau_runner.cpp
  cases/                # 対応する .lh と .luau
  run.py
  report.py
  results/              # 生データの出力先。通常は Git 管理外
```

Luau のソースパスを指定できる独立 CMake プロジェクトとし、既存の `LHAT_BUILD_BENCH` と切り離す。README に依存取得・Release ビルド・正解確認・全計測・レポート生成のコマンドを載せる。

結果には両リポジトリの SHA と未コミット変更の有無、OS、CPU、コンパイラ、ビルド設定、PGO/JIT、Luau の最適化レベル、ケースの入力、seed、時計、全サンプルを保存する。

レポートはケース別の実行時間、ばらつき、`L^ 時間 / Luau 時間` を表示する。比率は 1 未満なら L^ が速い。メモリと初回実行は別表にする。幾何平均を載せる場合は対象ケースを固定し、失敗ケースを明記する。

## 6. 実装順と完了条件

1. **基盤**：Luau の固定版取得手順、独立 CMake、両アダプタ、単一ケースの正解検証と JSON 出力を作る。
2. **初期スイート**：上表の「最初」の 6 分類を追加し、入力・計算意味・期待値をレビューする。
3. **再現可能な測定**：ウォームアップ、複数プロセス、実行順、サンプル保存、レポート生成を実装する。
4. **実用指標**：初回実行、フロントエンド、メモリを追加し、PGO 比較を行う。
5. **拡張**：ホスト API、ベクトル、JIT、Linux を必要に応じて追加する。

初期版は、Windows x64 で文書のコマンドから 6 分類の正解確認・VM 比較・生データ保存・レポート生成が再現できれば完了とする。通常 CI はビルドと小さな入力での正解確認のみ。性能のしきい値による合否判定は、専用マシンで安定性を確認してから導入する。
