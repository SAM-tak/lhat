# Reloading and distribution

## Custom file loaders

`LhatProgramLoader` receives a UTF-8 path and returns contents with a byte count.
Connect it to a virtual filesystem, archive, or unsaved editor buffer. Return NULL if the file is unavailable.

Allocate returned buffers with `lhat_alloc` and transfer ownership to the program.
The program frees them with `lhat_free`; do not return a stack array, `std::string::c_str()`, or a buffer from another allocator.
For source text, also provide room for a terminating NUL and exclude it from `length`.
A program with a NULL loader does not read files automatically.

`require^` dependencies are resolved relative to the current unit's path.
Keep logical paths consistent across the editor, runtime, and distributed files.

## Start with restart-based reloading

Initially, discarding script state and recreating the machine may be sufficient.
Apply changes at a frame boundary, with explicit handling for stopping workers and releasing engine references.
Do not destroy code or instances in the middle of an executing callback.

## Reload code while keeping state

`lhat_reload(program, path, machines, machine_count)` combines invalidation of changed and dependent units,
rechecking, recompilation, forgetting old module registrations, and reclaiming unheld retired code.
Pass every machine on which the program was installed, and call at a safe boundary with execution stopped.

- 0 means the source has not changed.
- `SIZE_MAX` means the program has no unit at that path.
- Other values count invalidated units; they are not a success boolean. Check diagnostics and compilation state separately.

If checking or compilation fails, existing old closures can continue using their old code.
Even after success, existing host-held instances and callbacks are not automatically replaced with new implementations.
Run modules again to obtain new exports, replace host references, and migrate any state you need.

The manual `lhat_program_discard_retired` function is safe only when no machine holds an old closure or suspended coroutine.
Normally use `lhat_program_discard_unheld`, with every affected machine stopped, to determine which retired code can be reclaimed.
See the [C API](../api/program.md#reloading) for details.

## Choose a distribution format

| Format | Host requirements |
| --- | --- |
| Source | A runtime with the frontend and normal API registrations |
| Compiled units | A runtime with a matching build fingerprint and matching API registrations |
| VM-only | The above plus a signature table generated by a full build |

Use `lhat_unit_write_binary` to serialize each checked and compiled unit in a full build.
Loading uses the same loader and `lhat_program_check` entry point; initial bytes identify a binary unit.
Source and binary units cannot be mixed in one program.
Write all dependencies too, preserving their logical paths.

For a VM-only build, set `LHAT_WITH_FRONTEND=OFF` and `LHAT_BUILD_LSP=OFF`.
Because this build cannot parse signature strings, generate a table with `lhat_program_write_signatures` from a full build of the same host.
In the distribution build, read it with `lhat_program_read_signatures` **before API registration**, then register the same host APIs as usual.

`lhat-host.json` is editor JSON. It does not replace a VM signature table or compiled units.
Do not treat binaries as a long-term compatible interchange format; regenerate them for the corresponding runtime and registrations.
