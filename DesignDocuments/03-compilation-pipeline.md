# L^ 処理の構成

ソースを受け取ってから実行するまでの段階構成と、
その構成を決めている実行時の値表現について定義する。

字句については [01-lexical-structure.md](01-lexical-structure.md)、
構文については [02-syntax.md](02-syntax.md) を参照。

本文書の未決事項には `P1`, `P2`, … の番号を振る。

**現状**: 段階構成、実行時の値表現、型検査の厳格度、推論の範囲が確定している。
バイトコードは命令の形式・呼び出し規約・捕捉の扱いが確定し、実装が追いついている。
多重定義の解決（5.11）は厳格度で分かれる——strict はコンパイル時、
relaxed と未検査は実行時。
ガベージコレクション（5.12）は標識と掃除で、命令の切れ目ごとに一歩ずつ進む。
捨てられたコルーチンの保留中の `finally^` も実行する。世代別は未着手。
コルーチンの実行時の形も確定している（5.7）。
未決は `P4`（REPL の型環境持ち越し）、`P6`（相互再帰の推論そのもの。
安全性は確保済み）、`P7`（`=` をテーブルの値比較にする）、
`P8`（relaxed の探索記述子を推論型で埋める）。

## 1. 段階構成

### 1.1 構文木

```text
ソース → 字句解析 → 構文木 → 型検査 → コード生成 → バイトコード
```

Lua が採る単一パス（トークンを読みながら直接バイトコードを出力する）は使えない。

「静的自動型付け」は型推論を意味する。
推論は **ソースの後方にある情報を必要とする** 場合がある。

- 再帰関数の返り値型は、本体を読み終えるまで決まらない
- 相互再帰する定義は、互いを読み終えるまで決まらない
- 注釈のない引数の型は本体の使用箇所が決めるので、署名を読み終えても決まらない（3.4）

Lua の単一パスが成立するのは動的型付けだからであり、
`expdesc` とレジスタ割当を読みながら確定できることが前提になっている。
L^ ではこの前提が崩れる。したがって **構文木を作る段が必須** である。

名前解決を型検査から分離して5段にする構成もありうる［提案］。
名前解決は型検査に必要な情報を用意する処理であり、
独立させたほうがスコープ規則（`$` `$^`、01 の 8 章）の実装が読みやすくなる。

### 1.2 単一パスを捨てて失うもの

Lua の `lcode.c` と `lparser.c` が実装している単一パスのコード生成技法
（`expdesc` による式の遅延評価、レジスタ割当、ジャンプパッチリスト）は、
L^ では **そのまま流用できない**。参照価値が下がる。

一方、これらと直交する部分は参照価値を保つ。

- レジスタ仮想機械のディスパッチループ
- 命令のビットレイアウト
- インクリメンタル GC と書き込みバリア（5.12 で借りた）
- 配列部とハッシュ部のハイブリッドなテーブル
- バイトコードの直列化（05 の 10 章がこれ）

### 1.3 診断の見せ方は段で分けない

1.1 の各段は **自分の誤り種別を持つ**。字句・構文・意味は問う対象が違うので、
種別が混ざらないほうがよい。

一方 **読み手にとって、どの段が言ったかは表示の形を変える理由にならない**。
そこで **種別は段のもの、描画は共有** とする。

```text
let^factorial = f^n:number^{ if^ n < 2: 1 else^: n * this^(n - 1) }
                                                                  ~
(stdin)1:67: error: expected a different token here
```

- 起きた行をそのまま引用し、その下に位置を指す
- **印は `^` ではなく `~`**。01 の 2.2 によりハットは文字であり、
  ハットだらけの行の下にハットの列を置くと行の続きに見える
- 位置は最後に置く。目が「行 → 印 → 理由」の順に動く

短い形（`main.lh:1:67: error: …`）も残す。ソースを手元に持たない呼び出し側では
引用できないため、その場合は自動的に短い形になる。

#### 長い行は窓で見せる

端末が折り返すと **印が別の行の下に落ちて意味を失う**。
そこで一定の幅を超える行は、印の周りだけを切り出し、
切った端に `...` を置く。

```text
...xxxxxxxxx : string^ = aaaaxxxxxxxxxxxxxxx
                         ~
```

印は印で **左の `...` の分だけずらす**。行の一部しか見えないほうが、
折り返して印がどこを指すか分からないよりはよい。

#### 桁の数え方は2つある［重要］

**診断が言う桁は文字数**である。エディタに「その位置へ行け」と言うのはこれ。

**印を置く位置は端末のセル数**である。UAX #11 の全角は2セルを取るので、
文字数で置くと日本語の後ろで印が左にずれる。

```text
let^ s = "日本語テスト" + nowhere
                          ~
(stdin)1:21: error: no such name in scope
```

`nowhere` は **21文字目**（バイトなら33）だが、印は **26セル目** に置く。
`日本語テスト` の6文字が12セルを取るためである。

同じ理由で、印の幅も文字数ではなくセル数になる。
全角1文字を指せば `~~` が2つ出る。

- **2セル** — CJK、かな、ハングル、全角形、絵文字
- **0セル** — 結合記号、ゼロ幅文字、異体字セレクタ
- **1セル** — それ以外

窓の幅も **セルで測る**。折り返しを避けるための機構なので、
端末が描く幅で数えなければ意味がない。

タブは、窓を使わない場合はそのまま出す
（行と印の両方が同じだけ広がるので揃う）。窓を使う場合は
セルの計算が狂うため空白1つに畳む。

#### 気づいた場所と直す場所は違うことがある

構文解析器が誤りに気づく位置は、**書き手が直す位置とは限らない**。
先読みなしで進む以上、判断を保留したまま読み進み、
だいぶ後ろで辻褄が合わなくなることがある。

02 の 5.1 の `el^` がその例である。条件を伴うか伴わないかは `:` が来て初めて分かるので、
`:` を落とすと後ろの値が条件として読まれ、構文を閉じる `;` まで気づけない。

```text
let^階乗=f^n{ if^n < 2: 1 else^ n * this^(n - 1);}
                                                ~
error: a ':' was expected here, and this is ';'
```

印は `;` に付くが、書き手が触るのは `else^` である。

> **後から曖昧が解けたなら、印は解けた場所ではなく、
> 曖昧を生んだ構文の先頭に戻す。**

上の例では、読んだ式の直後に構文を閉じるものが来た時点で
「条件ではなく値だった」が **確定する**（推測ではない）。
そこで印を `else^` に戻し、読んだ式は値として受け取る。

```text
let^階乗=f^n{ if^n < 2: 1 else^ n * this^(n - 1);}
                          ~~~~~
error: this needs a ':' after it; what follows was read as
       the condition of a further test, and no ':' came
```

値として受け取ることで **後続の診断も出なくなる**。
1つの書き損じに1つの診断が対応する。

確定しない場合は戻さない。上の例で式の後ろに値が続いていれば、
それは本当に条件だったのだから、印は `:` が入るべき位置に置く。

#### 種別が知らないことは診断が持つ

種別だけでは「別のトークンが必要」としか言えない。
だが構文解析器は **どのトークンを期待したかを知っている** — `;` を待って
`}` に出会った、というところまで分かっている。

```text
(stdin)1:67: error: a ';' was expected here
```

そこで **診断に期待したトークンを載せる**。種別は種別のまま、
それだけでは足りないものを診断側が持つ形になる。

メッセージが文字列定数でなくなるため、書き出しは
`lhat_report_write` と同じ「バッファを埋める」約束にする。
種別だけで足りるものは、従来どおり定数を返す入口が答える。

同じ手が他の種別にも効いている。**種別を1つも増やさずに言えることが増える。**

```text
(stdin)1:67: error: a ';' was expected here, and this is '}'
(stdin)1:6:  error: expected a name, and this is a number
(stdin)1:1:  error: no such name in scope: nowhere
(stdin)1:2:  error: this value has no such member: missing
```

- **期待したトークン** — `expect_op` が知っている
- **実際に来たトークン** — 診断を作る場所には必ずトークンがあるので、
  **呼び出し側を1つも変えずに**記録できる。触れるのは `report` だけ
- **名前** — 検査器が「その名前が無い」「もうある」と言うときに手元にある

名前は **ソースから借りる**。6 章がソースを診断より長生きさせるので複製は要らない。
毎回複製すると、**ほとんど読まれない文字列の代金をすべてのプログラムが払う**。

トークンの幅も記録するので、印が **トークン全体を覆う**。

#### `nil^` が理由なら演算子の規則を語らない

04 の 11.3 が「無いキーは `nil^` を答える」と決めているため、
**キーで表から読んだものは常に `T|nil^`** である。
`nil^` の側に演算子は無いので、演算子が見つからない最頻出の原因はこれになる。

```lhat
let^ f = f^ t:t^{ number^[] } -> number^ { return^ t[1] + 1 }
```

ここで 02 の 11.3改（どちらの operand が `self^` を持つか）を読ませても、
書き手は「演算子を書け」と受け取る。**足りないのは絞り込み**であって演算子ではない。

> **`nil^` の腕を落とせば通る場合に限り、専用の種別でそう言う。**

「落とせば通るか」は各報告点が自分の問いでもう一度確かめる。
確かめずに差し替えると、`string^|nil^ + 1` のように
`nil^` を落としても通らない形に嘘をつくことになる——
そちらは今までどおり「演算子が無い」と言う。

##### 直し方まで言う［補足］

02 の 13.11 は**添字をその場では絞り込まない**。
`if^ t[1] fits^ number^ { t[1] + 1 }` は通らない。
これを言わないと、書き手は素直な絞り込みを試して二度目の壁に当たる。
そこで文面は逃げ道を2つとも名指しする——11.7 の `??` を使うか、
**名前に束縛してからその名前を絞り込む**か。

##### 一部の腕だけが持つ場合は扱わない［補足］

`number^|string^ + 1` のように、`nil^` 以外の腕が原因で欠けている場合は
今のところ従来の文面のままである。`nil^` ほど頻繁ではなく、
上の確認が偽になるので誤ったことは言わない。

#### 型を出すのはまだ

`MISMATCH` が「どの型を期待してどの型が来たか」を言うには
**検査器の `LhatType` を文字列に書き出す機構**が要る。

02 の 14.16 の `typeof^(x).signature` は実行時の `LhatRuntimeType` を
文字列にするものであり、検査時の `LhatType` を文字列にするものではない
（4.2 が両者を独立させている理由がそのまま当てはまる —
検査結果は検査が終わると同時に捨てられ、コンパイルは構文木を独立に読み直す）。
`MISMATCH` 用の書き出しは、まだ別に作る必要がある。

#### stdio には触れない

05 の 8.10 のとおり、言語は周囲に手を伸ばさない。
描画は **バッファを埋めるだけ** で、どこへ出すかは呼び出し側が決める。
`lhat_value_write`（4 章）と同じ約束で、
`(NULL, 0)` で長さを問い、確保してからもう一度呼ぶ。

## 2. 実行時の値表現

### 2.1 値は型タグを持つ［重要］

**実行時の値は自身の型を保持する。** 型情報を消去した表現は採らない。

これは本文書で最も変更費用の高い決定である。
後から覆すには仮想機械を作り直すことになる。

#### 2つの設計と、選んだ理由

- **(a) 実行時は動的で、静的型付けは検査層** — 値がタグを持ち、
  静的検査は実行前に正しさを証明する役を担う。
  TypeScript と JavaScript、Common Lisp の型宣言、Python と mypy がこの関係にある
- **(b) 実行時は静的で、型は消去される** — 仮想機械は型が正しい前提で動く

L^ は **(a)** を採る。

L^ は Lua を継いだ設計であり、唯一のデータ構造がテーブル、
プロトタイプベース、コルーチンを持つ。この構造では値がどのみちタグを必要とする。
(b) を採ると、型検査を緩めた動作が **別の値表現と別の命令セット** を要求し、
実質2つの仮想機械を抱えることになる。

(a) であれば、型検査を緩めた動作は検査層を弱めるだけで得られる。

### 2.2 具体的な表現形式

> **タグ付き共用体を採る。** Lua 5 の `TValue` に相当する形である。

```c
typedef struct {
    union {
        double    real;
        int64_t   integer;
        bool      boolean;
        LhatObject *object;
    } as;
    LhatValueTag tag;
} LhatValue;
```

#### 整数は 64 ビット［重要］

01 の 4.1 が「Lua 5.3 以降と同様に整数型と浮動小数点型を区別する」と定めている。
その整数は **64 ビット符号つき** とする。

02 の 14.8 のとおり **型としては `number^` ひとつ** であり、
整数と実数の区別は実行時の表現の話である。本節はその表現を定めている。

グルー言語としてファイルの大きさ・時刻・識別子を扱う以上、
2^53 を超える整数が丸まらないことに意味がある。

#### NaN boxing は採らない

IEEE 754 の倍精度で NaN を表すビット列は 2^52 通り近くあるのに対し、
演算が実際に生む NaN は1つしかない。余った約 51 ビットに他の型を詰めれば、
**あらゆる値が 8 バイト1語** に収まる。LuaJIT と JavaScriptCore が採っている。

利点は小さくない。テーブルが唯一のデータ構造である以上、
配列部の消費とキャッシュ効率が2倍違う。

棄却の理由は2つあり、**どちらか片方の解決では足りない**。

- **整数の精度。** ペイロードは約 48 ビットで、64 ビット整数が入らない。
  「整数は 48 ビットで十分——32 ビットを超えてさえいれば、テーブルの
  自然数索引には届く」という妥協はありうる（2^47 要素のテーブルは
  数十 PB を要し、どの機械でも作れない）。14.8改が既に「溢れたら実数へ
  広げる」を定めており、その理屈は閾値が 2^63 でも 2^47 でも変わらない。
  **精度だけなら妥協できる。** だが——
- **ポインタの移植性。** NaN boxing は利用者空間のポインタが 48 ビットに
  収まることも前提とし、x86-64 の5段ページングや ARM64 の LVA を使う環境
  では成り立たない。整数側をどう妥協してもこちらは残る。
  ポインタを別枠に逃がすと 8 バイト1語が崩れ、利点の方が消える

#### タグ配列の分離（SoA 化）［実装済み］

キャッシュ効率の不満は NaN boxing でなくても解ける形をしていた。
`LhatValueTag` は 3 ビットで足りるのに、整列の都合で `LhatValue` は
16 バイトになり、**半分がほぼ空気**である。詰める先を1語の中（NaN boxing）
に求めず、**配置**に求める: ペイロード（8 バイトの共用体 `LhatValueUnion`）
の列とタグ（1 バイト）の列を並走させる Structure of Arrays（`LhatSlots`）。

- **スタック**: 16 → 実質 9 バイト/枠（128KB → 72KB）。
  タグ列は 64 枠が1キャッシュ行に載る
- **テーブル配列部**: 同じ比率。データ量に比例して効く本命
- **コルーチンの退避レジスタ**: スタックと同じ形——yield^ の写しと
  捕捉の付け替え（5.7）が同じ座標系で動く
- 整数は 64 ビットのまま。ポインタも素のまま——NaN boxing の
  2つの棄却理由のどちらにも触れない

**切り分け**: `LhatValue` は値渡しの通貨として現状のまま
（ホスト API・`LhatRunResult`・`lhat_table_get/set`・チャンク定数は無変更。
ホスト呼び出しと多重定義の候補判定は arity 分だけ束ねて渡す）。
**まとまった格納**と、そこを指すものが SoA である:

- フレームの `base` はスタック添字である
- upvalue の `location` は **`LhatValueRef`**（ペイロード*・タグ* の対）——
  指し先は機械スタック・コルーチン退避バッファ・自分の closed セルの
  3種で、5.7 の付け替えは対ごと差し替える。open リストの整列は
  ペイロードポインタだけで足りる（機械のリストには機械スタック分しか
  載らない）
- 生の `LhatValue *` を長期に持つ場所は**存在しない**。格納への
  アクセスは `lhat_slots_get/set`・`lhat_ref_get/set` に限られ、
  誤った直接添字はコンパイルエラーになる

ハッシュ部（`LhatTableEntry` の対）は据え置き——探索がキー比較主体で、
分離の利得が配列部ほど立たない。詰めるなら別途。

#### 参照型へ寄せる案 — 検討したが保留［保留］

逆方向、すなわち **`number^` を値型から参照型（ヒープ上のオブジェクト）へ寄せる**
案も検討した。動機は表現の統一そのものではなく、次の非対称である。

```lhat
let^ a = 0
let^ f = p^ x { x += 1 }
f(a)                        # a は変わらない
let^ t = { a = 0 }
let^ f3 = p^ x { x.a += 1 }
f3(t)                       # t は変わる
```

`f3(t)` は呼び出し元に届くのに `f(a)` は届かない。初学者が `f(a)` の挙動から
`f3(t)` も変えないと誤って学ぶ懸念がある。

「変数はすべて参照」と一括して説明することはできない。
名前が何を意味するかは **指す値の型によって変わる**。効率のために真偽値と数値は
値型であり（参照している先が無い即値である。02 の 13.11 が `is^` について同じ
ことを別の角度から言う）、05 の 8.9 でユーザー定義の値型まで入った以上、
参照で一括して語る方針は維持できない。上の非対称は説明の不整合ではなく
**`number^` が値型であることの帰結** である。

ただし **参照型化だけでは解決しない**。`x += 1` は現状「新しい結果に再束縛」
であり、参照型になっても呼び出し元には届かない。届かせるには再代入・複合代入を
「束縛中のオブジェクトの値を書き換える」意味に変える必要があり、そうすると今度は
`var^ b = a` で1つのオブジェクトを2つの束縛が共有した場合に `a` の変更が `b` にも
及ぶ——数値が値として独立に振る舞うという、より基本的な前提が壊れる。
避けるには所有権の追跡が要る（02 の 15.1改 が「本体が作ったテーブルか」を
出自で判定しているのと同じ領域である。02 の 8.9 の `var^` / `let^` は
**名前** の側を語るもので、ここで要る所有権の追跡とは別の軸になる）。

費用の側も、NaN boxing を採らなかった理由がまさに指摘した
**算術演算のたびに割り当てが起きる**問題をそのまま呼び戻すことになる。
「束縛と再代入のときだけ box 化し、計算途中は今までどおり値型」という案は
成り立つが、演算経路の設計をやり直す必要がある。

加えて、徹底するなら `bool^` も同じ扱いにしなければ中途半端になる。

したがって **保留** とする。方向としては、`number^` が将来 int/double だけでなく
bignum や rational も内部表現に取りうる（書き手はそれを意識せず素直に数式を書けば
妥当な精度の結果が得られる）という構想と噛み合うため、閉じてはいない。

その前段として **`LHAT_OBJECT_NUMBER` と box/unbox の基盤だけを実装したものが
ブランチ `feature/number-boxing` に残してある**（`lhat_number_box` /
`lhat_number_unbox`、GC 統合、単体テスト）。`LhatValue` 自体・算術・比較・
テーブルキーはいずれも無改造で、どこからも生成されない。再開するならここから。

#### 表現の変更は表現の層に閉じる

仮想機械は **値を直接触らない**。
構成・判定・取り出しをすべてアクセサ経由にしておくことで、
表現形式の変更（SoA 化がそうだった）が表現の層に閉じる。

#### タグ

```text
nil^ / bool^ / 整数 / 実数 / string^ / t^ / サブルーチン / コルーチン / 誤り
```

整数と実数を別のタグにするのは 14.8 と矛盾しない。
**型はひとつ、表現はふたつ** である。

## 3. 型検査の厳格度

### 3.1 コンパイル単位ごとの設定とする

型検査の厳格度は **コンパイル単位ごとの設定** であり、言語の方言ではない。

- **strict** — 既定。型エラーをコンパイル時に報告する
- **relaxed** — 推論が決まらない箇所を動的として扱う

REPL の既定は relaxed、ソースファイルの既定は strict とする。
ただしどちらも切り替えられる。

- ファイルを relaxed でコンパイルできる（試作時に有用）
- REPL で strict を有効にできる（ファイルへ貼る前の確認に有用）

> **実装の現状**: `lhat_check_unit`/`lhat_check_next`/`lhat_program_init` は
> どれも呼び出し側が渡す `strict` 引数をそのまま `Checker.strict` に落とす
> 作りで、CLI（`cli/main.c`）がこの節どおりの既定と切り替えを持つ——
> ファイル実行（`--check`/`--run`）は既定 strict、プロンプトは既定 relaxed。
> `--strict`/`--relaxed` を書けばどちらのモードでも既定を上書きできる。

ソースに書く場所は無い（3.2）——厳格度は単位の性質ではなく、`lhat_program_init`
を呼ぶ**ホストの選択**である。単位をまたぐ合成で片方だけ厳格度を変える手段が無く、
それでよい。ツールに伝える口は `lhat_program_dump_host_api` の書き出す
`"strict"`（program.h）——lhatls はこれを読んで、自分自身は常に strict で
検査したまま、strict だけが報告する3つ（次項）の severity を relaxed 宣言の
ホストでは Warning に下げる（`lhat_unit_diagnostic_relaxed_ok`）。

#### strict が報告する範囲［実装済み］

3.4 の推論には、まだ埋まっていない箇所（相互再帰で相手側が未検査のまま
呼ばれた戻り値、注釈を省略したパラメータ、多重代入で値が足りなかった先
など）が一時的に生じる。これは「矛盾」ではなく「まだ何も言えない」箇所
であり、検査器の内部ではこれを一時的な印（未確定を表す型）として運ぶ。

その印が本体の中で自分自身の推論に使われる分には何も報告しない
（3.4 の相互再帰が前方宣言なしで書けるのはこのため）。

> **走査を終えてなお印が残っていれば、strict はそれを報告する。
> 翻訳単位に未決定の型を1つも残さない。**

決めたくない箇所には 02 の 13.7 の `any^` を書く。`any^` は
「何が来るかを言わない」と **書き手が書いた** ものであり、
検査器が決められなかったこととは別物である（3.5）。

報告する場所は次の3つである。

**① 推論した返り値型に、走査を終えてなお印が残った定義。**

```lhat
let^ a = f^ n:number^ {
    if^ n <= 0 { return^ true^ }
    return^ b(n)
}                                       # ← ここで報告する
var^ b = f^ x { return^ x }             # ← ここでも。x に要求が1つも無い
```

`b` が `var^` なのは例の都合ではない。`let^` で束ねたリテラルなら
`a` の中の `b(n)` が呼び出し形になり、3.4改4 が `b` をその形で検査して
何も残らない。形を集めない束縛——`var^`（別のサブルーチンを持ち得る）、
呼ばれないもの、`public^` のもの——だけが、ここに残る。

**返り値型は呼び手全員への約束である。** 穴のある約束は呼び出し1つごとに
穴を配るので、配る側で1度言う。使う場所が1つも無ければ誰も気づかない、
という状態を残さないためでもある。

書けば決まる。書く場所は 3.4改 の期待される署名でもよく、
束縛に書いた署名の返り値型はその場に書いたのと同じに働く。

**相互再帰そのものは報告の理由にならない。** 3.4改2 が輪を走査し直して
閉じるので、上の `b` のように **輪の外で決まらない** ものが在るときだけ
印が残る。

**② その印が具体的な型を要求する場所まで生き残って現れたとき。**

```lhat
let^ y : bool^ = a(4)                   # 合併の腕に埋もれていても報告する
```

`a` の返り値型は `bool^|印` であり、7 章 P6 が「合併の腕の印は
素通しさせない」と定めている。①で定義が既に報告されている場合でも、
ここは別の場所として報告する。

**③ 走査を終えてなお印が残った、注釈のないパラメータと束縛。**

```lhat
let^ f = f^ n -> number^ { return^ 1 }   # ← n に要求が1つも無い。報告する
let^ g = f^ n:any^ -> number^ { return^ 1 }   # 通る。書き手が書いた
```

パラメータも返り値と同じに扱う。**署名は呼び手全員への約束であり、
穴のある約束は引数側でも同じく穴である。** 要求が食い違って決まらなかった
場合も同じに扱う——決まらなかったことに変わりはない。

束縛も同じである。印が名前の持つ型まで届けば、その名前を読む側全員に
穴が配られる。

```lhat
let^ y = a(4)                            # a の返り値に印が残っていれば報告する
```

02 の 13.11「テーブル部分型が黙る位置」や 14.12 の `overload^` 解決の
実装上の限界など、**推論の隙間ではない**「言うことがないだけ」の箇所は
この報告の対象に含めない。検査器の中では前者を `unknown^`、後者を
未確定の印として別に持つ。

02 の 1.2 でコマンドインタプリタモードを
「ホストがランタイム生成時に指定する設定」としたのと同じ位置づけになる。

### 3.2 ソースの字面は変わらない

「静的**自動**型付け」は型推論であり、注釈は省略できる。
したがって **strict と relaxed でソースの書き方は一切変わらない**。

差は「型の誤りをいつ報告するか」だけである。
書き分けが発生しないため、2つの方言に分かれることがない。

### 3.3 段の数は減らない

relaxed でも段は減らない。
型検査の段が **寛容になる**（推論が決まらない箇所を動的とみなす）だけである。

1つの経路にフラグが1つ増えるという構成になる。

### 3.4 推論の範囲

どこまでを推論するかを次のとおり定める。

#### 返り値型は推論する

明示しなければ、本体の `return^` から推論する。

```lhat
let^ foo = f^{ return^0 }
```

これは次のように書いたのと同じ意味になる。

```lhat
let^ foo = f^ -> number^ { return^0 }
```

`return^` が複数あれば、それらの合併になる。

```lhat
let^ bar = p^x:number^ {
    if^ x > 0 { return^nil^ }
    return^foo()
}
```

これは `p^number^ -> nil^|number^ ;` と解釈される。

#### 脱出をすべて数える

返り値型を決めるのは `return^` だけではない。**本体の末尾から落ちる経路も脱出である。**

```lhat
let^ f = p^ b:bool^ {
    if^ b { return^ 1 }
}                          # b が偽なら値を作らずに抜ける
```

これは `number^|nil^` とする。値を受け取る位置で使われている以上、
落ちた経路には値がなく、**「無いこと」は 04 の 11.3 が既に `nil^` と綴っている**。
第三の表現を作る理由がない。呼び出し側は 02 の 11.7 の `??` か絞り込みで扱うことになる。

##### 裸の `return^` も同じ脱出である

値を伴わない `return^` は、**末尾から落ちるのと同じ脱出** である。
書く位置が違うだけで、実行時に呼び出し側へ渡るものは同じ `nil^` になる。

```lhat
let^ f = p^ b:bool^ {
    if^ b { return^ 1 }
    return^                 # 末尾から落ちるのと同じ。値を作らない
}                           # number^|nil^
```

したがって以下も同様に扱う。

```lhat
f^ -> number^ { return^ }   # 誤り。13.2 により関数は必ず答える
p^ -> number^ { return^ }   # 誤り。書いた型が値なしの脱出を許さない
```

##### `try^` が通す誤りも脱出である

04 の 5.3 の `try^` は、誤りを **今の本体から外へ出す**。
`return^` と同じ脱出であり、返り値型を書いていなければ推論した型に入る。

```lhat
let^ open = f^ -> number^|IOError { … }

let^ read = f^ { return^ try^ open() }     # number^|IOError
let^ run  = p^ { let^ n = try^ open() }    # IOError|nil^
```

`run` に値を作る `return^` は無いが、誤りを出す経路が在る。
上の「`nil^` が加わるのは他の脱出が値を作っている場合だけ」がそのまま働き、
**失敗しうる手続きは、失敗しうることが型に出る**。

5.3 が定めているのは **書いた返り値型がその誤りを含むか** である。
書いていなければ含むかどうかを問う相手が無く、通ったものが型になる。

##### 「値を返さない」とは別である

02 の 13.2 が **返り値のない署名の形**（`p^number^;`）を定めている。
値を返す `return^` が本体に1つもなければ、書き手はそもそも値を求めていない。
その場合は **返り値なしのままとし、`nil^` にはしない**。

```lhat
let^ log = p^ msg:string^ { print(msg) }     # p^string^; のまま
```

`nil^` にしてしまうと、11.7 の `??` が `log(m) ?? 0` のような無意味な式に効く。
04 の 2.1 が誤りをテーブルにしなかったのと同じ種類の混同になる。

> **`nil^` が加わるのは、他の脱出が値を作っている場合だけである。**

##### 「値がない」は型である

上の理由が成り立つには、**返り値なしの呼び出しが値として使えない** 必要がある。
そのため「値がない」を型として持つ。`unknown`（推論が及ばなかった）とは別物であり、
**逆に振る舞う** — `unknown` は何にでも適合して報告を起こさないが、
「値がない」は **何にも適合せず、何もそこに適合しない**。

```lhat
let^ log = p^ msg:string^ { … }    # p^string^;

log(m) ?? 0            # 誤り。11.7 の左が nil^ になりえない
log(m) catch^ 0        # 誤り。04 の 4.1 も同じ
var^ v = log(m)        # 誤り。名前は値を束縛する
v := log(m)            # 誤り。再代入も同じ
log(m) + 1             # 誤り。算術は number^ を要る
if^ log(m) { }         # 誤り。条件は bool^ を要る
f(log(m))              # 誤り。引数は値
return^ log(m)         # 誤り。return^ は値を運ぶ
{ a := log(m) }        # 誤り。テーブルの要素は値
t[log(m)]              # 誤り。添字は値
log(m) as^ number^     # 誤り。注釈をつける対象がない
pack^ log(m)           # 誤り。まとめる対象がない
log(m) .. "a"          # 誤り。連結する対象がない
yield^ log(m)          # 誤り。出す値がない
$"v={log(m)}"          # 誤り。穴に入る値がない

log(m)                 # 通る。8.2 のとおり呼び出しは文として単独で立つ
```

**値を要求する位置がそれぞれ言う。** 呼び出しの側では言えない —
8.2 が呼び出しを単独の文として認めており、
返り値のない手続きの居場所はまさにそこだからである。

13.7 の `any^` にも適合しない。`any^` は **あらゆる値** の頂点であり、
ここにあるのは値ではない。

注釈として書く形は設けない。13.2 が `p^string^;` という**署名の形**で既に表しており、
式の型としてのこれは推論からのみ生まれる。

自分自身を呼ぶ本体は例外になる。3.4 は結果が未定であることを
「まだ決まっていない」として読むので、**自己呼び出しはその未定を持ち回る**。

##### 関数 `f^` では脱落そのものが誤り

02 の 13.2 が **「関数は必ず返り値を持つ」** と定めている。
したがって `f^` の本体が末尾に到達しうる時点で、**答えを持たない経路がある**。

```lhat
f^ b:bool^ {
    if^ b { return^ true^ }
}                              # 誤り。b が偽のとき答えがない
```

```lhat
f^ b:bool^ {
    if^ b { return^ true^ }
    return^ false^             # 全経路が答える
}
```

`p^` は値を返さずに抜けてよいので、上の `nil^` の追加が働く。
**この違いが `f^` と `p^` の唯一の非対称になる。**

返り値型を書いた場合も同じで、`f^ -> bool^|nil^` と書いても脱落は誤りとする。
`nil^` を答えるなら `return^ nil^` と書く。
`f^` の本体は全域であることを規則にしたほうが、読み手が経路を数えなくて済む。

##### `p^` が返り値型を書いた場合

明示した型が値なしの脱出を許さなければ誤りとする。

```lhat
p^ b:bool^ -> number^      { if^ b { return^ 1 } }   # 誤り
p^ b:bool^ -> number^|nil^ { if^ b { return^ 1 } }   # 通る
```

##### 判定の限界

「末尾に到達しうるか」の判定は保守的である。ただし
**終わらない繰り返しは1つだけ見分ける**。

##### 境界のない `repeat^` は脱出である

02 の 16.5 の `repeat^{ … }`（回数も条件も持たない形）は、
**それを抜ける `break^` が書かれていなければ終わらない**。
続く文に制御が届かないので、`return^` と同じく脱出として数える。

```lhat
f^ -> number^ { repeat^ { } }            # 通る。末尾に到達しない
f^ -> number^ { repeat^ { return^ 1 } }  # 通る。同上
f^ -> number^ { repeat^ { break^ } }     # 誤り。break^ の後は末尾
```

`break^` の探索は 02 の 9.8 に従う。多段の `break^[名前]` は提案のままで
処理系が拒むため、`break^` は常に最も内側の繰り返しを抜ける。
したがって **内側の繰り返しや入れ子の本体に書かれた `break^` は数えない**。
`for^ … if^` と `for^ … when^` は 16.3・17 章のとおり繰り返しではないので、
その中の `break^` は外側のものとして数える。

##### まだ保守的なもの

- `for^ … to^` `while^` `until^` `in^` — いずれも自然に終わりうる。
  中でしか `return^` しない本体は、末尾に到達しうると見なす
- `repeat^ while^ true^` — 条件が定数であることを畳んでいない
- 決して成立しない条件の下にある `break^`

これらを詰めるには到達可能性の解析か `never` に相当する型が要る。
いまは持たせていない。境界のない `repeat^` だけを見分けているのは、
**構文の形だけで決まり、解析を持ち込まずに済む** ためである。

#### 再帰は推論できる

> **返り値型は脱出の型の合併である。ただし
> 「求めようとしている型そのもの」を返している脱出は数えない。**

```lhat
let^ fact = f^ n:number^ {
    if^ n <= 1 { return^ 1 }        # → number^
    return^ n * this^(n - 1)        # 型は求めようとしているもの → 数えない
}
```

`number^` に決まる。注釈は要らない。
最小不動点をとれば消える項であり、合併に入れても情報が増えない。

##### 「再帰を含む脱出」ではなく「型が決まらない脱出」［重要］

落とす条件は **再帰呼び出しを含むこと** ではない。**その脱出の型が決まらないこと** である。

```lhat
let^ f = f^ x:number^ {
    if^ x > 1 { return^ "a" .. this^(x - 1).to_s() }   # 型は string^
    return^ 1                                       # 型は number^
}
```

`this^` を含んでいても、**この脱出の型は自分の返り値型に依存していない**。
`"a" .. …` は何を連結しても `string^` である。
落としてしまうと `number^` になり、**`string^` を返す経路が型から消える**。

正しくは `f^number^ -> number^|string^;` になる。

したがって規則は次になる。

> 再帰する脱出は、**その型が「まだ決まっていない」場合にのみ** 数えない。
> 決まっているなら、再帰を含んでいても合併に加える。

##### 脱出がすべて再帰なら誤り

```lhat
let^ f = f^ n:number^ { return^ this^(n - 1) }
```

**この本体は値を作れない。** 誤りとする。

これが静的に言えるのは、02 の 12.8 が例外機構を持たず、
5.6 が巻き戻しを持たないためである。**脱出の列挙が完全になる。**
`return^`、末尾からの脱落、`try^` が返す誤りしかない。

##### 走査は1回だけ［暫定］

本体は1度しか読まない。再帰呼び出しの型は、その1回の間ずっと「決まっていない」とする。

これは最小不動点の **1回目の反復** にあたる。
上の2つの例はどちらも1回目で不動点に達している。

2回目を要する形は書ける。

```lhat
let^ f = f^ x:number^ {
    if^ x > 1 { return^ { value := this^(x - 1) } }
    return^ 1
}
```

1回目では内側が決まっていないため、合併に「決まっていない部分を含む型」が入る。
反復を重ねると型が育ち続けるため、**そもそも不動点に達しない**（等再帰型が要る）。

反復を回す設計もありうるが、回数の上限と打ち切りの規則が要る。
**自分を呼ぶ1つの本体についてはいまは1回**とし、決まらない場合は返り値型を書く。
名前どうしが輪になっている場合——`def^` のメンバも、並んで書かれた `let^` も——は
下の 3.4改2 が反復を回す。

##### 再帰する脱出の型検査

数えなかった脱出については、**その式の型検査も行われない**。
返り値型が確定するのは本体を読み終えた後であり、
その時点で本体を読み直す仕組みを持たせていない。1回だけ読む上の決定の裏返しである。

#### 3.4改2 輪になった名前は答えが変わらなくなるまで走査する［重要］

`def^` のメンバの本体を歩く巡（02 の 14.7改 の2巡目）と、
**文の並びを歩く巡**は繰り返す。

```lhat
let^ R = def^{
    self^{ … },
    expr   := p^self^ { … self^.term()   … },
    term   := p^self^ { … self^.factor() … },
    factor := p^self^ { … self^.expr()   … },
}

let^ a = f^ n { if^ n <= 0 { return^ true^ } return^ b(n - 1) }
let^ b = f^ n { if^ n <= 0 { return^ false^ } return^ a(n - 1) }
```

**輪はどの順に書いても、どれか1つは自分より後のものを読む。**
その読みが答えるのは置かれた印であって、推論した型ではない
——`def^` なら 14.7改 の1巡目の仮置き、文の並びなら 8.7 が名前を集めた印。
次の巡が **前の巡の推論した型を種にして** 同じ本体を歩き直せば、輪は閉じる。

> **走査は、答えが変わらなくなるまで繰り返す。**

- **繰り返さない条件** — 1巡目が印を1つも読まなかったなら、その1巡が既に厳密であり、
  次の巡は同じことを言うだけである。前方参照の無い並びは1巡で終わる
- **打ち切る条件** — ある巡がすべてについて前の巡と同じ型を答えたら、そこが不動点である
- **上限** — 要素の数 + 1。読み先が決まれば読み手も決まるので、
  鎖なら長さの分の巡で足り、もう1巡が「変わらない」ことを確かめる

##### 種からは穴の腕を落とす［重要］

文の並びでは、印が **型の中に入り込む**。`a` の返り値は `bool^|印` になり、
2巡目に `b` の1巡目の型（これも `bool^|印`）を読めば、
答えは何巡回しても `bool^|印` のままで腕が消えない。

だから **巡と巡の間、種にするときに穴の腕を落とす**。
`bool^|印` を種 `bool^` にして2巡目を歩けば、`a` も `b` も `bool^` に落ち着く。

**落とすのは種だけで、答えは毎巡まるごと作り直す。**
`b` が本当は `string^` も返すなら、2巡目の `a` は `bool^|string^` になる
——落とした腕が本当に在るものなら、本体から読み直されて戻ってくる。
最後の巡の答えに穴が残っていれば、それは本当に決まらなかったということで、
3.1① がそこで報告する。

##### 巡の言い分は最後のものだけが残る

各巡は同じ本体を歩き、同じことを言い直す。
そのままでは輪の中の誤りが巡の数だけ報告される。
**巡を始めるとき、前の巡が出した診断と名前解決（07 の 4 章）は捨てる。**
残るのは最後の巡——最も型の決まった巡——の言い分だけである。

##### 上限で切れたときは決まらないままにする

「型が育ち続ける」形は、巡を重ねても不動点に達しない。
上限で切り、決まらなかったものは 3.1・3.5 の落とし先に落ちる。
**決まらなければ書く** という線はここでも変わらない。

```lhat
loop := p^self^ { return^ self^.loop() },              # 決まらない
loop := p^self^ -> number^ { return^ self^.loop() },   # 書けば決まる
```

##### 巡は2つ在り、骨組みだけを分け合う

`def^` の走査と文の並びの走査は、別の物を回している。

| | 回す対象 | 種の置き場 | 巡の間にすること |
| --- | --- | --- | --- |
| `def^` | 1つの `def^` の entry | 定義とインスタンスのメンバ | 仮置きに戻す |
| 文の並び | 1つの文の並び | スコープの束縛 | 8.7 の印を降ろす・種から穴の腕を落とす |

同じなのは **巻き戻し・上限・打ち切り** だけで、そこだけを共有する。

`def^` の走査を文の走査に畳むことはできない。`def^` の型は歩くたびに
作り直されるので、文の巡が `let^ R = def^{…}` を歩き直しても2巡目は
前巡の型を見ない。前巡の型を種にするには束縛が要るが、
14.9 の名前の付かない `def^`・テーブルリテラルの中・引数として書いた `def^`
には束縛が無い。それらの輪も今は閉じている。

##### 文の並びで二度目を打たせないもの

`def^` の entry はメンバの型を作るだけだが、**文は型を作る以外のこともする**。
歩き直すとき、次の3つは1巡目のものが既に在るので、二度目を打たない。

- 8.7 が名前を集める巡（`collect_bindings`）は巡の外で1度だけ。
  「同じスコープに2度書いた」の報告はそこが言う
- `import^` が束ねた名前・8.8 の path が生やしたメンバは、
  2巡目には在る。**自分の1巡目を再定義と読まない**
- 8.7 の「まだ届いていない」印は巡ごとに降ろす。
  降ろさなければ、定義より前に使った誤りが2巡目に消える

#### 引数型は本体の要求から推論する

**他所の呼び出し側は、要求としては1つも見ない。** 逆算の範囲を本体（と、下記の
「期待される署名」）に限れば全域推論にはならず、
読み終えれば決まるという点で、返り値型の推論とまったく同じ性質を持つ。
単位の中の呼び出しは、要求とは別の道具——3.4改4 の**呼び出し形**——で読む。
単位の外（`public^` の名前の呼び手）は、要求でも形でも読まない。

> **注釈のない引数の型は、本体がその引数に課した要求の交差である。**

```lhat
let^ f = p^ x { return^ x + 1 }        # p^number^ -> number^;
let^ g = p^ x { x.write("a") }         # p^t^{ write : p^string^; };
```

##### 単一化ではない［重要］

Hindley-Milner の型推論とは別物である。あちらは等式を解いて主要型を1つ出す。
02 の 13.5 の合併・14.5 の交差・11.3 の構造的な部分型付けがあると、
**主要型がそもそも存在しない場合がある**。等式は解けない。

ここでやるのは **要求を集めて交差すること** だけである。等式を立てず、変数を解かない。
11.3 が構造的であることは障害ではなく前提である。
`x.foo` が課す要求は `t^{ foo : … }`、すなわち 14.10 の「少なくともこれらを持つ」であり、
**テーブル型がそのまま要求の形になっている**。公称的な型ならこれが書けない。

##### 何が要求になるか

要求は、既に型が分かっている側から読める。

- `x + 1` — その演算子を**書ける型の合併**を要る。`x` の位置は受け手
  （14.4 の `self^`）。3.4改3 が下でこれを述べる
- `if^ x` `x and^ y` `!x` — 条件は `bool^`
- `x.foo` — `t^{ foo : unknown^ }`。14.10 の「少なくともこれらを持つ」がそのまま要求になる
- `g(x)` — `g` の引数型が既に分かっているなら、それ
- `let^ y : T = x` `y := x` — 書いてある型
- `return^ x` — 返り値型を書いてあるなら、それ
- `x .. y` — **要求にしない**。11.2 が `..` に連結と定義の合成の両方を持たせており、
  どちらの要求かが左辺の型で決まる。まだ決まっていない側からは読めない

##### 3.4改3 演算子の要求は候補から作る［重要］

> **演算子が課す要求は、その演算子を書ける型の合併である。
> 候補が1つならその型そのものになる。**

候補は3種類しかない。

- **11.8 の組込みが持つもの** — 演算子の名前ごとに違う。算術は `number^`、
  `..` は `string^`、`<=>` は **`number^` と `string^` の両方**（11.9）
- **その単位が `op^` を書いた型** — 単位が頂点で束縛した `def^` のうち、
  その名前の `op^` を持つもの
- **その単位が `import^` した登録型** — ホスト値（05 の 8.9）も
  ホストデータ（8.8）も、演算子を普通のメンバとして持つ。11.3 のとおり
  判定は構造的なので、登録されたものと `op^` で書かれたものは
  引き当てで区別されない

どれも無い単位では候補が組込みだけなので、要求は `number^` になる。
**これは従来の答えそのものである。**

```lhat
f^ x, y { x + y }       # f^number^, number^ -> number^;
```

`op^*` を書いた型が単位に在れば、候補が増える。

```lhat
let^ A = def^{
    self^{ a := 0 },
    op^* := f^self^, rhs:number^ -> Self^ { … },
    overload^op^* := f^lhs:number^, self^ -> Self^ { … },
}

f^ x, y { x * y }       # f^A|number^, A|number^ -> A|number^;
```

位置ごとに合併する。11.3改 の `self^` 末尾の腕は反対の順序を述べているので、
その受け手は**右**に立ちうるものとして数える。

##### 相手側が決まっているなら、そこで絞る［重要］

> **候補のうち、相手側を受けられる腕だけを数える。**

絞ってから合併する。絞らなければ、組込みしか無い単位でも `<=>` の候補が2つ
あるために順序が軒並み合併になってしまう。

```lhat
f^ x -> bool^ { return^ x < 1 }     # 相手が number^ → 候補は number^ だけ
f^ x -> bool^ { return^ x < "s" }   # 相手が string^ → 候補は string^ だけ
```

算術も同じである。`op^*` が `string^` しか取らない型が単位に在っても、
`x * 2` の候補は組込みだけに絞れる。

##### 順序は `<=>` の候補を要求する

`<` `>` `≦` `≧` は 11.9 のとおり `<=>` から読むので、要求もその候補である。

```lhat
f^ x, y -> bool^ { return^ x < y }  # どちらも未決 → 合併。本体は誤り
```

**`=` と `≠` は要求しない。** 11.9 のとおり**等価は `<=>` が無くても答える**
——14.2 がテーブルの同一性を定めており、`<=>` はそれを精密にするだけである。
だから `x = 1` が要るのは「相手と互いに素でないこと」であり、それは型ではない。
`number^` と互いに素でない型は `number^`・`any^`・`number^` を含む合併…と
有限の合併に畳めないので、**要求として書けない**。

11.9改 の `op^=`（順序を持たない型が同値だけを定める形）はこの集合を広げる側
であって、要求可能な形には近づけない。候補は**演算子名ごと**に持つので、
`op^=` だけを書いた型は `=` の候補であって `<=>` の候補ではなく、
**順序には混ざらない**——11.9改 の「`s < t` は誤り」がそのまま残る。

##### 合併になった本体は誤りだが、行き先を示している［重要］

`x : A|number^` は演算子を持たないので、その本体の `x * y` は
**どちらの演算子か定まらない**と報告される。

> **それでよい。署名が候補を名指しているので、書き手はそこから選べる。**

選び方は2つある。どちらも既にある道具である。

```lhat
f^ x:A, y { x * y }            # 注釈して1つに決める
```

```lhat
f^ x:A|number^ -> string^ {    # 合併のまま受けて、本体で絞る（13.11）
    if^ x fits^ A { return^ (x * 2).show() }
    return^ (x * 2).tostring^()
}
```

要求を作らずに 3.1③ へ渡す形は採らない。**候補を捨ててしまうと、
書き手はどの型を書けばよいかを自分で探すことになる。**

##### 見るのはこの単位が名指せるものだけである

`require^` した先が `op^` を書いていても、ここの推論は曖昧にならない。
**署名の意味が、それが書かれたファイルを読めば分かる状態を保つ**ためである。

`import^` は線の反対側にある。取り込みはその単位に書いてあるので上の
条件を破らず、05 の 8.7 のとおりホストの登録簿は**単位が検査される順序に
依らない**——`require^` を締め出している理由が当たらない。したがって
**取り込んだモジュールの登録型は候補に数える**。取り込んでいないものは
数えない（05 の 8.1）。

その結果、`import^` した先が `+` を持つ単位では `f^ x, y { x + y }` が
「どちらの演算子か定まらない」になる。**それでよい**——下の
「合併になった本体は誤りだが、行き先を示している」がこの場合であり、
組込みだけで候補が2つある `<` は最初からそう振る舞っている。

##### 位置には依らない

8.7 が名前を単位全体で見えるようにしている以上、`A` の定義より前に書かれた
本体も同じ答えでなければならない。候補は歩く前に構文から集める。

##### なぜメンバのように構造を要求しないのか［補足］

`x.foo` は `t^{ foo : … }` を要求する（上のとおり）。11.3 は演算子もメンバだと
定めているので、`x * y` も `t^{ "*" : … }` を要求してよさそうに見える。
できない理由が2つある。

- **型の側に演算子の鍵を書く文法が無い。** `t^{ … }` のメンバの鍵は識別子であり、
  `t^{ ["*"] : … }` とは書けない。14.16 が `.signature` を型注釈として
  読み戻せることを要求している以上、書けない型を推論するわけにいかない
- **`number^` はテーブルではない。** 構造要求にすると、算術のいちばん普通の
  相手が満たせなくなる

##### 3.4改 期待される署名も要求になる［重要］

> **その場所が「どんな署名を期待しているか」が分かっているなら、
> 注釈の無い引数はそこから型を取る。**

期待は、**書かれた型がその場所に既に立っているところ**すべてから来る。

```lhat
# 1. 束縛に書いた署名
let^ f : p^string^ -> number^; = p^ x { return^ x.length }

# 2. 書いたその場での呼び出し
let^ n = p^ x { return^ x.length }("abc")

# 3. 呼び出しの引数——その位置の仮引数の型が期待になる
let^ ff = f^ a:number^, b:string^, g:f^number^, string^ -> bool^; { g(a, b) }
ff(1, "s", f^ c, d { c > 0 })          # c は number^、d は string^

# 4. 同じ理由で、書かれた返り値・名前が持っている型・書かれた既定値の位置
let^ mk = f^ -> f^number^ -> bool^; { return^ f^ x { x > 0 } }
cb := f^ y { … }                        # cb が持っている署名から
let^ take = f^ g:f^number^ -> bool^; = f^ z { … } { g(1) }
```

**期待された型は、そこに注釈が書いてあったのと同じに働く。**
本体の要求はその型に対して検査され、規則が1つ増えるわけではない。

引数だけでなく **返り値型も期待から取る**。`-> T` をその場に書いたのと
同じであり、本体は推論する代わりにその型に対して検査される。
書いた署名が「書いたもの」として働かなければ、3.1 が返り値型を書けと
言ったときに **束縛に書く道が塞がっている**ことになる。

2 が「呼び出し側を見ない」に反しないのは、**その呼び出しが同じ式の中にある**
からである。上の規則が避けているのは「**他所の**呼び出し元が署名を決める」
ことであり——それを許すと、誰が呼んでいるかで署名が変わり、
05 の 6.2 が要る「相手の本体を検査せずに署名を読める」が崩れる——
書いたその場での呼び出しはそこにあたらない。読む範囲は式を出ない。

3 が反しないのは **向きが逆** だからである。決まっているのは呼ばれる側の
書かれた署名であり、それがその場に書かれたリテラルへ流れる。呼ばれる側の
署名は本体を検査せずに読めるものなので、6.2 はそのまま立っている。
C# のラムダ（`.Where(x => …)` の `x`）が型を書かずに済むのと同じ仕組みで、
決めているのは呼び出し元ではなく `Where` の側の署名である。

```lhat
var^ g = p^ x { … }
g(5)          # ここは要求にならない。x は決まらないまま
```

（`let^` なら 3.4改4 の呼び出し形がこれを決める。要求に**ならない**ことは
変わらない——決め方が違う。次節と 3.4改4 がその線を引く。）

**多重定義（02 の 14.12）では取らない。** どの腕を呼んでいるかは引数の型で
決まるので、引数を読む時点で位置が1つに定まらない。注釈を書くことになる。

`...` で撒く形（13.7）でも取らない。位置が仮引数と1対1に並ばないためである。
受け手（02 の 14.4）を書く形では、受け手の位置だけを外して残りを並べる
——ずれが何個ぶんかは書き方から分かる。

##### 3.1③ もこれで満たされる

束縛に署名が書いてあれば、引数も返り値もそこで決まる。
決めるものが他に無い形だけが残る。

```lhat
let^ f : p^string^ -> string^; = p^ x { return^ x }   # 通る
let^ g = p^ x { return^ x }                           # 誤り。x を決めるものが無い
```

##### 呼び出しは要求にしない

`x(1)` は `x` の型を、**要求としては**決めない。
**呼び出し1箇所からは署名が決まらない** ためである。

13.1 の署名は `f^` と `p^` の別を含み、13.2 が返り値なしを署名の形として持つ。
適合はそこまで問う（15.1 が `f^` から `p^` を呼ぶことを禁じる以上、両者は入れ替わらない）。
`x(1)` から読めるのは引数の並びだけであり、
**残りを埋めた署名を要求にすると、正しい引数を渡している呼び出し側を拒む**。

メンバも同じで、`x.foo(1)` の要求は `t^{ foo : unknown^ }` に留める。
`foo` を呼んでいることは分かるが、その署名は決まらない。

書き手が呼び出せる引数を求めているなら、その署名を書くのが早い。

呼び出しを閉め出すのはここまでで、閉め出したのは「要求に**する**」こと
——集めて交差し、1つの署名に畳むこと——である。3.4改4 は同じ呼び出しを
**形**として読む。形は交差されない。1形ごとに本体を1度歩く。

##### 3.4改4 単位の中の呼び出し形で本体を検査する［重要・実装済み］

> **`let^` が束ねたリテラルに注釈のない引数が残るとき、
> 単位の中の各呼び出しが渡している引数型の並び（形）を記録し、
> 本体をその形ごとに1度ずつ検査する。**

```lhat
let^ same = f^ want, used {              # 注釈なしで strict を通る
    for^ i from^ 1 to^ 9 {
        if^ want[i] != used[i] { return^ false^ }
    }
    return^ true^
}
let^ ok = same(want, r.used)             # ← この形が same を決める
```

`want[i]` は要求を立てない位置（13.11 のテーブル部分型が黙る位置）なので、
本体の要求だけではこの `same` は決まらず、3.1③ が注釈を求めていた。
呼び出しは形を持っている——それで検査すれば、書くはずだった注釈と
同じものがそこにある。

**仕組みは 3.4改の期待の再利用である。** 形はその位置に注釈が書いて
あったのと同じに働き、形ごとの走査は要求を集めない（決まっているものに
要求は要らない）。走査は 3.4改2 の反復に乗る：呼び出しが形を記録して
もう1周を求め、次の周で定義側が形ごとに本体を歩く。

- **呼び出しごとの答えは、その呼び出しの形のもの。**
  `id(1)` は `number^`、`id("s")` は `string^` を受け取る——
  合併に畳んだ答えを配ることはしない
- **残る署名は形の合併。** 束縛が持つ型・コンパイラが読む刻印は、
  記録された全形の位置ごとの合併で最後に1度歩いた結果である。
  形が1つなら合併はその形そのもの——単相の署名を書いたのと変わらない
- **本体が形を取れなければ、呼び出しの側で報告する**
  （`LHAT_CHECK_ERR_SHAPE_REFUSED`）。直すのは呼び出しか注釈であり、
  どちらも書くのは呼び出し側・宣言側の書き手である。形ごとの走査が
  本体の中に残した報告は、3.4改2 の周回と同じに巻き戻す
- **`this^` の再帰は形にならない**（束縛の呼び出しではない）。
  記録済みの1形の下で、返り値の再帰推論が従来どおり閉じる

**形を集めない束縛。** 集めるのは「その名前がこのリテラルを指し続ける」
と言える場合だけである。

- `var^` — 別のサブルーチンを持ち得る
- `public^` — 公開された署名は他の単位の呼び手への約束であり、
  **この単位の呼び出しが約束を狭めてはならない**（05 の 4.3）。
  公開名は本体の要求（と書いた注釈）だけで決まる
- 受け手（14.4）・可変長（13.7）を持つ署名 — 引数が仮引数と1対1に
  並ばない形は、3.4改が即時呼び出しで断るのと同じ理由で断る
- 引数の数が合わない呼び出し・型がまだ確定しない引数を持つ呼び出しは
  形として記録しない（後者は周回が戻って来てから記録される）
- 注釈のない引数を持つリテラルをその場に書いた引数 — その注釈は
  収集中の形からしか来ないので、循環する。全引数に注釈のある
  リテラルはそのまま形に乗る

**呼ばれないものは従来どおり残る。** 形が1つも無ければ 3.1③ の報告が
立つ——これが relaxed との関係も決める：3.4改4 は報告を**減らす**だけで、
relaxed が黙認していたものに新しい声を足さない（形の拒否は別で、
あれは両設定で言う本物の型誤りである）。

**単位の境界は越えない。** `require^` は依存順に検査する（相手が先に
閉じる）ので、公開名に他の単位の形が届く道はそもそも無い。05 の 6.2
「相手の本体を検査せずに署名を読める」はそのまま立つ——単位の中では
検査器はどのみち本体を持っている。それが線の引き所である。

要求が1つも集まらなかった引数は、**注釈が書かれなかったときと同じ扱いに留める**。
推論が決めたのではなく、決められなかったからである。

- **strict** — 3.1 のとおり「誰も書かなかった制約」として報告する
- **relaxed** — 黙認する（3.5）

要求が食い違って決まらなかった場合も同じに扱う。

`any^` にはしない。3.5 の最後が述べたとおりで、`any^` の値は絞り込むまで何もできず、
**書き手が何も書いていないのに絞り込みを強いることになる**。

##### 絞り込みの下の使用は数えない［重要］

```lhat
let^ f = p^ x {
    if^ x fits^ number^ { return^ x + 1 }
    return^0
}
```

`x + 1` は `number^` を要求しているが、これは **絞り込んだ後の `x`** への要求である。
引数そのものへの要求にすると `p^number^` になり、
**絞り込みを書いた意味が消える**（13.11 は合併を絞るために書かれる）。数えない。

引数の型は決まらず `unknown^` になる。`fits^` はそれを絞る。整合している。

##### 条件の下の要求は、矛盾しない限り足す

必ず通る経路が課した要求だけを交差する。分岐の中の要求は、
**それまでの交差と食い違わない場合にのみ** 加える。

```lhat
let^ f = p^ x {
    let^ n = x + 1                     # 無条件 → number^
    if^ b { x.write() }                # number^ と食い違う → 加えない
    return^ n
}
```

`p^number^` になる。`if^` の中は別に誤りとして報告される。
交差してしまうと 14.12 の意味で空になり、**引数に何を渡しても通らない型** ができる。

分岐しか要求がない場合は、それらの交差をとる。

```lhat
let^ f = p^ x {
    if^ b { return^ x + 1 }
    return^ x * 2                      # どちらも number^
}
```

食い違えば決まらなかったものとして扱う。使用箇所どうしの矛盾は
それぞれの箇所が自分で報告し、**引数の型が決まらなかったことは
3.1③ がその引数で報告する**。言っていることが違うので、両方出てよい。

##### 入れ子の本体からの要求も数える

```lhat
let^ f = p^ x {
    let^ inner = p^ { let^ n : number^ = x + 1 }
    inner()
}
```

`x` は `number^` になる。`inner` がいつ呼ばれるか、あるいは呼ばれるかどうかは分からない。
だが **呼ばれたときに要るものは、渡された値が満たしていなければならない**。

呼ばれないかもしれないことを理由に落とすと、`f("a")` が静的に通り、実行時に壊れる。
分岐の下の要求（上）とは事情が違う。あちらは **他の経路が別のものを要求している** 場合の話であり、
こちらは要求が1つしかない。

##### 引数への再代入で収集は終わる

```lhat
let^ f = p^ x {
    x := "a"
    return^ x .. "b"                   # 引数への要求ではない
}
```

`x := …` より後の使用は、渡されてきた値に対する要求ではない。そこで収集を打ち切る。

##### 総称型がないことの帰結［重要］

```lhat
let^ id = f^ x { return^ x }
```

**要求が1つもない。** `unknown^` になる。OCaml なら `'a -> 'a` になるところである。

L^ に総称型はない（02 の 13.7 の可変長、04 の 7 章）。ここは埋まらない。
**引数を素通しする関数・容器・高階関数は推論の当たりが悪い。**
書き手が `any^` と書くか、具体的な型を書くことになる。

この形は **strict では 3.1 の①に落ちる**。引数がそのまま返るので
返り値型も印のままであり、呼び手は答えの型を知らされない。
`f^ x:any^ { return^ x }` と書けば消える——上の「書くことになる」は、
strict では書かないと通らない、という意味である。

推論が効くのは要求が具体的な型に落ちる場合だけである。
これは OCaml のオブジェクト型が `< foo : 'a; .. >` を推論するのと同じ範囲であり、
**行多相にあたる部分は 14.10 のテーブル型が既に持っている**。持っていないのは型変数のほうである。

##### 走査は1回だけ［暫定］

返り値型と同じである。本体は1度しか読まない。
読んでいる途中の引数の型は「まだ決まっていない」であり、
**その位置の検査は要求を積むことで代える**。読み終えた時点で交差が確定する。

引数の型が確定した後で本体を読み直す仕組みは持たせていない。
再帰と同じ理由であり、同じ制限を受ける。

### 3.5 relaxed の緩さ

> **relaxed が動的にするのは、推論が型を決められなかった箇所だけである。
> 静的に矛盾と分かるものは strict と同じく報告する。**

`1 + "a"` のように、推論が両辺の型を決めたうえで矛盾している場合、
relaxed でもコンパイル時の誤りになる。**型検査を切る設定ではない。**

#### 3.1 の3つはここで黙る

3.1 の①②③——決まらなかった返り値・その印が届いた場所・決まらなかった
引数と束縛——は、どれも「まだ何も言えない」箇所であり、矛盾ではない。
relaxed はこれを黙認する。

```lhat
let^ f = f^ n -> number^ { return^ 1 }
f("何を渡してもよい")            # relaxed では通る。strict では n が 3.1③
```

黙認した箇所は実行時に落ちる（「検査の挿入は行わない」参照）。
**書き方は変わらない**（3.2）。変わるのはいつ言うかだけである。

公開されているかどうかで扱いを分けることもしない（05 の 4.3）。

#### 理由

4.1 の「保証は一方向」が意味を持つのはこの読みのときである。

relaxed で通ったものが strict で落ちる理由が **注釈が足りないことだけ** に限られるなら、
relaxed は strict への踏み台として働く。
矛盾まで通してしまうと、relaxed で動いていたものが strict で大量に落ちることになり、
移行の道のりが長くなる。

3.2 のとおり **strict と relaxed でソースの字面は変わらない**。
字面が同じものの意味が大きく違うと、
どちらで書かれたかを読み手が意識しなければならなくなる。

#### `any^` との関係［重要］

02 の 13.7 が `any^` を **頂点型であり、絞り込むまで何もできない** と定めた。
これと relaxed は **別の機構である**。役割は重ならない。

- **`any^`** — 書き手が「何が来るかを言わない」と宣言する。
  静的に安全であり、使うには絞り込みが要る
- **relaxed** — 検査器が決められなかった箇所を **黙認する**。
  書き手は何も書かない

一言でいえば、**`any^` は「何が来るか言わない」、relaxed は「今は確かめない」** である。

したがって **relaxed は決まらなかった型を `any^` に書き換えるのではない**。
書き換えると、`any^` の値には絞り込みなしで何もできない以上、
**relaxed のほうが strict より厳しくなる**。それは設定の意味と逆である。

#### 検査の挿入は行わない

relaxed が黙認した箇所で実際に型が合わなければ、
仮想機械の汎用命令（5.1）が踏んだその場所で panic する
——行番号と演算子名を持って（04 の 11.6）。それが relaxed の答えのすべてである。

理由は費用対効果にある。挿入検査が守るのは「失敗が原因から離れた場所で
出る」ことだけであり、relaxed——動的に書きたいときの設定——では
それは普通の動的言語の日常であって、守る価値より検査の実行時費用が上回る。
静的検査を通った箇所からは検査を **省きたい** のであって、増やしたいのではない。

なお、境界に検査を置く仕組み自体には別の使い道が残っている：
5.1 の特殊化命令（タグ検査を省いた命令）を strict のコードに入れるには、
未検証の値が入ってくる境界だけはどこかで実物を見る必要がある。
強制されない型は最適化に使えない——TypeScript の型を V8 が読まないのと
同じ理由である。**それは strict の性能の話であり、relaxed の安全の話ではない。**
特殊化を設計するときに、改めて起票する。

## 4. ファイルと REPL の一致

### 4.1 保証は一方向になる

02 の 3.4 は、貼り付けたコードがファイルに書いたときと同じ動作をすることを
保証すると述べた。01 の 10.9 を採った理由の一部でもある。

厳格度に既定の差を設けると、この保証は **型のレイヤで一方向になる**。

- **保証される**: strict で通るコードは relaxed でも同じく動作する
- **保証されない**: relaxed で動いたコードが strict で通るとは限らない。
  型の誤りを含んだまま、その経路を実行しなかっただけかもしれない

TypeScript と JavaScript、mypy と Python が持つ非対称性と同じものである。

### 4.2 構文と意味は分岐しない

厳格度が変えるのは **診断の時期だけ** であり、次はいずれも変わらない。

- 字句解析の結果
- 構文木の形
- 実行時の意味

02 の 3.4 が扱っていた「同じテキストが場所によって違う構文木になる」種類の問題は、
厳格度の設定によっては生じない。

#### 4.2改 同じことは同じ形で持つ［重要］

検査器と機械が同じ問いに違う答えを出すのは、**別の形で持っている**
ときに起きる。片方が写しを作り、もう片方がリンクを辿れば、写した
時点から先の食い違いは全部そこから出る。

02 の 14.7改2 の `delegate^` と 05 の 8.8改 のホスト型の基底が
その例である。機械は**リンク1本**（委譲キー、タグの基底）を持って
引くときに辿る。検査器も**同じくリンク1本**を持って同じ順に辿る。

> **写しを作らない。持ち方を合わせる。**

写した場合の代償は2つあり、どちらも実際に出た。

- **ずれる。** 委譲を写していた頃、写す側だけが知らない規則
（合成でどちらの委譲が残るか、メンバ本体からも引けるか）が
何度も食い違いを生んだ
- **重い。** 1クラス数百メンバのバインドでは、ラッパの数 ×
メンバ数の表が検査のたびに組み上がる。1.1 で検査は保存のたびに
走るので、それは書き手が待つ時間になる

「見え方」はリンクを辿って作ればよい——02 の 14.16 の書き出しも
`typeof^` の記述子も、写しではなく**引き**の結果である。

### 4.3 機械は呼び出し側のものである

REPL は **1つの機械が複数の入力に答える** 形をとる。
したがって機械は実行に属するのではなく、**呼び出し側が保持する対象** とする。

- `lhat_machine_new` / `lhat_machine_dispose` — 機械の生成と破棄
- `lhat_run(機械, proto)` — その機械で1つの入力を走らせる

スタックとフレーム配列を抱えるため実体は大きく、ヒープに置く。
静的に1つ持つ形は、**呼び出し側が1つに限られ、入れ子にもできない**ため採らない。

#### ヒープは機械が持つ

プログラムが確保したものは機械に属する。
実行の答えがテーブルや文字列でありうる以上、
**次の入力からそれに手が届く必要がある** ためである。

各実行が新たに始めるのはスタックとフレームだけである（5.2、5.4）。

#### 所有の模型は1つだけ

**実行の結果は何も所有しない。** 答えが有効なのは、
その機械が破棄されるか次を走らせるまでである。

「機械を内側で作って1回だけ走らせ、ヒープの所有を呼び出し側へ渡す」形も
考えられるが、**採らない**。所有の模型が2つになり、
結果に解放すべきものがある場合と無い場合が生じる。
ファイルを1つ走らせる用途でも、機械を作って破棄する手間は2行にすぎない。

#### 段ごとにセッションを持つ

トップレベルの名前は入力をまたいで残る必要がある。
**型検査と生成の各段がそれぞれセッションを持つ**。

- `LhatCheckSession` — 名前とその型、および型のアリーナ
- `LhatCompileSession` — 名前とそのレジスタ、次の空き番号、
  および **`def^` の連鎖と `errordef^` の宣言**

どちらも **名前を複製して保持する**。
名前は読み込んだソースを指しており、そのソースは入力とともに消えるためである。

生成のセッションは、その入力の proto に
**開始時点で既に値を持つレジスタ数** を書き込む。
機械はそこから上だけを消し、下は前の入力が置いた値のまま残す。

##### 名前とレジスタだけでは足りない

02 の 14.2 は **合成の連鎖を定義時に確定させる**と定め、
04 の 2.4 は **誤りの種別の同一性を宣言の場所**と定めている。
どちらも生成の段で解決され、**機械には届かない**。

したがってこの2つもセッションが運ぶ。運ばないと、次の入力で

```lhat
> let^ A = def^{ self^{ x = 1 } }
> let^ B = A .. def^{ … }          # A が定義として引けない
> errordef^ E { Bad }
> error^ E.Bad {}                   # 種別 E が引けない
```

##### 節点は、それを読んだ字句器と一緒に運ぶ［重要］

**節点はソース中の位置を持つだけである。** 別の入力の字句器で読めば、
同じ位置から **別の語が出てくる**。

```text
> let^ A = def^{ self^{ x = 1 } }
> let^ B = A .. def^{ … }
> B.new()                          # { r := 1 } — フィールド名が壊れる
```

黙って別の名前になるので、型検査は通り **実行時に落ちる**。

そこで連鎖の各部と種別の宣言は、**それを読んだ字句器を一緒に持つ**。
合成は入力をまたいで混ざりうる（`A .. def^{ … }` の左右で別の入力）ため、
字句器は **連鎖ではなく部ごと** に付く。

##### セッションは入力を捨てられない

上の帰結として、**セッションの入力はセッションより長生きしなければならない**。
連鎖の部は構文木を指し、種別は proto 上のオブジェクトを指す。

拒否された入力は何も登録しないので、捨ててよい。

##### 入力の最上位はブロックではない

通常のブロックは末尾で名前とレジスタを手放すが、
セッションの入力ではそれを行わない。5.4 の共有場所も閉じない。
ある入力で作った閉包が、後の入力による再代入を見られるのはこのためである。

##### 書き直しは再定義である

> **セッションの最上位に限り、同じ名前をもう一度 `let^` `var^` できる。
> それは同じ場所を書き直すことであり、新しい場所を作らない。**

8.7 は同じスコープでの二重定義を誤りとするが、それは
**1つの入力の中での話** とする。プロンプトは行を書き直すためのものであり、
書き直しごとに場所が増えると 250 個で尽きる（レジスタは命令の 8 ビット幅で
上限が決まっている）。

同じ場所なので、書き直しは **そこにある値を読める**。

```text
let^ x = 1
let^ x = x + 10     # 11。8.7 のとおり導入子の前から名前は見えている
```

1つの入力の中で同じ名前を2度定義するのは、従来どおり誤りである。

書き直しで型を変えた場合は **遮蔽** になる。GHCi と同じ扱いである。
古い名前を閉じた関数はその入力が終わった時点の値と型を持ち去っているため、
動作も型も変わらない（次項）。
同じ名前への再代入（`:=`、遮蔽ではなく既存の場所への書き込み）は
型を変えられないため、型が食い違えば拒否される。

##### 閉包は入力の終わりに持ち去る

5.4 の共有場所が共有であるのは、**それを持つフレームが生きている間** である。
セッションではフレームは1つの入力であり、入力が終わればそこで閉じられる。

したがって、ある入力で作った閉包は **その入力が終わった時点の値を持ち去る**。
後の入力が同じ名前を書き直しても、その閉包には届かない。

```text
let^ x = 1
let^ show = f^ -> number^ { return^ x }
let^ x = 2
show()          # 1。閉包が持ち去ったのは、それを作った入力の終わりの x
```

1つの入力の中では従来どおり共有される。

```text
let^ x = 1  let^ show = f^ -> number^ { return^ x }  x := 2  show()   # 2
```

これは同時に **健全性を保っている**。書き直しで型が変わっても、
先に作られた閉包は古い値と古い型を持ち去っているため、
その署名が嘘になることはない。

```text
let^ x : number^ = 1
let^ show = f^ -> number^ { return^ x }
let^ x : string^ = "now"     # 型が変わる
show() + 1                    # 2。show は number^ を返し続ける
```

型が変わるのは **これから書くコードにとって** であり、
既に検査を終えたものには及ばない。

##### 入力は最後の文の値で答える

> **入力の最後の文が式であるとき、その値がその入力の答えになる。**

02 の 8.2 は対話入力の最上位に限り裸の式を文として認める。
プロンプトで `2 + 3` を評価できないのでは意味がないからである。
生成はその式を `return^` に読み替えるのではなく、
**式文のまま最後に置き、その値を答えとして返す**。

```text
> 2 + 3
5
> let^ twice = f^ n:number^ -> number^ { return^ n * 2 }
> twice(21)
42
```

`return^` に読み替えない理由は2つある。

- `return^` は **後続の文を止める**。最後でなければ意味が変わる
- 値を返さない手続きの呼び出しは `return^` の対象にできない。
  `bump()` は答えを持たないが、文としては正当である

答えを持たない文で終わる入力は、**何も答えない**。
`var^` `let^` で終わる入力がプロンプトに何も出さないのはこのためである。

###### 答える文はコルーチンを作ってよい

15.8 は、コルーチンを作ってそれを何にも使わない呼び出しを誤りとする。
15.5 によりその呼び出しは本体を1行も走らせないため、
**その文には効果がないと証明できる** ことが根拠である。

入力が答える文はこれに当たらない。**答えは表示され、それが効果である**。

```text
> let^ t = { 1, 2 }
> t.iterate^()          # 誤りではない。走査の値が答えになる
> t.iterate^()          # 最後でなければ、従来どおり 15.8 の誤り
> let^ k = 1
```

規則が消えるのではなく、**規則の根拠にしていた推論のほうが成り立たなくなる**。

##### 途中で終わった入力は続きを読む

02 の 3.1 は「構文が誤っている入力」と
「入力が途中で終わっただけの入力」を別のものとして報告する。
プロンプトはこれを使い、**後者なら次の行を求める**。

```text
> let^ add = f^ a:number^, b:number^ -> number^ {
.     return^ a + b
. }
> add(2, 3)
5
```

括弧の数を読み手が数えるのではなく、
**構文解析器が「まだ終わっていない」と言ったかどうか** だけで決める。
途中で終わった入力の診断は表示しない。
次に何が来るかについて、その診断は何も述べていないためである。

終わりの見えない入力から抜けるために、
**続きを読んでいる間の空行はその入力を捨てる**。

## 5. バイトコード

### 5.1 まず実行時検査つきの汎用命令

型が確定した箇所向けの特殊化命令は最初から作らない。
まず全命令が実行時に型を確認する形で作り、動作するものを得る。

特殊化は後から足せる。CPython 3.11 以降が採った順路であり、
先に汎用命令の意味を固めてから、確定した型の情報で特殊化命令に差し替える。
最初の1つ（strict での多重定義の静的解決）は 5.11c で入っている。

この順路であれば relaxed もそのまま動く。
特殊化は strict で型が確定した箇所にのみ適用される最適化になる。

#### 安全性は strict の静的検査が担う

言語の安全性は strict の静的検査が全てであり、実行時検査は独立の安全網ではない。
命令の検査が保証するのは「壊れずに止まる」——誤った値は実行を止め、
機械のメモリを壊さない——ことだけで、それで足りる。
型誤りでの停止も、L^ レベルのスタックオーバーフローでの停止も許容される。
許容されないのは SEGV の類（メモリ破壊・C スタックの破壊・止まらない再帰）だけである。

だから実行時検査は速度と効率のために最低限であってよく、
特殊化が進めば strict で確定した箇所から消えていく。

#### 5.1改 メンバ読みは見つけた場所を覚える［実装済み］

> **`x.m` は、前回どこで見つけたかを呼び出し地点が覚える。当たれば
> 比較2回、外れれば今までどおり探して覚え直す。**

5.1 が予告した特殊化の2つ目である。1つ目（5.11c）と違い、**検査器を
使わない**——答えは `GETINDEX` が返すものと同一なので、4.2 のとおり
厳格度は関わらず、検査を経ないコンパイルでも同じだけ効く。

`bench/` が測ったのは「ホスト型のメンバ呼び出しのうち、受け手のメンバ
読みが占める分」で、入れる前は**4割前後**だった。入れると当たった地点で
それが消える。数は走らせた機械のものなので書かない。

##### 覚えているのは呼び出し地点［重要］

キャッシュは**チャンクの中**にある。ソースに書かれた `x.m` 1つにつき1件で、
値にも表にも付かない。メンバ自体は 14.3 が定義側に置いて共有しているので、
**1つの地点が何度も見るのは同じ場所**である。

だから「同じ名前を読む2つの地点」は2件になる。互いのキャッシュを
打ち消し合わないためで、これは節約ではなく正しさの側の要請である。

##### 当たり判定は表の版番号

表は**並びが変わった回数**を持つ（`LhatTable.version`）。上がるのは
鍵が増えたとき・鍵が消えたとき・並べ替え（rehash）・列の側へ移ったとき。
**既にある鍵への上書きでは上がらない**——何も動かないからで、これが
`self^.x := 1` をループで回しても `self^.y` の読みが生き続ける理由である。

##### インスタンスを跨いで当たる

`def^` のインスタンスは1つ1つ別のテーブルなので、表そのものを見比べる形
だと**インスタンスごとに外れる**。メンバは共有なのに当たらない、という
おかしなことになる。

見比べるのは表ではなく**「複製以来まだ構造を書かれていない」**という
事実（版番号が 0）である。5.10 がプロトタイプを封印しているので、
そのままの複製は**必ずプロトタイプと同じ鍵の集合**を持ち、定義側の
メンバを隠していない。だから:

```text
受け手の版が 0        — 自分は何も隠していない
受け手の定義が同じ    — 同じ def^
定義側の版が同じ      — 定義側も並びが変わっていない
```

自分の表へ鍵を足したインスタンスは版が 0 でなくなり、正しく外れる。

##### 覚えるのは表の経路だけ

この命令が答えるもののうち、コルーチンの操作・ホスト値のフィールド・
どの値も持つ組込みは**その場で作られる**ものであって、表のどこかに
在るものではない。覚える場所が無いので、そこは今までどおり通る。

#### 検査器が知っていて報告しないもの［参考］

型検査が確かめた事実のうち、**誤りとして報告しないが捨てるのも惜しいもの**は
この段の材料になる。現時点で分かっているのは次である。

- **左辺の型が答えを決めている `fits^`**（02 の 13.11）。
  右辺と互いに素なら常に偽、左辺全体が適合するなら常に真。
  到達しない側の枝を落とせる
- **絞り込みで選択肢が尽きた枝**（同）

02 の 13.11 がこれらを報告しないと決めているのは、
`fits^` が実行時に問うための記法であり、
**推論の結果を根拠に書き手を縛らない** ためである。
右辺だけで決まる `fits^ any^` はそこに当たらず、誤りとして報告される。

**報告しないことと、知らないことは別である。**

### 5.2 レジスタ仮想機械

レジスタ仮想機械を採る。命令は **32 ビット固定長** とする。

```text
┌─────┬───────┬───────┬───────┐
│ op  │   A   │   B   │   C   │   三項の形
│  8  │   8   │   8   │   8   │
└─────┴───────┴───────┴───────┘
┌─────┬───────┬───────────────┐
│ op  │   A   │      Bx       │   定数・飛び先
└─────┴───────┴───────────────┘
```

レジスタは 256、定数と飛び先は 65536 まで。超える場合は拡張命令で継ぐ。

#### 固定長にする理由

復号がシフトとマスクだけで済み、命令の長さを数えなくてよいので飛び先の計算も単純になる。
1.2 が「命令のビットレイアウトは参照価値を保つ」と述べていたのはこの形である。

可変長のバイト列（CPython、Wasm）はオペランドの大きさに上限がないが、
5.1 の「まず動作するものを得る」に対しては復号が重くなるだけである。

#### レジスタはフレームの中の枠

レジスタはフレーム内の位置であり、フレームの大きさはコンパイル時に決まる。
式の途中の値も名前もすべて枠に載る。

#### 枠は本体より先に作る

02 の 8.7 が「`let^` `var^` が作る名前はスコープ全体で見える。
書かれた位置より前でも見える」と定めた。

したがってコード生成は、**ブロックに入った時点でその `let^` `var^` の枠をすべて作り、
そのあとで値を生成する**。これで自身を呼ぶ本体も相互再帰も、
前方宣言なしに解決できる。8.7 が前方宣言を設けなかったのはこのためである。

枠は作った時点で `nil^` にする。
枠は前のブロックの値を持っている可能性があり、
8.7 は `let^` `var^` の実行前に（本体の中から）名前を読むことを許すためである。
「評価の前に読むことはできない」は 8.7 のとおり **静的検査の側で** 報告する。

### 5.3 呼び出し規約

引数は呼び出し先のレジスタの先頭に並べ、**返り値はひとつ** である。

02 の 13.8改 はその1つが `(A, B)` でありうると定めた。

- 1つの値は呼び出し元の1スロットに落ちる
- タプルは **連続するスロットの列** として落ちる。
  先頭が頭スロットで、位置の数を持ち、位置がその後ろに並ぶ

Lua の呼び出し規約が複雑なのは、返る値の個数が **実行時に決まり**、
呼び出し側が期待する個数に合わせて詰めたり切り詰めたりするためである。
L^ では個数が **型で決まる**。
**したがってその調整は存在しない。**

#### 両側が告げ、機械が照合する

合意は静的には取れない。呼び出し先は値であり（`overload^`、テーブルのメンバ、
`f^…` 型の引数）、未検査コンパイル・4.3 の対話・05 の 5.3 の単位は
別々に翻訳される。したがって両側が意図を告げ、機械が実行時に照合する。

- 呼び出し側 — `CALL` の `C` の上位ビットに「答えのために何スロット空けたか」
- 呼ばれる側 — `RETURN` の `B` に「何位置返すか」

**食い違いは黙って調停せず落とす。** タプルと `t^{…}` は別の型なので、
一方を他方に変えるのは `pack^` という書き手の言葉でしか起こらない。

`C` は 13.7 の `expr...` を表す真偽値がバイトを丸ごと占めていたので、
下位1ビットをその意味のまま残し、上位7ビットを幅に充てた。
`RETURN` の `B` は未使用だった。命令形式は変えていない。

#### 頭スロットが3度元を取る

1. 幅の自己記述 — 退避も収集器も `pack^` もこれを読む
2. **合併が解ける** — `(A, B)|SomeError` は幅の違う2つの選択肢を持つが、
   頭スロットのタグが誤りかタプルかを判別するので、
   誤りの検査命令は無改造で通り、確保も起きない
3. 位置1自体が誤り型の値でも、頭があれば区別できる

#### 位置は値であり、生バイトではない

05 の 8.9 のホスト値は連続スロットを占めるが、継続スロットは生バイトで、
参照を持たない。タプルの位置は **普通の値** であり、自分のタグを持つ。
収集器はそれを値として読む必要がある——後始末が走っている間、
答えはフレーム自身の部屋に退避されており、そこが根になる。
**これがタプルが機構に足した唯一のものである。**

#### 末尾呼び出しの余地

02 の 13.8改 に述べたとおり、切り詰め規則が生まれないので、
多値返却は末尾呼び出しの余地を狭めない。
`f^ g() -> (A,B) { return^ h() }` で h も `(A,B)` を返す形は、
呼び出し元が空けたスロット数と行き先を引き継ぐだけで潰せる。
妨げになるのは cleanup であり、多値とは無関係である。

**そのとおりに実装してある**——5.3 の「末尾呼び出しはフレームを再利用する」。

#### 引数の既定値は生成に現れない

02 の 13.4 のとおり、引数の既定値は編集の時点で呼び出しの側へ書き込まれる情報であり、
呼び出しの意味を変えない。したがって **生成する側は既定値を読まない**。
引数の個数は宣言どおりで、足りなければ実行時の誤り（arity）になる。

04 の 2.2 の誤りのフィールドの既定値（5.9）と違い、生成の場所へ展開する処理は要らない。
既定値の式は構文木に残り、コード補完とビジュアルエディターがそこから読む。

**検査だけは行う。** 02 の 13.4 のとおり、書いた既定値はその引数の型と照合する。
生成に現れないことと、書かれた式を放置することは別である。
なお 3.4 の推論には関わらない。要求を出すのは本体であり、既定値ではない。

#### 末尾呼び出しはフレームを再利用する［重要］

> **呼び出し元のフレームにもう用が無いなら、新しいフレームを積まずに
> そのフレームで呼ぶ。**

拾う形は2つ。どちらも受け手付き（`return^ self^.m(x)`）を含む。

```lhat
return^ f(x)                 # 値がちょうど呼び出し。答えはそのまま外へ

p^ loop(n) {
    if^ n <= 0 { return^ }
    loop(n - 1)              # 本体の最後の文が裸の呼び出し。答えは捨てる
}
```

2つ目が「捨てる」のは、その文の後に在るのが**本体の末尾からの脱落**——
すなわち `nil^` を返すこと——だからである。フレームが答えるものは変わらない。

##### 潰さない場合

- **後始末が保留している**（5.5 の `with^`・`finally^` の中）。
  後始末は呼び出しの**後**に走るので、先にフレームを畳めない。
  生成側が `cleanup_depth` で外し、機械も枠の保留数で確かめる
- **コルーチンのフレーム**（5.11）。そのフレームはコルーチンの本体である
- **セッションの最上位**（4.3）。スロットが次の入力まで生き残る
- **呼ぶ先が L^ の閉包でない**——ホストの関数（05 の 8.7）や組込み。
  乗り移る先のフレームが無いので、普通の呼び出しとして走る

いずれも命令の側が判断する。生成した命令は「潰してよい」という許しであって、
指図ではない。潰せなかったときは後ろに置いた `return` がそのまま働く。

##### やること

引数は 5.3 のとおり呼び出し元の枠の上に既に並んでいる。
その窓を**このフレームの枠へそのまま下ろし**、閉包・`pc` を張り替える。
行き先（呼び出し元が空けたスロットと数）と 11.9 の `<=>` の読み替えは、
**元の呼び出し元のものを引き継ぐ**。5.4 の捕捉は下ろす前に値を持ち出す。

##### 帰結2つ

- **終わらない末尾再帰は無限ループになる。** フレームが増えないので
  `LHAT_RUN_STACK_OVERFLOW` に当たらない。`f^ f() { return^ f() }` は止まらない
  ——止めたければ末尾でない位置に書く
- **診断の位置は呼ばれた側になる。** 呼び出し元のフレームは畳まれており、
  そこへ戻る道は無い

［補足］デバッガの行イベントも、末尾呼び出しでは呼ばれた側の先頭で、
同じ深さで鳴る（[09-debugger.md](09-debugger.md) §2.5）——フレームが増えないので、
`step over` と `step into` の区別はこの一手に対しては付かない。

### 5.4 捕捉は参照［重要］

入れ子の手続きが外側の名前を捕捉する場合、**値ではなく場所を共有する**。

02 の 8.6 が `:=` を再代入と定め、それが外側の束縛に届くと決めたためである。

```lhat
var^ count = 0
let^ bump = p^ { count := count + 1 }
```

`bump` が値を複製していたら、外の `count` は動かない。
8.6 が意図した動作にするには、両者が同じ場所を指している必要がある。

フレームが生きている間は枠を直接指し、
枠が消えるときに値を持ち出して独立した場所に移す。Lua の upvalue と同じ扱いになる。

#### 持ち出しはフレームの終わりだけでは足りない

枠を手放すのはフレームの終わりだけではない。
**ブロックが終われば、その `let^` `var^` が使っていた枠も再利用される。**

```lhat
var^ get = f^ { return^ 0 }
do^{
    let^ n = 5
    get := f^ { return^ n }     # n の枠を共有する
}
do^{
    let^ other = 99             # 同じ枠が回ってくる
}
return^ get()                   # 5 でなければならない
```

そこで **ブロックが名前を作っていた場合、その終わりで
その枠以降を共有から外す**（`close` 命令）。
フレームの終わりでの持ち出しは、この規則の特別な場合になる。

### 5.5 `finally^` はフレームの待ち行列

02 の 9.8 と 10 章により、`finally^` は **あらゆる脱出で実行される**。
`with^`（02 の 12 章）の `dispose()` も同じ扱いになる。

> **フレームが未実行の後始末を保持し、脱出のたびに仮想機械がそれを走らせる。**

出口ごとにコードを複製する案は採らない。
04 の 5 章により **失敗しうる呼び出しのそれぞれが `try^` の脱出点** になるため、
複製する数が呼び出しの数だけ増える。入れ子にすると掛け算で増える。

Lua 5.4 の to-be-closed 変数が同じ形を採っている。

#### 後始末の途中で失敗しない

02 の 12.7 が `dispose()` を失敗しないと定めたので、
待ち行列を順に走らせるだけでよい。
「後始末の最中に起きた失敗をどこへ報告するか」という問いが存在しない。

#### 後始末は「フレームが覚えている番地」である

待ち行列の要素は **命令の番地** ひとつとする。

- ブロックに入るとき、その `finally^` の本体の番地を積む
- `with^` の束縛ごとに、`dispose()` を呼ぶ短い本体の番地を積む

**`finally^` と `with^` が機械にとって同じものになる。**
`with^` の後始末は、コンパイラが書いた呼び出しにすぎない。

命令は3つで足りる。

- **積む** — 本体の番地を1つ覚える
- **流す** — 指定した深さまで、内側から順に走らせる
- **戻す** — 後始末の本体の終わり。次の1つへ制御を返す

「流す」は1つずつ進む。本体の最後の「戻す」が次の1つを起こす。
本体の中に呼び出しがあっても、それは通常のフレームの積み降ろしで処理される。

#### 3つの帰結が自動的に満たされる

- **02 の 12.2**（`dispose()` は定義の逆順）— 待ち行列が積み重ねだから
- **02 の 12.4**（`finally^` が先、`dispose()` が後）—
  `with^` はブロックの外側なので先に積まれ、後に流れる
- **02 の 10.4**（`return^` は抜けるすべての `finally^` を内側から実行）—
  返るときに深さ0まで流すだけでよい。位置ごとの生成が要らない

`break^` は 02 の 9.8 のとおり繰り返しにとって正常な終了なので、
繰り返しの深さまで流してから飛ぶ。

### 5.6 誤りに巻き戻しはない

02 の 12.8 のとおり誤りは値である。仮想機械に例外の機構は要らない。

`try^`（04 の 5 章）は次に落ちる。

```text
呼び出す → 結果が誤りか調べる → 誤りなら待ち行列を走らせて、その値を返す
```

**脱出は `return^` と同じ経路をたどる。** 9.8 が予告していたとおりである。

### 5.7 コルーチン

02 の 13.9 により、yieldable な手続きを呼ぶとコルーチンが返る。
どちらを出すかは呼び出しの時点で決まっている
（02 の 15.2 が yieldability を推論するため、コンパイル時に分かる）。

> **コルーチンは1フレームだけを保存する。独立したスタックは持たない。**

**この決定は 02 の 15.5 に乗っている。**
02 の 15.8 が明示的な委譲 `await^` に決着しているため、本節はそのまま成立する。

#### 捕捉はフレームと一緒に移動する

中断はフレームのレジスタをコルーチンの保存領域へ写し、スタックを明け渡す。
このとき、そのフレームのスロットを指す open な upvalue（5.4 の共有された場）を
そのままにすると、**別の深さからの resume で宙に浮く** — 元の番地は次に
積まれた誰かのフレームのものになっており、読めば他人のスロット、書けば
他人のスロットの破壊になる。

したがって捕捉は **レジスタと一緒に移動する**。yield^ は機械の open リストの
先頭（中断するフレームは最上段なので、そのスロット群は最高位アドレス＝
リスト先頭に揃っている）から自フレーム分を外し、`location` を保存領域内へ
付け替えてコルーチン自身のリストに移す。resume は逆をやる —
新しい base へ付け替え、機械のリストの先頭へ戻す（`reattach_upvalues`）。

中断中も共有は生きている: 逃がした閉包からの読み書きは保存領域に届き、
resume 後の本体から見える。GC には upvalue が `suspended_in` で
コルーチンを到達させる — ハンドルが捨てられても、捕捉が生きている限り
保存領域は解放されない。

#### 委譲は鎖になる

`await^ c` は、**外側が内側を回す繰り返し** に展開する。

```text
   <式> → co
   sent = nil^
 top:
   resume  sent, co        ; sent := co を再開した結果
   isdone  t, co
   jumpfalse t → 続ける
   jump → 完了
 続ける:
   yield   sent            ; 外へ出し、再開側が渡した値を受け取る
   jump top
 完了:
   into = sent             ; 内側の返り値（02 の 15.8）
```

外側は自分の `yield` で中断し、`co` をレジスタに持ったまま止まる。
**鎖は機械の側の仕掛けではなくレジスタである。** 各コルーチンは1フレームのままになる。

再開は入れ子の段数だけ転送を要する。
Python の `yield from` も素朴な実装では同じ費用であり、必要になった時点で畳めばよい。

##### 委譲はタプルの幅を言えない

上の `resume` は **空きオペランドに 0 を書く**。`for^` はここに幅を書ける
（名前の数は構文であり、未検査コンパイルでも同じ命令が出る。4.2）が、
`await^` に読める数は無い — 内側の本体が何位置出すかは型を見ないと
分からず、未検査コンパイルには見る型が無い。

そこで 0 を「**幅は問わない。来たものを前へ**」の意味とする。幅が判るのは
中断の側なので、内側の `yield` が組を置く先を、外側が予約しなかったスロット
ではなく **外側フレームの答えの部屋** にする（5.3 の同じ部屋）。外側の
`yield` はその部屋から位置を読んで頭スロットだけを持って出るので、鎖は
一段につき一部屋ずつ組を手渡していく。テーブルの走査を委譲する場合も同じ
経路で、走査が最初の一段を部屋に置く。

部屋に置かれた位置が回収されないのは、外側がその間コルーチンをレジスタに
持ち続けるからである（回すために持たざるを得ない）。組の値は中断の際に
そのコルーチンのレジスタへ写されており、到達性は部屋ではなくコルーチンを
通る — 5.12 が部屋を辿るのは「返却中のフレーム」に限られる。

#### 02 の 15.5 が決めている

15.5 が「呼び出しは伝染しない」と定めた。
`yield^` を含む手続きを呼んでも呼び出し側は中断せず、コルーチンが返るだけである。

したがって次が成り立つ。

> **中断点は必ず、その yieldable 手続き自身の本体の中にある。**

フレームを跨ぐ `yield^` が存在しない。保存すべきものは1フレームしかない。

#### Lua が独立スタックを要する理由

Lua のコルーチンは `lua_State` であり、**独立した値スタックと呼び出し情報の連鎖**を持つ。
Lua では入れ子の呼び出しの奥から `yield` できるため、複数フレームの退避が要る。

さらに Lua は C スタックを跨ぐ場合に手当てを要した。

- 5.1 — C の呼び出し境界を跨ぐ `yield` は誤り
- 5.2 — **継続関数**（`lua_callk` / `lua_pcallk` / `lua_yieldk`）を導入。
  C スタックを保存するのではなく、再開時に元の C 関数の途中へ戻らず継続関数を呼ぶ
- 5.4 — 仮想機械の実行ループを再構成し、ほとんどの操作から `yield` 可能に

**L^ にはこの問題が最初から存在しない。** 15.5 が跨ぐことを許していないためである。
15.5 が「呼び出しに色を要求しない」ために置かれた規則が、
実行時の形まで決めていたことになる。

Python のジェネレータが同じ位置にいる。15.5 が挙げているとおりである。

#### 保存するもの

```text
コルーチン = 本体 + 捕捉 + レジスタの控え + 中断位置
           + 保留中の後始末（5.5）+ 状態
```

レジスタの本数は 5.2 によりコンパイル時に決まるので、
**確保する大きさが生成の時点で分かる**。伸長する仕掛けが要らない。

- **再開** — 控えを機械のスタックへ戻し、フレームを積む
- **`yield^`** — レジスタと位置を控え、フレームを降ろす。
  02 の 15.4 のとおり双方向であり、**出した値を置いたレジスタに、
  再開側が渡した値が入る**。1本のレジスタが両方向を運ぶ
- **破棄** — 保留中の後始末を内側から順に走らせる（02 の 10.7）。
  5.5 の待ち行列をそのまま流すだけで済む

10.8 が「中断位置が静的に決まらないので実行時の機構が要る」としていたものは、
**5.5 の待ち行列がすでにその機構である**。
コルーチンはそれを1フレーム分持ち運ぶ。別の表は要らない。

#### 表面の記法［提案］

コルーチンは `resume` と `dispose` をメンバとして持つ。

```lhat
let^ c = gen()
let^ v = c.resume(x)
c.dispose()
```

`dispose` は 02 の 12.6 が既に `c.dispose()` と書いている。
`resume` はその対であり、綴りは提案とする。
15.6 のとおり、利用者が普段触れるのはこれを包んだ層のほうになる。

### 5.8 テーブルの実行時の形

02 の 14 章がテーブルを唯一のデータ構造と定めたので、
これが最も使われる値になる。

#### 密な部分とハッシュ部分に分ける

鍵 `1, 2, 3 …` が途切れずに並ぶ範囲は連続した配列に置き、
残りを開番地法のハッシュ表に置く。1.2 が Lua から残す価値があるとした形である。

途中から埋めた場合もハッシュ側から配列側へ移す。
そうしないと後ろから埋めた表が永久にハッシュ側に留まる。

#### 位置指定の要素は 1 から数える

`{ 10, 20, 30 }` の鍵は `1, 2, 3` とする。

- Lua を継いだ設計であり、`a.1.1` は「C で言う `a[0][0]`」、
  すなわち **`a.1` が最初の要素** である
- 16 章の `for^ i from^ 1 to^ n` が既に 1 から数える

#### `=` は文字列を内容で比べる

02 の 11.6 の `=` は、**文字列については同じ綴りかを問う**。
テーブル・サブルーチンについては、いまのところ **同一のものかを問う**（P7）。

文字列を内容で比べるのは、それが表す値がその綴りそのものだからである。
これにより `t.foo` と `t["foo"]` が同じ鍵になる。
別の翻訳単位でコンパイルされた文字列でも同じ場所に届く。

テーブルを内容で比べていないのは、**まだ実装していないため**である（P7）。
本来 `=` に求めているのは値としての比較であり、同一性そのものを問いたい場面には
別に `is^` がある（02 の 13.11）。テーブルの構造比較はメンバをたどる過程で
循環参照を追い続ける費用がかかるため後回しにしてあるが、それまでの間
`=` と `is^` がテーブルについて同じ答えを返すのは、暫定の実装がそうなっている
だけであり、`=` の最終形ではない。

#### 鍵の一致は厳密な等値で決まる［補足］

02 の 14.8 の `=` は実数の誤差を織り込むが、**鍵はそれを使わない**。
帯を持つ等値は推移律を満たさず同値類を作れないので、ハッシュと整合しない
——持ち込めば同じ鍵が入れた順によって別の場所に届く。

`2` と `2.0` が1つの鍵なのは別の話で、実数が整数と同じ数を名指すときに
整数の形へ畳んでいるだけである（正規化）。これは厳密な一致であって帯ではない。

同じ理由で、**コンパイル時の定数の畳み込み**（5.2 の定数プール）も厳密な等値で
行う。近い2つのリテラルが1つに潰れれば、書かれた別の数が黙って同じ数になる。

#### 鍵になれないもの

- **`nil^`** — 04 の 11.3 が「鍵がないこと」を `nil^` で表すため、
  鍵としても使えると意味が二重になる
- **NaN** — 自分自身と等しくないため、同じ鍵を2度引けない

いずれも実行時の誤りとして報告する。値として `nil^` を入れることは、
11.3 のとおり **その鍵を取り除く** ことを意味する。

### 5.9 誤りの実行時の形

04 が定めた「誤りは値である」を機械の側から書き下す。

#### 種別は宣言のたびに作られる1個の対象

04 の 2.4 が「種別の同一性は宣言の場所で決まる」としたので、
**種別ごとに対象を1つ作り、その番地を同一性とする**。
綴りも構造も比較に関与しない。

`errordef^ IOError { NotFound, Denied }` は3つ作る。

- `IOError` を表すもの（**群**）
- `IOError.NotFound`、`IOError.Denied`（それぞれが群を指す）

2.3 が宣言をその種別群の合併としたので、
群に対する判定は「いずれかの種別か」を問う。種別に対する判定は同一性を問う。

これらは **最も外側の翻訳単位が所有する**。
入れ子の本体が自前で作ると、同じ宣言に2つの同一性ができてしまう。

#### 誤りの値は種別とフィールド表

2.3 が `message` と `cause` を宣言なしに全種別へ与えているため、
宣言されたフィールドと同じ場所に置く。区別する理由がない。

したがって **`e.message` は表の索引と同じ命令で読める**。
5.1 のとおり索引の命令が実行時に相手を確かめており、そこに誤りを加えるだけで済む。

#### 既定値は生成の場所で評価する

2.2 が既定値を「生成のたびに評価される式」と定めた。
したがって既定値は宣言の側に蓄えず、
**生成の場所（`error^Kind{ … }`）に、書かれなかったフィールドの分だけ展開する**。

実行時に既定値を保持する機構が要らなくなる。

#### `try^` に巻き戻しは要らない

5.6 のとおりである。`try^` は「誤りなら返す」以上のことをしない。

```text
<式> → into
iserror t, into
jumpfalse t → 続き
return into
続き:
```

02 の 9.8 と 04 の 5.2 が求める「繰り返しの `last^` も `epilog^` も実行しない」は、
`return` がそれらを飛び越えることで自動的に満たされる。

`catch^` と `??` も同じ形である。左を評価し、
それが誤り（`??` では `nil^`）なら右を評価する。3つとも同じ枝の形になる。

### 5.10 オブジェクトモデルの実行時の形

02 の 14 章を機械の側から書き下す。

#### 定義は表＋プロトタイプ、インスタンスはその複製＋1本のリンク

- **定義** — 共有されるメンバの表（14.3）。雛形は **`self^` メンバの下の
  実テーブル**——プロトタイプ——として持つ（14.11）
- **インスタンス** — プロトタイプの複製。見つからない鍵は **定義側を見る**（14.7）

リンクは **生成時に張り、以後変えられない**。14.2 が委譲の連鎖を定義時に確定させ、
14.1 が metatable 相当の差し替え機構を設けないと定めたためである。

Lua の `__index` と同じ探索になるが、
差し替えられる仕掛けではなく **構造そのもの** として持つ。14.3 が求めた形にあたる。

プロトタイプ自身にもリンクと封印がある。定義に結ばれているのでメソッドは届き、
封印されているので書けない——生成が複製する「原初のインスタンス」を、
値としてそのまま `App.self^` に見せている。

#### 合成はコンパイル時に平坦化する

`Foo .. def^{ … }` は実行時の操作にしない。
コンパイラが **基底から派生まで並べて1つの表に畳む**。
後の要素のメンバが前の要素のものを上書きする。それが `override^`（14.12）の意味になる。

これができるのは 14.2 が
「連鎖は静的に既知であり、型検査器は任意の式について構成要素を決定できる」
と定めているためである。**実装の近道ではなく、設計の要請そのものである。**

#### 雛形は定義の構築の締めくくりに値になる

14.11 が初期化子を「定義の構築で一度だけ評価される式」と定めたので、
**定義を作る命令列の末尾で** 初期化子を——連鎖の base から、書かれた順に——評価し、
プロトタイプの表に書き込む。締めが `SETPROTO` の1命令で、
表を封印し、定義に結び、定義の `self^` に掛ける。
`SETPROTO` はそのとき各値を焼き込む：テーブルは**木ごと複製・封印して
定義の持ち物**にし——封印は木の内側まで及ぶ——、
14.11 の「既定値は同一性を持ち込まない値に限る」は検査器が綴りの側で拒み、
検査を経ないコンパイルにはこの命令が値の側で同じ答えを返す。

末尾に置くのは初期化子の見えるもののためである。全メンバが書き込まれた後なので
`def^` から何でも呼べる。`self^` は無い——インスタンスはまだ1つも無い。

#### 生成は複製の1命令

`NEWINSTANCE` がプロトタイプを複製し——場に持たれたテーブル（14.11 のリテラル木）は
その木ごと、定義への参照は共有のまま——定義へのリンクを張る。生成はこれだけである。
複製と焼き込みの再帰には機械自身の上限がある——C のスタックを越えないための深さで、
リテラル木に循環は書けないから、正しいプログラムがこの上限を見ることはない。

- **既定の `new`** — 複製して返すだけの機械語
- **書いた `new`** — 「複製 → 本体 → 複製を返す」の形にコンパイルされる。
  本体には `self^` がその複製として結ばれ、`return^` が何を言おうと答えは複製である
- **`super^`** — 前段に書かれた `new` の本体を、受け手を取る閉包（フック）として
  もう一度コンパイルし、ローカル `super^` に束ねたもの。呼び出しは
  14.4 の「受け手を渡すかどうかは呼ばれる側が決める」の機構にそのまま乗り、
  同じ `self^` に対して前段の調整が走る

#### `self^` と `def^` は普通の名前

- **`self^`** — メソッドでは 14.4 の第一引数、`new` の本体では複製を持つ
  ただのローカルである。どちらも **ただの名前** で、専用の機構は無い
- **`def^`** — 定義を作っている最中のレジスタに束ねる。
  メソッドからも初期化子からも 5.4 の捕捉で届く

`self^.value1` は表の索引そのものである。

#### 受け手を渡すかどうかは呼ばれる側が決める

`x.m()` は **受け手を呼び出し先と引数の間に置く**。
機械は呼び出し先が `self^` を取るかどうかを見て、渡すか飛ばすかを決める。

これで 14.4 の2つが同じ命令で成り立つ。

- `x.m()` — メソッドなら受け手が `self^` になる
- `Foo.make(21)` — `self^` を取らない静的メンバなら受け手は渡らない

`let^ g = f.get` として `g(f)` と書く形（14.4）も、
通常の呼び出しとして引数の数が合う。

### 5.11 多重定義の解決

02 の 14.12 の `overload^` は、1つの名前に複数の本体を持たせる。
どの本体を呼ぶかの決め方は厳格度で分かれる。

- **strict** — コンパイル時に決め、バイトコードに焼く（5.11c）。
  実行時の探索は走らない
- **relaxed と、検査を経ないコンパイル** — 実行時に、引数の値を見て
  合う候補を探す

実行時解決の性質:

- **多重定義された名前の呼び出しにだけ乗る。** 他の呼び出しは変わらない
- 14.12 が署名の重なりを禁じたので、**順位付けも曖昧性の解決も要らない**。
  合うものを1つ見つけたら終わる探索になる
- 判定の中身は、よくある場合（`string^` と `number^` の区別）が**タグの比較1回**。
  構造的な型（`t^{ radius : number^ }`）を使う候補では、そのメンバを引く分だけ増える

**relaxed の探索には既知の粗さがある**（P8）。探索が読む記述子は
`lower_type` が書かれた注釈から作るもので、注釈のない引数は
「何も問わない」——検査器の非重複検査（`signatures_overlap`）が推論した型で
埋めた署名を見るのとは基準が違う。strict は 5.11c が検査器の答えを焼くので
この粗さに触れないが、relaxed では注釈のない選択肢が本来と別の呼び出しを
掴みうる。根から断つには記述子を推論した型で埋める必要がある
（5.11a の `checked_type` を引数側へ広げる形。P8）。

#### 機構は他と共用する［重要］

実行時に「この値はこの型を満たすか」を問う仕組みは、
**多重定義のために作るものではない**。02 の 13.11 の `fits^`
——一般の構造的な適合の判定（5.13）——が同じ
`lhat_value_satisfies` を使い、11.6 の `as^` も同じ関係を
LHAT_BC_ASCAST で問う。

したがって多重定義に固有の費用は、**候補の探索だけ** になる。

書かれた型は、コンパイル時に記述子へ落として翻訳単位が持つ。
2.1 が値にタグを持たせているので、判定はそのタグと記述子の突き合わせになる。
書かれていない引数は何も問わない（`any^` と同じ扱い）。

#### `self^` は判定の対象外

14.12 が `override^` の変性検査から `self^` を外したのと同じ理由で、
候補の探索でも受け手は問わない。

#### 5.11a 検査器が1つだけ残す注釈

検査器は構文木を書き換えない（4.2）が、**節点に検査の答えを1つ置く** 枠を持つ。
`LHAT_NODE_FUNC` の `checked_type`（`void*`。`ast.h` に検査段の型を
持ち込まないための型消去）に、`infer_func`（3.4）が組み立てた署名まるごと
（`LhatType*`）を置く。コンパイラの `compile_subroutine` は、
戻り値注釈が書かれていない場合に **限って** これを読み、
`lower_type` が空だった `result_type` の穴を埋める
（`rt_from_checked` が `LhatType` を `LhatRuntimeType` の形に直す）。
これにより、書かれていない戻り値型も 14.16 の `typeof^(x).signature`
に現れる。

- **狭さを保つ条件が3つある。** (1) 戻り値注釈が書かれているときは触らない
  — 明示の `any^` は any^ のまま。(2) `checked_type` が無いとき
  （検査を経ずにコンパイルする経路 — `test_vm.c` の大半がこれで、
  意図的にそうしている）は `lower_type` だけで組み立つ。
  (3) 多重定義の判定（`fits_call`）と `fits^` の一般 narrowing は
  この注釈を読まない — どちらも書かれた型だけを見る（14.12、13.11）
- **これは 4.2 を破らない。** 4.2 が変えないと言っているのは
  「厳格度によって」実行時の意味が変わらないことで、
  「検査が走ったかどうか」で変わらないことまでは言っていない —
  (2) がその境目を保証する: 検査を経ない `typeof^` は素の答えを返す
- コルーチンの `R,Y,T`（02 の 14.16）も同じ経路で埋まる。
  `LhatProto` に `yield_produce_type`/`yield_receive_type` を持ち、
  `compile_subroutine` が yields のとき `checked_type` からこれも埋める。
  書かれた型に対応する記法が無いので、これらは常に
  `checked_type` からしか来ない。答え自体は `p^` 自身の型ではなく、
  それを **呼んで得たコルーチンの値** の型（15.5, 13.9）に乗る —
  `LhatRuntimeType` の COROUTINE 種が `receive`/`produce` を持ち、
  `reflect_type` がコルーチン値のリフレクションを返すとき
  `coroutine->closure->proto` からこの2つと `result_type` を読む
- 値の側の刻印も同じ枠を使う: 型がホスト値である式（05 の 8.9 — 幅が
  スロット数を決める）と、タプルを含む型の式（13.8改）。後者は
  タプルを選択肢に持つ合併（走査の `resume` の `(K, V)|nil^`）も刻む —
  答えを捨てる呼び出し文でも、組の届きうる幅だけ席を予約する必要が
  あるため（02 の 16.3 の手駆動）

#### 5.11b `typeof^` は静的な答えである

`typeof^(EXPR)` を検査するとき、
`EXPR` の型は検査器がその場で既に持っている（型推論の通常の副産物）。
それを **`LHAT_NODE_TYPEOF` 自身** の `checked_type` に置き、
コンパイラは `rt_from_checked` でチャンクの定数に変換して `LOADK` 1つで
答える。**オペランド自体は必ず走る**（副作用を飛ばさない）。

静的な答えが `typeof^` の **定義** であり、実行時に値の構造を走査して
リフレクションを組み立てる経路は存在しない（02 の 14.16）。
静的な答えは定義により正しい。

規則は2つ。

- **誤りに触れる型だけは命令に回す**（`mentions_error`）。検査器の型は
  種別の名前しか持たず、実行時の `LhatErrorKind` オブジェクトへ辿る経路が
  無い。一方、値は葉の種別をポインタ1つで持っている——
  `typeof^(e)` が宣言の合併でなく `IOError.NotFound` を答えるのはこちら
- **検査を経ていないコードは、値のタグが O(1) で言えることだけを答える**
  （`LHAT_BC_TYPEOF` → `tag_type`）。`number^` `string^` `t^{}`、
  サブルーチン・コルーチンは proto が既に持つ静的シグネチャ、
  多重定義は選択肢の数だけの交差。**構造は走査しない** — テーブルは中身が
  何であれ `t^{}` である

検査器の型は自分を含みうる（インスタンスの型が自分の定義を成員に持つ形）
ので、`rt_from_checked` は変換中の型を覚え、再訪では 13.7 の `t^{}` で
打ち切る。

#### 5.11c strict は呼び出しごとに選択肢を決める［実装済み］

> **strict では、多重定義された呼び出しがどの候補を意味するかを
> コンパイル時に決め、バイトコードに焼く。実行時の探索は走らない。**

5.1 が予告した特殊化の最初の1つで、**タグ検査を丸ごと省く**形になっている
——探索の中身が引数ごとの `lhat_value_satisfies` である以上、
探索を消せば判定も消える。

##### 経路は 5.11a と同じ形

`checked_arm`（`uint16_t`、選択肢の位置＋1。0 が「何も決まっていない」）を
節点に置く。

- **`LHAT_NODE_CALL`** — `infer_call` が当てた選択肢。**strict のときだけ書く**
- **`LHAT_NODE_TABLE_ENTRY`（`override^`）** — `override_one` が置き換えた選択肢。
  **厳格度によらず書く**（すぐ下の理由による）

コンパイラは前者を `PICKARM A Bx`（群 R[A] の Bx 番で R[A] を置き換える）に
落とし、`CALL` の直前に置く。`CALL` は無改造でよい——
R[A] は既に素のサブルーチンなので、実行時解決の探索分岐を素通りする。
群でない値が来たら `PICKARM` は何もしない。書かれていなければ
探索する（5.11a の条件 (2) と同じ形）。

##### 選択肢の番号は両側で同じものを指す

検査器の選択肢の並びと実行時の群の並びは一致していなければならない。
`overload^` は両側とも末尾に足すので一致する。
`override^` は **実行時もその場差し替え** とする（`OVERRIDEARM`。
`lhat_overload_replacing`）——置き換えられた選択肢は残さず落とす。
**14.12改 の `super^` は書き込み前の `GETINDEX` で旧グループを捕捉している**ので、
新グループに残す必要が元から無い。

どの選択肢かは検査器が知っているので、`override^` のエントリに書いて渡す。
**これは特殊化ではなく群の形の正規化**であり、厳格度で変えてはならない
（4.2。群の選択肢は 14.16 の `typeof^` からも読まれる）。だから strict の
呼び出し側注釈と違い、relaxed でも書く。落とすほうが型に忠実でもある——
検査器の型は置き換えられた選択肢を持っていない。

`OVERRIDEARM` は `A B C` を選択肢の番号に使い切るので、値は `R[B+1]` から読む。
`compile_def` が鍵と値を隣り合う枠に置くのは 5.3 が呼び出しを置くのと同じ形。
隣り合っていなければ `OVERRIDEINDEX` に落ちる。

##### 14.12 の非重複は選択肢ごとに問う

**新しい選択肢は、既にある選択肢のそれぞれと分離していなければならない**。
`overload^` も `override^` も、比較は選択肢1つずつ行う。
選択肢の集合（交差型）ごと `signatures_overlap` に渡すと、
署名でないものは「区別できない」＝重なり扱いになり、
明白に分離した選択肢まで拒否される。

##### 実行時に確かめ直さない

`PICKARM` は番号で取り出すだけで、引数の型を一切見ない。
外れた場合に探索へ落とす安全網は**置かない**。置けば判定が残り、
特殊化が消そうとしているものがそのまま残る。5.1 の特殊化は
「型が確定した箇所から検査を省く」ものであり、これはその定義どおりの形である。

代わりに払うのは、**検査器が間違えれば誤った本体が呼ばれる**という賭けである。
静的型付けが元から張っている賭けと同じもので、新しく増える種類ではない。

##### 演算子はまだ探索のまま

02 の 11.8 の `op^` も多重定義できるが、`PICKARM` はそこに載らない。
呼び出しと違い、**群がレジスタに載っていない** — 演算子の命令が持つのは
被演算子だけで、メンバの引き当ては `call_operator` が実行時に行う。
選択肢の番号を渡すには命令側に置き場所が要り、`ADD A B C` は既に埋まっている。
載せるなら別の形になるので、5.1 の特殊化を続けるときに改めて起票する。

**検査器の側は揃っている。** `infer_operator` は右被演算子で選択肢を選ぶ
（14.4 が左を `self^` に置くので、選択肢への問いは `x.m(右)` と同じ形になる）。
どの選択肢も取らなければ、単一の選択肢が右被演算子を拒むときと同じ報告をする。
**静的な答えは揃っている。焼く先が無いだけである。**

### 5.12 ガーベジコレクション

> **標識と掃除（mark and sweep）とし、対象は動かさない。
> 一度に全部ではなく、命令の切れ目ごとに一歩ずつ進める。**

1.2 は Lua のインクリメンタル GC と書き込みバリアを
「参照価値を保つもの」として挙げていた。**借りた。**
5.1 の順序に従いまず stop-the-world の動作する形を作り、
その上に段階的な実行を載せた。世代別はまだ載せていない。

停止時間の上限が要る用途（ゲームエンジンへの組み込み）が先に来たため、
世代別より先にこちらを入れている。

#### 対象を動かさないこと［重要］

写し取って詰める方式（copying / compacting）は採らない。
**対象が動かないなら、外に持たれた番地を直して回る必要がない。**

- 5.4 の upvalue は枠を直接指している
- 5.7 のコルーチンはレジスタの控えを持っている
- 実行ループは局所変数に現在のレジスタ列を持っている

いずれも動かす方式では追随が要る。動かさない方式ならどれも不要になる。

#### 走らせるのは命令の切れ目［重要］

**割り当ての最中には走らせない。**
そこには、まだどの根からも指されていない作りかけの対象がある。

命令の切れ目であれば、生きている値は必ず
**レジスタか、フレームか、開いた upvalue の列** にある。根の列挙が完全になる。

この規則は書き込みバリアの要否も決める。
**同じ命令の中で作った対象への書き込みにはバリアが要らない。**
その間に収集器が動くことはなく、誰もまだその対象を見ていないからである。
バリアが要るのは「前の切れ目の時点で既に存在していた対象」への書き込みだけ。

**問うのは割り当てた命令のそば**である。数が増えるのは割り当てた命令の中
だけなので、割り当てうる命令（表・閉包・複製・連結・文字列の切り出し・
呼び出し）の際にだけ閾値を見れば、毎切れ目に見るのと発火の位置は同じで、
無駄な検査だけが消える——Lua が checkGC を割り当てる命令の隣に置くのと
同じ形である。走らせる**場所**が切れ目であることは変わらない。
例外は偏執ビルド（LHAT_GC_PARANOID、debug 構成）で、こちらは検査網羅の
ために毎切れ目で問い続ける——目的が歩みの刻みでなくバリアの踏破だからである。

#### 三色と、白が二つあること

段階的に進めるには「どこまで進んだか」を対象自身に持たせる必要がある。

- **白** — まだ到達していない
- **灰** — 到達したが、指している先はまだ辿っていない
- **黒** — 到達し、指している先も辿り終えた

守るべき不変条件は **「黒は白を指さない」**。
黒はもう見終わったものなので、黒だけが指している白は
生きているのに掃除されてしまう。

白が二つあるのは、**掃除の最中もプログラムが走るから**である。
ヒープは片方の白を配り（`LhatHeap.white`）、掃除はもう片方を回収する。
掃除中に生まれた対象は「生きている側の白」を着て生まれ、その掃除に取られない。
二つは標識の終わりで入れ替わる。

#### 書き込みバリア

黒が白を指しうる書き込みは、バリアを通す。2種類ある。

- **前進バリア** — 指された白を今その場で標識する。
  一度か二度しか書かれない場所（閉じた upvalue、overload^ の選択肢）向け
- **後退バリア** — 親を灰に戻し、灰の列に積み直す。
  何度も書かれる場所（テーブル、コルーチンの保存レジスタ）向け。
  値ごとに標識するより、書き込みが落ち着いた後で親をもう一度見る方が安い

置き場所は上の規則で決まる。テーブルへの書き込み、`SETUPVAL` と upvalue を
閉じる処理、`yield^` によるレジスタの保存、`overload^` の選択肢の追加の4か所。

**バリアの欠落は静かに壊れる。** 生きている対象が解放され、
そのことが分かるのは後で別の場所からそれを読んだときになる。
そのため実装は、支払える構成（デバッグビルド）では
**不変条件そのものを毎サイクル検算する**。
併せてその構成では命令ごとに必ず一歩進め、
サイクルが常に途中である状態を作る——
そうしないと小さなヒープでは標識が一歩で終わってしまい、
バリアが一度も通らないまま「テストは通る」ことになる。

#### 停止しない部分と、する部分

- **標識（propagate）** — 一歩ずつ。プログラムが間に走る
- **atomic** — 止まる。根を最初から読み直し、灰を枯らし、10.7 の保留を隔離し、
  白を入れ替える。ここだけはプログラムを挟めない
- **掃除（sweep）** — 一歩ずつ。標識は終わっているので、
  プログラムが到達できるものはすべて黒か、入れ替え後に生まれた白。
  この間バリアは要らない

Lua はスタックをスレッド対象として扱い、atomic で全スレッドを辿り直すことで
スタックへの書き込みにバリアを不要にしている。
**L^ はスレッドが1本で、スタックは機械の生の配列である。**
したがって atomic で根をもう一度読むだけでよく、この部分は Lua より単純になる。

#### 根

- 各フレームのレジスタ列（5.2 が幅をコンパイル時に決めているので、
  式の途中の値もその幅に収まっている）
- 各フレームのクロージャ、属するコルーチン、返そうとしている値
- 開いた upvalue の列（5.4）

#### 翻訳単位が持つ対象は掃除しない

文字列定数、誤りの種別（5.9）、型の記述子（5.11）は翻訳単位のもので、
プログラムより長く生きる。**掃除は機械の側の一覧だけを走査する。**

標識は追跡の途中でそれらにも付くが、掃除が訪れないので害がない。

#### 循環参照は残らない

参照数を数える方式ではないため、
互いを指し合ったまま到達不能になった対象も回収される。

#### 捨てられたコルーチンの `finally^`

02 の 10.7 は、**捨てられたコルーチンの保留中の `finally^` が実行される** とし、
12.6 はGCをその最後の受け皿としている。

実行するのは収集の中ではない。走らせるものが `L^` のコードである以上、
掃除の途中のヒープの上でも、割り当てが再びGCを呼ぶ位置でも動かせない。
したがって **2周に分ける**。Lua が `__gc` に対して採ったのと同じ経路である。

1. **印付けの後、掃除の前（隔離）** — 機械の一覧を走査し、
   印が付いておらず、本体を持つコルーチンであり、中断中であり、
   保留中の `finally^` を持つものを見つける。
   これを到達済みにして機械の待ち行列に積み、その後もう一度灰色を枯らす。
   コルーチンが指すもの（保存レジスタ、捕捉した場所）も同時に生き延びる
2. **次の命令境界（消費）** — 待ち行列から1つ取り出し、
   `dispose()` と同じフレームを積んで巻き戻す。1境界につき1つだけ。
   破棄処理の最中（`disposing`）は手をつけない

「まだ実行していない」印に専用の旗は持たない。
保留中の数（`cleanup_count`）がそのまま条件であり、
待ち行列に載っている間は根から印が付くので隔離を素通りする。
巻き戻しが終われば `cleanup_count` は 0 になり、二度目はない。

待ち行列は機械が持ち、繋ぎは対象自身の中の一本の指し先である
（5.4 の開いた upvalue の列と同じ形、同じ理由）。
**根の列挙はこの待ち行列も走査しなければならない。**
走査しなければ、積んだ直後の掃除がそれを持ち去り、
「`finally^` が呼ばれない」という消極的な失敗になる。

#### 実行の走りの終わりの一度

上の2周は、隔離が収集の中、実行が次の命令境界で起きる。
プログラムが終われば次の命令境界が無いので、
**最後の数命令で捨てられたコルーチンはそのどちらにも当たらず、
保留中の `finally^` が走らないまま走りが終わる**。
`finally^` が走るかどうかが、GCがたまたま間に合ったかという偶然に決まる。

**そこで、最後のフレームが去る直前に一度だけ収集を行い、
待ち行列が空になるまで走りを終わらせない。**

その時点でフレームはまだ数えられている。
レジスタも `answer` も根のままであり、問う到達可能性は他の収集と同じである。
プログラムがまだ保持しているものはここでも生きている。

行うのは、**保留中の後始末を抱えて中断しているコルーチンが存在するときだけ**である。
機械はその数を数えている——増えるのは `yield^` が空でない後始末の列を
保存するときだけ、減るのはその中断が再開または破棄で取り上げられるときだけ。
0 なら、この収集が見つけるものは無いと分かっているので、走りは収集なしで終わる。
ホストが繰り返し呼び込む走りが、負っていない約束の代金を払うことはない。

### 5.13 `fits^` は1命令

> **`fits^` の右辺に何を書いても、機械が問うのは1つである。
> 書かれた型を記述子（`LhatRuntimeType`）に落とし、
> `x fits^ T` は `ISA A B C` 1命令になる。**

02 の 13.11 は `fits^` を **一般の適合の判定** と定めており、
右辺の書き方（誤りの種別、ホスト型、組み込み名、構造、合併、定義の名前）で
別の演算子になるわけではない。実行時に問うことも1つである。

したがって専用命令を並べない。誤りの種別は `LHAT_TYPE_RT_ERROR_KIND` の
記述子であり、ホスト型は `LHAT_TYPE_RT_HOSTDATA` の記述子である。どちらも
5.11 の `lhat_value_satisfies` がそのまま答える
——「機構は他と共用する」がここで実際に共用になる。

11.6 の `as^` は同じ記述子を `ASCAST` に渡す。
違いは**答えの形だけ**である。`fits^` は真偽を返し、`as^` は合わなければ落ちる。

#### 型はコンパイル時の記述である。実行時の値は型を持たない

14.9 は定義の名前を **ラベル** とし、同一性を構造で決める。
よって `x fits^ Point` は「Point の形を満たすか」であり、
その形は 14.11 の雛形の欄と 14.3 のメンバの両方からなる——
**コンパイル時に**。14.2 が合成の連鎖をコンパイル時に解決するので
（`def_chain_of`）、両方の半分が木の中にあり、
記述子（構造）に落として定数にする。合併の選択肢でも `t^{ … }` のメンバでも同じ。
これが `fits^` と `as^` の **唯一の経路** である。

> **実行時に届いた値は、型を持たない。すべて `t^{}` である。**

コンパイル時に見えない定義（引数として渡された定義、別の翻訳単位のメンバ）を
値として読み、実行時に定義テーブルから形を読む経路は **無い**。
理由は2つ。第一に、実行時のテーブルは純粋なデータであり、
数万エントリを持ちうる——そこから型情報を組み立てようとする方向自体に無理がある。
第二に、そうした経路は主経路より弱くしか問えない（14.11 の雛形は定義テーブルに
保存されないため、欄の名前が読めない）——同じ綴りが場所によって
違う強さで問うのは、13.11 が1つの演算子に統一した意味を割る。

実行時にしか届かないテーブルを受け取ったプログラムは、
**動的なコードとして書く**: メンバごとに `?.` や 後置 `?` や
`x fits^ t^{ … }`（書かれた構造への適合——費用は書いた型の大きさで抑えられる）
で確かめて使う。3.5 の relaxed と同じ向きである——
実行時は型情報を製造しない。問えるのは書かれた型だけである。

検査器も同じ形である（値である名前は型の位置で `unknown type` になる）。
`as^` も同じ規則で拒む——「合わなければ panic」の約束がある以上、
何も確かめない cast が黙って通ってはならない。

#### `any^` は命令にしない

13.7 が `any^` をあらゆる値の頂点と定めているので、
`x fits^ any^` の答えは左辺に依らず真である。定数に畳む。
検査器は書いたこと自体を誤りとして報告する（02 の 13.11）が、
検査を経ないコンパイル経路（4.2）も答えを持たねばならない。

## 7. 未決事項

- **P4 — REPL での型環境の持ち越し**

  入力ごとに独立してコンパイルされる一方、定義は残る。
  strict を有効にした REPL では、推論した型環境を入力間で持ち越す必要がある。
  relaxed が既定である限り優先度は低い。

- **P6 — 相互再帰の返り値型推論（3.4）** — 安全性は確保。推論そのものはまだ未対応

  3.4 が自己再帰について定めた「再帰を経由しない脱出の合併」は、
  互いを呼び合う定義の群には**まだ適用していない**。

  ```lhat
  let^ a = f^ n:number^ { if^ n <= 0 { return^ true^ } return^ b(n - 1) }
  let^ b = f^ n:number^ { if^ n <= 0 { return^ false^ } return^ a(n - 1) }
  ```

  自己再帰は本体の中で名前が一致するかを見るだけで判別できるが、
  群の場合は **どこまでが群か** を先に求めたうえで、群全体の不動点をとることになる。
  ここはまだ手を付けていない。

  8.7 の事前収集が `a` `b` を `unknown^` として束ねるため、`a` の本体を検査する
  時点で `b` はまだ本体を検査していない（コード上の記述順に検査するため）。
  `b(n - 1)` の型は `unknown^` になり、`a` の返り値は `bool^|unknown^` という
  合併になる。

  安全性は次の2つの規則が守っている。

  - `lhat_type_equal` は `conforms` の緩さを使わない（`unknown^` と
    非 `unknown^` は常に不等）。緩さが等価判定に漏れると、
    `bool^|unknown^` の `unknown^` の選択肢が握りつぶされて単なる `bool^` になり、
    不確定な型が正しい型として黙って通る
  - `lhat_type_conforms` は、合併の選択肢に `unknown^` が混ざっている場合は
    どんな期待型にも不適合とする。`unknown^` 単体の緩さ
    （推論の隙間はミスマッチではない、3.5）とは別の話で、合併に
    混ざった `unknown^` は「まだ検査していない」ことの印であり、
    安全側（不適合）に倒す

  これにより、**実際に返しうる型を注釈すれば定義順序によらず正しく検査され**、
  注釈がなければ `unknown^` の選択肢を理由にミスマッチとして拒否される。
  「注釈を書けば検査される、書かなければ安全に拒否される」
  という妥協で、当面はしのげる。

- **P7 — `=` をテーブルの値比較にする**

  02 の 11.6 で `=` に求めているのは本来 **値としての比較** であり、
  現状のテーブルに対する同一性判定（5.8）は実装の都合による暫定形である。

  値比較への切り替えを保留している理由は実装費用にある。
  テーブルはメンバをたどって内容を比べる必要があり、循環参照を追い続ける
  ことになる（Lua の `==` も同様の理由で同一性のままにしている）。
  比較の途中で見つけた循環をどう扱うか（等しいとみなすか、誤りにするか）も
  決まっていない。

  02 の 13.11 で `is^`（同一のインスタンスかを問う、値比較とは別の演算子）を
  適合の判定から切り離したのは、この P7 を待たずに **同一性の判定手段を残す**
  ためである。`=` が値比較に切り替わっても `is^` の意味は変わらない。

  文字列は既に値（綴り）で比べているため、この保留の影響を受けない。

- **P8 — relaxed の探索記述子を推論型で埋める**

  5.11 のとおり、実行時解決の記述子は書かれた注釈だけから作られ、
  注釈のない引数は何も問わない。検査器の非重複検査は推論した型で埋めた
  署名を見るため、両者の基準が違う——relaxed では注釈のない選択肢が
  本来と別の呼び出しを掴みうる。5.11a の `checked_type` を引数側へ
  広げ、記述子を推論した型で埋めれば根から断てる。

  単位の無注釈の `x + y` は「どちらの演算子か定まらない」になる——
  組込みだけで候補が2つある `<` と同じ振る舞いである

- **演算子の要求は候補から作る**: 3.4 は `x + 1` の要求を `number^` と決め打って
  いた。理由は「14.8 が `number^` を唯一の算術の持ち主にしている」だったが、
  それは**組込みについてしか正しくない**——利用者が `op^*` を書けば前提が崩れ、
  自分の型を注釈の無い引数に流せなかった。要求をその演算子の候補
  （組込みとその単位が `op^` を書いた型）の合併に改めた（3.4改3）。
  候補が組込みだけなら `number^` になり、従来の答えと変わらない。
  合併になった本体は誤りになるが、**署名が候補を名指すので注釈も絞り込みも
  選べる**——要求を作らず 3.1③ に渡す形（候補を捨てる形）は採らなかった。
  併せて、片側が決まっていて相手の腕がこの向きに1つしか無い場合に
  諦めていたのを改めた（`f^ x:A, y { x * y }` が解ける）

- **比較にも届かせた**: 上を入れた時点で、組込みの候補が `number^` 決め打ちの

  `check_comparison` を通って要求を作る道に入っていなかったことの2つが
  残っていた。組込みは `chk_builtin_operator` に演算子名ごとに訊く形に改め、
  順序は `<=>` の候補を要求するようにした。併せて**相手側が決まっているなら
  そこで候補を絞る**ようにした——これが無いと組込みだけの単位でも `<=>` の
  候補が2つあり、順序が軒並み合併になって役に立たない。
  `f^ x -> bool^ { x < 1 }` が `f^number^ -> bool^;` に解ける（3.4改3）

- P1（relaxed の緩さ）・P2（値表現）・P3（REPL の再定義）・
  P5（コルーチンの実行時の形）は決定済みとして本文に取り込み欠番
- NaN boxing は当初「保留」だったが、整数精度の再検討（2026-08）を経て
  **恒久棄却**（ポインタ移植性は妥協で解けない）。キャッシュ効率の不満は
  SoA 化（2.2）が解いた
- relaxed への実行時検査の挿入（旧 3.5改）は撤回。黙認した箇所の型不一致は
  命令の panic が答える。この撤回に伴い 04 の relaxed `nil^` 参照も
  誤り値から panic に変わった
- 再帰関数の返り値型は当初「明示を要する」だったが推論に変更（3.4）。
  根拠にしていた「C++/Kotlin/Swift が同じ制限」は正確でなかった
  （該当するのは Kotlin のみ）
- 引数型は当初「推論しない（全域推論になるため）」だったが、
  逆算を本体の中に限れば当たらないと判明し、要求の交差による推論に変更（3.4）
- 多重定義は当初すべて実行時解決だった。検査器と実行時で判定基準が
  食い違い strict を通ったものが落ちる健全性の破れが見つかり、
  strict はコンパイル時解決（5.11c）に分離。`override^` の選択肢の並びも
  実行時をその場差し替えに揃えた。`overload^` の非重複検査が選択肢の集合ごと
  比較していた誤りも選択肢ごとに修正
- `typeof^` は当初、実行時に値を走査してリフレクションを組み立てるもので、
  静的な答えは最適化だったが、S36 で反転し静的な答えが定義になった（5.11b）。
  値から型情報を読む第2の経路（実行時の定義テーブル走査）も撤回（5.13）
- 演算子の多重定義は当初検査器が1つも解決していなかった（選択肢の型が式に
  出ず、右被演算子が検査されない）。右被演算子で選択肢を選ぶよう修正
- コルーチンの yield が open upvalue を放置し、別深度からの resume で
  他フレームを読み書きするバグを実際に観測してから、捕捉の付け替え
  （5.7）で塞いだ
- 期待される署名も引数の要求になる（3.4改）。束縛に書いた署名と、
  書いたその場での呼び出しの2つから流れる。他所の呼び出し側は今までどおり見ない
- その期待を **呼び出しの引数**へ広げた（3.4改）。`ff(1, "s", f^ c, d { … })` の
  `c`・`d` は `ff` の書かれた署名から決まる。当初は束縛と IIFE だけを見て
  いたので、C# のラムダなら書かずに済む場所で注釈を求めていた（ユーザー指摘）。
  向きが逆——呼ばれる側の署名が流れるだけ——なので 05 の 6.2 は保たれる。
  同じ理由で、書かれた返り値・再代入先が持っている型・書かれた既定値の位置
  からも流れる。多重定義（14.12）だけは腕が引数で決まるため取らない
- `def^` のメンバの走査は当初1巡だったが、答えが変わらなくなるまで繰り返す
  ことにした（3.4改2）。輪のうち1つだけが返り値型の注釈を要していたのが
  外れた。素の再帰する `let^` は1回のままである
- strict の報告する場所に「推論した返り値型に印が残った定義」を足した（3.1①）。
  それまでは印が具体型を要求する場所に届いたときだけ報告しており、
  要求する場所が1つも無ければ穴のある署名がそのまま通っていた
- 3.4改2 の反復を文の並びへ広げた。並んで書かれた `let^` の相互再帰も
  注釈なしで閉じる。当初 `def^` のメンバに限ったのは、文が型を作る以外の
  こともするためで（名前を束ね、テーブルを育て、8.7 の印を立てる）、
  「素の `let^` には種の置き場がない」と書いていたのは誤りだった
  ——8.7 が名前を集める巡が先に置いている
- 3.4改 の期待される署名は当初引数だけを埋めていた。返り値型も埋めるようにし、
  束縛に書いた署名が 3.1① の「書けば決まる」道になるようにした
- `try^` が通す誤りを脱出として数えるようにした（3.4、04 の 5.3）。
  それまでは書いた返り値型に対して検査するだけで、書いていない本体では
  誤りが型に出ず、その本体を呼んで `catch^` で受けることができなかった
- 末尾呼び出しでフレームを再利用するようにした（5.3）。02 の 13.8改 が
  「余地は狭まらない」と書いたとおりの形で、妨げになるのは 5.5 の後始末・
  5.11 のコルーチン・4.3 のセッションの最上位だけである。
  終わらない末尾再帰は溢れずに回り続けるようになった
- strict が翻訳単位に未決定の型を1つも残さないようにした（3.1③）。
  それまでは注釈のないパラメータと、印が届いた束縛が黙って通り、
  `typeof^` が `UNKNOWN` と書き出す署名を strict が咎めなかった。
  決めたくない箇所は 02 の 13.7 の `any^` を書く。
  「要求する側が未確定なだけなら `any^` と同じ扱い」という但し書きは、
  relaxed の側の話として 3.5 へ移した
- 鍵の一致と定数プールの畳み込みが厳密な等値で決まることを明記（5.8）。
  02 の 14.8 の `=` が実数の誤差を織り込むようになったので、両者が別の述語で
  あることを書いておかないと、NaN を鍵から外す理由（自分自身と等しくない）と
  繋がらなくなる
- 演算子が見つからない理由が `nil^` の腕であるとき、専用の種別でそう言うことにした
  （1 章「`nil^` が理由なら演算子の規則を語らない」新設）。04 の 11.3 がキーで読んだ
  ものを常に `T|nil^` にする以上これが最頻出の原因であり、02 の 11.3改 を読ませても
  直し方に繋がらない。02 の 13.11 が添字をその場で絞り込まないので、`??` と
  「名前に束縛して絞り込む」の2つを文面が名指しする
