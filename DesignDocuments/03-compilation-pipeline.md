# L^ 処理の構成

ソースを受け取ってから実行するまでの段階構成と、
その構成を決めている実行時の値表現について定義する。

字句については [01-lexical-structure.md](01-lexical-structure.md)、
構文については [02-syntax.md](02-syntax.md) を参照。

記法ラベル（［確定］／［提案］／［未決］）の意味は [README.md](README.md) を参照。
本文書の未決事項には `P1`, `P2`, … の番号を振る。

**現状**: 段階構成、実行時の値表現、型検査の厳格度、推論の範囲が確定している。
バイトコードと仮想機械の設計は未着手。

## 1. 段階構成

### 1.1 少なくとも4段になる［確定］

```text
ソース → 字句解析 → 構文木 → 型検査 → コード生成 → バイトコード
```

Lua が採る単一パス（トークンを読みながら直接バイトコードを出力する）は使えない。

Memo.md L7 の「静的自動型付け」は型推論を意味する。
推論は **ソースの後方にある情報を必要とする** 場合がある。

- 再帰関数の返り値型は、本体を読み終えるまで決まらない
- 相互再帰する定義は、互いを読み終えるまで決まらない
- 使用箇所から引数の型を推論する場合、定義より後ろを見る必要がある

Lua の単一パスが成立するのは動的型付けだからであり、
`expdesc` とレジスタ割当を読みながら確定できることが前提になっている。
L^ ではこの前提が崩れる。したがって **構文木を作る段が必須** である。

名前解決を型検査から分離して5段にする構成もありうる［提案］。
名前解決は型検査に必要な情報を用意する処理であり、
独立させたほうがスコープ規則（`$` `$$` `$^`、01 の 8 章）の実装が読みやすくなる。

### 1.2 単一パスを捨てて失うもの［確定］

Lua の `lcode.c` と `lparser.c` が実装している単一パスのコード生成技法
（`expdesc` による式の遅延評価、レジスタ割当、ジャンプパッチリスト）は、
L^ では **そのまま流用できない**。参照価値が下がる。

一方、これらと直交する部分は参照価値を保つ。

- レジスタ仮想機械のディスパッチループ
- 命令のビットレイアウト
- インクリメンタル GC と書き込みバリア
- 配列部とハッシュ部のハイブリッドなテーブル
- バイトコードの直列化

## 2. 実行時の値表現

### 2.1 値は型タグを持つ［確定・重要］

**実行時の値は自身の型を保持する。** 型情報を消去した表現は採らない。

これは本文書で最も変更費用の高い決定である。
後から覆すには仮想機械を作り直すことになる。

#### 2つの設計と、選んだ理由

- **(a) 実行時は動的で、静的型付けは検査層** — 値がタグを持ち、
  静的検査は実行前に正しさを証明する役を担う。
  TypeScript と JavaScript、Common Lisp の型宣言、Python と mypy がこの関係にある
- **(b) 実行時は静的で、型は消去される** — 仮想機械は型が正しい前提で動く

L^ は **(a)** を採る。

L^ は Lua を継いだ設計であり、唯一のデータ構造がテーブル、
プロトタイプベース、コルーチンを持つ。この構造では値がどのみちタグを必要とする。
(b) を採ると、型検査を緩めた動作が **別の値表現と別の命令セット** を要求し、
実質2つの仮想機械を抱えることになる。

(a) であれば、型検査を緩めた動作は検査層を弱めるだけで得られる。

### 2.2 具体的な表現形式［確定・旧 P2］

> **タグ付き共用体を採る。** Lua 5 の `TValue` に相当する形である。

```c
typedef struct {
    union {
        double    real;
        int64_t   integer;
        bool      boolean;
        LhatObject *object;
    } as;
    LhatValueTag tag;
} LhatValue;
```

#### 整数は 64 ビット［確定・重要］

01 の 4.1 が「Lua 5.3 以降と同様に整数型と浮動小数点型を区別する」と定めている。
その整数は **64 ビット符号つき** とする。

02 の 14.8 のとおり **型としては `number^` ひとつ** であり、
整数と実数の区別は実行時の表現の話である。本節はその表現を定めている。

グルー言語としてファイルの大きさ・時刻・識別子を扱う以上、
2^53 を超える整数が丸まらないことに意味がある。

#### NaN boxing を採らなかった理由

もう一方の案は NaN boxing である。
IEEE 754 の倍精度で NaN を表すビット列は 2^52 通り近くあるのに対し、
演算が実際に生む NaN は1つしかない。余った約 51 ビットに他の型を詰めれば、
**あらゆる値が 8 バイト1語** に収まる。LuaJIT と JavaScriptCore が採っている。

利点は小さくない。テーブルが唯一のデータ構造である以上、
配列部の消費とキャッシュ効率が2倍違う。

**採らないのは、ペイロードが約 48 ビットしかないためである。**
64 ビット整数が入らない。入れるならヒープに置くことになり、
整数演算のたびに割り当てが起きる。

つまり NaN boxing を先に選ぶと、
**64 ビット整数を持つかという言語の決定を、値表現の都合が先に決めてしまう**。
順序が逆である。

移植性の条件も付く。NaN boxing は
利用者空間のポインタが 48 ビットに収まることを前提とし、
x86-64 の5段ページングや ARM64 の LVA を使う環境では成り立たない。

#### 後から差し替えられる形にしておく［確定］

6.2 が「値表現は決定を遅らせても安い」としているのは、
**外から見える性質（値がタグを持つ、2.1）が同じだから** である。

したがって仮想機械は **値を直接触らない**。
構成・判定・取り出しをすべてアクセサ経由にしておけば、
NaN boxing への差し替えは表現の層に閉じる。

将来 NaN boxing に移るなら、その時点で整数の幅を再考することになる。
本節はその判断を先送りしているのであって、閉じてはいない。

#### タグ

```text
nil^ / bool^ / 整数 / 実数 / string^ / table^ / サブルーチン / コルーチン / 誤り
```

整数と実数を別のタグにするのは 14.8 と矛盾しない。
**型はひとつ、表現はふたつ** である。

## 3. 型検査の厳格度

### 3.1 コンパイル単位ごとの設定とする［確定］

型検査の厳格度は **コンパイル単位ごとの設定** であり、言語の方言ではない。

- **strict** — 既定。型エラーをコンパイル時に報告する
- **relaxed** — 推論が決まらない箇所を動的として扱い、実行時に検査する

REPL の既定は relaxed、ソースファイルの既定は strict とする。
ただしどちらも切り替えられる。

- ファイルを relaxed でコンパイルできる（試作時に有用）
- REPL で strict を有効にできる（ファイルへ貼る前の確認に有用）

02 の 1.2 でコマンドインタプリタモードを
「ホストがランタイム生成時に指定する設定」としたのと同じ位置づけになる。

### 3.2 ソースの字面は変わらない［確定］

Memo.md L7 の「静的**自動**型付け」は型推論であり、注釈は省略できる。
したがって **strict と relaxed でソースの書き方は一切変わらない**。

差は「型の誤りをいつ報告するか」だけである。
書き分けが発生しないため、2つの方言に分かれることがない。

### 3.3 段の数は減らない［確定］

relaxed でも段は減らない。
型検査の段が **寛容になる**（推論が決まらない箇所を動的とみなし、
実行時検査を挿入する）だけである。

1つの経路にフラグが1つ増えるという構成になる。

### 3.4 推論の範囲［確定］

Memo.md L7 の「静的**自動**型付け」は型推論を意味する。
どこまでを推論するかを次のとおり定める。

#### 返り値型は推論する

明示しなければ、本体の `return^` から推論する。

```lhat
let^ foo = f^{ return^0 }
```

これは次のように書いたのと同じ意味になる。

```lhat
let^ foo = f^ :: number^ { return^0 }
```

`return^` が複数あれば、それらの合併になる。

```lhat
let^ bar = p^x:number^ {
    if^ x > 0 { return^nil^ }
    return^foo()
}
```

これは `p^number^ :: nil^|number^ ;` と解釈される。

#### 再帰する場合は明示を要する［提案］

自身を呼ぶ関数の返り値型は、自身に依存するため素朴な推論では決まらない。

```lhat
let^ f = f^{ … return^ f() … }
```

**再帰する関数・手続きは返り値型を明示する** こととする。
C++、Kotlin、Swift がいずれも同じ制限を課している。

#### 引数型は推論しない［確定］

引数の型は明示する。使用箇所から逆算することはしない。

使用箇所からの逆算は全域推論となり、
構造的な部分型付け（02 の 11.3）と組み合わさると急速に難しくなる。
返り値型の推論は本体を読み終えれば決まる局所的な処理であり、
1.1 の段階構成にそのまま乗る。将来の課題として残す。

### 3.5 relaxed の緩さ［確定・旧 P1］

> **relaxed が動的にするのは、推論が型を決められなかった箇所だけである。
> 静的に矛盾と分かるものは strict と同じく報告する。**

`1 + "a"` のように、推論が両辺の型を決めたうえで矛盾している場合、
relaxed でもコンパイル時の誤りになる。**型検査を切る設定ではない。**

#### 理由

4.1 の「保証は一方向」が意味を持つのはこの読みのときである。

relaxed で通ったものが strict で落ちる理由が **注釈が足りないことだけ** に限られるなら、
relaxed は strict への踏み台として働く。
矛盾まで通してしまうと、relaxed で動いていたものが strict で大量に落ちることになり、
移行の道のりが長くなる。

3.2 のとおり **strict と relaxed でソースの字面は変わらない**。
字面が同じものの意味が大きく違うと、
どちらで書かれたかを読み手が意識しなければならなくなる。

#### `any^` との関係［重要・旧 S16 と対］

02 の 13.7 が `any^` を **頂点型であり、絞り込むまで何もできない** と定めた。
これと relaxed は **別の機構である**。役割は重ならない。

- **`any^`** — 書き手が「何が来るかを言わない」と宣言する。
  静的に安全であり、使うには絞り込みが要る
- **relaxed** — 検査器が決められなかった箇所に **実行時検査を挿す**。
  書き手は何も書かない

一言でいえば、**`any^` は「何が来るか言わない」、relaxed は「今は確かめない」** である。

したがって **relaxed は決まらなかった型を `any^` に書き換えるのではない**。
書き換えると、`any^` の値には絞り込みなしで何もできない以上、
**relaxed のほうが strict より厳しくなる**。それは設定の意味と逆である。

## 4. ファイルと REPL の一致

### 4.1 保証は一方向になる［確定］

02 の 3.4 は、貼り付けたコードがファイルに書いたときと同じ動作をすることを
保証すると述べた。01 の 10.9 を採った理由の一部でもある。

厳格度に既定の差を設けると、この保証は **型のレイヤで一方向になる**。

- **保証される**: strict で通るコードは relaxed でも同じく動作する
- **保証されない**: relaxed で動いたコードが strict で通るとは限らない。
  型の誤りを含んだまま、その経路を実行しなかっただけかもしれない

TypeScript と JavaScript、mypy と Python が持つ非対称性と同じものである。

### 4.2 構文と意味は分岐しない［確定］

厳格度が変えるのは **診断の時期だけ** であり、次はいずれも変わらない。

- 字句解析の結果
- 構文木の形
- 実行時の意味

02 の 3.4 が扱っていた「同じテキストが場所によって違う構文木になる」種類の問題は、
厳格度の設定によっては生じない。

## 5. バイトコード

### 5.1 まず実行時検査つきの汎用命令［提案］

型が確定した箇所向けの特殊化命令は最初から作らない。
まず全命令が実行時に型を確認する形で作り、動作するものを得る。

特殊化は後から足せる。CPython 3.11 以降が採った順路であり、
先に汎用命令の意味を固めてから、確定した型の情報で特殊化命令に差し替える。

この順路であれば relaxed もそのまま動く。
特殊化は strict で型が確定した箇所にのみ適用される最適化になる。
