# L^ 処理の構成

ソースを受け取ってから実行するまでの段階構成と、
その構成を決めている実行時の値表現について定義する。

字句については [01-lexical-structure.md](01-lexical-structure.md)、
構文については [02-syntax.md](02-syntax.md) を参照。

記法ラベル（［確定］／［提案］／［未決］）の意味は [README.md](README.md) を参照。
本文書の未決事項には `P1`, `P2`, … の番号を振る。

**現状**: 段階構成、実行時の値表現、型検査の厳格度の扱いが確定している。
バイトコードと仮想機械の設計は未着手。

## 1. 段階構成

### 1.1 少なくとも4段になる［確定］

```text
ソース → 字句解析 → 構文木 → 型検査 → コード生成 → バイトコード
```

Lua が採る単一パス（トークンを読みながら直接バイトコードを出力する）は使えない。

Memo.md L7 の「静的自動型付け」は型推論を意味する。
推論は **ソースの後方にある情報を必要とする** 場合がある。

- 再帰関数の返り値型は、本体を読み終えるまで決まらない
- 相互再帰する定義は、互いを読み終えるまで決まらない
- 使用箇所から引数の型を推論する場合、定義より後ろを見る必要がある

Lua の単一パスが成立するのは動的型付けだからであり、
`expdesc` とレジスタ割当を読みながら確定できることが前提になっている。
L^ ではこの前提が崩れる。したがって **構文木を作る段が必須** である。

名前解決を型検査から分離して5段にする構成もありうる［提案］。
名前解決は型検査に必要な情報を用意する処理であり、
独立させたほうがスコープ規則（`$` `$$` `$^`、01 の 8 章）の実装が読みやすくなる。

### 1.2 単一パスを捨てて失うもの［確定］

Lua の `lcode.c` と `lparser.c` が実装している単一パスのコード生成技法
（`expdesc` による式の遅延評価、レジスタ割当、ジャンプパッチリスト）は、
L^ では **そのまま流用できない**。参照価値が下がる。

一方、これらと直交する部分は参照価値を保つ。

- レジスタ仮想機械のディスパッチループ
- 命令のビットレイアウト
- インクリメンタル GC と書き込みバリア
- 配列部とハッシュ部のハイブリッドなテーブル
- バイトコードの直列化

## 2. 実行時の値表現

### 2.1 値は型タグを持つ［確定・重要］

**実行時の値は自身の型を保持する。** 型情報を消去した表現は採らない。

これは本文書で最も変更費用の高い決定である。
後から覆すには仮想機械を作り直すことになる。

#### 2つの設計と、選んだ理由

- **(a) 実行時は動的で、静的型付けは検査層** — 値がタグを持ち、
  静的検査は実行前に正しさを証明する役を担う。
  TypeScript と JavaScript、Common Lisp の型宣言、Python と mypy がこの関係にある
- **(b) 実行時は静的で、型は消去される** — 仮想機械は型が正しい前提で動く

L^ は **(a)** を採る。

L^ は Lua を継いだ設計であり、唯一のデータ構造がテーブル、
プロトタイプベース、コルーチンを持つ。この構造では値がどのみちタグを必要とする。
(b) を採ると、型検査を緩めた動作が **別の値表現と別の命令セット** を要求し、
実質2つの仮想機械を抱えることになる。

(a) であれば、型検査を緩めた動作は検査層を弱めるだけで得られる。

### 2.2 具体的な表現形式［未決 → P2］

タグを持つことは確定しているが、持たせ方は未決。

- NaN boxing — 64 ビットの double に全値を詰める
- タグ付き共用体 — Lua 5 の `TValue` に相当する形

どちらもレジスタ仮想機械と両立する。3 章以降の決定には影響しない。

## 3. 型検査の厳格度

### 3.1 コンパイル単位ごとの設定とする［確定］

型検査の厳格度は **コンパイル単位ごとの設定** であり、言語の方言ではない。

- **strict** — 既定。型エラーをコンパイル時に報告する
- **relaxed** — 推論が決まらない箇所を動的として扱い、実行時に検査する

REPL の既定は relaxed、ソースファイルの既定は strict とする。
ただしどちらも切り替えられる。

- ファイルを relaxed でコンパイルできる（試作時に有用）
- REPL で strict を有効にできる（ファイルへ貼る前の確認に有用）

02 の 1.2 でコマンドインタプリタモードを
「ホストがランタイム生成時に指定する設定」としたのと同じ位置づけになる。

### 3.2 ソースの字面は変わらない［確定］

Memo.md L7 の「静的**自動**型付け」は型推論であり、注釈は省略できる。
したがって **strict と relaxed でソースの書き方は一切変わらない**。

差は「型の誤りをいつ報告するか」だけである。
書き分けが発生しないため、2つの方言に分かれることがない。

### 3.3 段の数は減らない［確定］

relaxed でも段は減らない。
型検査の段が **寛容になる**（推論が決まらない箇所を動的とみなし、
実行時検査を挿入する）だけである。

1つの経路にフラグが1つ増えるという構成になる。

### 3.4 relaxed の緩さ［未決 → P1］

「推論が決まらない箇所を動的として扱う」の範囲が未決。

- 推論が失敗した箇所だけを動的とするのか
- 明らかな型の矛盾も実行時まで通すのか

前者は「推論できない部分だけ諦める」設計、
後者は「型検査を実質的に無効化する」設計であり、性質がかなり違う。

## 4. ファイルと REPL の一致

### 4.1 保証は一方向になる［確定］

02 の 3.4 は、貼り付けたコードがファイルに書いたときと同じ動作をすることを
保証すると述べた。01 の 10.9 を採った理由の一部でもある。

厳格度に既定の差を設けると、この保証は **型のレイヤで一方向になる**。

- **保証される**: strict で通るコードは relaxed でも同じく動作する
- **保証されない**: relaxed で動いたコードが strict で通るとは限らない。
  型の誤りを含んだまま、その経路を実行しなかっただけかもしれない

TypeScript と JavaScript、mypy と Python が持つ非対称性と同じものである。

### 4.2 構文と意味は分岐しない［確定］

厳格度が変えるのは **診断の時期だけ** であり、次はいずれも変わらない。

- 字句解析の結果
- 構文木の形
- 実行時の意味

02 の 3.4 が扱っていた「同じテキストが場所によって違う構文木になる」種類の問題は、
厳格度の設定によっては生じない。

## 5. バイトコード

### 5.1 まず実行時検査つきの汎用命令［提案］

型が確定した箇所向けの特殊化命令は最初から作らない。
まず全命令が実行時に型を確認する形で作り、動作するものを得る。

特殊化は後から足せる。CPython 3.11 以降が採った順路であり、
先に汎用命令の意味を固めてから、確定した型の情報で特殊化命令に差し替える。

この順路であれば relaxed もそのまま動く。
特殊化は strict で型が確定した箇所にのみ適用される最適化になる。

### 5.2 仮想機械の形式［未着手］

レジスタ仮想機械を採る前提で検討する。命令の設計は本文書ではまだ扱わない。

## 7. 未決事項

- **P1 — relaxed の緩さ（3.4）**

  推論が失敗した箇所のみを動的とするか、型の矛盾も実行時まで通すか。

- **P2 — 値表現の具体形（2.2）**

  NaN boxing かタグ付き共用体か。

- **P3 — REPL での再定義（4 章に関連）**

  `x := 1` の後に `x := "文字列"` と入力したときの扱い。
  ソースファイル中では同一スコープでの再定義は誤りだが、
  対話的な試行では置き換えられることが期待される。
  GHCi はこれを遮蔽として扱う。

- **P4 — REPL での型環境の持ち越し**

  入力ごとに独立してコンパイルされる一方、定義は残る。
  strict を有効にした REPL では、推論した型環境を入力間で持ち越す必要がある。
  relaxed が既定である限り優先度は低い。
