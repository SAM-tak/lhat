# 04 誤りの表現と伝播

02 の 12.8 が「誤りは値として返す」とだけ定め、
表現の形・伝播の記法・受け取り損ねの検出を本文書に委ねた（S14）。ここで決める。

節番号のうち「02 の」「01 の」と前置きしたものは他文書を指す。
未決事項には `E` を冠して 12 章にまとめる。

---

## 1. 前提

02 の 12.8 で確定していることを再掲する。

- **L^ は例外機構を持たない。** 失敗しうる操作は誤りを表す値を返す
- 誤りは暗黙に伝播しない。したがって
  「後始末の最中に例外が飛んだらどうするか」という問題が発生しない
- `dispose()` は誤りを返さない（12.7）
- `finally^` は返り値を変更できない（10.5）

本文書はこの上に、値の形と、それを扱う記法を載せる。

---

## 2. 誤りの種別は型である［確定］

### 2.1 なぜテーブルではないのか［重要］

誤りを普通のテーブルで表す案があった。構造的型付けを採る以上、
`t^{ kind : string^, message : string^ }` と書けば済むように見える。**採らない。**

理由は 02 の 14.12 が多重定義のために定めた「互いに素」の規則にある。

> **構造どうしは、同名のメンバの型が互いに素でなければ、互いに素にならない。**

誤りを扱う記法は、`T|E` という値に対して
**「これは誤りか」を確実に判定できなければ成立しない**。
`E` がテーブル構造で `T` もテーブルなら、両方を満たす値が普通に作れてしまい、
この判定に答えがない。

```lhat
# もしテーブルで表したら
f^ load() -> t^{value : number^} | t^{kind : string^, message : string^};

# 両方を満たす値が作れる。どちらとして扱えばよいのか決まらない
{ value := 1, kind := "x", message := "y" }
```

言語の中核にある制御構造が、**型システムの強制できない命名規約** に乗ることになる。
`.kind` を持っていたら誤り、という約束は、破っても検査器が何も言わない。

### 2.2 `errordef^` — 種別を宣言する［確定］

誤りの種別は **あらかじめ宣言する**。宣言形式であり、名前を伴う。

```lhat
errordef^ IOError {
    NotFound,
    Denied,
}
```

種別は付随情報を宣言できる。

```lhat
errordef^ ParseError {
    Syntax { line : number^, column : number^ },
    Eof,
}
```

#### フィールドは既定値を持てる［確定・旧 E5］

```lhat
errordef^ ParseError {
    Syntax { line := 0, column := 0 },
    Eof,
}
```

既定値を書いた場合、**型は書かなくてよい**。初期値の型がそのフィールドの型になる。
両方書いてもよい。

```text
フィールド := 名前 : 型
            | 名前 := 式
            | 名前 : 型 := 式
```

##### なぜ `:=` なのか

02 の 14.6 の雛形が既に同じものを書いている。

```lhat
self^{ value1 := 0, value2 := "" }
```

**名前付きのフィールドに初期値を与える形** であり、種別のフィールドと同じである。
綴りを変える理由がない。

引数の既定値（02 の 13.4）に揃えて `名前 : 型 = 式` とする案もあったが採らない。
02 の 8.6 が **`=` を使えるのは式が現れえない位置だけ** と定めており、
その位置は `let^ 名前` の後と引数名の後の2つである。
`{ … }` の中はそこに含まれない。3つ目の例外を作らない。

##### 既定値を持つフィールドは生成時に省ける

2.5 のとおり、既定値のないフィールドは生成時にすべて与える。
既定値のあるフィールドは省いてよく、省けばその値になる。

02 の 14.11 が雛形について定めたのと同じ扱いである。
初期値は **生成のたびに評価される式** であり、格納された値ではない。

### 2.3 宣言が作るもの［確定］

`errordef^ IOError { NotFound, Denied }` は次を作る。

- **`IOError.NotFound`、`IOError.Denied`** — それぞれが **型**
- **`IOError`** — その2つの合併
- どちらも `error^` の部分型

```text
IOError.NotFound  <:  IOError  <:  error^
```

**種別が型であることが本章の要になっている。** 3 章と 7 章がこれに乗る。

どの種別も次の2つを持つ。宣言に書く必要はない。

| メンバ | 型 | 意味 |
| --- | --- | --- |
| `message` | `string^` | 人間向けの説明。既定は空文字列 |
| `cause` | `error^`\|`nil^` | 連鎖元。既定は `nil^`（10 章） |

種別を表す別のメンバは持たない。**種別は型そのもの** であり、
`typeof^(e)` が `IOError.NotFound` を返す。

### 2.4 構造的型付けの例外［確定・重要］

```lhat
errordef^ IOError   { NotFound, Denied }
errordef^ UserError { NotFound, Invalid }
```

この2つの `NotFound` は **構造が同じ** である。
02 の 11.3 と 14.9 の規則をそのまま適用すれば同じ型になり、取り違えが起きる。

> **誤りの種別の同一性は、構造ではなく宣言の場所で決まる。**

**これは構造的型付けの明示的な例外である。**

例外が正当なのは、記述している対象が違うためである。

- **`def^` は「形」を記述する。** 同じ形なら通じ合うべきである。
  それが構造的型付けの利点そのものであり、14.9 が名前を札に留めた理由でもある
- **`errordef^` は「互いに異なる種別」を宣言する。**
  別々に宣言した種別が混ざらないことが目的そのものである

実際に書かれる種別名は `NotFound` `Invalid` `Timeout` `Denied` に集中する。
**衝突は例外的な事故ではなく通常の事態** であり、
構造で同一視すると標準ライブラリと利用者の種別が一致してしまう。

同一性は **原文の宣言の位置** に結び付く。

TypeScript が構造的型付けを採りながら `enum` だけを公称にしているのが同じ例外である。

#### 記法にも違いが出る

02 の 14.9 が `def^` を式にしたのは、名前が同一性に関与しないからだった。
名前が札にすぎないなら束縛から拾えばよい。

**`errordef^` では名前が同一性そのものである。**
ならば名前は、束縛される先から拾うものではなく宣言に書かれるべきものになる。

> **記法の違いが、意味の違いを表している。**

無名の種別は書けない。書く手段が存在しない。
これは 02 の 14.10 の要請でもある。
無名の種別には注釈として書ける名前がなく、構造で書き表すこともできないためである。

### 2.5 生成 — `error^種別{ … }`［確定］

```lhat
return^ error^IOError.NotFound{ message := "no such file" }

return^ error^ParseError.Syntax{
    message := "unexpected ')'",
    line := 3,
    column := 12,
}
```

**既定値のないフィールドはすべて与える。**
既定値のあるものは省いてよい（2.2）。`message` と `cause` は常に任意である。

値として組み立ててから返してもよい。

```lhat
let^ e = error^IOError.Denied{ message := "permission denied" }
return^ e
```

#### `error^` の前置は働いている

`IOError.NotFound{ … }` と書けるようにする案もあったが、
その形では **構文解析器が型の知識なしに判別できない**。
修飾された名前に `{` が続く形は、10.7 によりテーブルリテラルが並んだ形とも読める。

`error^` が前に付けば、その1トークンで決まる。

### 2.6 `error^` は他のあらゆる型と互いに素［確定・重要］

> **誤りの種別を満たす値は、誤り以外のどの型も満たさない。**

これが 2.1 の問題を解く。`T|IOError` はいつでも判別できる。

02 の 14.12 が定めた互いに素の判定に、次が加わる。

- **異なる種別どうし** — 互いに素
- **種別と誤り以外** — 互いに素
- **`error^` と種別** — 互いに素にならない（上位型のため）

この性質は規則として置いたものであり、構造から導かれるものではない。
そこが宣言された型にする意味である。

## 3. 失敗しうる手続きの型［確定］

### 3.1 合併で書く

失敗しうる操作は、成功時の型と誤りの型の合併を返す。
02 の 11.5 の `|` をそのまま使う。新しい型構成子は要らない。

```lhat
f^ open(p:string^) -> file^|IOError;               # IOError のいずれか
f^ read(p:string^) -> string^|IOError.NotFound;    # これしか返さない
f^ risky() -> number^|error^;                      # どの誤りでもよい
p^ save(x:number^) -> IOError|nil^;
```

4つ目のように、**返す値がなく失敗だけしうる** 操作は誤りと `nil^` の合併を返す。
成功が `nil^` である。

**返しうる誤りを署名に書けることが 7 章を成り立たせている。**
Zig の error set にあたるものが、既にある記法だけで表せる。

### 3.2 略記を設けない［確定］

Zig の `!T` にあたる略記は **設けない**。`file^|IOError` と書く。

02 の 14.10 が「`typeof^(x).signature` の出力は、そのまま型注釈として解析できる」と定めた。
型を書き表す言語が2つあると、この要請に条件が付く。
`|` だけで足りている以上、増やす理由がない。

`nil^` 側との釣り合いも保たれる。
`number^|nil^` に略記がないのだから、こちらにもない。

## 4. `catch^` — その場で代替する［確定］

### 4.1 形

```lhat
let^ n = parse(s) catch^ 0
```

左の式が誤りを返したとき、**全体の値は右の式の値になる**。
誤りでなければ、全体の値は左の値から誤りを除いた型になる。

```lhat
let^ n = parse(s) catch^ 0        # n : number^
```

`catch^` は二項演算子であり、右辺は式である。文の並びは書けない。
それが要る場合は 6 章の絞り込みを使う。

左の式が失敗しえない場合、`catch^` は誤りとする。書いても働かないためである。

### 4.2 誤りの名前は `it^`［確定］

右辺からは、捕まえた誤りを `it^` で参照できる。

```lhat
let^ n = parse(s) catch^ fallbackFor(it^)
let^ n = parse(s) catch^ if^ it^ is^ ParseError.Eof: 0 el^: -1 ;
```

02 の 16.2 が `it^` を「焦点の既定の名前」と定めた。
`catch^` の右辺では誤りが焦点である。同じ語を同じ意味で使う。

名前を付け直す記法は設けない。`catch^` の右辺は式ひとつであり、
`it^` の指すものを見失う長さにならない。

### 4.3 優先順位［確定］

`catch^` は **すべての二項演算子より強く、単項演算子より弱い**。
02 の 11.6 の表に加える。

```lhat
let^ total = base + parse(s) catch^ 0
#               ~~~~~~~~~~~~~~~~ ここが catch^ の範囲
```

失敗するのは `parse(s)` であって `base + parse(s)` ではない。
**代替値はその操作の値の代わり** なのだから、
`catch^` は周囲の計算にではなく操作に付くべきである。

これを最も弱くする案（Zig の位置）もあったが、
その場合 `base + parse(s)` が先に結合し、
`number^` に `number^|IOError` を足す型の誤りになる。
書いた形と読みが一致しない。

右辺も単項までなので、`f() catch^ 0 + 1` は `(f() catch^ 0) + 1` である。
代替値に計算が要る場合は括弧を書く。

### 4.4 意図的に無視する［確定］

誤りを捨てる専用の記法は設けない。`catch^` で書ける。

```lhat
save(x) catch^ nil^      # 失敗しても構わない、と明示している
```

Go の `_` にあたるものが不要なのは 8.2 による。

## 5. `try^` — 呼び出し元へ返す［確定］

### 5.1 形

```lhat
let^ h = try^ open(p)
```

左の式が誤りを返したとき、**その誤りをそのまま今の手続きの返り値として返す**。
誤りでなければ、`try^` 全体の値は誤りを除いた型になる。

```lhat
f^ read(p:string^) -> string^|IOError {
    with^ h = try^ open(p) {
        return^ try^ h.readAll()
    }
}
```

`with^`（02 の 12 章）と組み合わさる。`try^` が誤りを返して抜けた場合も
`h.dispose()` は呼ばれる。5.2 のとおり `return^` と同じ側の脱出だからである。

`finally^` を直接書く場合は、02 の 9.2 が定める順序に従い **最後に置く**。
`finally^:` より後ろに書いた文はその節の本体になる。

```lhat
f^ read(p:string^) -> string^|IOError {
    let^ h = try^ open(p)
    return^ try^ h.readAll()
    finally^: h.dispose()
}
```

`try^ e` は `e catch^ { return^ it^ }` の意味だが、
02 の 8.2 により文の並びを式の中に書けないので、記法として設ける。

値を捨ててよい場合は文としても書ける。

```lhat
try^ save(x)
```

`try^` は単項演算子であり、11.6 の単項の水準に置く。
`try^ f() + 1` は `(try^ f()) + 1` である。

### 5.2 `return^` と同じ側の脱出［確定］

02 の 9.8 が既にこの場合を予告している。

> そうした脱出は `return^` と同じ側に属し、`finally^` のみを実行する。

したがって `try^` による離脱は次のように振る舞う。

| 脱出の仕方 | `last^` | `epilog^` | `finally^` |
| --- | --- | --- | --- |
| `try^` が誤りを返した | 実行しない | 実行しない | 実行 |

繰り返しの中で `try^` が働いた場合、`last^` も `epilog^` も走らない。
繰り返しにとって正常な終了ではないためである。

### 5.3 返り値が誤りを含むこと［確定］

`try^` は、**今の手続きの返り値の型が、その誤りを含む場合にのみ書ける**。

```lhat
f^ read(p:string^) -> string^|IOError {
    let^ h = try^ open(p)      # open が返すのは IOError のいずれか。含まれる
}

f^ read(p:string^) -> string^|IOError.NotFound {
    let^ h = try^ open(p)      # 誤り。IOError.Denied を返せない
}
```

報告は `try^` を書いた場所で行う。02 の 14.12、01 の 10.9 と同じ原則である。
返せない誤りを返そうとしているのは `try^` の側であり、
呼び出し元が悪いわけではない。

診断では代替を示す。

```text
try^ が返そうとする IOError.Denied は、この手続きの返り値に含まれていない。
返り値を string^|IOError にするか、catch^ でここで処理する。
```

**この検査は 3.1 で署名に誤りの集合を書けることの帰結である。**
どの誤りが素通りするかが署名から決まるため、その場で確かめられる。

## 6. `is^` による判別と絞り込み［確定］

### 6.1 形

`catch^` の右辺は式ひとつなので、
記録して続ける・再試行する・別の誤りに包んで返すといった処理は書けない。
その場合は合併のまま受けて絞り込む。

```lhat
let^ r = parse(s)
if^ r is^ ParseError.Syntax {
    report(r.line, r.column)      # 絞り込まれているのでフィールドが見える
    return^ r
}
# ここでは r : number^|ParseError.Eof
```

`is^` の意味と絞り込みの規則は 02 の 13.11 で定めた。
右辺には型を書き、`T` と書かれた位置に左辺を置けるかを問う。

**種別が型であること（2.3）と、種別が互いに素であること（2.6）から、
この判定は常に決定できる。**

絞り込みにより、宣言したフィールドが見えるようになる。
`ParseError.Syntax` と分かって初めて `.line` があると言えるためである。

### 6.2 3つの使い分け

| 書きたいこと | 記法 |
| --- | --- |
| 代替値で続ける | `expr catch^ v` |
| 呼び出し元へ返す | `try^ expr` |
| それ以外 | 合併のまま受けて `is^` で絞り込む |

## 7. 網羅性［確定・旧 E2］

「この手続きが返しうる誤りをすべて処理したか」を検査できる。

3.1 により署名に誤りの集合が書かれているので、
**特別な機構は要らない。合併の絞り込みがそのまま網羅性の検査になる。**

```lhat
f^ open(p:string^) -> file^|IOError;

let^ r = open(p)                        # r : file^|IOError.NotFound|IOError.Denied

if^ r is^ IOError.NotFound {
    create(p)
    elseif^ r is^ IOError.Denied:
        fallback()
    else^:
        use(r)
}
```

両方の種別を尽くしたので、最後の節では `r : file^` である。
尽くしていなければ、`r` を `file^` として使う場所で型の誤りになる（8 章）。

Zig の error set にあたるものを、
**総称型なしで** 実現している。合併と部分型だけで足りる。

### 種別を値にした案では解けなかった

種別を **値**（列挙体の要素など）として持たせる案では、これが成立しない。
署名に書ける情報が `kind : 何らかの列挙体の要素` までで止まり、
どの種別が返りうるかを型に載せられないためである。
径数化された誤り型が必要になり、L^ に総称型がないため行き止まりになる。

**種別を型にしたことが、この行き止まりを消している。**
経緯は 12 章に記す。

## 8. 取りこぼしの検出［確定］

S14 の3つ目、「値を受け取り損ねたことをどう検出するか」。

### 8.1 新しい機構は要らない［重要］

**型検査がそのまま検出になる。**

```lhat
let^ n = parse(s)      # n : number^|ParseError.Syntax|ParseError.Eof
let^ m = n + 1         # 誤り。number^ の位置に誤りを含む合併がある
```

Rust の `#[must_use]` にあたる仕組みは要らない。
誤りを処理しなければ、値が使えないだけである。

### 8.2 多値返却の廃止が効いている［重要］

Go の典型的な失敗は、`v, err := f()` の `err` を無視できることである。
静的検査では捕まらず、専用の検査器が後付けで警告している。

**L^ にはこの形が存在しない。** 02 の 13.8 が多値返却を廃止したためである。

> 誤りは、別に返る値ではなく、**必要な値そのものの中にある**。

無視できる別の値がないので、取りこぼす形が構文的に作れない。
13.8 は多値返却の展開規則（S17）を消すために決めたものだったが、
誤りの設計にも同じだけ効いている。

## 9. 後始末との関係［確定］

02 の 12.7・12.8 で決着している。ここでは帰結だけを確認する。

- `finally^` の中で失敗しうる操作を呼べば誤り値を受け取るが、
  **それを外へ伝播させる手段がない**。`try^` は使えない（5.3）。
  `finally^` は返り値を変更できないため（10.5）、返り値の型に誤りを足せない
- `dispose()` は誤りを返さない（12.7）ので、
  解放の途中で誤りが起きることはない
- したがって「抑制された例外」「巻き戻し中の失敗」にあたる分類が存在しない

`finally^` の中で誤りを受け取った場合にできるのは、記録するか、無視することである。

```lhat
finally^: flush() catch^ nil^
```

## 10. 誤りの連鎖［確定］

下位の誤りを包んで返す場合、`cause` に元の誤りを入れる。

```lhat
let^ r = parse(s)
if^ r is^ ParseError {
    return^ error^ConfigError.Invalid{
        message := "config could not be read",
        cause := r,
    }
}
```

`cause` は `error^|nil^` なので、辿る側は `?.` で書ける（01 の 7.1）。

```lhat
let^ depth = e.cause?.cause?.message
```

連鎖は **包む側が明示的に入れたときだけ** できる。自動では付かない。
自動で付けると、どこまで遡れるかが呼び出しの深さに依存し、実行時にしか分からなくなる。

`cause` の型が `error^` である以上、辿った先の種別は上位型までしか分からない。
必要なら `is^` で絞り込む。

## 11. 実行時の異常［確定・旧 E4］

02 の 12.7 が「実装上の欠陥による異常終了は誤りとは別の分類である」と述べ、
どちらに属するかを保留していた。ここで定める。

### 11.1 決定

> **実行時に検出される失敗は誤りとして返す。`catch^` で拾えない停止は設けない。**

ただし「実行時の異常」と括られていたものは同じ性質ではない。
それぞれ別の答えになり、**そのほとんどは実行時の問いですらなくなる**。

この決定が指しているのは **誤り**（本章が形を定める値）の範囲であって、
02 の 12.7 が別分類とした **panic**（検査器の約束が実行時に破れたもの、
旧 02 の 12.7改）はそもそも範囲の外にある。`t.foo` が実際には無かった、
演算に想定外の型が渡った、といった panic は依然として `catch^` では
拾えない — 11.6 に記す。

### 11.2改 ゼロ除算は実数へ広がる［確定］

02 の 14.8 が Lua 5.3 の数値模型を採ると定めた。当初は Lua 5.3 に倣い、
`/` はゼロで割っても誤りにならない（IEEE 754 の `inf`/`nan`）が
`//` と `%` はゼロで誤りを返す、と2つに分けていた。**これは撤回する。**

02 の 14.8改が桁溢れを「誤りにせず実数へ広げる」と定めたのと同じ理由が、
ゼロ除算にもそのまま当てはまる。`//` と `%` も、ゼロを割った時点で
整数の計算をやめて実数として計算し直す。実数の除算は元から失敗しないので、
そこから先は `/` と同じ答えになる。

```lhat
a / b        # number^。失敗しない
a // b       # number^。ゼロで割れば inf/nan（実数へ広がる）
a % b        # number^。同じく inf/nan
```

`ArithError.DivideByZero` のような誤り種別を新設する案を検討したが、
12.4 のとおり撤回した。

#### 汚染が起きない

誤りを返す操作はその返り値を合併にする（11.3, 11.4）。
ゼロ除算がそちらに合流していたら、`//` `%` を使う **すべての式** が
合併に触れることになっていた。**実数へ広げる方式ならそれが起きない** —
`//` と `%` は常に `number^` のままである。

```lhat
let^ mean = total / count            # 触れない
let^ half = total // count           # ゼロを渡しても number^ のまま
```

これは本章のために作った例外ではなく、14.8改の決定から従っている。

### 11.3 表の添字［確定］

**「範囲外」という概念が存在しない。** 表は写像であり、鍵があるかないかしかない。

そして構造的型付けにより、2つの記法が**必要な線でちょうど分かれている**。

- **`t.foo`** — 静的なメンバ。型検査器が構造を知っているので `T` である。
  型にないメンバを書けば **静的な誤り** になる。実行時の問いにならない
- **`t[k]`** — 動的な鍵。`T|nil^` である

```lhat
t.foo        # T。静的に解決する
t[k]         # T|nil^
let^ v = t[k] ?? 0     # 欠落したときの既定値は ?? で書く（02 の 11.7）
```

#### 欠落は失敗ではない

`t[k]` が誤りを返さないのは、**鍵がないことが写像に問うたことの普通の結果** だからである。
失敗と呼ぶと、存在を確かめるだけの問い合わせが毎回誤り値を作ることになる。

Lua の振る舞いを型に載せた形にあたる。

#### Lua にない利点

Lua では `t.foo` も実行時の索引であり、綴りを誤れば `nil` になる。
L^ は構造的型付けを採るため **`t.foo` が静的に解決する**。

その結果、`nil^` との合併に触れるのは
**本当に動的な添字だけ** に閉じ込められる。

### 11.4 `nil^` の参照［確定］

strict では **静的に防がれる**。`x : T|nil^` に対する `x.foo` は型の誤りであり、
`is^` で絞り込む（02 の 13.11）か `?.` を書くしかない。

**検査されたコードには、この実行時検査が残らない。**

relaxed（03 の 3.1）では静的に決まらない箇所が実行時に落ちる。
そこで `nil^` を参照した場合は誤りを返す。11.1 のとおり停止はしない。

### 11.5 費用［確定］

11.1 の選択による実行時の費用は小さい。内訳は次のとおり。

- **`//` と `%`** — 除算の前に比較と分岐が1つ増える。
  整数除算は数十サイクルを要し、予測の当たる分岐は実質ゼロに近い。
  **除算自体に埋もれる**
- **`t[k]`** — 検査は **既に存在する**。
  配列部か連想部かの判定と境界の確認は、返す値の種類によらず必要である。
  欠落時に何を返すかを変えても検査の回数は変わらない
- **`nil^` の参照** — strict では実行時検査そのものが生じない（11.4）

加えて、L^ はバイトコード仮想機械であり、
**値は既に型タグを持つ**（03 の 2.1）。合併を返すために箱詰めが増えることはない。
命令ディスパッチの費用に対して、分岐1つは計測に現れない。

誤りを値として返す方式は、例外機構に比べて
**成功する経路にも分岐が残る** という取引を伴う。Go と Zig が同じ取引をしており、
ネイティブ生成に進んだ段階でも許容されている範囲にある。

### 11.6 panic は行番号と演算子名を持って返る［確定］

02 の 12.7改 の panic は `catch^` で拾えないが、無言で落ちるわけではない。
`lhat_run` は必ず `LhatRunResult{ status, line, op_name, ... }` を
普通に返す — C レベルで異常終了することはなく、ホストが受け取って
次にどうするかを選ぶ（REPL なら次の入力へ進む、ファイル実行なら
終了する、など）。

- **`line`** — その命令が生まれた元のソース行。`LhatChunk.lines[]` という、
  命令列と並ぶ配列（命令ごとに1個、圧縮なし）から引く。列は持たない
  — 実行時の診断は「file:line」程度で十分とする（Lua も列を持たない）。
  検査時の診断（offset/line/column 全部）とは別物で、そちらの精度を
  落とすものではない
- **`op_name`** — 落ちた命令が演算子（02 の 11.8: `+` `-` `*` `/` `//` `%`
  `**` `..`）だったときのその綴り。演算子でない命令(呼び出し・添字等)
  では `NULL`

まず単純な形（命令ごとに1ワード）で作った。Lua 5.4 はここを
差分圧縮＋疎な絶対値アンカーで詰めているが、5.1 の「まず汎用形、
特殊化は後」により、メモリが実測で問題になった時点まで見送る。

#### `panic^` はプログラム自身が起こす panic

02 の 12.7改 に書いたとおり、検査器が検出する panic の他に
`panic^ EXPR` という文がある。Zig の `@panic()`、Rust の `panic!()` と
同じ位置づけ — 「ここへは来ないはず」を書いた本人が言明する。

```lhat
panic^ "実装されていない経路"
```

`EXPR` は `any^`（文字列に限らない）。`LHAT_BC_PANIC` は他の panic と
まったく同じ経路（`finish()` → `LhatRunResult{ status = LHAT_RUN_PANIC,
line, value }`）を通る。他の panic は `value` を常に `nil^` で捨てるが、
これだけは **書いた値がそのまま乗る** — メッセージは検査器の知らない
ことなので、行番号や演算子名のような機械的な情報では足りない。

値を答えないので `return^`/`break^` と同じ「戻ってこない」文であり、
`always_exits`（03 の 3.4 の網羅性判定）もその2つと同列に扱う —
`panic^` だけで終わる `f^` の本体は「値を返さないまま抜ける」エラーに
ならない。

なお本節が費用として扱っているのは実行時の話であり、
**設計上の費用は返り値が合併になること** のほうが大きい。
11.2 と 11.3 がその汚染を限定しているのは、そちらが本題だからである。

## 12. 撤回した案

決定の経緯として残す。いずれも「種別をどう表すか」の案であった。

### 12.1 テーブルで表す

2.1 のとおり。誤りと通常の値を確実に判別できない。

### 12.2 `kind : string^`

種別を文字列で持たせる案。当初の記述はこの形だった。

綴りを誤っても静的に捕まらない。
`kind = "FileNotFound"` と `kind = "FileNotFund"` の区別が付かない。

### 12.3 `kind` を汎用の列挙体の要素にする［撤回］

`enum^ IOError { NotFound, Denied }` のような **汎用の列挙体** を別に導入し、
`kind : enum^`（何らかの列挙体の要素）とする案。一度は文書化した。

綴りの誤りは捕まる。だが **網羅性が解けない**。

署名に書けるのは `-> file^|error^` までであり、
**どの種別が返りうるかを型に載せられない**。
載せるには `error^` を列挙体で径数化する必要があり、L^ に総称型がない。

```lhat
f^ open(p:string^) -> file^|error^;    # kind が IOError に限られることを書けない
```

**種別を値にしたことが原因** だった。
値は型に現れないので、署名が種別について何も言えない。

種別を型にすれば（2.3）、合併がそのまま集合を表し、
7 章の網羅性も 5.3 の検査も成立する。**総称型は要らなくなる。**

汎用の列挙体そのものも、この用途がなくなったため導入しない。
Memo.md L126–L134 のテーブルの採番糖衣は、着想として Memo.md に残る。
必要になった時点で、その時の要求に基づいて改めて起こす。

### 12.4 `ArithError.DivideByZero`［撤回・11.2改で解消］

ゼロ除算を `errordef^ ArithError { DivideByZero, }` という誤り値で
表す案を、11.2 は当初これで確定としていた。

実装に取り掛かる段になって、02 の 14.8改（桁溢れは誤りにせず実数へ広げる）
と同じ手が使えると気づいた。ゼロ除算も同様に実数へ広げれば、
`/` が既に持っている inf/nan の答えにそのまま合流する。
**専用の誤り種別も、それを言語コア組み込みにする経路も要らなくなった。**

検討の過程で、`errordef^` で宣言される種別（04 の 2.2）とは別に
**言語コア組み込みの誤り種別**（`errordef^` を書かずに存在する種別）を
どう作るかも設計した — プロセス全体で1回だけ、通常の
`lhat_error_kind_new`/`lhat_string_new` で確保し、二度と破棄しない
専用のヒープにキャッシュする案（`resolve_kind` に特別な1件として
知らせる）。ゼロ除算では要らなくなったが、**この経路自体は撤回しない** —
04 の 11.4（`nil^` 参照）が同じものを必要とする見込みが高く、
そちらに着手する際に改めて起こす。

## 14. 文法のまとめ

### 14.1 追加する語

`errordef^`、`try^`、`catch^`。どれも 01 の 2.1 により、
**字句解析器には何も足さない**。`^` を伴う語は既に1種のトークンであり、
意味を知るのは構文解析器だけである。

### 14.2 形

```text
文 := errordef^ 名前 { 種別, … }
    | try^ 呼び出し                # 5.1。値を捨てる場合

種別 := 名前
      | 名前 { 名前 : 型, … }      # 付随情報を宣言する場合

式 := 式 catch^ 式                 # 4 章
    | try^ 式                      # 5 章
    | error^ 修飾名 { 要素, … }    # 2.5
```

### 14.3 優先順位

02 の 11.6 の表に2行が加わる。弱い順に、

- `catch^` — `as^` より強く、単項より弱い。左結合
- `try^` — 単項の水準

### 14.4 型

```text
型 := … | error^ | 種別の集合の名前 | 修飾された種別名
```

```lhat
error^                # どの誤りでもよい
IOError               # IOError のいずれか
IOError.NotFound      # この種別
```

修飾された名前を型として書けることが要る。02 の 13 章の型の文法に加わる。

### 14.5 02 の 14.13 の族との関係

02 の 14.6 の `self^{ … }` は
「組み込みの識別子に `{ … }` が直に続く形」である。

`error^ 修飾名 { … }` は **この族ではない**。間に名前が入る。
構文解析器は `error^` の次のトークンを見るだけで区別できる。

- `error^` の次が名前 — 生成（2.5）
- `error^` の次が `{` — 誤り。種別を書くよう促す
- 型の位置の `error^` — 上位型（13.4）
