# 04 誤りの表現と伝播

02 の 12.8 が「誤りは値として返す」とだけ定め、
表現の形・伝播の記法・受け取り損ねの検出を本文書に委ねた（S14）。ここで決める。

節番号のうち「02 の」「01 の」と前置きしたものは他文書を指す。
未決事項には `E` を冠して 10 章にまとめる。

---

## 1. 前提

02 の 12.8 で確定していることを再掲する。

- **L^ は例外機構を持たない。** 失敗しうる操作は誤りを表す値を返す
- 誤りは暗黙に伝播しない。したがって
  「後始末の最中に例外が飛んだらどうするか」という問題が発生しない
- `dispose()` は誤りを返さない（12.7）
- `finally^` は返り値を変更できない（10.5）

本文書はこの上に、値の形と、それを扱う2つの記法を載せる。

---

## 2. `error^` は組み込み型［確定］

### 2.1 なぜテーブルではないのか［重要］

誤りを普通のテーブルで表す案があった。構造的型付けを採る以上、
`t^{ kind : string^, message : string^ }` と書けば済むように見える。**採らない。**

理由は 02 の 14.12 が多重定義のために定めた「互いに素」の規則にある。

> **構造どうしは、同名のメンバの型が互いに素でなければ、互いに素にならない。**

誤りを扱う記法は、`T|E` という値に対して
**「これは誤りか」を確実に判定できなければ成立しない**。
`E` がテーブル構造で `T` もテーブルなら、両方を満たす値が普通に作れてしまい、
この判定に答えがない。

```lhat
# もしテーブルで表したら
f^ load() -> t^{value : number^} | t^{kind : string^, message : string^};

# 両方を満たす値が作れる。どちらとして扱えばよいのか決まらない
{ value := 1, kind := "x", message := "y" }
```

言語の中核にある制御構造が、**型システムの強制できない命名規約** に乗ることになる。
`.kind` を持っていたら誤り、という約束は、破っても検査器が何も言わない。

組み込み型にすれば、この判定を宣言で与えられる（2.4）。

**表現力は落ちない。** 付随情報は `payload` に持たせる（2.2）ので、
テーブルで表した場合の柔軟性はそのまま残る。
捨てるのは「誤りと通常の値が区別できない」という性質だけである。

### 2.2 `error^` の構造［確定］

`error^` は次のメンバを持つ組み込み型とする。

| メンバ | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `kind` | `string^` | 必須 | 種別。判別に使う |
| `message` | `string^` | 任意 | 人間向けの説明。既定は空文字列 |
| `payload` | `table^` | 任意 | 付随情報。既定は空テーブル |
| `cause` | `error^`\|`nil^` | 任意 | 連鎖元。既定は `nil^`（9 章） |

`kind` を必須にするのは、**判別が `kind` で行われる** ためである。
`message` だけを持つ誤りは、呼び出し側が文字列を照合するしかなくなる。

利用者が独自の誤り型を `def^` で作る仕組みは設けない。
種別は `kind` で、付随情報は `payload` で表す。
`error^` が1種であることが、2.4 の性質を維持する費用を最も小さくする。

### 2.3 生成 — `error^{ … }`［確定］

```lhat
e := error^{
    kind := "FileNotFound",
    message := "no such file",
    payload := { path := p },
}
```

02 の 14.6 の `self^{ … }` と同じ形である。両者は同じ族に属する。

> **組み込みの識別子に `{ … }` が直に続く形は、その種類の値を名前付きの場で構成する。**

`self^` と同じく、`{` が直に続く場合に限りこの形になる。
それ以外の位置の `error^` は型名である。型と式は別の文法なので衝突しない。

### 2.4 `error^` は他のあらゆる型と互いに素［確定・重要］

> **`error^` を満たす値は、他のどの型も満たさない。**

これが 2.1 の問題を解く。`T|error^` はいつでも判別できる。
`T` が何であっても、`T` 側の値が誤りと見分けられなくなることはない。

02 の 14.12 が定めた互いに素の判定に、次の行が加わる。

- `error^` と `error^` 以外 — **常に互いに素**

この性質は規則として置いたものであり、構造から導かれるものではない。
そこが組み込み型にする意味である。

## 3. 失敗しうる手続きの型［確定］

### 3.1 `T|error^`

失敗しうる操作は、成功時の型と `error^` の合併を返す。
02 の 11.5 の `|` をそのまま使う。新しい型構成子は要らない。

```lhat
f^ read(p:string^) -> string^|error^;
f^ parse(s:string^) -> number^|error^;
p^ save(x:number^) -> error^|nil^;
```

3つ目のように、**返す値がなく失敗だけしうる** 操作は `error^|nil^` を返す。
成功が `nil^` である。

### 3.2 略記を設けない［確定］

Zig の `!T` にあたる略記は **設けない**。`number^|error^` と書く。

02 の 14.10 が「`rawsignature^` の出力は、そのまま型注釈として解析できる」と定めた。
型を書き表す言語が2つあると、この要請に条件が付く。
`|` だけで足りている以上、増やす理由がない。

`nil^` 側との釣り合いも保たれる。
`number^|nil^` に略記がないのだから、`number^|error^` にもない。

## 4. `catch^` — その場で代替する［確定］

### 4.1 形

```lhat
n := parse(s) catch^ 0
```

左の式が誤りを返したとき、**全体の値は右の式の値になる**。
誤りでなければ、全体の値は左の値から `error^` を除いた型になる。

```lhat
n := parse(s) catch^ 0        # n : number^
```

`catch^` は二項演算子であり、右辺は式である。文の並びは書けない。
それが要る場合は 6 章の絞り込みを使う。

左の式が失敗しえない場合、`catch^` は誤りとする。書いても働かないためである。

### 4.2 誤りの名前は `it^`［確定］

右辺からは、捕まえた誤りを `it^` で参照できる。

```lhat
n := parse(s) catch^ fallbackFor(it^)
n := parse(s) catch^ if^ it^.kind = "Empty": 0 el^: -1 ;
```

02 の 16.2 が `it^` を「焦点の既定の名前」と定めた。
`catch^` の右辺では誤りが焦点である。同じ語を同じ意味で使う。

名前を付け直す記法は設けない。`catch^` の右辺は式ひとつであり、
`it^` の指すものを見失う長さにならない。

### 4.3 優先順位［確定］

`catch^` は **すべての二項演算子より強く、単項演算子より弱い**。
02 の 11.6 の表に加える。

```lhat
total := base + parse(s) catch^ 0
#               ~~~~~~~~~~~~~~~~ ここが catch^ の範囲
```

失敗するのは `parse(s)` であって `base + parse(s)` ではない。
**代替値はその操作の値の代わり** なのだから、
`catch^` は周囲の計算にではなく操作に付くべきである。

これを最も弱くする案（Zig の位置）もあったが、
その場合 `base + parse(s)` が先に結合し、
`number^` に `number^|error^` を足す型の誤りになる。
書いた形と読みが一致しない。

右辺も単項までなので、`f() catch^ 0 + 1` は `(f() catch^ 0) + 1` である。
代替値に計算が要る場合は括弧を書く。

### 4.4 意図的に無視する［確定］

誤りを捨てる専用の記法は設けない。`catch^` で書ける。

```lhat
save(x) catch^ nil^      # 失敗しても構わない、と明示している
```

Go の `_` にあたるものが不要なのは 7.2 による。

## 5. `try^` — 呼び出し元へ返す［確定］

### 5.1 形

```lhat
h := try^ open(p)
```

左の式が誤りを返したとき、**その誤りをそのまま今の手続きの返り値として返す**。
誤りでなければ、`try^` 全体の値は `error^` を除いた型になる。

```lhat
f^ read(p:string^) -> string^|error^ {
    h := try^ open(p)
    finally^: h.dispose()
    return^ try^ h.readAll()
}
```

`try^ e` は `e catch^ { return^ it^ }` の意味だが、
02 の 8.2 により文の並びを式の中に書けないので、記法として設ける。

値を捨ててよい場合は文としても書ける。

```lhat
try^ save(x)
```

`try^` は単項演算子であり、11.6 の単項の水準に置く。
`try^ f() + 1` は `(try^ f()) + 1` である。

### 5.2 `return^` と同じ側の脱出［確定］

02 の 9.8 が既にこの場合を予告している。

> そうした脱出は `return^` と同じ側に属し、`finally^` のみを実行する。

したがって `try^` による離脱は次のように振る舞う。

| 脱出の仕方 | `last^` | `epilog^` | `finally^` |
| --- | --- | --- | --- |
| `try^` が誤りを返した | 実行しない | 実行しない | 実行 |

繰り返しの中で `try^` が働いた場合、`last^` も `epilog^` も走らない。
繰り返しにとって正常な終了ではないためである。

### 5.3 返り値が `error^` を含むこと［確定］

`try^` は、**今の手続きの返り値の型が `error^` を含む場合にのみ書ける**。
含まない手続きの中に書いたら誤りとする。

報告は `try^` を書いた場所で行う。02 の 14.12、01 の 10.9 と同じ原則である。
返せない誤りを返そうとしているのは `try^` の側であり、
呼び出し元が悪いわけではない。

診断では代替を示す。

```text
try^ はこの手続きの返り値に error^ が含まれていないと書けない。
返り値を string^|error^ にするか、catch^ でここで処理する。
```

## 6. 絞り込みで扱う［確定］

### 6.1 `is^` による判別

`catch^` の右辺は式ひとつなので、
記録して続ける・再試行する・別の誤りに包んで返すといった処理は書けない。
その場合は合併のまま受けて絞り込む。

```lhat
r := parse(s)
if^ r is^ error^ {
    log(r.message)
    return^ error^{ kind := "ConfigInvalid", message := "bad config", cause := r }
}
# ここでは r : number^
```

`is^` は 02 の 11.6 で比較の水準に置かれている演算子である。
`r is^ error^` は 2.4 により常に判定できる。

`if^` の分岐の中で `r` の型が狭まること（絞り込み）は、
合併一般に対する規則として 02 の 13 章に属する。**まだ書かれていない（E3）。**
本章が必要とするのは `error^` に対する絞り込みだけであり、
それは 2.4 から従う。

### 6.2 3つの使い分け

| 書きたいこと | 記法 |
| --- | --- |
| 代替値で続ける | `expr catch^ v` |
| 呼び出し元へ返す | `try^ expr` |
| それ以外 | 合併のまま受けて `is^` で絞り込む |

## 7. 取りこぼしの検出［確定］

S14 の3つ目、「値を受け取り損ねたことをどう検出するか」。

### 7.1 新しい機構は要らない［重要］

**型検査がそのまま検出になる。**

```lhat
n := parse(s)      # n : number^|error^
m := n + 1         # 誤り。number^ の位置に number^|error^ がある
```

Rust の `#[must_use]` にあたる仕組みは要らない。
誤りを処理しなければ、値が使えないだけである。

### 7.2 多値返却の廃止が効いている［重要］

Go の典型的な失敗は、`v, err := f()` の `err` を無視できることである。
静的検査では捕まらず、専用の検査器が後付けで警告している。

**L^ にはこの形が存在しない。** 02 の 13.8 が多値返却を廃止したためである。

> 誤りは、別に返る値ではなく、**必要な値そのものの中にある**。

無視できる別の値がないので、取りこぼす形が構文的に作れない。
13.8 は多値返却の展開規則（S17）を消すために決めたものだったが、
誤りの設計にも同じだけ効いている。

## 8. 後始末との関係［確定］

02 の 12.7・12.8 で決着している。ここでは帰結だけを確認する。

- `finally^` の中で失敗しうる操作を呼べば誤り値を受け取るが、
  **それを外へ伝播させる手段がない**。`try^` は使えない（5.3）。
  `finally^` は返り値を変更できないため（10.5）、返り値の型に `error^` を足せない
- `dispose()` は誤りを返さない（12.7）ので、
  解放の途中で誤りが起きることはない
- したがって「抑制された例外」「巻き戻し中の失敗」にあたる分類が存在しない

`finally^` の中で誤りを受け取った場合にできるのは、記録するか、無視することである。

```lhat
finally^: flush() catch^ nil^
```

## 9. 誤りの連鎖［確定］

下位の誤りを包んで返す場合、`cause` に元の誤りを入れる。

```lhat
r := parse(s)
if^ r is^ error^ {
    return^ error^{
        kind := "ConfigInvalid",
        message := "config could not be read",
        cause := r,
    }
}
```

`cause` は `error^|nil^` なので、辿る側は `?.` で書ける（01 の 7.1）。

```lhat
root := e.cause?.cause?.kind
```

連鎖は **包む側が明示的に入れたときだけ** できる。自動では付かない。
自動で付けると、どこまで遡れるかが呼び出しの深さに依存し、
`payload` に何が入っているかと同じく実行時にしか分からなくなる。

## 10. 未決事項

- **E1 — `kind` の型**

  現在は `string^`。Memo.md L127 の `enum^` を導入すれば、
  綴りの誤りを静的に捕まえられ、網羅性の検査も可能になる。
  `enum^` 自体が未仕様のため、そちらが決まってから見直す。

- **E2 — 誤りの一覧を静的に知る手段**

  Zig の error set にあたるもの。
  「この手続きが返しうる `kind` の集合」を型に載せられると、
  `catch^` の網羅性を検査できる。E1 に依存する。

- **E3 — 合併の絞り込み規則（02 の 13 章）**

  `if^ r is^ error^ { … }` の分岐内で `r` の型が狭まる規則。
  `error^` に限れば 2.4 から従うが、合併一般の規則は書かれていない。
  02 の 13 章に属する。

- **E4 — 実行時の異常と誤りの区別**

  02 の 12.7 が「実装上の欠陥による異常終了は誤りとは別の分類」と述べている。
  ゼロ除算、範囲外の添字、`nil^` の参照が
  `error^` になるのか、それとも回復不能な停止になるのかは未決。
  後者にすると `catch^` で拾えない停止が存在することになる。

## 11. 文法のまとめ

### 11.1 追加する語

`try^` と `catch^`。どちらも 01 の 2.1 により、
**字句解析器には何も足さない**。`^` を伴う語は既に1種のトークンであり、
意味を知るのは構文解析器だけである。

### 11.2 形

```text
式 := 式 catch^ 式          # 4 章
    | try^ 式               # 5 章
    | error^{ 要素, … }     # 2.3

文 := try^ 呼び出し          # 5.1。値を捨てる場合
```

### 11.3 優先順位

02 の 11.6 の表に2行が加わる。弱い順に、

- `catch^` — `as^` より強く、単項より弱い。左結合
- `try^` — 単項の水準

### 11.4 型

```text
型 := … | error^
```

`error^` は組み込みの型名であり、`number^` などと同じ水準に置く。
