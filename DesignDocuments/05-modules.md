# 05 名前空間とモジュール

名前をまとめて別の単位から取り込む仕組みを定める。

節番号のうち「01 の」「02 の」「03 の」「04 の」と前置きしたものは他文書を指す。
未決事項には `M` を冠して 9 章にまとめる。

---

## 1. 動機

発端は誤りの種別名の衝突である。
`errordef^` の種別名が標準ライブラリと利用者のコードで衝突する。

だが **これは誤りに限った問題ではない**。
`def^` を束縛した名前も、手続きの名前も同じように衝突する。
種別を入れ子にしても、衝突する場所が1つ減るだけで解決しない。

01 の 8 章のスコープ指定子（`$` `$^`）は
**入れ子のスコープを指すもの** であり、名前空間ではない。
`$` がファイルスコープを指すので単位の概念は字句の段階で先取りされているが、
単位をまたいで名前を渡す手段が別に要る。

---

## 2. 名前の環境はひとつ［重要］

### 2.1 なぜひとつでなければならないか

02 の 14.9 は **「定義の右辺に `def^` が直接現れる場合、その名前を型の名前として採る」**
と定めている。値の場と型の場が分かれていると、この決定と食い違う。

```lhat
let^ Foo = def^{ self^{ v = 1 } }
let^ x : Foo = Foo.new()          # Foo は値としても型としても引ける必要がある
```

### 2.2 ひとつにする

> **名前の場はひとつである。ひとつの名前は値・型・その両方のいずれかを指す。**

| 宣言 | 指すもの |
| --- | --- |
| `let^ x = 1` | 値 |
| `let^ Foo = def^{ … }` | 値（定義そのもの）と型（そのインスタンス） |
| `errordef^ E { … }` | 型のみ |

同じ場にあるので、`errordef^ E` の後の `let^ E = 1` は
02 の 8.7 の再定義として誤りになる。**衝突が見えるようになる。**

#### 場が同じでも、型の位置に書けるとは限らない

上の表のとおり `let^ x = 1` が指すのは **値だけ** である。
「その値の型」を名前で指す機能は、本節も 02 の 13 章も定めていない。

```lhat
let^ x = 1
let^ y : x = 2      # 誤り。x は型を指さない
```

とはいえ「定義と `errordef^` だけを型とする」まで狭めると、
実際には型として書かれているものが落ちる。

- **定義が自分自身を指す場合** — `def^` の中からその束縛名を書くと、
  その時点で束縛の型はまだ定義に定まっていない
- **ホストが登録した型**（8.8）と **`require^` が答える単位のメンバ**（6.1）

そこで線は **構造を持たない値** に引く。

- **拒む** — `number^` `string^` `bool^` `nil^`、サブルーチン、コルーチン。
  問える構造がなく、型として書ける意味がない
- **通す** — テーブルであるもの。02 の 11.3 が同一性を構造で決めるので、
  定義・ホスト型・単位・手で書いたテーブルのいずれも
  「その形を持つか」を問う対象になる

`self^` と `def^` は別に拒む（02 の 13.1）。前者は構造を持つ値であり、
後者は定義そのものなので、この線では止まらない。

#### 定義名を型として書くとインスタンスを指す

02 の 14.7 が「注釈に定義名を書くと **そのインスタンスが持つものすべて** を
要求する」と述べている。持つのは雛形の欄と受け手を取るメンバであり、
`new` と静的メンバは定義のものである。

```lhat
let^ x : Foo = Foo.new()
```

`Foo` は値としては **定義**、型としては **そのインスタンス** を意味する。
14.7 の記述をそのまま読んだ結果であり、新しい規則ではない。
定義そのものを注釈に書きたい場合は、14.10 の `self^{ … }` の区画を持つ形を書く。

## 3. 単位は `module^` を宣言する

```lhat
module^ namespace1.module1
```

- **1つのファイルに1回まで。** 2回目は誤り
- ファイルの先頭に置く
- 名前は `.` で区切れる
- **ファイルの置き場所から独立している**

### 3.1 パスから独立させる理由

ファイルの位置は都合で動く。型の名前が位置に縛られていると、
**ファイルを移すだけで診断の文言と型のラベルが変わる**。

宣言された名前は 7 章で型のラベルになり、5.3 で登録の鍵になる。
どちらもファイルの位置とは無関係であってほしい。

`module^` が名乗ったパスは **検査の結果に残る**。5.5 の省略形が
それを読んで束縛先を決めるためである。7.1 のラベルもここから採る。

### 3.2 省略できる

`module^` のないファイルも読み込める。その場合、型のラベルには解決したパスを使う。

主となるスクリプトに単位名は要らない。
`require^` される側は付けるのが望ましい、という関係になる。

#### スクリプトの最上位は `p^...` である

> **`module^` の無い単位（スクリプト）の最上位は `p^...` の本体であり、
> `...` はそれを走らせたものが渡した引数を集めた表である。**

コマンドラインなら `lhat --run main.lh a b` の `a` `b`（文字列）、
`require^` なら空の表、8.8改 の `std.load` が答えた閉包なら呼び出しの引数。
型は `t^{any^[]}` で、読む側が `fits^` で絞る。

```lhat
let^ args = ...
for^ a in^ args { … }
```

`module^` を持つ単位は `require^` の相手で、引数を取らない——そこで `...` は
名前ではない。3.1 と対で、**単位名を持つか持たないかが「ライブラリか
スクリプトか」を決める**。

## 4. `public^` が公開を決める

```lhat
module^ namespace1.module1

public^ errordef^ Error {
    SomeError,
    FatalError,
}

let^ privateValue = 0

public^ let^ publicProc = p^ { print(privateValue) }
```

- **既定は非公開。** `public^` を付けたものだけが外から見える
- 付けられるのは単位の最上位の宣言（`let^`、`errordef^`）に限る。
  `public^ var^` は認めない（4.4）
- 公開された名前が `require^` の返すテーブルのメンバになる

### 4.1 末尾の `return` を書かせない［重要］

Lua の `require` は、モジュールがファイルの末尾でテーブルを `return` する約束で成り立つ。
**これは踏襲しない。**

理由は書き味だけではない。

> **`return <式>` は実行しなければ何が公開されるか分からない。**

返る値は実行時に組み立てられうるので、**単位を実行せずに公開分を知ることができない**。
6 章が型検査に依存を辿らせる以上、これは成立しない。

`public^` は宣言ごとの印なので、**構文解析だけで公開分が決まる**。
6 章の静的な取り込みと、`return` を書かせないことは互いを支えている。

書き忘れの事故が消えるのは副次的な利得である。
Lua では `return` を忘れても読み込みは成功し、使う場所で初めて `nil` になる。

### 4.2 公開されるのは名前であって定義ではない

`public^` は **その名前を外から見えるようにする** だけである。
非公開の名前を公開された手続きが使うことは妨げない。上の `privateValue` がそれにあたる。

### 4.3 公開しても型の求め方は変わらない

`public^` は名前を外から見えるようにするだけであり、**型注釈を要求しない**。
公開された `p^`・`f^` の引数と返り値は、非公開のものとまったく同じに
03 の 3.4 が推論する。

```lhat
public^ let^ add = p^ x, y { return^ x + y }        # 通る。x も y も number^ に決まる
public^ let^ hold = p^ x { }                        # 誤り。x を決めるものが無い
```

穴の開いた署名が単位の外へ出ないことは、公開の側の規則ではなく
**03 の 3.1③ が単位ぜんたいに課している**——決まらなかった型は
公開・非公開によらずその場で報告される。公開分だけを別扱いする規則を
重ねる必要がない。

03 の 3.4改4 の呼び出し形は、**公開された名前には集めない**。公開された
署名は他の単位の呼び手への約束であり、この単位が自分の呼び出しで約束を
狭めてよい理由がない。公開名の型を決めるのは本体の要求と書いた注釈だけ
——上の `hold` が誤りのままなのはこのためで、単位の中に `hold(1)` と
書き足しても変わらない。

> 4.1 — **何が公開されるか** は構文解析だけで決まる
> 4.3 — **公開されたものの型に穴が無い** ことは単位ぜんたいの性質である

書き手が署名を本体から切り離したければ、束縛に書けばよい（03 の 3.4改）。

```lhat
public^ let^ add : p^number^, number^ -> number^; = p^ x, y { return^ x + y }
```

これは書き手の選択であって要求ではない。要求にしない理由は、**固定できる
範囲がサブルーチンの署名で終わらない** ことにある。公開された `def^` は
メンバの型も `self^` のデータメンバの型も推論で決まるので、
「本体を1行足すと公開している型が変わる」を本当に塞ぐならそこまで
書かせることになる。署名だけを特別扱いしても、守っているつもりの性質は
守れない。

### 4.4 公開する束縛は `let^` である

`public^ var^` は認めない。

```lhat
public^ let^ answer = 42     # よい
public^ var^ answer = 42     # 誤り
```

**理由**: 01 の 8.3 は「グローバル変数は持たない」と定めている。
`public^ var^` は **他の単位から見える名前が、その単位の与り知らぬところで
変わる** ものであり、綴りを替えたグローバル変数にほかならない。
8.1 の「取り込まないものは何も見えない」を守っても、
取り込んだものが黙って変わるなら同じ問題が戻ってくる。

4.1 と 4.3 が並べた一方向の保証にもう1行が加わる。

> 4.1 — **何が公開されるか** は構文解析だけで決まる
> 4.3 — **公開されたものの型に穴が無い** ことは単位ぜんたいの性質である
> 4.4 — **公開された名前が何を指すか** は取り込んだ後で変わらない

単位の状態を動かしたければ、状態は非公開の `var^` に置き、
`public^ let^` の `p^` を通す。**何が変えるのかが単位の中に閉じる。**

```lhat
var^ count = 0                        # 非公開
public^ let^ bump = p^ { count := count + 1 }
public^ let^ current = f^ -> number^ { return^ count }
```

### 4.5 公開した名前の型はホストから読める

> **ホストは検査の後、単位が公開した名前とその型を C から読み、
> 書いた型への適合を訊ける。**

ゲームのループがスクリプトの `update` を毎フレーム呼ぶとき、`update` が
`p^number^;` でなければ最初の呼び出しで型誤りになる——それを**起動時**に、
単位が実際に書いた型を添えて言いたい。検査器は既に答えを持っている
（4.3: 公開されたものの型に穴は無い）ので、それを渡すだけでよい。

```c
const LhatUnit *unit = lhat_program_check(program, "game.lh");
if (!lhat_unit_export_conforms(unit, "update", "p^number^;")) {
    char spelt[128];
    lhat_unit_export_type_text(unit, "update", spelt, sizeof spelt);
    // "game.lh: update is p^string^;, and the game asks for p^number^;"
}
```

- `lhat_unit_export_count` / `lhat_unit_export_name` —— 公開した名前の一覧
- `lhat_unit_export_type` —— 歩ける記述子（`LhatRuntimeType`）。合併の腕・
  メンバ・def^ のインスタンス形まで、綴りをパースせずに読める。単位の
  コンパイル済み本体と同寿命
- `lhat_unit_export_type_text` —— 02 の 14.10 の綴り（`typeof^(x).signature` と
  同じ文）。無い名前は `SIZE_MAX`
- `lhat_unit_export_conforms` —— 02 の 13.5 の適合。書く型は 8.7 の登録の
  署名と同じに読まれるので、ホストが登録した型も名指せる

`module^` の無いスクリプトは何も公開しない（3.2）——答えは `return^` の値で、
この口の相手ではない。

これは 9 章の M7（機械の印を「所有単位だけが書ける」へ広げるか）とは
別の話である。M7 が問うているのは **テーブルのメンバ** を誰が書けるかで、
本節が言っているのは **名前** を誰が書けるかである（02 の 8.9）。

## 5. `require^`

```lhat
let^ m = require^ "lib/module1.lt"

m.publicProc()
var^ e : m.Error = …
```

### 5.1 パスで指す

引数は **要求する側からの相対パス** である。単位名では指さない。

単位名で指すと **名前からファイルを見つける探索路の仕様が別に要る**。
どこを探すか、複数見つかったらどうするかを決めなければならない。
パスで指せばその問いが生じない。

`module^` の名前は 7 章のラベルと 5.3 の鍵として働く。**指し方とは役割が違う。**

### 5.2 引数はリテラルでなければならない

6 章が型検査に依存を辿らせるため、**パスは構文解析の時点で決まっている必要がある**。
計算された文字列は受け付けない。

実行時に決まる読み込みは別の機構である——5.6 の `std.load`。

### 5.3 一度だけ読み込まれる

同じ単位を2度 `require^` しても、**同じテーブルが返る**。
単位の本体が2度走ることはない。

登録の鍵は `module^` の名前、宣言がなければ解決したパスである。
登録簿は実行時のものであり（8.6）、綴りは標準ライブラリの設計に属する（M2）。

一度きりを成立させているのは**単位自身の前置きが登録簿に自分を問い合わせる
ガード**であって、`require^` の側ではない。単位を作り直したときに何が要るかは
これで決まる——5.7。

### 5.4 取り込みは名前を撒かない［重要］

`require^` が束縛するのは **1つの名前だけ** であり、それは取り込む側が選ぶ。
単位の中の名前が呼び出し側の場に流れ込むことはない。

1 章の衝突は、これで起きなくなる。
同じ名前の単位を2つ取り込んでも、束縛する名前を分ければ済む。

```lhat
let^ theirs = require^ "vendor/geometry.lt"
let^ ours   = require^ "src/geometry.lt"
```

名前をまとめて現在の場へ流し込む形（`use^` のようなもの）は設けない。
それを入れると衝突が戻ってくる。

### 5.5 省略形は単位が名乗ったパスに束縛する

> **`let^` `var^` を書かずに `require^ "path"` と書ける。
> そのとき単位は、自分が `module^` で名乗ったパスの下に入る。**

```lhat
require^ "lib/m1.lh"        # module^ namespace1.module1
require^ "lib/m2.lh"        # module^ namespace1.module2

namespace1.module1.publicProc()
let^ n : number^ = namespace1.module2.answer
```

#### 5.4 の何が変わり、何が変わらないか

- **「名前を撒かない」は保たれる。** 導入されるのは **根1つ**（`namespace1`）だけで、
  単位の中の名前は `namespace1.module1.` の下に留まる。`use^` 相当ではない
- **「取り込む側が選ぶ」が緩む。** 省略形では単位の側が選ぶ

5.4 が恐れた衝突は戻らない。`module^` のパスは名前空間であり、
同じ完全パスを2つの提供元が名乗ったなら、それは提供元の側の過失である。
`let^` `var^` で名前を選ぶ形はそのまま残るので、逃げ道もある。

```lhat
let^ theirs = require^ "vendor/geometry.lt"    # 従来どおり選べる
require^ "src/geometry.lt"                      # 名乗ったパスに入る
```

#### 接頭辞は合流する

02 の 8.8 がそのまま効く。**2つ目が1つ目を潰さない。**

同じパスを2つの単位が名乗れば、8.8 の末尾の規則により再定義の誤りになる。
同じ単位を2度書いた場合も同じで、5.3 が一度しか読み込まないこととは別に、
**書いた側の重複**として報告される。

#### `module^` の無い単位には使えない

3.2 は `module^` の省略を許している。名乗っていない単位には
束縛すべきパスが無いので、省略形は誤りとする。`let^` または `var^` で名前を選ぶ。

```text
この単位は module^ を宣言していないため、束縛するパスがありません。
'let^ name = require^ ...' と書いてください。
```

#### 文であって式ではない

省略形は **文** とする。02 の 8.2 の「裸の式は文にしない」を
崩さないためである。値としての `require^` は従来どおり式のまま。

### 5.6 実行時の読み込み — `std.load`

> **`require^` が決めていること（パスはリテラル・一度きり・残る）を、
> 全部裏返した口が `std.load` である。パスは値、読むたびにコンパイル、
> 答えの閉包と共に消える。**

ロード画面の後に読むステージのスクリプト、道具が作ったテキスト——
`require^` では書けないもの（5.2）の置き場所で、M3 の答えである。

```lhat
import^ std.load
let^ stage = std.load.file("stages/3.lh")        # p^... -> any^; | std.load.Error
let^ gen = std.load.text(source, "gen/stage")    # name は診断名と require^ の基点
if^ stage fits^ std.load.Error {
    …
else^:
    let^ api = stage()          # module^ 単位なら public^ の表、スクリプトなら return^ の値
    if^ api fits^ t^{} { … }     # 答えは any^——読む側が fits^ で絞る（M3 の「型」の答え）
}
```

#### 答えは閉包、閉包の答えは単位が決める

- **スクリプト**（`module^` 無し）——閉包は `p^...`（3.2改）、答えは最上位の
  `return^`。呼び出しの引数が `...`
- **`module^` を持つ単位**——閉包は引数を取らず、答えは **`public^` だけを
  集めた封印表**。5.3 の番人も登録簿への書き込みも無い: `L^.modules` に
  入らないので `import^` からは見えず、2度 load すれば2つの表。`module^` の
  名前はラベル（7.2 のとおり同一性ではない）と診断のためだけに残る

#### 読むたびにコンパイルし、記憶しない

Lua の `load`/`loadfile` と同じ線。一度きりが欲しければ `require^`（5.3）。
ただし **読んだものの中の `require^` は普通の `require^`**——その単位は
program の単位として検査・コンパイルされ、最初に走ったときに登録され、残る。
それが `require^` の意味であり、load はそれを変えない。`name`（`file` なら
パス）が診断の名前であり、中の `require^` の基点である（5.1）。

#### バイトコードは閉包と共に消える

program の単位の本体は program のものでどの機械より長生きするが、load が
作った本体は **機械のヒープのもの**（`LhatLoadedScript`）である。閉包がそれを
指し、最後の閉包が回収されたときに本体も消える。検査器が作った型は
読み込みごとのアリーナに置き、コンパイルが済めば捨てる——program に残る
のは `require^` で連れてきた単位だけ。

本体の定数が名指すもの（文字列・型記述子）は本体の chunk のもので、
回収されない色で生まれる。それが外へ出ていることがある——std.lton が
答えた表のキーは本文の文字列そのものである。だから本体が消えるとき、
定数のオブジェクトは**機械のヒープへ譲る**（生まれたての色で）。その掃除は
残し、次の周期が到達性で判定する。表が生きていればキーも生き、
何も指さなければ消える。

その裏返しとして、**load が作った閉包は別の機械へ運べない**（8.8改 の
carry が拒む）。本体が機械のものである以上、写しは向こうで宙に浮く。

#### 誤りは値

- `std.load.Error.CannotRead`——loader に無いパス、または loader を持たない
  program（8.9 の線: 言われなければファイルシステムへ届かない）
- `std.load.Error.Rejected`——検査器かコンパイラが言ったこと。`message` に
  診断が1行ずつ、CLI と同じ描画で入る

#### `L^` ではなく標準ライブラリに置く

`L^` は機械そのもの（8.6）だが、読み込みには program と loader が要る。
登録しないホストには実行時のコード読み込みが存在しない——組み込み先が
選べるのはこの置き方だけである。C 側の口は `lhat_program_load_text` /
`_load_file`（検査して切り離した単位としてコンパイル、proto を返す）と
`lhat_machine_adopt_script`（機械が proto を所有し閉包を答える）の3つ。

load は program を書くので、**同時には1機械からだけ**——std.thread の
worker からは呼ばない。

### 5.7 単位が書き換わったとき

ひとつの program に多くの単位を載せ、機械はスレッドの数だけ持つ——これが
組み込み先に望む形である。単位ごとに program を分ければ、共有ライブラリは
枚数だけ検査・コンパイルされる。

［補足］かつてはここに「さらに登録が program ごとになるので同名の型が
別物になる」という理由も並んでいた。それは 8.7 で解いた——**宣言とは C の
呼び出しであり、program がいくつあっても同一性はひとつ**。残っているのは
重複した検査とコンパイルの費用だけで、それは費用であって誤りではない。

program に単位を足すのは 5.3 の増分コンパイルで既にできる。足りないのは
**編集への追随**——エディタは1枚ずつ保存を投げてくる。

#### 差し替えは単位ひとつずつ［重要］

**プロジェクトぜんたいを読み直すなら、program と機械を捨てて作り直す。**
差し替えは要らない。単位ひとつの差し替えが要るのは、**走らせながら書き換える
live edit** の側だけである。

「全単位を差し替える」呼び方は置いていない。単位の差し替えは古い本体の定数を
program の寿命まで抱える（後述）ので、全部を差し替えるのは**捨てて作り直す
より多くを残す**。捨てて作り直しても、ホストが登録した同一性は残る（8.7）
——新しい program は前と同じ世界に戻ってくる。

単位の殻はリストに残る（stale）ので、ホストが握っている `const LhatUnit *`
はそのパスの単位であり続ける。

#### 退役 — 古い世界と新しい世界が並ぶ

`lhat_program_invalidate(program, path)` は、その単位と、`require^` が
そこへ届く**すべての単位**を退役させる。連鎖は推移的でなければならない:
要求する側の検査済みの型は要求される側が公開したものから来ており、その
コンパイル済みの本体は `require^` が答える proto そのものの表を握っている。

辺は**検査でも記録する**——コンパイルの側だけではない。誤りのある単位は
コンパイルされないので、コンパイル時にしか辺を知らないと、エディタで最も
起きること（誤りのある単位を直す）に連鎖が届かない。読めなかったパスへの
`require^` も辺である: そのファイルが現れて無効化されたとき、読み直す
べきなのは要求していた側だからである。

無効化は、退役させた単位が引き起こした program 側の診断も取り下げる。
残しておくと、直したあとも `lhat_program_has_errors` が永久に真を答える。

**無効化は何も解放しない。** 古い本体は program の退役リストへ移るだけで、
無効化より前に作られた閉包はその本体を走らせ続け、その本体が読む単位表も
古い本体を指したまま。**古い世界と新しい世界が、それぞれ内部的に無矛盾な
まま並ぶ**。退役しなかった依存——変わらなかった上流——は両方の世界から
指され、program が生きている限り解放されない。

解放は `lhat_program_discard_retired` で、**時機を決めるのはホスト**である。
どの機械も退役した本体を走らせておらず、どの機械のヒープにもその閉包が
残っていない、と言えるのはホストだけだから。`lhat_program_free` も捨てる。

**確かめ方**は、機械ごとに: 古い本体を握っていたものを落とし（エディタなら
全部を新しい本体で着せ直し）、`lhat_machine_collectgarbage`、そのあと
`lhat_machine_pending_disposals` が 0 であること。回収が、もう誰も握って
いない閉包を持っていく。2つめは**回収だけでは終われない唯一のもの**——
10.7 は落ちたコルーチンをその `finally^` が走るまで生かし、そのコルーチンは
中断した先の閉包を握っている。

#### 解放されるのは本体であって定数ではない［重要］

`discard_retired` が解放するのは**符号**だけで、その本体の定数が名指して
いたものは program が終わるまで残る。

chunk のオブジェクトは**あらゆる機械より長生きする前提**で born black に
なっている（5.12）。退役はその前提を変えない——`LOADK` がレジスタに置くのは
文字列定数そのものであり、プログラムがそれをテーブルのキーとして仕舞えば、
**本体が消えたあとも機械のテーブルがそれを握っている**。`L^.modules` は
まさに、単位自身の前置きが読み込む文字列で鍵付けされている。どれが逃げたかを
ホストが知る術は無いので、ひとつも解放しない。

同じ本文で保存し直しただけなら何も退役しない——単位は最後に読んだ本文の
ハッシュを持っている。読めなくなったパスは保守的に退役させる。消された
ファイルが program のコンパイル結果であり続けてはならない。

#### 機械に忘れさせる義務［重要］

単位が一度しか読み込まれないのは、**単位自身の前置きが機械の `L^.modules`
に自分を問い合わせ、あればそれを答える**ガードで成立している（5.3）。
だから単位を退役させて作り直しただけでは足りない——**新しい本体が古い
テーブルを見つけて、それを答えてしまう**。新しい本文は二度と走らない。

`lhat_machine_forget_unit(machine, module)` が `L^.modules` からその単位を
外す。**program に載せた機械ごとに1回**。program は自分の機械を知らない
ので、代わりにやることはできない。
`module` は `lhat_unit_module_name` が答えるパスで、これは無効化を越えて
生き残る——必要になるのがまさに無効化の直後だからである。

#### 手順は1本 — `lhat_reload`

上の全部——無効化、機械ごとの忘却、再検査、再コンパイル、退役した本体の
解放——を正しい順で束ねる:

```c
lhat_reload(program, path, machines, machine_count);  // machines は載せた全機械
```

解放は「信じてくれ」ではなく**確かめて**行う。機械ごとに
`lhat_machine_collectgarbage` のあと、退役した本体（入れ子含む）の閉包・
コルーチンがどの機械のヒープにも無く（`lhat_machine_holds_body`）、後始末
待ちも無い——そのときだけ `discard_retired` が走る。握られていれば
**見送るだけ**で、次の差し替えに持ち越す。何もしないホストが program の
解放まで積むのと同じ側にしか倒れない。再読が検査かコンパイルで止まれば、
古い世界が走り続け、診断がそれを言い、次の保存がやり直す。

部品は各節のとおりすべて公開のままなので、時機を自分で持ちたいホストは
今までどおり自分で組める。

#### 差し替えは積む

型はアリーナから来て個別には解放されない（6 章: 単位が公開した型は、それを
要求する単位の中で有効であり続けなければならない）。定数も同じ——上のとおり
本体を捨てても残る。だから**差し替えは program のメモリを増やす一方**で、
減らす口は無い。

本文ハッシュが「変えずに保存」を弾くので、増加は実際の編集回数に比例する。
live edit の一回一回は小さく、遊んでいる間で閉じる。

**減らす口は program を捨てることであり、それで足りる。** これが「全部の
差し替え」を置かない理由でもある——全部やれば全部積み、捨てて作り直すほうが
きれいに終わる。

## 6. 型検査は依存を辿る

### 6.1 静的に辿る

`require^ "…"` に出会った型検査器は、**その単位を先に処理して型を得る**。
返るテーブルの型は、公開された名前とその型からなる構造である。

```lhat
let^ g = require^ "lib/geometry.lt"
let^ p : g.Point = g.Point.new()
g.dist(p, "text")                    # 型の誤りとして報告される
```

`g.Point` が型として書けるのは、04 の 12.4 が
**修飾された名前を型として書ける** ことを既に定めているためである。
誤りの種別のために作った形が、そのまま単位のメンバに効く。

02 の 13.14 の別名も同じ道で渡る: `public^ let^ Vec = t^{number^[2]}` を
公開した単位の `m.Vec` は、他の単位の型の位置に立つ。輸出されたメンバは
値（記述子）とともに「何を名指すか」を運ぶので、`f^…;` の別名——値の型の
形だけでは型と読めないもの——も届く。

### 6.2 処理の順序

03 の 1.1 の段階構成に、単位の依存順が加わる。

```text
単位の依存関係を辿る → 依存の順に（字句 → 構文木 → 型検査）→ コード生成
```

依存の側が先に型検査を終えていなければ、要求する側の型検査が行えない。

### 6.3 循環は誤り

単位の依存に循環があれば誤りとする。

許して「これまでに公開された分だけ見える」とする案（Lua、Python）は採らない。
**何が見えるかが読み込みの順序に依存する。**
同じソースが、どちらを先に読んだかで通ったり通らなかったりする。

02 の 8.7 が単位の中の相互再帰を解いているのは
「スコープ全体で見える」という規則が順序に依存しないからであり、
単位をまたいでその性質を保つには循環を持ち込まないほうが早い。

Go が同じ判断をしている。共通部分は第3の単位に出す。

## 7. 型の名前

### 7.1 単位名が型のラベルになる

`module^` を宣言した単位の中で作られた型は、**その名前で修飾されたラベル** を持つ。

```lhat
# lib/module1.lt
module^ namespace1.module1
public^ let^ Point = def^{ self^{ x = 0, y = 0 } }
```

```lhat
let^ m = require^ "lib/module1.lt"
let^ p = m.Point.new()
print(typeof^(p))          # namespace1.module1.Point
```

**ラベルは `require^` を束縛したローカルの名前と無関係である。**
`m` を何と名付けても、`typeof^` の答えは変わらない。

### 7.2 ラベルであって同一性ではない［重要］

02 の 11.3 と 14.9 は変わらない。

> 名前は表示と診断のためのラベルにすぎない。型の同一性は構造で決まる。

したがって **別の単位の同じ形の `Point` は同じ型である**。
単位の境界は型の互換性を分けない。

多くの言語ではモジュールが公称の分離を作るが、L^ では作らない。
14.9 が「名前を同一性に含めると公称型付けになる」と述べたとおりである。

### 7.3 誤りの種別だけは同一性

04 の 2.4 の例外はそのまま効く。種別の同一性は宣言の場所であり、
**別の単位で宣言された同名の種別は別の型である**。

```lhat
# それぞれの単位で errordef^ Error { SomeError }
theirs.Error.SomeError     # 別の型
ours.Error.SomeError
```

表示上の衝突は名前空間（本章）が解き、
取り違えのほうは 04 の 2.4 が最初から防いでいる。

ホストが登録するものについては、**宣言とはそれを行う C の呼び出し**である
——同じ呼び出しを2つの program に対して行っても宣言はひとつ。8.7 を見よ。

### 7.4 `typeof^` が返すのは型である

```lhat
print(typeof^(m.publicProc).signature)
```

`publicProc` は手続きの **値** であり、その型は署名である。
出力は `p^;` にあたる形になる。`namespace1.module1.publicProc` にはならない。

`typeof^(m.publicProc)` 自身（`.signature` を付けない場合）は
値そのものを直接印字する手立てを持たない（02 の 14.16）。

02 の 14.10 が「`.signature` の出力はそのまま型注釈として解析できる」と定めており、
`namespace1.module1.publicProc` は型注釈ではない。

単位名で修飾された名前が現れるのは **型そのものがラベルを持つ場合** である。
`def^` が作った型（7.1）と誤りの種別（7.3）がそれにあたる。

値の出自を問う機能が要るなら、それは `typeof^` とは別のリフレクション機構になる（M4）。

## 8. 無指定で見える名前

### 8.1 何も見えない

> **`require^` を書かなければ、名前はひとつも見えない。**

言語が名前を配ることはしない。標準ライブラリも例外ではない。

```lhat
let^ io = require^ "system/io.lh"
let^ f = io.File.open("path/to")
```

短く書きたければ、取り込む側が自分で名前を付ける。

```lhat
let^ open = io.File.open
let^ f = open("path/to")
```

5.4 のとおり `require^` は名前を撒かないので、
**どの名前が現在の場にあるかは、その場に書かれた `let^` または `var^` を読めば分かる**。
無指定の名前があると、この性質が崩れる。

`L^`（8.6）はこの性質を崩さない。**それは名前ではない**。
01 の 2.2 のハット識別子であり、`let^` `var^` が作れる綴りと交わらない。

### 8.2 初期束縛はホストの設定

修飾なしの `print("message")` が成り立つのは、`print` が言語に属するからではない。

> **ランタイムの生成時に、ホストが初期束縛を与える。**

既定では次のようなものが暗黙に実行された状態から始まる、という形になる。

```lhat
let^ print = require^ "system/debug.lh".print
```

**都合が悪ければホストは与えなければよい。** 既定はあくまで既定である。

これは 02 の 1.2 と 4 章が既に採っている形と同じである。
入力形式の選択も断片の与え方もホストの責務であり、
ランタイムはモードを状態として持たない。初期束縛もそこに並ぶ。

#### 束縛は `L^` のメンバを指す

8.3 が「型はホストが C 側で書く」と定めるので、初期束縛もそこに合わせる。
ホストは **`L^` に置いたものへ名前を結ぶ**。

```c
lhat_register_global(&program, "print", "f^string^ -> nil^;", host_print, NULL);
lhat_bind_initial(&program, "print", "L^.print");
lhat_bind_initial(&program, "collectgarbage", "L^.collectgarbage");
```

```lhat
print("hello")           # 修飾は要らない
collectgarbage()         # 8.6 が L^ に置いているものも同じ形で結べる
```

##### 8.1 は崩れない［重要］

8.1 が守っているのは **「言語が名前を配らない」** ことである。配るのはホストであり、
何も結ばないホストの下では名前は1つも見えない。そこは変わらない。

裸の名前は **どのスコープにも無いときだけ** 引かれる。
したがって同じ綴りの `var^` が普通に遮蔽する。

```lhat
let^ collectgarbage = p^ {
    print("start garbage collection")
    L^.collectgarbage()      # 元のものはいつでも届く
}
collectgarbage()             # 自分で書いたほう
```

`L^` で元に届くのは 8.1 の最後がそのまま効いているためである。
**ハット識別子は `let^` `var^` が作れる綴りと交わらない。**

##### 実行時には何も増えない

裸の名前は `L^.<メンバ>` の読み出しに落ちる。
グローバルな変数の仕組みを持ち込まない。

結ばれていない名前は今までどおり「そんな名前はない」になる。

### 8.3 ホストは型を書いて登録する

初期束縛の名前が何の型かを、検査器は知らなければならない
（6 章が型検査に依存を辿らせるため）。その手段は
「ソースとして読む」ではなく、**ホストが型を書いて渡す**（8.7）。

```c
lhat_register_func(&program, "system.io", "print", "p^string^;", print_fn, NULL);
```

`"p^string^;"` は 02 の 13 章の型の文法そのままであり、検査器はそれを読む。

こちらのほうが小さい。**宣言と実装が離れない** ためである。
ソース側に宣言を置く形では、`.lh` の宣言と C の実装が食い違いうるので、
突き合わせる段が要る。両方を C 側に置けば食い違いようがない。

したがって 02 の 2.3 のコマンド形式で `ls` が使えるかどうかは、
**ホストがそれを登録したかどうか** で決まる。言語の側に約束はない。

### 8.4 構文である語は取り込まない

`require^` は名前ではなく **構文** である。したがって取り込む必要がない。
`try^`（04 の 5 章）や `pack^`（02 の 13.8改）と同じ位置づけになる。

`typeof^` も同様に構文とする。

`typeof^` は **検査器の静的な型には頼れない**。03 の 4.2 が「厳格度が変えるのは
診断の時期だけで、実行時の意味は変わらない」と定めており、検査結果は検査が
終わると同時に捨てられる（03 の 4.3 とは別に、検査とコンパイルは独立した2つの
パスである）。`typeof^` の答えが検査器の推論に頼ると、非厳格モードで答えが
変わってしまう。したがって `typeof^` は **実行時に値の実際の形を走査して** 答える
（14.7 の「その定義を返す」がそのままリフレクションの設計になる）。

それでも構文として取り込まないのは、次の理由による。

- 常に `typeof^(式)` と丸括弧を伴い、演算子としての優先順位を持たない
  一次式であり、通常の手続き呼び出しとは形が違う
- 7.1 の単位名のラベルは `def^` が作った型と誤りの種別に乗るが、
  `typeof^` 自身の答え（14.16 の「型情報」）は別の一様な型であり、
  単位をまたいで取り込む対象にならない

### 8.5 コルーチンの操作は言語に属する

> **コルーチンの `start`、`resume`、`dispose`、`iterate`、`done`、`started` は
> 取り込まずに使える。標準ライブラリの一部ではない。**

8.1 の「何も見えない」に対する例外ではない。
これらは **語彙ではなく値のメンバ** であり、
コルーチンを手に入れた時点で、そのコルーチンが持っている。

#### 言語コアから切り離せない

「ライブラリの顔をさせる」形は事実に反する。

- **02 の 13.9 が反復子をコルーチンと定めている。**
  02 の 16.3 の `for^ … in^` はコルーチンなしに成り立たない。
  切り離せば `in^` が消え、**ビルドの選択肢ではなく別の言語** になる
- **型の側も絡んでいる。** `c^{ … }` は合併と適合の判定に載っている
- **実行時の機構は共有物である。** 03 の 5.7 がコルーチンを1フレームの保存と定めたため、
  フレーム、後始末の待ち行列（03 の 5.5）、`p^` の呼び出し規約のいずれもが、
  コルーチンの有無にかかわらず必要なものになっている。
  **コルーチン専用の重い機構が存在しない**

実測でも同じ結論になる。実行ファイル約 100 KB、ソース 13,618 行に対し、
コルーチンに帰せる行は 400〜500 行（3〜4%）。
実行時のメモリはコルーチン1つあたり 328 バイトと、その本体のレジスタ分であり、
**使わなければ発生しない**。静的に確保している機械の側で減るのは 3.2 KB / 197 KB である。

削る効果が大きいのは別の場所にある（値スタックの大きさ、フレーム数の上限、
そして構文解析器と型検査器を外して事前コンパイル済みバイトコードだけを走らせる構成）。

#### Lua が標準ライブラリに置いている理由［参考］

Lua の `coroutine.*` がライブラリなのは、L^ に当てはまらない事情による。

- **yieldable を印していない**（02 の 15.6）。
  どの関数からでも `yield` できるため、関数を呼ばずに渡す `coroutine.create` が要る
- **C API との対称性。** `lua_newthread` / `lua_resume` / `lua_yield` が先にあり、
  Lua 側の `coroutine` はその薄い包みである。ライブラリにすれば実装が1つで済む
- Lua は方針としてコアを小さく保ち、`string` や `table` も含めてライブラリに寄せている

L^ は 15.2 の推論を持ち、C API との対称性を先に決めてもいない。同じ形を採る理由がない。

### 8.6 `L^` — 機械そのもののテーブル

> **`L^` は取り込まずに使えるテーブルであり、言語の実行環境そのものを指す。**

8.1 の「何も見えない」に反しない。**`L^` は名前ではない。**
01 の 2.2 のハット識別子であり、`let^` `var^` が作れる綴りと交わらないため、
「その場にある名前は書かれた `let^` `var^` を読めば分かる」という性質は保たれる。
`this^`（02 の 15.10）と同じ位置づけである。

#### 何を載せるか

載せるのは **プログラムが自分では用意できないもの** に限る。
便利な道具は標準ライブラリに属し、8.1 のとおり `require^` で取り込む。

```lhat
L^.collectgarbage()      # GCを手で走らせる
L^.modules               # 登録簿
```

`collectgarbage` は `p^;` である。効果であって値を作らないので `f^` ではない。

**ホストからも同じ周期を頼める** — `lhat_machine_collectgarbage`。組み込み先は
L^ のコードを一行も走らせずに機械を持っていることがあり、そこに口が無いと
回収を頼む手段が無い。C 側は生存オブジェクト数を答える（バイト数ではない。
ヒープが数えているのはオブジェクトだけ）。

ただし**ホストが握っているものは根ではない**。機械が辿るのは `L^`（したがって
`L^.modules` の下すべて）と、フレームのクロージャ・コルーチン・レジスタ、
閉包が共有する場所、ホストが答えを詰める部屋、直前の fault だけである。
`lhat_machine_make_*` で作ってまだ機械の届く所へ入れていない値は、この回収が
持っていく。**走り終わった run のレジスタも根ではない**——フレームが無いので、
プログラムが持っていたものはその時点で誰も持っていない。

02 の 10.7 の後始末待ちも、`L^.collectgarbage()` と同じく**ここで走る**。
つまりこの呼び出しは L^ のコードを走らせる——落ちたコルーチンの `finally^`
や `with^` を。走らせるのはこの周期が見つけた分だけで、後始末自体がさらに
コルーチンを落としたら次の呼び出しに回る（際限なく続けさせない）。

これが**ホストにとって本質的**なのは 5.7 の理由による。後始末が済むまで、
落ちたコルーチンは中断した先の閉包を握り、したがってその閉包を作った本体を
握っている——退役した本体を捨てようとしているホストが、まさに解放しようと
しているものを。

走らせきれないものは残る: 後始末が fault したもの（**見捨てられる**。
巻き戻しの途中で誰にも報告できない以上、枠を残せば `pending_disposals` が
「待ちは無い」と答えながら枠が本体を指し続けることになる。だから枠ごと畳む）、
既に別の後始末が進行中のところで呼ばれた場合、枠やスタックの余地が無い場合。
`lhat_machine_pending_disposals` が残りを数える。

ホストは 8.2 のとおり、ここへ自分のものを足せる。
足せるのは同じ理由に適うものだけである — **プログラムが自分では用意できないもの**。

出力はその境目にある。02 の 10.6 が「デバッグ用のログ出力などの脱法関数」を
`f^` の制約の唯一の例外として挙げており、`print` はその実例にあたる。
**変わるのはホスト側の状態であって、機械の側ではない。**
プログラムから読み返せるものは何も動かないので、`f^` として置ける。
13.2 が返り値を求めるので `f^string^ -> nil^;` になる。

#### `L^.modules` は登録簿である

5.3 は「同じ単位は一度しか読み込まない」と定めた。**その登録簿がこれにあたる**。

単位は `module^` が宣言したパスの下に入る。
02 の 8.8 がテーブルの途中の段を作るので、登録は **02 の 8.8 の形で表せる**。

```lhat
let^ L^.modules.namespace1.module1 = ...
```

接頭辞を共有する単位は **合流する**。8.8 が2つ目に1つ目を潰させない。

```lhat
let^ L^.modules.ns1.mod1 = ...
let^ L^.modules.ns1.mod2 = ...   # ns1 は両方を持つ
```

同じパスを別の単位が名乗れば、8.8 の末尾の規則により再定義の誤りになる。

##### ただし書き手はこれを書けない

上の行は **処理系が出すものの説明** であって、そのままコンパイルできる L^ ではない。
`L^` は機械のものである以上、
**登録簿にメンバを足すことも、そこにあるものを差し替えることも、L^ の側からはできない。**

```lhat
let^ L^.modules.ns1.mod1 = { }   # 誤り
L^.collectgarbage := p^ { }      # 誤り
```

読むことは妨げない。`L^.modules` を辿って何が読み込まれているかを見るのは通る。

##### 登録するのは単位自身である

`require^` の側が登録するのではない。**単位が自分の先頭と末尾で行う。**

```lhat
# module^ ns.m1 と書かれた単位が、これと同じものになる
if^ L^.modules.ns.m1 { return^ L^.modules.ns.m1 }   # 番人
… 本体 …
let^ module = { <public^ の名前をすべて> }
let^ L^.modules.ns.m1 = module
return^ module
```

置き場所が要である。`require^` の側に置くと、要求元ごとに書かれることになり、
**一度しか走らないことの根拠が呼ぶ側に散る**。単位の側に置けば根拠は1箇所で、
どこから何度要求されても本体は最初の1回しか走らない。

番人は書かれた L^ としては通らない。`L^.modules.ns.m1` は
まだ型に無いメンバだからである。生成される命令列としては成立する —
04 の 11.3 が「無いキーは `nil^`」と定めており、読み出しは失敗しない。
**脱糖は説明であって、そのままコンパイルできる L^ ではない。**

##### 型の側も同じことを言う

`require^` は単位を走らせ、走れば必ず登録される。したがって
**検査器の `L^.modules` の型にも同じ登録を行う**。これがなければ
登録簿は L^ から書けるだけで読めない。

```lhat
require^ "one.lh"                  # module^ ns.one
return^ L^.modules.ns.one.v        # 読める
```

嘘にならないのは、登録が **単位自身の前置き** にあるためである。
呼ぶ側が省略できる位置にあれば「型が実体を先回りする」ことになるが、
そうなっていない。同じ単位を2度要求しても 5.3 が一度しか走らせないので、
型の側の登録も冪等とする（8.7 の衝突にはしない）。

#### 機械が持ち、機械が根にする

`L^` は機械とともに作られ、**どのフレームにも属さない**。
ガベージコレクションの根は機械の側にあり、登録された単位は集められない。

#### 型は検査の側にもう1つある

実行時の表と別に、検査器が同じ形の型を持つ。
セッション（03 の 4.3）では入力をまたいで保たれるので、
ある入力が登録した単位は次の入力からも見える。

**2つの一覧が同じことを言っている必要がある。** 片方だけに足すと食い違う。

食い違いを作れるのは **この2箇所を書く側だけ** である。
スクリプトの側からは作れない。

- `var^ L^.x = v` は検査器の型と実行時の表を**同時に**増やす。片方だけは起きない
- `var^ L^.modules = …` は 02 の 8.7 の再定義の誤りになる
- `L^.modules := …` は実行時の中身を入れ替えるが、
  検査器が持つ型のオブジェクトは変わらないので、型の食い違いにはならない

#### 機械のテーブルは L^ から書けない

> **`L^`、その登録簿、そして `require^`／`import^` が答えるテーブルは、
> ホストが自分の API で書く。L^ の側からは書けない。**

- **差し替え** — `L^.collectgarbage := …`、`m.name := …`
- **追加** — `var^ L^.modules.ns.m = …`、`var^ m.name = …`

読むことは妨げない。

##### 記法は要らない［重要］

書き手が可変性を指定する必要がないので、**綴りを1つも足さない**。
型に印が1つあり、機械が作るテーブルにそれを立てるだけである。

ホスト側の許可は自動で成り立つ。検査器が見るのは L^ のソースだけであり、
**ホストは 8.7・8.8 の C の API を通るので検査器を通らない**。
したがって「L^ に書かれたものを一律に拒む」がそのまま規則になり、
ホスト用の抜け道を作る必要がない。

##### 検査だけでは足りない

検査器が捕まえられるのは **名前で書かれたもの** だけである。
一度引数を通せば抜ける。

```lhat
let^ poke = p^ x:t^{ v:number^ } { x.v := 99 }
let^ m = require^ "lib"
poke(m)                # x の型は t^{ … }。印を持たない
```

受け手側に印を書く綴りがない以上、**型の適合では止められない**。
止めようとすると、機械のテーブルをどの手続きにも渡せなくなる。

そこで **実行時にも同じ問いを置く**。テーブルに印を持たせ、
書き込みの命令がそれを見て拒む。

ホスト側はここでも自動的に自由である。
ホストは 8.7・8.8 の C の API でテーブルに触るので、**命令を通らない**。
検査器のときと同じ構造がそのまま成り立つ。

02 の 15.1改 が `f^` の側から塞いでいる経路とも重なる。
`f^` の中からは静的に、`p^` と最上位からは実行時に止まる。

##### 中身には伝播させない

印が立つのは **そのテーブル自身** だけである。
公開された名前が持つテーブルは、持たれていたときと同じだけ書ける。

```lhat
let^ m = require^ "lib"
m.registry := { }      # 誤り。モジュールのテーブルは機械のもの
m.registry.x := 1      # 通る。公開されたテーブルの中身は別の話
```

4.2 が「公開されるのは名前であって定義ではない」と定めている。
その名前が持つものをどこまで書けるかは、**まだ決めていない**（M7）。
伝播させるとここで決めてしまうことになる。

##### 2つの軸が重なる

02 の 15.1改 が `f^` の側から同じ場所を守っている。両者は別の軸である。

- **どこから書けるか**（15.1改）— 式の由来。静的にしか意味を持たない
- **誰が書けるか**（この規則）— 値に付く。ホストと L^ の境目を引く

`f^` の中からの書き込みは 15.1改 が止め、`p^` と最上位からのものをこの規則が止める。

### 8.7 ホストの登録と `import^`

> **ホストは C 側で型を書いて自分の機能を登録し、
> スクリプトは `import^` でそれを自分の場に導入する。**

#### 登録

```c
lhat_program_init(&program, true);

lhat_register_type(&program, "system.gfx", "Texture");
lhat_register_member(&program, "system.gfx", "Texture",
                     "width", "f^ -> number^;", width_fn, ctx);
lhat_register_func(&program, "system.gfx", "load",
                   "f^string^ -> system.gfx.Texture;", load_fn, ctx);

lhat_program_check(&program, "main.lh");     # 登録はこれより前
```

モジュールは最初の登録で暗黙に作られる。
**すべて型検査より前**でなければならない。検査器が型を知る必要があるためである。

#### シグネチャは 13 章 の型の文法である

文字列は型としてそのまま解析される。14.10 が
「`typeof^(x).signature` の出力はそのまま型注釈として解析できる」と定めているので、
この入口は元々必要なものである。

名前として書けるのは **組み込み型と、それより前に登録されたホスト型** だけである。
`require^` が持ち込む単位の型は書けない — 書けると
**単位が検査される順序に答えが左右される**。

互いを参照する型は、**先に型だけを2つ登録してから**メンバを足す。
C のヘッダにおける前方宣言と同じ形になる。

#### 8.7改4 境界は個数で答える［重要］

> **ホスト関数は答えを機械が渡した部屋に書き、いくつ書いたかを言う。**

```c
typedef void (*LhatHostFn)(LhatMachine *machine, void *context,
                           const LhatValue *arguments, size_t count,
                           LhatValue *answers, int *answer_count);
```

引数は配列＋個数のままである。13.1 が個数を静的に決めるので、Lua が
スタックを使う理由（実行時まで個数が分からない）がそもそも無い。
**変えたのは答えの側だけ**である。

元の形は `LhatValue` を1つ返すもので、02 の 13.8改 の多値は別の入口
から渡していた。**型が「1つしか返せない」と言っているのに実際は返せる**
という状態で、境界を初めて読む書き手に嘘をついていた。個数で答える形なら
多値が型に出る。

```c
answers[0] = lhat_integer(a / b);
answers[1] = lhat_integer(a % b);
*answer_count = 2;
```

**部屋は機械のもの**で、`LHAT_MAX_TUPLE` 幅、収集器が辿る——だから
答えを書いてから返るまでの間にホストがテーブルを組んでも、L^ を呼び戻しても、
書いたものは生きている。ホストは確保も解放もしない。

`*answer_count` は 0 で届く。**何も答えない登録は何も書かずに返る**
——`p^` の登録がそれである。

##### 答えを取らない呼びには部屋を渡さない［重要］

`answers` と `answer_count` が**両方 NULL で届く**呼びが2つある。
どちらも呼び出しではなく**フック**で、答えを待っている者が居ない。

- **`dispose^`** — 収集器が値を返すとき（8.8）
- **`release`** — ホストの歩きを作るときに渡したもの（8.8）

待っている者が居ないので、置き場も用意しない。フックの側は
`answers` に書いてはならない。

##### フックが `LhatHostFn` のままなのはなぜか

「答えない関数」に専用の型を与えたくなるが、**`dispose^` は
普通のメンバでもある**。1つの登録が、同じ C 関数を型のメンバ表と
タグの両方に置く。

```c
lhat_register_member(program, "m", "T", "dispose", "p^self^;", fn, ctx);
//   → メンバ表の LhatHost{ .call = fn }
//   → タグの tag->release = fn
```

機械は、手で書かれた `x.dispose()` を**この2つの同一性**で見分け、
02 の 10.7 の「返却は一度きり」を守る。型を分ければ、
**1つの関数が2つの型に見える**ことになり、その同一性が書けなくなる。

##### 幅を超える署名は登録で拒む

部屋が `LHAT_MAX_TUPLE` 幅なのは**機械の部屋がその幅だから**である。
運べない署名は**宣言された所で拒む**——後で、ホストが渡された部屋を
超えて書いた後に分かるのでは遅い。コンパイラが書かれた呼び出し位置で
拒むものを、これが登録された位置で拒む。

#### 8.8改2 歩きは Y と T を言い分ける［重要］

> **歩きの1歩は同じ形で答え、続くかどうかだけを返す。**

```c
typedef bool (*LhatHostStepFn)(LhatMachine *machine, void *context,
                               const LhatValue *sent, size_t sent_count,
                               LhatValue *answers, int *answer_count);
```

答え方が `LhatHostFn` と同じで、**差は返り値の型だけ**である。
書き手が覚える作法はひとつになる。

返り値が言うのは 02 の 13.9 の区画である。

- **`true`** — 歩きは続く。書いたものは **Y**（yield）。続くなら必ず何か書く
- **`false` ＋ 書いた** — 歩きは終わり、書いたものは **T**。
  本体コルーチンが `return^` で埋める区画に、ホストの歩きも届くようになった
- **`false` ＋ 書かない** — 何も残さず終わる。多くの歩きはこれ

T が届くのは 16.3 の `for^` に影響しない。ループは resume のあとに
**別に `ISDONE` を問う**ので、終わったときに何が置かれていても束ねない。
手で書いた `resume()` だけがそれを読む。

`sent` も配列＋個数である。13.8改 で `c.resume(a, b)` が書けるのに、
**ホストの歩きには先頭1つしか届いていなかった**。本体コルーチンには
全部渡していたので、これは境界だけの欠落だった。

#### 同じ名前を何度でも登録できる［確定］

**同じ名前への2度目の登録は、置き換えではなく腕の追加である。**
02 の 14.12 の `overload^` を書いたのと同じものになり、
呼び出し側は両者を区別しない。

```c
lhat_register_hostvalue_member(p, "m", "C", "-", "f^self^ -> number^;", neg, tag);
lhat_register_hostvalue_member(p, "m", "C", "-", "f^self^, number^ -> number^;", sub, tag);
lhat_register_hostvalue_member(p, "m", "C", "+", "f^number^, self^ -> number^;", radd, tag);
```

02 の 11.3改 の末尾 `self^` も書ける。上の3つ目は
**受け手が右の被演算子**であり、`1 + v` がこれを見つける。

14.12 の「重なるシグネチャは書けない」は **登録の時点で効く** —
既にある腕のどれかと同じ呼び出しを受け取りうるものは、
`lhat_register_*` が偽を返す。L^ 側では検査が言うことを、
ホスト側では登録が言う。

分かれる条件は、**機械の探索が分けられるものと同じ**である——書かれた
引数の位置で型が交わらないか、片方が受け取る個数の引数にもう片方が
置き場を持たないか。13.7 の可変長の尾は個数を下限にし、呼び出しでは
型を見ないので、書かれた引数の先は何でも受ける。

```c
f^string^ -> T;            f^number^, ... -> T;           # 先頭で分かれる
f^number^ -> T;            f^number^, number^, ... -> T;  # 個数で分かれる
f^string^, ... -> T;       f^string^, Font, ... -> T;     # 拒否——2引数の呼び出しが両方に収まる
```

最後の組が欲しければ、尾の無い腕（`f^string^ -> T;`）と尾のある腕
（`f^string^, Font, ... -> T;`）に分ける。

C 関数は登録した個数ちょうどで呼ばれる。
どの腕が選ばれたかは `count` と受け取った値で分かる。

##### メンバの署名は自分の型を `Self^` と書ける

13.13 の `Self^` は、`lhat_register_member` / `_hostvalue_member` の署名では
**登録先の型**を指す。`"f^self^, Self^ -> Self^;"` は
`"f^self^, m.T -> m.T;"` と同じもの。モジュール関数や global の署名に
`Self^` は無い（外側に構造が無い）。

##### 実行時の選択は登録した署名から作られる

L^ で書いた多重定義は、コンパイラが本体から候補の型を作る。
ホスト関数には本体が無いので、**登録が受け取った署名から同じものを作る**。
だから選択の精度は L^ 側と変わらない —
個数でも、位置ごとの型でも、受け手がどちら側かでも分かれる。

作るのは**登録のとき一度**で、置き場は program 自身のヒープ（誤り種別と
同じ、生まれながらに黒）。機械は install でそこへのポインタを受け取る
だけで、型を組み立てない——コンパイル済みの単位の記述子が chunk のヒープに
あるのと同じ線で、**実行時に型は作らない**。

#### 登録された型は公称である

`lhat_register_type` が作るのは 7.3 と同じ **宣言の場所が同一性** の型である。
11.3 の構造的型付けの例外にあたる。詳細は 8.8。

02 の 8.8 の印も立てるので、`var^ t.x = …` でメンバを後から足せない。

同一性が宣言である以上、**2つの登録型に同時に属する値は無い**。だから
14.12 の重なりの判定でも2つは分かれ、`take(File)` と `take(FileData)` は
腕として並べられる——メンバ名をいくら共有していてもよい。構造で見れば
「共有する名前が無ければ重なる」に落ちて並べられなかった。

#### 宣言とは、それを行う C の呼び出しである［重要］

同一性が宣言なら、**宣言とは何か**を決めなければならない。答えは
`lhat_register_hostdata_type(program, "std.io", "File")` という **C の
呼び出しそのもの**である。同じコードが2つの program に対して呼ばれたのなら、
それは**ひとつの宣言を2度行った**のであって、2つの宣言ではない。

だから3つの登録は、既に宣言されているものを**同じもので答える**:

- `lhat_register_hostdata_type` — 同じタグ
- `lhat_register_hostvalue_type` — 同じタグ（`width` も `index` も）
- `lhat_register_error_kind` — 同じ群と同じ変種

**これは飾りではない。** 実行時はタグをアドレスで比べる（`fits^`、値の等値、
`t.width()` の行き先）。program ごとに別のタグを作れば、**同じ綴りの型が
2つになり、一致するのは「決め手になるただ一つのこと」以外の全部**という
状態になる。値が program の境を越えた瞬間にそれが表に出る。

**食い違いは拒む。** 同じ名前を、別の大きさのホスト値型として、別の変種の
一覧の誤り種別として、別の関数の `dispose^` として宣言し直すのは、ひとつの
名前に2つの宣言を与えることであり、7.3 が防いでいるものそのもの。
ひとつの program の中で同じ名前を2度使うのが誤りであること（8.7 の「一つの
名前に一つ」）は、これとは別に今までどおり。

program に残るのは、検査器が読む型と、ホスト関数が受け取る `context` である。
だから `std.load` は自分の `context` に program を持てる。

同一性は process の寿命——**リロードの回数に比例しない**。これが
「ホストの登録は静的であるべき」ということ。`lhat_registry_dispose` が
まとめて返すが、呼べるのは **`LhatProgram` がひとつも存在しないとき**だけ
である。process が終わるまで走る組み込み先には要らない;
プラグインとして外される側には要る。

登録簿は process 大域の可変状態で、**錠は無い**。登録は何かが走る前に
済ませるという既存の規律で足り、`std.thread` が糸を立てるのはそれより後。

#### C 関数の形

```c
typedef LhatValue (*LhatHostFn)(LhatMachine *machine, void *context,
                                const LhatValue *arguments, size_t count);
```

- **引数は配列で渡す。** 13.1 が個数も型も走る前に決めているので、
  動的な言語が境界で行う数え上げがここには無い。Lua のスタック API に相当するものが要らない
- **誤りは値で返す。** 04 と 12.8 のとおりなので、
  巻き戻しの手配も `pcall` に相当するものも要らない
- **`context`** は登録時に渡した生ポインタ。ホストの持ち物であり、
  ガベージコレクションからは見えない

##### `context` の始末

`context` はガベージコレクションの外なので、誰が捨てるかを**ホストが決める**。
分かれ目は**そのポインタをホストがまだ持っているか**である。

- **持っている** — 自分で捨てる。program を解放する側と同じ側に居るのだから、
  同じ場所で `free` すればよい。コアに頼むことは何も無い
- **持っていない** — 登録する関数が `bool` を返すだけで、確保したものの
  handle を呼び手に渡していない形。標準ライブラリのモジュールがこれで、
  誤りの種別やタグ（**この program のもの**で、他の program とは共有できない）
  を1つの構造体にまとめて `context` に載せている。この場合だけ
  **`lhat_program_on_dispose(program, call, context)`** で program に頼む

program が解放されるとき、登録の逆順に、program 自身の中身が壊される前に
呼ばれる。「登録が program に渡したもの」のための口であって、ホストが自分で
持っているものを代わりに捨ててもらうための口ではない。

##### 多値も答えられる

署名に `-> (A, B)` と書けば、C 関数は複数の値を答えられる（02 の 13.8改）。

```c
LhatValue out[2] = { q, r };
LhatValue answer;
lhat_make_tuple(machine, out, 2, &answer);
return answer;
```

**`LhatHostFn` の綴りは変わらない。** 8.9 のホスト値と同じ往復であり、
値は機械の部屋に置かれ、呼び出しが返った瞬間に機械が全幅をスロットへ書き出す。
既存のホスト関数は1行も変わらない——run 以外を返す限り、今までの経路を通る。

登録が `-> (A, B)` と言い、C 関数が1つしか答えなければ、**機械が落とす**。
両者は別々に翻訳されうるので、食い違いは実行時にしか判らない。

`op^` は1値のままである。11.8 の形に複数の余地が無い。

#### `import^`

```lhat
import^ system.io                 # system.io をこの場に導入する
let^ m = import^ some.module      # 名前を選んで導入する
```

`require^` との違いは **何を指すか** である。
`require^` はファイルパス、`import^` はモジュールパス。

導入の仕方は 5.5 と同じで、02 の 8.8 が途中のテーブルを作る。
接頭辞を共有するモジュールは合流する。

##### 親と子を同じ場に取り込める

```lhat
import^ love
import^ love.graphics       # どちらの順でもよい
love.getVersion()
love.graphics.line(…)
```

登録簿は入れ子のテーブル1つなので、**親のテーブルは子を含んでいる**。
親を取り込めば子はその中にあり、子を取り込んだ後に親を取り込めば、
子だけを持っていた仮置きのテーブルが**親のテーブルに置き換わる**——
仮置きが持っていたものは親も持っているので、失われるものが無い。
衝突の報告はそれ以外の場合に残る。

**取り込んでいないものは届かない**のは変わらない。`import^ love.graphics`
だけを書いた場に `love.getVersion` は無い——仮置きのテーブルにあるのは
`graphics` だけである。

#### `import^` が届くのはホストの登録簿だけ［重要］

> **`require^` で読み込まれた単位は、`import^` では導入できない。誤りとする。**

`require^` された単位も `L^.modules` に入るので、
そこを見に行けば `import^` でも届いてしまう。**そうしない。**

理由は順序である。`import^ ns.m` が通るかどうかが
「先に検査された単位が `ns.m` を `require^` していたか」で決まると、
**同じソースが、要求元の並び順で通ったり通らなかったりする**。

ホストの登録簿だけを見るなら、登録は検査より前に全部済んでいるので、
`import^` の成否は **ホストが何を登録したか だけの関数** になる。

診断はそれを言い分ける。`L^.modules` に見えているのに拒まれる形になるためである。

```text
import^ はホストが登録したものに届きます。その名前のモジュールはありません。
ファイルから読み込む単位は require^ "path" で入ります。
```

#### 実行時

登録されたものは、走る前に機械の `L^.modules` へ入る
（`lhat_program_install`）。したがって `import^` の生成は
**`L^.modules` を辿るだけ**であり、専用の命令を持たない。

##### `import^` の名前は入れ子の本体で捕捉されない［重要］

> **`import^` が束縛した名前を入れ子の本体が書いたとき、
> それは捕捉ではなく、走っている機械の `L^.modules` を辿り直す。**

登録は **機械ごとの値** である。C 関数そのものはどの機械でも同じでも、
それを包む値はその機械のヒープの上に作られる。捕捉は「作った機械の物」を
運ぶことなので、**別の機械で本体を走らせる形**——ホストが機械を1つ増やして
そこで閉包を走らせる場合——では捕捉した登録は使えない。

辿り直せば、その本体は **自分が走っている機械の登録** に当たる。
同じ機械の中では今までと同じものを指す（`import^` 自身がその歩きで
束縛している）ので、見える値は変わらない。

`require^` の根はこれに含めない。単位の値は走らせて作ったものであり、
辿って読み直せるものではない。入れ子の本体からは今までどおり捕捉される。

したがって **02 の 15.13 の `closed^` を書いた本体でも、`import^` した名前は
書ける**。捕捉が起きていないので、約束は破れていない。

#### 8.7改 入れ子の呼び出しの fault はホストを素通りしない

ホスト関数が `lhat_machine_call` で L^ を呼び戻し、その走行が fault した
とき、フレームは巻き戻らずに立ったままである（04 の 11.6改）。ホスト関数は
値しか返せないので、素通りさせると外側の走行が死んだフレームの上に自分の
呼び出しを積んでいくことになる。

そこで機械の側が栓をする: **ホスト関数から戻ったとき、呼び出し前より
フレームが増えていたら、外側の走行を同じ fault（panic の値も含めて）で
終える。** ホスト関数の側の作法は「入れ子の呼び出しが失敗したら速やかに
戻る」だけでよい — 何を返しても外側はその fault で終わる。トレースバックは
入れ子の分まで全部立っている。

std.regex の `gsub` が置換関数を呼び戻すのがこの形の初出で、同一機械への
呼び戻しをする stdlib はこれが最初である（std.thread は別機械なので
この問題を持たない）。

#### 8.7改2 ホストは `panic^` を書ける

> **ホスト関数は答える代わりに `lhat_machine_panic(machine, value)` を呼んで
> よい。関数が戻った時点で、呼び出し位置が `panic^ value` を書いたのと同じに
> 走行が終わる。**

プログラマの誤り——描画関数に負の幅を渡した、存在しない資源を名指した——は
04 の 11.2 の「失敗しうる操作は返り値を合併にする」の相手ではない。合併に
すれば呼ぶ側は毎回 `catch^` を書かされ、書かれた L^ 側では `panic^` で
済むものがホスト製というだけで重くなる。かといって未宣言の誤り値や `nil^`
を返せば、次に使われた所で型誤りになり、**何が悪かったかの文が消える**。

そこでホストにも `panic^` を渡す。値は何でもよく（12.7改）、普通は文字列か
誤りの値。`lhat_machine_panic_text` は文字列を作って同じことをする。
`LHAT_RUN_PANIC`、`LhatRunResult.value` に値、トレースバックはホスト関数を
呼んだ位置に立つ——書かれた `panic^` と区別がつかない。8.7改 と同じ場所
（ホスト関数から戻った直後）で見るので、3つの経路——普通の呼び出し・
ホスト値の演算子・`lhat_machine_call` でホストがホストを呼ぶ形——の
どれでも同じに終わる（最後のものは呼んだホストに `LHAT_RUN_PANIC` の
結果として返る。機械のフレームは関わらないので範囲は空）。

`f^` の登録から呼んでもよい。純粋性は検査器の話で、panic は走行の終わりで
あって走行中の作用ではない。

#### 8.7改3 ホストは値の型を問える［重要］

> **`lhat_value_type` は 02 の 14.16 の `typeof^` が答えるものを返す。
> 同じ読みであり、別の読みではない。**

ホストが値の型に応じて動く必要があるとき、いま採れる手は「L^ 側に文字列で
書いておいてもらう」だけである。それは**型の写し**であり、本体とずれる。

```lhat
let^ Item = def^{
    self^{ abstract^ gdobj : godot.Resource },
    override^new = f^ obj { self^{ gdobj = obj } },
    gdBaseClass = "Resource",      # ← 写し。Node2D と書いても通る
}
```

本体は構築子の署名にある。`Item.new` の型を問えば、取るのが
`godot.Resource` だと分かり、8.8 のタグからそのまま `"godot"` と
`"Resource"` が出る。**引数に注釈が無くてもよい**——02 の 14.16 のとおり、
書かれていない引数も推論が決めた型を答える。

答えは機械のものなので、**次に機械を走らせるまで**読める。8.9 の
フォルト時フレームと同じ寿命である。ただしぶら下がっているもの——
署名の引数型——は proto の chunk が持ち、機械より長生きする。写さずに
そのまま答えているためで、ホストが握るのは普通そちら側になる。

#### 定数 — 8.7改

登録できるのは手続きだけではない。`lhat_register_const_integer` /
`_real` / `_bool` / `_string` は**値そのもの**を置く——enum の数、上限、
名前。`type` を NULL にすればモジュール直下、登録済みの型名（8.8 の
hostdata・8.9 のホスト値型どちらも）を書けばその型の静的メンバになり、
`godot.Node.NOTIFICATION_READY` と読める。型の表とメンバの表は同一物
なので、値からも（`v.NOTIFICATION_READY`）読めるのは帰結であって例外
ではない。

設置時に一度だけ値が作られ、以後はテーブルの普通の要素——読みは
GETMEMBER がそのまま返し、書き込みは 8.6 のとおり拒否される。署名文字列は
無く、検査器には number^ / bool^ / string^ の共有ノードが1つ置かれる
だけなので、数千個の登録も表への挿入の費用しか払わない。同名は登録時に
拒否——定数はオーバーロードの腕ではない。

### 8.8 ホストのデータ

> **ホストが作ったものは、L^ がポインタとして持つ。中身は覗かない。**

#### 他の言語の形［参考］

骨格はどれも同じで、**インタプリタがヘッダを持ち、ホストがペイロードを持ち、
終わりにコールバックでペイロードを返す**。分かれるのは誰が確保するかである。

- **埋め込み** — Lua の full userdata、Wren の foreign class。
  インタプリタのヒープ内にバイト列を確保し、ホストがそこに構築する。
  C++ では placement new が要る
- **ポインタ** — Ruby の `Data_Wrap_Struct`、V8 の `External`。
  ホストが確保し、インタプリタはポインタと解放関数を持つ。**C++ には素直**

L^ は **ポインタ側**を採る。12.5 の `dispose()` が既に寿命の記法を持っており、
12.6 の明示的破棄と 10.7 のガベージコレクションによる回収という二段構えは、
素の finalizer より強い（実行時期の確定する手段がある）。

#### `LhatValue` は広げない［重要］

ポインタは **値ではなくオブジェクトに載る**。
値の表現（03 の 2.2 の SoA 分離）はスタック・テーブル・退避の全部が
同じ1枠の形を前提にしており、ここに手を入れることはしない。
（8.9 のホスト値は枠を**広げず**に連続スロットを使う別の答えであり、
この規則の例外ではない。）

したがってホストが `LhatValue` を自分で組み立てることはない。
**機械が作る。** 生のポインタには `LhatObject` のヘッダが無く、
機械のヒープに繋がっていないのでガベージコレクションから見えないためでもある。

```c
bool  lhat_machine_make_hostdata(LhatMachine *, const LhatHostDataTag *, void *ptr,
                             LhatValue *out);
void *lhat_hostdata_pointer(LhatValue value, const LhatHostDataTag *tag);
```

#### タグが同一性である

`lhat_register_hostdata_type` が返すタグは、**登録ごとに1つ**であり、
比較は同一性だけで行う。`lhat_hostdata_pointer` はタグが違えば `NULL` を返す。

型の側も同じく公称とする。**11.3 が譲るのはここだけである。**

理由は 7.3 より強い。不透明なホスト型には **比較すべき構造が無い**ので、
構造で同一視すればホスト型はすべて同じ型になる。
渡し違えれば C 側が生ポインタを別の型として読む。**メモリ破壊になる。**

したがって検査と実行時の二重で守る。

- **検査** — `store.Held` を求める位置に `store.Other` は書けない
- **実行時** — `lhat_hostdata_pointer` のタグ照合。relaxed（03 の 3.1）で抜けても止まる

#### 8.8改 ホスト型は基底を1つ持てる［重要］

> **ホスト型は登録のときに基底を1つ名指せる。基底の在るタグは、基底を
> 求める位置に立てる。**

```c
lhat_register_hostdata_type(program, "godot", "Node");
lhat_register_hostdata_subtype(program, "godot", "Node2D", "godot", "Node");
```

**公称は緩めていない。**上の「渡し違えればメモリ破壊」は、そのままである。
変わったのは、宣言が**自分は何の下に在るか**を言えるようになったこと
だけである。

自分の模型が既にクラスの木であるホスト——エンジンの ClassDB、部品箱——が
その木をここに書けるようにするためのもの。書けなければ全部を1つの
不透明型に潰すしかなく、検査器が持てたはずの境界がすべて失われる。

**単一継承である。** そうした模型が持つのがそれだからで、interface に
当たるものは設けない。

##### これはポインタについてのホストの約束である

基底を宣言することは、**この型のポインタを基底のものとして読んでよい**と
ホストが言うことである。C++ の単一継承・仮想基底無しなら真だが、
**言語には検かめようが無い**。02 の 15.13 の `closed^` と同じ種類のもの——
知っている者が書き、下流はその言葉どおりに扱う。

だから `lhat_hostdata_pointer` は、値のタグが求めるものか**その派生**なら
生ポインタを答える。そうでなければホストは自分が宣言した関係を使えない。

##### 継ぐものは2つあり、置き場所が違う［重要］

- **メンバ** — 型の表に在る。**登録が閉じた時点**（最初の検査）で基底から
  写す。登録のたびに写すのでは間に合わない——互いを名指す型は
  「まず素の型を全部、あとからメンバを」の順でしか登録できないので、
  関係を宣言した時点では基底にメンバが1つも無い。だから
  **登録の順に規則は増えない**
- **`dispose`** — **タグに在る**。写さず、鎖を辿って引く。タグは
  プロセス全体で共有されるものであり、プログラムごとの処理が書き込む
  先ではない

**この2つを分け損ねると黙って壊れる。** 12.5 は破棄可能かを
「`dispose` という名のメンバが在るか」で判定するので、メンバだけ継いで
タグを継がないと、`with^` は検査を通り、実行時は何も走らない。
誤りにすらならない。「二度は返さない」の見分け（上記3契機）も同じ所を
読むので、同じ扱いが要る。

派生が自分で `dispose` を登録すれば、鎖を辿って先に見つかるものが
それになる。上書きは規則を足さずに効く。

##### 記述子はタグで止める。ホストの API を写さない［重要］

実行時の型記述子（8.7 の輸出記述子、02 の 14.16 の `typeof^`、02 の 13.11 の
`fits^` が引くもの）は、鎖の途中でホスト型に当たったら**メンバを写さず、
タグを置いて打ち切る**。委譲先（02 の 14.7改2）が `godot.Node` なら、包みの
記述子は自分のメンバと「加えて `godot.Node` を持つ」というタグだけを持つ。
印字は `t^{ gdobj : godot.Node } & godot.Node`（14.5 の `&`）。

写すと、クラス木の全 API（各メソッドの署名込み）が定義と instance の
2回ずつ記述子に入り、1.4KB の単位が 160KB のバイナリになる。そもそも
「ホスト型は宣言そのもの」（8.8）であって、メンバの写しに意味は無い。

`fits^` の実行時判定は、列挙されたメンバの後に、値が**そのホスト型の値か、
委譲1段先にそれを持つか**（14.7改2 の引きと同じ1段、タグの基底鎖込み）を
問う。検査器の側は変わらない——写しは適合判定の内側の話で、委譲先の
メンバは今までどおり引ける。

##### 帰結: 基底と派生で多重定義できない

14.12 は重なる署名の多重定義を拒む。基底と派生は互いに素でなくなるので、
`f(Node)` と `f(Sprite2D)` は書けない。**特定度による選択は 14.12 が
持たない規則であり、ここで持たせるつもりも無い。**

##### ホスト値型（8.9）には及ぼさない

`Vector2` のような値型に継承は無い。

#### 値の等値はタグと実体ポインタ

hostdata が立っているのはホストが作ったもののほうであって、ラッパでは
ない。だから `=` は **同タグ・同ポインタ** で答える — 同一オブジェクトを
2度包んだ2つのラッパは等しく、テーブルのキーとしても1つに畳まれる
（キーのハッシュも同じ対から取る）。Lua が弱値レジストリで「同一
userdata を返す」ことで得ていた同一性を、L^ はラッパを増やしたまま
等値の側で成立させる。

- `is^` は従来どおり**ラッパそのものの同一性**。2つのラッパは `is^` で
  区別できる
- **release 後は自分自身としか等しくない**。返したポインタは再利用され
  得るので、値としても比較しない（ハッシュは release で変えない —
  格納済みキーのハッシュが動いてはならないため。ポインタは値として
  混ぜるだけで、参照は決してしない）
- タグが違えばポインタが同じでも等しくない（上の公称則そのまま）
- 既知の乖離: hostdata 型に `op^=` を登録すると検査は通るが、実行時の
  演算子ディスパッチ（operator_candidate）は hostdata の members を
  見ないため呼ばれない。組込みの等値が上記で定義された今、実害は無いが
  未解消のまま

#### 登録したものは書き換えられない

ホスト型が持つのは **ホストが登録したもの** である。
`length` は `foo_length` という C 関数であり、生ポインタをタグの型として読む。

```lhat
p.length := f^self^ -> number^ { return^ 0 }   # 誤り
var^ p.other := 1                              # 誤り
```

- **メンバの追加** — 02 の 8.8 の印が既に拒む。ホスト型は登録の時点で形が固定される
- **メンバの差し替え** — 上と同じ理由で拒む。
  差し替えを許すと、タグは `Foo` と言い続けるのに中身が別のものを指す

上の「渡し違えれば C 側が生ポインタを別の型として読む」がそのまま当てはまる。
**不透明であることが、そのまま書けない理由になる。**
テーブルの可変性をモジュール単位で決める機構（M7）を待つ必要はない。

02 の 14.16 の型情報も同じ扱いとする。公称であり、何を持つかは作った側が決めている。

`def^` のインスタンスは公称ではないので、この規則の対象外である。
14 章のフィールドを書き換えるのは、フィールドの用途そのものである。

##### 応答できるようにするなら2つ要る［提案］

ホスト型が将来メンバへの代入に応答するようになった場合、
**上の一律の禁止を外すだけでは足りない**。

```lhat
let^ shared = shapes.makeFoo(3, 4)

let^ f = f^ n:number^ -> shapes.Foo {
    shared.x := n                    # 不正のまま。呼び出し側のもの（02 の 15.1改）
    let^ mine = shapes.makeFoo(0, 0)
    mine.x := n                      # これを通したい
    return^ mine
}
```

要るのは次の2つで、**対にして入れる**。片方だけでは `mine.x := n` が通らない。

1. **この節の禁止を、ホストが可変と登録したメンバに限る。**
   何が書けるかを決めるのは登録した側であり、公称であること自体ではなくなる
2. **02 の 15.1改 の「本体が作った」に、構築関数の呼び出しを加える。**
   `makeFoo` は 8.7 の普通の関数なので、いまは「作った」に数えられない

2 は 15.1改 が置いた `fresh^` の印にあたる。ホスト側は 8.7 の登録に
その印を持たせればよく、`lhat_register_func` に渡す署名の側の話になる。
**C の中は見えないので確かめず、申告を信じる。**
このファイルが既にホストへ課している約束（借用のぶら下がり、解放関数の制限）と同じ立場である。

#### 構築は普通の関数である

`new`（14 章）は `def^` のための機構であり、ホスト型には載せない。
Lua の `io.open` と同じく、モジュールの関数が作る。記法を増やさずに済む。

```lhat
import^ shapes
let^ p = shapes.makeFoo(3, 4)
let^ n : number^ = p.length()
p.dispose()
```

```c
foo_tag = lhat_register_hostdata_type(&program, "shapes", "Foo");
lhat_register_member(&program, "shapes", "Foo", "length",
                     "f^self^ -> number^;", foo_length, NULL);
lhat_register_member(&program, "shapes", "Foo", "dispose",
                     "p^self^;", foo_dispose, NULL);
lhat_register_func(&program, "shapes", "makeFoo",
                   "f^number^, number^ -> shapes.Foo;", foo_make, NULL);
```

`self^` は 13.4 のとおり引数の一覧に入らない。
受け取り手はホスト関数の `arguments[0]` に来る。

#### 借用と所有は `dispose` の有無で決まる

新しい軸を作らない。**12.5 がテーブルに対して行っている判定をそのまま使う。**

- `dispose : p^self^;` を登録した → **所有**。`with^` に渡せ、12.6 の破棄が効く
- 登録しない → **借用**。走るものが無い。寿命はホストのもの

#### 借用のぶら下がりはホストの責任

ホストが先に解放したポインタを L^ が持ち続ける場合を、言語側では守らない。
light userdata と同じ立場である。守るなら所有側（`dispose` を登録する）を使う。

#### 返す口は値が持つ

**解放関数はタグに載せる。値から辿れる場所に置く。**

メンバのテーブルから `dispose` を引く形は採らない。
**掃除は順不同**であり、値を回収する時点でそのテーブルが
既に解放済みでありうるためである。

タグは登録簿のものなので、**どの機械よりも長生きする**。値が持つのは
「もう返したか」の印だけでよい。

#### 返るのは3つの契機

10.7 の二段構えがそのまま効く。

- **手で `dispose()` を呼ぶ** — 実行時期が確定する
- **到達不能になり、GCが回収する** — 掃除の中で返す
- **機械が破棄される** — 残っているものをすべて返す

**二度は返さない。** 10.7 の「すでに実行済みのものは破棄時に再実行されない」を
そのまま適用する。手で呼んだ `dispose()` は機械が見分けて印を立てる。

`dispose` を登録していない型（借用）では、どの契機でも何も走らない。

#### 解放関数は L^ の API を呼んではならない

掃除の途中で呼ばれるためである。その時点でヒープは半分掃かれており、
そこへ値を作りに行くことはできない。

**ポインタを解放する以外のことをする理由が無い**ので、制約として明記するに留め、
Lua や Python のように解放を別のフェーズへ回す機構は設けない。
コルーチンの `finally^`（10.7）は L^ のコードなので事情が違うが、
そちらが要求するまで待つ。

#### `for^ in^` で歩けるようにする — `iterate^` の登録

ホストデータ型に `iterate^` を登録すれば、02 の 16.3 がテーブルに
与えているのと同じ足場に乗る——`for^ x in^ value` が登録した歩みを回す。
登録しなければ `in^` に渡すのは検査の誤りである（16.3）。
ホストデータはメンバの引き方だけがテーブルであり、裏に歩けるテーブルは
無いからである。

登録は普通のメンバである。コルーチンを答える署名を書く:

```c
lhat_register_member(&program, "godot", "PackedFloat32Array", "iterate^",
                     "f^self^ -> c^{p^ -> number^};",
                     packed_iterate, NULL);
```

本体は、歩みの状態を確保して `lhat_machine_make_coroutine` に step と
release を渡すだけである:

```c
// One step per resume: fill *out and answer true, or answer false when
// the walk is over.
static bool packed_step(LhatMachine *machine, void *context,
                        LhatValue sent, LhatValue *out)
{
    PackedWalk *walk = (PackedWalk *)context;
    if (walk->at >= walk->size) {
        return false;
    }
    *out = lhat_real(walk->data[walk->at++]);
    return true;
}

static LhatValue packed_iterate(LhatMachine *machine, void *context,
                                const LhatValue *arguments, size_t count)
{
    PackedWalk *walk = /* allocate; read the array off arguments[0] */;
    LhatValue out = lhat_nil();
    if (!lhat_machine_make_coroutine(machine, packed_step, walk,
                                     packed_release, arguments[0], &out)) {
        /* free walk */
        return lhat_nil();
    }
    return out;
}
```

- `held` に渡した `arguments[0]`（歩く対象）は、歩みが生きている間
  収集器から到達可能に保たれる
- `release` は上の解放関数と同じ契約——**一度だけ**、掃除の途中から
  呼ばれうるので **L^ の API に触れない**。歩みが尽きても、明示の
  `dispose()` でも、機械の破棄でも、どの終わり方でも走る
- 鍵と値の組を出す歩みは、step が `lhat_make_tuple` の答えを `*out` に
  書く。署名は `c^{p^ -> (number^, T)}`、ループは
  `for^ k, v in^ value` になる
- 歩みは本体を持たないコルーチンである。テーブルの走査（02 の 16.3）と
  同じ第3の出自であり、`start()` / `resume()` / `dispose()` / `done()` も
  手駆動もそのまま効く

#### ホスト境界のコルーチン API

Lua の `lua_newthread` / `lua_resume` / `lua_status` に相当する3つで、
ホストは書かれた本体と同じ足場に立つ。

- `lhat_machine_make_coroutine(machine, step, context, release, held, &out)`
  ——本体が C であるコルーチン。上の `iterate^` が答えるものそのもの
- `lhat_machine_resume(machine, coroutine, sent, sent_count)` ——どの
  コルーチンでも C から1歩進める。**start は無く、resume が兼ねる**
  （`lua_resume` と同型）: 未開始の本体は頭から走り、最初の送りは
  捨てられる——受ける `yield^` がまだ無いからで、慣用は `NULL, 0`。
  送りは配列で、個数は `R` の幅（02 の 13.9——タプルの `R` はその幅の
  引数）。答えは 13.9 の union(Y, T) であり、区別は `done()` に訊く
  （02 の 15.6改 と同じ線）。多値の答えはこの境界を `positions` として
  渡る（8.7）。**ホスト値も両方向を丸ごと渡る**（8.9改2）:
  受け——`yield^` の産出も `return^` の T も pointer 形の `LhatValue` と
  して `value` に乗り、中身は `lhat_hostvalue_data(value, tag)`（タグ照合
  込み）。バイトの寿命は `positions` と同文——**次に機械を動かす呼び出し
  まで**（部屋は機械のスクラッチ1つ。跨がせるならホストが写す）。
  送り——`lhat_make_hostvalue` が作った pointer 形を sent に1つ置く。
  **1席に丸ごと1値**（多値に混ぜれば拒否）。検査済みの本体へは下ろされた
  `R` の**タグと照合**し、違う登録の値は届く前に拒む——値数しか見ない
  従来の境界検査より強い
- `lhat_machine_coroutine_done(coroutine)` ——15.6改 の `done()` を C から
- `lhat_machine_fault_depth / _fault_frame / _traceback` ——04 の 11.6改 の
  トレースバック。fault の後（次の実行/破棄まで）に読む。fault が無ければ
  「いま立っているフレーム」を答えるので、ホスト関数の中から
  「どこで呼ばれたか」も訊ける

書かれた yieldable な手続きを `lhat_machine_call` で呼ぶと、実行されずに
コルーチンが返る——コンパイルされた呼び出しと同じ 02 の 15.5 の形が、
この境界でもそのまま成り立つ（`lua_newthread` の位置）。本体は機械自身の
フレームで走るので、これらは `lhat_machine_call` が入れ子にできる場所
ならどこでも入れ子にできる。

##### `lua_yieldk` 相当は設けない

Lua の `yieldk` が継続 k で解いているもの——「C 関数の途中で止まり、
後で続きから」——は、ここでは step コールバックそのものである。歩みの
状態は `context` に置かれ、resume ごとに step が1回呼ばれる。継続が
可視で単純な等価物として最初からあるので、別の機構は足さない。

#### 機械の間を運ぶ — `stdlib/carry`

> **別の機械へ渡す値は、どの機械にも属さない木に一度ほどき、向こうで
> 組み直す。ホストは深いコピーを自前で書かない。**

機械はヒープを共有しない。テーブルや閉包はポインタなので、そのままでは
別の機械の値にならない。`lhat_carry(value, &carried, &refused)` が値を
`LhatCarried`——どの機械のヒープも指さない木——にほどき、
`lhat_uncarry(machine, carried, &out)` が目的の機械の上に組み直す。
std.thread の `spawn` の引数・`join` の答えがこの道を通る。LOVE2D の
Channel のような「値を別の機械へ置く」バインドも同じ部品で済む。

運ぶもの:

- `nil^` / `bool^` / `number^` / `string^` —— そのまま
- **素のテーブル** —— 配列部もハッシュ部も再帰。**循環は保つ**
  （元のオブジェクトを memo し、同じものは向こうでも同じ1つになる）
- **閉包** —— proto は両機械で共有できる（同じ program のもの。
  `lhat_proto_new` の注記のとおり生まれながらに黒）ので、運ぶのは
  **proto の参照 ＋ 捕捉した値の写し**。同じ場所を捕捉した2つの閉包は
  向こうでも同じ1つの場所を共有する（捕捉セルも memo の対象）。
  向こうで書いても元の機械には流れない——機械が隔離されている以上、
  捕捉が**スナップショット**になるのが正しい意味（Erlang がプロセス間に
  fun を送るときと同じ）。02 の 15.13 の `closed^` は std.thread の
  要件ではなくなった（書いてあれば従来どおり検査され、spawn に収まる）

運ばないもの（`refused` に理由が立つ）:

- **始まっているコルーチン** —— 機械のフレームそのもの。まだ始まっていないものは
  下の 8.8改3 で渡る
- **def^ とそのインスタンス** —— 定義テーブルの同一性を向こうで引き直す
  規則が要る。素のテーブルだけが運べる
- **`std.load` が作った閉包** —— 本体が機械のヒープのもの（5.6）で、
  写しは向こうで宙に浮く
- **ホスト値・ホストの手続き** —— スタックの中の値と、機械ごとに install
  されるもの。ホストデータは下の共有契約を宣言した型だけが渡る
- **誤りの値・単位** —— 単位は走らせて作ったもので、辿り直すものではない
  （上の `import^` の節と同じ線）

##### 8.8改3 まだ始まっていないコルーチンは渡る

> **`gen()` は 02 の 15.5 により本体を1行も走らせない。よってその値は
> 「閉包＋積まれた引数、進捗ゼロ」でしかなく、運べる。**

```lhat
let^ gen = p^ n:number^ { yield^ n * 2 }
ch.push(gen(4))          # 向こうの機械で start() できる
```

拒否の理由は「フレームは走らせる機械のもの」だったが、**まだフレームが無い**。
運ぶのは閉包（8.8改 のとおり proto は共有・捕捉は写し）と、呼び出しが既に積んだ
レジスタ像。向こうでは呼び直さずに**作る**——呼び直すと 13.7 の可変長の尾が
二重に集められるので、機械自身が書いた像をそのまま写す
（`lhat_machine_make_coroutine_from`、vm.h）。

組み直したものは**別のコルーチン**である。元はこちらで未開始のまま残り、
両方が独立に start できる——閉包の写しがスナップショットであるのと同じ線。

始まっているもの・表の走査・ホストが書いた走査は今までどおり運ばない
（どれも機械の状態そのもの）。

##### 8.8改2 共有契約——宣言した型のホストデータは渡る

> **`lhat_register_hostdata_shared(program, module, name, retain, let_go, ctx)`
> で宣言した型のホストデータは、ポインタとして運ばれ、向こうの機械で
> 同じ型の包みになる。ポインタの寿命はホストが `retain` / `let_go` で数える。**

ポインタの再鋳造が安全に言えなかったのは所有の規則が無かったからで、
規則はホストの側にある——参照カウント、あるいは「ホストが持つ、数えない」
（両方 NULL）。宣言は型ごと: lhatove は `love::Object` の全型に立て、
graphics の Texture には立てない、という選択ができる。スレッド安全性は
ホストの約束（Lua 版と同じ）。

hold は3つで釣り合う: carry が木に1つ取り、`lhat_carried_free` が返す。
`lhat_uncarry` は包みを作るたびに1つ取り、その包みの `dispose^`（8.8 の
3契機）が返す。`dispose^` はタグのものなので、program を install して
いない機械に組み直した包みも同じに返す（メンバ表は空）。`dispose` 済みの
値は運ばない。
二つ目のプログラムの宣言は同じ組なら同じ宣言、違えば拒む（7.3）。

#### 待ちは armed した機械のもの — `std.async`

待ちの表は program のものだが、**待ちは armed した機械に答える**。program に
機械は何台でも在り（std.thread はワーカーごとに1台）、id が意味を持つのは
それを armed したスケジューラに対してだけだから。

これが無いと、2つ目のスケジューラが「今 ready なもの」を訊いたときに1つ目の
id を持って行き、両方止まる——1つ目は自分のが来ず、2つ目は取った id に心当たりが無い。
`wait` / `next` / `pending` / `drop` は自分の機械の分だけを見る。押す側
（`lhatstdlib_async_complete`、別スレッド）は id しか持たないので全体を見る。

`lhatstdlib_async_take(waits, machine, id)`（async.h）は「その id が ready なら取る」
——1本のジョブを駆動する側が使う。`wait` の「ready なものを1つ」はタスクの表を持つ
スケジューラの形で、id を1つだけ持つワーカーには他人の分まで取ってしまう。

#### 終わりは押して届ける — `awaitable` / `failed` / 完了フック

> **`join()` を呼ぶまで気づけない、では困る。ワーカーの終わりは
> スケジューラにもホストにも押して届く。**

- `h.awaitable() -> number^` —— `std.async.external` の待ちを1つ配り、
  本体が終わったときに押す。スケジューラはその id を出して止まればよく、
  `done()` を数 ms おきに訊く形は要らない（`sample/async.lh` の `joined`
  がこの形に変わった）。std.async が登録されていなければ 0
- `h.failed() -> string^|nil^` —— join せずに誤りだけ読む。走っている間と
  正常終了は `nil^`
- `lhatstdlib_thread_on_finish(program, fn, ctx)`（thread.h）——
  本体が終わった時点で**ワーカー自身のスレッドから**呼ばれる。機械はもう
  無い。LÖVE の `threaderror` を積むのがこれ。L^ には触れない
- `lhatstdlib_thread_join_all(program)` —— program を捨てる前に、走って
  いる本体を全部待つ。ハンドルはそのまま（後の `join()` は答えを返す）。
  ハンドルを手放したワーカーが proto を読み続ける経路を塞ぐ口

`join` の答えは `any^` になった。carry が運ぶものは 8.8改2 以降
テーブル・閉包・ホストのオブジェクトも含み、scalar の合併では嘘になる。

#### 常駐する機械の群れ — `std.task`

> **N 台の機械を立てたままにし、ジョブを配る。ジョブは carry した
> 「まだ始まっていないコルーチン」か `p^...` の閉包。走り切るまで
> その機械のもので、途中で他へ移らない。**

```lhat
std.task.start(6)                  # 6本。何も言わなければコア数
let^ t1 = std.task.async(gen1())   # gen1 が yieldable なら gen1() は
let^ t2 = std.task.async(gen2())   # 未開始コルーチン（8.8改3）
std.task.await(t1)                 # 2つは別スレッドで並行
std.task.stop()
```

std.thread は呼ぶたびに機械と OS スレッドを1つ作る（実測 1.55ms/本）。
std.task は `start` のときだけそれを払い、以後はジョブを配る。

- **ジョブの中の `await^` は効く。** ワーカーがコルーチンを駆動し、
  yield された値がその機械の std.async の待ちなら、その id が来るまで待つ
  （8.7改 の id 指定の取り出し）。待ちでない値——0 でも、他の数でも、
  他の種類でも——は「渡すために止まった」であって待ちではないので、そのまま進む。
  sample/async.lh の Scheduler と同じ読み
- `await` は呼んだ機械を止める。ループを持つ側は `t.done()` か
  `t.awaitable()`（15.14改 の押し）
- `Task` は共有型（8.8改2）。チャネルに積める・他のジョブへ渡せる
- **プールは program の本体を握る。** 破棄の前に `std.task.stop()`
  （C からは `lhatstdlib_task_stop`）。モジュールの後始末も保険で止める

**横取りは無い。** 終わらないジョブはそのワーカーを握り続ける。BEAM の
軽量プロセスとの差はここで、埋めるには実行予算での中断が要る（未着手）。

#### 機械の間のキュー — `std.channel`

> **carry の上に置く MPMC の待ち行列。中身は運ばれた木のまま持ち、
> 取り出す機械で組み直す。**

spawn の引数と join の答えは一往復ずつで、仕事を配られ続けるワーカーや、
何度も答えるワーカーには足りない。std.channel はその置き場である
（LÖVE の `love.thread.Channel` と同じ形——バインドが自前で持つ必要は
無くなる）。

```lhat
let^ jobs = std.channel.named("jobs")     # プロセス全体で同じ1つ
let^ ch = std.channel.new()               # 手渡した先だけが持つ

ch.push(v) -> number^      # 積んで番号（1, 2, 3 …）を答える
ch.supply(v[, 秒])         # 積み、誰かが取るまで待つ。取られたか
ch.pop() -> any^           # 先頭。無ければ nil^
ch.demand([秒]) -> any^    # 来るまで待つ。切れたら nil^
ch.peek() / ch.count() / ch.hasRead(番号) / ch.clear()
ch.atomic(p^ c:std.channel.Channel { … })   # 錠を持ったまま呼ぶ
```

- 渡るものは carry が運ぶもの（8.8改2 のホストデータを含む）。それ以外は
  `ChannelError.Refused` に carry の理由文がそのまま乗る
- **Channel 自身が 8.8改2 の共有型**なので、チャネルをチャネルに積める・
  `spawn` の引数に渡せる。ワーカープールはこれで書ける（`demand` で待つ
  ワーカーを N 本）
- `atomic` の中では待たない——錠を持っているのは自分なので、`supply` と
  `demand` は `push` / `pop` と同じに答える。追加引数は取らない
  （閉包が捕捉すればよい。固定引数の閉包は可変長署名に適合しない）
- 名前付きはプロセスの表。閉包を積んだまま program を捨てるなら、
  その前に `lhatstdlib_channel_forget_named()`（本体は機械のヒープのもの、
  5.6 の裏返し）

### 8.9 ホストの値

> **ホストは参照だけでなく値も定義できる。8.8 のホストデータが「ホストが
> 持ち、L^ がポインタで指す」ものだったのに対し、ホスト値は「機械が
> バイト列ごとスタックに置く」ものである。Lua の light/full userdata の
> 「誰が確保するか」の軸を、L^ は **値／参照** の軸として切り直す。**

第一の動機は数学型である。Godot の `Vector3` に相当する書き心地 --
`let^ to = a + b` の一時値がヒープ確保ゼロでスタック上を流れること --
を、ホストが登録した型で実現する。

#### スタック表現

03 の 2.2 が payload とタグを並走配列に分けたので、連続する payload
スロットは**素で連続したバイト列**である。ホスト値はそこに置かれる。

```text
slot i   : payload = LhatHostValueTag*   tag = HOSTVALUE   … head
slot i+1 : payload = 生バイト            tag = CONT
…
幅 = 1 + ceil(size / 8)     例: f32×3 の Vector3(12B) → 3 スロット
```

head が自己記述する（タグから型と幅が引ける）ので、一括コピー・退避・
GCの走査は幅を知らずに正しく動く -- CONT はオブジェクトではない
ので走査は素通りし、コピーはスロットを盲写しするだけでよい。

登録は `lhat_register_hostvalue_type(program, module, name, size)`。
メンバ（演算子・メソッド）は `lhat_register_hostvalue_member`、
フィールドは `lhat_register_hostvalue_field(…, offset, kind)` で申告し、
`v.x` はホスト呼び出しなしにバイト列を直に読み書きする。

#### スタックの外に出られない［重要］

> **ホスト値はスタックのスロット以外のどこにも住めない。**

テーブルの要素・捕捉（上位値）・`any^` への昇格・`...`・def^ の
フィールド・タプルの位置・セッション最上位の束縛・プログラムの答え --
これらは全部この一原則の症例として検査器が拒む
（`LHAT_CHECK_ERR_HOSTVALUE_ESCAPES`）。**relaxed でも拒む**：実行時検査は
表現に無い場所を作れないからである（03 の 3.5 の例外）。コンパイラも
同じ拒否を持ち、検査なしのコンパイルの背止めになる。

**拒むのは幅であって種別ではない。** 検査はどれも「その席に何スロット
あるか」を訊いており、合併がホスト値を運んでいれば席の話は変わらない——
`Vector3|nil^` はどちらの腕が来ても Vector3 のスロットを要る。だから
上の一覧はすべて合併越しにも効く（`print(v?.x)` のように `?.` が作った
合併も同じ理由で可変長の席に載らない）。

#### 8.9改 合併には立てる

> **ホスト値は合併の腕に立てる——他の腕がすべて1スロットで、
> 頭スロットのタグで判別できるものであるかぎり。**

かつては合併も上の一覧に並んでいたが、**それは誤りだった**。
`Vector3|nil^` はスタックの外に出ない——出ないのだから一原則の症例では
ない。詰まっていたのは幅で、席が1スロットしか予約されないことだった。
判別のほうは最初から可能である: 頭スロットのタグは `HOSTVALUE` と `NIL`
で別物であり、`??`・`?.`・`fits^`・ループの終了判定はそのタグを読む。

立てる条件は 13.8改 が**タプル**に与えたものと同じ family である
（幅のある値の隣は、頭スロットのタグで判別でき、判別する構文があるもの
だけ）——`nil^` と誤りの種別。

```lhat
let^ pick = f^ n:number^ -> std.math.vector3.Vector3|nil^ { … }
var^ m = pick(1)
if^ m? { print(m.x) }                     # narrow して読む
let^ y = (m ?? std.math.vector3.new(0, 0, 0)).x  # 既定を与える
let^ known = m fits^ std.math.vector3.Vector3      # 訊く
```

席の予約は幅のほうに合わせる。値の腕はその幅を書き、`nil^` の腕は頭
スロットだけを書いて残りをそのままにする——読まれないので構わない。
ホストの登録も同じ形を答えられる（`f^ -> test.c.C|nil^;`）。

**立てられない相手**:

- **`any^`** ——読むべき頭が無い。合併すれば `any^` そのものになるので、
  置いた覚えのないまま逃げたことになる
- **幅のある腕どうし**（タプルとホスト値、ホスト値2つ）——頭スロット1つ
  では2通りの読みを持てない
- **判別する構文の無い腕**（`Vector3|string^` など）

どれも `LHAT_CHECK_ERR_HOSTVALUE_UNION` で拒む。

`box^` は合併を受け取らない。先に narrow してから箱に入れる。

保持したければ**箱に入れる**。箱は言語が型ごとに1つ用意する --
ホスト値型 `T` を登録すると **`T.Box^`** が付いてくる。
`box^値` が箱を作り、`get()` が unboxing、`set(値)` が boxing である。
何かを保持することが綴りとして見えるのは意図であって不便ではない
——見えない変換は、C# の struct が黙って複製へ書き捨てる罠と、
気づかないうちに boxing が積み上がる罠の両方を持ち込むので採らない。

```lhat
let^ b = box^std.math.vector3.new(1, 2, 3)   # std.math.vector3.Vector3.Box^
let^ t = { held = b }                  # 普通のヒープ値。テーブルにも
var^ m : std.math.vector3.Vector3.Box^|nil^   # 合併にも any^ にも入る
                                       # （8.9改: 値のまま合併に立てるなら
                                       #  std.math.vector3.Vector3|nil^ でよい。
                                       #  箱が要るのは保持のためである）
let^ v = b.get()                       # 取り出しは常に複製（値意味論）
b.set(v * 2)                           # 同じ型の値でバイト列を上書き
```

箱の性質は次で全部である。

- **普通のヒープオブジェクト**。上の escape 一覧のどこにでも住める。
  `=` は**中身**（同タグ・同バイト。スタック上の値の `=` と同じ答え）、
  `is^` は容器の同一性 -- 文字列と同じ分担である。異タグの箱の `=` は
  検査が INCOMPARABLE で拒む
- **`T.ConstBox^` -- get 専用の封印箱**が対になる。`constbox^式` で作り
  （ホスト値から直に、または箱の封印複製として。常にコピー）、set を
  持たない。conforms は一方向: **Box^ は ConstBox^ の要求席に適合**
  （読みだけのビューに可変箱を渡すのは常に安全）、逆は set が嘘になる
  ので不可。よって ConstBox^ 型は封印済み実体の**保証ではなくビュー**
  であり、封印実体を作るのは constbox^ だけ
- **キーとして記録できる箱は封印済みのものだけ**。キーのハッシュは
  バイト列であり、封印だけがそれを止めておく。静的には**書きの位置**
  （リテラルの `[k] =`・`t[k] :=`）の箱型キーに ConstBox^ を求め
  （MUTABLE_KEY）、実行時は未封印の箱の**記録**を BAD_KEY で拒む --
  ビュー越しに可変箱が届いた場合も実行時で止まり、「後からハッシュが
  動いて行方不明になるエントリ」は一切作らない。**引くのは Box^ の
  ままでよい** -- 照合はその瞬間の内容で行われ、表が持つキーは全部
  封印済みなので何も動かない（set() すれば別のエントリに届く、それが
  内容キーの意味である）。**引きは裸のホスト値でもよい** -- `t[vec]` は
  その瞬間のバイトで照合する（箱の比較が読むのはどうせ get() のバイト
  である）。裸のホスト値を**記録**することだけができない -- キーの席は
  1スロットであり幅が乗らない。記録するときは constbox^ に入れる
- **中身はインラインのバイト列**（登録フィールドは全数値）。参照を含まないので
  コレクタの葉であり、**dispose は無い**
- `box^` の失敗は機械停止（テーブルリテラルと同格）。合併も try^ も要らない
- 02 の 14.11 の既定値になれる**複製されるノード**である —
  焼き込みが封印コピーを持ち、生成が各インスタンスに未封印コピーを配る
- `typeof^` は `T.Box^` を答える。箱と中身は別の型である

#### 検査と幅

ホスト値の型と幅は**常に静的に既知**である。`any^` に広がれないので、
値の出所は登録された関数の返り値かホスト値演算に限られ、どちらも署名が
型を言う。検査器は式の型がホスト値だったとき、そのノードに
`checked_type` を印す（03 の 5.11a と同じ経路）-- 型盲目のコンパイラは
この印から幅を読み、レジスタ確保と移動（MOVE の連発）を幅つきで行う。

呼び出し規約は変えない。引数は呼び先の窓に幅つきで並び、呼び先は同じ
幅で引き取る -- 窓の重なりはそのままである。返り値だけが手術点で、
1 スロットの `answer` に載らないため、フレーム自身が持つ部屋
（`answer_run`）を経由して drain（finally^）を生き延び、pop が呼び元の
スロットへ全幅書き出す。

#### 等値は既定でバイト列

ホスト値には同一性が無い。それが値であることの半分である。
**何も書かれていなければ** `=` は **タグの同一 ＋ バイト列の一致**であり、
head だけ比べて「同型なら等しい」と誤答する道は塞いである。
作られるたびに末尾バイトはゼロ埋めされるので、スロット丸ごとの比較で足りる。

**これは既定であって、動かせない規則ではない。**
02 の 11.9 はホスト値にもそのまま当てはまる — **`op^=` を登録した型では
`=` と `≠` がそれを読み、`op^<=>` を登録した型では順序も等価もそれが答える**。
探す順は 11.9改 のとおり `op^=`・`op^<=>`・既定の3段であり、
バイト列の一致は最後の段——「何も書かれていないとき何を答えるか」を
定めているだけで、書かれたものを覆さない。

テーブルとの違いは既定の側だけである。テーブルは 14.2 の参照同一性から
値の等価に変わり、ホスト値は**バイト列の一致から型が定める等価に変わる**。
浮動小数を持つ型が `-0.0` と `0.0` を等しいとしたい、といった場合がこれにあたる。
順序を持たない型なら `op^=` だけを登録すればよい。

```c
lhat_register_hostvalue_member(program, "geo", "Vec2", "<=>",
                               "f^self^, o:Vec2 -> number^;",
                               vec2_compare, module);

lhat_register_hostvalue_member(program, "m", "Handle", "=",
                               "f^self^, o:Handle -> bool^;",
                               handle_equal, module);
```

`is^` は別である。11.9 のとおり**同一性は順序とも等価とも別の問い**であり、
ホスト値の同一性はバイト列そのものだから、`op^=` や `op^<=>` があっても
変わらない。

順序（`<` など）も 11.9 に従う。`op^<=>` を登録していないホスト値を
順序で比べようとすれば、11.9 が言うとおり**検査時の誤り**になる。

#### 8.8 と共有する規則

- **タグが同一性**（7.3 の例外の再適用）。同じ形の2つのホスト値型は別の型
  である。取り違えれば C がバイト列を別の型として読む
- **検査＋実行時の二重**。relaxed で静的検査を抜けても、head のタグ照合が
  実行時に止める
- **登録時に形が固定**。メンバの追加・差し替えは不可。ただし
  **フィールドへの代入は許す** -- 中身がポインタでなくバイト列なので、
  8.8 が差し替えを拒んだ理由（タグが言う型と中身の乖離）が当たらない

#### 文字列にする

02 の 14.17 は **どの値も `tostring` を持つ** と定めており、ホスト値も外れない。

```c
lhat_register_hostvalue_member(program, "std.math.vector3", "Vector3", "tostring",
                               "f^self^ -> string^;", vec3_tostring, module);
```

**名前は裸の `tostring`** である。ハットが要るのは 14.17改 の素のテーブル
——書き手が自由に名前を足せる唯一の値——だけであり、登録された型の名前は
全部ライブラリのものなので隔てるものが無い。よって2つの綴りは同じメンバを
指し、01 の 5.4 の穴（`tostring^` を尋ねる）にも裸の登録がそのまま届く。

**登録が無ければ組込みが書く。** L^ の中の `tostring^`（穴・`.tostring^()`）
は型の名前を書く——`v.tostring^` の束縛が運ぶのは head（タグ）だけで、
バイト列は手元に無いからである。ホストが `lhat_value_text` /
`lhat_value_write` に**引数（pointer 形）**を渡した場合は、登録フィールドを
バイト列から読んで `module.Name(1.0, 2.0, 3.0)` と内容ごと書く——
ホスト側の値には常にバイト列が付いているので、書けるものは全部書く。
箱も同じ綴りで、種別を挟んで `std.math.vector3.Vector3.ConstBox^(1.0, 2.0, 3.0)`
と書く（封印の別は表示に出る）。

```lhat
$"{v}"            # "<std.math.vector3.Vector3>"    tostring 未登録（L^ 内・タグのみ）
$"{v}"            # "{x:3.0 y:4.0 z:0.0}"    std.math.vector3 が登録したもの
$"{b}"            # "std.math.vector3.Vector3.ConstBox^(1.0, 2.0, 3.0)"  箱は常に内容
```

`<…>` は 14.17 が `c^{ … }` や `f^` に与えている「それが何であるかを示す
短い綴り」と同じ立場である。

**穴は「スタックの外」ではない。** 値を読んで文字列を作るだけで何も保持
しないので、上の一原則にはあたらない。読み手はスタックの上の幅つきの値を
そのまま受け取る（呼び出し規約は上のとおり変わらない）。

#### 8.8 と共有しない規則

借用／所有の軸・`dispose`・10.7 の3契機・「ぶら下がりはホストの責任」は
**全部非適用**である。寿命が無い。GCの対象にならない。ホスト値は
ビット列であり、それ以上ではない。

#### ホスト境界

引数はスタックの head を指す形で渡り、`lhat_hostvalue_data(argument,
tag)` がタグ照合の上でバイト列を返す（`lhat_hostdata_pointer` のバイト版）。
返す側は `lhat_make_hostvalue(machine, tag, bytes, &out)` -- 機械の
スクラッチに head 形の run を組み、呼び出しが返った瞬間に機械が全幅を
スロットへ書き出す。ホストが保持できる形はどこにも無い。

##### 部屋は2つあり、片方だけが根である

02 の 13.8改 の多値も同じ往復をする（`lhat_make_tuple`）。
だが **収集器から見た扱いが違う**。

| | 中身 | 収集器 |
| --- | --- | --- |
| ホスト値のスクラッチ | 生バイト。参照を持たない | 根ではない |
| タプルの部屋 | 普通の値 | **根である** |

ホストは部屋を埋めてから返るまでの間に確保できる——テーブルを作る、
`lhat_machine_call` で L^ を走らせる。ホスト値の側はビット列なので
そこで何が起きても関係ないが、タプルの位置は値であり、
根にしなければ掃かれる。フレームの答えの部屋（03 の 5.3改）が
同じ理由で歩かれているのと同じことである。

##### 逆向きも多値を運ぶ

`LhatRunResult` は位置を持つ。

```c
LhatValue value;              // 今までどおり。タプルなら位置1
const LhatValue *positions;   // 機械の部屋を指す
size_t position_count;        // 単値の答えなら 0
```

`value` の意味を変えていないので、**タプル以前に書かれたホストは
読み替えを要さない**——位置1を読むことになり、それは使える値である。
`positions` は次の実行までの寿命であり、跨がせるならホストが写す。

#### コルーチンとホスト値（8.9改）

ホスト値は **yield^/resume/コルーチンの答えを丸ごと渡る**。1席に1値 --
産出も送りも答えも、その席の全幅で運ばれる（YIELD は幅の札
`LHAT_YIELD_HOSTVALUE`、resume は送りをスクラッチ経由の pointer 形で、
受けは席へ全幅展開）。await^ の委譲も転送する。

残る制限（設計によるもの）:

- **多値の席には混ぜない**。タプルの位置は1スロットであり、ホスト値は
  その幅で乗らない（13.8改 の位置規則そのまま）。`yield^ 1, vec` は拒否
- **ホスト境界の resume も丸ごと渡る**（8.9改2）。受けは pointer 形
  （機械のスクラッチ指し、寿命はタプルの `positions` と同文——次の実行
  まで。跨がせるならホストが写す）、送りは `lhat_make_hostvalue` の
  pointer 形をそのまま。詳細は 8.8 のコルーチン API の節
- **Y|T の合併にホスト値の腕は作れない**（8.9 の合併拒否そのまま）。
  産出と答えの両方に書くなら同じ型を書く -- 合併が畳まれて1本になる

#### v1 の制限

- 可変長引数を持つ署名は、幅つき引数と併用できない
  （収集が値番号でスロットを数えるための拒否）
- 箱のフィールドは**読みだけ直アクセスできる**（`b.x` は `b.get().x`
  の糖衣）。書きは `set()` に集約したまま。演算子の委譲も無い --
  箱は容器であって値の別名ではない
- 16 バイト境界を要求する型（`__m128` 等）は対象外。整列は 8 バイト

### 8.11 program の書込はホストの錠を通せる

> **`lhat_program_set_lock(program, lock, unlock, ctx)`。渡せば、program を
> 書く公開入口と `lhat_program_install` がその錠を取る。渡さなければ
> 従来どおり。**

std.thread はワーカーごとに `lhat_program_install` を呼び、その間ホストは
検査もコンパイルも読み込みも続けられる（エディタの保存、`std.load`、
本体から呼ばれた `spawn`）。それらは**書き**であり、走っているワーカーの
install が歩いている最中のグラフに落ちてはいけない。

- 取るのは公開入口だけ: `check` / `compile` / `load_text*` / `load_file` /
  `write_text` / `install` / `invalidate` / `discard_retired` / `reload`
- **入れ子にしない。** 中で他の入口を呼ぶものは、錠の内側にいる半分
  （`compile_all`・`check_held`・`load_text_held`）を呼ぶ。だからホストの
  錠は再帰でなくてよい（ただの mutex で足りる）
- **走る側は何も要らない。** 機械は proto の上を走り、書きは proto を
  動かさない（5.7 は本体を retire するのであって解放しない）
- 錠は登録と同じく、何かが走る前に置く

これが無いと、`love.filesystem.load` と `spawn` を同時に呼べない、という
運用でしのぐことになる（lhatove の thread-design 4.4）。

### 8.10 継ぎ目は2つある

> **メモリの確保と単位の読み込みは `lhat_*` の公開関数として切り出す。
> 静的リンクなら実装ファイルごと差し替え、共有ライブラリなら登録する。**

宣言は `src/port.h`、既定の実装は `port/` にある。

```c
void *lhat_alloc(size_t size);
void *lhat_calloc(size_t count, size_t size);
void *lhat_realloc(void *pointer, size_t size);
void  lhat_free(void *pointer);

char *lhat_load_file(void *context, const char *path, size_t *length);
```

#### リンカの継ぎ目［主］

`port/alloc.c` をコピーして書き換え、`lhatport` をリンクから外す。
コアは在るほうに解決される。

- **登録するものが無いので、登録し忘れが起きない**
- **間接呼び出しが1つも無い**

FreeRTOS が `heap_1.c` … `heap_5.c` から1つ選ばせるのと同じ形である。

#### 登録の継ぎ目［共有ライブラリのため］

**DLL ではリンカの継ぎ目が届かない。** ホストが見る前にリンクが済んでおり、
既定を抱えたまま出来上がるためである。そこで既定の実装が表を1つ持つ。

```c
LhatAllocator mine = { alloc, calloc, realloc, free, context };
lhat_set_allocator(&mine);
```

払う代償は **確保1回につき間接呼び出し1回**。
リンカの継ぎ目を採ったホストはこれを払わない（表ごと消えるため）。

##### 順序は検査する

登録形が持つ唯一の失敗は「**最初の確保より後に登録する**」である。
リンカの継ぎ目にはこれが無い。

**検査できるので検査する。** 一度でも確保が起きた後の `lhat_set_allocator` は
`false` を返して何もしない。既に確保済みのものを別の `free` に渡すほうが害が大きい。

#### 単位の読み込みには既定を置かない

`lhat_program_init` が **ローダーを受け取る**。既定でファイルを読むことはしない。

```c
lhat_program_init(&program, true, lhat_load_file, NULL);  // ファイルを読む
lhat_program_init(&program, true, NULL, NULL);            // 何も読まない
```

**組み込まれた言語が、言われてもいないのにファイルシステムに触らない**ようにするため。
`NULL` を渡せば `require^` は「読めない」を報告するだけになる。

`port/loader.c` の `lhat_load_file` は、その形をした既定の実装にすぎない。
リンカの継ぎ目で差し替えてもよいし、ホストが自分のものを書いて渡してもよい。

#### ビルドの構成

```text
include/lhat.h  ホストが名指す唯一のヘッダ
src/            言語そのもの        → lhat.lib / lhat.dll
port/           継ぎ目の既定実装    → lhatport.lib / lhatport.dll
cli/            コマンドライン      → lhat.exe
```

**ホストのインクルードパスに載るのは `include/` だけ**とする。
`src/` には `source.h` `value.h` `token.h` のような一般的すぎる名前があり、
他人のインクルードパスに置くものではない。`include/lhat.h` がそこへ届く。

名前は組み込み C の慣例に倣った。FreeRTOS・lwIP・mbedTLS がいずれも
**環境ごとに差し替える層を「port 層」と呼ぶ**。`host` は 8.7 で
「ホストアプリが登録するもの」に、`env` は 8.6 の `L^` に取られている。

`lhat` は `lhatport` に依存する。ホストが自分の実装を持つなら、
`lhatport` をリンクから外して自分のものを置く。

- **M4 — 値の出自を問う機構**

  「この値はどの単位のどの名前から来たか」を問う機能を設けるかは別の判断になる。

- **M8 — 差し替えは program のメモリを増やす一方である**

- **M7 — 公開されたテーブルの可変な範囲**

  自分の単位からは書けて外からは書けない、という形にしたいかどうかは決めていない。
  決めるなら印を二値から「所有する単位」へ広げることになる。困ってはいない。

## 10. バイナリ単位

> **検査・コンパイル済みの単位は、そのままバイト列に書き出せる。ローダが
> そのバイト列を返せば、同じパス・同じ `require^`・同じ
> `lhat_program_check` で、テキストを見ずに同じ単位が立つ。**

目的は **VM のみビルド**——構文解析器と型検査器を外し、事前コンパイル済みだけを
走らせる構成（5 章の余談）の前提を作ること。単位ごとに書き出すので、シーン単位の
部分ロード・破棄はそのまま保たれる。

### 10.1 拡張子は変えない。先頭のバイトが種別を言う

ファイルの先頭 4 バイト（UTF-8 のテキストが始まり得ない 0x89 で始まる magic）が
バイナリであることを言う。ローダは `.lh` のテキストとバイナリを区別せず、
プログラムがバイト列を見て分岐する。だから VM のみビルドへ移してもファイル名は
変わらず、ホストのローダも何も知らなくてよい。

```
lhat --compile main.lh -o out        # 到達した全単位を out に同じ相対配置・同じ名前で
lhat --run out/main.lh               # テキストと同じ道で走る
```

### 10.2 何が名前で渡るか

チャンクが持つものは機械のもの——operand は索引、定数、記述子——であり、
チャンクの外を指すポインタは「名前で見つけ直せるもの」だけである。それらは
名前で書かれ、読む側のプログラムで解決される。

- 他の単位: 自パスからの相対パス（`UNIT` 命令が数える順）
- 登録されたホスト型（8.8）・ホスト値型（8.9）: モジュールと名前。ホスト値型は
  **幅も**書く——フレームがその幅で配置されているので、別の大きさで登録された
  同名の型は別の型である
- 登録されたエラー種（8.7）: モジュール・名前・変種。言語自身の
  `localerror^.CastFailure` は印ひとつ
- 登録された enum（8.7改2）: モジュール・型・名前
- `enum^` の宣言（02 の 19 章）: 宣言した単位のパスと名前。これが `fits^` の
  比べる同一性で、プログラムは (単位, 名前) ごとに一つのトークンを持つ——
  バイナリ単位 B の `x fits^ A.E` は、バイナリ単位 A が作った値に対して真になる

単位自身の `errordef^` 種と記述子は、単位のルート本体のヒープに作り直される。
他の単位の種は定数に現れない（値として実行時に流れる）ので、名前で渡すのは
ホストの種だけである。

### 10.3 テキストとバイナリは混ぜない

**プログラムはテキストかバイナリかのどちらかである。** テキスト単位が
`require^` で辿り着いた単位がバイナリなら、バイナリ単位の `require^` が辿り着いた
単位がテキストなら、どちらも `LHAT_PROGRAM_ERR_MIXED`。判別は常に内容であって
名前ではない。

混ぜないのは、輸出型を運ばないためである。検査器が読む輸出は型検査器の型グラフ
（6.1）であり、それを適合判定に耐える精度で書き出し・読み戻す機構は、この形式の
他の全部を合わせたより重い。混在に明確な用途が無い今、その重さは払わない。
決定は反転可能で、その時に足すのは輸出型の節ひとつである。

同じ理由で、**バイナリ単位の `def^` は他の単位から `..` で合成できない**——合成の
平坦化は相手の構文木を読む（`resolve_unit_body`）。

### 10.4 信頼: 版印とハッシュ、検証器は無い

ヘッダは形式の版・ビルドの指紋（レジスタとタプルの上限、opcode 表、ライブラリの
版）・本文の FNV-1a ハッシュを持つ。どれかが合わないファイルは
`LHAT_PROGRAM_ERR_BAD_BINARY` で拒否される。**それ以上は検査しない。** VM は
コンパイラを信用して operand を検査しない（03 §4.2）ので、改竄されたファイルは
SEGV し得る。読むのは自分が書いたものだけ、という前提である。

このプログラムが同じように登録していない名前（未登録の型・種・enum、幅の違う
ホスト値型）は `LHAT_PROGRAM_ERR_HOST_MISMATCH`。

### 10.5 何が残り、何を落とせるか

- 行表・`source_name`・`debug_name` は**常に残る**。traceback（04 の 11.6改）が
  出荷ビルドでも読む
- ローカル名・捕捉名（09 の 4 章、デバッガが読む）は**落とせる**
  （`--strip-debug`、`lhat_unit_write_binary` の `with_debug_names`）
- `member_cache` の答えなど実行時のスクラッチは書かない

### 10.6 ホストが訊けること

`lhat_unit_export_count / _name / _type / _type_text`（4.5）はバイナリ単位でも
答える——輸出の記述子（`LhatRuntimeType`）は本文と一緒に運ばれる。
`lhat_unit_export_conforms` は検査器の型を要するので、バイナリ単位には
偽を答える。

02 の 18 の反射 API（`lhat_unit_annotation_count / _annotation`・
`lhat_annotation_argument`・`lhat_unit_documentation`・`lhat_unit_member_count /
_member / _member_parameter / _member_written_name_count / _member_written_name`）も
バイナリ単位で答える。テキスト単位が木から読む答え——注釈とその引数、説明文、
定義のメンバとフィールドとそのパラメタ、本体の書かれた名前——を書き出し時に
同じ API で集めてレコードの節に運び、読み手はそれで答える。木は運ばない。
最上位束縛の列は書かれた順、合成 def^ のメンバは左から右。説明文は書き出した
ビルドがコメントを保持していた（`LHAT_WITH_COMMENTS`）ときだけ残る。
節はデバッグ名と違って落とせない——ホストがバイナリだけを配る場面こそ、
これらを訊く場面だから。

書き出しは `lhat_unit_write_binary(unit, with_debug_names, &bytes, &length)`
（program.h）。検査・コンパイル済みの単位から。

### 10.7 署名表——登録のテキストを前段なしで読む

ホスト登録の署名は文字列（`"f^number^ -> number^;"`）で、それを読むのは構文解析器と
型検査器である。前段の無いビルド（10.8）がホストを登録できる道は一つ——
**フルビルドが同じ登録から書いた表を引く**こと。

- `lhat_program_write_signatures(program, &bytes, &length)`: 登録を終えた
  プログラムから、署名テキストごとに1レコード。値は **install がそのエントリに
  作る記述子そのもの**（引数を parts に、受け手と可変長の印を付けた
  `SUBROUTINE`）——解析し直さない。二つ目の文法も解決器も持たない
- `lhat_program_read_signatures(program, bytes, length)`: どのビルドでも読める。
  レコードは自己完結（自分の文字列・外部参照・オブジェクト表）で、**引く時に
  初めてデコード**する——型登録と関数登録が交互に来ても（生成 API はクラスごとに
  そう並ぶ）順序を問わない
- 前段の無いビルドの `lhat_register_func` / `_member` / `_hostvalue_member` /
  `_global` は表を引く。表に無いテキストは `LHAT_PROGRAM_ERR_NO_SIGNATURE`、
  表にあってもこのプログラムが同じに登録していない名前は `HOST_MISMATCH`。
  検査器の hosted 表は作らない（読む者がいない）
- 前段のあるビルドは従来どおりテキストを読み、表を引かない——状態を増やさない
  ための線。起動短縮（表ヒットで解析を飛ばす）は後日の opt-in

CLI: `lhat --dump-signatures FILE` がこのドライバの登録から表を書き、
`lhat --signatures FILE` が登録の前に読む。

### 10.8 VM のみビルド——`LHAT_WITH_FRONTEND`

CMake の `LHAT_WITH_FRONTEND`（既定 ON）を OFF にすると、字句解析器・構文解析器・
構文木・型検査器・コンパイラ・semantic・token をライブラリから外す。残るのは
vm/gc/object/value/code/program/registry/rttype/serialize/debug/source/error/
number と **type.c**（登録が型を作る中核で、前段を一切読まない）。

その構成で:

- 単位はバイナリだけ。テキストに出会えば `LHAT_PROGRAM_ERR_NO_FRONTEND`
- 登録は署名表（10.7）。表なしでは署名付き登録が失敗する
- `std.load` / `std.lton` はバイト列だけ読む: フルビルドが
  `lhat_program_write_text` / `lhatstdlib_lton_write`（CLI は
  `--compile x.lton`）で書いたものを、同じ入口が先頭バイトで見分けて
  前段なしに読む（08 の 7改）。テキストを渡せば「前段なし」で拒む。
  プロンプト・`--tokens`・構文木の出力・LSP・テスト・ベンチマークは無い。
  DAP は式評価だけ「前段なし」を答え、フレームの読みと traceback は動く
- 反射 API（`lhat_unit_annotation*` / `_member*` / `_documentation`）はバイナリ
  単位のレコード（10.6）から答える——木を歩く道が無いだけで、答えは同じ。
  `lhat_unit_export_conforms` は偽、`lhat_unit_write_binary` は偽

プリセット `vmonly`（Ninja Release）。往復は
`lhat --dump-signatures sig.bin` と `lhat --compile main.lh -o out` をフルで、
`lhat --signatures sig.bin --run out/main.lh` を vmonly で。

## 改定履歴（要約）

- **std.task（2026-09-04）: 常駐する機械の群れ。** N 台の機械と OS スレッドを
  立てたままジョブを配る。ジョブは未開始コルーチン（8.8改3）か `p^...` の閉包で、
  run-to-completion。ジョブ内の `await^` はワーカーが駆動する。

- **8.7改（2026-09-04）: std.async の待ちは armed した機械のもの。**
  async.h が最初からそう書いていたのに、表は program ごと1つで「ready なものを1つ」
  が誰のでも持って行っていた（std.thread のワーカーと本体で既に踏む）。
  待ちに機械を刻み、`wait`/`next`/`pending`/`drop` は自分の分だけ見る。

- **8.8改3（2026-09-04）: まだ始まっていないコルーチンが渡る。** 15.5 が

- **15.14改（2026-09-04）: ワーカーの終わりを押して届ける。** `awaitable()`

  ホストのループへ、`lhatstdlib_thread_join_all` が破棄前の待ち。

- **std.channel（2026-09-04）: 機械の間のキュー。** carry の上に載せた

  Channel 自身が共有型なので手渡せる——`demand` で待つワーカーを並べる
  プールが書けるようになった（lhatove の thread-design 4.2）
- **8.8改2（2026-09-04）: ホストデータの共有契約。** carry が「境界の外」に

- **8.7改4 と 8.8改2（2026-08-28）: 境界は個数で答え、歩きは Y と T を
  言い分ける。** 多値は 13.8改 の時点で境界を通っていたのに、
  `LhatHostFn` が `LhatValue` を1つ返す形のままで、**型が嘘をついていた**
  ——多値は別の入口（`lhat_make_tuple`）から渡す形だったので、境界を
  初めて読む書き手には1つしか返せないように見えた。答えを機械の部屋に
  書いて個数を言う形にし、その入口は畳んだ。
  引数側は配列＋個数のまま——13.1 が個数を静的に決めるので、Lua が
  スタックを使う理由が無い。**Lua 風スタック API は速さの理由にも
  ならなかった**: SoA のスタックから `LhatValue` を組み立て直す代金を
  測ったところ、1引数あたり 9.2ns（ホスト側）に対し境界の無い L^
  クロージャが 9.8ns で、差はノイズ以下だった。
  歩きも同じ答え方に揃え、差は返り値だけにした。そこで 13.9 の T
  ——「値を出して終わる」——がホストにも書けるようになる。
  `for^` は resume のあとに別に `ISDONE` を問うので影響しない。
  合わせて `sent` が配列になり、`c.resume(a, b)` の2つ目以降が
  ホストの歩きに届かなかった欠落も塞がった

- **8.8改（2026-08-27）: ホスト型が基底を1つ持てる。** Godot バインドが
  971 クラスを `godot.Object` 1つで扱っていて、境界が型を持てなかった。
  検討した3案のうち、構造的型付けは不可（メンバ0個の不透明型が `t^{}` と
  等しくなり何でも適合する。実行時はタグ同値のままなので検査を通った値が
  NULL を返す＝03 の 4.2 が禁じる形）、L^ 側の委譲だけでも不可（メンバ
  適合が共変なので `gdobj : godot.Node2D` を `godot.Node` の席へ置くには
  結局この関係が要る）。公称のまま単一継承を足すのが、検査器と実行時が
  揃う唯一の案だった。**公称は緩めていない**——宣言が自分の下位関係を
  言えるようになっただけで、ポインタについてのホストの約束（15.13 の
  `closed^` と同種）がその裏付けである。
  継ぐものは2つあり置き場所が違う: メンバは型の表なので**登録が閉じた
  時点**で写し（登録のたびでは間に合わない——「素の型を全部、あとから
  メンバを」の順で登録されるため）、`dispose` はタグに在るので写さず
  鎖を辿る（タグはプロセス共有）。分け損ねると 12.5 がメンバを見て
  `with^` を通し、実行時は何も走らない——誤りにならず黙って壊れるので、
  試験で押さえた。実装中に、手で呼んだ `dispose()` の見分けも同じ所を
  読んでいることが判り（「二度は返さない」）、歩きを1箇所に閉じた。
  `HostData .. def^` で L^ 側に派生型を書く案は採らない——8.8 が
  「`new` はホスト型には載せない」と定めており、14.5 の合成が要求する
  雛形がホスト型に無いので、合成した型を作る手段が無い

- **8.7改5（2026-08-24）: 親と子を同じ場に取り込める／登録型は互いに交わらない。**
  LOVE2D バインドからの2件。(1) `import^ love` と `import^ love.graphics` が
  同じ単位で衝突していた——登録簿は入れ子1つで親が子を含むので、届いて
  いれば何もせず、子だけの仮置きは親のテーブルに置き換える（どちらの順でも
  よい）。(2) 8.8 の公称性を 14.12 の重なり判定にも通し、別の登録型を取る腕
  どうしが並べられるようにした（構造で見て「同じメンバ名がある」と
  重なり扱いになっていた）。あわせて、型の分かっている2つの登録型の `=` は
  「既に決まっている比較」として検査時に報告される

- **8.7改4（2026-08-23）: 登録の記述子は program のヒープに一度だけ。**
  install が機械ごとに署名を下ろし直していたのをやめ、登録時に
  `host_heap`（旧 `host_error_heap` を広げた）へ作って機械には
  ポインタ配列の写しを渡す。「実行時に型を作らない」が単位にもホストにも
  揃った。あわせて登録型（hostdata）は葉1個に下ろす（メンバを展開しない
  ——相互参照5型で600万ノードになっていた、LOVE2D の physics で発覚）

- **8.7改3（2026-08-23）: 自型を答え・取るメンバの登録が終わらなかった。**
  登録署名を機械の記述子へ下ろす program.c の独自歩きが構築中の型を覚えず
  （`translate -> m.T` と `apply(m.T)` で 3^32 歩）、LOVE2D の Transform で
  発覚。rttype.c の `Self^` を立てる歩きに一本化して独自実装を削除。
  あわせて (1) メンバ署名に `Self^` を書ける、(2) 可変長の腕の重なり判定を
  「常に重なる」から機械の探索が分けられる条件そのものに

- **4.5（2026-08-23）: 公開した名前の型はホストから読める。**
  `lhat_unit_export_count/_name/_type/_conforms`。LOVE2D バインドの
  「update の型違いを起動時に弾きたい」に対し、検査器の exports 表を
  そのまま C に見せた（従来の `lhat_unit_member` は木の粗い読みで、
  def^ のメンバ向け）

- **8.7改2（2026-08-22）: ホストは `panic^` を書ける。** `lhat_machine_panic`
  /`_panic_text`。LOVE2D バインドで「プログラマの誤りを `|love.Error` の
  戻り値にすると毎回 `catch^` が要って成立せず、未宣言の誤り値や nil^ を
  返すと次の使用で TYPE_ERROR になり文が消える」と指摘されたもの。8.7改 の
  「戻ったらフレームが増えていた」と同じ検査に載せ、3経路を1本に
  寄せた——ホスト値の演算子経路には入れ子 fault の検査も無かったので
  一緒に塞いだ

- **5.6（2026-08-22）: 実行時の読み込み `std.load`（M3 解決）。** check →
  compile → machine 確定後に単位を足す経路が C API 上も無く（compile は
  一度きりで、後から check した単位は index 0 のまま別の単位を走らせて
  いた）、LOVE2D バインドの指摘で発覚。機械の単位配列をやめて **単位表を
  proto に持たせ**（UNIT 命令は自分の単位の表を引く）、compile を増分に
  した上で、`std.load.file/text` を置いた。答えは `p^... -> any^;|Error`、
  module^ 単位なら public^ の表を登録簿に入れず答える。本体は機械の
  ヒープのもの（`LhatLoadedScript`）で閉包と共に回収、carry は拒む。
  `L^.load` でなく stdlib に置いた理由は 5.6 末尾

- **3.2改（2026-08-22）: スクリプトの最上位は `p^...`。** `module^` の無い
  単位の最上位に `...`（`t^{any^[]}`）を束縛し、走らせたもの（CLI の
  コマンドライン引数・`require^` の空表・`std.load` の閉包の呼び出し）が
  その中身を決める。`lhat_run` は `lhat_run_arguments(…, NULL, 0)` に。
  `module^` 単位は従来どおり引数を取らない

- **8.8改（2026-08-22）: 機械の間を運ぶ共通部品 `stdlib/carry`。**
  std.thread の境界は nil^/bool^/number^/string^ の4つしか運べず、
  テーブルも閉包も拒んでいた（LOVE2D バインドからの指摘）。値を機械に
  属さない木にほどいて向こうで組み直す `lhat_carry`/`lhat_uncarry` に
  置き換え、テーブル（循環込み）と閉包（proto 共有＋捕捉のスナップ
  ショット、共有セルは共有のまま）が渡るようになった。spawn の fn は
  `closed^p^...` から `p^...` へ。同一機械の閉包 clone は作らない——
  同じセルを共有する複製は元と区別がつかず、スナップショットする複製は
  欲しい場面が無い（Lua の `string.dump` も upvalue を捨てる）

- **8.7改（2026-08-22）: 入れ子の呼び出しの fault はホストを素通りしない。**
  ホスト関数の中の lhat_machine_call が fault してもホストは値しか返せず、
  外側の走行が死んだフレームの上を走り続けていた。機械が栓をする — ホスト
  から戻ってフレームが増えていたら、外側を同じ fault（panic の値ごと）で
  終える。std.regex の gsub（同一機械への呼び戻しの初出）で発覚

- **8.9改（2026-08-20）: ホスト値は合併に立てる。** 一原則「スタックの外
  に出られない」の症例一覧に合併が並んでいたが、**誤りだった**——
  `Vector3|nil^` はスタックの外に出ない。詰まっていたのは幅（席が
  1スロットしか予約されない）だけで、判別は最初から可能だった（頭
  スロットのタグが `HOSTVALUE` と `NIL` で別物、`fits^` は合併越しに
  ホスト値の腕を見られる）。立てる条件は 13.8改 がタプルに与えたものと
  同じ family——`nil^` と誤り。`any^`・幅のある腕どうし・判別する構文の
  無い腕は `LHAT_CHECK_ERR_HOSTVALUE_UNION` で拒む。
  発端は `print(a?.get())` が検査を通って実行時に落ちた件（ユーザー報告）
  ——逃走検査17箇所が「その型がホスト値か」を kind で訊いており、`?.` が
  作った合併がすり抜けていた。17箇所すべて**幅**の規則だったので合併越し
  に見るよう改め、可変長の席の拒否がその場で出るようになった。
  あわせてホスト呼び出しの答えの経路を直した——予約が run か幅かを
  「1スロットの答えが判別できる腕か」で見分ける（従来は幅の予約に
  `TUPLE_ARITY` を返していた）

- **std.debug.traceback（2026-08-20）**: 04 の 11.6改 のトレースバックを
  L^ から `f^ -> string^;` で。読むだけで観測可能な変化を残さないので
  log と同じく f^。std.thread の join は worker の fault に worker 側で
  描いたトレースバックを message へ連結して返すようになった

- **8.8改・8.9改（2026-08-20）: ホスト製の値の可用性を引き上げた。**
  LOVE2D バインドの弱参照要求を掘ると同根の欠落が3つあった
  （yield がホスト値を運べない・Box^ もホストデータもキーとして
  ポインタ同一性でしか引けない）ため、弱値キャッシュより先にこちらを
  実装した（弱値キャッシュは churn 最適化に格下げして保留）。
  (1) hostdata の `=` は**タグ+実体ポインタ**（released 後は自分のみ、
  `is^` はラッパ同一性のまま）—— fresh-wrapper のまま同一オブジェクトの
  `==` とキーが成立し、Lua の弱値レジストリが担っていた同一性が等値側で
  立つ。(2) Box^ の `=` は**内容**、`is^` は同一性（文字列と同じ分担）。
  **ConstBox^**（`constbox^`、get 専用の封印箱・常にコピー）を導入し、
  キーとして**記録**できる箱は封印済みだけ（書き位置の静的 MUTABLE_KEY +
  実行時 BAD_KEY の二段。可変箱を記録すると set() でエントリが行方不明に
  なるため。可変長の席 `...` への裸のホスト値も同根で拒否 —— 収集先の
  テーブルにも host の erased な席にも幅が乗らない。`print(v)` は
  `print(box^v)` か登録 tostring の穴で書く。組込みの値書き出しは
  内容付きに: 箱は `Name.ConstBox^(値…)`、ホスト側 API の pointer 形は
  `Name(値…)`）。**引きは Box^ でも裸のホスト値でもよい**（照合はその瞬間の
  内容、表の中は全部封印済み。裸値の引きは専用の読み口
  lhat_table_get_by_value が箱と同じ内容ハッシュで照合する）。裸の
  ホスト値の**記録**は静的に拒否（従来は検査を抜けて「絶対ヒットしない
  エントリ」になる穴だった）。
  conforms は Box^→ConstBox^ の一方向。箱のフィールドは
  読みのみ直アクセス可に。(3) yield^/resume/答えはホスト値を**丸ごと**
  運ぶ（席の全幅。多値の席には混ぜない。ホスト境界の resume は同日中に
  開通——8.9改2、受けはスクラッチ指しの pointer 形で positions と同じ
  寿命契約、送りは R のタグ照合つき）。「コルーチン境界値不可」「yield
  本体と幅つき引数併用不可」の
  v1 制限を削除。書かれた c^ 型の3席へのホスト値一括拒否も撤去し、
  登録署名は記述として通して**消費地点で拒む**方針に統一（登録失敗は
  「メンバが無い」にしか見えず読者に何も伝えないため）

- **`public^` が型注釈を要求する規則を撤回した（4.3）。**
  公開分だけ引数の注釈を求めても、公開された `def^` のメンバや `self^` の
  データメンバは推論のままであり、「本体を1行足すと公開している型が変わる」は

  つもりの性質が守れていなかった。穴の開いた型が単位の外へ出ないことは、
  03 の 3.1③ が単位ぜんたいに課すほうで担保する。
  署名を本体から切り離したい書き手は、いままでどおり束縛に書ける
- **単位を書き換えたときの規定を置いた（5.7）。** ひとつの program に多くの
  単位を載せ、機械はスレッドの数だけ持つ形を組み込み先に望むが、単位ごとに
  program を分けるとホストの登録が program ごとになり、7.3 の同一性で同じ
  綴りの型が別物になってしまう。無効化は要求する側へ推移的に及び、古い本体は
  解放せず退役させる——古い世界と新しい世界がそれぞれ無矛盾なまま並ぶ。
  解放の時機はホストが決める。あわせて、単位の読み込みが一度きりなのは
  単位自身の前置きのガードによる（5.3）という事実から、機械の登録簿から
  外す口が要ることを明記した。これを呼ばなければ新しい本体は走らない

  あわせて型アリーナを2本に割った——単位を検査して作られたものと、登録が

  一方通行だからで、登録の署名が `require^` の持ち込みを名指せないという

  積む」だけに縮んだ

  後始末待ちは回すループが無いので次に L^ が走るまで待つこと
- **ホストの回収が後始末まで走らせるようにした（8.6・5.7）。** godot バインドの
  指摘。`L^.collectgarbage()` は元から `finally^` を走らせており、走らせて
  いなかったのは C の口だけだった——対等性の取り違えである。走らせないと、
  落ちたコルーチンが中断先の閉包を握ったまま `pending_disposals` が数えられず、
  `discard_retired` の前提をホストが確かめようがなかった。数える口も足した。
  後始末が fault した場合は見捨てて枠ごと畳む（枠を残すのが他所の規則だが、
  ここで残すと「待ちは無い」と答えながら枠が本体を指し続ける）。
  あわせて **`discard_retired` が解放するのは符号だけ**であることを明記した
  ——chunk のオブジェクトはあらゆる機械より長生きする前提で born black に
  なっており、`L^.modules` は単位の前置きが読み込む文字列で鍵付けされている。
  本体を捨てて定数まで解放すると、機械のテーブルの鍵がぶら下がる
- **`context` の始末に口を置いた（8.7）。** `lhat_program_on_dispose`。
  登録する関数が `bool` しか返さない形——標準ライブラリのモジュールがそうで、
  この program の誤り種別とタグをまとめた構造体を `context` に載せている
  ——では、確保したものの handle が呼び手に渡らず、**ホストには解放する術が
  無かった**。計数アロケータで測って 5 ブロック / 112 バイトが program ごとに
  漏れていた（tests/test_leak.c）。ポインタをホストがまだ持っている場合は
  自分で捨てればよく、この口は要らない。
- **「全単位の差し替え」を取り下げた（5.7）。** 差し替えは型も定数も解放
  できないので、全部やると**捨てて作り直すより多くを残す**。プロジェクトを
  読み直すなら program と機械を作り直すのが正しく、それで 7.3 の同一性の
  問題も起きない（program がひとつなら起きない）。単位ひとつの差し替えは
  live edit のために残る。あわせて、そのために割っていた型アリーナの2本立ても
  取り下げた——用が無くなった
- **ホストの登録の同一性を process にひとつにした（8.7・7.3）。**
  同一性が宣言なら、宣言とは何かを決めなければならない——答えは**それを行う
  C の呼び出し**であり、同じ呼び出しを2つの program に対して行っても宣言は
  ひとつである。program ごとにタグを作っていたのは実装の都合で、その結果
  「同じ綴りの型が2つあり、決め手になるただ一つのこと以外は全部一致する」
  という状態を作っていた。単位ごとに program を分けた組み込み先が踏んだのは
  これで、5.7 の一連の作業はその症状への手当てだった。
  食い違う宣言（別の大きさ・別の変種の一覧・別の `dispose^`）は拒む。
  同一性は process の寿命で、`lhat_registry_dispose` がまとめて返す。
  副産物として標準ライブラリのモジュール構造体の多くが静的になった
