# 05 名前空間とモジュール

名前をまとめて別の単位から取り込む仕組みを定める。

節番号のうち「01 の」「02 の」「03 の」「04 の」と前置きしたものは他文書を指す。
未決事項には `M` を冠して 9 章にまとめる。

---

## 1. 動機

発端は誤りの種別名の衝突である。
`errordef^` の種別名が標準ライブラリと利用者のコードで衝突する。

だが **これは誤りに限った問題ではない**。
`def^` を束縛した名前も、手続きの名前も同じように衝突する。
種別を入れ子にしても、衝突する場所が1つ減るだけで解決しない。

01 の 8 章のスコープ指定子（`$` `$^`）は
**入れ子のスコープを指すもの** であり、名前空間ではない。
`$` がファイルスコープを指すので単位の概念は字句の段階で先取りされているが、
単位をまたいで名前を渡す手段が別に要る。

---

## 2. 名前の環境はひとつ［重要］

### 2.1 なぜひとつでなければならないか

02 の 14.9 は **「定義の右辺に `def^` が直接現れる場合、その名前を型の名前として採る」**
と定めている。値の場と型の場が分かれていると、この決定と食い違う。

```lhat
let^ Foo = def^{ self^{ v = 1 } }
let^ x : Foo = Foo.new()          # Foo は値としても型としても引ける必要がある
```

### 2.2 ひとつにする

> **名前の場はひとつである。ひとつの名前は値・型・その両方のいずれかを指す。**

| 宣言 | 指すもの |
| --- | --- |
| `let^ x = 1` | 値 |
| `let^ Foo = def^{ … }` | 値（定義そのもの）と型（そのインスタンス） |
| `errordef^ E { … }` | 型のみ |

同じ場にあるので、`errordef^ E` の後の `let^ E = 1` は
02 の 8.7 の再定義として誤りになる。**衝突が見えるようになる。**

#### 場が同じでも、型の位置に書けるとは限らない

上の表のとおり `let^ x = 1` が指すのは **値だけ** である。
「その値の型」を名前で指す機能は、本節も 02 の 13 章も定めていない。

```lhat
let^ x = 1
let^ y : x = 2      # 誤り。x は型を指さない
```

とはいえ「定義と `errordef^` だけを型とする」まで狭めると、
実際には型として書かれているものが落ちる。

- **定義が自分自身を指す場合** — `def^` の中からその束縛名を書くと、
  その時点で束縛の型はまだ定義に定まっていない
- **ホストが登録した型**（8.8）と **`require^` が答える単位のメンバ**（6.1）

そこで線は **構造を持たない値** に引く。

- **拒む** — `number^` `string^` `bool^` `nil^`、サブルーチン、コルーチン。
  問える構造がなく、型として書ける意味がない
- **通す** — テーブルであるもの。02 の 11.3 が同一性を構造で決めるので、
  定義・ホスト型・単位・手で書いたテーブルのいずれも
  「その形を持つか」を問う対象になる

`self^` と `class^` は別に拒む（02 の 13.1）。前者は構造を持つ値であり、
後者は定義そのものなので、この線では止まらない。

#### 定義名を型として書くとインスタンスを指す

02 の 14.7 が「注釈に定義名を書くと **そのインスタンスが持つものすべて** を
要求する」と述べている。持つのは雛形の欄と受け手を取るメンバであり、
`new` と静的メンバは定義のものである。

```lhat
let^ x : Foo = Foo.new()
```

`Foo` は値としては **定義**、型としては **そのインスタンス** を意味する。
14.7 の記述をそのまま読んだ結果であり、新しい規則ではない。
定義そのものを注釈に書きたい場合は、14.10 の `self^{ … }` の区画を持つ形を書く。

## 3. 単位は `module^` を宣言する

```lhat
module^ namespace1.module1
```

- **1つのファイルに1回まで。** 2回目は誤り
- ファイルの先頭に置く
- 名前は `.` で区切れる
- **ファイルの置き場所から独立している**

### 3.1 パスから独立させる理由

ファイルの位置は都合で動く。型の名前が位置に縛られていると、
**ファイルを移すだけで診断の文言と型のラベルが変わる**。

宣言された名前は 7 章で型のラベルになり、5.3 で登録の鍵になる。
どちらもファイルの位置とは無関係であってほしい。

`module^` が名乗ったパスは **検査の結果に残る**。5.5 の省略形が
それを読んで束縛先を決めるためである。7.1 のラベルもここから採る。

### 3.2 省略できる

`module^` のないファイルも読み込める。その場合、型のラベルには解決したパスを使う。

主となるスクリプトに単位名は要らない。
`require^` される側は付けるのが望ましい、という関係になる。

## 4. `public^` が公開を決める

```lhat
module^ namespace1.module1

public^ errordef^ Error {
    SomeError,
    FatalError,
}

let^ privateValue = 0

public^ let^ publicProc = p^ { print(privateValue) }
```

- **既定は非公開。** `public^` を付けたものだけが外から見える
- 付けられるのは単位の最上位の宣言（`let^`、`errordef^`）に限る。
  `public^ var^` は認めない（4.4）
- 公開された名前が `require^` の返すテーブルのメンバになる

### 4.1 末尾の `return` を書かせない［重要］

Lua の `require` は、モジュールがファイルの末尾でテーブルを `return` する約束で成り立つ。
**これは踏襲しない。**

理由は書き味だけではない。

> **`return <式>` は実行しなければ何が公開されるか分からない。**

返る値は実行時に組み立てられうるので、**単位を実行せずに公開分を知ることができない**。
6 章が型検査に依存を辿らせる以上、これは成立しない。

`public^` は宣言ごとの印なので、**構文解析だけで公開分が決まる**。
6 章の静的な取り込みと、`return` を書かせないことは互いを支えている。

書き忘れの事故が消えるのは副次的な利得である。
Lua では `return` を忘れても読み込みは成功し、使う場所で初めて `nil` になる。

### 4.2 公開されるのは名前であって定義ではない

`public^` は **その名前を外から見えるようにする** だけである。
非公開の名前を公開された手続きが使うことは妨げない。上の `privateValue` がそれにあたる。

### 4.3 公開する引数は明示を要する

03 の 3.4 は、注釈のない引数の型を本体の要求から推論する。**公開されるものはその対象から外す。**

> **`public^` の付いた宣言の中に書かれた `p^`・`f^` は、引数の型を明示しなければならない。**

```lhat
public^ let^ add = p^ x:number^, y:number^ { return^ x + y }   # 明示が要る

let^ helper = p^ x { return^ x + 1 }                           # 通る。非公開
```

#### 束縛に書いてもよい

求めているのは「本体から読まないこと」なので、
**署名を束縛の側に書いても満たされる**（03 の 3.4改）。
そこから引数の型が流れるので、引数の位置に書き直す必要はない。

```lhat
public^ let^ add : p^number^, number^ -> number^; = p^ x, y { return^ x + y }
```

#### 本体が署名を決めてはならない

公開された名前の署名は、他の単位が書かれる相手である。
推論に任せると **本体を1行足しただけで公開している署名が変わりうる**。
利用側は自分の単位を1文字も変えていないのに壊れる。

TypeScript が `noImplicitAny` で引数だけを推論の外に置いているのも同じ理由である。
難しいからではない。

#### 6 章の取り込みが軽くなる［重要］

より強い理由がこちらにある。**取り込む側は、相手の本体を検査せずに署名を読める。**

4.1 が `return` を書かせないことで「単位を実行せずに公開分が分かる」を得た。
これはその署名版である。

> 4.1 — **何が公開されるか** は構文解析だけで決まる
> 4.3 — **公開されたものの型** は本体を読まずに決まる

引数まで推論すると、6.2 の順序は他単位の本体の検査を待つことになる。
返り値型の推論だけでも既に本体は要るが、それは 6.3 の循環検査が支える一方向の依存に収まる。
引数は呼び出し側から逆算しない（03 の 3.4）以上、ここで切っておけば逆向きの依存が生まれない。

#### 中に書かれたものは一律に含める

範囲は **`public^` の宣言の中に構文的に現れる `p^`・`f^` のすべて** とする。
外に出るものだけに絞らない。

```lhat
public^ let^ make = p^ {
    let^ step = p^ x { return^ x + 1 }   # 誤り。public^ の中は一律に要る
    return^ step
}
```

`step` は返り値型の推論を通って `make` の署名に現れる。
だが **返すのか、渡すのか、閉じ込めるのかは構文からは区別できない**。
区別を持ち込むと、4.1 が守っている「構文解析だけで決まる」が崩れる。一律にする。

過剰に見える場合は `public^` を外すか、注釈を書く。どちらも1行である。

#### relaxed でも要る

03 の 3.5 が緩めるのは「推論が決められなかった箇所」であり、これは **書き手が書かなかった箇所** である。
公開する署名は、相手の単位がどちらの厳格度で書かれていても読まれる。
4.1 の一方向の保証は、単位の境界で型が確定していることに乗っている。

### 4.4 公開する束縛は `let^` である

`public^ var^` は認めない。

```lhat
public^ let^ answer = 42     # よい
public^ var^ answer = 42     # 誤り
```

**理由**: 01 の 8.3 は「グローバル変数は持たない」と定めている。
`public^ var^` は **他の単位から見える名前が、その単位の与り知らぬところで
変わる** ものであり、綴りを替えたグローバル変数にほかならない。
8.1 の「取り込まないものは何も見えない」を守っても、
取り込んだものが黙って変わるなら同じ問題が戻ってくる。

4.1 と 4.3 が並べた一方向の保証にもう1行が加わる。

> 4.1 — **何が公開されるか** は構文解析だけで決まる
> 4.3 — **公開されたものの型** は本体を読まずに決まる
> 4.4 — **公開された名前が何を指すか** は取り込んだ後で変わらない

単位の状態を動かしたければ、状態は非公開の `var^` に置き、
`public^ let^` の `p^` を通す。**何が変えるのかが単位の中に閉じる。**

```lhat
var^ count = 0                        # 非公開
public^ let^ bump = p^ { count := count + 1 }
public^ let^ current = f^ -> number^ { return^ count }
```

これは 9 章の M7（機械の印を「所有単位だけが書ける」へ広げるか）とは
別の話である。M7 が問うているのは **テーブルのメンバ** を誰が書けるかで、
本節が言っているのは **名前** を誰が書けるかである（02 の 8.9）。

## 5. `require^`

```lhat
let^ m = require^ "lib/module1.lt"

m.publicProc()
var^ e : m.Error = …
```

### 5.1 パスで指す

引数は **要求する側からの相対パス** である。単位名では指さない。

単位名で指すと **名前からファイルを見つける探索路の仕様が別に要る**。
どこを探すか、複数見つかったらどうするかを決めなければならない。
パスで指せばその問いが生じない。

`module^` の名前は 7 章のラベルと 5.3 の鍵として働く。**指し方とは役割が違う。**

### 5.2 引数はリテラルでなければならない

6 章が型検査に依存を辿らせるため、**パスは構文解析の時点で決まっている必要がある**。
計算された文字列は受け付けない。

実行時に決まる読み込みは別の機構になる（M3）。

### 5.3 一度だけ読み込まれる

同じ単位を2度 `require^` しても、**同じテーブルが返る**。
単位の本体が2度走ることはない。

登録の鍵は `module^` の名前、宣言がなければ解決したパスである。
登録簿は実行時のものであり（8.6）、綴りは標準ライブラリの設計に属する（M2）。

### 5.4 取り込みは名前を撒かない［重要］

`require^` が束縛するのは **1つの名前だけ** であり、それは取り込む側が選ぶ。
単位の中の名前が呼び出し側の場に流れ込むことはない。

1 章の衝突は、これで起きなくなる。
同じ名前の単位を2つ取り込んでも、束縛する名前を分ければ済む。

```lhat
let^ theirs = require^ "vendor/geometry.lt"
let^ ours   = require^ "src/geometry.lt"
```

名前をまとめて現在の場へ流し込む形（`use^` のようなもの）は設けない。
それを入れると衝突が戻ってくる。

### 5.5 省略形は単位が名乗ったパスに束縛する

> **`let^` `var^` を書かずに `require^ "path"` と書ける。
> そのとき単位は、自分が `module^` で名乗ったパスの下に入る。**

```lhat
require^ "lib/m1.lh"        # module^ namespace1.module1
require^ "lib/m2.lh"        # module^ namespace1.module2

namespace1.module1.publicProc()
let^ n : number^ = namespace1.module2.answer
```

#### 5.4 の何が変わり、何が変わらないか

- **「名前を撒かない」は保たれる。** 導入されるのは **根1つ**（`namespace1`）だけで、
  単位の中の名前は `namespace1.module1.` の下に留まる。`use^` 相当ではない
- **「取り込む側が選ぶ」が緩む。** 省略形では単位の側が選ぶ

5.4 が恐れた衝突は戻らない。`module^` のパスは名前空間であり、
同じ完全パスを2つの提供元が名乗ったなら、それは提供元の側の過失である。
`let^` `var^` で名前を選ぶ形はそのまま残るので、逃げ道もある。

```lhat
let^ theirs = require^ "vendor/geometry.lt"    # 従来どおり選べる
require^ "src/geometry.lt"                      # 名乗ったパスに入る
```

#### 接頭辞は合流する

02 の 8.8 がそのまま効く。**2つ目が1つ目を潰さない。**

同じパスを2つの単位が名乗れば、8.8 の末尾の規則により再定義の誤りになる。
同じ単位を2度書いた場合も同じで、5.3 が一度しか読み込まないこととは別に、
**書いた側の重複**として報告される。

#### `module^` の無い単位には使えない

3.2 は `module^` の省略を許している。名乗っていない単位には
束縛すべきパスが無いので、省略形は誤りとする。`let^` または `var^` で名前を選ぶ。

```text
この単位は module^ を宣言していないため、束縛するパスがありません。
'let^ name = require^ ...' と書いてください。
```

#### 文であって式ではない

省略形は **文** とする。02 の 8.2 の「裸の式は文にしない」を
崩さないためである。値としての `require^` は従来どおり式のまま。

## 6. 型検査は依存を辿る

### 6.1 静的に辿る

`require^ "…"` に出会った型検査器は、**その単位を先に処理して型を得る**。
返るテーブルの型は、公開された名前とその型からなる構造である。

```lhat
let^ g = require^ "lib/geometry.lt"
let^ p : g.Point = g.Point.new()
g.dist(p, "text")                    # 型の誤りとして報告される
```

`g.Point` が型として書けるのは、04 の 12.4 が
**修飾された名前を型として書ける** ことを既に定めているためである。
誤りの種別のために作った形が、そのまま単位のメンバに効く。

### 6.2 処理の順序

03 の 1.1 の段階構成に、単位の依存順が加わる。

```text
単位の依存関係を辿る → 依存の順に（字句 → 構文木 → 型検査）→ コード生成
```

依存の側が先に型検査を終えていなければ、要求する側の型検査が行えない。

### 6.3 循環は誤り

単位の依存に循環があれば誤りとする。

許して「これまでに公開された分だけ見える」とする案（Lua、Python）は採らない。
**何が見えるかが読み込みの順序に依存する。**
同じソースが、どちらを先に読んだかで通ったり通らなかったりする。

02 の 8.7 が単位の中の相互再帰を解いているのは
「スコープ全体で見える」という規則が順序に依存しないからであり、
単位をまたいでその性質を保つには循環を持ち込まないほうが早い。

Go が同じ判断をしている。共通部分は第3の単位に出す。

## 7. 型の名前

### 7.1 単位名が型のラベルになる

`module^` を宣言した単位の中で作られた型は、**その名前で修飾されたラベル** を持つ。

```lhat
# lib/module1.lt
module^ namespace1.module1
public^ let^ Point = def^{ self^{ x = 0, y = 0 } }
```

```lhat
let^ m = require^ "lib/module1.lt"
let^ p = m.Point.new()
print(typeof^(p))          # namespace1.module1.Point
```

**ラベルは `require^` を束縛したローカルの名前と無関係である。**
`m` を何と名付けても、`typeof^` の答えは変わらない。

### 7.2 ラベルであって同一性ではない［重要］

02 の 11.3 と 14.9 は変わらない。

> 名前は表示と診断のためのラベルにすぎない。型の同一性は構造で決まる。

したがって **別の単位の同じ形の `Point` は同じ型である**。
単位の境界は型の互換性を分けない。

多くの言語ではモジュールが公称の分離を作るが、L^ では作らない。
14.9 が「名前を同一性に含めると公称型付けになる」と述べたとおりである。

### 7.3 誤りの種別だけは同一性

04 の 2.4 の例外はそのまま効く。種別の同一性は宣言の場所であり、
**別の単位で宣言された同名の種別は別の型である**。

```lhat
# それぞれの単位で errordef^ Error { SomeError }
theirs.Error.SomeError     # 別の型
ours.Error.SomeError
```

表示上の衝突は名前空間（本章）が解き、
取り違えのほうは 04 の 2.4 が最初から防いでいる。

### 7.4 `typeof^` が返すのは型である

```lhat
print(typeof^(m.publicProc).signature)
```

`publicProc` は手続きの **値** であり、その型は署名である。
出力は `p^;` にあたる形になる。`namespace1.module1.publicProc` にはならない。

`typeof^(m.publicProc)` 自身（`.signature` を付けない場合）は
値そのものを直接印字する手立てを持たない（02 の 14.16）。

02 の 14.10 が「`.signature` の出力はそのまま型注釈として解析できる」と定めており、
`namespace1.module1.publicProc` は型注釈ではない。

単位名で修飾された名前が現れるのは **型そのものがラベルを持つ場合** である。
`def^` が作った型（7.1）と誤りの種別（7.3）がそれにあたる。

値の出自を問う機能が要るなら、それは `typeof^` とは別のリフレクション機構になる（M4）。

## 8. 無指定で見える名前

### 8.1 何も見えない

> **`require^` を書かなければ、名前はひとつも見えない。**

言語が名前を配ることはしない。標準ライブラリも例外ではない。

```lhat
let^ io = require^ "system/io.lh"
let^ f = io.File.open("path/to")
```

短く書きたければ、取り込む側が自分で名前を付ける。

```lhat
let^ open = io.File.open
let^ f = open("path/to")
```

5.4 のとおり `require^` は名前を撒かないので、
**どの名前が現在の場にあるかは、その場に書かれた `let^` または `var^` を読めば分かる**。
無指定の名前があると、この性質が崩れる。

`L^`（8.6）はこの性質を崩さない。**それは名前ではない**。
01 の 2.2 のハット識別子であり、`let^` `var^` が作れる綴りと交わらない。

### 8.2 初期束縛はホストの設定

修飾なしの `print("message")` が成り立つのは、`print` が言語に属するからではない。

> **ランタイムの生成時に、ホストが初期束縛を与える。**

既定では次のようなものが暗黙に実行された状態から始まる、という形になる。

```lhat
let^ print = require^ "system/debug.lh".print
```

**都合が悪ければホストは与えなければよい。** 既定はあくまで既定である。

これは 02 の 1.2 と 4 章が既に採っている形と同じである。
入力形式の選択も断片の与え方もホストの責務であり、
ランタイムはモードを状態として持たない。初期束縛もそこに並ぶ。

#### 束縛は `L^` のメンバを指す

8.3 が「型はホストが C 側で書く」と定めるので、初期束縛もそこに合わせる。
ホストは **`L^` に置いたものへ名前を結ぶ**。

```c
lhat_register_global(&program, "print", "f^string^ -> nil^;", host_print, NULL);
lhat_bind_initial(&program, "print", "L^.print");
lhat_bind_initial(&program, "collectgarbage", "L^.collectgarbage");
```

```lhat
print("hello")           # 修飾は要らない
collectgarbage()         # 8.6 が L^ に置いているものも同じ形で結べる
```

##### 8.1 は崩れない［重要］

8.1 が守っているのは **「言語が名前を配らない」** ことである。配るのはホストであり、
何も結ばないホストの下では名前は1つも見えない。そこは変わらない。

裸の名前は **どのスコープにも無いときだけ** 引かれる。
したがって同じ綴りの `var^` が普通に遮蔽する。

```lhat
let^ collectgarbage = p^ {
    print("start garbage collection")
    L^.collectgarbage()      # 元のものはいつでも届く
}
collectgarbage()             # 自分で書いたほう
```

`L^` で元に届くのは 8.1 の最後がそのまま効いているためである。
**ハット識別子は `let^` `var^` が作れる綴りと交わらない。**

##### 実行時には何も増えない

裸の名前は `L^.<メンバ>` の読み出しに落ちる。
グローバルな変数の仕組みを持ち込まない。

結ばれていない名前は今までどおり「そんな名前はない」になる。

### 8.3 ホストは型を書いて登録する

初期束縛の名前が何の型かを、検査器は知らなければならない
（6 章が型検査に依存を辿らせるため）。その手段は
「ソースとして読む」ではなく、**ホストが型を書いて渡す**（8.7）。

```c
lhat_register_func(&program, "system.io", "print", "p^string^;", print_fn, NULL);
```

`"p^string^;"` は 02 の 13 章の型の文法そのままであり、検査器はそれを読む。

こちらのほうが小さい。**宣言と実装が離れない** ためである。
ソース側に宣言を置く形では、`.lh` の宣言と C の実装が食い違いうるので、
突き合わせる段が要る。両方を C 側に置けば食い違いようがない。

したがって 02 の 2.3 のコマンド形式で `ls` が使えるかどうかは、
**ホストがそれを登録したかどうか** で決まる。言語の側に約束はない。

### 8.4 構文である語は取り込まない

`require^` は名前ではなく **構文** である。したがって取り込む必要がない。
`try^`（04 の 5 章）や `pack^`（02 の 13.8改）と同じ位置づけになる。

`typeof^` も同様に構文とする。

`typeof^` は **検査器の静的な型には頼れない**。03 の 4.2 が「厳格度が変えるのは
診断の時期だけで、実行時の意味は変わらない」と定めており、検査結果は検査が
終わると同時に捨てられる（03 の 4.3 とは別に、検査とコンパイルは独立した2つの
パスである）。`typeof^` の答えが検査器の推論に頼ると、非厳格モードで答えが
変わってしまう。したがって `typeof^` は **実行時に値の実際の形を走査して** 答える
（14.7 の「その定義を返す」がそのままリフレクションの設計になる）。

それでも構文として取り込まないのは、次の理由による。

- 常に `typeof^(式)` と丸括弧を伴い、演算子としての優先順位を持たない
  一次式であり、通常の手続き呼び出しとは形が違う
- 7.1 の単位名のラベルは `def^` が作った型と誤りの種別に乗るが、
  `typeof^` 自身の答え（14.16 の「型情報」）は別の一様な型であり、
  単位をまたいで取り込む対象にならない

### 8.5 コルーチンの操作は言語に属する

> **コルーチンの `start`、`resume`、`dispose`、`iterate`、`done`、`started` は
> 取り込まずに使える。標準ライブラリの一部ではない。**

8.1 の「何も見えない」に対する例外ではない。
これらは **語彙ではなく値のメンバ** であり、
コルーチンを手に入れた時点で、そのコルーチンが持っている。

#### 言語コアから切り離せない

「ライブラリの顔をさせる」形は事実に反する。

- **02 の 13.9 が反復子をコルーチンと定めている。**
  02 の 16.3 の `for^ … in^` はコルーチンなしに成り立たない。
  切り離せば `in^` が消え、**ビルドの選択肢ではなく別の言語** になる
- **型の側も絡んでいる。** `c^{ … }` は合併と適合の判定に載っている
- **実行時の機構は共有物である。** 03 の 5.7 がコルーチンを1フレームの保存と定めたため、
  フレーム、後始末の待ち行列（03 の 5.5）、`p^` の呼び出し規約のいずれもが、
  コルーチンの有無にかかわらず必要なものになっている。
  **コルーチン専用の重い機構が存在しない**

実測でも同じ結論になる。実行ファイル約 100 KB、ソース 13,618 行に対し、
コルーチンに帰せる行は 400〜500 行（3〜4%）。
実行時のメモリはコルーチン1つあたり 328 バイトと、その本体のレジスタ分であり、
**使わなければ発生しない**。静的に確保している機械の側で減るのは 3.2 KB / 197 KB である。

削る効果が大きいのは別の場所にある（値スタックの大きさ、フレーム数の上限、
そして構文解析器と型検査器を外して事前コンパイル済みバイトコードだけを走らせる構成）。

#### Lua が標準ライブラリに置いている理由［参考］

Lua の `coroutine.*` がライブラリなのは、L^ に当てはまらない事情による。

- **yieldable を印していない**（02 の 15.6）。
  どの関数からでも `yield` できるため、関数を呼ばずに渡す `coroutine.create` が要る
- **C API との対称性。** `lua_newthread` / `lua_resume` / `lua_yield` が先にあり、
  Lua 側の `coroutine` はその薄い包みである。ライブラリにすれば実装が1つで済む
- Lua は方針としてコアを小さく保ち、`string` や `table` も含めてライブラリに寄せている

L^ は 15.2 の推論を持ち、C API との対称性を先に決めてもいない。同じ形を採る理由がない。

### 8.6 `L^` — 機械そのもののテーブル

> **`L^` は取り込まずに使えるテーブルであり、言語の実行環境そのものを指す。**

8.1 の「何も見えない」に反しない。**`L^` は名前ではない。**
01 の 2.2 のハット識別子であり、`let^` `var^` が作れる綴りと交わらないため、
「その場にある名前は書かれた `let^` `var^` を読めば分かる」という性質は保たれる。
`this^`（02 の 15.10）と同じ位置づけである。

#### 何を載せるか

載せるのは **プログラムが自分では用意できないもの** に限る。
便利な道具は標準ライブラリに属し、8.1 のとおり `require^` で取り込む。

```lhat
L^.collectgarbage()      # GCを手で走らせる
L^.modules               # 登録簿
```

`collectgarbage` は `p^;` である。効果であって値を作らないので `f^` ではない。

ホストは 8.2 のとおり、ここへ自分のものを足せる。
足せるのは同じ理由に適うものだけである — **プログラムが自分では用意できないもの**。

出力はその境目にある。02 の 10.6 が「デバッグ用のログ出力などの脱法関数」を
`f^` の制約の唯一の例外として挙げており、`print` はその実例にあたる。
**変わるのはホスト側の状態であって、機械の側ではない。**
プログラムから読み返せるものは何も動かないので、`f^` として置ける。
13.2 が返り値を求めるので `f^string^ -> nil^;` になる。

#### `L^.modules` は登録簿である

5.3 は「同じ単位は一度しか読み込まない」と定めた。**その登録簿がこれにあたる**。

単位は `module^` が宣言したパスの下に入る。
02 の 8.8 がテーブルの途中の段を作るので、登録は **02 の 8.8 の形で表せる**。

```lhat
let^ L^.modules.namespace1.module1 = ...
```

接頭辞を共有する単位は **合流する**。8.8 が2つ目に1つ目を潰させない。

```lhat
let^ L^.modules.ns1.mod1 = ...
let^ L^.modules.ns1.mod2 = ...   # ns1 は両方を持つ
```

同じパスを別の単位が名乗れば、8.8 の末尾の規則により再定義の誤りになる。

##### ただし書き手はこれを書けない

上の行は **処理系が出すものの説明** であって、そのままコンパイルできる L^ ではない。
`L^` は機械のものである以上、
**登録簿にメンバを足すことも、そこにあるものを差し替えることも、L^ の側からはできない。**

```lhat
let^ L^.modules.ns1.mod1 = { }   # 誤り
L^.collectgarbage := p^ { }      # 誤り
```

読むことは妨げない。`L^.modules` を辿って何が読み込まれているかを見るのは通る。

##### 登録するのは単位自身である

`require^` の側が登録するのではない。**単位が自分の先頭と末尾で行う。**

```lhat
# module^ ns.m1 と書かれた単位が、これと同じものになる
if^ L^.modules.ns.m1 { return^ L^.modules.ns.m1 }   # 番人
… 本体 …
let^ module = { <public^ の名前をすべて> }
let^ L^.modules.ns.m1 = module
return^ module
```

置き場所が要である。`require^` の側に置くと、要求元ごとに書かれることになり、
**一度しか走らないことの根拠が呼ぶ側に散る**。単位の側に置けば根拠は1箇所で、
どこから何度要求されても本体は最初の1回しか走らない。

番人は書かれた L^ としては通らない。`L^.modules.ns.m1` は
まだ型に無いメンバだからである。生成される命令列としては成立する —
04 の 11.3 が「無いキーは `nil^`」と定めており、読み出しは失敗しない。
**脱糖は説明であって、そのままコンパイルできる L^ ではない。**

##### 型の側も同じことを言う

`require^` は単位を走らせ、走れば必ず登録される。したがって
**検査器の `L^.modules` の型にも同じ登録を行う**。これがなければ
登録簿は L^ から書けるだけで読めない。

```lhat
require^ "one.lh"                  # module^ ns.one
return^ L^.modules.ns.one.v        # 読める
```

嘘にならないのは、登録が **単位自身の前置き** にあるためである。
呼ぶ側が省略できる位置にあれば「型が実体を先回りする」ことになるが、
そうなっていない。同じ単位を2度要求しても 5.3 が一度しか走らせないので、
型の側の登録も冪等とする（8.7 の衝突にはしない）。

#### 機械が持ち、機械が根にする

`L^` は機械とともに作られ、**どのフレームにも属さない**。
ガベージコレクションの根は機械の側にあり、登録された単位は集められない。

#### 型は検査の側にもう1つある

実行時の表と別に、検査器が同じ形の型を持つ。
セッション（03 の 4.3）では入力をまたいで保たれるので、
ある入力が登録した単位は次の入力からも見える。

**2つの一覧が同じことを言っている必要がある。** 片方だけに足すと食い違う。

食い違いを作れるのは **この2箇所を書く側だけ** である。
スクリプトの側からは作れない。

- `var^ L^.x = v` は検査器の型と実行時の表を**同時に**増やす。片方だけは起きない
- `var^ L^.modules = …` は 02 の 8.7 の再定義の誤りになる
- `L^.modules := …` は実行時の中身を入れ替えるが、
  検査器が持つ型のオブジェクトは変わらないので、型の食い違いにはならない

#### 機械のテーブルは L^ から書けない

> **`L^`、その登録簿、そして `require^`／`import^` が答えるテーブルは、
> ホストが自分の API で書く。L^ の側からは書けない。**

- **差し替え** — `L^.collectgarbage := …`、`m.name := …`
- **追加** — `var^ L^.modules.ns.m = …`、`var^ m.name = …`

読むことは妨げない。

##### 記法は要らない［重要］

書き手が可変性を指定する必要がないので、**綴りを1つも足さない**。
型に印が1つあり、機械が作るテーブルにそれを立てるだけである。

ホスト側の許可は自動で成り立つ。検査器が見るのは L^ のソースだけであり、
**ホストは 8.7・8.8 の C の API を通るので検査器を通らない**。
したがって「L^ に書かれたものを一律に拒む」がそのまま規則になり、
ホスト用の抜け道を作る必要がない。

##### 検査だけでは足りない

検査器が捕まえられるのは **名前で書かれたもの** だけである。
一度引数を通せば抜ける。

```lhat
let^ poke = p^ x:t^{ v:number^ } { x.v := 99 }
let^ m = require^ "lib"
poke(m)                # x の型は t^{ … }。印を持たない
```

受け手側に印を書く綴りがない以上、**型の適合では止められない**。
止めようとすると、機械のテーブルをどの手続きにも渡せなくなる。

そこで **実行時にも同じ問いを置く**。テーブルに印を持たせ、
書き込みの命令がそれを見て拒む。

ホスト側はここでも自動的に自由である。
ホストは 8.7・8.8 の C の API でテーブルに触るので、**命令を通らない**。
検査器のときと同じ構造がそのまま成り立つ。

02 の 15.1改 が `f^` の側から塞いでいる経路とも重なる。
`f^` の中からは静的に、`p^` と最上位からは実行時に止まる。

##### 中身には伝播させない

印が立つのは **そのテーブル自身** だけである。
公開された名前が持つテーブルは、持たれていたときと同じだけ書ける。

```lhat
let^ m = require^ "lib"
m.registry := { }      # 誤り。モジュールのテーブルは機械のもの
m.registry.x := 1      # 通る。公開されたテーブルの中身は別の話
```

4.2 が「公開されるのは名前であって定義ではない」と定めている。
その名前が持つものをどこまで書けるかは、**まだ決めていない**（M7）。
伝播させるとここで決めてしまうことになる。

##### 2つの軸が重なる

02 の 15.1改 が `f^` の側から同じ場所を守っている。両者は別の軸である。

- **どこから書けるか**（15.1改）— 式の由来。静的にしか意味を持たない
- **誰が書けるか**（この規則）— 値に付く。ホストと L^ の境目を引く

`f^` の中からの書き込みは 15.1改 が止め、`p^` と最上位からのものをこの規則が止める。

### 8.7 ホストの登録と `import^`

> **ホストは C 側で型を書いて自分の機能を登録し、
> スクリプトは `import^` でそれを自分の場に導入する。**

#### 登録

```c
lhat_program_init(&program, true);

lhat_register_type(&program, "system.gfx", "Texture");
lhat_register_member(&program, "system.gfx", "Texture",
                     "width", "f^ -> number^;", width_fn, ctx);
lhat_register_func(&program, "system.gfx", "load",
                   "f^string^ -> system.gfx.Texture;", load_fn, ctx);

lhat_program_check(&program, "main.lh");     # 登録はこれより前
```

モジュールは最初の登録で暗黙に作られる。
**すべて型検査より前**でなければならない。検査器が型を知る必要があるためである。

#### シグネチャは 13 章 の型の文法である

文字列は型としてそのまま解析される。14.10 が
「`typeof^(x).signature` の出力はそのまま型注釈として解析できる」と定めているので、
この入口は元々必要なものである。

名前として書けるのは **組み込み型と、それより前に登録されたホスト型** だけである。
`require^` が持ち込む単位の型は書けない — 書けると
**単位が検査される順序に答えが左右される**。

互いを参照する型は、**先に型だけを2つ登録してから**メンバを足す。
C のヘッダにおける前方宣言と同じ形になる。

#### 同じ名前を何度でも登録できる［確定］

**同じ名前への2度目の登録は、置き換えではなく腕の追加である。**
02 の 14.12 の `overload^` を書いたのと同じものになり、
呼び出し側は両者を区別しない。

```c
lhat_register_hostvalue_member(p, "m", "C", "-", "f^self^ -> number^;", neg, tag);
lhat_register_hostvalue_member(p, "m", "C", "-", "f^self^, number^ -> number^;", sub, tag);
lhat_register_hostvalue_member(p, "m", "C", "+", "f^number^, self^ -> number^;", radd, tag);
```

02 の 11.3改 の末尾 `self^` も書ける。上の3つ目は
**受け手が右の被演算子**であり、`1 + v` がこれを見つける。

14.12 の「重なるシグネチャは書けない」は **登録の時点で効く** —
既にある腕のどれかと同じ呼び出しを受け取りうるものは、
`lhat_register_*` が偽を返す。L^ 側では検査が言うことを、
ホスト側では登録が言う。

C 関数は登録した個数ちょうどで呼ばれる。
どの腕が選ばれたかは `count` と受け取った値で分かる。

##### 実行時の選択は登録した署名から作られる

L^ で書いた多重定義は、コンパイラが本体から候補の型を作る。
ホスト関数には本体が無いので、**登録が受け取った署名から同じものを作る**。
だから選択の精度は L^ 側と変わらない —
個数でも、位置ごとの型でも、受け手がどちら側かでも分かれる。

#### 登録された型は公称である

`lhat_register_type` が作るのは 7.3 と同じ **宣言の場所が同一性** の型である。
11.3 の構造的型付けの例外にあたる。詳細は 8.8。

02 の 8.8 の印も立てるので、`var^ t.x = …` でメンバを後から足せない。

#### C 関数の形

```c
typedef LhatValue (*LhatHostFn)(LhatMachine *machine, void *context,
                                const LhatValue *arguments, size_t count);
```

- **引数は配列で渡す。** 13.1 が個数も型も走る前に決めているので、
  動的な言語が境界で行う数え上げがここには無い。Lua のスタック API に相当するものが要らない
- **誤りは値で返す。** 04 と 12.8 のとおりなので、
  巻き戻しの手配も `pcall` に相当するものも要らない
- **`context`** は登録時に渡した生ポインタ。ホストの持ち物であり、
  ガベージコレクションからは見えない

##### 多値も答えられる

署名に `-> (A, B)` と書けば、C 関数は複数の値を答えられる（02 の 13.8改）。

```c
LhatValue out[2] = { q, r };
LhatValue answer;
lhat_make_tuple(machine, out, 2, &answer);
return answer;
```

**`LhatHostFn` の綴りは変わらない。** 8.9 のホスト値と同じ往復であり、
値は機械の部屋に置かれ、呼び出しが返った瞬間に機械が全幅をスロットへ書き出す。
既存のホスト関数は1行も変わらない——run 以外を返す限り、今までの経路を通る。

登録が `-> (A, B)` と言い、C 関数が1つしか答えなければ、**機械が落とす**。
両者は別々に翻訳されうるので、食い違いは実行時にしか判らない。

`op^` は1値のままである。11.8 の形に複数の余地が無い。

#### `import^`

```lhat
import^ system.io                 # system.io をこの場に導入する
let^ m = import^ some.module      # 名前を選んで導入する
```

`require^` との違いは **何を指すか** である。
`require^` はファイルパス、`import^` はモジュールパス。

導入の仕方は 5.5 と同じで、02 の 8.8 が途中のテーブルを作る。
接頭辞を共有するモジュールは合流する。

#### `import^` が届くのはホストの登録簿だけ［重要］

> **`require^` で読み込まれた単位は、`import^` では導入できない。誤りとする。**

`require^` された単位も `L^.modules` に入るので、
そこを見に行けば `import^` でも届いてしまう。**そうしない。**

理由は順序である。`import^ ns.m` が通るかどうかが
「先に検査された単位が `ns.m` を `require^` していたか」で決まると、
**同じソースが、要求元の並び順で通ったり通らなかったりする**。

ホストの登録簿だけを見るなら、登録は検査より前に全部済んでいるので、
`import^` の成否は **ホストが何を登録したか だけの関数** になる。

診断はそれを言い分ける。`L^.modules` に見えているのに拒まれる形になるためである。

```text
import^ はホストが登録したものに届きます。その名前のモジュールはありません。
ファイルから読み込む単位は require^ "path" で入ります。
```

#### 実行時

登録されたものは、走る前に機械の `L^.modules` へ入る
（`lhat_program_install`）。したがって `import^` の生成は
**`L^.modules` を辿るだけ**であり、専用の命令を持たない。

##### `import^` の名前は入れ子の本体で捕捉されない［重要］

> **`import^` が束縛した名前を入れ子の本体が書いたとき、
> それは捕捉ではなく、走っている機械の `L^.modules` を辿り直す。**

登録は **機械ごとの値** である。C 関数そのものはどの機械でも同じでも、
それを包む値はその機械のヒープの上に作られる。捕捉は「作った機械の物」を
運ぶことなので、**別の機械で本体を走らせる形**——ホストが機械を1つ増やして
そこで閉包を走らせる場合——では捕捉した登録は使えない。

辿り直せば、その本体は **自分が走っている機械の登録** に当たる。
同じ機械の中では今までと同じものを指す（`import^` 自身がその歩きで
束縛している）ので、見える値は変わらない。

`require^` の根はこれに含めない。単位の値は走らせて作ったものであり、
辿って読み直せるものではない。入れ子の本体からは今までどおり捕捉される。

したがって **02 の 15.13 の `closed^` を書いた本体でも、`import^` した名前は
書ける**。捕捉が起きていないので、約束は破れていない。

### 8.8 ホストのデータ

> **ホストが作ったものは、L^ がポインタとして持つ。中身は覗かない。**

#### 他の言語の形［参考］

骨格はどれも同じで、**インタプリタがヘッダを持ち、ホストがペイロードを持ち、
終わりにコールバックでペイロードを返す**。分かれるのは誰が確保するかである。

- **埋め込み** — Lua の full userdata、Wren の foreign class。
  インタプリタのヒープ内にバイト列を確保し、ホストがそこに構築する。
  C++ では placement new が要る
- **ポインタ** — Ruby の `Data_Wrap_Struct`、V8 の `External`。
  ホストが確保し、インタプリタはポインタと解放関数を持つ。**C++ には素直**

L^ は **ポインタ側**を採る。12.5 の `dispose()` が既に寿命の記法を持っており、
12.6 の明示的破棄と 10.7 のガベージコレクションによる回収という二段構えは、
素の finalizer より強い（実行時期の確定する手段がある）。

#### `LhatValue` は広げない［重要］

ポインタは **値ではなくオブジェクトに載る**。
値の表現（03 の 2.2 の SoA 分離）はスタック・テーブル・退避の全部が
同じ1枠の形を前提にしており、ここに手を入れることはしない。
（8.9 のホスト値は枠を**広げず**に連続スロットを使う別の答えであり、
この規則の例外ではない。）

したがってホストが `LhatValue` を自分で組み立てることはない。
**機械が作る。** 生のポインタには `LhatObject` のヘッダが無く、
機械のヒープに繋がっていないのでガベージコレクションから見えないためでもある。

```c
bool  lhat_machine_make_hostdata(LhatMachine *, const LhatHostDataTag *, void *ptr,
                             LhatValue *out);
void *lhat_hostdata_pointer(LhatValue value, const LhatHostDataTag *tag);
```

#### タグが同一性である

`lhat_register_hostdata_type` が返すタグは、**登録ごとに1つ**であり、
比較は同一性だけで行う。`lhat_hostdata_pointer` はタグが違えば `NULL` を返す。

型の側も同じく公称とする。**11.3 が譲るのはここだけである。**

理由は 7.3 より強い。不透明なホスト型には **比較すべき構造が無い**ので、
構造で同一視すればホスト型はすべて同じ型になる。
渡し違えれば C 側が生ポインタを別の型として読む。**メモリ破壊になる。**

したがって検査と実行時の二重で守る。

- **検査** — `store.Held` を求める位置に `store.Other` は書けない
- **実行時** — `lhat_hostdata_pointer` のタグ照合。relaxed（03 の 3.1）で抜けても止まる

#### 登録したものは書き換えられない

ホスト型が持つのは **ホストが登録したもの** である。
`length` は `foo_length` という C 関数であり、生ポインタをタグの型として読む。

```lhat
p.length := f^self^ -> number^ { return^ 0 }   # 誤り
var^ p.other := 1                              # 誤り
```

- **メンバの追加** — 02 の 8.8 の印が既に拒む。ホスト型は登録の時点で形が固定される
- **メンバの差し替え** — 上と同じ理由で拒む。
  差し替えを許すと、タグは `Foo` と言い続けるのに中身が別のものを指す

上の「渡し違えれば C 側が生ポインタを別の型として読む」がそのまま当てはまる。
**不透明であることが、そのまま書けない理由になる。**
テーブルの可変性をモジュール単位で決める機構（M7）を待つ必要はない。

02 の 14.16 の型情報も同じ扱いとする。公称であり、何を持つかは作った側が決めている。

`def^` のインスタンスは公称ではないので、この規則の対象外である。
14 章のフィールドを書き換えるのは、フィールドの用途そのものである。

##### 応答できるようにするなら2つ要る［提案］

ホスト型が将来メンバへの代入に応答するようになった場合、
**上の一律の禁止を外すだけでは足りない**。

```lhat
let^ shared = shapes.makeFoo(3, 4)

let^ f = f^ n:number^ -> shapes.Foo {
    shared.x := n                    # 不正のまま。呼び出し側のもの（02 の 15.1改）
    let^ mine = shapes.makeFoo(0, 0)
    mine.x := n                      # これを通したい
    return^ mine
}
```

要るのは次の2つで、**対にして入れる**。片方だけでは `mine.x := n` が通らない。

1. **この節の禁止を、ホストが可変と登録したメンバに限る。**
   何が書けるかを決めるのは登録した側であり、公称であること自体ではなくなる
2. **02 の 15.1改 の「本体が作った」に、構築関数の呼び出しを加える。**
   `makeFoo` は 8.7 の普通の関数なので、いまは「作った」に数えられない

2 は 15.1改 が置いた `fresh^` の印にあたる。ホスト側は 8.7 の登録に
その印を持たせればよく、`lhat_register_func` に渡す署名の側の話になる。
**C の中は見えないので確かめず、申告を信じる。**
このファイルが既にホストへ課している約束（借用のぶら下がり、解放関数の制限）と同じ立場である。

#### 構築は普通の関数である

`new`（14 章）は `def^` のための機構であり、ホスト型には載せない。
Lua の `io.open` と同じく、モジュールの関数が作る。記法を増やさずに済む。

```lhat
import^ shapes
let^ p = shapes.makeFoo(3, 4)
let^ n : number^ = p.length()
p.dispose()
```

```c
foo_tag = lhat_register_hostdata_type(&program, "shapes", "Foo");
lhat_register_member(&program, "shapes", "Foo", "length",
                     "f^self^ -> number^;", foo_length, NULL);
lhat_register_member(&program, "shapes", "Foo", "dispose",
                     "p^self^;", foo_dispose, NULL);
lhat_register_func(&program, "shapes", "makeFoo",
                   "f^number^, number^ -> shapes.Foo;", foo_make, NULL);
```

`self^` は 13.4 のとおり引数の一覧に入らない。
受け取り手はホスト関数の `arguments[0]` に来る。

#### 借用と所有は `dispose` の有無で決まる

新しい軸を作らない。**12.5 がテーブルに対して行っている判定をそのまま使う。**

- `dispose : p^self^;` を登録した → **所有**。`with^` に渡せ、12.6 の破棄が効く
- 登録しない → **借用**。走るものが無い。寿命はホストのもの

#### 借用のぶら下がりはホストの責任

ホストが先に解放したポインタを L^ が持ち続ける場合を、言語側では守らない。
light userdata と同じ立場である。守るなら所有側（`dispose` を登録する）を使う。

#### 返す口は値が持つ

**解放関数はタグに載せる。値から辿れる場所に置く。**

メンバのテーブルから `dispose` を引く形は採らない。
**掃除は順不同**であり、値を回収する時点でそのテーブルが
既に解放済みでありうるためである。

タグは登録簿のものなので、**どの機械よりも長生きする**。値が持つのは
「もう返したか」の印だけでよい。

#### 返るのは3つの契機

10.7 の二段構えがそのまま効く。

- **手で `dispose()` を呼ぶ** — 実行時期が確定する
- **到達不能になり、GCが回収する** — 掃除の中で返す
- **機械が破棄される** — 残っているものをすべて返す

**二度は返さない。** 10.7 の「すでに実行済みのものは破棄時に再実行されない」を
そのまま適用する。手で呼んだ `dispose()` は機械が見分けて印を立てる。

`dispose` を登録していない型（借用）では、どの契機でも何も走らない。

#### 解放関数は L^ の API を呼んではならない

掃除の途中で呼ばれるためである。その時点でヒープは半分掃かれており、
そこへ値を作りに行くことはできない。

**ポインタを解放する以外のことをする理由が無い**ので、制約として明記するに留め、
Lua や Python のように解放を別のフェーズへ回す機構は設けない。
コルーチンの `finally^`（10.7）は L^ のコードなので事情が違うが、
そちらが要求するまで待つ。

### 8.9 ホストの値

> **ホストは参照だけでなく値も定義できる。8.8 のホストデータが「ホストが
> 持ち、L^ がポインタで指す」ものだったのに対し、ホスト値は「機械が
> バイト列ごとスタックに置く」ものである。Lua の light/full userdata の
> 「誰が確保するか」の軸を、L^ は **値／参照** の軸として切り直す。**

第一の動機は数学型である。Godot の `Vector3` に相当する書き心地 --
`let^ to = a + b` の一時値がヒープ確保ゼロでスタック上を流れること --
を、ホストが登録した型で実現する。

#### スタック表現

03 の 2.2 が payload とタグを並走配列に分けたので、連続する payload
スロットは**素で連続したバイト列**である。ホスト値はそこに置かれる。

```text
slot i   : payload = LhatHostValueTag*   tag = HOSTVALUE   … head
slot i+1 : payload = 生バイト            tag = CONT
…
幅 = 1 + ceil(size / 8)     例: f32×3 の LVector3(12B) → 3 スロット
```

head が自己記述する（タグから型と幅が引ける）ので、一括コピー・退避・
GCの走査は幅を知らずに正しく動く -- CONT はオブジェクトではない
ので走査は素通りし、コピーはスロットを盲写しするだけでよい。

登録は `lhat_register_hostvalue_type(program, module, name, size)`。
メンバ（演算子・メソッド）は `lhat_register_hostvalue_member`、
フィールドは `lhat_register_hostvalue_field(…, offset, kind)` で申告し、
`v.x` はホスト呼び出しなしにバイト列を直に読み書きする。

#### スタックの外に出られない［重要］

> **ホスト値はスタックのスロット以外のどこにも住めない。**

テーブルの要素・捕捉（上位値）・`any^` や合併への昇格・`...`・def^ の
フィールド・yield^ が運ぶ値・セッション最上位の束縛・プログラムの答え --
これらは全部この一原則の症例として検査器が拒む
（`LHAT_CHECK_ERR_HOSTVALUE_ESCAPES`）。**relaxed でも拒む**：実行時検査は
表現に無い場所を作れないからである（03 の 3.5 の例外）。コンパイラも
同じ拒否を持ち、検査なしのコンパイルの背止めになる。

保持したければ**箱に入れる**。箱はライブラリの仕事であり、言語機構では
ない -- std.math は `Vector3`（8.8 のホストデータ）を箱として提供し、
`get()` が unboxing、`set()` が boxing である。何かを保持することが
綴りとして見えるのは意図であって不便ではない。

#### 検査と幅

ホスト値の型と幅は**常に静的に既知**である。`any^` に広がれないので、
値の出所は登録された関数の返り値かホスト値演算に限られ、どちらも署名が
型を言う。検査器は式の型がホスト値だったとき、そのノードに
`checked_type` を印す（03 の 5.11a と同じ経路）-- 型盲目のコンパイラは
この印から幅を読み、レジスタ確保と移動（MOVE の連発）を幅つきで行う。

呼び出し規約は変えない。引数は呼び先の窓に幅つきで並び、呼び先は同じ
幅で引き取る -- 窓の重なりはそのままである。返り値だけが手術点で、
1 スロットの `answer` に載らないため、フレーム自身が持つ部屋
（`answer_run`）を経由して drain（finally^）を生き延び、pop が呼び元の
スロットへ全幅書き出す。

#### 等値は既定でバイト列

ホスト値には同一性が無い。それが値であることの半分である。
**何も書かれていなければ** `=` は **タグの同一 ＋ バイト列の一致**であり、
head だけ比べて「同型なら等しい」と誤答する道は塞いである。
作られるたびに末尾バイトはゼロ埋めされるので、スロット丸ごとの比較で足りる。

**これは既定であって、動かせない規則ではない。**
02 の 11.9 はホスト値にもそのまま当てはまる — **`op^=` を登録した型では
`=` と `≠` がそれを読み、`op^<=>` を登録した型では順序も等価もそれが答える**。
探す順は 11.9改 のとおり `op^=`・`op^<=>`・既定の3段であり、
バイト列の一致は最後の段——「何も書かれていないとき何を答えるか」を
定めているだけで、書かれたものを覆さない。

テーブルとの違いは既定の側だけである。テーブルは 14.2 の参照同一性から
値の等価に変わり、ホスト値は**バイト列の一致から型が定める等価に変わる**。
浮動小数を持つ型が `-0.0` と `0.0` を等しいとしたい、といった場合がこれにあたる。
順序を持たない型なら `op^=` だけを登録すればよい。

```c
lhat_register_hostvalue_member(program, "std.math", "LVector3", "<=>",
                               "f^self^, o:LVector3 -> number^;",
                               lvec3_compare, module);

lhat_register_hostvalue_member(program, "m", "Handle", "=",
                               "f^self^, o:Handle -> bool^;",
                               handle_equal, module);
```

`is^` は別である。11.9 のとおり**同一性は順序とも等価とも別の問い**であり、
ホスト値の同一性はバイト列そのものだから、`op^=` や `op^<=>` があっても
変わらない。

順序（`<` など）も 11.9 に従う。`op^<=>` を登録していないホスト値を
順序で比べようとすれば、11.9 が言うとおり**検査時の誤り**になる。

#### 8.8 と共有する規則

- **タグが同一性**（7.3 の例外の再適用）。同じ形の2つのホスト値型は別の型
  である。取り違えれば C がバイト列を別の型として読む
- **検査＋実行時の二重**。relaxed で静的検査を抜けても、head のタグ照合が
  実行時に止める
- **登録時に形が固定**。メンバの追加・差し替えは不可。ただし
  **フィールドへの代入は許す** -- 中身がポインタでなくバイト列なので、
  8.8 が差し替えを拒んだ理由（タグが言う型と中身の乖離）が当たらない

#### 文字列にする

02 の 14.17 は **どの値も `tostring` を持つ** と定めており、ホスト値も外れない。

```c
lhat_register_hostvalue_member(program, "std.math", "LVector3", "tostring",
                               "f^self^ -> string^;", lvec3_tostring, module);
```

**名前は裸の `tostring`** である。ハットが要るのは 14.17改 の素のテーブル
——書き手が自由に名前を足せる唯一の値——だけであり、登録された型の名前は
全部ライブラリのものなので隔てるものが無い。よって2つの綴りは同じメンバを
指し、01 の 5.4 の穴（`tostring^` を尋ねる）にも裸の登録がそのまま届く。

**登録が無ければ組込みが型の名前を書く。**

```lhat
$"{v}"            # "<std.math.LVector3>"    tostring 未登録
$"{v}"            # "{x:3.0 y:4.0 z:0.0}"    std.math が登録したもの
```

`<…>` は 14.17 が `c^{ … }` や `f^` に与えている「それが何であるかを示す
短い綴り」と同じ立場である。ホスト値のバイト列は意味がライブラリの側にあり、
処理系が書けるのは型の名前までだからである。

**穴は「スタックの外」ではない。** 値を読んで文字列を作るだけで何も保持
しないので、上の一原則にはあたらない。読み手はスタックの上の幅つきの値を
そのまま受け取る（呼び出し規約は上のとおり変わらない）。

#### 8.8 と共有しない規則

借用／所有の軸・`dispose`・10.7 の3契機・「ぶら下がりはホストの責任」は
**全部非適用**である。寿命が無い。GCの対象にならない。ホスト値は
ビット列であり、それ以上ではない。

#### ホスト境界

引数はスタックの head を指す形で渡り、`lhat_hostvalue_data(argument,
tag)` がタグ照合の上でバイト列を返す（`lhat_hostdata_pointer` のバイト版）。
返す側は `lhat_make_hostvalue(machine, tag, bytes, &out)` -- 機械の
スクラッチに head 形の run を組み、呼び出しが返った瞬間に機械が全幅を
スロットへ書き出す。ホストが保持できる形はどこにも無い。

##### 部屋は2つあり、片方だけが根である

02 の 13.8改 の多値も同じ往復をする（`lhat_make_tuple`）。
だが **収集器から見た扱いが違う**。

| | 中身 | 収集器 |
| --- | --- | --- |
| ホスト値のスクラッチ | 生バイト。参照を持たない | 根ではない |
| タプルの部屋 | 普通の値 | **根である** |

ホストは部屋を埋めてから返るまでの間に確保できる——テーブルを作る、
`lhat_machine_call` で L^ を走らせる。ホスト値の側はビット列なので
そこで何が起きても関係ないが、タプルの位置は値であり、
根にしなければ掃かれる。フレームの答えの部屋（03 の 5.3改）が
同じ理由で歩かれているのと同じことである。

##### 逆向きも多値を運ぶ

`LhatRunResult` は位置を持つ。

```c
LhatValue value;              // 今までどおり。タプルなら位置1
const LhatValue *positions;   // 機械の部屋を指す
size_t position_count;        // 単値の答えなら 0
```

`value` の意味を変えていないので、**タプル以前に書かれたホストは
読み替えを要さない**——位置1を読むことになり、それは使える値である。
`positions` は次の実行までの寿命であり、跨がせるならホストが写す。

#### v1 の制限

- 可変長引数を持つ署名・yield する本体は、幅つき引数と併用できない
  （値番号でスロットを数える2箇所を守るための拒否）
- コルーチン境界の値（yield/receive/produce/答え）は不可。**本体内の
  ローカルは可** -- 退避と復帰はスロットの盲写しなので安全である
- 単項 `-` は未対応（`v * -1` か登録メソッドで書く）
- 16 バイト境界を要求する型（`__m128` 等）は対象外。整列は 8 バイト

### 8.10 継ぎ目は2つある

> **メモリの確保と単位の読み込みは `lhat_*` の公開関数として切り出す。
> 静的リンクなら実装ファイルごと差し替え、共有ライブラリなら登録する。**

宣言は `src/port.h`、既定の実装は `port/` にある。

```c
void *lhat_alloc(size_t size);
void *lhat_calloc(size_t count, size_t size);
void *lhat_realloc(void *pointer, size_t size);
void  lhat_free(void *pointer);

char *lhat_load_file(void *context, const char *path, size_t *length);
```

#### リンカの継ぎ目［主］

`port/alloc.c` をコピーして書き換え、`lhatport` をリンクから外す。
コアは在るほうに解決される。

- **登録するものが無いので、登録し忘れが起きない**
- **間接呼び出しが1つも無い**

FreeRTOS が `heap_1.c` … `heap_5.c` から1つ選ばせるのと同じ形である。

#### 登録の継ぎ目［共有ライブラリのため］

**DLL ではリンカの継ぎ目が届かない。** ホストが見る前にリンクが済んでおり、
既定を抱えたまま出来上がるためである。そこで既定の実装が表を1つ持つ。

```c
LhatAllocator mine = { alloc, calloc, realloc, free, context };
lhat_set_allocator(&mine);
```

払う代償は **確保1回につき間接呼び出し1回**。
リンカの継ぎ目を採ったホストはこれを払わない（表ごと消えるため）。

##### 順序は検査する

登録形が持つ唯一の失敗は「**最初の確保より後に登録する**」である。
リンカの継ぎ目にはこれが無い。

**検査できるので検査する。** 一度でも確保が起きた後の `lhat_set_allocator` は
`false` を返して何もしない。既に確保済みのものを別の `free` に渡すほうが害が大きい。

#### 単位の読み込みには既定を置かない

`lhat_program_init` が **ローダーを受け取る**。既定でファイルを読むことはしない。

```c
lhat_program_init(&program, true, lhat_load_file, NULL);  // ファイルを読む
lhat_program_init(&program, true, NULL, NULL);            // 何も読まない
```

**組み込まれた言語が、言われてもいないのにファイルシステムに触らない**ようにするため。
`NULL` を渡せば `require^` は「読めない」を報告するだけになる。

`port/loader.c` の `lhat_load_file` は、その形をした既定の実装にすぎない。
リンカの継ぎ目で差し替えてもよいし、ホストが自分のものを書いて渡してもよい。

#### ビルドの構成

```text
include/lhat.h  ホストが名指す唯一のヘッダ
src/            言語そのもの        → lhat.lib / lhat.dll
port/           継ぎ目の既定実装    → lhatport.lib / lhatport.dll
cli/            コマンドライン      → lhat.exe
```

**ホストのインクルードパスに載るのは `include/` だけ**とする。
`src/` には `source.h` `value.h` `token.h` のような一般的すぎる名前があり、
他人のインクルードパスに置くものではない。`include/lhat.h` がそこへ届く。

名前は組み込み C の慣例に倣った。FreeRTOS・lwIP・mbedTLS がいずれも
**環境ごとに差し替える層を「port 層」と呼ぶ**。`host` は 8.7 で
「ホストアプリが登録するもの」に、`env` は 8.6 の `L^` に取られている。

`lhat` は `lhatport` に依存する。ホストが自分の実装を持つなら、
`lhatport` をリンクから外して自分のものを置く。

## 9. 未決事項

- **M2 — 標準ライブラリの構成**

  登録簿とその機構は済んだ（8.6）。残っているのは
  8.2 の既定の初期束縛に何を入れるか、
  `system/io.lh` `system/debug.lh` のような単位をどう切るかである。
  いずれも標準ライブラリの設計であり、言語の規則ではない。

- **M3 — 実行時の読み込み**

  5.2 によりパスはリテラルに限る。
  計算されたパスから読み込む機構を設けるか、設けるならその結果の型をどう扱うか。

- **M4 — 値の出自を問う機構**

  7.4 のとおり `typeof^` は型を返す。
  「この値はどの単位のどの名前から来たか」を問う機能を設けるかは別の判断になる。

- **M7 — 公開されたテーブルの可変な範囲**

  8.6 が印を立てるのは機械のテーブル自身までであり、**中身には伝播させない**。
  したがって `public^` で公開されたテーブルは、いまも誰からでも書ける。

  自分の単位からは書けて外からは書けない、という形にしたいかどうかは決めていない。
  決めるなら印を二値から「所有する単位」へ広げることになる。困ってはいない。
