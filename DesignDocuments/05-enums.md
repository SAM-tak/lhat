# 05 列挙体

04 の E1（`error^` の `kind` の型）が発端。
綴りの誤りを静的に捕まえられる種別の表現が要る。

節番号のうち「01 の」「02 の」「04 の」と前置きしたものは他文書を指す。
未決事項には `N` を冠して 8 章にまとめる。

---

## 1. Memo.md の案では足りない

Memo.md L126–L134 は列挙体を **テーブルの糖衣** として書いている。

```text
{enum^:
a,
b,
c,
enum^10:
d,
e}
```

これは次と同義であるとされていた。

```lhat
{ a := 1, b := 2, c := 3, d := 10, e := 11 }
```

`foo.e` は **数値の 11** である。したがって次が起きる。

- 他の列挙体の `11` と等しくなる。種別として区別できない
- `foo.x` と綴りを誤っても `nil^` になるだけで、静的には捕まらない

採番の便宜であって、型ではない。04 の E1 はこれでは解けない。

---

## 2. 構造的型付けの例外［確定・重要］

### 2.1 求めているもの

標準ライブラリの誤りと利用者の誤りが、同じ要素名を持っても混ざらないこと。

```lhat
enum^ IOError { NotFound, Denied }        # 標準ライブラリ
enum^ UserError { NotFound, Invalid }     # 利用者定義

IOError.NotFound = UserError.NotFound     # 偽であってほしい
```

### 2.2 規則どおりなら区別できない

02 の 14.9 はこう定めている。

> 名前は表示と診断のための札にすぎない。型の同一性は構造で決まる。
> 名前を同一性に含めると公称型付けになり、
> 構造的な型検査を採るという決定と衝突する。

`IOError` と `UserError` は構造が同じである。
規則をそのまま適用すれば **同じ型** であり、上の比較は **真** になる。求めているものと逆になる。

### 2.3 記号方式では足りない

要素を「名前だけを持つ記号」とし、
列挙体を「その記号の集合」として構造的に定義する案があった。

```text
IOError   = 記号 NotFound か 記号 Denied のいずれか
UserError = 記号 NotFound か 記号 Invalid のいずれか
```

綴りの誤り（`IOError.NotFund`）は捕まる。**例外を作らずに済む。**

だが `IOError.NotFound = UserError.NotFound` は **真のまま** である。
同じ記号だからである。

実際に書かれる要素名は `NotFound` `Invalid` `Timeout` `Cancelled` `Denied` に集中する。
**衝突は例外的な事故ではなく通常の事態** であり、
標準ライブラリの `NotFound` と利用者の `NotFound` が一致することは、
2つを別々に宣言した意味を失わせる。採らない。

### 2.4 決定 — 同一性は宣言の場所で決まる［確定］

> **列挙体の同一性は、構造ではなく宣言の場所で決まる。**

**これは構造的型付けの明示的な例外である。** 02 の 11.3 と 14.9 に対する例外として扱う。

同じ要素名を持つ2つの宣言は、別の型であり、その要素は別の値である。

```lhat
enum^ IOError { NotFound, Denied }
enum^ UserError { NotFound, Invalid }

IOError.NotFound = UserError.NotFound     # 偽
```

同一性は **原文の出現位置** に結び付く。評価のたびに新しくなるのではない。
手続きの中で宣言された列挙体も、何度呼んでも同じ列挙体である。

#### 前例

**TypeScript は構造的型付けを採りながら、`enum` だけを公称にしている。**
同じ問題に対する同じ例外であり、位置づけまで一致する。

### 2.5 `def^` との違い［重要］

例外を認めても一貫性は保たれる。2つは違うものを記述しているためである。

- **`def^` は「形」を記述する。** 同じ形なら通じ合うべきである。
  それが構造的型付けの利点そのものであり、14.9 が名前を札に留めた理由でもある
- **列挙体は「互いに異なる札の集合」を宣言する。**
  別々に宣言した集合が混ざらないことが目的そのものである。
  構造で同一視すると、宣言した意味が消える

構造的型付けが有利なのは **形が偶然一致したものを通したい** 場合であり、
列挙体が求めるのは正反対の性質である。同じ規則で扱うほうが不自然になる。

## 3. 形［確定］

### 3.1 宣言形式である

```lhat
enum^ UserError {
    ErrorA,
    ErrorB,
}
```

**`enum^` は宣言形式であり、名前を伴う。** `def^` のような式ではない。

無名の列挙体は書けない。書く手段が存在しない。

### 3.2 なぜ `def^` と違い式にしないのか［重要］

02 の 14.9 が `def^` を式にしたのは、名前が同一性に関与しないからである。
名前が札にすぎないなら、束縛から拾えばよい。

**列挙体では名前が同一性そのものである（2.4）。**
ならば名前は、束縛される先から拾うものではなく、宣言に書かれるべきものになる。

> **記法の違いが、意味の違いを表している。**

14.9 が式形を選んだもう一つの理由は合成（`..`）だった。
**列挙体に合成は要らない。** 2つの列挙体を混ぜた列挙体は、
要素が元の要素なのか新しい要素なのかが決まらず、2.4 と噛み合わない。
したがってこの理由もここには効かない。

#### 無名を許さないことは 14.10 の要請でもある

02 の 14.10 は「`rawsignature^` の出力はそのまま型注釈として解析できる」と定めた。

無名の列挙体には **注釈として書ける名前がない**。
構造で書き表すこともできない。同一性が構造にないためである（2.4）。
つまり **例外を認めたことが、名前を必須にすることを強制している**。

宣言形式にすれば、この制約が規則ではなく文法として実現される。

### 3.3 Memo.md の `{enum^: … }` は撤回［確定］

テーブルの中に置く採番の糖衣（1 章）は **撤回する**。

同じ `enum^` という綴りが、
一方では型を宣言し、他方ではテーブルに数値を詰める意味になる。
本言語が繰り返し退けてきた「1つの綴りに2つの意味」にあたる
（01 の Q8、02 の S11 など）。

自動採番されたテーブルが要るなら別の綴りで導入する。
現時点で要求がないため、置かない。

## 4. 要素［確定］

### 4.1 数値は属性であって同一性ではない［重要］

各要素は数値を伴う。ただし **数値は同一性ではない**。

```lhat
enum^ A { X }        # X の値は 1
enum^ B { Y }        # Y の値は 1

A.X = B.Y            # 偽。値が同じでも別の要素
```

数値は直列化や FFI のために持たせるものであり、比較の根拠ではない。
比較は要素そのものの同一性で行う（6 章）。

### 4.2 採番

Memo.md L126–L134 の規則を引き継ぐ。

- 既定は **1 から** の連番
- `名前 := 数` で明示できる。**以降の要素はそこから続く**

```lhat
enum^ Errno {
    Ok,                  # 1
    NotFound := 10,      # 10
    Denied,              # 11
}
```

Memo.md の `enum^10:` という区切りは、
`名前 := 数` に置き換わる。初期値を伴う束縛は `:=` という規則が
言語全体で保たれる（02 の 16.3 が `from^` を退けたのと同じ理由）。

### 4.3 `name` と `value`

要素は2つのメンバを持つ。どちらも読み取り専用。

| メンバ | 型 | 意味 |
| --- | --- | --- |
| `name` | `string^` | 宣言に書かれた綴り |
| `value` | `number^` | 4.2 の数値 |

```lhat
Errno.NotFound.name     # "NotFound"
Errno.NotFound.value    # 10
```

要素名が `name` や `value` である場合、`E.name.name` のように重なる。
曖昧ではないが読みにくいため、診断で注意を促す。

### 4.4 要素は必ず修飾して書く

`UserError.ErrorA` と書く。`ErrorA` 単独では参照できない。

列挙体を宣言しただけで要素名が周囲の場を占めることはない。
2.1 が避けようとしている衝突を、名前の解決の段でも起こさないためである。

## 5. 型としての扱い［確定］

### 5.1 `UserError` と `enum^`

- **`UserError`** — その列挙体の要素であること
- **`enum^`** — **何らかの列挙体の要素であること**

```lhat
k : UserError        # UserError の要素のいずれか
a : enum^            # どの列挙体の要素でもよい
```

`enum^` が要るのは 7 章のためである。
`error^` の `kind` は、標準ライブラリの列挙体も、
**まだ書かれていない利用者の列挙体も** 受けなければならない。
固定の合併では書けない。

複数を限って受けるなら合併で書く。

```lhat
k : IOError|UserError
```

### 5.2 互いに素（02 の 14.12）

02 の 14.12 が定めた互いに素の判定に、次が加わる。

- **異なる列挙体どうし** — 互いに素
- **列挙体と列挙体以外** — 互いに素
- **`enum^` とどの列挙体** — 互いに素にならない（上位型のため）

したがって 04 の 2.4 と同じく、`T|UserError` はいつでも判別できる。
多重定義（14.12）で列挙体ごとに分けることもできる。

### 5.3 `typeof^` と `rawsignature^`

`typeof^(要素)` は **宣言された列挙体の名前** を返す。

```lhat
typeof^(UserError.ErrorA)     # UserError
```

要素ひとつを表す型（単集合型）には広げず、列挙体まで広げて表示する。
3.2 のとおり無名の列挙体は存在しないので、返す名前は常にある。
14.10 の「出力がそのまま注釈として解析できる」も満たされる。

単集合型を注釈として書けるようにするかは未決（N1）。

## 6. 比較［確定］

要素どうしは `=` と `≠` で比較する。02 の 11.6 の比較の水準に乗る。

```lhat
if^ err.kind = UserError.ErrorA { … }
```

**大小比較は行わない。** 順序が要る場合は数値を明示して比べる。

```lhat
if^ a.value < b.value { … }
```

数値が同一性ではない以上（4.1）、
それを暗黙に順序として使うと 4.1 の区別が崩れる。

### 静的に偽と分かる比較

5.2 により、異なる列挙体は互いに素である。
したがって次は **常に偽** であり、診断できる。

```lhat
k : IOError
if^ k = UserError.ErrorA { … }     # 誤り。IOError と UserError は互いに素
```

`kind : enum^` のように上位型で受けている場合は、
どの列挙体とも重なるため比較は正当である。

## 7. `error^` の `kind`［確定・04 の E1 を閉じる］

04 の 2.2 が `kind : string^` としていたものを **`kind : enum^`** に改める。

```lhat
enum^ UserError { ErrorA, ErrorB }

return^ error^{
    kind := UserError.ErrorA,
    message := "…",
}
```

受け取る側は 02 の 5.2 の文形で振り分ける。

```lhat
if^ err.kind = IOError.NotFound {
    elseif^ err.kind = UserError.ErrorA:
        handle()
    else^:
        return^ err
}
```

`IOError.NotFound` と `UserError.ErrorA` は別の列挙体の要素なので、
綴りが同じでも取り違えは起きない。綴りの誤りは 5.2 により静的に捕まる。

### 網羅性は解けない［重要］

**本章は 04 の E1 を閉じるが、E2（網羅性）は閉じない。**

「この手続きが返しうる誤りは `IOError` のいずれか」を型に書くには、
`error^` を列挙体で径数化する必要がある。

```lhat
f^ open(p:string^) -> file^|error^;      # kind が IOError に限られることを書けない
```

**L^ に総称型がない。** E2 は総称型を導入するか、
誤り専用の仕組みを別に作るかの判断であり、E1 とは別の決定になる。

## 8. 未決事項

- **N1 — 単集合型を注釈に書けるようにするか**

  `UserError.ErrorA` を型として書く形。
  型の文法に修飾された名前が必要になる（02 の 13 章）。
  絞り込み（04 の E3）が要求するかどうかで決まる。

- **N2 — 網羅性の検査**

  `if^` の連鎖やパターンマッチ（02 の S19）で
  列挙体の全要素を尽くしたかを検査するか。04 の E2 と対になる。

- **N3 — ビット旗の用途**

  `A.X | A.Y` のような合成をどう扱うか。
  合成した値は 2.4 の意味では列挙体の要素ではない。
  現在 `|` は型の合併であり（02 の 11.5）、値の演算子として空いていない。

- **N4 — 直列化と FFI**

  数値との相互変換をどこまで言語が用意するか。
  `value` から要素を引く操作（逆引き）は、
  範囲外の数値に対して何を返すかを決める必要がある。

## 9. 文法のまとめ

### 9.1 追加する語

`enum^`。01 の 2.1 により **字句解析器には何も足さない**。

### 9.2 形

```text
文 := enum^ 名前 { 要素, … }

要素 := 名前
      | 名前 := 数
```

`enum^` の直後に `{` が来た場合は無名の宣言であり、誤りとする（3.1）。
診断では名前を書くよう促す。

### 9.3 型

```text
型 := … | enum^ | 列挙体の名前
```

### 9.4 02 の 14.13 の族との関係

04 の 2.3 で `error^{ … }` を
「組み込みの識別子に `{ … }` が直に続く形」の族に入れた。
`self^{ … }`（02 の 14.6）と同じ族である。

**`enum^ 名前 { … }` はこの族ではない。** 間に名前が入る。
構文解析器は `enum^` の次のトークンを見るだけで区別できる。

- `enum^` の次が名前 — 列挙体の宣言
- `enum^` の次が `{` — 誤り（3.1）
- 型の位置の `enum^` — 上位型（5.1）
