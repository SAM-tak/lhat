# L^ 構文仕様

構文解析器が扱う範囲、すなわちトークン列から構文木を得るまでを定義する。
トークンの定義は [01-lexical-structure.md](01-lexical-structure.md) を参照。

記法ラベル（［確定］／［提案］／［未決］）の意味は [README.md](README.md) を参照。
本文書の未決事項には `S1`, `S2`, … の番号を振る（01 の `Q` 番号とは別系統）。

**現状**: 入力形式、コマンドインタプリタモード、REPL 統合、条件分岐、
`:` 導入構文の終端、文の構成、繰り返しの節、`finally^` 節が確定している。
残りは 7 章に着手すべき領域として列挙してある。

---

## 1. 2つの入力形式

L^ の処理系は2種類の入力を受け付ける。両者は文法規則が異なるのではなく、
**入力チャネルの性質が異なる**。この区別が本章以降のほぼすべての根拠になる。

### 1.1 通常形式 — 自由形式ソース［確定］

ソースファイルに書かれるコード。空白と改行に文法的な意味はない
（01 の 9.2、Q1）。唯一の例外は呼び出し括弧の規則（01 の 10.9）。

### 1.2 コマンドインタプリタモード — 行指向入力［確定］

対話プロンプトなどから1行ずつ受け取る入力。

**このモードを選ぶのはホストアプリケーションであり、
L^ ランタイムを生成する時点で指定する。**
ソースコード中からこのモードへ遷移する構文は存在しない。

Memo.md L116–L117 の `>> foo 1 2 3` に現れる `>>` は
コマンドプロンプトを表す表記であって構文ではない。詳細は 01 の 7.7 を参照。

## 2. 並置呼び出し

括弧を伴わない手続き呼び出し。

```text
foo 1 2 3
```

### 2.1 通常形式では構文エラー［確定］

通常形式のソースにこれを書くことはできない。

理由は **引数リストの終端が決まらない** ことにある。
01 の Q1 で改行に文法的意味を持たせないと決めた以上、次の2行は
ひと続きのトークン列でしかない。

```text
foo 1 2 3
bar 4 5
```

これを `foo(1,2,3)` と `bar(4,5)` に切る根拠がない。
`foo(1, 2, 3, bar, 4, 5)` も等しく合法な読みである。

シェル・Tcl・Ruby・Nim・Perl の並置呼び出しが成立しているのは、
いずれも改行を文の終端として扱っているからである。例外はない。

#### 前処理による読み替えも解決にならない

「構文解析器の手前で `foo 1 2 3` を `foo(1, 2, 3)` に書き換える」方式も採らない。
その前処理器は行の切れ目を正しく判定するために、次をすべて扱う必要がある。

- 複数行文字列の内部の改行
- 括弧内で折り返された改行
- ブロックコメント `#[ … ]#` をまたぐ改行
- `"""` 行末文字列

つまり前処理器が完全な字句解析器になる。
そこまで作るなら、それは改行に敏感な構文解析器を1層余計にして作ったのと同じであり、
層が増えた分だけ悪い。

#### この決定が買っているもの

通常形式で並置呼び出しを許さないことにより、
**2つのモードの差が文レベルの解析規則1箇所に閉じる**。
式の解析にも字句解析にもモードが波及しない。

仮に通常形式でも並置を許すと、`foo -1` が
「引数 `-1` の呼び出し」なのか「`foo` から `1` を引く式」なのかが
常に問題になり続ける。Ruby と Nim はこれを空白の有無で解決しているが、
それは改行敏感よりさらに強い制約であり、01 の Q1 の方針から最も遠い。

### 2.2 コマンドモードで成立する理由［確定］

コマンドモードで並置呼び出しが成立するのは、**文法が改行に敏感だからではない**。
入力チャネルそのものが行指向であり、
プロンプトに打ち込まれた1行は Enter の時点で入力単位が確定しているためである。
構文解析器は改行を解釈しているのではなく、そもそも1行しか渡されていない。

2つのモードの差は「規則の違い」ではなく
**「行指向の入力チャネル」対「自由形式のソースファイル」** の違いである。

### 2.3 コマンド形式が成立する条件［確定］

コマンドモードであっても、入力が常に並置呼び出しとして解釈されるわけではない。

> 並置呼び出しとして解釈するのは、先頭が識別子であり、かつ
> **その次のトークンが式を継続できないもの** である場合に限る。

この条件がないと、プロンプトでの算術が壊れる。
`x - 1` の先頭は識別子なので、無条件に並置とみなすと `x(-1)` になってしまう。

| 入力 | 次のトークン | 解釈 |
| --- | --- | --- |
| `print "done"` | 文字列 | 並置 → `print("done")` |
| `ls` | 入力終端 | 並置 → `ls()` |
| `foo 1 2 3` | 整数 | 並置 → `foo(1, 2, 3)` |
| `foo {a := 1}` | `{`（テーブルリテラル） | 並置 → `foo({a := 1})` |
| `foo !x` | `!`（前置のみ） | 並置 → `foo(!x)` |
| `x - 1` | `-`（二項になれる） | 通常 → 減算 |
| `x.y` | `.`（継続） | 通常 → メンバアクセス |
| `x := 1` | `:=`（継続） | 通常 → 定義 |
| `foo(1)` | `(`（後置） | 通常 → 呼び出し |

`foo -1` は減算になる。呼び出したい場合は `foo (-1)` と書く。
Haskell と同じ割り切りであり、空白の有無に意味を持たせずに済む。

**この判定に使う「式を継続できるトークンか」の分類は、
01 の 10.9 が用いているものと同一である。** 分類表は1つで両方に効く。

### 2.4 呼び出し括弧は並置より強く結合する［確定］

`foo(1, 2, 3)` はコマンドモードでも通常形式でも同じ結果になる。

`(` は 01 の 10.9 により（直前に改行がないので）呼び出し括弧である。
したがってコマンド形式として解釈しても `foo(1,2,3)` 全体が1個の primary となり、
並置引数は0個になる。両形式で同じ構文木に落ちる。

10.9 の規則は空白ではなく **改行だけ** を見ているため、
`foo (1, 2, 3)` とスペースを空けても結果は変わらない。
Ruby のような空白敏感にはならない。

## 3. REPL 統合

コマンドモードのプロンプトに、通常形式で書かれた複数行のコード片を
貼り付けて実行できる必要がある。

### 3.1 未完入力の検出［確定］

実現の鍵は、**構文エラーと「入力が途中で終わっただけ」を区別する** ことにある。
Python・Node・irb・GHCi・Lua の REPL がいずれも行っている。

Lua はエラーメッセージの末尾が `<eof>` かどうかを文字列で判定しているが、
この実装は真似しない。**専用のエラー種別として最初から区別して返す。**
後から入れると面倒だが、最初から設計に入れておけば追加コストはほぼない。

字句解析器の側で「入力を待て」を意味するのは次の2つだけであり、
これらは既に実装されている。残りはすべて本物のエラーである。

- `LHAT_ERR_UNTERMINATED_STRING` — 複数行文字列の途中
- `LHAT_ERR_UNTERMINATED_BLOCK_COMMENT` — `#[ … ]#` の途中

数値リテラルなどは行をまたげないため、未完にはならない。

### 3.2 解析の手順［確定］

1. 入力をバッファに追加する
2. 入力が対話的な1行であり、2.3 の条件を満たすなら **コマンド形式** として解析する
3. そうでなければ **通常形式** として解析する
4. 成功したら実行し、バッファを空にする
5. 失敗の原因が「未完」なら、エラーを出さずに次の行を待つ
6. それ以外の失敗は構文エラーとして報告する

貼り付けられた複数行はこう流れる。

```text
Counter := {          # コマンド形式不成立（次が :=） → 通常形式 → 未完 → 継続
    value := 0,       # 継続
}                     # 完成 → 実行
```

プロンプトに打ち込まれた1行はこう流れる。

```text
print "done"          # 次が文字列 → コマンド形式 → print("done")
```

### 3.3 貼り付けの扱い［提案］

入力が複数行の塊として届いた場合は、2 を飛ばして **通常形式として一括解析する**。

行単位で処理すると、継続行が孤立する。

```text
foo
  .bar()
```

1行目の `foo` は単体で成立してしまうため、コマンド形式なら `foo()` を即実行し、
2行目の `.bar()` が行き場を失う。
貼り付けたコードがファイルに書いた場合と違う動作をすることになり、
01 の 10.9 で潰したはずの問題が REPL 経由で復活する。

貼り付け全体を1単位として受け取れれば、通常形式としてまとめて解析でき、
ファイルと同じ結果が得られる。

**これを実現する手段（端末の bracketed paste など）はホストの責務であり、
言語仕様の範囲外である。** 言語側は 4 章の API を提供するにとどまる。

### 3.4 ファイルと REPL の一致［確定］

01 の 10.9 の決定は、ここで予期していなかった利得を生んでいる。

Lua では次のコードがファイルと REPL で異なる意味になる。

```lua
a = b
(f or g)()
```

- ファイル → `a = b(f or g)()` という1文
- REPL → 1行目が単体で完結するため実行され、2行目が別に実行される

L^ は「改行直後の `(` は呼び出し括弧にならない」と決めているため、
ファイルでも2文になり、REPL の逐次実行と一致する。
**貼り付けたコードがファイルに書いたときと同じ動作をすることが保証される。**

## 4. ランタイムに必要な API［提案］

ホストが 3 章の手順を組めるように、ランタイムは次を提供する。

- 断片を通常形式として解析するエントリポイント（1行でも複数行でもよい）
- 断片をコマンド形式として解析するエントリポイント
- **未完を示す専用のエラー種別** — 3.1 のとおり文字列判定に頼らない

モードの選択、行の蓄積、プロンプトの切り替え、貼り付けの検出はいずれも
ホスト側の責務であり、ランタイムはモードを状態として保持しない。

## 5. 条件分岐［確定・旧 S1］

### 5.1 if 式の推奨形

```text
if^expr: expr el^expr: expr el^: expr ;
```

`el^` ひとつで「そうでなくもし」と「そうでなければ」の両方を表す。
両者は **条件式の有無** で区別する。

- `el^expr:` — 条件つき。他言語の else if にあたる
- `el^:` — 条件なし。他言語の else にあたる

構文解析器は `el^` の次のトークンが `:` かどうかを見るだけでよく、
1トークンの先読みで足りる。

Memo.md L182 の推奨形 `if^expr: or^expr: or^: ;` は撤回する。
`or^` を節マーカーに使うと論理和と衝突するため（01 の Q8）。
節の構造はそのまま、マーカーだけを `or^` から `el^` に替えた形になっている。

### 5.2 if 文の推奨形

```text
if^expr {
    elseif^expr:
        stats
    else^:
        stats
}
```

Memo.md L177 のとおり。文の側では短縮形を使わない。

短縮形 `ei^` `el^` を if 式に限るのは Memo.md L623–L624 の判断による。
複数行にわたる文では長い綴りのほうが読みやすく、
1行に収める式では短いほうがよい。

### 5.3 許容する綴り［確定］

Memo.md L156–L177 は「全部許していいでしょう」としており、これに従う。

- 条件つき: `elseif^` `else^if^` `elsif^` `elif^` `ei^` `el^expr:`
- 条件なし: `else^` `el^`

`or^` は **論理和専用** であり、節マーカーとしては使えない（01 の Q8）。

整形時にどの綴りへ寄せるかはフォーマッタが決める。
字句解析器も構文解析器も、綴りの違いを情報として保持する必要はない。

## 6. `:` 導入構文の終端［確定・旧 S2］

`:` で本体を導入する構文は、**`;` で明示的に閉じる**。省略できない。

### 6.1 関数・手続き定義式

Memo.md L148–L151 が挙げていた次の形は **不正** とする。

```text
foo(f^:x, y)      # 誤り。; がない
```

`x, y` が関数の返り値リストなのか、`y` が `foo` の第2引数なのかが決まらない。
どちらの意図であれ `;` を書く。

```text
foo(f^:x;, y)     # 返り値は x。y は foo の第2引数
foo(f^:x, y;)     # 返り値は x, y。foo の引数は1個
```

`;` を省略可能にして「閉じられていなければ最後まで」と定めることもできるが、
その規則では読み手が2つの解釈を毎回突き合わせる必要が残る。必須とする。

### 6.2 if 式

5.1 のとおり `;` で閉じる。

```text
r := if^a: 1 el^: 2 ;
```

### 6.3 共通する原則

この2つは同じ問題の別の現れである。

> `:` は開いた構造を導入する。開いたものは `;` で閉じる。

01 の 9.2 で「`;` は改行方針とは独立に必要」と切り出したのがこれにあたる。
改行に意味を持たせても解決しない。1行に書いても同じく決まらないためである。

`{ … }` で本体を囲む形（if 文、`do^{}`、繰り返し）は
閉じ括弧が終端になるため `;` を要しない。

## 8. 文の構成［確定・旧 S3］

### 8.1 何が問題なのか

「文として何を許すか」は一見どうでもよい分類の話に見えるが、
**01 の 10.9 が扱う曖昧性の範囲を直接決める** ため、先に固める必要がある。

10.9 の規則は「継続にも文頭にもなれるトークン」が改行直後に現れたときに、
人間の読みと構文解析器の読みが食い違う、という問題への対処だった。
そして対象を `(` だけに絞れたのは、
**他のトークンが文頭になれないと判断したから** である。

つまり、文になれる形を増やすと 10.9 の対象トークンが増える。
逆に絞れば増えない。両者は同じ問題の表と裏である。

### 8.2 裸の式は文にしない［確定］

`a + b` のように値を計算するだけで何も起こさない式は、
ソースファイル中では文として認めない。

理由は 8.1 のとおり。裸の式を文として認めると、
`+` `-` `*` `..` などあらゆる二項演算子が文頭に立てるようになり、
改行直後に現れたときの曖昧性が全演算子に広がる。

REPL は別扱いとする。プロンプトで `2 + 3` を評価できないのは論外なので、
**対話入力の最上位でのみ裸の式を受理する**。
Python が同じ扱いをしている（ファイル中では合法だが、REPL では値が表示される）。
L^ はファイル中では不正とする点だけが異なる。

### 8.3 文になれる形［確定］

- ハット識別子で始まるもの — 制御構文、`return^`、`break^`、`yield^`、
  `do^{}`、`with^` など。すべて先頭が `HAT_IDENT` なので判別が容易
- 定義 — `x := expr`
- 再代入 — `x << expr`
- 呼び出し — `foo(…)`、`foo.bar()`、`foo?.baz()`

いずれも先頭は **ハット識別子・識別子・名前リテラル・`$` 指定子・`(`** のどれかになる。
このうち式を継続できるのは `(` だけであり、それが 10.9 の規則の対象である。

### 8.4 後置形を撤回した理由

当初 Q2 は再代入を後置形 `expr -> x` と定めていた。
この形は **文の先頭に任意の式が来ることを許す**。

01 の 10.9 には次のように書いた。

> `-` — 「負数だけの文」は意味を持たないため文頭になれない

**この判断は誤りである。** 「負数だけの文」は確かに無意味だが、
負数を代入する文は無意味ではない。

```text
update()
-1 -> counter
```

`-1 -> counter` は「counter に -1 を代入する」という自然な文である。
しかし改行に意味がないため、この2行は次のように解釈される。

```text
update() - 1 -> counter
```

これはソース式が `update() - 1`、対象が `counter` の **完全に妥当な再代入文** である。
構文エラーにならないため、誤読は黙って通る。
10.9 で潰したはずの Lua 型の問題が、`-` について残っている。

該当するのは `-` のみである。`!` `@` `$` は前置専用で式を継続できず、
識別子・数値・文字列・名前リテラルも式を継続できない
（並置呼び出しを禁じたため、2.1）。

### 8.4.1 演算子の綴りを替えても解決しない

再代入の記号を `->` から、未使用の `>>` に替える案を検討した。
`->` が `-` で始まることが原因なら、綴りを替えれば済むはずである。

**原因はそこではない。** 曖昧なのは文頭に置かれた **ソース式 `-1` の `-`** であり、
演算子の綴りとは無関係である。

```text
update()
-1 >> counter     # 行頭の - は依然として二項か単項か決まらない
```

原因は後置形そのものにある。
後置形は文が任意の式で始まることを許すため、
その式が `-` で始まる可能性を構造的に排除できない。

対象を先に置く形であれば文が識別子で始まり、
識別子は式を継続できないため曖昧性が生じない。

なお、前置形を **追加** するだけでは足りない。
後置形が併存する限り、後置で書かれた文に対して規則が必要になる。
後置形を廃止して初めて解消する。

### 8.5 決定 — 再代入を `<<` に変え、規則を増やさない［確定］

> **再代入は `target << value` と書く。後置形は廃止する。**

これにより文の先頭は常に対象（識別子・名前リテラル・`$` 指定子）から始まり、
`-` が文頭に立つことがなくなる。8.4 の誤読は **構造的に発生しなくなる**。

```text
update()
counter << -1     # 2文。counter は式を継続できないので誤読しようがない
```

#### 検討して採らなかった案

- **改行直後の `-` を単項に固定する。** 10.9 の考え方を `-` にも広げる案。
  人間の読みには最も近いが、改行に意味を持つトークンが2つに増える。
  行頭に二項演算子を置く整形が `-` についてのみ書けなくなり、
  `+` には単項の用法がないため `-` だけが例外的にふるまう不統一も生じる
- **文が `-` で始まることを禁じ、`(-1) -> counter` と書かせる。**
  規則は増えないが、負数の代入という自然な記述に括弧を強いる
- **再代入の記号を `>>` に替える。** 8.4.1 のとおり、
  原因が演算子の綴りではないため何も解決しない

いずれも 8.4 の問題を **回避** する案であり、
`<<` への変更だけが問題そのものを **消している**。

#### 波及

- **改行に意味を持つ規則は 10.9 のひとつに保たれた。**
  「改行は文法的に無意味」という Q1 の原則が、例外1件のまま維持される
- **字句解析器は演算子表の入れ替えのみ。** `<<` を追加し、`->` は残す。
  `->` は言語の一部ではないが、Memo.md にも本文書の旧版にも後置形の記述があるため、
  構文解析器が「後置形は廃止された。`target << value` と書く」と
  指摘できるようトークンとして認識し続ける
- 8.2 と 8.3 は変更を受けない

## 9. 繰り返しの節［確定・旧 S4］

繰り返し文の本体は、5種類の節に分けて書ける。

### 9.1 節の一覧

| 節 | 実行時期 | 条件不成立時 | 省略 |
| --- | --- | --- | --- |
| `prolog^` | 繰り返しに入る前に1回 | 実行される | 可 |
| `first^` | 最初の反復の先頭で1回 | 実行されない | 可 |
| `main^` | 毎回 | — | 条件つきで可（9.3） |
| `last^` | 繰り返し終了時に1回 | 実行されない | 可 |
| `epilog^` | 繰り返し終了時に1回 | 実行される | 可 |

`prolog^` と `epilog^` は **実行条件の成否にかかわらず** 実行される。
`first^` と `last^` は **条件が一度も成立しなかった場合には実行されない**。

`last^` はループ変数などが「条件が成立した最後の状態」で実行される。

### 9.2 順序は固定［確定］

節は必ずこの順に書く。

```text
prolog^  →  first^  →  main^  →  last^  →  epilog^  →  finally^
```

- `prolog^` はブロック先頭に置く
- `first^` はブロック先頭、`prolog^` がある場合はその直後に置く
- `last^` はブロック末尾、後続の節がある場合はその直前に置く
- `epilog^` はブロック末尾、`finally^` がある場合はその直前に置く
- `finally^` はブロック末尾に置く（10 章）

順序を強制することで、構文解析器は集合ではなく **単純な並び** として扱える。
順序が違えば「`prolog^` は先頭に置く」と位置を特定した診断が出せる。

```lhat
repeat^until^i ≧ 10 {
    prolog^:
        total := 0
    first^:
        log("開始")
    main^:
        total << total + i
    last^:
        log("最後の i は " .. i)
    epilog^:
        log("終了")
}
```

節の区切りは次の節の見出しまたは閉じ括弧が担うため、`;` は要らない。
6.3 に述べた「`{ … }` で囲む形は閉じ括弧が終端になる」に該当する。

### 9.3 `main^` を省略できる条件［確定］

- `prolog^` も `first^` もない場合、`main^` は省略できる。
  見出しのない文の並びが本体になる
- どちらか一方でもある場合、`main^` は **必須**

この非対称には理由がある。
`prolog^` と `first^` は **前置** の見出しであり、
見出しを付けずに本体を書くと、それが `prolog^` 節の続きなのか本体なのかが
書き手の意図として曖昧になる。

```lhat
repeat^n {
    prolog^:
        total := 0
    total << total + 1     # prolog の続き？ 本体？
}
```

構文としては `prolog^` 節の続きに決まるが、書き手が本体のつもりで書く事故を防ぐため
`main^` を要求する。

`last^` と `epilog^` は **後置** の見出しであり、
見出しより前の文は本体であることが一意に決まる。したがって制限を課さない。

```lhat
repeat^n {
    total << total + 1     # 本体。曖昧性がない
    epilog^:
        log("終了")
}
```

### 9.4 変数のスコープと寿命［確定］

繰り返し文のブロックは、**寿命の異なる2層** を持つ。

- `prolog^` および `first^` で宣言した変数
  — スコープは繰り返し文のブロック内、**寿命は繰り返し処理の全体**
- `main^` で宣言した変数 — **寿命は1回の反復**

`prolog^` が存在する目的がこれである。
繰り返しの外に変数を漏らさず、しかし寿命を繰り返し全体と揃えたい場合に使う。

`last^` と `epilog^` からは、`prolog^` と `first^` の変数が見える。
`main^` の変数は寿命が1反復であり、最後の反復の終了とともに消えているため見えない。
繰り返しをまたいで値を持ち越したい場合は `prolog^` か `first^` で宣言する。

### 9.5 適用範囲［確定］

Memo.md L215 のとおり、**すべての繰り返し構文** がこれらの節を持てる。

- `repeat^n { … }`、`repeat^{ … }`
- `repeat^while^expr { … }`、`repeat^until^expr { … }`
- `for^i from^1 to^10 { … }`（`step^` つきを含む）
- `for^k, v in^table { … }`
- `for^i := 1 while^expr next^expr { … }`、`for^i := 1 until^expr next^expr { … }`

### 9.6 綴りの別形［確定］

- `prolog^` / `prologue^`
- `epilog^` / `epilogue^`

どちらで書いてもよい。整形時にどちらへ寄せるかはフォーマッタが決める。
条件分岐の綴り（5.3）と同じ扱いである。

### 9.7 実装上の含意

#### `first^` は内側で実行し、外側へ宣言する

`first^` は最初の反復の先頭で実行されるため、実行位置は繰り返しの内側にある。
しかし 9.4 のとおり、そこで宣言された変数の寿命は繰り返し全体である。

したがってコード生成では、
**`first^` の実行は繰り返しの内側、宣言の割り付けは外側のスコープ** に分ける。
`prolog^` と同じ記憶域に、実行時期だけを遅らせて書き込む形になる。

#### `last^` は状態の保存を要する

Memo.md L210 が「`last^` があると前回の状態を保存しておく必要があるな」と
指摘しているのがこれにあたる。

繰り返しが終わるのは条件が **成立しなくなった** ときである。
その時点でループ変数は、条件を満たさなかった値になっている。

```lhat
for^i from^1 to^10 {
    last^:
        log(i)      # 10 でなければならない。11 ではない
}
```

素朴に実装すると `last^` は 11 を見る。
「次の反復があるか」は条件を評価するまで分からず、
条件式には副作用がありうるため先読みできない。

したがって **`last^` を持つ繰り返しでは、ループ変数の値を控えておき、
脱出後にその値で `last^` を実行する**。

控えを取る時期は **各反復の先頭**、条件が成立した直後とする。
反復の終了時ではない。9.8 のとおり `break^` は反復の途中での脱出であり、
そのとき妥当な最後の要素は **現在の反復の値** だからである。
終了時に控える方式では1つ前の反復の値を見てしまう。

先頭で控える方式は通常終了にも正しく働く。
条件が成立した最後の時点が、最後の反復の先頭にあたるためである。

費用は `last^` を書いた繰り返しにのみ生じる。
`last^` のない繰り返しは控えを取らない。

#### `first^` と `last^` は「1回以上実行されたか」を要する

どちらも条件が一度も成立しなければ実行されない。
`first^` は最初の反復に入った時点で実行すればよいが、
`last^` は脱出後に判定するため真偽値を1つ保持する。
これも `last^` を持つ繰り返しにのみ生じる費用である。

### 9.8 脱出時の扱い［確定・旧 S7］

| 脱出の仕方 | `last^` | `epilog^` | `finally^` |
| --- | --- | --- | --- |
| 条件が成立しなくなった（通常終了） | 一度でも成立していれば実行 | 実行 | 実行 |
| `break^` | 妥当な最後の要素があれば実行 | 実行 | 実行 |
| `return^` | 実行しない | 実行しない | 実行 |

#### 3段階の強度

3つの節は、実行される範囲が段階的に広がる関係にある。

1. **`last^`** — 条件が一度でも成立した場合のみ。最後の要素に対する締めくくり
2. **`epilog^`** — 条件の成否によらず実行。ただし繰り返しを正常に抜けた場合に限る
3. **`finally^`** — あらゆる脱出で実行される（10 章）

`break^` は繰り返しにとって正常な終了である。
やるべきことが済んだので抜ける、という意味であり、その後の処理は通常どおり続く。
したがって `last^` と `epilog^` の両方が実行される。

`return^` は関数からの離脱であり、繰り返しにとっては正常な終了ではない。
`last^` も `epilog^` も実行されず、**`finally^` だけが実行される**。

この区別は、今後 例外や誤りによる脱出を設計する際の指針にもなる。
そうした脱出は `return^` と同じ側に属し、`finally^` のみを実行する。

#### `epilog^` は finally ではない

`epilog^` は `return^` で実行されないため、他言語の `finally` には相当しない。
脱出の種類を問わない後始末が必要な場合は `finally^` を使う（10 章）。

繰り返しに `finally^` を書くこともできる。その場合 `epilog^` は
`finally^` の直前に置くことが強制される（9.2）。

#### `break^` 時に `last^` が見る値

`break^` は反復の **途中** での脱出であり、その反復では条件が成立している。
したがって妥当な最後の要素は **現在の反復の値** である。

```lhat
for^i from^1 to^10 {
    main^:
        if^ i = 5 { break^ }
    last^:
        log(i)      # 5。4 ではない
}
```

9.7 で控えを各反復の **先頭** で取ると定めたのはこのためである。

#### 実装上の含意

`last^` と `epilog^` はいずれも `return^` では実行されないため、
**繰り返しの脱出経路に閉じた処理として生成できる**。
関数からの離脱に伴う巻き戻しの機構は必要ない。それは `finally^` の仕事になる（10.4）。

#### 多段の `break^`［提案 → 要確認］

Memo.md L500 と L538 には `break^[name]` `break^[1]` という
複数の繰り返しを一度に抜ける記法がある。

上の原則を素直に適用すると次のようになる。

- **脱出先として指定された繰り返し** — 正常な終了なので `last^` と `epilog^` を実行
- **途中で抜けられる内側の繰り返し** — その繰り返しにとっては
  外側へ抜けるための離脱であり `return^` と同じ側にあたる。`finally^` のみ実行

原則からの帰結として記す。多段 `break^` の記法自体がまだ確定していないため、
記法を決める際に併せて確認する。

### 9.9 `dispose` と `defer^` は無関係［確定］

Memo.md L52 に「`for` の場合はスコープ終了で `dispose` が呼ばれる。
他言語で言う `using`」という記述があるが、
**`dispose` は繰り返し構文とは無関係である**。

`dispose` が指しているのは C# の `IDisposable` と `using` に相当する仕組みであり、
L^ では `with^`（Memo.md L371–L372）が担う。
繰り返しのスコープ終了で自動的に呼ばれるものではない。

`defer^`（Memo.md L146）については、構想が定まっていないため
本文書では扱わない。遅延評価の指定を意図したものと思われるが、
設計が固まった時点で改めて位置づける。

## 10. `finally^` 節［確定］

### 10.1 ブロック一般の機構である

`finally^` は繰り返し固有の節ではなく、**ブロックの末尾に置ける汎用の節** である。

```lhat
do^{
    r := open("data")
    process(r)
finally^:
    r.close()
}
```

置けるブロックは次のとおり。

- `do^{ … }`
- `if^` 文のブロック
- 繰り返し文のブロック（9.2 の順序に従い、`epilog^` の直後）
- `with^` のブロック

関数定義の本体ブロックには置けない［要確認］。
`f^…{ … }` の `{ }` は関数の本体であり、通常のブロックとは別の構文上の位置にある。

### 10.2 あらゆる脱出で実行される

ブロックをどのように抜けても実行される。

- 末尾まで到達した場合
- `break^` で繰り返しを抜けた場合
- `return^` で関数から離脱した場合
- 多段の `break^` で通過された場合

他言語の `finally` に相当する。将来 例外や誤りによる脱出を導入した場合も、
`finally^` は実行される側に属する。

### 10.3 位置は末尾に強制

ブロックの最末尾に置く。
繰り返しの節と併用する場合の順序は 9.2 のとおりで、`finally^` が最後になる。

```text
prolog^  →  first^  →  main^  →  last^  →  epilog^  →  finally^
```

### 10.4 実装上の含意

`finally^` が関数からの離脱でも実行される以上、
**`return^` は、抜けるすべてのブロックの `finally^` を内側から順に実行してから
関数を出る** 必要がある。

どのブロックの内側にいるかは構文上わかるため、実行時の巻き戻し表は要らない。
`return^` の位置ごとに、抜けるブロックの `finally^` を順に呼ぶコードを生成すればよい。

この機構を `finally^` に集約したことにより、
繰り返しの節（`last^` `epilog^`）は繰り返しの脱出経路だけを扱えばよくなった。
**巻き戻しの担い手が1つに定まる。**

例外や誤りによる脱出を導入する際は、静的に位置が定まらない脱出が生じるため、
実行時の機構が必要になるかを改めて検討する。

### 10.5 `epilog^` との使い分け

- 繰り返しが正常に終わったときだけの後始末 → `epilog^`
- 脱出の種類を問わない後始末（資源の解放など） → `finally^`

繰り返し以外のブロックには `epilog^` がないため、選択の余地はない。
