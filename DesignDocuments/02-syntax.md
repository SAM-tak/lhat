# L^ 構文仕様

構文解析器が扱う範囲、すなわちトークン列から構文木を得るまでを定義する。
トークンの定義は [01-lexical-structure.md](01-lexical-structure.md) を参照。

記法ラベル（［確定］／［提案］／［未決］）の意味は [README.md](README.md) を参照。
本文書の未決事項には `S1`, `S2`, … の番号を振る（01 の `Q` 番号とは別系統）。

**現状**: 入力形式、コマンドインタプリタモード、REPL 統合、条件分岐、
`:` 導入構文の終端、文の構成、繰り返しの節、`finally^` 節、演算子と優先順位、
`with^`、型の文法、オブジェクトモデル、サブルーチンの種別が確定している。
残りは 7 章に着手すべき領域として列挙してある。

## 1. 2つの入力形式

L^ の処理系は2種類の入力を受け付ける。両者は文法規則が異なるのではなく、
**入力チャネルの性質が異なる**。この区別が本章以降のほぼすべての根拠になる。

### 1.1 通常形式 — 自由形式ソース［確定］

ソースファイルに書かれるコード。空白と改行に文法的な意味はない
（01 の 9.2、Q1）。唯一の例外は呼び出し括弧の規則（01 の 10.9）。

### 1.2 コマンドインタプリタモード — 行指向入力［確定］

対話プロンプトなどから1行ずつ受け取る入力。

**このモードを選ぶのはホストアプリケーションであり、
L^ ランタイムを生成する時点で指定する。**
ソースコード中からこのモードへ遷移する構文は存在しない。

Memo.md L116–L117 の `>> foo 1 2 3` に現れる `>>` は
コマンドプロンプトを表す表記であって構文ではない。詳細は 01 の 7.7 を参照。

## 2. 並置呼び出し

括弧を伴わない手続き呼び出し。

```text
foo 1 2 3
```

### 2.1 通常形式では構文エラー［確定］

通常形式のソースにこれを書くことはできない。

理由は **引数リストの終端が決まらない** ことにある。
01 の Q1 で改行に文法的意味を持たせないと決めた以上、次の2行は
ひと続きのトークン列でしかない。

```text
foo 1 2 3
bar 4 5
```

これを `foo(1,2,3)` と `bar(4,5)` に切る根拠がない。
`foo(1, 2, 3, bar, 4, 5)` も等しく合法な読みである。

シェル・Tcl・Ruby・Nim・Perl の並置呼び出しが成立しているのは、
いずれも改行を文の終端として扱っているからである。例外はない。

#### 前処理による読み替えも解決にならない

「構文解析器の手前で `foo 1 2 3` を `foo(1, 2, 3)` に書き換える」方式も採らない。
その前処理器は行の切れ目を正しく判定するために、次をすべて扱う必要がある。

- 複数行文字列の内部の改行
- 括弧内で折り返された改行
- ブロックコメント `#[ … ]#` をまたぐ改行
- `"""` 行末文字列

つまり前処理器が完全な字句解析器になる。
そこまで作るなら、それは改行に敏感な構文解析器を1層余計にして作ったのと同じであり、
層が増えた分だけ悪い。

#### この決定が買っているもの

通常形式で並置呼び出しを許さないことにより、
**2つのモードの差が文レベルの解析規則1箇所に閉じる**。
式の解析にも字句解析にもモードが波及しない。

仮に通常形式でも並置を許すと、`foo -1` が
「引数 `-1` の呼び出し」なのか「`foo` から `1` を引く式」なのかが
常に問題になり続ける。Ruby と Nim はこれを空白の有無で解決しているが、
それは改行敏感よりさらに強い制約であり、01 の Q1 の方針から最も遠い。

### 2.2 コマンドモードで成立する理由［確定］

コマンドモードで並置呼び出しが成立するのは、**文法が改行に敏感だからではない**。
入力チャネルそのものが行指向であり、
プロンプトに打ち込まれた1行は Enter の時点で入力単位が確定しているためである。
構文解析器は改行を解釈しているのではなく、そもそも1行しか渡されていない。

2つのモードの差は「規則の違い」ではなく
**「行指向の入力チャネル」対「自由形式のソースファイル」** の違いである。

### 2.3 コマンド形式が成立する条件［確定］

コマンドモードであっても、入力が常に並置呼び出しとして解釈されるわけではない。

> 並置呼び出しとして解釈するのは、先頭が識別子であり、かつ
> **その次のトークンが式を継続できないもの** である場合に限る。

この条件がないと、プロンプトでの算術が壊れる。
`x - 1` の先頭は識別子なので、無条件に並置とみなすと `x(-1)` になってしまう。

| 入力 | 次のトークン | 解釈 |
| --- | --- | --- |
| `print "done"` | 文字列 | 並置 → `print("done")` |
| `ls` | 入力終端 | 並置 → `ls()` |
| `foo 1 2 3` | 整数 | 並置 → `foo(1, 2, 3)` |
| `foo {a := 1}` | `{`（テーブルリテラル） | 並置 → `foo({a := 1})` |
| `foo !x` | `!`（前置のみ） | 並置 → `foo(!x)` |
| `x - 1` | `-`（二項になれる） | 通常 → 減算 |
| `x.y` | `.`（継続） | 通常 → メンバアクセス |
| `x := 1` | `:=`（継続） | 通常 → 定義 |
| `foo(1)` | `(`（後置） | 通常 → 呼び出し |

`foo -1` は減算になる。呼び出したい場合は `foo (-1)` と書く。
Haskell と同じ割り切りであり、空白の有無に意味を持たせずに済む。

**この判定に使う「式を継続できるトークンか」の分類は、
01 の 10.9 が用いているものと同一である。** 分類表は1つで両方に効く。

### 2.4 呼び出し括弧は並置より強く結合する［確定］

`foo(1, 2, 3)` はコマンドモードでも通常形式でも同じ結果になる。

`(` は 01 の 10.9 により（直前に改行がないので）呼び出し括弧である。
したがってコマンド形式として解釈しても `foo(1,2,3)` 全体が1個の primary となり、
並置引数は0個になる。両形式で同じ構文木に落ちる。

10.9 の規則は空白ではなく **改行だけ** を見ているため、
`foo (1, 2, 3)` とスペースを空けても結果は変わらない。
Ruby のような空白敏感にはならない。

## 3. REPL 統合

コマンドモードのプロンプトに、通常形式で書かれた複数行のコード片を
貼り付けて実行できる必要がある。

### 3.1 未完入力の検出［確定］

実現の鍵は、**構文エラーと「入力が途中で終わっただけ」を区別する** ことにある。
Python・Node・irb・GHCi・Lua の REPL がいずれも行っている。

Lua はエラーメッセージの末尾が `<eof>` かどうかを文字列で判定しているが、
この実装は真似しない。**専用のエラー種別として最初から区別して返す。**
後から入れると面倒だが、最初から設計に入れておけば追加コストはほぼない。

字句解析器の側で「入力を待て」を意味するのは次の2つだけであり、
これらは既に実装されている。残りはすべて本物のエラーである。

- `LHAT_ERR_UNTERMINATED_STRING` — 複数行文字列の途中
- `LHAT_ERR_UNTERMINATED_BLOCK_COMMENT` — `#[ … ]#` の途中

数値リテラルなどは行をまたげないため、未完にはならない。

### 3.2 解析の手順［確定］

1. 入力をバッファに追加する
2. 入力が対話的な1行であり、2.3 の条件を満たすなら **コマンド形式** として解析する
3. そうでなければ **通常形式** として解析する
4. 成功したら実行し、バッファを空にする
5. 失敗の原因が「未完」なら、エラーを出さずに次の行を待つ
6. それ以外の失敗は構文エラーとして報告する

貼り付けられた複数行はこう流れる。

```text
Counter := {          # コマンド形式不成立（次が :=） → 通常形式 → 未完 → 継続
    value := 0,       # 継続
}                     # 完成 → 実行
```

プロンプトに打ち込まれた1行はこう流れる。

```text
print "done"          # 次が文字列 → コマンド形式 → print("done")
```

### 3.3 貼り付けの扱い［提案］

入力が複数行の塊として届いた場合は、2 を飛ばして **通常形式として一括解析する**。

行単位で処理すると、継続行が孤立する。

```text
foo
  .bar()
```

1行目の `foo` は単体で成立してしまうため、コマンド形式なら `foo()` を即実行し、
2行目の `.bar()` が行き場を失う。
貼り付けたコードがファイルに書いた場合と違う動作をすることになり、
01 の 10.9 で潰したはずの問題が REPL 経由で復活する。

貼り付け全体を1単位として受け取れれば、通常形式としてまとめて解析でき、
ファイルと同じ結果が得られる。

**これを実現する手段（端末の bracketed paste など）はホストの責務であり、
言語仕様の範囲外である。** 言語側は 4 章の API を提供するにとどまる。

### 3.4 ファイルと REPL の一致［確定］

01 の 10.9 の決定は、ここで予期していなかった利得を生んでいる。

Lua では次のコードがファイルと REPL で異なる意味になる。

```lua
a = b
(f or g)()
```

- ファイル → `a = b(f or g)()` という1文
- REPL → 1行目が単体で完結するため実行され、2行目が別に実行される

L^ は「改行直後の `(` は呼び出し括弧にならない」と決めているため、
ファイルでも2文になり、REPL の逐次実行と一致する。
**貼り付けたコードがファイルに書いたときと同じ動作をすることが保証される。**

## 4. ランタイムに必要な API［提案］

ホストが 3 章の手順を組めるように、ランタイムは次を提供する。

- 断片を通常形式として解析するエントリポイント（1行でも複数行でもよい）
- 断片をコマンド形式として解析するエントリポイント
- **未完を示す専用のエラー種別** — 3.1 のとおり文字列判定に頼らない

モードの選択、行の蓄積、プロンプトの切り替え、貼り付けの検出はいずれも
ホスト側の責務であり、ランタイムはモードを状態として保持しない。

## 5. 条件分岐［確定・旧 S1］

### 5.1 if 式の推奨形

```text
if^expr: expr el^expr: expr el^: expr ;
```

`el^` ひとつで「そうでなくもし」と「そうでなければ」の両方を表す。
両者は **条件式の有無** で区別する。

- `el^expr:` — 条件つき。他言語の else if にあたる
- `el^:` — 条件なし。他言語の else にあたる

構文解析器は `el^` の次のトークンが `:` かどうかを見るだけでよく、
1トークンの先読みで足りる。

Memo.md L182 の推奨形 `if^expr: or^expr: or^: ;` は撤回する。
`or^` を節マーカーに使うと論理和と衝突するため（01 の Q8）。
節の構造はそのまま、マーカーだけを `or^` から `el^` に替えた形になっている。

### 5.2 if 文の推奨形

```text
if^expr {
    elseif^expr:
        stats
    else^:
        stats
}
```

Memo.md L177 のとおり。文の側では短縮形を使わない。

短縮形 `ei^` `el^` を if 式に限るのは Memo.md L623–L624 の判断による。
複数行にわたる文では長い綴りのほうが読みやすく、
1行に収める式では短いほうがよい。

### 5.3 許容する綴り［確定］

Memo.md L156–L177 は「全部許していいでしょう」としており、これに従う。

- 条件つき: `elseif^` `else^if^` `elsif^` `elif^` `ei^` `el^expr:`
- 条件なし: `else^` `el^`

`or^` は **論理和専用** であり、節マーカーとしては使えない（01 の Q8）。

整形時にどの綴りへ寄せるかはフォーマッタが決める。
字句解析器も構文解析器も、綴りの違いを情報として保持する必要はない。

## 6. `:` 導入構文の終端［確定・旧 S2］

`:` で本体を導入する構文は、**`;` で明示的に閉じる**。省略できない。

### 6.1 関数・手続き定義式

Memo.md L148–L151 が挙げていた次の形は **不正** とする。

```text
foo(f^:x, y)      # 誤り。; がない
```

`x, y` が関数の返り値リストなのか、`y` が `foo` の第2引数なのかが決まらない。
どちらの意図であれ `;` を書く。

```text
foo(f^:x;, y)     # 返り値は x。y は foo の第2引数
foo(f^:x, y;)     # 返り値は x, y。foo の引数は1個
```

`;` を省略可能にして「閉じられていなければ最後まで」と定めることもできるが、
その規則では読み手が2つの解釈を毎回突き合わせる必要が残る。必須とする。

### 6.2 if 式

5.1 のとおり `;` で閉じる。

```text
r := if^a: 1 el^: 2 ;
```

### 6.3 共通する原則

この2つは同じ問題の別の現れである。

> `:` は開いた構造を導入する。開いたものは `;` で閉じる。

01 の 9.2 で「`;` は改行方針とは独立に必要」と切り出したのがこれにあたる。
改行に意味を持たせても解決しない。1行に書いても同じく決まらないためである。

`{ … }` で本体を囲む形（if 文、`do^{}`、繰り返し）は
閉じ括弧が終端になるため `;` を要しない。

## 8. 文の構成［確定・旧 S3］

### 8.1 何が問題なのか

「文として何を許すか」は一見どうでもよい分類の話に見えるが、
**01 の 10.9 が扱う曖昧性の範囲を直接決める** ため、先に固める必要がある。

10.9 の規則は「継続にも文頭にもなれるトークン」が改行直後に現れたときに、
人間の読みと構文解析器の読みが食い違う、という問題への対処だった。
そして対象を `(` だけに絞れたのは、
**他のトークンが文頭になれないと判断したから** である。

つまり、文になれる形を増やすと 10.9 の対象トークンが増える。
逆に絞れば増えない。両者は同じ問題の表と裏である。

### 8.2 裸の式は文にしない［確定］

`a + b` のように値を計算するだけで何も起こさない式は、
ソースファイル中では文として認めない。

理由は 8.1 のとおり。裸の式を文として認めると、
`+` `-` `*` `..` などあらゆる二項演算子が文頭に立てるようになり、
改行直後に現れたときの曖昧性が全演算子に広がる。

REPL は別扱いとする。プロンプトで `2 + 3` を評価できないのは論外なので、
**対話入力の最上位でのみ裸の式を受理する**。
Python が同じ扱いをしている（ファイル中では合法だが、REPL では値が表示される）。
L^ はファイル中では不正とする点だけが異なる。

### 8.3 文になれる形［確定］

- ハット識別子で始まるもの — 制御構文、`return^`、`break^`、`yield^`、
  `do^{}`、`with^` など。すべて先頭が `HAT_IDENT` なので判別が容易
- 定義 — `x := expr`
- 再代入 — `x << expr`
- 呼び出し — `foo(…)`、`foo.bar()`、`foo?.baz()`

いずれも先頭は **ハット識別子・識別子・名前リテラル・`$` 指定子・`(`** のどれかになる。
このうち式を継続できるのは `(` だけであり、それが 10.9 の規則の対象である。

### 8.4 後置形を撤回した理由

当初 Q2 は再代入を後置形 `expr -> x` と定めていた。
この形は **文の先頭に任意の式が来ることを許す**。

01 の 10.9 には次のように書いた。

> `-` — 「負数だけの文」は意味を持たないため文頭になれない

**この判断は誤りである。** 「負数だけの文」は確かに無意味だが、
負数を代入する文は無意味ではない。

```text
update()
-1 -> counter
```

`-1 -> counter` は「counter に -1 を代入する」という自然な文である。
しかし改行に意味がないため、この2行は次のように解釈される。

```text
update() - 1 -> counter
```

これはソース式が `update() - 1`、対象が `counter` の **完全に妥当な再代入文** である。
構文エラーにならないため、誤読は黙って通る。
10.9 で潰したはずの Lua 型の問題が、`-` について残っている。

該当するのは `-` のみである。`!` `@` `$` は前置専用で式を継続できず、
識別子・数値・文字列・名前リテラルも式を継続できない
（並置呼び出しを禁じたため、2.1）。

### 8.4.1 演算子の綴りを替えても解決しない

再代入の記号を `->` から、未使用の `>>` に替える案を検討した。
`->` が `-` で始まることが原因なら、綴りを替えれば済むはずである。

**原因はそこではない。** 曖昧なのは文頭に置かれた **ソース式 `-1` の `-`** であり、
演算子の綴りとは無関係である。

```text
update()
-1 >> counter     # 行頭の - は依然として二項か単項か決まらない
```

原因は後置形そのものにある。
後置形は文が任意の式で始まることを許すため、
その式が `-` で始まる可能性を構造的に排除できない。

対象を先に置く形であれば文が識別子で始まり、
識別子は式を継続できないため曖昧性が生じない。

なお、前置形を **追加** するだけでは足りない。
後置形が併存する限り、後置で書かれた文に対して規則が必要になる。
後置形を廃止して初めて解消する。

### 8.5 決定 — 再代入を `<<` に変え、規則を増やさない［確定］

> **再代入は `target << value` と書く。後置形は廃止する。**

これにより文の先頭は常に対象（識別子・名前リテラル・`$` 指定子）から始まり、
`-` が文頭に立つことがなくなる。8.4 の誤読は **構造的に発生しなくなる**。

```text
update()
counter << -1     # 2文。counter は式を継続できないので誤読しようがない
```

#### 検討して採らなかった案

- **改行直後の `-` を単項に固定する。** 10.9 の考え方を `-` にも広げる案。
  人間の読みには最も近いが、改行に意味を持つトークンが2つに増える。
  行頭に二項演算子を置く整形が `-` についてのみ書けなくなり、
  `+` には単項の用法がないため `-` だけが例外的にふるまう不統一も生じる
- **文が `-` で始まることを禁じ、`(-1) -> counter` と書かせる。**
  規則は増えないが、負数の代入という自然な記述に括弧を強いる
- **再代入の記号を `>>` に替える。** 8.4.1 のとおり、
  原因が演算子の綴りではないため何も解決しない

いずれも 8.4 の問題を **回避** する案であり、
`<<` への変更だけが問題そのものを **消している**。

#### 波及

- **改行に意味を持つ規則は 10.9 のひとつに保たれた。**
  「改行は文法的に無意味」という Q1 の原則が、例外1件のまま維持される
- **字句解析器は演算子表の入れ替えのみ。** `<<` を追加し、`->` は残す。
  `->` は言語の一部ではないが、Memo.md にも本文書の旧版にも後置形の記述があるため、
  構文解析器が「後置形は廃止された。`target << value` と書く」と
  指摘できるようトークンとして認識し続ける
- 8.2 と 8.3 は変更を受けない

## 9. 繰り返しの節［確定・旧 S4］

繰り返し文の本体は、5種類の節に分けて書ける。

### 9.1 節の一覧

| 節 | 実行時期 | 条件不成立時 | 省略 |
| --- | --- | --- | --- |
| `prolog^` | 繰り返しに入る前に1回 | 実行される | 可 |
| `first^` | 最初の反復の先頭で1回 | 実行されない | 可 |
| `main^` | 毎回 | — | 条件つきで可（9.3） |
| `last^` | 繰り返し終了時に1回 | 実行されない | 可 |
| `epilog^` | 繰り返し終了時に1回 | 実行される | 可 |

`prolog^` と `epilog^` は **実行条件の成否にかかわらず** 実行される。
`first^` と `last^` は **条件が一度も成立しなかった場合には実行されない**。

`last^` はループ変数などが「条件が成立した最後の状態」で実行される。

### 9.2 順序は固定［確定］

節は必ずこの順に書く。

```text
prolog^  →  first^  →  main^  →  last^  →  epilog^  →  finally^
```

- `prolog^` はブロック先頭に置く
- `first^` はブロック先頭、`prolog^` がある場合はその直後に置く
- `last^` はブロック末尾、後続の節がある場合はその直前に置く
- `epilog^` はブロック末尾、`finally^` がある場合はその直前に置く
- `finally^` はブロック末尾に置く（10 章）

順序を強制することで、構文解析器は集合ではなく **単純な並び** として扱える。
順序が違えば「`prolog^` は先頭に置く」と位置を特定した診断が出せる。

```lhat
repeat^until^i ≧ 10 {
    prolog^:
        total := 0
    first^:
        log("開始")
    main^:
        total << total + i
    last^:
        log("最後の i は " .. i)
    epilog^:
        log("終了")
}
```

節の区切りは次の節の見出しまたは閉じ括弧が担うため、`;` は要らない。
6.3 に述べた「`{ … }` で囲む形は閉じ括弧が終端になる」に該当する。

### 9.3 `main^` を省略できる条件［確定］

- `prolog^` も `first^` もない場合、`main^` は省略できる。
  見出しのない文の並びが本体になる
- どちらか一方でもある場合、`main^` は **必須**

この非対称には理由がある。
`prolog^` と `first^` は **前置** の見出しであり、
見出しを付けずに本体を書くと、それが `prolog^` 節の続きなのか本体なのかが
書き手の意図として曖昧になる。

```lhat
repeat^n {
    prolog^:
        total := 0
    total << total + 1     # prolog の続き？ 本体？
}
```

構文としては `prolog^` 節の続きに決まるが、書き手が本体のつもりで書く事故を防ぐため
`main^` を要求する。

`last^` と `epilog^` は **後置** の見出しであり、
見出しより前の文は本体であることが一意に決まる。したがって制限を課さない。

```lhat
repeat^n {
    total << total + 1     # 本体。曖昧性がない
    epilog^:
        log("終了")
}
```

### 9.4 変数のスコープと寿命［確定］

繰り返し文のブロックは、**寿命の異なる2層** を持つ。

- `prolog^` および `first^` で宣言した変数
  — スコープは繰り返し文のブロック内、**寿命は繰り返し処理の全体**
- `main^` で宣言した変数 — **寿命は1回の反復**

`prolog^` が存在する目的がこれである。
繰り返しの外に変数を漏らさず、しかし寿命を繰り返し全体と揃えたい場合に使う。

`last^` と `epilog^` からは、`prolog^` と `first^` の変数が見える。
`main^` の変数は寿命が1反復であり、最後の反復の終了とともに消えているため見えない。
繰り返しをまたいで値を持ち越したい場合は `prolog^` か `first^` で宣言する。

### 9.5 適用範囲［確定］

Memo.md L215 のとおり、**すべての繰り返し構文** がこれらの節を持てる。

- `repeat^n { … }`、`repeat^{ … }`
- `repeat^while^expr { … }`、`repeat^until^expr { … }`
- `for^i from^1 to^10 { … }`（`step^` つきを含む）
- `for^k, v in^table { … }`
- `for^i := 1 while^expr next^expr { … }`、`for^i := 1 until^expr next^expr { … }`

### 9.6 綴りの別形［確定］

- `prolog^` / `prologue^`
- `epilog^` / `epilogue^`

どちらで書いてもよい。整形時にどちらへ寄せるかはフォーマッタが決める。
条件分岐の綴り（5.3）と同じ扱いである。

### 9.7 実装上の含意

#### `first^` は内側で実行し、外側へ宣言する

`first^` は最初の反復の先頭で実行されるため、実行位置は繰り返しの内側にある。
しかし 9.4 のとおり、そこで宣言された変数の寿命は繰り返し全体である。

したがってコード生成では、
**`first^` の実行は繰り返しの内側、宣言の割り付けは外側のスコープ** に分ける。
`prolog^` と同じ記憶域に、実行時期だけを遅らせて書き込む形になる。

#### `last^` は状態の保存を要する

Memo.md L210 が「`last^` があると前回の状態を保存しておく必要があるな」と
指摘しているのがこれにあたる。

繰り返しが終わるのは条件が **成立しなくなった** ときである。
その時点でループ変数は、条件を満たさなかった値になっている。

```lhat
for^i from^1 to^10 {
    last^:
        log(i)      # 10 でなければならない。11 ではない
}
```

素朴に実装すると `last^` は 11 を見る。
「次の反復があるか」は条件を評価するまで分からず、
条件式には副作用がありうるため先読みできない。

したがって **`last^` を持つ繰り返しでは、ループ変数の値を控えておき、
脱出後にその値で `last^` を実行する**。

控えを取る時期は **各反復の先頭**、条件が成立した直後とする。
反復の終了時ではない。9.8 のとおり `break^` は反復の途中での脱出であり、
そのとき妥当な最後の要素は **現在の反復の値** だからである。
終了時に控える方式では1つ前の反復の値を見てしまう。

先頭で控える方式は通常終了にも正しく働く。
条件が成立した最後の時点が、最後の反復の先頭にあたるためである。

費用は `last^` を書いた繰り返しにのみ生じる。
`last^` のない繰り返しは控えを取らない。

#### `first^` と `last^` は「1回以上実行されたか」を要する

どちらも条件が一度も成立しなければ実行されない。
`first^` は最初の反復に入った時点で実行すればよいが、
`last^` は脱出後に判定するため真偽値を1つ保持する。
これも `last^` を持つ繰り返しにのみ生じる費用である。

### 9.8 脱出時の扱い［確定・旧 S7］

| 脱出の仕方 | `last^` | `epilog^` | `finally^` |
| --- | --- | --- | --- |
| 条件が成立しなくなった（通常終了） | 一度でも成立していれば実行 | 実行 | 実行 |
| `break^` | 妥当な最後の要素があれば実行 | 実行 | 実行 |
| `return^` | 実行しない | 実行しない | 実行 |

#### 3段階の強度

3つの節は、実行される範囲が段階的に広がる関係にある。

1. **`last^`** — 条件が一度でも成立した場合のみ。最後の要素に対する締めくくり
2. **`epilog^`** — 条件の成否によらず実行。ただし繰り返しを正常に抜けた場合に限る
3. **`finally^`** — あらゆる脱出で実行される（10 章）

`break^` は繰り返しにとって正常な終了である。
やるべきことが済んだので抜ける、という意味であり、その後の処理は通常どおり続く。
したがって `last^` と `epilog^` の両方が実行される。

`return^` は関数からの離脱であり、繰り返しにとっては正常な終了ではない。
`last^` も `epilog^` も実行されず、**`finally^` だけが実行される**。

この区別は、今後 例外や誤りによる脱出を設計する際の指針にもなる。
そうした脱出は `return^` と同じ側に属し、`finally^` のみを実行する。

#### `epilog^` は finally ではない

`epilog^` は `return^` で実行されないため、他言語の `finally` には相当しない。
脱出の種類を問わない後始末が必要な場合は `finally^` を使う（10 章）。

繰り返しに `finally^` を書くこともできる。その場合 `epilog^` は
`finally^` の直前に置くことが強制される（9.2）。

#### `break^` 時に `last^` が見る値

`break^` は反復の **途中** での脱出であり、その反復では条件が成立している。
したがって妥当な最後の要素は **現在の反復の値** である。

```lhat
for^i from^1 to^10 {
    main^:
        if^ i = 5 { break^ }
    last^:
        log(i)      # 5。4 ではない
}
```

9.7 で控えを各反復の **先頭** で取ると定めたのはこのためである。

#### 実装上の含意

`last^` と `epilog^` はいずれも `return^` では実行されないため、
**繰り返しの脱出経路に閉じた処理として生成できる**。
関数からの離脱に伴う巻き戻しの機構は必要ない。それは `finally^` の仕事になる（10.4）。

#### 多段の `break^`［提案 → 要確認］

Memo.md L500 と L538 には `break^[name]` `break^[1]` という
複数の繰り返しを一度に抜ける記法がある。

上の原則を素直に適用すると次のようになる。

- **脱出先として指定された繰り返し** — 正常な終了なので `last^` と `epilog^` を実行
- **途中で抜けられる内側の繰り返し** — その繰り返しにとっては
  外側へ抜けるための離脱であり `return^` と同じ側にあたる。`finally^` のみ実行

原則からの帰結として記す。多段 `break^` の記法自体がまだ確定していないため、
記法を決める際に併せて確認する。

### 9.9 `dispose` と `defer^` は無関係［確定］

Memo.md L52 に「`for` の場合はスコープ終了で `dispose` が呼ばれる。
他言語で言う `using`」という記述があるが、
**`dispose` は繰り返し構文とは無関係である**。

`dispose` が指しているのは C# の `IDisposable` と `using` に相当する仕組みであり、
L^ では `with^`（Memo.md L371–L372）が担う。
繰り返しのスコープ終了で自動的に呼ばれるものではない。

`defer^`（Memo.md L146）については、構想が定まっていないため
本文書では扱わない。遅延評価の指定を意図したものと思われるが、
設計が固まった時点で改めて位置づける。

## 10. `finally^` 節［確定］

### 10.1 ブロック一般の機構である

`finally^` は繰り返し固有の節ではなく、**ブロックの末尾に置ける汎用の節** である。

```lhat
do^{
    r := open("data")
    process(r)
finally^:
    r.close()
}
```

置けるブロックは次のとおり。

- `do^{ … }`
- `if^` 文のブロック
- 繰り返し文のブロック（9.2 の順序に従い、`epilog^` の直後）
- `with^` のブロック
- **手続き `p^` の本体**

**関数 `f^` の本体には置けない。** 理由は 10.6 に述べる。

手続きの本体には置ける。資源や効果を扱うのは手続きであり、
`finally^` が最も必要になる場所である。

```lhat
p^{
    r := open("data")
    process(r)
finally^:
    r.close()
}
```

### 10.2 あらゆる脱出で実行される

ブロックをどのように抜けても実行される。

- 末尾まで到達した場合
- `break^` で繰り返しを抜けた場合
- `return^` で関数から離脱した場合
- 多段の `break^` で通過された場合

他言語の `finally` に相当する。

ただし L^ は例外機構を持たない（12.8）。
`finally^` の中で誤りを受け取っても、それを外へ伝播させる手段はない。
返り値も変更できない（10.5）。誤りは `finally^` の中で処理し切ることになる。

### 10.3 位置は末尾に強制

ブロックの最末尾に置く。
繰り返しの節と併用する場合の順序は 9.2 のとおりで、`finally^` が最後になる。

```text
prolog^  →  first^  →  main^  →  last^  →  epilog^  →  finally^
```

### 10.4 実装上の含意

`finally^` が関数からの離脱でも実行される以上、
**`return^` は、抜けるすべてのブロックの `finally^` を内側から順に実行してから
関数を出る** 必要がある。

`return^` については、どのブロックの内側にいるかが構文上わかるため、
抜けるブロックの `finally^` を順に呼ぶコードを位置ごとに生成すればよい。

この機構を `finally^` に集約したことにより、
繰り返しの節（`last^` `epilog^`）は繰り返しの脱出経路だけを扱えばよくなった。
**巻き戻しの担い手が1つに定まる。**

ただし静的に位置が定まらない脱出も存在する。
コルーチンの破棄がこれにあたり、実行時の機構を要する。10.8 を参照。

### 10.5 返り値を変更できない［確定］

`finally^` の中に `return^` は書けない。`finally^` は返り値を差し替えられない。

Java は `finally` から `return` できてしまい、
本来返るはずだった値が黙って置き換わる罠として知られている。C# はこれを禁じている。

L^ も禁じる。この制限は 10.6 の議論の前提にもなっている。

### 10.6 関数 `f^` の本体に置けない理由［確定・旧 S8］

#### 純粋性が壊れるからではない

`finally^` は制御構文であって効果構文ではない。
`f^` の中に置かれた `finally^` の中身は、`f^` の制限をそのまま受ける（Memo.md L54）。

- 関数しか呼べない
- 代入は局所変数に対してのみ

したがって `finally^` の中に書けるのは純粋な処理だけであり、
関数型言語としての性質を壊す手段は最初から存在しない。

#### 純粋関数では観測不能であり、意味を持たないから

`finally^` が価値を持つのは「どの経路で抜けても後始末したい」場合だが、
純粋関数には後始末すべきものが存在しない。

- 資源を開けない。`open` のような入出力は手続きであり `f^` から呼べない
- 復元すべき可変状態がない。代入先は局所変数のみ
- 局所変数はフレームとともに消える

10.5 により返り値も変更できない。
よって `f^` 内の `finally^` は **外から一切観測できない**。
意味論的に何もしないのと同じであり、書けても混乱を招くだけになる。

#### 唯一の例外は脱法関数

Memo.md L54 は「デバッグ用にログ出力などの脱法関数は用意する」としている。
これを使えば `f^` 内の `finally^` にも用途が生まれる。

ただし、純粋性の保証の外に置かれた抜け道のために言語機能を設計するのは筋が悪い。
`f^` からは除外する。

### 10.7 コルーチンとの組み合わせ［確定・旧 S9］

`yield^` を含む手続きは呼び出すとコルーチンを返す（15 章）。
コルーチンが `yield^` した後、**再開されないまま捨てられた場合も
保留中の `finally^` は実行される**。

同じ `finally^` が二度実行されることはない。
すでに実行済みのものは破棄時に再実行されない。

これは他言語でも難所として知られている箇所であり、いずれも同じ結論に至っている。

- Python のジェネレータは終了処理で `GeneratorExit` を投げて `finally` を走らせる
- Lua 5.4 は `coroutine.close` と to-be-closed 変数をこのために導入した

#### 保留中の `finally^` は内側から順に実行する

コルーチンが入れ子のブロックの内側で中断していた場合、
保留中の `finally^` は複数ある。破棄時には **内側から順に** 実行する。
通常の脱出と同じ順序である。

#### 破棄処理の中で `yield^` はできない

破棄中のコルーチンには再開を待つ相手がいない。
`finally^` の中で `yield^` することは禁じる。
Python も同じ制限を課している。

#### 破棄の契機

破棄の契機は2種類ある。両方が必要になる。

- **明示的な破棄** — 実行時期が確定する。資源の解放にはこちらが要る
- **到達不能になったコルーチンの回収** — ごみ集めが最後の受け皿となる。
  ただし実行時期は不定であり、資源が想定より長く保持されうる

明示的な破棄の手段は未決とする（S10）。

### 10.8 実行時の巻き戻し機構が必要になる［確定］

10.4 では「入れ子の関係は構文上わかるので実行時の巻き戻し表は要らない」と述べた。
**10.7 の決定により、この前提は成り立たなくなる。**

コルーチンが中断している位置は実行時にしか分からず、
したがって **どの `finally^` が保留中かも静的には決まらない**。
破棄処理は、中断位置から保留中の `finally^` を割り出せなければならない。

実現方法は2通りある。

- **PC から手続きへの対応表** — 関数ごとに「この位置で有効な `finally^`」を表に持つ。
  巻き戻しが起きない限り費用がかからない。Java や .NET の例外表と同じ仕組み
- **フレームごとの有効な `finally^` の一覧** — 実行時に積み上げる。
  Lua 5.4 の to-be-closed 変数がこの形

前者を推す。通常の実行経路に費用が乗らない。

`return^` と `break^` については、静的に位置が定まるため
10.4 のとおり呼び出しを直接生成してもよい。
巻き戻し表に一本化して重複した生成を避ける選択もあり、どちらを採るかは実装の判断とする。

**静的に位置が定まらない脱出は、コルーチンの破棄だけである。**
12.8 のとおり L^ は例外機構を持たず、誤りは値として返される。
誤りが暗黙に脱出を起こすことがないため、
この機構が扱う対象は今後も増えない。

### 10.9 `epilog^` との使い分け

- 繰り返しが正常に終わったときだけの後始末 → `epilog^`
- 脱出の種類を問わない後始末（資源の解放など） → `finally^`

繰り返し以外のブロックには `epilog^` がないため、選択の余地はない。

## 11. 演算子［確定・旧 S5］

### 11.1 演算子は関数である

Memo.md L62 のとおり、**すべての演算子は関数として扱う**。

> op^演算子 関数扱い すべての演算子は関数としての性質を満たすことを強制する、またyield不可

したがって演算子の実装は `f^` の制約を受ける。

- 関数しか呼べない
- 代入は局所変数に対してのみ
- `yield^` できない（15.3 の帰結。別の規則として書く必要はない）

利用者が定義した演算子も同じ制約を受ける。
**演算子に副作用を持たせられない。**

### 11.2 `..` は「連結」であって「文字列連結」ではない［確定］

`..` は文字列専用の演算子ではない。**一般の連結演算子** である。
文字列の連結は、そのうちの一例にすぎない。

`..` に応答できるオブジェクトであれば、いずれも正当な被演算子になる。

```lhat
"abc" .. "def"                        # 文字列の連結
def^Foo { … } .. aspect .. protocol   # 定義の合成（Memo.md L357）
```

Memo.md L357 が継承を `..` で書いているのは、
**同じ記号を別の意味に多重定義しているのではなく、同じ演算を別の型に適用している** ためである。
`def^` の値が `..` に応答し、その応答が合成になる。

### 11.3 正当性は意味解析で判定する［確定］

`x .. y` が正当かどうかは、**型検査の段階で決まる**。

- 構文解析では判定しない。`..` は単なる二項演算子として構文木に載る
- 実行時まで持ち越さない（strict の場合）

これは 03 の段階構成と噛み合っている。
型検査が独立した段として存在するため、
「この型は `..` に応答するか」をそこで問える。

判定は **構造的** に行う。Memo.md L364–L365 のとおり
プロトタイプベースかつダックタイピングであり、静的型検査も同じ方針を採る。
名前による継承関係ではなく、`..` の実装を持つかどうかで判定する。

relaxed（03 の 3.1）では、静的に決まらない箇所が実行時の検査に落ちる。
実行時の値が型タグを持つ（03 の 2.1）ため、この検査が可能になる。

### 11.4 他の演算子も同じ枠組みに載る［提案］

`..` に固有の性質ではない。
`+` `-` `*` `/` `//` `%` `**` なども、
オブジェクトが応答できれば正当とするのが一貫している。

Memo.md L46 は数値オブジェクトが `inc()` `dec()` `add(a)` `sub(a)` を
メンバとして持つとしており、演算子とメソッドの対応が前提になっている。

どの演算子がどの名前のメソッドに対応するかは未決。
`op^` による演算子定義の記法とあわせて決める。

### 11.5 優先順位と結合性［方針確定・細部が未決 → S11］

基本方針は **主要な言語の慣習に合わせる** こととする。
以下は慣習で決まるため、個別に決定しない。

- 後置（`.` `?.` 呼び出し `[]`）が最も強い
- 単項（`!` 単項の `-`）がその次
- `* / // %` が `+ -` より強い
- 比較（`= ≠ < > ≦ ≧` `is^`）が算術より弱い
- `and^` が `or^` より強く、どちらも比較より弱い
- 二項算術は左結合

#### 慣習では決まらないもの

次の5点は、主要な言語に前例がないか、前例が割れている。

##### (1) `..` の優先順位と結合性

Lua 5.4 は `..` を **`+ -` より低く**、かつ **右結合** としている。
優先順位表の該当部分は次のとおり（低い順）。

```text
<<  >>
..
+  -
*  /  //  %
単項演算子
^
```

低く置く理由は、`"合計: " .. a + b` が `"合計: " .. (a + b)` と読まれてほしいためである。
逆であれば `("合計: " .. a) + b` になり、ほぼ常に誤りになる。
連結は行の最も外側の操作になることが多い。

右結合にする理由は、`a .. b .. c` を右から畳むと
文字列の連結で中間結果の複製が減るためである。

L^ でも文字列については同じ理屈がそのまま効く。
定義の合成（Memo.md L357）は被演算子が一次式であるため優先順位の影響を受けず、
合成が結合的である限り結合性も観測できない。

**Lua と同一とする。** `+ -` より低く、右結合。

##### (2) べき乗と単項の `-` の関係

争点はこの1つの並びに集約される。

```text
-2 ** 2      # -(2 ** 2) = -4 か、(-2) ** 2 = 4 か
```

**両者を同じ優先順位にしても解決しない。**
前置演算子と中置演算子の混在であり、結合性の指定では曖昧が残る。
どちらが先に適用されるかを決める必要がある。

数学では −2² = −(2²) = −4 である。
Python・Ruby・Fortran はいずれもこれに従い、べき乗を単項マイナスより強くする。

01 の 7.1 に記した設計動機
（数学的な見た目をした記法には数学的な意味だけを与える）に照らせば、
数学と一致させる読みを採るのが一貫する。

**べき乗を単項マイナスより強くする。** `-2 ** 2` は `-4` である。

なお `2 ** -1` は書ける。
べき乗の右側には単項式を許す、という非対称で解決される。Python の文法が同じ形をとる。

べき乗自体は **右結合** とする。`2 ** 3 ** 2` は `2 ** (3 ** 2)` であり `512` になる。
これも数学の慣習と一致する。

##### (3) 型の合併は `|` とする［確定］

Memo.md L305 は nilable の指定を `k as^number^or^nil^` と書いていた。
この記法は **撤回する**。

`or^` が型の一部（合併）と論理和の両方を意味することになり、
同じ記号が文脈によって別物になる。
優先順位をどう決めても解消しない種類の曖昧さである。

代わりに **`|` を型の合併演算子とする**。

```lhat
k as^number^|nil^
```

曖昧さが消える理由は3つある。

- **`|` は未使用だった。** Q3 でビット演算を演算子として提供しないと決めたため空いていた
- **型の文脈は構文上識別できる。** `as^` の右、`:` による型注釈、`::` の返り値型。
  いずれも構文解析器が「いま型を読んでいる」と判断できる位置にある
- **`or^` が論理和専用に戻る。** 同じ記号が文脈で別物になる状態が解消する

字句解析器は型の文脈を知らない。`|` をトークンとして返すだけであり、
それが型の合併であるかどうかは構文解析器が判断する。

`as^` 自身の優先順位は 11.6 に示す。

##### (4) `@` — 決定済み。現状は非対応

Memo.md L99 の中間値参照（`f(1 + 2 + @(a(3)), @1 + 3)`）は
**演算子ではなく構文要素として扱う**。

- `@(式)` — 中間値を捕まえる形
- `@自然数` — 捕まえた値を参照する形
- `@式` — 不正。上の2つの形以外は認めない

構文要素であるため優先順位を持たない。一次式として解析される。

ただし **この機構自体の構想が固まっていないため、現状は非対応とする**。
記法の形だけを上に記録しておき、機構が定まった時点で改めて扱う。

##### (5) 比較の連鎖

比較演算子を3項以上並べた書き方を指す。

```text
1 ≦ x ≦ 10
```

読み方が3通りありうる。

- **数学の読み** — 「1 ≦ x かつ x ≦ 10」
- **C 系の読み** — `(1 ≦ x) ≦ 10`。真偽値と数値を比較する。
  C では真偽値が整数であるため黙って通り、有名な罠になっている
- **Python の読み** — 連鎖を認め、数学と同じ意味になる

**L^ に固有の事情がある。** `≦` `≧` を採用し、
数学記法に寄せることを推奨としている（01 の 7.2）以上、
利用者が数学どおりの読みを期待する度合いが他の言語より高い。

一方で L^ には C にない安全弁がある。
連鎖を認めない場合でも `(1 ≦ x) ≦ 10` は真偽値と数値の比較になり、
**静的型検査で誤りとして報告される**。黙って通ることはない。

**連鎖を認める。** 記法の見た目と意味を一致させる方針を優先する。

意味は次のとおり。

- `a < b < c` は `(a < b) and^ (b < c)` と同じ意味を持つ
- **共有される被演算子は1度だけ評価する。** 上の `b` は2度評価されない。
  Python が同じ規則を採る。手続きの呼び出しが被演算子に現れうる以上、
  この規定がないと副作用の回数が変わる
- 連鎖できるのは比較の水準の演算子（`=` `≠` `<` `>` `≦` `≧` `is^`）とする
- 種類を混ぜた連鎖（`a < b = c`）も認める
- 連鎖全体の値は真偽値である

### 11.6 優先順位表

弱い順に並べる。

| 水準 | 演算子 | 結合性 |
| --- | --- | --- |
| 1 | `or^` | 左 |
| 2 | `and^` | 左 |
| 3 | `=` `≠` `<` `>` `≦` `≧` `is^` | 連鎖（11.5 の (5)） |
| 4 | `..` | **右** |
| 5 | `+` `-` | 左 |
| 6 | `*` `/` `//` `%` | 左 |
| 7 | `as^` | 左［提案］ |
| 8 | 単項 `!` `-` | — |
| 9 | `**` | **右** |
| 10 | 後置 `.` `?.` 呼び出し `?(` `[` `?[` | 左 |

`as^` の位置は提案である。Rust と Kotlin の `as` が二項演算子より強く
単項より弱い位置にあるのに倣った。`a + b as^T` は `a + (b as^T)` になる。

型の合併 `|` は型の文法の中でのみ現れるため、この表には載らない。
型の文法は未着手である。

#### 表に載らないもの

次は式の演算子ではないため、優先順位を持たない。

- `:=` と `<<` — 文のレベルの記法（8.3）
- `::` — シグネチャの中でのみ現れる（01 の 7.6）
- `|` — 型の文脈でのみ現れる（11.5 の (3)）
- `@(式)` と `@自然数` — 一次式の形（11.5 の (4)）
- `$` `$$` `$^` — 識別子に密着する接頭辞であり、字句の段階で1つのトークンになる
  （01 の 8 章）

## 12. `with^` と `dispose()`［確定・旧 S10］

### 12.1 記法

`with^` は **局所変数の定義だけ** を受け付ける。

```lhat
with^ r := open("data")
with^ w := create("out")
{
    copy(r, w)
}
```

定義された変数が指すオブジェクトは、**`dispose()` メソッドを持つことが求められる**。

```lhat
with^ bar := Boo()   # error : Boo は dispose を持たない
```

Memo.md L371–L372 の記述に対応する。

### 12.2 スコープ終了時に `dispose()` を呼ぶ

ブロックのスコープが終わる時点で、
`with^` で指定されたすべてのオブジェクトに対して `dispose()` を呼ぶ。

**呼ぶ順序は定義の逆順とする**［提案］。
後から定義した資源が先に定義した資源に依存している場合、
逆順でなければ解放の順序が壊れる。

### 12.3 あらゆる脱出で呼ばれる［確定］

`dispose()` は 10.2 の `finally^` と同じ強さを持つ。

- 末尾まで到達した場合
- `break^` で繰り返しを抜けた場合
- `return^` で関数から離脱した場合
- コルーチンが破棄された場合（10.7）

したがって 10.8 の巻き戻し機構を共有する。
`with^` のスコープは、その機構にとって `finally^` と同じ扱いの区間になる。

### 12.4 `finally^` との順序［提案］

同じブロックに `finally^` と `with^` の両方がある場合、
**`finally^` が先、`dispose()` が後** とする。

`with^` はブロックを外側から包む構造であり、
`finally^` はブロックの内側の最後の節だからである。

```lhat
with^ r := open("data")
{
    process(r)
finally^:
    log("処理終了")     # こちらが先
}                       # r.dispose() はこの後
```

### 12.5 `dispose()` の有無は型検査で判定する［確定］

Memo.md L372 が `error` としているとおり、
`dispose()` を持たないオブジェクトを `with^` に渡すのは誤りである。

判定は 11.3 と同じく **構造的** に行う。
`dispose()` という名前と適合する実装を持つかどうかだけを見る。
特定の型を継承しているかは問わない。

12.7 のとおり `dispose()` は誤りを返さないため、
検査の条件は **「戻り値を持たない `dispose()` を持つこと」** になる。

strict では型検査の段で報告される。
relaxed では実行時の検査に落ちる（03 の 3.1）。

### 12.6 コルーチンの破棄はこの仕組みに載る［確定］

コルーチンオブジェクトは `dispose()` を持つ。
したがって破棄の手段は2通りある。

- **明示的に呼ぶ** — `c.dispose()`
- **`with^` に渡す** — スコープ終了時に暗黙に呼ばれる

10.7 で述べた「保留中の `finally^` を実行する」処理は、
コルーチンの `dispose()` の中身にあたる。

これにより 10.7 の「明示的な破棄の手段」が定まった。
ごみ集めによる回収は、どちらも行われなかった場合の最後の受け皿として残る。

### 12.7 `dispose()` は失敗しない［確定・旧 S12］

**`dispose()` は誤りを返さない。** 戻り値を持たない。

失敗しうる後始末が必要な場合は、`flush()` や `commit()` のように
**利用者が明示的に呼ぶ別の操作** として提供する。
`dispose()` はその後に呼ばれ、失敗しない処理だけを行う。

#### 理由

自動的に呼ばれる後始末は、**誤りを返す先が構造的に存在しない位置** で走る。
巻き戻しの途中、`return^` の最中、コルーチンの回収時などである。
ここで失敗しうるようにすると、どこかで必ず握りつぶすことになる。

Zig が同じ判断をしている。`std.fs.File.close()` の戻り値は `void` であり、
閉じる操作は失敗しない。書き込みが完了したことを確認したい場合は、
閉じる前に明示的に同期を要求する。

Go は逆に `Close()` が誤りを返すが、`defer f.Close()` はそれを捨てる。
書き込み用のファイルではこれが取りこぼしになり、
検査器が警告する既知の問題として残っている。

#### 帰結

- 複数のオブジェクトを解放する途中で誤りが起きることはない。
  したがって「残りの `dispose()` を呼ぶか」という問題が生じない
- 12.5 の型検査は「`dispose()` を持つ」だけでなく
  **「戻り値を持たない `dispose()` を持つ」** を要求する

なお、実装上の欠陥による異常終了は誤りとは別の分類である。
`dispose()` が誤りを返さないことと、
`dispose()` の実装に不具合がありえないこととは別の話になる。

### 12.8 誤りは値として返す［確定］

L^ は **例外機構を持たない**。Zig や Go と同じく、
失敗しうる操作は誤りを表す値を返し、呼び出し側がそれを受け取って処理する。

この選択は本章と 10 章の設計を大きく単純にしている。

「後始末の最中に例外が飛んだらどうするか」は他言語で難所とされてきた。
C++ の `terminate`、Java の抑制された例外、Python の `__context__` は
いずれもこの問題への対処である。

**誤りが暗黙に伝播しない以上、この問題は発生しない。**
`finally^` や `dispose()` の中で失敗しうる操作を呼べば誤り値を受け取るが、
それを外へ伝播させる手段がない。`finally^` は返り値も変更できない（10.5）。
構造的に閉じている。

誤りの表現、伝播の記法、値を受け取り損ねたことの検出などは本文書の範囲を超える。
別の文書で扱う（S14）。

## 13. 型の文法［一部確定・S13］

### 13.1 シグネチャの形［確定］

関数と手続きの型は、定義と同じ記号で始め、
引数の型を並べ、`::` を置き、返り値の型を並べ、`;` で閉じる。

```text
f^引数型, … :: 返り値型, … ;
p^引数型, … :: 返り値型, … ;
```

```lhat
p^number^, number^ :: number^, number^ ;
```

これは「`number^` を2つ受け取り、`number^` を2つ返す手続き」を表す。

02 の 6 章に述べた原則「開いた構造は `;` が閉じる」にそのまま従っている。

Memo.md L304–L308 は区切りを `:` と書いているが、これは撤回する。理由は 13.6 の (1)。

### 13.2 引数と返り値が空の場合［確定］

`::` は省略できない。空の側は何も書かない。

```lhat
p^number^, number^ :: ;      # 返り値なし
p^ :: number^, number^ ;     # 引数なし
p^ :: ;                      # どちらもなし
```

Memo.md L305–L308 に対応する。
L308 が「省略できない方が間違えなくていい」としているのに従う。

### 13.3 `;` は省略できない［確定］

シグネチャは入れ子になりうる。内側の `;` がなければ、
その後の `,` がどちらのリストに属するか決まらない。

```lhat
p^number^, p^number^ :: number^ ;, number^ :: number^ ;
```

外側は「`number^`、`p^number^::number^;`、`number^` の3つを受け取り `number^` を返す手続き」。
内側の `;` が内側のシグネチャを閉じ、続く `,` が外側のリストのものであることを確定させる。

Memo.md L428 が同じ形を書いている。
`;` は装飾ではなく、この曖昧さを消すために必要な要素である。

### 13.4 引数名と既定値は型に含まれない［提案］

定義には引数名と既定値が書ける。

```lhat
f := f^a:number^, b:number^=2 :: number^, string^ { … }
```

型はこれらを持たない。`f^number^, number^ :: number^, string^ ;` になる。

引数名と既定値は値の側の情報であり、
Memo.md L318–L323 の `f.parameters[0].name` や `.default` はそちらを参照する。

既定値を持つ手続きが、既定値を書いていない型に適合するかは未決（13.6 の (3) と併せて決める）。

### 13.5 合併は `|`［確定］

11.5 の (3) のとおり。

```lhat
k as^ number^|nil^
```

### 13.6 未決事項

#### (1) 区切りは `::` に統一する［確定］

Memo.md L304–L308 は型のシグネチャで区切りを `:` と書いていたが、
定義における返り値型は Q9 で `::` と決めてある。
同じ概念に2つの綴りがある状態だったため、**`::` に統一する**。

```lhat
f := f^a:number^, b:number^=2 :: number^, string^ { … }   # 定義
f^number^, number^ :: number^, string^ ;                   # 型
```

これにより2つの記号の役割が分かれる。

- **`:` — 名前と型を結びつける。** `a:number^` の引数注釈、
  構造的な型における `member : type`（(2) を参照）
- **`::` — 引数と返り値を区切る。** 定義でも型でも同じ

この整理は (2) の構造的な型にも効く。
そこで `member : type` を用いても `::` と衝突しない。

#### (2) オブジェクトの構造的な型 → 14.10 で確定

`table^{ dispose : p^self^ :: ; }` の形で書く。
判定は「少なくともこれらのメンバを持つ」。詳細は 14.10。

#### (3) 可変長引数

Memo.md L281 の `new^...{` に `...` が現れる。
可変長の引数を型としてどう書くかが未定。
既定値を持つ引数の扱い（13.4）も同じ項目で決める。

#### (4) yieldable な手続きの型

15 章のとおり `c^` は廃止し、`yield^` の有無から yieldable かどうかを推論する。
その情報を型にどう載せるかが未決。

Memo.md L60–L61 は「返り値の一個目が必ず継続になる」としている。

```lhat
p^number^ :: number^ ;
```

と書いたとき、これが yieldable であるかどうかを読み取る手段が要る。
返り値の羅列に継続が現れる形にするのか、
`p^` 側に印を付ける形にするのかが決まっていない。

## 14. オブジェクトモデル［一部確定・S15］

13.6 の (2) が求めていた「オブジェクトの構造的な型」を書けるようにするための土台。

### 14.1 `def^` が唯一の機構［確定］

利用者定義の型は **`def^` のみ** で作る。

Lua の metatable に相当する機構は **設けない**。
オブジェクトに委譲先を指す場を持たせ、実行時にそれを差し替える手段は提供しない。

### 14.2 委譲の連鎖は定義時に確定する［確定・重要］

**実行時にプロトタイプの連鎖を張り替えることはできない。**

これは利便性の判断ではなく、型システムからの要請である。

委譲先を実行時に差し替えられると、
**あるオブジェクトがどのメンバを持つかを型検査器が知りえない**。
11.3 と 12.5 が定めた構造的な型検査は、その時点で成立しなくなる。

Lua で `setmetatable` がいつでも呼べるのは Lua が動的型付けだからであり、
静的検査を採る L^ には持ち込めない。

したがって次が成り立つ。

- インスタンスの形とメソッド集合は、生成時に定義によって確定する
- 委譲の連鎖は `..` により **定義の時点で** 組まれる（14.5）
- 連鎖は静的に既知であり、型検査器は任意の式について構成要素を決定できる

プロトタイプ方式の利点（名前による階層を持たない、合成で組む、ダックタイピング）は
そのまま保たれる。外したのは静的解析を壊す部分だけである。

### 14.3 メソッドとフィールドを分ける［確定］

`def^` の中で、**インスタンスごとに複製される場** と
**定義ごとに1つだけ存在するもの** を分けて書く。

- フィールドの雛形 — インスタンスごとに複製される。関数・手続きは置けない
- メソッド — 定義ごとに1つ。インスタンスは参照するだけ

Lua の `__index` が存在する理由がまさにこの分離である
（メソッドは共有し、フィールドは複製する）。
L^ ではそれを暗黙の仕組みではなく、**構造として明示する**。

### 14.4 `self^` がメソッドを標識する［確定］

第一引数に `self^` を取る関数・手続きは **インスタンスメソッド** として扱う。

```lhat
methodA := p^self^ { print(self^.value1) }
```

`xxx.methodA()` と呼び出すと、`xxx` が暗黙の第一引数として渡される。
暗黙に渡したくない場合は次のように書く。

```lhat
method := foo2.methodA
method(foo2)
```

`self^` を取らないものは **静的メンバ** になる。
インスタンスか静的かを表す修飾子は要らない。シグネチャの形が決める。

インスタンスのメンバへの参照は `self^` を介して行う。
定義側のメンバへの参照は `class^` を介して行う。

### 14.5 合成は `..`、型の表示は `&`［確定］

定義の合成（継承）は連結演算子 `..` で書く。単一継承のみ。

```lhat
FooBar2 := FooBar .. def^{ … }
```

`..` を用いるのは順序に意味があるためである（Memo.md L357）。

一方、型としての表示には `&` を用いる。
型の情報は合成の順序によらないためであり、
`|`（合併、11.5 の (3)）と対になる。

- **`|`** — 合併。いずれかの型である
- **`&`** — 交差。すべての構造を備える

TypeScript が同じ2つを持つ。`&` は Q3 でビット演算を演算子から外したため空いている。

### 14.6 フィールドの雛形は `self^`［確定］

インスタンスごとに複製される場は `self^{ … }` と書く。

```lhat
FooBar := def^{
    self^{
        value1 := 0,
        value2 := "",
    },
    methodA := p^self^ { print(self^.value1) },
}
```

Memo.md L350 の `self^={ … }` に対応する。
インスタンスのメタ変数 `self^` と語が一致する。

`proto^` は採らない。
慣例では「プロトタイプ」は委譲先を指す語であり（Self、JavaScript）、
雛形の意味で用いると逆の連想を招く。

### 14.7 インスタンスは定義側のメンバも見る［確定］

Memo.md L295 のとおり、インスタンスから定義側のメンバを参照できる。

```lhat
f.classmethod()   // 合法
```

したがって **インスタンスの型は定義の構造をそのまま含む**。
`typeof^(インスタンス)` はその定義を返し、
`new^` や静的メンバがその構造に現れるのは正しい。

構造のうち `self^{ … }` の区画が「インスタンスごとに複製される部分」を示す。
共有される部分との区別は記法上そこで付く。

この帰結として、注釈に定義名を書くと **その定義の構造すべて** を要求することになる。
より緩く「必要なメンバだけ」で受けたい場合は、構造をそのまま書く（14.10）。
どちらを使うかは書き手が選ぶ。

### 14.8 数値の型は `number^` ひとつ［確定］

整数と実数を型として区別しない。どちらも `number^` である。

01 の 4.1 が整数リテラルと実数リテラルを別のトークンとしているのは
値の表現に関する区別であり、型の区別ではない。
実行時に内部表現を区別することはありうる。

Lua 5.3 以降が同じ構成を採っている。
型としては1つで、内部に整数と実数の2つの表現を持つ。

### 14.9 定義の名前は束縛から採る［確定］

`def^` は **式のままとする**。名前を伴う宣言形式にはしない。

```lhat
FooBar := def^{ … }
```

定義の右辺に `def^` 式が直接現れる場合、その名前を型の名前として採る。
それ以外の位置に現れた `def^` は無名であり、構造の記述だけが手掛かりになる。

Zig の `const Point = struct { … }` が同じ方式である。

#### 式のままにする理由

宣言形式にすると合成が書きにくくなる。

```lhat
FooBar2 := FooBar .. def^{ … }
```

`def^` が式であることが、`..` による合成を自然にしている（14.5）。
通常の記号定義との直交性も保たれる。

#### 名前は型の同一性に関与しない［重要］

名前は **表示と診断のための札** にすぎない。
型の同一性は構造で決まる（11.3）。

名前を同一性に含めると公称型付けになり、
構造的な型検査を採るという決定と衝突する。

### 14.10 構造をそのまま書く形［一部確定・S15］

13.6 の (2) が求めていたもの。`table^{ … }` の形で構造を書き下す。

```lhat
table^{ dispose : p^self^ :: ; }
```

`with^` が要求する「戻り値を持たない `dispose()` を持つ」はこれで表せる。

綴りは 13 章と 14.4 に従う。
`dispose` はインスタンスメソッドなので第一引数が `self^` であり、
返り値がないので `::` の後ろが空になる。`::` は省略できない（13.2）。

#### 判定は「少なくともこれらを持つ」［確定］

`table^{ … }` は **列挙したメンバを備えていること** を要求する。
それ以外のメンバを持っていてもよい。

「ちょうどこれらだけ」とすると、
`open()` の戻り値のように多くのメンバを持つ値が何も適合しなくなる。

#### 注釈と `rawsignature^` は同じ文法［確定］

型の情報を文字列として得る `rawsignature^` の出力は、
**注釈として書く形と同一の文法** とする。

異なる形式にすると型を書き表す言語が2つあることになり、
一方を読んで他方へ書き写せない。

この決定は具体的な適合条件を与える。

> `rawsignature^` の出力は、そのまま型注釈として解析できなければならない。

名前を展開するかどうかだけは選べる。
`Foo & table^{ … }` のように名前を残す形と、
名前を構造に開いた形の両方がありうるが、文法は同じである。

### 14.11 生成［確定］

#### 既定の `new^`

`new^` を定義しなかった場合、**引数を取らない既定の `new^`** が使える。

```lhat
blahblah := FooBar.new^()
```

`self^{ … }` 節で各メンバに初期値が定まっているので、それを複製して返す。

#### 初期化子は一部だけ書けばよい

`new^` の中では `self^{ … }` の形でフィールドを埋める。

```lhat
new^ := f^v1:number^, v2:string^ {
    return^ self^{
        value1 := v1,
        value2 := v2,
    }
}
```

**すべてのフィールドを書く必要はない。**
言及しなかったフィールドは `self^{ … }` 節の初期値になる。

`self^{ … }` は定義の本体では雛形の宣言、`new^` の中では生成の記法になる。
どちらも「インスタンスのフィールド」を指しており、語としては一貫する。

#### 未決 — 初期値の複製の深さ［S15］

既定の `new^` が雛形を複製する際、複製が浅いと
**可変な初期値がすべてのインスタンスで共有される**。

```lhat
self^{ items := {} }
```

浅い複製では、すべてのインスタンスが同一のテーブルを指すことになる。
Python の可変な既定引数と同じ問題である。

対処は2通りある。

- **深く複製する** — Memo.md L11 の `deepclone()` にあたる。
  大きな構造では費用が乗る
- **初期値を、格納された値ではなく生成のたびに評価される式として扱う** —
  Java や C# のフィールド初期化子がこの方式。共有が起きず、費用も予測しやすい

後者を推す。型の情報には影響しないため `rawsignature^` の形は変わらない。

### 14.12 同名メンバ — `override^` と `overload^`［確定］

#### 既定では誤り

合成した定義の側で、元の定義と同名のメンバを定義することは **誤り** とする。
Memo.md L297 が「警告、もしくはエラー？」として保留していた箇所を、誤りに定める。

#### `override^` — 置き換える

意図して置き換える場合は `override^` を指定する。

```lhat
Bar := Foo .. def^{
    override^
    foo := p^ { print("b") },
}
```

##### 置き換えは置換可能でなければならない［確定］

> `override^` した定義は、**元の定義の位置でそのまま使えなければならない**。
> 引数はより広く、返り値はより狭くしてよい。逆は不正。

- **引数を広げるのは正当** — `p^string^ :: ;` を `p^string^|number^ :: ;` で
  置き換えるなら、元が受けていたものはすべて受けられる
- **返り値を狭めるのは正当** — 元が `number^|nil^` を返す位置で `number^` を返すなら、
  受け手の想定を裏切らない
- **引数を狭める、返り値を広げるのは不正**

```lhat
Foo := def^{ self^{}, foo := p^ { print("a") } }

Bar := Foo .. def^{
    override^
    foo := p^x:string^ { print(x) },   # 不正。引数を空から string^ 必須へ狭めている
}
```

シグネチャの完全な一致を求める案もあるが、それでは返り値を絞る正当な置き換えまで
禁じてしまう。Java の共変な返り値、C# 9 以降の共変な返り値が認めている範囲にあたる。

##### `self^` は検査の対象外［確定］

第一引数 `self^` の型は、元の定義では合成前の型、置き換え側では合成後の型になる。
合成後の型は狭いため、上の規則を素直に当てると **すべての置き換えが不正になる**。

受け手を特別扱いするのは、この種の型システムに共通する扱いである
（いわゆる binary method 問題）。**`self^` は変性の検査から除く。**

##### なぜ制限するのか

構造的な型付けを採っているため、制限がなくても **安全ではある**。
置き換えによって構造が変われば、その定義は元の定義の部分型でなくなり、
渡そうとした場所で誤りになる。

問題は **どこで報告されるか** にある。

```lhat
Bar := Foo .. def^{ override^ foo := p^x:string^ { … } }   # ここは通ってしまう

blah := p^ f:Foo { f.foo() }
blah(barInstance)                                            # 離れたここで初めて誤りになる
```

`Foo .. def^{ … }` と書いた時点で「これは `Foo` である」と宣言している。
それが崩れたのなら **崩した場所で報告する** べきである。
01 の 10.9 や Q7 で採ったのと同じ原則にあたる。

##### 実装の費用は増えない

変性の検査には関数型どうしの部分型関係が要るが、それは別途必要になる。
14.10 の `table^{ … }` が「少なくともこれらのメンバを持つ」判定を求めており、
メンバの型を比較する仕組みはそこで作ることになる。
`override^` はそれを使うだけである。

##### 診断

引数を狭めた置き換えは、`overload^` の書き間違いであることが多い。
そのため診断では代替を示す。

```text
override^ は元の定義と置き換え可能でなければならない。
引数を狭めることはできない。
呼び出し方を増やしたい場合は overload^ を使う。
```

##### `override^` が捕まえるもの

以上より `override^` の役目は2つになる。

- **うっかり同名を定義した事故を捕まえる** — 指定がなければ誤り
- **置き換えが置換可能であることを、定義した場所で確かめる**

## 15. サブルーチンの種別［確定］

### 15.1 種別は2つ

サブルーチンは **関数 `f^`** と **手続き `p^`** の2種類とする。

Memo.md L57 が挙げていた **継続 `c^` は廃止する**。

| 種別 | 呼べる相手 | 代入 | `yield^` |
| --- | --- | --- | --- |
| `f^` 関数 | 関数のみ | 局所変数のみ | **不可** |
| `p^` 手続き | 関数と手続き | — | **可** |

### 15.2 yieldable かどうかは推論する［確定］

`yield^` を含む手続きは **yieldable** として扱う。
そのために別の記号を書く必要はない。

Memo.md L60–L61 が既に同じ結論に達している。

> 構文上は関数もしくは手続きで、yieldを呼んでるかどうかでYieldableとマークされ、
> 返り値の一個目が必ず継続になる。

`c^` という第三の記号は、`yield^` の有無から静的に分かる情報を二重に書かせていた。
`yield^` を1行足すたびに `p^` を `c^` に書き換え、
参照している型注釈もすべて直す必要が生じる。冗長な保守の負担になる。

#### 区別は消えず、記号から型へ移る［重要］

呼び出す側は「これは継続を返すのか」を知る必要があるため、
yieldable であることは **型に載る**（13.6 の (4)）。

したがって `c^` の廃止は型システムの区別をなくすものではない。
**減るのは表面の記号だけ** である。

これは情報の置き場所として正しい。
`yield^` の有無は本体を見れば分かるので記号は冗長だが、
呼び出す側からは本体が見えないので型には必要になる。

### 15.3 `f^` は `yield^` できない［確定］

**関数に `yield^` を許すと、`f^` と `p^` を分けた理由が崩れる。**

`yield^` で中断し、再開時に値を受け取るなら、
その結果は引数だけで決まらなくなる。同じ引数で呼んでも、
再開時に渡される値によって結果が変わる。

参照透過性が失われ、メモ化も並べ替えも省略もできなくなる。
`f^` の制約（関数しか呼べない、局所変数にしか代入できない）は
その性質を守るためにあり、`yield^` はその穴になる。

#### 一方向の `yield^` なら話が変わりうる［保留］

`yield^` が値を出すだけで再開時に受け取らないのであれば、
その関数は「遅延列を返す純粋関数」として説明できる。
2回呼べば独立した2つの列ができ、いずれも同じ列を生む。
Haskell の遅延リストと同じ構図であり、純粋である。

Lua の `coroutine.yield` は双方向（`resume` に渡した値が返る）。
**L^ の `yield^` をどちらにするかは未決** であり、`f^` の可否はそこに従属する。

#### 狭いほうから始める

当面は `p^` のみ許可とする。可逆性が非対称であるためである。

- 後から `f^` に広げるのは **後方互換** — 通るプログラムが増えるだけ
- 後から狭めるのは **破壊的** — 動いていたものが壊れる

### 15.4 呼び出しは伝染しない［確定］

`yield^` を含む手続きを呼んでも、**呼び出した側は中断しない**。
呼び出しはコルーチンを返すだけである。

Memo.md L60 の「返り値の一個目が必ず継続になる」がこれにあたる。

```lhat
gen := someYieldingProc(args)
```

呼び出し側が yieldable である必要はない。
この設計により、`async` と `await` を持つ言語で問題になる
**関数の色分け**（呼び出す側も同じ印を要求される連鎖）が発生しない。

Python のジェネレータが同じ構成を採っている。

### 15.5 コルーチンの生成に専用の記法は要らない［確定］

`c^` が暗黙に持つとされていた `new^`（Memo.md L57）は不要になる。
呼び出しがそのままコルーチンを返すためである。

ライブラリが担うのは Memo.md L61 の後半、
**生の継続を包んで扱いやすくする仕組み** のほうになる。

> コルーチンはこれをラップして継続を隠蔽して返り値のみ扱えるようにする仕組み

### 15.6 演算子の制約が自動的に従う

Memo.md L62 は演算子について次のように述べている。

> op^演算子 関数扱い すべての演算子は関数としての性質を満たすことを強制する、またyield不可

11.1 のとおり演算子は関数として扱われ、15.3 により関数は `yield^` できない。
**「yield 不可」は別の規則として書く必要がなく、帰結として従う。**

#### `overload^` — 呼び出し方を増やす

関数・手続きに限り、元の定義を残したまま呼び出し方を増やせる。

```lhat
Foo := def^{
    self^{},
    foo := p^ { print("a") },
}

Bar := Foo .. def^{
    overload^
    foo := p^x:string^ { print(x) },
    bar := f^ { 1 },
}
```

`Bar` のインスタンスは `foo()` と `foo("bbb")` の両方を受け付ける。

#### 多重定義の型は交差である［重要］

`Bar.foo` の型は次のとおり。

```text
p^ :: ; & p^string^ :: ;
```

**合併 `|` ではない。**
多重定義されたメンバは「引数なしでも文字列1個でも呼べる」のであり、
両方の性質を **同時に** 備える。14.5 の区別に照らせば交差である。

合併にすると「どちらか一方である」という意味になり、
`foo()` が呼べる保証が失われる。文字列を要求する側かもしれないためである。

TypeScript が多重定義を関数型の交差として扱うのも同じ理由による。

```lhat
print(Bar.rawsignature^)
```

```text
Foo & table^{ foo : p^ :: ; & p^string^ :: ;, bar : f^ :: number^ ; }
```

合成の表示にも `&` を用いる（14.5）ため、記号が一貫する。

#### 未決 — 多重定義の解決［S15］

呼び出し側でどの定義が選ばれるかの規則が未決。
引数の型が複数の候補に適合する場合の優先順位を決める必要がある。
構造的な部分型付けと組み合わさるため、単純な一致では決まらない場合がある。
