# L^ 構文仕様

構文解析器が扱う範囲、すなわちトークン列から構文木を得るまでを定義する。
トークンの定義は [01-lexical-structure.md](01-lexical-structure.md) を参照。

記法ラベル（［確定］／［提案］／［未決］）の意味は [README.md](README.md) を参照。
本文書の未決事項には `S1`, `S2`, … の番号を振る（01 の `Q` 番号とは別系統）。

**現状**: 入力形式、コマンドインタプリタモード、REPL 統合、条件分岐、
`:` 導入構文の終端、文の構成、繰り返しの節、`finally^` 節、演算子と優先順位、
`with^`、型の文法、オブジェクトモデル、サブルーチンの種別、
`for^` と `repeat^` が確定している。
未決事項は 7 章にまとめてある。**未決は S22（`_^`）と S23（8.8 の先回り）。**

## 1. 2つの入力形式

L^ の処理系は2種類の入力を受け付ける。両者は文法規則が異なるのではなく、
**入力チャネルの性質が異なる**。この区別が本章以降のほぼすべての根拠になる。

### 1.1 通常形式 — 自由形式ソース［確定］

ソースファイルに書かれるコード。空白と改行に文法的な意味はない
（01 の 9.2、Q1）。唯一の例外は呼び出し括弧の規則（01 の 10.9）。

### 1.2 コマンドインタプリタモード — 行指向入力［確定］

対話プロンプトなどから1行ずつ受け取る入力。

**このモードを選ぶのはホストアプリケーションであり、
L^ ランタイムを生成する時点で指定する。**
ソースコード中からこのモードへ遷移する構文は存在しない。

Memo.md L116–L117 の `>> foo 1 2 3` に現れる `>>` は
コマンドプロンプトを表す表記であって構文ではない。詳細は 01 の 7.7 を参照。

## 2. 並置呼び出し

括弧を伴わない手続き呼び出し。

```text
foo 1 2 3
```

### 2.1 通常形式では構文エラー［確定］

通常形式のソースにこれを書くことはできない。

理由は **引数リストの終端が決まらない** ことにある。
01 の Q1 で改行に文法的意味を持たせないと決めた以上、次の2行は
ひと続きのトークン列でしかない。

```text
foo 1 2 3
bar 4 5
```

これを `foo(1,2,3)` と `bar(4,5)` に切る根拠がない。
`foo(1, 2, 3, bar, 4, 5)` も等しく合法な読みである。

シェル・Tcl・Ruby・Nim・Perl の並置呼び出しが成立しているのは、
いずれも改行を文の終端として扱っているからである。例外はない。

#### 前処理による読み替えも解決にならない

「構文解析器の手前で `foo 1 2 3` を `foo(1, 2, 3)` に書き換える」方式も採らない。
その前処理器は行の切れ目を正しく判定するために、次をすべて扱う必要がある。

- 複数行文字列の内部の改行
- 括弧内で折り返された改行
- ブロックコメント `#[ … ]#` をまたぐ改行
- `"""` 行末文字列

つまり前処理器が完全な字句解析器になる。
そこまで作るなら、それは改行に敏感な構文解析器を1層余計にして作ったのと同じであり、
層が増えた分だけ悪い。

#### この決定が買っているもの

通常形式で並置呼び出しを許さないことにより、
**2つのモードの差が文レベルの解析規則1箇所に閉じる**。
式の解析にも字句解析にもモードが波及しない。

仮に通常形式でも並置を許すと、`foo -1` が
「引数 `-1` の呼び出し」なのか「`foo` から `1` を引く式」なのかが
常に問題になり続ける。Ruby と Nim はこれを空白の有無で解決しているが、
それは改行敏感よりさらに強い制約であり、01 の Q1 の方針から最も遠い。

### 2.2 コマンドモードで成立する理由［確定］

コマンドモードで並置呼び出しが成立するのは、**文法が改行に敏感だからではない**。
入力チャネルそのものが行指向であり、
プロンプトに打ち込まれた1行は Enter の時点で入力単位が確定しているためである。
構文解析器は改行を解釈しているのではなく、そもそも1行しか渡されていない。

2つのモードの差は「規則の違い」ではなく
**「行指向の入力チャネル」対「自由形式のソースファイル」** の違いである。

### 2.3 コマンド形式が成立する条件［確定］

コマンドモードであっても、入力が常に並置呼び出しとして解釈されるわけではない。

> 並置呼び出しとして解釈するのは、先頭が識別子であり、かつ
> **その次のトークンが式を継続できないもの** である場合に限る。

この条件がないと、プロンプトでの算術が壊れる。
`x - 1` の先頭は識別子なので、無条件に並置とみなすと `x(-1)` になってしまう。

| 入力 | 次のトークン | 解釈 |
| --- | --- | --- |
| `print "done"` | 文字列 | 並置 → `print("done")` |
| `ls` | 入力終端 | 並置 → `ls()` |
| `foo 1 2 3` | 整数 | 並置 → `foo(1, 2, 3)` |
| `foo {a := 1}` | `{`（テーブルリテラル） | 並置 → `foo({a := 1})` |
| `foo !x` | `!`（前置のみ） | 並置 → `foo(!x)` |
| `x - 1` | `-`（二項になれる） | 通常 → 減算 |
| `x.y` | `.`（継続） | 通常 → メンバアクセス |
| `x := 1` | `:=`（継続） | 通常 → 再代入（8.6） |
| `foo(1)` | `(`（後置） | 通常 → 呼び出し |

`foo -1` は減算になる。呼び出したい場合は `foo (-1)` と書く。
Haskell と同じ割り切りであり、空白の有無に意味を持たせずに済む。

**この判定に使う「式を継続できるトークンか」の分類は、
01 の 10.9 が用いているものと同一である。** 分類表は1つで両方に効く。

### 2.4 呼び出し括弧は並置より強く結合する［確定］

`foo(1, 2, 3)` はコマンドモードでも通常形式でも同じ結果になる。

`(` は 01 の 10.9 により（直前に改行がないので）呼び出し括弧である。
したがってコマンド形式として解釈しても `foo(1,2,3)` 全体が1個の primary となり、
並置引数は0個になる。両形式で同じ構文木に落ちる。

10.9 の規則は空白ではなく **改行だけ** を見ているため、
`foo (1, 2, 3)` とスペースを空けても結果は変わらない。
Ruby のような空白敏感にはならない。

### 2.5 値を名指すハット識別子は文を始められる［確定］

呼び出しの後に何が来たかを 2.3 の分類だけで決めると、
`self^` のような語が **前の呼び出しの引数として飲み込まれる**。

```lhat
step := p^self^ {
    self^.a()
    self^.n := 1     # ここが self^.a(self^.n := 1) と読まれてはならない
}
```

ハット識別子の大半は構文の語（`if^` `let^` `for^` …）だが、
いくつかは **値を名指す**。値を名指すものは通常の名前と同じであり、
8.3 のとおり呼び出しも代入もそこから始まる。したがって

> **値を名指すハット識別子は、文を始められるものとして扱う。**

現在この扱いを受けるのは次の4つである。

- `L^` — 機械そのもの（05 の 8.6）
- `this^` — 自分自身の呼び出し（15.10）
- `self^` — 受け手（14.4）
- `it^` — 焦点（16.2）
- `super^` — `override^` が置き換えた側（14.12改）

## 3. REPL 統合

コマンドモードのプロンプトに、通常形式で書かれた複数行のコード片を
貼り付けて実行できる必要がある。

### 3.1 未完入力の検出［確定］

実現の鍵は、**構文エラーと「入力が途中で終わっただけ」を区別する** ことにある。
Python・Node・irb・GHCi・Lua の REPL がいずれも行っている。

Lua はエラーメッセージの末尾が `<eof>` かどうかを文字列で判定しているが、
この実装は真似しない。**専用のエラー種別として最初から区別して返す。**
後から入れると面倒だが、最初から設計に入れておけば追加コストはほぼない。

字句解析器の側で「入力を待て」を意味するのは次の2つだけであり、
これらは既に実装されている。残りはすべて本物のエラーである。

- `LHAT_ERR_UNTERMINATED_STRING` — 複数行文字列の途中
- `LHAT_ERR_UNTERMINATED_BLOCK_COMMENT` — `#[ … ]#` の途中

数値リテラルなどは行をまたげないため、未完にはならない。

構文解析器の側も同じ印を立てる。**入力の終端で誤りを報告したなら未完である**。
閉じられていない `{` も、`1 +` で終わった式も、この形で捕まる。
括弧の数を読み手が数える必要はない。

未完の入力に付いた診断は **表示しない**。
次に何が来るかについて、その診断は何も述べていないためである。

### 3.2 解析の手順［確定］

1. 入力をバッファに追加する
2. 入力が対話的な1行であり、2.3 の条件を満たすなら **コマンド形式** として解析する
3. そうでなければ **通常形式** として解析する
4. 成功したら実行し、バッファを空にする
5. 失敗の原因が「未完」なら、エラーを出さずに次の行を待つ
6. それ以外の失敗は構文エラーとして報告する

貼り付けられた複数行はこう流れる。

```text
let^ Counter = {     # コマンド形式不成立（let^ で始まる） → 通常形式 → 未完 → 継続
    value := 0,       # 継続
}                     # 完成 → 実行
```

プロンプトに打ち込まれた1行はこう流れる。

```text
print "done"          # 次が文字列 → コマンド形式 → print("done")
```

### 3.3 貼り付けの扱い［提案］

入力が複数行の塊として届いた場合は、2 を飛ばして **通常形式として一括解析する**。

行単位で処理すると、継続行が孤立する。

```text
foo
  .bar()
```

1行目の `foo` は単体で成立してしまうため、コマンド形式なら `foo()` を即実行し、
2行目の `.bar()` が行き場を失う。
貼り付けたコードがファイルに書いた場合と違う動作をすることになり、
01 の 10.9 で潰したはずの問題が REPL 経由で復活する。

貼り付け全体を1単位として受け取れれば、通常形式としてまとめて解析でき、
ファイルと同じ結果が得られる。

**これを実現する手段（端末の bracketed paste など）はホストの責務であり、
言語仕様の範囲外である。** 言語側は 4 章の API を提供するにとどまる。

### 3.4 ファイルと REPL の一致［確定］

01 の 10.9 の決定は、ここで予期していなかった利得を生んでいる。

Lua では次のコードがファイルと REPL で異なる意味になる。

```lua
a = b
(f or g)()
```

- ファイル → `a = b(f or g)()` という1文
- REPL → 1行目が単体で完結するため実行され、2行目が別に実行される

L^ は「改行直後の `(` は呼び出し括弧にならない」と決めているため、
ファイルでも2文になり、REPL の逐次実行と一致する。
**貼り付けたコードがファイルに書いたときと同じ動作をすることが保証される。**

## 4. ランタイムに必要な API［提案］

ホストが 3 章の手順を組めるように、ランタイムは次を提供する。

- 断片を通常形式として解析するエントリポイント（1行でも複数行でもよい）
- 断片をコマンド形式として解析するエントリポイント
- **未完を示す専用のエラー種別** — 3.1 のとおり文字列判定に頼らない

モードの選択、行の蓄積、プロンプトの切り替え、貼り付けの検出はいずれも
ホスト側の責務であり、ランタイムはモードを状態として保持しない。

## 5. 条件分岐［確定・旧 S1］

### 5.1 if 式の推奨形

```text
if^expr: expr el^expr: expr el^: expr ;
```

`el^` ひとつで「そうでなくもし」と「そうでなければ」の両方を表す。
両者は **条件式の有無** で区別する。

- `el^expr:` — 条件つき。他言語の else if にあたる
- `el^:` — 条件なし。他言語の else にあたる

構文解析器は `el^` の次のトークンが `:` かどうかを見るだけでよく、
1トークンの先読みで足りる。

Memo.md L182 の推奨形 `if^expr: or^expr: or^: ;` は撤回する。
`or^` を節マーカーに使うと論理和と衝突するため（01 の Q8）。
節の構造はそのまま、マーカーだけを `or^` から `el^` に替えた形になっている。

### 5.2 if 文の推奨形

```text
if^expr {
    elseif^expr:
        stats
    else^:
        stats
}
```

Memo.md L177 のとおり。文の側では短縮形を使わない。

短縮形 `ei^` `el^` を if 式に限るのは Memo.md L623–L624 の判断による。
複数行にわたる文では長い綴りのほうが読みやすく、
1行に収める式では短いほうがよい。

#### どちらの形かは条件の後で分かる［確定・5.2改］

`if^` の次に来るのは条件であり、**文か式かを決めるのはその後ろのトークン**である。

- `{` — 5.2 の文
- `:` — 5.1 の式

したがって構文解析器は、文の位置でも **まず条件を読み、それから決める**。
先読みは増えない。条件は元々読む必要があるものだからである。

同じことが `for^` にも当てはまる。16.1 のとおり `for^` は続く節の形を採るので、
`for^ … if^` と 17 章の `when^` 節群にも文と式の2つがある。
どちらかは **駆動節を読み終えてから** 分かる。

##### 式が文の位置に来てよいかは 8.2 が決める［重要］

**5.1 と 5.2 の区別とは別の問題である。** 混ぜると、
文の位置に来た if 式が「`{` が要る」と拒まれることになる。

```lhat
> if^ true^: 1 el^: 2;                    # プロンプトでは 8.2 により答えになる
1
> for^ n := 5 if^ n > 1: n el^: 0 ;       # for^ も同じ
5
> for^ 2: when^ 1: "x" other^: "y" ;      # 17 章のマッチも同じ
"y"
```

ファイルの中では 8.2 のとおり「裸の式は文にならない」誤りになる。
そこで式形を書いた書き手は文形を意図している。

### 5.3 許容する綴り［確定］

Memo.md L156–L177 は「全部許していいでしょう」としており、これに従う。

- 条件つき: `elseif^` `else^if^` `elsif^` `elif^` `ei^` `el^expr:`
- 条件なし: `else^` `el^`

`or^` は **論理和専用** であり、節マーカーとしては使えない（01 の Q8）。

整形時にどの綴りへ寄せるかはフォーマッタが決める。
字句解析器も構文解析器も、綴りの違いを情報として保持する必要はない。

## 6. `:` 導入構文の終端［確定・旧 S2］

`:` で本体を導入する構文は、**`;` で明示的に閉じる**。省略できない。

### 6.1 関数・手続き定義式

Memo.md L148–L151 が挙げていた次の形は **不正** とする。

```text
foo(f^:x, y)      # 誤り。; がない
```

`x, y` が関数の返り値リストなのか、`y` が `foo` の第2引数なのかが決まらない。
どちらの意図であれ `;` を書く。

```text
foo(f^:x;, y)     # 返り値は x。y は foo の第2引数
foo(f^:x, y;)     # 返り値は x, y。foo の引数は1個
```

`;` を省略可能にして「閉じられていなければ最後まで」と定めることもできるが、
その規則では読み手が2つの解釈を毎回突き合わせる必要が残る。必須とする。

### 6.2 if 式

5.1 のとおり `;` で閉じる。

```text
let^ r = if^a: 1 el^: 2 ;
```

### 6.3 共通する原則

この2つは同じ問題の別の現れである。

> `:` は開いた構造を導入する。開いたものは `;` で閉じる。

01 の 9.2 で「`;` は改行方針とは独立に必要」と切り出したのがこれにあたる。
改行に意味を持たせても解決しない。1行に書いても同じく決まらないためである。

`{ … }` で本体を囲む形（if 文、`do^{}`、繰り返し）は
閉じ括弧が終端になるため `;` を要しない。

## 8. 文の構成［確定・旧 S3］

### 8.1 何が問題なのか

「文として何を許すか」は一見どうでもよい分類の話に見えるが、
**01 の 10.9 が扱う曖昧性の範囲を直接決める** ため、先に固める必要がある。

10.9 の規則は「継続にも文頭にもなれるトークン」が改行直後に現れたときに、
人間の読みと構文解析器の読みが食い違う、という問題への対処だった。
そして対象を `(` だけに絞れたのは、
**他のトークンが文頭になれないと判断したから** である。

つまり、文になれる形を増やすと 10.9 の対象トークンが増える。
逆に絞れば増えない。両者は同じ問題の表と裏である。

### 8.2 裸の式は文にしない［確定］

`a + b` のように値を計算するだけで何も起こさない式は、
ソースファイル中では文として認めない。

理由は 8.1 のとおり。裸の式を文として認めると、
`+` `-` `*` `..` などあらゆる二項演算子が文頭に立てるようになり、
改行直後に現れたときの曖昧性が全演算子に広がる。

REPL は別扱いとする。プロンプトで `2 + 3` を評価できないのは論外なので、
**対話入力の最上位でのみ裸の式を受理する**。

もう1つの例外が 15.12 である。**`f^` の本体が式1つだけのとき**、
その式は返り値になる。どちらの例外でも
「前に文が無い、または前の文が並置と区別できる」ため、上の曖昧さは生じない。
Python が同じ扱いをしている（ファイル中では合法だが、REPL では値が表示される）。
L^ はファイル中では不正とする点だけが異なる。

#### 裸の式は式文として読む［確定・旧「`return^` として読む」］

対話入力の最上位に置かれた裸の式は、
**呼び出し文と同じ節点になる**（`LHAT_NODE_CALL_STMT`）。
新しい節点も新しい規則も要らない。

そのうち **最後の文の値が入力の答えになる**（03 の 4.3）。

当初は `return^ 式` と同じ構文木にすると定めていたが、**撤回する**。
`return^` として読むと次の2つが壊れる。

- **後続の文が走らない**。`bump()` を2度書いて `n` を見る、
  といった対話の基本形が最初の1つで止まる
- **答えを持たない呼び出しを文にできない**。
  `bump()` は値を返さないが、文としては正当である

##### 区切り記号がないので、裸の式は文の末尾に寄る

L^ には文の区切り記号がなく、2.1 は
「次のトークンが文を始められないなら並置である」と定めている。
したがって裸の式の直後に **式でしか始まらない行** が来ると並置の誤りになる。

```lhat
2 + 2
1 + 1        # 誤り。'2 + 2 1' の並置と区別できない
```

プロンプトでは1行が1つの入力なので、この形は生じない。
複数行にまたがる入力でも、完成した行はその時点で走るため同じである。

##### 最上位に限る

`do^{ … }` の中や手続きの本体では、対話入力でも裸の式は文にならない。
8.2 の理由（あらゆる二項演算子が文頭に立てるようになる）は
入れ子の中でもそのまま当てはまるためである。

##### `x = 1` はプロンプトでは比較である

8.6 は `x = 1` を「`:=` の書き間違い」として専用の診断を出すが、
それは **ファイルでの話** である。ファイルではその行は誤りにしかなりえない。

プロンプトでは `x = 1` は **等値比較を評価している** と読む。
そう読まなければ、対話で等値を確かめる手段がなくなる。
値が真偽値として返るので、代入のつもりで書いた場合もその場で分かる。

### 8.3 文になれる形［確定］

- ハット識別子で始まるもの — 制御構文、`return^`、`break^`、`yield^`、
  `do^{}`、`with^`、`let^` など。すべて先頭が `HAT_IDENT` なので判別が容易
- 定義 — `let^ x = expr`（8.6）
- 再代入 — `x := expr`（8.6）
- 呼び出し — `foo(…)`、`foo.bar()`、`foo?.baz()`

いずれも先頭は **ハット識別子・識別子・名前リテラル・`$` 指定子・`(`** のどれかになる。
このうち式を継続できるのは `(` だけであり、それが 10.9 の規則の対象である。

#### 値であるハット識別子も文を始める［確定］

ハット識別子はほとんどが構文の語だが、**値を名指すものが2つある**。

- `L^` — 機械そのもののテーブル（05 の 8.6）
- `this^` — いま実行しているサブルーチン（15.10）

この2つを通した呼び出しは、名前を通した呼び出しと同じく文である。
したがって 2.1 の並置判定でも **文を始められる側** に数える。

```lhat
foo()
L^.collectgarbage()      # 'foo() L^' の並置ではない
```

数えなければ、直前が呼び出し文だったときに並置と読まれてしまう。

### 8.4 後置形を撤回した理由

当初 Q2 は再代入を後置形 `expr -> x` と定めていた。
この形は **文の先頭に任意の式が来ることを許す**。

01 の 10.9 には次のように書いた。

> `-` — 「負数だけの文」は意味を持たないため文頭になれない

**この判断は誤りである。** 「負数だけの文」は確かに無意味だが、
負数を代入する文は無意味ではない。

```text
update()
-1 -> counter
```

`-1 -> counter` は「counter に -1 を代入する」という自然な文である。
しかし改行に意味がないため、この2行は次のように解釈される。

```text
update() - 1 -> counter
```

これはソース式が `update() - 1`、対象が `counter` の **完全に妥当な再代入文** である。
構文エラーにならないため、誤読は黙って通る。
10.9 で潰したはずの Lua 型の問題が、`-` について残っている。

該当するのは `-` のみである。`!` `@` `$` は前置専用で式を継続できず、
識別子・数値・文字列・名前リテラルも式を継続できない
（並置呼び出しを禁じたため、2.1）。

### 8.4.1 演算子の綴りを替えても解決しない

再代入の記号を `->` から、未使用の `>>` に替える案を検討した。
`->` が `-` で始まることが原因なら、綴りを替えれば済むはずである。

**原因はそこではない。** 曖昧なのは文頭に置かれた **ソース式 `-1` の `-`** であり、
演算子の綴りとは無関係である。

```text
update()
-1 >> counter     # 行頭の - は依然として二項か単項か決まらない
```

原因は後置形そのものにある。
後置形は文が任意の式で始まることを許すため、
その式が `-` で始まる可能性を構造的に排除できない。

対象を先に置く形であれば文が識別子で始まり、
識別子は式を継続できないため曖昧性が生じない。

なお、前置形を **追加** するだけでは足りない。
後置形が併存する限り、後置で書かれた文に対して規則が必要になる。
後置形を廃止して初めて解消する。

### 8.5 決定 — 前置形にし、規則を増やさない［確定］

> **再代入は対象を先に書く。後置形は廃止する。**

当初この節は綴りを `target << value` と定めていた。
8.6 で再代入が `:=` になったため綴りは変わったが、
**本節が問題を消している理由は綴りではなく位置にある**（8.4.1）。
以下の記述はそのまま成り立つ。

これにより文の先頭は常に対象（識別子・名前リテラル・`$` 指定子）から始まり、
`-` が文頭に立つことがなくなる。8.4 の誤読は **構造的に発生しなくなる**。

```text
update()
let^ counter = -1     # 2文。counter は式を継続できないので誤読しようがない
```

#### 検討して採らなかった案

- **改行直後の `-` を単項に固定する。** 10.9 の考え方を `-` にも広げる案。
  人間の読みには最も近いが、改行に意味を持つトークンが2つに増える。
  行頭に二項演算子を置く整形が `-` についてのみ書けなくなり、
  `+` には単項の用法がないため `-` だけが例外的にふるまう不統一も生じる
- **文が `-` で始まることを禁じ、`(-1) -> counter` と書かせる。**
  規則は増えないが、負数の代入という自然な記述に括弧を強いる
- **再代入の記号を `>>` に替える。** 8.4.1 のとおり、
  原因が演算子の綴りではないため何も解決しない

いずれも 8.4 の問題を **回避** する案であり、
前置形への変更だけが問題そのものを **消している**。

#### 波及

- **改行に意味を持つ規則は 10.9 のひとつに保たれた。**
  「改行は文法的に無意味」という Q1 の原則が、例外1件のまま維持される
- 8.2 と 8.3 は変更を受けない
- `->` はトークンとして認識し続ける。
  Memo.md にも本文書の旧版にも後置形の記述があるため、
  構文解析器が「後置形は撤回された」と指摘できるようにする

### 8.6 定義は `let^`、再代入は `:=`［確定］

#### 何が問題だったのか

定義を `:=` と書き、入れ子のスコープで同名の定義を許すと、
**再代入のつもりで定義を書いてしまう**。

```text
i := 0            # 旧仕様。:= が定義だった
if^ foo() {
    i := 1        # 内側に新しい i ができる。外の i は 0 のまま
}
```

これは黙って通る。Go の `:=` で実際に起きている事故である。

入れ子の同名定義を禁じれば消えるが、
**作業変数の名前をいちいち一意にする手間を嫌って許可した**（Memo.md）。
そこは変えない。`=` を比較専用とした決定（01 の Q3）も変えない。

原因は **危険なほうを短く書けること** にある。

#### 決定

> **新しい名前を作るのは `let^`。`:=` は再代入。**

```lhat
let^ i = 0
if^ foo() {
    i := 1        # 再代入。外の i が 1 になる
}
```

遮蔽したい場合は `let^` を書く。**意図が字面に出る。**

```lhat
if^ foo() {
    let^ i = 1    # 意図した遮蔽
}
```

Rust の `let`、Swift の `var`/`let`、JavaScript の `let` が同じ配置である。
Go だけが定義を短い記号に割り当てており、事故が知られているのもそこである。

#### 許容する形［確定］

```lhat
let^ x = 0                 # 推奨形
let^ x := 0                # 冗長だが許容
let^ x : number^ = 0       # 推奨形
let^ x : number^ := 0      # 許容
```

`let^` があれば `=` でも `:=` でも曖昧にならない。

#### 波括弧の中も導入である［確定・14.14改］

テーブルリテラルの要素と `self^{ … }` のフィールドは **導入** なので、
同じ理由で `=` と書く。

```lhat
let^ t = { a = 0, b = "x" }
let^ P = def^{ self^{ w = 5 } }
```

ここでは `=` が比較にならない。比較が要るなら括弧で囲む（14.14）。
`:=` も従来どおり読む。
5.3 の `elseif^` / `el^` と同じ多綴りの関係であり、整形はフォーマッタが決める。

`let^` は **値を必ず伴う**。`let^ x : number^` のような宣言だけの形は認めない
（8.7）。

#### なぜ `=` を許せるのか［重要］

01 の 7.1 は `=` を比較と定め、代入ではないことを強調している。
それでも `let^ x = 0` が書けるのは、**式が現れえない位置だから** である。

> **`=` は式が現れえない位置でだけ使える。**

`let^ 名前` の直後には式が来ない。引数名の直後も同じで、
13.4 の既定値 `p^ x:number^ = 1` が既にこの形である。新しい用法ではない。

逆に、式が現れうる位置では `=` を使えない。

```lhat
{ a = 1 }              # 「メンバ a に 1」か「位置指定の要素 a = 1」か決まらない
for^ i = 1 to^ 10      # 焦点が比較式 i = 1 とも読める（16.2）
with^ h = open(p)      # 同じ
```

テーブルリテラルは位置指定の要素を許し（10.7）、
`for^` は名前のない焦点を許す（16.2）。
どちらも `=` の左に式が立ちうるため、真の曖昧性になる。**これらは `:=` のままとする。**

#### 導入子が名前を作る［確定］

`:=` が定義になるか再代入になるかは、**前に導入子があるか** で決まる。

| 形 | 導入子 | 意味 |
| --- | --- | --- |
| `let^ x = 0` | `let^` | 定義 |
| `x := 1` | なし | 再代入 |
| `{ a := 1 }` | `{` | メンバの定義 |
| `for^ i := 1 to^ 10` | `for^` | 焦点の定義（16.3） |
| `with^ h := open(p)` | `with^` | 束縛の定義（12 章） |

> **`:=` は値を与える。名前を作るかどうかは導入子が決める。**

文の位置には導入子がないため、**文の `:=` は必ず再代入になる**。
冒頭の事故が構造的に起きなくなるのはこのためである。

#### `x = 1` は文にならない［確定］

8.2 により裸の式は文ではないので、C 系の習慣で書いた `x = 1` は誤りになる。
黙って通ることはない。診断では両方の意図を示す。

```text
= は比較です。値を入れるなら x := 1、新しい名前を作るなら let^ x = 0 と書きます。
```

#### `<<` は撤回［確定］

再代入が `:=` になったため、`<<` は同じ意味の2つ目の綴りになる。**撤回する。**

`->`（8.5 の波及）と同じく、トークンとしては認識し続け、
構文解析器が代わりを示せるようにする。

### 8.7 名前が見える範囲［確定］

#### スコープ全体で見える

> **`let^` が作る名前は、それを含むスコープ全体で見える。
> 書かれた位置より前でも見える。**

これは相互再帰のために要る。

```lhat
let^ isEven = f^ n:number^ -> bool^ {
    if^ n = 0 { return^ true^ }
    return^ isOdd(n - 1)          # まだ書かれていない
}
let^ isOdd = f^ n:number^ -> bool^ {
    if^ n = 0 { return^ false^ }
    return^ isEven(n - 1)
}
```

03 の 3.4 が既にこれを前提にしている。
そこに挙がっている `f := f^{ … return^ f() … }` は自身を呼んでおり、
**定義される前に名前が見えなければ書けない**。相互再帰はその一段外側にすぎない。

Go がパッケージの水準で、Rust が全面的に同じ規則を採る。

#### 評価の前に読むことはできない

見えることと、その時点で値があることは別である。

```lhat
let^ x = y + 1     # 誤り。y の定義はまだ実行されていない
let^ y = 2
```

**判定は静的にできる。** ある名前を、その `let^` より前で、
かつ **遅延して実行される本体の外** で読んでいれば誤りとする。

関数・手続きの本体は定義の時点では実行されないため、この規則に触れない。
上の相互再帰が通り、`let^ x = y + 1` が通らないのはこの違いによる。

#### 前方宣言は設けない［確定］

値を伴わない `let^ x : number^` は認めない。

前方宣言で相互再帰を解く案（C や Lua の `local f`）もあるが、
**「全経路で代入されてから読んでいるか」の解析が必要になる**。
本節の可視性の規則はそれなしで同じ問題を解いている。

分岐ごとに違う値を入れたい場合は if 式（5.1）を使う。

```lhat
let^ x = if^ foo(): 1 el^: 2 ;
```

#### 同じスコープでの再定義は誤り

同じスコープで同じ名前を2度 `let^` するのは誤りとする。
内側のスコープでの `let^` は遮蔽であり、8.6 のとおり認める。

### 8.8 `let^` はメンバも導入する［確定］

> **`let^ a.b.c = v` は、`a` と `b` が辿るテーブルの中に `c` を導入する。
> 途中のテーブルは、無ければ作る。**

#### これは 8.6 の欠けていた半分である

8.6 は `let^` を導入、`:=` を再代入と定めた。
**メンバに対してはその片方しか存在しなかった。**

```lhat
let^ t = { a := 1 }
t.b := 2          # 誤り。b というメンバがない
```

`:=` は既にあるメンバしか書けない。
一方で **メンバを増やす手段が言語に1つも無かった**。
実行時には可能であり、拒んでいたのは型検査だけである。

したがって規則は 8.6 をそのままメンバへ広げたものになる。

- `t.b := v` — **既にある** メンバを書き換える
- `let^ t.b = v` — メンバを **導入する**

新しい概念ではない。ドット付きの多段はこの一般形にすぎない。

#### 途中の段は辿り、無ければ作る

```lhat
let^ a.b.c = 1        # a も b も無い → a = { b := { c := 1 } }
let^ a.b.d = 2        # a も b もある → a.b に d が増える
let^ a.z   = 9        # a はある → a に z が増える
```

**2つ目が1つ目を潰さない。** 同じテーブルを通る2つの経路は合流する。

#### 末尾は新しい名前である

末尾の段は **導入** なので、既にあれば 8.7 の再定義の誤りになる。

```lhat
let^ a.b = 1
let^ a.b = 2          # 誤り。書き換えるなら a.b := 2
```

#### 根は遮蔽しない

根の名前が外側のスコープに既にあれば、**それを辿る**。
新しい局所を作って遮蔽することはしない。
`let^ a.b = 1` が言っているのは「`b` がどこに入るか」であって、`a` については何も言っていない。

根がどこにも無いときに限り、それを含むスコープに新しい名前として作る。

#### 途中の段はテーブルでなければならない

テーブルでないものが既にあれば誤りとする。

```lhat
let^ a = 1
let^ a.b = 2          # 誤り。a は number^ であってテーブルではない
```

#### `def^` のインスタンスには足せない［確定］

14 章 は `def^` が **そのインスタンスの持ち物を決める** と定めている。
後からメンバを足せると、その保証が崩れる。

```lhat
let^ P = def^{ self^{ x := 0 } }
let^ p = P.new^()
let^ p.y = 1          # 誤り
```

定義そのものにも足せない。14.12 の多重定義はそのための記法を別に持っている。

判定は型に印を持たせて行う。11.3 のとおり **同一性は構造で決まる** ため、
この印は適合の判定には一切参加しない。`is_definition`（14.5 が合成の判別に使う）
と同じ位置づけであり、**構造が何であるかではなく、何が作ったかを記録している**。

したがって構造的な型注釈を経由すれば抜けられる。

```lhat
let^ q : t^{ x : number^ } = P.new^()
let^ q.y = 1          # 通る。注釈は「その形のテーブル」としか言っていない
```

これは 11.3 を採ったことの帰結であり、本節に固有の穴ではない。

#### 型は後から増える

`let^ a.z = 9` は `a` の型を増やす。
先に `let^ t = a` していれば、`t` の型はその時点のままである。

**不健全ではない。** 構造的型付けの幅部分型により、
型が実体より少ないメンバを言うのは保守的であるにすぎない。
読めなくなるだけで、嘘は言わない。

##### 逆向きは不健全である［未決・S23］

上と逆に、**型が実体を先回りする**場合がある。こちらは嘘をつく。

検査器は本体も分岐も歩くので、`let^` が **実際には実行されない経路** にあっても
メンバを型に足す。実行時のテーブルはその `let^` が走るまで増えない。

```lhat
let^ t = { }
let^ never = p^ { let^ t.b = 1 }   # 呼ばれない
t.b + 1                            # 型検査は通る。実行時に落ちる
```

```text
error: an instruction was given the wrong type
```

分岐でも同じことが起きる。

```lhat
if^ c { let^ t.b = 1 }
t.b + 1
```

名前についてはこれが起きない。`let^` の作る名前はブロックを越えないためである。
**メンバで起きるのは、テーブルがブロックより長く生きるから**である。

03 の 5.1 の実行時型検査が **使用箇所で** 捕まえるので、
壊れ方は `_yield^`（15.11）やセッションの再定義（03 の 4.3）と同じ形になる。
ただしそれらと違い、**静的な型のほうが楽観的**である点は認めておく。

完全な対処は安くない。

- **直線コードに限る** — 8.7 は既に「遅延して実行される本体の外」を判定しており、
  遅延本体の中の `let^` パスはその機構で拒める。**分岐の中は別の解析が要る**
- **読み出し時に作る** — 11.3 の「`nil^` は無いこと」と衝突する

現状は **指摘に留める**。実行時検査が最後の砦として働いている。

## 9. 繰り返しの節［確定・旧 S4］

繰り返し文の本体は、5種類の節に分けて書ける。

### 9.1 節の一覧

| 節 | 実行時期 | 条件不成立時 | 省略 |
| --- | --- | --- | --- |
| `prolog^` | 繰り返しに入る前に1回 | 実行される | 可 |
| `pre^` | 毎回、**条件判定の前** | 1回実行される | 可（9.10） |
| `first^` | 最初の反復の先頭で1回 | 実行されない | 可 |
| `main^` | 毎回、条件判定の後 | — | 条件つきで可（9.3） |
| `last^` | 繰り返し終了時に1回 | 実行されない | 可 |
| `epilog^` | 繰り返し終了時に1回 | 実行される | 可 |

`prolog^` と `epilog^` は **実行条件の成否にかかわらず** 実行される。
`first^` と `last^` は **条件が一度も成立しなかった場合には実行されない**。
`pre^` は判定の前にあるため、**条件が最初から成立しなくても1回は実行される**（9.10）。

`last^` はループ変数などが「条件が成立した最後の状態」で実行される。

### 9.2 順序は固定［確定］

節は必ずこの順に書く。**書く順は実行される順でもある。**

```text
prolog^  →  pre^  →  first^  →  main^  →  last^  →  epilog^  →  finally^
                  ↑ ここで条件を判定する
```

- `prolog^` はブロック先頭に置く
- `pre^` は `prolog^` がある場合はその直後、`first^` がある場合はその直前に置く
- `first^` はブロック先頭、`prolog^` や `pre^` がある場合はその直後に置く
- `last^` はブロック末尾、後続の節がある場合はその直前に置く
- `epilog^` はブロック末尾、`finally^` がある場合はその直前に置く
- `finally^` はブロック末尾に置く（10 章）

順序を強制することで、構文解析器は集合ではなく **単純な並び** として扱える。
順序が違えば「`prolog^` は先頭に置く」と位置を特定した診断が出せる。

```lhat
repeat^until^i ≧ 10 {
    prolog^:
        let^ total = 0
    first^:
        log("開始")
    main^:
        total := total + i
    last^:
        log("最後の i は " .. i)
    epilog^:
        log("終了")
}
```

節の区切りは次の節の見出しまたは閉じ括弧が担うため、`;` は要らない。
6.3 に述べた「`{ … }` で囲む形は閉じ括弧が終端になる」に該当する。

### 9.3 本体は1つ要る［確定・改］

**`first^`、`pre^`、`main^`、`last^` が本体の節である。**
繰り返しはこのうち **少なくとも1つ** を持たなければならない。

見出しを1つも書かなければ、波括弧の中身がまるごと暗黙の `main^` になる。
空の `{ }` もこれにあたるので、見出しのない繰り返しは常に本体を持つ。

```lhat
repeat^n { total := total + 1 }        # 暗黙の main^
repeat^n { }                            # 同上。空でよい
repeat^n { prolog^: let^ t = 0 last^: log(t) }   # last^ が本体
repeat^n { prolog^: let^ t = 0 }        # 誤り。本体の節がない
```

#### 見出しを書き始めたら本体も名指す

節に切り分けた時点で、見出しのない文は **直前の節の続き** になる。
`prolog^` の後に本体のつもりで書いた文は `prolog^` に吸われ、
繰り返しごとではなく1回しか走らない。

```lhat
repeat^n {
    prolog^:
        let^ total = 0
    total := total + 1     # prolog^ の続きになる。誤りとする
}
```

構文としては `prolog^` 節の続きに決まるが、書き手が本体のつもりで書く事故を防ぐため
**本体の節を1つ要求する**。ここでは `main^:` を書けばよい。

#### 見出しより前の文は本体である

`last^` と `epilog^` は **後置** の見出しであり、
見出しより前の文は本体であることが一意に決まる。したがって制限を課さない。

```lhat
repeat^n {
    total := total + 1     # 本体。曖昧性がない
    epilog^:
        log("終了")
}
```

逆に、**前置の見出しより前** に文を書くことは認めない。
`main^:` を書いてどちらであるかを言う（9.2 が `prolog^` をブロック先頭と定めている）。

### 9.4 変数のスコープと寿命［確定］

繰り返し文のブロックは、**寿命の異なる2層** を持つ。

- `prolog^` および `first^` で宣言した変数
  — スコープは繰り返し文のブロック内、**寿命は繰り返し処理の全体**
- `pre^` および `main^` で宣言した変数 — **寿命は1回の反復**

`prolog^` が存在する目的がこれである。
繰り返しの外に変数を漏らさず、しかし寿命を繰り返し全体と揃えたい場合に使う。

`last^` と `epilog^` からは、`prolog^` と `first^` の変数が見える。
`main^` の変数は寿命が1反復であり、最後の反復の終了とともに消えているため見えない。
繰り返しをまたいで値を持ち越したい場合は `prolog^` か `first^` で宣言する。

### 9.5 適用範囲［確定］

Memo.md L215 のとおり、**すべての繰り返し構文** がこれらの節を持てる（16 章）。

- `repeat^ n { … }`、`repeat^ { … }`
- `repeat^ while^ expr { … }`、`repeat^ until^ expr { … }`
- `for^ i := 1 to^ 10 { … }`、`for^ i := 10 downto^ 1 { … }`（`step^` つきを含む）
- `for^ k, v in^ table { … }`
- `for^ i := 1 while^ expr next^ stmt { … }`、`for^ i := 1 until^ expr next^ stmt { … }`

**`for^ … if^ … { … }` は繰り返しではないため、これらの節を持てない**（16.3）。

### 9.6 綴りの別形［確定］

- `prolog^` / `prologue^`
- `pre^` / `premain^`
- `epilog^` / `epilogue^`

どちらで書いてもよい。整形時にどちらへ寄せるかはフォーマッタが決める。
条件分岐の綴り（5.3）と同じ扱いである。

### 9.7 実装上の含意

#### `first^` は内側で実行し、外側へ宣言する

`first^` は最初の反復の先頭で実行されるため、実行位置は繰り返しの内側にある。
しかし 9.4 のとおり、そこで宣言された変数の寿命は繰り返し全体である。

したがってコード生成では、
**`first^` の実行は繰り返しの内側、宣言の割り付けは外側のスコープ** に分ける。
`prolog^` と同じ記憶域に、実行時期だけを遅らせて書き込む形になる。

#### `last^` は状態の保存を要する

Memo.md L210 が「`last^` があると前回の状態を保存しておく必要があるな」と
指摘しているのがこれにあたる。

繰り返しが終わるのは条件が **成立しなくなった** ときである。
その時点でループ変数は、条件を満たさなかった値になっている。

```lhat
for^ i := 1 to^ 10 {
    last^:
        log(i)      # 10 でなければならない。11 ではない
}
```

素朴に実装すると `last^` は 11 を見る。
「次の反復があるか」は条件を評価するまで分からず、
条件式には副作用がありうるため先読みできない。

したがって **`last^` を持つ繰り返しでは、ループ変数の値を控えておき、
脱出後にその値で `last^` を実行する**。

控えを取る時期は **各反復の先頭**、条件が成立した直後とする。
反復の終了時ではない。9.8 のとおり `break^` は反復の途中での脱出であり、
そのとき妥当な最後の要素は **現在の反復の値** だからである。
終了時に控える方式では1つ前の反復の値を見てしまう。

先頭で控える方式は通常終了にも正しく働く。
条件が成立した最後の時点が、最後の反復の先頭にあたるためである。

費用は `last^` を書いた繰り返しにのみ生じる。
`last^` のない繰り返しは控えを取らない。

#### `first^` と `last^` は「1回以上実行されたか」を要する

どちらも条件が一度も成立しなければ実行されない。
`first^` は最初の反復に入った時点で実行すればよいが、
`last^` は脱出後に判定するため真偽値を1つ保持する。
これも `last^` を持つ繰り返しにのみ生じる費用である。

### 9.8 脱出時の扱い［確定・旧 S7］

| 脱出の仕方 | `last^` | `epilog^` | `finally^` |
| --- | --- | --- | --- |
| 条件が成立しなくなった（通常終了） | 一度でも成立していれば実行 | 実行 | 実行 |
| `break^` | 妥当な最後の要素があれば実行 | 実行 | 実行 |
| `return^` | 実行しない | 実行しない | 実行 |

#### 3段階の強度

3つの節は、実行される範囲が段階的に広がる関係にある。

1. **`last^`** — 条件が一度でも成立した場合のみ。最後の要素に対する締めくくり
2. **`epilog^`** — 条件の成否によらず実行。ただし繰り返しを正常に抜けた場合に限る
3. **`finally^`** — あらゆる脱出で実行される（10 章）

`break^` は繰り返しにとって正常な終了である。
やるべきことが済んだので抜ける、という意味であり、その後の処理は通常どおり続く。
したがって `last^` と `epilog^` の両方が実行される。

`return^` は関数からの離脱であり、繰り返しにとっては正常な終了ではない。
`last^` も `epilog^` も実行されず、**`finally^` だけが実行される**。

この区別は、今後 例外や誤りによる脱出を設計する際の指針にもなる。
そうした脱出は `return^` と同じ側に属し、`finally^` のみを実行する。

#### `epilog^` は finally ではない

`epilog^` は `return^` で実行されないため、他言語の `finally` には相当しない。
脱出の種類を問わない後始末が必要な場合は `finally^` を使う（10 章）。

繰り返しに `finally^` を書くこともできる。その場合 `epilog^` は
`finally^` の直前に置くことが強制される（9.2）。

#### `break^` 時に `last^` が見る値

`break^` は反復の **途中** での脱出であり、その反復では条件が成立している。
したがって妥当な最後の要素は **現在の反復の値** である。

```lhat
for^ i := 1 to^ 10 {
    main^:
        if^ i = 5 { break^ }
    last^:
        log(i)      # 5。4 ではない
}
```

9.7 で控えを各反復の **先頭** で取ると定めたのはこのためである。

#### 実装上の含意

`last^` と `epilog^` はいずれも `return^` では実行されないため、
**繰り返しの脱出経路に閉じた処理として生成できる**。
関数からの離脱に伴う巻き戻しの機構は必要ない。それは `finally^` の仕事になる（10.4）。

#### 多段の `break^`［提案 → 要確認］

Memo.md L500 と L538 には `break^[name]` `break^[1]` という
複数の繰り返しを一度に抜ける記法がある。

上の原則を素直に適用すると次のようになる。

- **脱出先として指定された繰り返し** — 正常な終了なので `last^` と `epilog^` を実行
- **途中で抜けられる内側の繰り返し** — その繰り返しにとっては
  外側へ抜けるための離脱であり `return^` と同じ側にあたる。`finally^` のみ実行

原則からの帰結として記す。多段 `break^` の記法自体がまだ確定していないため、
記法を決める際に併せて確認する。

### 9.9 `dispose` と `defer^` は無関係［確定］

Memo.md L52 に「`for` の場合はスコープ終了で `dispose` が呼ばれる。
他言語で言う `using`」という記述があるが、
**`dispose` は繰り返し構文とは無関係である**。

`dispose` が指しているのは C# の `IDisposable` と `using` に相当する仕組みであり、
L^ では `with^`（Memo.md L371–L372）が担う。
繰り返しのスコープ終了で自動的に呼ばれるものではない。

`defer^`（Memo.md L146）については、構想が定まっていないため
本文書では扱わない。遅延評価の指定を意図したものと思われるが、
設計が固まった時点で改めて位置づける。

### 9.10 `pre^` — 条件判定の前に走る本体［確定］

> **`pre^` は毎回の反復の先頭、条件を判定する前に実行される本体である。**

判定より前にあるため、**条件が最初から成立しなくても1回は実行される**。
C の後置 while（`do { … } while (…)`）にあたる形がこれで書ける。

```lhat
repeat^while^ line ≠ "" {
    prolog^:
        let^ line = ""
    pre^:
        line := read()
}
```

`premain^` は同じ節の別綴りである（9.6）。

#### `main^` と併用できる

両方書けば、**条件判定を挟んで本体が前後に分かれる**。
読んでから判定し、通ったら使う——Dijkstra の loop-and-a-half がそのまま書ける。

```lhat
repeat^while^ line ≠ "" {
    prolog^: let^ line = ""
    pre^:    line := read()      # 毎回。判定の前
    main^:   use(line)           # 判定を通った回だけ
}
```

`pre^` は `main^` より **1回多く** 走る。判定に落ちた回も `pre^` は走っているためである。

#### 宣言は `prolog^` に置く

`pre^` で宣言した名前の寿命は1回の反復である（9.4）。
判定式や `main^` から見える名前が要る場合は `prolog^` で宣言する。
`prolog^` が存在する目的がこれにあたる。

#### `first^` と `last^` は変わらない［確定］

`pre^` は **繰り返しに入ったことにしない**。
9.1 のとおり `first^` と `last^` は **条件が成立した反復** のためのものであり、
`pre^` だけが走って抜けた繰り返しでは、どちらも実行されない。

```lhat
repeat^while^ false^ {
    pre^:   a()      # 1回走る
    first^: b()      # 走らない
    last^:  c()      # 走らない
}
```

`pre^` を「反復に入った」と数える案は採らない。
`first^` と `last^` の意味が `pre^` の有無で変わることになり、
文脈で意味が変わる形（01 の Q8、11.5 の (3)）を避ける方針に反する。

#### `for^ … in^` では書けない［確定］

16.3 のとおり `in^` は歩きのコルーチンを再開して焦点を束縛する。
**束縛はコルーチンが答えた後** に起きるので、その前に走る節からは
前の反復の値——初回は未束縛——しか見えない。

```lhat
for^ k, v in^ t {
    pre^: log(v)     # 誤り。v はまだこの反復のものではない
}
```

構文の誤りとする。`to^`・`downto^`・`while^`・`until^`・`repeat^` は
焦点が繰り返しの前に用意されるため、この問題を持たない。

## 10. `finally^` 節［確定］

### 10.1 ブロック一般の機構である

`finally^` は繰り返し固有の節ではなく、**ブロックの末尾に置ける汎用の節** である。

```lhat
do^{
    let^ r = open("data")
    process(r)
finally^:
    r.close()
}
```

置けるブロックは次のとおり。

- `do^{ … }`
- `if^` 文のブロック
- 繰り返し文のブロック（9.2 の順序に従い、`epilog^` の直後）
- `with^` のブロック
- **手続き `p^` の本体**

**関数 `f^` の本体には置けない。** 理由は 10.6 に述べる。

手続きの本体には置ける。資源や効果を扱うのは手続きであり、
`finally^` が最も必要になる場所である。

```lhat
p^{
    let^ r = open("data")
    process(r)
finally^:
    r.close()
}
```

### 10.2 あらゆる脱出で実行される

ブロックをどのように抜けても実行される。

- 末尾まで到達した場合
- `break^` で繰り返しを抜けた場合
- `return^` で関数から離脱した場合
- 多段の `break^` で通過された場合

他言語の `finally` に相当する。

ただし L^ は例外機構を持たない（12.8）。
`finally^` の中で誤りを受け取っても、それを外へ伝播させる手段はない。
返り値も変更できない（10.5）。誤りは `finally^` の中で処理し切ることになる。

### 10.3 位置は末尾に強制

ブロックの最末尾に置く。
繰り返しの節と併用する場合の順序は 9.2 のとおりで、`finally^` が最後になる。

```text
prolog^  →  first^  →  main^  →  last^  →  epilog^  →  finally^
```

### 10.4 実装上の含意

`finally^` が関数からの離脱でも実行される以上、
**`return^` は、抜けるすべてのブロックの `finally^` を内側から順に実行してから
関数を出る** 必要がある。

`return^` については、どのブロックの内側にいるかが構文上わかるため、
抜けるブロックの `finally^` を順に呼ぶコードを位置ごとに生成すればよい。

この機構を `finally^` に集約したことにより、
繰り返しの節（`last^` `epilog^`）は繰り返しの脱出経路だけを扱えばよくなった。
**巻き戻しの担い手が1つに定まる。**

ただし静的に位置が定まらない脱出も存在する。
コルーチンの破棄がこれにあたり、実行時の機構を要する。10.8 を参照。

### 10.5 返り値を変更できない［確定］

`finally^` の中に `return^` は書けない。`finally^` は返り値を差し替えられない。

Java は `finally` から `return` できてしまい、
本来返るはずだった値が黙って置き換わる罠として知られている。C# はこれを禁じている。

L^ も禁じる。この制限は 10.6 の議論の前提にもなっている。

### 10.6 関数 `f^` の本体に置けない理由［確定・旧 S8］

#### 純粋性が壊れるからではない

`finally^` は制御構文であって効果構文ではない。
`f^` の中に置かれた `finally^` の中身は、`f^` の制限をそのまま受ける（Memo.md L54）。

- 関数しか呼べない
- 代入は局所変数に対してのみ

したがって `finally^` の中に書けるのは純粋な処理だけであり、
関数型言語としての性質を壊す手段は最初から存在しない。

#### 純粋関数では観測不能であり、意味を持たないから

`finally^` が価値を持つのは「どの経路で抜けても後始末したい」場合だが、
純粋関数には後始末すべきものが存在しない。

- 資源を開けない。`open` のような入出力は手続きであり `f^` から呼べない
- 復元すべき可変状態がない。代入先は局所変数のみ
- 局所変数はフレームとともに消える

10.5 により返り値も変更できない。
よって `f^` 内の `finally^` は **外から一切観測できない**。
意味論的に何もしないのと同じであり、書けても混乱を招くだけになる。

#### 唯一の例外は脱法関数

Memo.md L54 は「デバッグ用にログ出力などの脱法関数は用意する」としている。
これを使えば `f^` 内の `finally^` にも用途が生まれる。

ただし、純粋性の保証の外に置かれた抜け道のために言語機能を設計するのは筋が悪い。
`f^` からは除外する。

### 10.7 コルーチンとの組み合わせ［確定・旧 S9］

`yield^` を含む手続きは呼び出すとコルーチンを返す（15 章）。
コルーチンが `yield^` した後、**再開されないまま捨てられた場合も
保留中の `finally^` は実行される**。

同じ `finally^` が二度実行されることはない。
すでに実行済みのものは破棄時に再実行されない。

これは他言語でも難所として知られている箇所であり、いずれも同じ結論に至っている。

- Python のジェネレータは終了処理で `GeneratorExit` を投げて `finally` を走らせる
- Lua 5.4 は `coroutine.close` と to-be-closed 変数をこのために導入した

#### 保留中の `finally^` は内側から順に実行する

コルーチンが入れ子のブロックの内側で中断していた場合、
保留中の `finally^` は複数ある。破棄時には **内側から順に** 実行する。
通常の脱出と同じ順序である。

#### 破棄処理の中で `yield^` はできない

破棄中のコルーチンには再開を待つ相手がいない。
`finally^` の中で `yield^` することは禁じる。
Python も同じ制限を課している。

#### 破棄の契機

破棄の契機は2種類ある。両方が必要になる。

- **明示的な破棄** — 実行時期が確定する。資源の解放にはこちらが要る
- **到達不能になったコルーチンの回収** — ごみ集めが最後の受け皿となる。
  ただし実行時期は不定であり、資源が想定より長く保持されうる

明示的な破棄の手段は未決とする（S10）。

### 10.8 実行時の巻き戻し機構が必要になる［確定］

10.4 では「入れ子の関係は構文上わかるので実行時の巻き戻し表は要らない」と述べた。
**10.7 の決定により、この前提は成り立たなくなる。**

コルーチンが中断している位置は実行時にしか分からず、
したがって **どの `finally^` が保留中かも静的には決まらない**。
破棄処理は、中断位置から保留中の `finally^` を割り出せなければならない。

実現方法は2通りある。

- **PC から手続きへの対応表** — 関数ごとに「この位置で有効な `finally^`」を表に持つ。
  巻き戻しが起きない限り費用がかからない。Java や .NET の例外表と同じ仕組み
- **フレームごとの有効な `finally^` の一覧** — 実行時に積み上げる。
  Lua 5.4 の to-be-closed 変数がこの形

前者を推す。通常の実行経路に費用が乗らない。

`return^` と `break^` については、静的に位置が定まるため
10.4 のとおり呼び出しを直接生成してもよい。
巻き戻し表に一本化して重複した生成を避ける選択もあり、どちらを採るかは実装の判断とする。

**静的に位置が定まらない脱出は、コルーチンの破棄だけである。**
12.8 のとおり L^ は例外機構を持たず、誤りは値として返される。
誤りが暗黙に脱出を起こすことがないため、
この機構が扱う対象は今後も増えない。

### 10.9 `epilog^` との使い分け

- 繰り返しが正常に終わったときだけの後始末 → `epilog^`
- 脱出の種類を問わない後始末（資源の解放など） → `finally^`

繰り返し以外のブロックには `epilog^` がないため、選択の余地はない。

## 11. 演算子［確定・旧 S5］

### 11.1 演算子は関数である

Memo.md L62 のとおり、**すべての演算子は関数として扱う**。

> op^演算子 関数扱い すべての演算子は関数としての性質を満たすことを強制する、またyield不可

したがって演算子の実装は `f^` の制約を受ける。

- 関数しか呼べない
- 代入は局所変数に対してのみ
- `yield^` できない（15.3 の帰結。別の規則として書く必要はない）

利用者が定義した演算子も同じ制約を受ける。
**演算子に副作用を持たせられない。**

### 11.2 `..` は「連結」であって「文字列連結」ではない［確定］

`..` は文字列専用の演算子ではない。**一般の連結演算子** である。
文字列の連結は、そのうちの一例にすぎない。

`..` に応答できるオブジェクトであれば、いずれも正当な被演算子になる。

```lhat
"abc" .. "def"                        # 文字列の連結
def^Foo { … } .. aspect .. protocol   # 定義の合成（Memo.md L357）
```

Memo.md L357 が継承を `..` で書いているのは、
**同じ記号を別の意味に多重定義しているのではなく、同じ演算を別の型に適用している** ためである。
`def^` の値が `..` に応答し、その応答が合成になる。

### 11.3 正当性は意味解析で判定する［確定］

`x .. y` が正当かどうかは、**型検査の段階で決まる**。

- 構文解析では判定しない。`..` は単なる二項演算子として構文木に載る
- 実行時まで持ち越さない（strict の場合）

これは 03 の段階構成と噛み合っている。
型検査が独立した段として存在するため、
「この型は `..` に応答するか」をそこで問える。

判定は **構造的** に行う。Memo.md L364–L365 のとおり
プロトタイプベースかつダックタイピングであり、静的型検査も同じ方針を採る。
名前による継承関係ではなく、`..` の実装を持つかどうかで判定する。

例外は2つだけである。どちらも **構造を比べても何も分からない** ものにあたる。

- **誤りの種別** — `errordef^` が宣言する種別の同一性は、
  構造ではなく宣言の場所で決まる（[04-errors.md](04-errors.md) の 2.4）
- **ホストが登録した型** — ホストのポインタを包むだけで中身が見えないため、
  構造で同一視すればホスト型がすべて同じ型になり、
  C 側が生ポインタを別の型として読む。
  同一性は登録の場所で決まる（[05-modules.md](05-modules.md) の 8.8）

relaxed（03 の 3.1）では、静的に決まらない箇所が実行時の検査に落ちる。
実行時の値が型タグを持つ（03 の 2.1）ため、この検査が可能になる。

#### 判定の形［確定］

**左の被演算子に問う。** 11.8 の `op^` が定めるとおり、演算子は
**その演算子を名前とするメンバ** である。

1. 左が `..` を持たなければ誤り
2. 持てば、それは関数である（11.1）。右の被演算子は **その引数**
3. 式全体の型は **その関数の返り値**

同じ問いを `..` と算術のすべてに用いる（11.4）。
どの型が何を持つかは 11.4 の表による。

| 左の型 | 持つもの |
| --- | --- |
| `string^` | `..`（組込み、11.8） |
| `number^` | 算術7つ（組込み、11.8） |
| `bool^` `nil^` | 何も持たない |
| 定義・インスタンス | `op^` を書いたものだけ |
| 合併 | すべての腕が持つ場合のみ |
| `any^` | 何も言わない（13.7） |
| 推論が及ばなかった箇所 | 何も言わない（03 の 3.5） |

```lhat
let^ x : string^|nil^ = "a"
x .. "b"        # 誤り。nil^ は `..` を持たない
```

##### 判定は構造的である［確定］

11.3 冒頭のとおり、問うのは「その名前のメンバを持つか」だけである。
`def^` に `op^` と書いたかどうかではない。

14.14 の `[ … ] :=` は演算子の綴りをキーにできるため、
`def^` を経ずに同じメンバを持たせられる。**これも答える。**

```lhat
let^ t = { [".."] := f^self^, o:string^ -> string^ { return^ o } }
t .. "x"        # 通る
```

`op^` は 14.12 の印と並べて書けるようにするための記法であり、
判定を変えるものではない。

##### 定義どうしは合成であって呼び出しではない［確定］

14.5 の合成が優先する。**両辺が定義であれば常に合成** であり、
どちらかが `op^..` を持っていても呼ばれない。

```lhat
let^ Foo = def^{ self^{}, op^.. := f^self^, o:string^ -> string^ { … } }
let^ Bar = Foo .. def^{ … }     # 合成。op^.. は関わらない
let^ i = Foo.new^()
i .. "a"                         # こちらが op^..
```

14.7 は定義とそのインスタンスに同じメンバを持たせるため、
**構造からは両者を区別できない**。何から作られたかで判別する。
11.3 の構造的な同一性はそのまま — これは「何であるか」ではなく
「何が作ったか」を見ている。

### 11.4 他の演算子も同じ枠組みに載る［確定］

`..` に固有の性質ではない。
`+` `-` `*` `/` `//` `%` `**` も **同じ問いで判定する** — 左の被演算子に
その演算子を問い、右をその引数として照合する（11.3）。

Memo.md L46 は数値オブジェクトが `inc()` `dec()` `add(a)` `sub(a)` を
メンバとして持つとしており、演算子とメソッドの対応が前提になっている。
対応の付け方は 11.8 で決めた — **演算子そのものがメンバ名になる**。
別名を割り当てないので、演算子を増やすのに新しい決定は要らない。

#### 組込み型が答えるもの［確定］

| 型 | 答える演算子 |
| --- | --- |
| `number^` | `+` `-` `*` `/` `//` `%` `**`。いずれも `number^` を取り `number^` を答える |
| `string^` | `..` のみ |
| `bool^` | なし |

したがって次はいずれも誤りである。

```lhat
1 + "a"          # number^ の + は number^ を取る
"a" + "b"        # string^ は + を答えない。連結は `..`
true^ + 1        # bool^ は何も答えない
```

`number^ + string^` を許さないのは、数値化を **明示させる** ためである。
`string^ + string^` を許さないのは、連結が `..` だからである（11.2）。

#### `and^` `or^` 単項 `!` は言語のもの［確定］

これらは組込みの論理演算だけを意味する。`op^` の対象にしない。
8.6 の条件規則が真偽値を `bool^` に限っており、
そこに利用者定義を差し込む余地を作らない。

11.5 の比較（`=` `≠` `<` `>` `≦` `≧`）も対象外である。
判定は 14.12 の互いに素性で行い（11.5）、型に問う形をとらない。

#### 単項 `-` も対象外

11.8 の形は **左の被演算子が答える二項の演算** である。
単項には受け手と引数の区別がなく、同じ形に載らない。

### 11.5 優先順位と結合性［方針確定・細部が未決 → S11］

基本方針は **主要な言語の慣習に合わせる** こととする。
以下は慣習で決まるため、個別に決定しない。

- 後置（`.` `?.` 呼び出し `[]`）が最も強い
- 単項（`!` 単項の `-`）がその次
- `* / // %` が `+ -` より強い
- 比較（`= ≠ < > ≦ ≧` `is^`）が算術より弱い
- `and^` が `or^` より強く、どちらも比較より弱い
- 二項算術は左結合

#### 慣習では決まらないもの

次の5点は、主要な言語に前例がないか、前例が割れている。

##### (1) `..` の優先順位と結合性

Lua 5.4 は `..` を **`+ -` より低く**、かつ **右結合** としている。
優先順位表の該当部分は次のとおり（低い順）。

```text
<<  >>
..
+  -
*  /  //  %
単項演算子
^
```

低く置く理由は、`"合計: " .. a + b` が `"合計: " .. (a + b)` と読まれてほしいためである。
逆であれば `("合計: " .. a) + b` になり、ほぼ常に誤りになる。
連結は行の最も外側の操作になることが多い。

右結合にする理由は、`a .. b .. c` を右から畳むと
文字列の連結で中間結果の複製が減るためである。

L^ でも文字列については同じ理屈がそのまま効く。
定義の合成（Memo.md L357）は被演算子が一次式であるため優先順位の影響を受けず、
合成が結合的である限り結合性も観測できない。

**Lua と同一とする。** `+ -` より低く、右結合。

##### (2) べき乗と単項の `-` の関係

争点はこの1つの並びに集約される。

```text
-2 ** 2      # -(2 ** 2) = -4 か、(-2) ** 2 = 4 か
```

**両者を同じ優先順位にしても解決しない。**
前置演算子と中置演算子の混在であり、結合性の指定では曖昧が残る。
どちらが先に適用されるかを決める必要がある。

数学では −2² = −(2²) = −4 である。
Python・Ruby・Fortran はいずれもこれに従い、べき乗を単項マイナスより強くする。

01 の 7.1 に記した設計動機
（数学的な見た目をした記法には数学的な意味だけを与える）に照らせば、
数学と一致させる読みを採るのが一貫する。

**べき乗を単項マイナスより強くする。** `-2 ** 2` は `-4` である。

なお `2 ** -1` は書ける。
べき乗の右側には単項式を許す、という非対称で解決される。Python の文法が同じ形をとる。

べき乗自体は **右結合** とする。`2 ** 3 ** 2` は `2 ** (3 ** 2)` であり `512` になる。
これも数学の慣習と一致する。

##### (3) 型の合併は `|` とする［確定］

Memo.md L305 は nilable の指定を `k as^number^or^nil^` と書いていた。
この記法は **撤回する**。

`or^` が型の一部（合併）と論理和の両方を意味することになり、
同じ記号が文脈によって別物になる。
優先順位をどう決めても解消しない種類の曖昧さである。

代わりに **`|` を型の合併演算子とする**。

```lhat
k as^number^|nil^
```

曖昧さが消える理由は3つある。

- **`|` は未使用だった。** Q3 でビット演算を演算子として提供しないと決めたため空いていた
- **型の文脈は構文上識別できる。** `as^` の右、`:` による型注釈、`->` の返り値型。
  いずれも構文解析器が「いま型を読んでいる」と判断できる位置にある
- **`or^` が論理和専用に戻る。** 同じ記号が文脈で別物になる状態が解消する

字句解析器は型の文脈を知らない。`|` をトークンとして返すだけであり、
それが型の合併であるかどうかは構文解析器が判断する。

`as^` 自身の優先順位は 11.6 に示す。

##### (4) `@` — 決定済み。現状は非対応

Memo.md L99 の中間値参照（`f(1 + 2 + @(a(3)), @1 + 3)`）は
**演算子ではなく構文要素として扱う**。

- `@(式)` — 中間値を捕まえる形
- `@自然数` — 捕まえた値を参照する形
- `@式` — 不正。上の2つの形以外は認めない

構文要素であるため優先順位を持たない。一次式として解析される。

ただし **この機構自体の構想が固まっていないため、現状は非対応とする**。
記法の形だけを上に記録しておき、機構が定まった時点で改めて扱う。

##### (5) 比較の連鎖

比較演算子を3項以上並べた書き方を指す。

```text
1 ≦ x ≦ 10
```

読み方が3通りありうる。

- **数学の読み** — 「1 ≦ x かつ x ≦ 10」
- **C 系の読み** — `(1 ≦ x) ≦ 10`。真偽値と数値を比較する。
  C では真偽値が整数であるため黙って通り、有名な罠になっている
- **Python の読み** — 連鎖を認め、数学と同じ意味になる

**L^ に固有の事情がある。** `≦` `≧` を採用し、
数学記法に寄せることを推奨としている（01 の 7.2）以上、
利用者が数学どおりの読みを期待する度合いが他の言語より高い。

一方で L^ には C にない安全弁がある。
連鎖を認めない場合でも `(1 ≦ x) ≦ 10` は真偽値と数値の比較になり、
**静的型検査で誤りとして報告される**。黙って通ることはない。

**連鎖を認める。** 記法の見た目と意味を一致させる方針を優先する。

意味は次のとおり。

- `a < b < c` は `(a < b) and^ (b < c)` と同じ意味を持つ
- **共有される被演算子は1度だけ評価する。** 上の `b` は2度評価されない。
  Python が同じ規則を採る。手続きの呼び出しが被演算子に現れうる以上、
  この規定がないと副作用の回数が変わる
- 連鎖できるのは比較の水準の演算子（`=` `≠` `<` `>` `≦` `≧` `is^`）とする
- 種類を混ぜた連鎖（`a < b = c`）も認める
- 連鎖全体の値は真偽値である

### 11.6 優先順位表［確定］

弱い順に並べる。

| 水準 | 演算子 | 結合性 |
| --- | --- | --- |
| 1 | `or^` | 左 |
| 2 | `and^` | 左 |
| 3 | `=` `≠` `<` `>` `≦` `≧` `is^` | 連鎖（11.5 の (5)） |
| 4 | `..` | **右** |
| 5 | `+` `-` | 左 |
| 6 | `*` `/` `//` `%` | 左 |
| 7 | `as^` | 左 |
| 8 | `catch^` `??` | 左 |
| 9 | 単項 `!` `-` `try^` `yieldall^` | — |
| 10 | `**` | **右** |
| 11 | 後置 `.` `?.` 呼び出し `?(` `[` `?[` | 左 |

`catch^` と `try^` は [04-errors.md](04-errors.md) の 4 章・5 章で定める。
`catch^` を二項演算子より強くしたのは、
`base + parse(s) catch^ 0` で失敗するのが `parse(s)` であって
`base + parse(s)` ではないためである（04 の 4.3）。

`??` は 11.7 で定める。`catch^` と同じ水準に置くのは、
両者が **同じ形の記法** だからである（11.7）。

`is^` は右辺に型を書く適合の判定であり、分岐の中で左辺の型を狭める。
13.11 で定める。

`as^` は二項演算子より強く単項より弱い。`a + b as^T` は `a + (b as^T)` になる。
Rust と Kotlin の `as` が同じ位置にある。`as^` 自体は未実装（S27）。

型の合併 `|` は型の文法の中でのみ現れるため、この表には載らない。
型の文法は未着手である。

#### 表に載らないもの

次は式の演算子ではないため、優先順位を持たない。

- `:=` と `let^` — 文のレベルの記法（8.3, 8.6）
- `->` — シグネチャの中でのみ現れる（01 の 7.6）
- `|` — 型の文脈でのみ現れる（11.5 の (3)）
- `@(式)` と `@自然数` — 一次式の形（11.5 の (4)）
- `$` `$$` `$^` — 識別子に密着する接頭辞であり、字句の段階で1つのトークンになる
  （01 の 8 章）

### 11.7 `??` — `nil^` のときの既定値［確定・旧 04 の E7］

```lhat
let^ v = t[k] ?? 0
```

左の式が `nil^` のとき、**全体の値は右の式の値になる**。
`nil^` でなければ、全体の値は左の値から `nil^` を除いた型になる。

```lhat
let^ v = t[k] ?? 0        # t[k] : T|nil^ に対して v : T|number^
```

#### なぜ要るのか

04 の 11.3 が、動的な添字 `t[k]` は鍵が欠けていれば `nil^` を返すと定めた。
**欠落は誤りではない** ので `catch^` は使えない（04 の 4.1）。

`??` がないと、既定値を書くのに次の形しか残らない。

```lhat
let^ v = if^ t[k] is^ nil^: 0 el^: t[k] ;
```

**`t[k]` を2度評価してしまう。** 添字が副作用を持ちうる以上、これは同値ではない。

#### `catch^` と同じ形である［重要］

`??` と `catch^` は、**合併から腕を1つ落として代わりの値を置く** という同じ記法である。
落とす腕が `nil^` か誤りかだけが違う。

したがって次がすべて共通する。

- **優先順位** — 二項演算子より強く、単項より弱い（11.6）。
  `base + t[k] ?? 0` の範囲は `t[k] ?? 0` である。
  `nil^` になるのは `t[k]` であって `base + t[k]` ではない
- **右辺は必要なときだけ評価する** — 左が `nil^` でなければ右は評価されない
- **左が `nil^` になりえない場合は誤り** — 書いても働かないため

同じ水準に置いてあるので左結合で並べられる。

```lhat
let^ v = f() catch^ nil^ ?? 0     # 誤りも欠落も 0 にする
```

#### `it^` は使わない

`catch^` の右辺では捕まえた誤りを `it^` で参照できる（04 の 4.2）。
`??` にはそれがない。**左が `nil^` だったという以上の情報がなく、名指す値がない**。

#### 綴り

C#、JavaScript、Swift、PHP、Dart が同じ綴りで同じ意味を持つ。
`?.` `?(` `?[` と同じ `?` の族に属する（01 の 7.1）。

**これは記号の演算子なので、字句解析器に追加が要る。**
`try^` や `catch^` が何も要らなかったのは `^` を伴う語だからである（01 の 2.1）。

### 11.8 `op^` — 演算子の定義［確定］

> **演算子は、その演算子を名前とするメンバである。**

`def^` の中に `op^演算子 := …` と書く。

```lhat
let^ Vec = def^{
    self^{ tag := "v" },
    op^.. := f^self^, other:string^ -> string^ {
        return^ self^.tag .. other
    },
}
```

#### 名前は演算子そのもの

対応表を作らない。`concat` のような別名を割り当てれば、
**どの演算子がどの語かを覚える対象** が増える。

01 の 6 章がメンバ名を識別子と定めているため、
`..` は **利用者が手で書けない名前** になる。
書けない以上、利用者のメンバと衝突しない。
14.10 の位置の型が数字をメンバ名に使うのと同じ手である。

#### 左の被演算子が答える

14.4 のとおり第一引数は `self^` であり、そこに **左の被演算子** が入る。
右の被演算子はその引数になる。

この形により、1つの型が **複数の右辺型に答えられる**。
14.12 の `overload^` がそのまま効く — 演算子はメンバであり、
多重定義はメンバの機構だからである。

```lhat
op^.. := f^self^, other:string^ -> string^ { … },
overload^ op^.. := f^self^, other:Vec -> Vec { … },
```

#### 組込み型は処理系が持つ

`string^` の `..` も `number^` の算術も処理系が持つ。L^ で書き下すのではない。
コルーチンが `start()` を持つのと同じ扱いである（15.6、05 の 8.5）。

```text
string^ の ..  :  f^self^, string^ -> string^;
number^ の +   :  f^self^, number^ -> number^;     # - * / // % ** も同じ形
```

したがって 11.3 の判定は組込み型と利用者定義型で同じ形になる。
どちらも「その演算子を持つか」を問うだけである。

実行時も同じ形をとる。命令は自分の型を直接扱い、
**扱えなかったときにだけ** メンバを探す。
組込みの数値演算と文字列連結はこの探索の費用を負わない。

#### 形は決まっている［確定］

> **`op^` は `self^` と引数1つを取る `f^` でなければならない。**

```lhat
op^.. := f^self^, other:T -> R { … }     # これだけ
```

外れた形は誤りとする。

```lhat
op^.. := f^ o:string^ -> string^ { … }         # 誤り。self^ がない
op^.. := p^self^, o:string^ { … }              # 誤り。11.1 により関数
op^.. := f^self^ -> string^ { … }              # 誤り。右の被演算子を取らない
op^.. := f^self^, a:T, b:T -> R { … }          # 誤り。引数は1つ
op^.. := 5                                      # 誤り。関数ですらない
```

**後段は形を確かめない。** 呼び出し側は署名を読んでそのまま信じ、
処理系は本体の宣言によらず受け手と引数1つを渡す。
したがって形の判定はここで済ませる必要がある。

14.12 の `overload^` を付けた場合は **腕ごとに** 同じ判定を受ける。

`p^` を退けるのは 11.1 による。演算子に副作用を持たせないためであり、
`yield^` できないことも同じ帰結として従う（15.3）。

#### 書けるのは `..` と算術だけ

11.4 のとおり、`and^` `or^` 単項 `!` と比較は言語のものであり、
単項 `-` はこの形に載らない。それらに `op^` を書けば誤りとする。

## 12. `with^` と `dispose()`［確定・旧 S10］

### 12.1 記法

`with^` は **局所変数の定義だけ** を受け付ける。

```lhat
with^ r := open("data")
with^ w := create("out")
{
    copy(r, w)
}
```

定義された変数が指すオブジェクトは、**`dispose()` メソッドを持つことが求められる**。

```lhat
with^ bar := Boo()   # error : Boo は dispose を持たない
```

Memo.md L371–L372 の記述に対応する。

### 12.2 スコープ終了時に `dispose()` を呼ぶ

ブロックのスコープが終わる時点で、
`with^` で指定されたすべてのオブジェクトに対して `dispose()` を呼ぶ。

**呼ぶ順序は定義の逆順とする**［提案］。
後から定義した資源が先に定義した資源に依存している場合、
逆順でなければ解放の順序が壊れる。

### 12.3 あらゆる脱出で呼ばれる［確定］

`dispose()` は 10.2 の `finally^` と同じ強さを持つ。

- 末尾まで到達した場合
- `break^` で繰り返しを抜けた場合
- `return^` で関数から離脱した場合
- コルーチンが破棄された場合（10.7）

したがって 10.8 の巻き戻し機構を共有する。
`with^` のスコープは、その機構にとって `finally^` と同じ扱いの区間になる。

### 12.4 `finally^` との順序［提案］

同じブロックに `finally^` と `with^` の両方がある場合、
**`finally^` が先、`dispose()` が後** とする。

`with^` はブロックを外側から包む構造であり、
`finally^` はブロックの内側の最後の節だからである。

```lhat
with^ r := open("data")
{
    process(r)
finally^:
    log("処理終了")     # こちらが先
}                       # r.dispose() はこの後
```

### 12.5 `dispose()` の有無は型検査で判定する［確定］

Memo.md L372 が `error` としているとおり、
`dispose()` を持たないオブジェクトを `with^` に渡すのは誤りである。

判定は 11.3 と同じく **構造的** に行う。
`dispose()` という名前と適合する実装を持つかどうかだけを見る。
特定の型を継承しているかは問わない。

12.7 のとおり `dispose()` は誤りを返さないため、
検査の条件は **「戻り値を持たない `dispose()` を持つこと」** になる。

strict では型検査の段で報告される。
relaxed では実行時の検査に落ちる（03 の 3.1）。

### 12.6 コルーチンの破棄はこの仕組みに載る［確定］

コルーチンオブジェクトは `dispose()` を持つ。
したがって破棄の手段は2通りある。

- **明示的に呼ぶ** — `c.dispose()`
- **`with^` に渡す** — スコープ終了時に暗黙に呼ばれる

10.7 で述べた「保留中の `finally^` を実行する」処理は、
コルーチンの `dispose()` の中身にあたる。

これにより 10.7 の「明示的な破棄の手段」が定まった。
ごみ集めによる回収は、どちらも行われなかった場合の最後の受け皿として残る。

### 12.7 `dispose()` は失敗しない［確定・旧 S12］

**`dispose()` は誤りを返さない。** 戻り値を持たない。

失敗しうる後始末が必要な場合は、`flush()` や `commit()` のように
**利用者が明示的に呼ぶ別の操作** として提供する。
`dispose()` はその後に呼ばれ、失敗しない処理だけを行う。

#### 理由

自動的に呼ばれる後始末は、**誤りを返す先が構造的に存在しない位置** で走る。
巻き戻しの途中、`return^` の最中、コルーチンの回収時などである。
ここで失敗しうるようにすると、どこかで必ず握りつぶすことになる。

Zig が同じ判断をしている。`std.fs.File.close()` の戻り値は `void` であり、
閉じる操作は失敗しない。書き込みが完了したことを確認したい場合は、
閉じる前に明示的に同期を要求する。

Go は逆に `Close()` が誤りを返すが、`defer f.Close()` はそれを捨てる。
書き込み用のファイルではこれが取りこぼしになり、
検査器が警告する既知の問題として残っている。

#### 帰結

- 複数のオブジェクトを解放する途中で誤りが起きることはない。
  したがって「残りの `dispose()` を呼ぶか」という問題が生じない
- 12.5 の型検査は「`dispose()` を持つ」だけでなく
  **「戻り値を持たない `dispose()` を持つ」** を要求する

なお、実装上の欠陥による異常終了は誤りとは別の分類である。
`dispose()` が誤りを返さないことと、
`dispose()` の実装に不具合がありえないこととは別の話になる。

### 12.8 誤りは値として返す［確定］

L^ は **例外機構を持たない**。Zig や Go と同じく、
失敗しうる操作は誤りを表す値を返し、呼び出し側がそれを受け取って処理する。

この選択は本章と 10 章の設計を大きく単純にしている。

「後始末の最中に例外が飛んだらどうするか」は他言語で難所とされてきた。
C++ の `terminate`、Java の抑制された例外、Python の `__context__` は
いずれもこの問題への対処である。

**誤りが暗黙に伝播しない以上、この問題は発生しない。**
`finally^` や `dispose()` の中で失敗しうる操作を呼べば誤り値を受け取るが、
それを外へ伝播させる手段がない。`finally^` は返り値も変更できない（10.5）。
構造的に閉じている。

誤りの表現、伝播の記法、値を受け取り損ねたことの検出は
[04-errors.md](04-errors.md) で決めた（旧 S14）。
誤りの種別は `errordef^` で宣言する型であり、
失敗しうる操作は成功時の型と種別の合併を返す。
`catch^` がその場で代替し、`try^` が呼び出し元へ返す。

## 13. 型の文法と束縛［確定］

### 13.1 シグネチャの形［確定］

関数と手続きの型は、定義と同じ記号で始め、
引数の型を並べ、`->` を置き、返り値の型を書き、`;` で閉じる。

```text
f^引数型, … -> 返り値型 ;
p^引数型, … -> 返り値型 ;
```

```lhat
p^number^, number^ -> number^ ;
```

これは「`number^` を2つ受け取り、`number^` を1つ返す手続き」を表す。

**返り値は1つである**（13.8）。複数の値を返したい場合はテーブルを返す。

02 の 6 章に述べた原則「開いた構造は `;` が閉じる」にそのまま従っている。

Memo.md L304–L308 は区切りを `:` と書いているが、これは撤回する。理由は 13.6 の (1)。

### 13.2 引数と返り値が空の場合［確定］

```lhat
p^number^, number^ -> ;      # 返り値なし
p^ -> number^ ;              # 引数なし
p^ -> ;                      # どちらもなし
```

#### `->` は返り値が空のときに限り省略できる［確定］

> `->` は、**返り値が空のとき** に限り省略できる。

```lhat
p^number^, number^;          # 2つ受け取り、返り値なし
p^;                          # 引数も返り値もなし
p^number^ -> string^;        # 返り値があるので -> が要る
f^ -> number^;               # 同上
```

無名の型の署名は長くなりやすいため、頻出する形を短く書けるようにする。

##### 逆向きは省略できない

引数が空の側を省略することはできない。

```text
p^number^;
```

これが「`number^` を1つ受け取り返り値なし」なのか
「引数なしで `number^` を1つ返す」なのかが決まらなくなる。

返り値を持たない手続きは頻出する一方、
引数を取らず返り値だけを持つ型は `f^ -> number^;` と書けば十分短い。
したがって省略形は前者の意味に固定する。

##### 構文解析は決定的である

型の羅列を読んだあと、`->` に当たれば返り値が続き、
`;` に当たればその羅列は引数だったと確定する。先読みを要しない。

##### `f^` は実質この省略形を使わない

Memo.md L152 のとおり関数は必ず返り値を持つため、
`f^` の返り値が空になることはない。

`f^` だけを特別扱いし、`f^number^;` を「`number^` を返す」と読ませる案は採らない。
`p^number^;` と `f^number^;` が同じ形で逆の意味になり、
本設計が一貫して排除してきた「文脈によって意味が変わる記号」に戻ってしまう。

規則は一様に保ち、`f^` はその条件を満たさないだけとする。

##### 定義との対応が取れる

省略を認めない場合、定義と型で見た目がずれていた。

```lhat
let^ foo = p^x:number^ { … }     # 定義。{ が区切るので -> を書かない
p^number^ -> ;               # その型。区切りを書かされる
```

省略を認めることで、型の側が `p^number^;` となり定義と対応する。

##### Memo.md L308 との関係

L308 は「省略できない方が間違えなくていい」としている。
懸念自体は妥当だが、引数と返り値の取り違えは型検査で捕捉される。
署名の文字列が長くなる不利益のほうが大きいと判断した。

### 13.3 `;` は省略できない［確定］

シグネチャは入れ子になりうる。内側の `;` がなければ、
その後の `,` がどちらのリストに属するか決まらない。

```lhat
p^number^, p^number^ -> number^ ;, number^ -> number^ ;
```

外側は「`number^`、`p^number^->number^;`、`number^` の3つを受け取り `number^` を返す手続き」。
内側の `;` が内側のシグネチャを閉じ、続く `,` が外側のリストのものであることを確定させる。

Memo.md L428 が同じ形を書いている。
`;` は装飾ではなく、この曖昧さを消すために必要な要素である。

### 13.4 引数名と既定値は型に含まれない［提案］

定義には引数名と既定値が書ける。

```lhat
let^ f = f^a:number^, b:number^=2 -> string^ { … }
```

型はこれらを持たない。`f^number^, number^ -> string^ ;` になる。

引数名と既定値は値の側の情報であり、
Memo.md L318–L323 の `f.parameters[0].name` や `.default` はそちらを参照する。

既定値を持つ手続きが、既定値を書いていない型に適合するかは未決（13.6 の (3) と併せて決める）。

### 13.5 合併は `|`［確定］

11.5 の (3) のとおり。

```lhat
k as^ number^|nil^
```

### 13.6 検討の記録

#### (1) 区切りは `->` に統一する［確定］

Memo.md L304–L308 は型のシグネチャで区切りを `:` と書いていたが、
定義の側は別の記号を用いる（01 の Q9）。
同じ概念に2つの綴りがある状態だったため、**`->` に統一する**。

```lhat
let^ f = f^a:number^, b:number^=2 -> string^ { … }   # 定義
f^number^, number^ -> string^ ;                  # 型
```

なお Q9 は当初 `::` を採っていた。
当時 `->` が後置再代入に使われており、記号の重複を避ける必要があったためである。
Q2 で再代入が前置形になり `->` が空いたこと、
および `:` を多用する中で `::` が視覚的に埋没することから `->` へ変更した（01 の 7.6）。

これにより2つの記号の役割が分かれる。

- **`:` — 名前と型を結びつける。** `a:number^` の引数注釈、
  構造的な型における `member : type`（(2) を参照）
- **`->` — 引数と返り値を区切る。** 定義でも型でも同じ

この整理は (2) の構造的な型にも効く。
そこで `member : type` を用いても `->` と衝突しない。

#### (2) オブジェクトの構造的な型 → 14.10 で確定

`t^{ dispose : p^self^; }` の形で書く。
判定は「少なくともこれらのメンバを持つ」。詳細は 14.10。

#### (3) 可変長引数 → 13.7 で確定

`...:型` の形で書き、同型可変長を既定とする。
型を省略した `...` は `any^` になる。詳細は 13.7。

#### (4) yieldable な手続きの型 → 13.9 で確定

コルーチンの型は `c^{ 受け取る型, 出す型, 返り値型 }` と書く。詳細は 13.9。

### 13.7 可変長引数［確定］

引数リストの末尾に限り、可変長の引数を置ける。
**`...` を引数名の位置に置き、その型を `:` の後ろに書く。**

```lhat
let^ sum = f^ ...:number^ -> number^ { … }
```

型としても同じ形になる。

```lhat
f^ ...:number^ -> number^ ;
f^ x:number^, ...:number^ ;
```

他の引数が `名前:型` の形をとるため、`...` をその名前の位置に置く。
型の側では通常の引数に名前が付かないが（13.4）、
`...` は名前ではなく可変長であることを示す印であり、衝突しない。

本体の中では `...` がそのまま集めた引数を指す。

#### 同型を既定とする

**可変長引数はすべて同じ型でなければならない。**
Go の `...int`、Swift の `Int...`、Kotlin の `vararg`、C# の `params` と同じ方式である。

静的に検査できることが利点である。

#### 型を省略すると `any^` になる

`:` 以降を省略した `...` は `any^` を意味する。

```lhat
f^ x:number^, ... ;          # 末尾の可変長は any^
f^ x:number^, ...:number^ ;  # number^ の可変長
```

異型を扱う手続きは短く書ける。

```lhat
let^ print = p^ ... ;
```

`any^` の場合、型の不一致は実行時にしか検出されない。
**その代償を負うのは型を省略した箇所だけ** であり、
可変長引数を使った時点で一律に静的検査が失われるわけではない。

すべての可変長引数を `any^` とする案もあったが採らない。
`print` のような異型の用例が正典的である以上、
それを既定にすると可変長を使うたびに静的検査が消えることになる。

#### 可変長ジェネリクスは採らない

型の並びごと型変数にして異型を静的に扱う機構（パラメータパック）は導入しない。

TypeScript の可変長タプル型、Swift 5.9 のパラメータパック、
Python の PEP 646、C++ のパラメータパックがこれにあたるが、
いずれも型システムとして重い。

**後から追加できる** ため、当面は同型で始める。

#### 位置と個数

- 可変長引数は **引数リストの末尾** にのみ置ける
- 1つの引数リストに1つまで
- 既定値を持つ引数（13.4）との併用の規則は未決とする

#### `...` の照合順序［実装上の注意］

字句解析器は `...` を `..`（連結）より先に照合しなければならない。
順序を誤ると可変長の印が `..` と `.` に分解される（01 の 7.5）。

#### `any^` は頂点型。ただし絞り込むまで何もできない［確定・旧 S16］

> **`any^` にはあらゆる値が適合する。
> そして `any^` の値にできるのは、渡すことと `is^` で絞り込むことだけである。**

TypeScript の `unknown` にあたる。`any` ではない。

##### `table^{}` とは同一視しない

要求するメンバがゼロの型として `t^{}` と同一視する案は採らない。

14.10 の「少なくともこれらを持つ」により `t^{}` はあらゆる **テーブル** に適合するが、
`number^` は適合しない。テーブルではないためである。
可変長引数に数値を渡せなくなり、13.7 の用例が成立しない。

`any^` は **テーブルの頂点** ではなく **すべての値の頂点** である。

##### 脱出口にはしない［重要］

`x : any^` に対して `x.foo` や `x + 1` を書けるようにする案（TypeScript の `any`）は
**採らない**。書けば静的な誤りとする。

理由は既存の決定の側にある。

- [04-errors.md](04-errors.md) の設計全体が **「絞り込むまで値を使えない」** という規律である。
  8.1 のとおり `number^|error^` は `number^` の位置で使えない。
  `any^` を脱出口にすると、ここにだけ穴が開く
- 脱出口は報告を **遠くの実行時に飛ばす**。
  01 の 10.9 と 14.12 が採ってきた「書いた場所で報告する」と逆になる
- 13.7 が「すべての可変長引数を `any^` とする」案を退けた理由がそのまま当てはまる。
  **使うたびに静的検査が消える**

逃げ道は既にある。13.11 の `is^` と絞り込みである。

```lhat
p^ ...:any^ {
    for^ x in^ ... {
        if^ x is^ number^ { total := total + x }
    }
}
```

##### 渡すことはできる

**`any^` の値を `any^` を受ける位置へ渡すのは正当** である。
可変長引数の最も多い用途である転送はそのまま書ける。

```lhat
let^ log = p^ ... { print(...) }        # print も any^ を受ける
```

13.7 が挙げた `print` のように、値の形を見て振る舞いを変える手続きは
組み込みとして提供する。実行時の型タグ（03 の 2.1）を直接見られるためである。
同じことを利用者のコードで書く場合は `is^` で絞り込む。

##### 判定への影響

- **互いに素**（14.12）— `any^` はあらゆる値を含むので、**何とも互いに素にならない**。
  したがって `any^` を取る引数と多重定義することはできない
- **`is^`**（13.11）— `x is^ any^` は左辺が何であっても常に真であり、
  問いとして空である。13.11 のとおり **誤りとする**

### 13.8 多値返却は持たない［確定・旧 S17］

**関数と手続きの返り値は常に1つである。** Lua のような多値返却は採らない。

複数の値を返したい場合はテーブルを返し、束縛の側で分解する。

```lhat
let^ divmod = f^ a:number^, b:number^ -> t^{ q:number^, r:number^ } { … }

q, r := divmod(7, 2)
```

#### 用例はすべて別の手段で足りる

| 用途 | 多値なしでの表現 |
| --- | --- |
| 誤りの返却 | `T\|Error^` の合併（12.8） |
| 値の交換 | 多重代入 `a, b := b, a`。返り値と無関係 |
| `for^k, v in^t` | 反復子が組を出し、束縛側で分解 |
| 複数の関連値 | テーブルを返し、束縛側で分解 |
| 可変長の取り出し | `...` は集合であり、束縛側で分解 |

Python の `for k, v in d.items()`、Rust の `for (k, v) in map` と同じ形になる。
いずれの言語も多値返却を持たない。

#### 決め手は型システムの一様性

多値は **L^ の型システムの中で唯一「型でないもの」** だった。
値の並びであって、それ自体を名指せない。

その不規則性が各所に波及していた。

- コルーチンの型（13.9）の区画に多値の合併を書けるかが決まらない
- `overload^` の交差型（14.12）、関数型の合併、部分型の判定
- 可変長引数へ渡す際の展開規則

多値をなくすと、これらは **解決するのではなく発生しなくなる**。
Q6 の `{^` 不採用や Q2 の前置形への変更と同じ形の判断である。

とりわけ Lua の「途中の呼び出しは1値に切り詰め、末尾だけ展開する」という規則は
誤解を招くことで知られているが、その規則自体が不要になる。

#### 性能上の代償は実装で吸収する

テーブルを返すと確保が生じるという懸念は、実装の側で解ける。

**多値返却は呼び出し規約であって言語機能ではない。**
Lua はそれを言語の表面に露出させたが、L^ は実装に留める。

- Swift と Rust はタプルを型として持ちながら、ABI ではレジスタで返す
- `q, r := divmod(7, 2)` のように直後に分解される形は、コンパイラが平坦化できる

したがって **タプルを言語に導入する必要はない**。
テーブルが唯一のデータ構造であるという方針（Memo.md L23）も維持される。

#### 必要になるもの — 分解束縛

13.10 を参照。

### 13.9 コルーチンの型［確定］

`yield^` を含む手続きは呼び出すとコルーチンを返す（15 章）。
そのコルーチンの型を `c^{ … }` と書く。

```text
c^{ 受け取る型, 出す型, 返り値型 }
```

3つの型は中断点によらず **一様** である。
本体中のすべての `yield^`（`yieldall^` が委譲する先も含む）は、
出す型・受け取る型ともに単一の型に統一されなければならない。
異なれば型エラーになる（15.2 改。旧版は中断点ごとの出す型を合併していたが、
異種の yield^ を型で見分けさせない方針に変えた）。

Python の `Generator[YieldType, SendType, ReturnType]`、
TypeScript の `Generator<T, TReturn, TNext>` と同じ構成である。

#### 受け取る型はどう決まるか［15.2 改］

`yield^` 自体には型を書く構文がない。
受け取る型は、その値を直接受け取る `let^` 束縛の型注釈から決まる。

```lhat
let^ a:number^ = yield^ 1   # 受け取る型は number^
```

値を使わず捨てる `yield^ expr;` は注釈を要らない —
何も受け取らないので、受け取る型に何も言わないからである。
一方、束縛以外の位置（式の途中に埋め込む、`:=` で再代入する）に書かれた
`yield^` は、注釈の書き場がないため誤りとする。

#### `c^` は型構成子として復活する

15.1 で廃止したのは **サブルーチンの定義子** としての `c^` である。
型を書く記号としての役割は別であり、衝突しない。

`table^{ … }` と同じく「ハット識別子 + `{ … }`」の形をとる。

#### 区切りに `->` を使わない

`c^` は `f^` や `p^` と構造が異なるため、
`->`（引数と返り値の区切り）を流用すると紛らわしい。
3つの型はカンマで区切り、`{ }` で囲む。

#### 中断点ごとの型は表さない

3つの型は中断点によらず一様であり、15.2 改によりすべての `yield^` が
実際に一致することを型検査が要求する。
順序まで型で表すには **セッション型 / typestate** が要るが、
03 の段階構成に載せるには重い。

順序（何回目の再開でどの中断点か）までは表さないので、
消費側が中断点を取り違えても実害はない — どの中断点でも型は同じだからである。

#### 再開の結果

コルーチンを再開した結果は「出す型」と「返り値型」の合併になる。

**合併が本来必要なのはこの位置** であり、コルーチンの型そのものではない。

まだ続くのか終わったのかは、**この合併からは判別できない**。
2つの型が一致していれば値が同じ形で現れるためである。
判別は `done()` に任せる（15.6 改）。
一致が例外ではなく既定で起きること（終端に到達した本体は `nil^` を返すため）も
15.6 改に述べる。

返り値型は **最終再開が受け取る値の型** であり、
03 が言う「`p^` を呼んだ結果の型」とは別のものである。15.6 改を参照。

#### 終われない本体には返り値型がない［確定］

本体が **終わりようがない** 場合、最終再開そのものが存在しない。
返り値型は「そこにある値の型」なので、**置くべき値がない**。

```lhat
let^ g = p^ { repeat^ { yield^ 1 } }   # 03 により終端に到達しない
let^ v : number^ = g().start()          # 通る。nil^ は混ざらない
```

この位置に `nil^` を置くと、**決して届かない値を消費側全員が絞り込む** ことになる。
`p^` の署名が返り値なしを表せるのと同じく、
コルーチンの型も第3枠を持たないことがある。

判定は 03 の「脱出をすべて数える」に一致する。
**値を作らない脱出が1つでもあれば返り値型を持つ。**

```lhat
p^ { repeat^ { yield^ 1 } }          # 脱出なし        → 返り値型なし
p^ { repeat^ { yield^ 1 break^ } }   # break^ で終わる → nil^
p^ { yield^ 1 }                      # 終端に到達      → nil^
p^ { yield^ 1 return^ }              # 裸の return^    → nil^
p^ { yield^ 1 return^ 9 }            # 値を返す        → number^
```

##### 書き表す形は3つのまま

`c^{ … }` の記法は変えない。**注釈として書く場合は常に3つ並べる。**
第3枠を持たない型は推論からしか生まれない。

終われないコルーチンに `c^{R, Y, nil^}` と注釈を書くことは妨げない。
決して起きない再開について何を言っても、その主張が破られることはないためである。

### 13.10 分解束縛［確定・旧 S18］

多値返却を廃止した（13.8）ため、
複数の値を返す手続きはテーブルを返す。それを受け取る側の記法。

```lhat
let^ q, r = unpack^ divmod(7, 2)
let^ q:number^, r:number^ = unpack^ divmod(7, 2)   # 型注釈つき
q, r := unpack^ divmod(7, 2)                       # 既存の変数へ（8.6）
```

#### 各名前は自分の位置の型を受け取る［確定］

14.10 のとおり列の側も型を持つので、
分解した名前にはそれぞれ **その位置の型** が付く。

```lhat
let^ q, r = unpack^ { 1, "a" }
let^ n : number^ = q     # 通る
let^ s : string^ = q     # 誤り
```

注釈を書いた場合はその位置の型が収まることを要求する。
型が何も述べていない位置については何も言わない（14.10）。

#### `unpack^` は右辺に置く

分解であることは **値の側に `unpack^` を付けて** 示す。

これは多重定義と区別するために要る。両者は左辺の形が同じであり、
印がなければ右辺の個数を数えなければ判別できない。

```lhat
a, b := x, y                # 多重定義。右辺は2つの式。対で束縛する
q, r := unpack^ f()         # 分解束縛。右辺は1つの値。分解して束縛する
```

Python はタプルを持つため `x, y` が1つの値になり、両者が同じ機能に統合される。
L^ は 13.8 でタプルを持たないと決めたため統合できない。
個数で意味を切り替える設計は、Q8・Q3・S11 の (3) で排除してきた
「文脈によって意味が変わる」形にあたるため採らない。

##### 左辺に置く案から変更した理由

当初は分解の印を左辺に置き、`let^ q, r := f()` と書く案を採っていた。
右辺へ移したのは次の理由による。

- **再代入に適用できる。** 分解の印を左辺の語が兼ねる形では
  既存の変数への分解を表せず、一度束縛してから代入する2段の回避が必要だった。
  値の側に印を置けばその制限が消える
- **印が分解される側に付く。** 分解は値に対する操作であり、束縛の形式ではない。
  左辺に置く形は、位置と意味がずれていた

3つ目の理由として「`let` の慣用とのずれ」を挙げていた。
他言語の `let` は束縛の導入一般を指すが、当時の L^ は通常の定義に要らなかった、
というものである。

**この理由は 8.6 で失効した。** `let^` は現在すべての定義に付き、
他言語と同じ「束縛の導入」を意味する。
ただし `let^` が示すのは束縛であって分解ではないため、
上の2つの理由により `unpack^` は右辺のままとする。

##### 対象リストは通常の定義と同じもの

右辺に印を移したことで、分解の対象は **多重定義の対象リストそのもの** になる。
型注釈つきの対象も、単独の定義 `let^ x:number^ = 1` と同じ規則で解析される。

##### `{ … }` を使わない理由

`{q, r} := f()` のように波括弧で標識する案もあったが採らない。

- **10.7 と衝突する。** 素の `{` はテーブルリテラルであるため、
  構文解析器は文頭の `{` をまずテーブルリテラルとして読み始め、
  `:=` に達して初めて誤りに気づく。後戻りか先読みを要する
- **`{ }` の役割が既に4つある。** テーブルリテラル、ブロック、
  構造的な型 `t^{ … }`、コルーチンの型 `c^{ … }`。5つ目を負わせたくない

#### `unpack^` の位置と個数［確定］

- `unpack^` は **`let^` の値または `:=` の値としてのみ** 現れる
- `unpack^` を用いる場合、**値は1つでなければならない**。
  `a, b := unpack^ f(), 3` は誤り
- 再代入の対象には型注釈を書けない。変数は既に存在するため

#### 位置で分解する［確定］

分解は **位置** による。名前による分解は当面設けない。

`for^ k, v in^ t` では利用者が変数名を決めるため、
名前による分解では成立しない。したがって位置による分解が必須になる。

```lhat
for^ k, v in^ t { … }
```

`for^` の束縛位置は `in^` が続くため多重定義と紛れず、`unpack^` を要しない。

#### 合わない場合は誤りとする［確定］

- 右辺がテーブルでない場合は誤り
- 左辺の名前の個数と分解できる要素数が合わない場合も誤り

```lhat
q, r := unpack^ f()      # f が number^ を1つ返すなら誤り
```

Lua は余った変数に `nil` を入れるが、これは値リストの調整という仕組みに基づく。
13.8 で多値を廃止した以上、調整すべきリストが存在しない。
また `number^` は分解できる構造を持たない。

**分解できないものを分解しようとしたことは静的に検出できる。**
コンパイル時に捕捉できる誤りを実行時の `nil` に落とすと、
その `nil` は後段の型検査もすり抜ける。

relaxed（03 の 3.1）では実行時の検査に落ちるため、対話的な試行では緩くなる。

#### 入れ子の分解は当面設けない［確定］

`q, {b, c} := unpack^ f()` のような入れ子は当面認めない。
必要になった時点で改めて設計する。

### 13.11 `is^` と絞り込み［確定・旧 04 の E3］

`is^` は 11.6 の優先順位表に置かれていたが、意味が定まっていなかった。ここで定める。

#### `is^` は適合を問う［確定］

```lhat
x is^ T
```

> **`T` と書かれた位置に `x` を置けるか** を問う。真偽値を返す。

これは **型検査器が注釈に対して問うのと同じ問い** である。
したがって同じ型式は、注釈に書いても `is^` の右辺に書いても同じ意味になる。

```lhat
x : t^{a : number^}          # 少なくとも a を持つ（14.10）
x is^ t^{a : number^}        # 同じ判定
```

右辺は型であり、値ではない。

#### 完全一致の演算子は設けない［確定・重要］

`is^` を完全一致とし、部分型の判定に `isa^` を別に置く案があった。**採らない。**

14.10 が `t^{ … }` を **「少なくともこれらを持つ」** と定めている。
`is^` を完全一致にすると、同じ型式が
**注釈では「少なくとも」、`is^` では「ちょうど」** を意味することになる。
1つの綴りに2つの意味を与える形であり、
01 の Q8、11.5 の (3)、04 の 12.3 で退けてきたものと同じ形になる。

14.7 の側でも食い違う。`FooBar2 := FooBar .. def^{ … }` としたとき、
注釈 `x : FooBar` は `FooBar2` の実体を受ける。完全一致の `is^` は受けない。

さらに、完全一致は構造に対してほとんど使えない。
14.10 が「ちょうどこれらだけ」を退けた理由がそのまま当てはまり、
メンバの多い値がどの構造にも適合しなくなる。

**適合として定義すれば、完全一致の振る舞いは右辺の書き方で得られる。**

```lhat
e is^ IOError.NotFound       # 葉の型。これ以外は適合しない
e is^ IOError                # 合併。部分型の判定として働く
x is^ t^{a : number^}        # 構造。「少なくとも」
```

区別が **どちらの演算子を選ぶか** ではなく
**右辺に何を書くか** に宿る。演算子を増やさずに済む。

型の同一性そのものを比べたい場合は `typeof^` を使う。

```lhat
typeof^(x) = typeof^(y)
```

#### 絞り込み［確定］

`is^` を `if^` の条件に直接書いた場合、分岐の中で左辺の型が狭まる。

```lhat
let^ r = parse(s)                        # number^|ParseError.Syntax|ParseError.Eof

if^ r is^ ParseError.Syntax {
    report(r.line, r.column)         # ここでは r : ParseError.Syntax
    else^:
        use(r)                       # ここでは r : number^|ParseError.Eof
}
```

規則は次のとおり。

- **真の側** — 合併の腕のうち `T` に適合するものだけが残る
- **偽の側** — 適合しない腕だけが残る
- 腕が1つも残らない場合、その分岐は到達しない

#### 左辺の推論からは報告しない［確定］

左辺の静的な型から `is^` の答えが決まる場合がある。

```lhat
let^ x : number^ = 1
x is^ string^      # 互いに素。常に false^
x is^ number^      # 全体が適合する。常に true^
```

> **これらを誤りとして報告しない。**

`is^` は **実行時に問うための記法** である（13.11 冒頭）。
検査器が「自分の知っている型から見れば答えは決まっている」として拒むと、
13.7 が `any^` を導入した目的——静的な型より広い値を受け取り、
使う側で絞り込む——を検査器の側から狭めることになる。

左辺の型は後から広がりうる。いま冗長な `is^` が、
引数の型を緩めた翌日には意味を持つ。**推論の結果を根拠に書き手を縛らない。**

比較演算子（`=`、`<` など）は互いに素な被演算子を誤りとする。
そちらには「それでも実行時に確かめたい」という読みが存在せず、
`is^` にはそれが存在する。**この非対称は意図したものである。**

#### `is^ any^` だけは誤りとする［確定］

右辺が `any^` の場合に限り誤りとする。

```lhat
x is^ any^         # 誤り
x is^ any^|nil^    # 誤り。13.5 により any^ に潰れる
```

上の規則と衝突しない。**根拠が左辺にないためである。**

13.7 が `any^` をあらゆる値の頂点と定めているので、
`x is^ any^` は **左辺が何であっても、将来何に変わっても** 真である。
左辺の型を読んで決めているのではなく、**右辺だけで決まっている**。
「後から意味を持つ」余地が存在しない唯一の形になる。

> **左辺の推論を根拠にしては報告しない。右辺だけで決まる無意味さは報告する。**

`T & any^` は 14.5 により `T` に潰れるため、この規則には掛からない。

#### 決まっていること自体は捨てない

報告しないことと、知らないことは別である。
到達しない枝が分かることは **最適化の材料** になる
（03 の 5.1 の特殊化と同じ位置づけ。strict で型が確定した箇所にのみ効く）。

- 常に真の `is^` — 偽の側の枝を落とせる
- 常に偽の `is^` — 真の側の枝を落とせる
- 絞り込みで腕が尽きた枝 — 同上

診断に回さず最適化に回すのは、**書き手に直させる話ではない** ためである。
冗長な `is^` を書いた本人がそう思っていない場面は普通にあり、
生成されたコードや、型が後から狭まった箇所では特にそうなる。

#### 絞り込める対象［確定］

**名前、および名前から `.` でたどった安定な経路** に限る。

```lhat
if^ r is^ T { … }              # 絞り込む
if^ a.b is^ T { … }            # 絞り込む
if^ f() is^ T { … }            # 絞り込まない。呼ぶたびに値が変わりうる
if^ a[i] is^ T { … }           # 絞り込まない。i が変われば別の要素
```

呼び出しと添字を外すのは、**2度目に同じ値である保証がない** ためである。
絞り込みは「今検査した値が、この後も同じ型である」という主張であり、
それが成り立たない対象に広げると、静的に確かめたことが実行時に崩れる。

再代入は絞り込みを打ち切る。

```lhat
if^ r is^ ParseError.Syntax {
    r := parse(t)              # ここで絞り込みは失われる
    report(r.line)             # 誤り
}
```

#### 組み合わせ［確定］

- `!(x is^ T)` — 真偽が入れ替わる。真の側と偽の側が入れ替わる
- `x is^ T and^ …` — `and^` の右側と真の側で絞り込みが効く
- `x is^ T or^ …` — `or^` の右側では偽の側の絞り込みが効く
- `elseif^` の連鎖 — 前の条件が偽であったことが積み上がる

11.5 の (5) の連鎖（`a < b < c`）に `is^` を混ぜた場合、
連鎖全体の値は真偽値になるが、**絞り込みは行わない**。
どの被演算子について何が言えるかが自明でないためである。

#### `catch^` も絞り込む

04 の 4.1 のとおり、`expr catch^ v` 全体の型からは誤りが除かれる。
これは `is^` と同じ仕組みであり、規則を別に持たない。

### 13.12 `_^` — 束縛しない受け皿［提案・未実装］

> **`_^` は名前が要らない位置に書ける。変数ではないので読めず、
> 同じ並びに何度でも書ける。**

#### 動機

型注釈は要るが名前は要らない位置がある。最も分かりやすいのは 15.11 の `_yield^` で、
R を言うためだけに `let^` を書くことになる。

```lhat
let^ got : string^ = _yield^ 1     # got は誰も読まない。しかも実行時は nil^
```

名前を作ってしまうと、**その名前が嘘を持つ**。
`got` は `string^` を名乗るが、`_yield^` は再開されないので中身は `nil^` になる。
`_^` を使えば嘘を持つ入れ物そのものが存在しない。

```lhat
let^ _^ : string^ = _yield^ 1      # R は string^。読める名前はどこにもない
```

分解束縛（13.10）では位置ごとに要否が分かれるので、使い回せることが要る。

```lhat
let^ _^ : number^, _^ : number^ = _yield^ 1
let^ _^, v = unpack^ pair()
```

#### 書ける場所

- `let^` と `:=` の対象 — 値を捨てる
- 分解束縛の各位置（13.10）
- 引数（13.1）— 署名に合わせるが本体で使わないもの。`override^` で効く
- `for^ … in^` の焦点（16.3）— 対の片方だけ要る場合
- `with^ _^ := open() { … }` — 名前は要らないが 12.6 の破棄は要る

#### 読むと誤り

`_^` は名前ではないので、式の位置に現れたら誤りとする。
Go の空白識別子、Rust・Erlang・OCaml のワイルドカードパターン、
C# の破棄、Java 22 の無名変数がいずれもこの形をとっている。

#### `_x` は採らない［確定］

Rust の `_x`、Erlang の `_X` は **実在する束縛で、未使用警告だけを黙らせる**。
`_^` の「破棄」とは別の意味であり、**採用しない**。

L^ の `_` 接頭辞は破棄の意味で揃っている。

- `_^` — 束縛を破棄する
- `_yield^` — 中断を破棄する（15.11）

ここに `_x` を足すと接頭辞が二義になる。
Elixir が `_x` を実際に使ったときに警告を出しているのは、
この不一致を後から補正しているのに等しい。最初から入れない。

#### 15.8 は黙らせない

`let^ _^ = gen()` は、コルーチンを作って何もしないことに変わりがない。
15.8 の誤りは出続ける。あの規則は「使っていない」ではなく
**「効果がない」** を言っているので、破棄を書いても効果は生えない。

#### `_^ := expr` は要らない

Go は `_ = foo()` しか持たないが、L^ には `let^ _^ = foo()` がある。
再代入形を別に持つ意味がない。

#### 字句には手を入れない

01 の 134 が `_` を識別子の開始文字として許しているので、
`_^` はいまでもハット識別子として読める。桁区切りの `_`（01 の 266）とは位置が違う。
ハット識別子はもともと普通の名前ではないため、
「`_^` は変数ではない」も既存の読み方から外れない。

## 14. オブジェクトモデル［確定］

13.6 の (2) が求めていた「オブジェクトの構造的な型」を書けるようにするための土台。

### 14.1 `def^` が唯一の機構［確定］

利用者定義の型は **`def^` のみ** で作る。

Lua の metatable に相当する機構は **設けない**。
オブジェクトに委譲先を指す場を持たせ、実行時にそれを差し替える手段は提供しない。

### 14.2 委譲の連鎖は定義時に確定する［確定・重要］

**実行時にプロトタイプの連鎖を張り替えることはできない。**

これは利便性の判断ではなく、型システムからの要請である。

委譲先を実行時に差し替えられると、
**あるオブジェクトがどのメンバを持つかを型検査器が知りえない**。
11.3 と 12.5 が定めた構造的な型検査は、その時点で成立しなくなる。

Lua で `setmetatable` がいつでも呼べるのは Lua が動的型付けだからであり、
静的検査を採る L^ には持ち込めない。

したがって次が成り立つ。

- インスタンスの形とメソッド集合は、生成時に定義によって確定する
- 委譲の連鎖は `..` により **定義の時点で** 組まれる（14.5）
- 連鎖は静的に既知であり、型検査器は任意の式について構成要素を決定できる

プロトタイプ方式の利点（名前による階層を持たない、合成で組む、ダックタイピング）は
そのまま保たれる。外したのは静的解析を壊す部分だけである。

### 14.3 メソッドとフィールドを分ける［確定］

`def^` の中で、**インスタンスごとに複製される場** と
**定義ごとに1つだけ存在するもの** を分けて書く。

- フィールドの雛形 — インスタンスごとに複製される。関数・手続きは置けない
- メソッド — 定義ごとに1つ。インスタンスは参照するだけ

Lua の `__index` が存在する理由がまさにこの分離である
（メソッドは共有し、フィールドは複製する）。
L^ ではそれを暗黙の仕組みではなく、**構造として明示する**。

### 14.4 `self^` がメソッドを標識する［確定］

第一引数に `self^` を取る関数・手続きは **インスタンスメソッド** として扱う。

```lhat
let^ methodA = p^self^ { print(self^.value1) }
```

`xxx.methodA()` と呼び出すと、`xxx` が暗黙の第一引数として渡される。
暗黙に渡したくない場合は次のように書く。

```lhat
let^ method = foo2.methodA
method(foo2)
```

`self^` を取らないものは **静的メンバ** になる。
インスタンスか静的かを表す修飾子は要らない。シグネチャの形が決める。

#### 括弧は束縛を外さない［確定］

判定は **呼び出し対象がメンバアクセスの形かどうか** だけで行う。
括弧で包んでも形は変わらない。

```lhat
(foo2.methodA)(foo2)   # 誤り。依然として束縛形であり、引数は 0 個
```

外すには 14.4 のとおり **名前に取り出す**。それが唯一の手立てである。

`.` は 11.6 の最強の水準にあるため、`(x.m)` の括弧は
**優先順位のためには決して必要にならない**。したがって
「外す」側に倒すこともでき、非束縛形をその場で書けるという利点はある。
それでも外さないのは、失うものが2つあるためである。

- **「括弧で囲むのは常に安全」が崩れる** — 整形器やコード生成器は
  式を機械的に括弧で包む。呼び出し対象の位置だけ意味が変わるなら、
  そのすべてに特例が要る
- **見た目が近い2つが別物になる** — `(x).m(1)` は受け手を包んでおり束縛される。
  `(x.m)(1)` が束縛されないなら、括弧がどこまで掛かっているかを
  読み手が毎回判定することになる

一時変数に受ける形（14.4 の例）は初等的であり、
その場で書けないことの不便は小さい。
JavaScript も同じ側に倒れており、外すには参照を捨てる細工
（`(0, obj.m)()`）が要る。

受け手の側を括弧で包むのは別の話であり、こちらは影響を受けない。

```lhat
(if^ cond: x el^: y;).foo()   # 呼び出し対象は (…).foo。受け手は括弧の値
```

インスタンスのメンバへの参照は `self^` を介して行う。
定義側のメンバへの参照は `class^` を介して行う。

### 14.5 合成は `..`、型の表示は `&`［確定］

定義の合成（継承）は連結演算子 `..` で書く。単一継承のみ。

```lhat
let^ FooBar2 = FooBar .. def^{ … }
```

`..` を用いるのは順序に意味があるためである（Memo.md L357）。

一方、型としての表示には `&` を用いる。
型の情報は合成の順序によらないためであり、
`|`（合併、11.5 の (3)）と対になる。

- **`|`** — 合併。いずれかの型である
- **`&`** — 交差。すべての構造を備える

TypeScript が同じ2つを持つ。`&` は Q3 でビット演算を演算子から外したため空いている。

#### 右辺は `def^` リテラルでなくてよい［確定］

Memo.md L349 の `aspect..protocol..prototype..def^{ … }` のとおり、
名前で束縛済みの定義を並べて合成できる。

```lhat
let^ D = A .. B .. def^{ … }
```

14.2 のとおり連鎖は定義時に確定するので、コンパイラは名前を辿って
全パートを順に展開する。**型もこれと一致しなければならない** —
両辺のメンバをすべて備え、インスタンスは両方の雛形を持つ。

`new^` は書かれていなくても 14.11 が与えるため両辺に必ずある。
これは衝突として扱わず、合成後のインスタンスを返すものに作り直す。

#### 名前形での同名は曖昧になる［確定・14.5改］

14.12 の印（`override^` `overload^`）は `def^` の中にしか書けない。
名前で持ち込んだ定義は、相手を知らずに書かれているので印を持たない。
したがって **どちらも「答え」ではない**。

> **両辺が同名のメンバを持つとき、合成そのものは成立する。
> その名前が合成した型を通して届かなくなる。**

```lhat
let^ Draw = def^{ self^{}, reset := f^self^ -> number^ { return^ 1 } }
let^ Save = def^{ self^{}, reset := f^self^ -> number^ { return^ 2 } }

let^ Both = Draw .. Save        # 成立する
Both.new^().reset()             # 誤り。どちらとも決まらない
Both.new^().draw()              # 片方だけが持つ名前は普通に届く
```

黙って右辺を勝たせる案は採らない。
互いを知らない2つの定義の一方が他方の実装を差し替えてしまうのは、
14.12 が印を要求してまで防いでいる事故そのものである。

##### 側を名指せば届く［確定］

逃げ道には **新しい記法が要らない**。14.4 の「メソッドを値として取り出す」がそれである。

```lhat
let^ drawReset = Draw.reset
let^ saveReset = Save.reset

let^ o = Both.new^()
drawReset(o)      # 1
saveReset(o)      # 2
```

構造的型付けなので、取り出したメソッドは
**それに適合する任意のインスタンス**に適用できる。
`Draw` の系統でなくてもよい。

Rust の `Trait::m(&x)`、Go の埋め込み（同じ深さで衝突した名前は昇格せず
`x.A.foo` で届く）、C++ の `x.A::foo()` と同じ形である。
Eiffel の `rename` は合成側で改名する別の解だが、記法が重い。

##### 実行時にも書かない［確定］

曖昧な名前は平坦化したテーブルに **書き込まない**。
最後に書いた側が残ると、検査器が「届かない」と言っている名前が
実行時には値を持つことになるためである。

##### 場の衝突は誤りのままとする［確定］

メソッドは定義側にあり共有されるので、上の逃げ道が効く。
**場（`self^{ … }` のフィールド）にはこれがない。**

平坦化したインスタンスは1つのテーブルであり、`x.A.n` にあたる区画が存在しない。
落とせば両側のメソッドが実行時に何も読めなくなる。
したがって場の衝突は `..` の位置で誤りとする。

書き手の側の答えは 14.15 にある — **ミックスインは場を持たず、宣言する**。

```lhat
let^ A = def^{ self^{ abstract^ v : number^ }, … }
let^ B = def^{ self^{ abstract^ v : number^ }, … }
let^ D = Host .. A .. B      # 衝突しない。宣言どうしは対になる
```

### 14.6 フィールドの雛形は `self^`［確定］

インスタンスごとに複製される場は `self^{ … }` と書く。

```lhat
let^ FooBar = def^{
    self^{
        value1 := 0,
        value2 := "",
    },
    methodA := p^self^ { print(self^.value1) },
}
```

Memo.md L350 の `self^={ … }` に対応する。
インスタンスのメタ変数 `self^` と語が一致する。

`proto^` は採らない。
慣例では「プロトタイプ」は委譲先を指す語であり（Self、JavaScript）、
雛形の意味で用いると逆の連想を招く。

### 14.7 インスタンスは定義側のメンバも見る［確定］

Memo.md L295 のとおり、インスタンスから定義側のメンバを参照できる。

```lhat
f.classmethod()   // 合法
```

したがって **インスタンスの型は定義の構造をそのまま含む**。
`typeof^(インスタンス)` はその定義を返し、
`new^` や静的メンバがその構造に現れるのは正しい。

構造のうち `self^{ … }` の区画が「インスタンスごとに複製される部分」を示す。
共有される部分との区別は記法上そこで付く。

この帰結として、注釈に定義名を書くと **その定義の構造すべて** を要求することになる。
より緩く「必要なメンバだけ」で受けたい場合は、構造をそのまま書く（14.10）。
どちらを使うかは書き手が選ぶ。

### 14.8 数値の型は `number^` ひとつ［確定］

整数と実数を型として区別しない。どちらも `number^` である。

01 の 4.1 が整数リテラルと実数リテラルを別のトークンとしているのは
値の表現に関する区別であり、型の区別ではない。
実行時に内部表現を区別することはありうる。

Lua 5.3 以降が同じ構成を採っている。
型としては1つで、内部に整数と実数の2つの表現を持つ。

#### 桁が溢れたら実数へ広げる［確定・14.8改］

> **整数でいられる間は整数。いられなくなったら実数。**

`+` `-` `*` と単項 `-` は、結果が整数に収まらなければ実数で計算し直す。

```lhat
f(20)    # 2432902008176640000   整数のまま
f(21)    # 5.10909e+19           広がる
f(100)   # 9.33262e+157
```

##### 誤りにはしない［確定］

04 の 11.2 が「失敗しうる操作は返り値を合併にする」と定め、
**すべての除算が合併を返すと普通の算術が書けなくなる**としている。
オーバーフローを誤りにすると `+` `-` `*` のすべてが
`number^|ArithError.Overflow` になり、この判断と衝突する。

##### 折り返しも採らない［確定］

Lua 5.3 は折り返す。L^ は採らない。`100!` が `0` になるのは
近似ですらなく、**嘘**だからである。

Lua が折り返すのは性能のためではなく、整数を入れた目的が
配列添字・ビット演算・C 連携での厳密な64ビット意味論にあり、
`i = i + 1` が黙って実数になると `t[i]` が壊れるためである。

L^ にはこれが当たらない。

- **鍵は正規化される** — `t[2.0]` と `t[2]` は同じ鍵（04 の 11.3）
- **ビット演算がない** — Q3 で演算子から外した

##### 表現は約束していない［重要］

本節が最初から「実行時に内部表現を区別することはありうる」としか
言っていないため、広げても書き手への約束を破らない。

`**` は既に常に実数を返しており、この規則は **`**` に他を揃える** ことでもある。

代償は、正確さが黙って終わることである。`20!` までは正確で `21!` から近似になる。
多倍長整数を持てば正確なままにできるが、算術の経路に確保が入るため採らない。

### 14.9 定義の名前は束縛から採る［確定］

`def^` は **式のままとする**。名前を伴う宣言形式にはしない。

```lhat
let^ FooBar = def^{ … }
```

定義の右辺に `def^` 式が直接現れる場合、その名前を型の名前として採る。
それ以外の位置に現れた `def^` は無名であり、構造の記述だけが手掛かりになる。

Zig の `const Point = struct { … }` が同じ方式である。

#### 式のままにする理由

宣言形式にすると合成が書きにくくなる。

```lhat
let^ FooBar2 = FooBar .. def^{ … }
```

`def^` が式であることが、`..` による合成を自然にしている（14.5）。
通常の記号定義との直交性も保たれる。

#### 名前は型の同一性に関与しない［重要］

名前は **表示と診断のための札** にすぎない。
型の同一性は構造で決まる（11.3）。

名前を同一性に含めると公称型付けになり、
構造的な型検査を採るという決定と衝突する。

#### 誤りの種別だけは逆である［確定］

[04-errors.md](04-errors.md) の `errordef^` が宣言する種別は、
**名前が同一性そのもの** である。本節の規則に対する明示的な例外として扱う。

理由は記述している対象が違うことにある。
`def^` は **形** を記述しており、同じ形なら通じ合うべきである。
`errordef^` は **互いに異なる種別** を宣言しており、
別々に宣言した種別が混ざらないことが目的そのものである。

この違いは記法にも出る。`def^` は式であり名前を束縛から採るが、
`errordef^` は宣言形式であり名前を宣言に書く（04 の 2.4）。

### 14.10 構造をそのまま書く形［確定］

13.6 の (2) が求めていたもの。`table^{ … }` の形で構造を書き下す。

```lhat
t^{ dispose : p^self^; }
```

`with^` が要求する「戻り値を持たない `dispose()` を持つ」はこれで表せる。

綴りは 13 章と 14.4 に従う。
`dispose` はインスタンスメソッドなので第一引数が `self^` であり、
返り値がないので `->` の後ろが空になる。`->` は省略できない（13.2）。

#### `t^` は `table^` の別綴り［確定］

`table^` と `t^` は同じ型を指す。どちらで書いてもよい。

```lhat
t^{ dispose : p^self^; }
```

多値返却を廃止した（13.8）ことにより、
複数の値を返す手続きはテーブルを返すようになり、
署名の中に `table^` が頻出する。
**型の情報を文字列として得る場合は `t^` を用いる。**

`prolog^` と `prologue^`、`elseif^` と `ei^` と同じく別綴りの関係であり、
整形時にどちらへ寄せるかはフォーマッタが決める（5.3, 9.6）。

`t^` は Memo.md L706 でテーブルリテラルの記法候補として挙げられていたが、
Q6 でその案が退けられたため空いていた。同じ領域での再利用になる。

なお、頻出するという理由で型名を1文字に縮める方針を一般化はしない。
`table^` は多値廃止の結果として突出して頻出するため、例外として扱う。

#### 裸の `t^` は「テーブルの頂点」［確定］

メンバを1つも列挙しない `t^` は、`{ }` ごと省いて書ける。
**あらゆるテーブルに適合し、テーブルでないものには適合しない**（13.7 のとおり、
これは「あらゆる値の頂点」ではない。それは `any^` である）。

```lhat
let^ x : table^ = { a := 1 }    # 通る
let^ y : table^ = 5             # 誤り
let^ z : table^|nil^ = nil^     # 合併にも入る
```

`t^{}` と同じ型を指す。`{ }` を書くかどうかは綴りの違いにすぎない。
ほかの型名（`number^`、`string^`）と同じ形になるため、
合併・交差・`is^` のいずれにもそのまま載る。

##### `{` の直前では `{ }` を省けない

`t^` の直後に `{` があれば、それは **メンバの列挙** として読まれる。
本体の開き括弧をそこに置く形では、`{ }` を省略できない。

```lhat
p^ x:t^{} { … }     # 引数の型は「あらゆるテーブル」、{ … } が本体
p^ x:t^ { … }       # 誤り。{ … } がメンバの列挙として食われる
```

`t^{ … }` が構造を書く記法である以上、
1トークン先読みでこの2つを見分ける手立てはない。
`t^{}` と書けば済むため、規則を足してまで解く問題ではない。

#### 列の側も型を持つ［確定］

14 章はテーブルを **列と写像の両方** としている。
写像の側は名前でメンバを述べるが、列の側も同じく型を持つ。

```lhat
let^ t = { 10, "a" }
let^ n : number^ = t[1]     # 通る
let^ s : string^ = t[1]     # 誤り
```

##### 序数は 1 から［確定］

Lua に倣い、**列の側の添字は 1 から始まる自然数** である。
自然数でないものは序数ではなく、**常にキー** として写像の側に入る。

```lhat
let^ t = { 10, 20 }
t[1]      # 10。列の側
t[2]      # 20
t[0]      # 列ではない。キー 0 を引いている
```

位置は **1 から数え、キーを伴うエントリは飛ばす**。
処理系が密な部分を並べる順序と一致させる。

```lhat
let^ t = { 10, a := "x", 20 }
t[1]    # 10
t[2]    # 20   ← a は位置を取らない
t.a     # "x"
```

添字が書かれていればその位置（またはその名前）の型が分かる。
計算された添字は 04 の 11.3 のとおり不在でありうるため、何も言わない。

##### 位置の型は並べて書く［確定］

`t^{ … }` に **名前を伴わない型** を並べれば、それが位置の型になる。
1 番目から順に対応する。

```lhat
t^{ number^, string^ }        # 位置1が number^、位置2が string^
```

名前つきメンバと混ぜられる。**名前つきは位置を消費しない** ので、
書く順序を変えても位置の番号は動かない。

```lhat
t^{ number^, a : string^ }    # 位置1、および名前 a
t^{ a : string^, number^ }    # 同じ型。number^ はやはり位置1
```

判別は `:` の有無だけで決まる。`名前 :` で始まればメンバ、
それ以外は型式として読んで次の位置に割り当てる。1トークンの先読みで足り、
曖昧さは生じない。

```lhat
t^{ Foo }         # 位置1が Foo 型
t^{ Foo : Bar }   # 名前 Foo が Bar 型
```

13.8 がタプルを退けた判断は保つ。**値の言語は変えていない** —
テーブルは以前のままであり、その形をより細かく書けるようになっただけである。

##### 位置でも名前でもないキーの *型* はまだ書けない

値の側は `{ [k] := v }` で書ける（14.14）。
それに対応する **型の記法**（`t^{ [0] : number^ }` のような形）は
まだ設けていない。

リテラルのキーであれば型は推論から得られるため、
書けないことで困るのは「実行時にしか決まらないキーの型を宣言したい」場合に限られる。
その用途が具体化してから決める。

##### これが効く先

- `t[1]` — 上のとおり
- `unpack^` の分解束縛（13.10）— 各名前が自分の位置の型を受け取る
- `for^ k, v in^ t`（16.3）— 組の位置 1 が鍵、位置 2 が値

#### 判定は「少なくともこれらを持つ」［確定］

`table^{ … }` は **列挙したメンバを備えていること** を要求する。
それ以外のメンバを持っていてもよい。
列の側も同じで、**型が述べていない位置については何も言っていない**。

「ちょうどこれらだけ」とすると、
`open()` の戻り値のように多くのメンバを持つ値が何も適合しなくなる。

#### 注釈と `typeof^(x).signature` は同じ文法［確定・14.16 で実装］

型の情報を文字列として得る `typeof^(x).signature`（14.16）の出力は、
**注釈として書く形と同一の文法** とする。

異なる形式にすると型を書き表す言語が2つあることになり、
一方を読んで他方へ書き写せない。

この決定は具体的な適合条件を与える。

> `.signature` の出力は、そのまま型注釈として解析できなければならない。

名前を展開するかどうかは 14.16 で述べる — 現在の実装は常に構造を開く。

### 14.11 生成［確定］

#### 既定の `new^`

`new^` を定義しなかった場合、**引数を取らない既定の `new^`** が使える。

```lhat
let^ blahblah = FooBar.new^()
```

`self^{ … }` 節が各フィールドの初期化子を定めているので、それを評価して返す。

#### 初期化子は一部だけ書けばよい

`new^` の中では `self^{ … }` の形でフィールドを埋める。

```lhat
new^ := f^v1:number^, v2:string^ {
    return^ self^{
        value1 := v1,
        value2 := v2,
    }
}
```

**すべてのフィールドを書く必要はない。**
言及しなかったフィールドは雛形の初期化子から埋まる。

`self^{ … }` は定義の本体では雛形の宣言、`new^` の中では生成の記法になる。
どちらも「インスタンスのフィールド」を指しており、語としては一貫する。

#### 初期値は生成のたびに評価される［確定］

雛形の `名前 := 式` は、**格納された値ではなく初期化子** である。
生成のたびに式が評価され、その結果がそのインスタンスのフィールドになる。

```lhat
self^{ items := {} }
```

これで **可変な初期値が全インスタンスで共有される問題は起きない**。
生成ごとに `{}` が評価され、別のテーブルができる。
Python の可変な既定引数にあたる罠が、そもそも存在しなくなる。

Java と C# のフィールド初期化子が同じ方式である。

雛形を格納された値として持ち、生成時に深く複製する案もあった。
だが複製の費用が構造の大きさに比例して読みにくくなるうえ、
「どこまで深く複製するのか」という問いを生成のたびに背負うことになる。
初期化子として扱えばその問いが消える。

型の情報には影響しないため `typeof^(x).signature` の形は変わらない（14.10, 14.16）。

##### 評価の順序と範囲［確定］

初期化子は副作用を持ちうるので、いつ何が評価されるかを定めておく。

- **書かれた順に評価する** — `self^{ … }` 節に並んだ順序
- **`new^` が明示したフィールドの初期化子は評価しない** —
  上書きされる値を作るために副作用を起こすのは筋が通らない
- **評価は定義が書かれた場所の環境で行う**

3つ目から次が従う。

> 初期化子から `self^` は見えない。`class^` は見える。

雛形は定義の本体に書かれたものであってメソッドではない。
その位置に立っているインスタンスは存在しないので、
`self^` は指すものを持たない。一方、定義は存在するので `class^` は指せる。

これは制限のために置いた規則ではなく、書かれている場所からの帰結である。
同時に、**初期化の途中のフィールドを読む余地** も消える。
Java では初期化子から `this` と先行フィールドが見えるためこの穴が残るが、
L^ では見えないので順序を知らずに書いても壊れない。

#### 明示的な複製は `deepclone()`［確定］

値を複製する操作そのものは、組み込みの `deepclone()` として別に提供する
（Memo.md L11）。生成とは無関係で、書き手が必要な場所で呼ぶ。

**複製の深さ、循環の扱い、複製できない値の扱いは `deepclone()` の実装時に定める。**
生成がこれに依存しなくなったため、この決定を後回しにできる。

### 14.12 同名メンバ — `override^` と `overload^`［確定］

#### 既定では誤り

合成した定義の側で、元の定義と同名のメンバを定義することは **誤り** とする。
Memo.md L297 が「警告、もしくはエラー？」として保留していた箇所を、誤りに定める。

#### `override^` — 置き換える

意図して置き換える場合は `override^` を指定する。

```lhat
let^ Bar = Foo .. def^{
    override^
    foo := p^ { print("b") },
}
```

##### 置き換えは置換可能でなければならない［確定］

> `override^` した定義は、**元の定義の位置でそのまま使えなければならない**。
> 引数はより広く、返り値はより狭くしてよい。逆は不正。

- **引数を広げるのは正当** — `p^string^;` を `p^string^|number^;` で
  置き換えるなら、元が受けていたものはすべて受けられる
- **返り値を狭めるのは正当** — 元が `number^|nil^` を返す位置で `number^` を返すなら、
  受け手の想定を裏切らない
- **引数を狭める、返り値を広げるのは不正**

```lhat
let^ Foo = def^{ self^{}, foo := p^ { print("a") } }

let^ Bar = Foo .. def^{
    override^
    foo := p^x:string^ { print(x) },   # 不正。引数を空から string^ 必須へ狭めている
}
```

シグネチャの完全な一致を求める案もあるが、それでは返り値を絞る正当な置き換えまで
禁じてしまう。Java の共変な返り値、C# 9 以降の共変な返り値が認めている範囲にあたる。

##### `self^` は検査の対象外［確定］

第一引数 `self^` の型は、元の定義では合成前の型、置き換え側では合成後の型になる。
合成後の型は狭いため、上の規則を素直に当てると **すべての置き換えが不正になる**。

受け手を特別扱いするのは、この種の型システムに共通する扱いである
（いわゆる binary method 問題）。**`self^` は変性の検査から除く。**

##### なぜ制限するのか

構造的な型付けを採っているため、制限がなくても **安全ではある**。
置き換えによって構造が変われば、その定義は元の定義の部分型でなくなり、
渡そうとした場所で誤りになる。

問題は **どこで報告されるか** にある。

```lhat
let^ Bar = Foo .. def^{ override^ foo := p^x:string^ { … } }   # ここは通ってしまう

let^ blah = p^ f:Foo { f.foo() }
blah(barInstance)                                            # 離れたここで初めて誤りになる
```

`Foo .. def^{ … }` と書いた時点で「これは `Foo` である」と宣言している。
それが崩れたのなら **崩した場所で報告する** べきである。
01 の 10.9 や Q7 で採ったのと同じ原則にあたる。

##### 実装の費用は増えない

変性の検査には関数型どうしの部分型関係が要るが、それは別途必要になる。
14.10 の `table^{ … }` が「少なくともこれらのメンバを持つ」判定を求めており、
メンバの型を比較する仕組みはそこで作ることになる。
`override^` はそれを使うだけである。

##### 診断

引数を狭めた置き換えは、`overload^` の書き間違いであることが多い。
そのため診断では代替を示す。

```text
override^ は元の定義と置き換え可能でなければならない。
引数を狭めることはできない。
呼び出し方を増やしたい場合は overload^ を使う。
```

##### 隠したものは `super^` で呼べる［確定・14.12改］

> **`override^` の本体の中では、`super^` が置き換えられた側を指す。**

```lhat
let^ Base = def^{ self^{ n := 0 }, step := p^self^ { self^.n := self^.n + 1 } }

let^ Derived = Base .. def^{
    self^{},
    override^ step := p^self^ {
        self^.n := self^.n + 10
        super^()               # 置き換える前の step
    },
}
```

平坦化された1つのテーブルを作る際、パートは順に処理される。
`override^` が書き込む時点でテーブルには置き換えられる側が入っているので、
書き込みの直前に読み出しておけばよい。**中間のテーブルは要らない。**

###### 書けるのは `override^` の中だけ［確定］

`overload^` は元の定義を残すので、隠されたものが無い。
`class^.m` で全ての腕に届く（14.12 の交差）。したがって `super^` の出番はない。

印のないメンバの中でも書けない。そこには置き換えた相手がいないためである。
「無ければ現在の値」とする案は採らない。その名前を自分が定義していれば
`super^` が **自分自身になり、黙って無限再帰する**。

###### `super^` は値である［確定］

`this^`（15.10）と同じく、名前として書けば普通の値になる。

```lhat
override^ get := f^self^ -> number^ {
    let^ old = super^
    return^ old(self^) + old(self^)
}
```

したがって 14.4 がそのまま効く — **値として取り出せば受け手を明示する**。

###### 呼び出しの位置では受け手が暗黙になる［確定］

`super^(…)` は `x.m(…)` と同じ束縛形である。
置き換えた相手は同じ定義のメンバなので、渡すべき受け手は
本体が既に持っている `self^` に決まっている。書かせるのは冗長である。

```lhat
super^()          # 受け手は self^。書かない
let^ f = super^
f(self^)          # 値として取り出したので書く
```

`self^` を取らない静的メンバでは受け手そのものが無いので、
どちらの形も同じものになる。

###### 多重定義された名前を `override^` した場合［確定］

`super^` は **その名前が担っていたもの全体**、すなわち交差を指す。
`override^` は腕1つを置き換えるが、読み出しは書き込みの前に行うので、
`super^` には置き換えられる腕も他の腕も含まれる。

```lhat
override^ m := f^ -> number^ { return^ super^() + 100 }
                                    # 引数なしの腕。置き換えられる側
```

呼び出しがどの腕を指すかは、通常の検索（本節）で決まる。

##### `override^` が捕まえるもの

以上より `override^` の役目は2つになる。

- **うっかり同名を定義した事故を捕まえる** — 指定がなければ誤り
- **置き換えが置換可能であることを、定義した場所で確かめる**

置き換える相手がまだいない場合は誤りとせず、合成待ちとして扱う（14.15改）。
そのときは置換可能性の検査も `..` の位置に移る。

### 14.13 `def^` の形［確定］

14.1 〜 14.12 の帰結をまとめる。実装の過程で明示が必要になった点を含む。

```text
def^{ 要素, 要素, … }

要素 := self^{ … }                         # 雛形。1つの定義に1つ
      | [override^ | overload^] 名前 := 式  # メンバ
      | abstract^ 名前 : 型                 # 宣言のみ（14.15）

雛形の要素 := 名前 := 初期値
            | abstract^ 名前 : 型           # 宣言のみ（14.15）
```

- 要素の区切りは `,`。末尾の `,` は許す
- `self^{ … }` の中は名前を伴う要素のみ。**位置指定の要素は書けない**
  （フィールドは名前で参照されるため）
- `self^{ … }` は **1つの定義に1つ**
- `override^` / `overload^` は **メンバに付く**。雛形には付かない。
  `abstract^`（14.15）は両方に付く
- メンバの名前には `new^` のような `^` 付きの語も書ける
- 定義の合成は `..`（14.5）。`def^` は式なので特別な規則は要らない（14.9）

雛形に関数・手続きを置けないこと（14.3）と、
`override^` の置換可能性（14.12）は型検査で確かめる。
どちらも値の型を見て初めて判定できるためである。

#### `self^` の2つの読み［確定］

`self^` の後ろに `{` が続く場合に限り 14.6 / 14.11 の形になる。
それ以外の `self^` は通常の値である。

```lhat
self^{ value1 := 0 }    # 雛形の宣言、または生成
self^.value1            # 通常の値
```

引数欄の `self^` と衝突しないのは、引数欄が名前だけを読み、
`{` が引数欄の終わりを表すためである。

```lhat
let^ methodA = p^self^ { print(1) }
#            ~~~~~ 引数    ~~~~~~~~~~~ 本体
```

引数の既定値として書いた場合は式として読まれるので、こちらも曖昧にならない。

```lhat
let^ m = p^ x = self^{ a := 1 } { … }
#           ~~~~~~~~~~~~~~ 既定値   ~~~~~ 本体
```

### 14.14 テーブルリテラルのキー［確定］

テーブルリテラルの要素は3つの形をとる。

```text
要素 := 式                # 位置。1 から順に割り当てる
      | 名前 = 式         # 名前のキー
      | [ 式 ] = 式       # 任意の値のキー
```

`[ 式 ] =` は **01 の 6 章が識別子として書けないキー** のためにある。
序数でも名前でもないキーを、リテラルの中で指定できる。

```lhat
{ [0] = "zero" }          # 0 は序数でない（14.10）。キーとして入る
{ ["a b"] = 1 }           # 識別子にならない綴り
{ [k + 1] = v }           # 実行時に決まるキー
```

#### 綴りは `=` である［確定・14.14改］

> **要素は `=` で書く。`:=` も従来どおり読むが、`=` が本来の綴りである。**

8.6 が `let^ x = v` を **導入**、`x := v` を **再代入** と定めている。
8.8 はそれをメンバへ広げ、`let^ t.b = v` が導入、`t.b := v` が再代入とした。

**テーブルリテラルの要素は導入である。** したがって `=` が筋であり、
当初の `:=` のほうが不整合だった。

```lhat
let^ t = { a = 0, b = "aaaaa" }     # メンバを2つ持つテーブル
```

##### 引き換えは括弧1組

`a = 0` が位置要素としての **比較** になれなくなる。
比較のリストが欲しければ括弧で囲む。

```lhat
let^ t = { (a = 0), (b = "aaaaa") }     # { false^, true^ }
```

`(` は名前を始めないので、判定から完全に外れる。**先読みは1つのままである。**

現状のまま `{ a = 0, b = "aaaaa" }` が `{ false^, true^ }` に解決されるほうが、
書き手の意図から遠い。比較のリストを波括弧で作りたい場面は稀である。

#### 文字列のキーと名前は同じもの

`t.a` と `t["a"]` は同じ入口である（14 章、Lua と同じ）。
したがって `{ ["a"] = 1 }` と `{ a = 1 }` は同じテーブルを作る。

#### キーを伴う要素は位置を消費しない

名前つきと同じ扱いである。位置は残りの要素だけで数える。

```lhat
let^ t = { 10, ["k"] := 20, 30 }
t[1]      # 10
t[2]      # 30   ← ["k"] は位置を取らない
t["k"]    # 20
```

#### キーは値であればよい

キーの式は他の式と同じく検査され、実行時に評価される。
04 の 11.3 のとおり `nil^` はキーになれない。
**`nil^` にしかなりえないキーは型検査で誤りとし**、
実行時に `nil^` になった場合は処理系が報告する。
NaN も同じく処理系の側で拒む — 14.8 の単一の数値型は静的に見分けない。

#### `self^{ … }` では書けない

14.6 のとおり雛形のフィールドは名前で参照されるため、
キーを伴う要素は書けない。位置指定を認めていないのと同じ理由である。

### 14.15 `abstract^` — 実装を合成先に委ねる［確定］

> **`abstract^ 名前 : 型` は、そのメンバを宣言するが提供しない。
> 合成される側が与えなければならない。**

これによって `def^` が **既定の実装を持つプロトコル** として働く。
Memo.md L349 が「実体型・抽象型・プロトコル定義・オブジェクトテンプレート・
アスペクト、全部を def^ テーブル一個で済ます」と言っていた抽象型がこれにあたる。

```lhat
let^ Counting = def^{
    self^{ count := 0 },
    abstract^ step : f^ -> number^;,          # 合成先が与える
    bump := p^self^ { self^.count := self^.count + class^.step() },
}

let^ Fast = Counting .. def^{
    self^{},
    step := f^ -> number^ { return^ 10 },     # ここで埋まる
}

Fast.new^()      # 可
Counting.new^()  # 誤り。step を誰も与えていない
```

`Counting.bump` は自分が実装していない `step` を呼べる。
Rust の trait の必須メソッド、Java の抽象メソッドにあたる。

#### 印は 14.12 と同じ位置に置く［確定］

`override^` `overload^` と並ぶ3つ目の印である。
綴りを `:` だけにする案もあったが、帰結が大きい
（**その定義はインスタンス化できなくなる**）ため、
`:=` との1文字差で表すのは読み落としやすい。

値がないので、型を `:` に続けて書く。14.10 の `t^{ a : number^ }` と同じ綴りである。

#### 雛形の場にも書ける［確定］

```lhat
let^ Greet = def^{
    self^{ abstract^ n : number^ },           # ホストが持つべき場
    hello := f^self^ -> number^ { return^ self^.n + 1 },
}

let^ Thing = Greet .. def^{ self^{ n := 10 } }
Thing.new^().hello()                          # 11
```

これがないと、ミックスインは `self^` を通してホストの場に触れられない。
`self^` の型はその `def^` 自身の雛形だからである。

場を**持つ**のではなく**宣言する**ことは、14.5改 の衝突を避けることでもある。
宣言どうしは対になるので、同じ場を使う2つのミックスインを重ねられる。

宣言された場には初期化子がないので、14.11 の構築では何も走らない。
埋めた側の初期化子だけが走る。

#### 埋めるのに印は要らない［確定］

宣言は**メンバの定義ではない**ので、埋めることは 14.12 の衝突にあたらない。

```lhat
let^ B = A .. def^{ self^{}, m := f^ -> number^ { return^ 1 } }            # 可
let^ C = A .. def^{ self^{}, override^ m := f^ -> number^ { return^ 1 } }  # 誤り
```

`override^` を誤りとするのは、置き換えた相手がいないためである
（`super^` が指すものもない）。

宣言が要求するのは **書いた型に適合すること** だけである。

```lhat
let^ D = A .. def^{ self^{}, m := f^ -> string^ { return^ "x" } }   # 誤り。型が合わない
```

逆に、既に提供されているメンバを `abstract^` で宣言し直すのは誤りとする。
要求する相手が既にいるため、その宣言は何も述べていない。

#### 名前形の合成でも対になる［確定］

14.5 の名前どうしの合成では同名を誤りとするが、
**片方が宣言・片方が提供** の組み合わせは衝突ではない。それが宣言の目的である。

```lhat
let^ Need = def^{ self^{}, abstract^ m : f^ -> number^; }
let^ Give = def^{ self^{}, m := f^ -> number^ { return^ 7 } }
let^ D = Need .. Give        # 可。順序はどちらでもよい
```

両方が宣言のままなら、穴は開いたまま次に渡る。

#### インスタンス化で報告する［確定］

宣言を残したままの定義は **それ自体は正当** である。合成の材料として使う。
誤りになるのは `new^` を呼んだ時点であり、報告もそこで行う。

```text
error: this definition declares a member that nothing has provided,
       so there is no instance of it to make: step
```

14.12 が「崩した場所で報告する」を採ったのと同じ原則であり、
穴を残したこと自体ではなく **穴があるものを実体化しようとしたこと** が誤りにあたる。

#### 相手のいない `override^` も待つ［確定・14.15改］

> **合成前の `def^` に書いた `override^` は誤りではない。
> 置き換える相手を合成が連れてくることを要求する。**

これによって、**基底を知らずに書いたミックスインが `super^` で元を呼べる**。
Scala の `abstract override`（積み重ね可能なトレイト）にあたる。

```lhat
let^ Base = def^{ self^{ n := 0 }, run := p^self^ { self^.n := self^.n + 1 } }

let^ Logged = def^{
    self^{ abstract^ n : number^ },      # ホストが持つべき場（14.15）
    override^ run := p^self^ {           # 置き換える相手は合成が連れてくる
        self^.n := self^.n + 10
        super^()
    },
}

let^ App = Base .. Logged
App.new^().run()                          # n は 11
Logged.new^()                             # 誤り。run の相手がいない
```

14.15 の宣言と条件が逆である点に注意する。

- `abstract^ m` — **実装がない**。後ろのパートが埋める
- 相手のいない `override^ m` — **実装はある**。無いのは `super^` の相手で、
  **前のパート**が埋める

どちらも「合成待ち」であり、`new^` を同じように塞ぐ。

##### 積み重ねられる［確定］

```lhat
let^ App = Base .. A .. B      # B → A → Base の順に super^ が連なる
```

ミックスインどうしを重ねても、どちらの待ちも解けない。
両方の下に置かれるものを連鎖がまだ必要としているためである。

```lhat
let^ X = A .. B      # 正当。ただし X も new^ できない
let^ App = Base .. X # ここで解ける
```

##### 置換可能性は出会った場所で検査する［確定］

14.12 の検査は本来 `def^` の位置で行うものだが、
相手がまだいないのだから行いようがない。**`..` の位置で行う。**

```lhat
let^ Bad = def^{ self^{}, override^ run := f^ -> string^ { return^ "x" } }
let^ App = Base .. Bad       # 誤り。Base.run は number^ を返す
```

##### `super^` の型［確定］

相手がまだいないので、**そこに書かれた署名そのもの**を `super^` の型とする。

14.12 が「置き換えは元の位置でそのまま使える」を求めているため、
書かれた署名は元の署名が使える場所すべてで使える。
したがってこの読みは元より多くを約束しない。

Scala が `abstract override` に同じ制約を課している。

##### `overload^` にはこの読みがない［確定］

相手のいない `overload^` は従来どおり誤りとする。
**無いものに呼び出し方を増やす**という記述に意味がないためである。

### 14.16 `typeof^` — 値の型を文字列で得る［確定］

> **`typeof^(式)` は、式の値が実際に持つ形を表す「型情報」を返す。
> `typeof^(式).signature` は、それを 14.10 の構造そのままの文字列にする。**

```lhat
typeof^(5).signature           # "number^"
typeof^("x").signature         # "string^"

let^ Point = def^{ self^{ x := 0, y := 0 } }
typeof^(Point.new^()).signature
# "t^{ new : f^;, x : number^, y : number^ }"

let^ f = f^ n:number^, s:string^ -> bool^ { return^ true^ }
typeof^(f).signature
# "f^number^, string^ -> bool^;"
```

Memo.md が構想していた「ホスト関数登録の署名文字列を、対応する L^ 側の定義から
機械的に得る」がこれで書ける。書き手は 14.10 の文法を手で書く機会が減る。

`rawsignature^` という名で提案されていたが、実装はなく撤回した。
`typeof^(x).signature` に一本化する。

#### ハット識別子ではない［確定］

`.signature` は `signature^` ではない。組み込み型を「静的メンバを持つクラス」
として扱う構想（`number^.nan` 等）の最初の一歩であり、
`typeof^(x)` が返す値を **普通のテーブルのように** 読ませたい。
タイプミスではなく、意図してハットを外している。

#### 実行時の反射で答える［確定・重要］

`typeof^` は **検査器が推論した静的な型を再現しない**。
その場で **値が実際に持つ形を歩いて** 答える。

03 の 4.2 が「厳格度が変えるのは診断の時期だけであり、実行時の意味は変わらない」
と定めている。検査結果（`LhatType`）は検査が終わると同時に捨てられ、
コンパイルは構文木を独立に読み直す（03 の 4.3 とは別に、検査とコンパイルは
別パスである）。`typeof^` の答えが検査器の推論に頼ると、
検査を経ていない場合に答えが変わってしまい、4.2 に違反する。

都合よく、14.7 の文言がそのまま反射の設計になる。

> `typeof^(インスタンス)` はその定義を返す。

インスタンスは実行時に自分がどの定義から作られたかを覚えている。
定義は自分のメソッドを持つ、ただのテーブルである。
**両方を歩けば、14.7 が約束する構造がそのまま得られる** —
新しい実行時メタデータは要らない。

```lhat
let^ Point = def^{
    self^{ x := 0, y := 0 },                  # インスタンス側にある
    sum := f^self^ -> number^ { … },          # 定義側にある
}
typeof^(Point.new^()).signature
# 両方を歩いた結果: "t^{ new : f^;, sum : f^ -> number^;, x : number^, y : number^ }"
```

反射なので、値が実際に持つ形を正直に映す。静的注釈より広い形で構築された値
（`any^` を経由した場合など）も、その広い形のまま報告する。

#### 名前で持ち込んだ2つは対等に扱う（14.5改）とも整合する

構造で比べる（11.3）ため、`typeof^(x) = typeof^(y)` は
**独立に書かれた2つの定義が同じ形なら真になる**（14.9）。

```lhat
let^ A = def^{ self^{ n := 0 } }
let^ B = def^{ self^{ n := 0 } }
typeof^(A.new^()) = typeof^(B.new^())    # true^
```

#### 綴りの形［確定］

- 序数のメンバ（14 章の列側）は名前を持たず、位置のまま並べる — `t^{ number^, string^ }`
- 名前のメンバはアルファベット順に並べる — ハッシュ表の内部順は書き手の意図でも
  安定でもないため、`.signature` の出力と `typeof^(x) = typeof^(y)` の両方が
  ある1つの順序に頼らずに済むよう、反射した時点で並べ替える
- `p^` に返り値が無ければ `-> …` を書かない
- `self^` は署名に現れない（14.4 のとおり、受け手は引数ではない）
- 誤りの値は、その種別の完全修飾名をそのまま返す — `"IOError.NotFound"`
  （04 の 2.4: 識別性は宣言そのものにある）

#### まだ反射しないもの（S28）

- **可変長引数 `...`** — `LhatProto` が可変長かどうかを実行時に持たない。
  もっとも、現状は可変長引数を持つ `f^`/`p^` が **コンパイルできない**
  （13.7 の構文・検査は通るが、コンパイラが `LHAT_COMPILE_UNSUPPORTED` で拒む）。
  これは `typeof^` と無関係な既存の欠落であり、別途扱う
- **コルーチンの `R,Y,T`** — `typeof^` は `c^{any^, any^, any^}` を返す。
  実際の3つの型を実行時に持っていないため
- **循環するテーブル** — `t.self := t` のような自己参照は 8.6 の代入規則が
  阻むため、通常の書き方では作れないことを確認した。ただし全ての経路を
  検証していないため、循環があれば `typeof^` は無限再帰する

## 15. サブルーチンの種別［確定］

### 15.1 種別は2つ

サブルーチンは **関数 `f^`** と **手続き `p^`** の2種類とする。

Memo.md L57 が挙げていた **継続 `c^` は廃止する**。

| 種別 | 呼べる相手 | 代入 | `yield^` |
| --- | --- | --- | --- |
| `f^` 関数 | 関数のみ | 局所変数のみ | **不可** |
| `p^` 手続き | 関数と手続き | — | **可** |

### 15.2 yieldable かどうかは推論する［確定］

`yield^` を含む手続きは **yieldable** として扱う。
そのために別の記号を書く必要はない。
中断せずに署名だけを合わせたい場合は `_yield^` を使う（15.11）。

Memo.md L60–L61 が既に同じ結論に達している。

> 構文上は関数もしくは手続きで、yieldを呼んでるかどうかでYieldableとマークされ、
> 返り値の一個目が必ず継続になる。

`c^` という第三の記号は、`yield^` の有無から静的に分かる情報を二重に書かせていた。
`yield^` を1行足すたびに `p^` を `c^` に書き換え、
参照している型注釈もすべて直す必要が生じる。冗長な保守の負担になる。

#### 区別は消えず、記号から型へ移る［重要］

呼び出す側は「これは継続を返すのか」を知る必要があるため、
yieldable であることは **型に載る**（13.6 の (4)）。

したがって `c^` の廃止は型システムの区別をなくすものではない。
**減るのは表面の記号だけ** である。

これは情報の置き場所として正しい。
`yield^` の有無は本体を見れば分かるので記号は冗長だが、
呼び出す側からは本体が見えないので型には必要になる。

### 15.3 `f^` は `yield^` できない［確定］

**関数に `yield^` を許すと、`f^` と `p^` を分けた理由が崩れる。**

`yield^` で中断し、再開時に値を受け取るなら、
その結果は引数だけで決まらなくなる。同じ引数で呼んでも、
再開時に渡される値によって結果が変わる。

参照透過性が失われ、メモ化も並べ替えも省略もできなくなる。
`f^` の制約（関数しか呼べない、局所変数にしか代入できない）は
その性質を守るためにあり、`yield^` はその穴になる。

15.4 のとおり `yield^` は双方向であり、再開時に値を受け取る。
したがって関数に許せば参照透過性が確実に失われる。`f^` からは除く。

#### 一方向に制限すれば許せるか — 検討したが採らない

「`f^` の中の `yield^` だけ値を受け取れないことにすれば許せるのではないか」
という案を検討した。**技術的には成立する** が、採らない。

`f^` の純粋性自体は保たれる。同じ引数なら同じ列を生むコルーチンが返り、
本体は `f^` の制約下にあるため副作用を持てない。呼び出しは参照透過である。

**しかし、動機である「純粋な遅延列」は得られない。**

返ってきたコルーチンは状態を持つ。進めれば変化し、2度消費すれば2度目は尽きている。
そして「進める」操作は変更であり手続きにあたる。`f^` は手続きを呼べない。

```lhat
let^ sum = f^ s { let^ total = 0; for^ v in^ s { total := total + v }; total }
```

つまり `f^` の中で遅延列を **生成できても消費できない**。
純粋な関数型の連結（map・filter・fold を純粋なコードで組む）という
主たる動機がそのまま失われる。

これを回避するには「再開が新しいコルーチンを返す」形にする必要があるが、
それは **コルーチンではなく永続的な遅延リスト** であり、別のデータ構造になる。
純粋な遅延列が必要になった場合に用意すべきものは
`f^` の `yield^` ではなく、そうしたライブラリの型である。

加えて `yield^` の意味が文脈で変わる。
`f^` の中では文、`p^` の中では式となり、
Q8・Q3・S11 の (3) で一貫して排除してきた
「文脈によって意味が変わる記号」を再び持ち込むことになる。

なお、後から許可する方向への変更は後方互換である
（通るものが増えるだけ）。いま決めない費用はない。

### 15.4 `yield^` は双方向［確定］

`yield^` は値を外に出すと同時に、**再開時に外から値を受け取る**。
`yield^` は文ではなく式であり、その値は再開した側が渡したものになる。

Lua の `coroutine.yield` と同じである。

```lhat
let^ pager = p^{
    let^ cursor = 0
    repeat^{
        let^ page = load(cursor)
        let^ cmd:string^ = yield^ page  # cmd は再開側が渡した値
        if^ cmd = "skip" { cursor := cursor + 10 }
        el^: { cursor := cursor + 1 }
    }
}
```

`cmd:string^` の注釈は 13.9 改が要求するもので、受け取る型を固定する
（本体に他の `yield^` があれば、そこも `string^` で揃える必要がある）。

#### 決め手は非同期処理

`await` は本質的に双方向である。

```text
let^ result = await^ fetch(url)
```

コルーチンに落とすと「待つ対象を出して中断」し、
スケジューラが後で **結果を渡して再開** する。
**再開時に値を受け取れなければ `await` は成立しない。**

Python はこの順序をたどった。
PEP 342 がジェネレータに `send()` を加えてコルーチンを可能にし、
PEP 492 の `async` と `await` がその上に築かれている。
Lua でも同様に、非同期の枠組みは `resume` が値を渡せることに依存している。

Memo.md L65 の「（本物の）非同期はどうしよう？」への道がこれで確保される。

#### 一方向の用途は失われない

純粋な反復子のように一方向で足りる用途は、
双方向の上に **ライブラリで** 構築できる。逆はできない。

Memo.md L61 の「コルーチンをラップして継続を隠蔽して返り値のみ扱えるようにする仕組み」が
まさにその層にあたる。

したがって双方向は厳密に表現力が広く、選ばない理由がない。

一方向の書き方が失われないのは注釈の要否にも表れている。
値を使わず捨てる `yield^ expr;` は 13.9 改の下でも注釈を要らない —
受け取る型に何も言っていないからである。
注釈が要るのは、`let^` でその値を直接受け取る場合だけである。

#### 双方向は基盤側の能力である

日常の記述で `yield^` の値を受け取る場面は多くない。
反復子や生成器はほとんど一方向で足りる。

双方向を必要とするのは **非同期の層を実装する側** であり、
利用者は `await` に相当する糖衣を書くだけになる。
Python でも `send()` を直接呼ぶ利用者側のコードはまれである。

「よく書くか」ではなく「これがなければ非同期を構築できるか」で判断している。

#### 型は3つを持つ

コルーチンの型は次の3つを含む必要がある（13.6 の (4)）。

- 出す値の型
- **受け取る値の型**
- 最終的な返り値の型

一方向であれば2つ目は常に `nil^` で済んだ。
双方向に決めたため、記法にこの区画が要る。

### 15.5 呼び出しは伝染しない［確定］

`yield^` を含む手続きを呼んでも、**呼び出した側は中断しない**。
呼び出しはコルーチンを返すだけである。

Memo.md L60 の「返り値の一個目が必ず継続になる」がこれにあたる。

```lhat
let^ gen = someYieldingProc(args)
```

呼び出し側が yieldable である必要はない。
この設計により、`async` と `await` を持つ言語で問題になる
**関数の色分け**（呼び出す側も同じ印を要求される連鎖）が発生しない。

Python のジェネレータが同じ構成を採っている。

#### 呼び出しの時点では本体が始まらない［確定・重要］

> **`p()` は本体を一行も実行しない。`start()` が先頭から動かす。**

（`start()`/`resume()` の分離は 15.2 改。以前は最初の `resume` が
この起動を兼ねていたが、それでは resume のシグネチャが
「引数なし、または1つ」の2通りになってしまい、13.4 が既定値を型に
含めない方針と噛み合わなかった。詳しくは 15.2 改を参照。）

```lhat
let^ p = p^ {
    print("a")
    yield^
    print("b")
}

let^ c = p()      # 何も出力されない
c.start()         # ここで "a"
c.resume(nil^)    # ここで "b"
```

「最初の `yield^` まで走り、その後の残りが返る」という読みもありうるが、**採らない**。
既に決まっていることが3つとも同じ側を指している。

- **13.8 が多値返却を廃止している。** 先走る読みでは
  `p()` が「コルーチン」と「最初に出した値」の2つを答えることになる。
  出した値の行き場がない
- **15.4 の例が成り立たない。** そこでは最初の `yield^` が `load(cursor)` の結果を出すが、
  呼び出しの時点では **受け取る相手がまだいない**
- **本節が挙げている Python のジェネレータがこの形である。**
  JavaScript の generator、C# の反復子、Kotlin の sequence も同じ

「継続」という語が先走る読みを引き寄せる点は注意を要する。
継続は「残りの計算」を指す語だが、
ここで返るものは **本体全体であり、再開位置が先頭にある** ものである。

`iterate`（16.3）が呼ばれた時点で反復が1つ進んでしまわないのも、この規則による。

### 15.6 コルーチンの生成に専用の記法は要らない［確定］

`c^` が暗黙に持つとされていた `new^`（Memo.md L57）は不要になる。
呼び出しがそのままコルーチンを返すためである。

Memo.md L61 の後半が構想していた「包んで扱いやすくする仕組み」は、
15.9 のとおり言語には持たせない。

#### Lua が `coroutine.create` を要する理由［参考］

**Lua は yieldable かどうかを印していない。**
どの関数からでも `coroutine.yield()` を呼べるため、
処理系にはどれがコルーチンの本体か分からない。
したがって `f(x)` を「コルーチンを作る」と読ませようがなく、
**関数を呼ばずに渡す記法** が要る。それが `coroutine.create(f)` である。

L^ に要らないのは、15.2 が `yield^` の有無から
**コンパイル時に yieldability を推論している** ためである。
呼び出しの時点でどちらを出すか決まっている。本節はその帰結にすぎない。

#### コルーチンが持つメンバ［15.6 改］

コルーチンは次を持つ。いずれも取り込みを要さない（05 の 8.5）。

| メンバ | 型 | 何をするか |
| --- | --- | --- |
| `start()` | `f^ -> Y\|Ret;` | 先頭から本体を走らせる（15.2 改） |
| `resume(v)` | `f^ R -> Y\|Ret;` | 続きを走らせ、`v` を送る（15.4） |
| `dispose()` | `f^;` | 残っている後始末を走らせて終わらせる（10.7、12.6） |
| `iterate()` | `f^ -> c^{R, Y, Ret};` | 自分自身（16.3） |
| `done()` | `f^ -> bool^;` | 本体が終端まで走ったか |
| `started()` | `f^ -> bool^;` | `start()` が既に走ったか |

##### `done()` が要る理由 — 合併が判別子にならない［確定］

13.9 は再開の結果を「出す型 ∪ 返り値型」と定め、
**「まだ続くのか終わったのかを、消費側が判別する」** と書いている。
しかしこの合併は判別子を伴わない。2つの型が一致していれば、
値を見ても どちらだったのか分からない。

一致は例外ではなく **既定で起きる**。
値を返す `return^` を持たない本体は、終端に到達した時点で
**再開した側に `nil^` を渡す**。よって返り値型は `nil^` になり、
`yield^` が値を伴わなければ出す型も `nil^` になる。

```lhat
let^ gen = p^ { yield^ }     # c^{nil^, nil^, nil^}
let^ c = gen()
c.start()                    # nil^。中断したのか、終わったのか
c.resume(nil^)               # nil^。同上
```

同じ `nil^` が、中断して出した値としても、終わって返した値としても現れる。
値の側で解けないので、状態を直接問う。

`done()` があれば消費側は値を詮索せずに済み、
出す型が `nil^` を含んでいても困らない。

##### この `nil^` は 03 の「返り値なし」ではない［確定］

03 の「脱出をすべて数える」は、値を返す `return^` を持たない `p^` を
**返り値なしのまま** とし、`nil^` にはしないと定めている。
上の `nil^` はそれに反していない。**別のものを指しているためである。**

- 03 が言うのは **`p^` を呼んだ結果の型** である。
  yieldable な `p^` は 15.5 によりコルーチンを答えるので、
  その「返り値なし」は呼び出しの結果として表に出る機会がない
- 13.9 の返り値型は **最終再開が受け取る値の型** である。
  終端に到達した本体は実際に `nil^` を渡すので、`nil^` はそこにある値の型になる

03 が `nil^` を避けた理由もここには当てはまらない。
`log(m) ?? 0` が無意味なのは `log(m)` が値を作らないからであり、
`c.resume(v) ?? 0` は意味を持つ — `resume` は本当に `nil^` を答えうる。

必ず値を返す本体では `nil^` は混ざらない。

```lhat
let^ a = p^ { yield^ 1 }            # c^{nil^, number^, nil^}
let^ b = p^ { yield^ 1 return^ 9 }  # c^{nil^, number^, number^}

a().start()   # number^|nil^
b().start()   # number^ のみ
```

##### `started()` も要る理由 — `done()` だけでは足りない［確定］

`done()` は「終わったか」であり、**始まっていないコルーチンにも `false^` を答える**。
中断中のものと区別がつかない。

自分で作ったコルーチンなら `start()` を呼ぶ側が状態を知っているので問題にならないが、
**引数として渡されたコルーチン** はそうではない。
`start()` と `resume()` のどちらを呼ぶべきかを問う手段が要る。

```lhat
let^ drain = p^ c {
    if^ !c.started() { c.start() }
    repeat^ while^ !c.done() { c.resume(nil^) }
}
```

2つの `bool^` で 15.2 改の3状態（未開始・中断・終了）がすべて判別できる。

##### 実行時の誤りは残す

15.2 改の `LHAT_RUN_COROUTINE_NOT_STARTED` と
`LHAT_RUN_COROUTINE_ALREADY_STARTED` は、この2つを足しても残る。
問う手段があることと、問わずに呼んだ場合を許すことは別である。

`started()` は「呼ぶ前に確かめる道」であって、
誤った呼び出しを黙認する規則ではない。

##### 型検査では判定しない

コルーチンが始まっているかどうかは実行時にしか分からない（15.2 改）。
`done()` と `started()` は **その実行時の状態を問う手続き** であり、
型検査が状態を追うわけではない。追うには typestate が要り、
13.9 がその重さを理由に退けている。

### 15.7 演算子の制約が自動的に従う

Memo.md L62 は演算子について次のように述べている。

> op^演算子 関数扱い すべての演算子は関数としての性質を満たすことを強制する、またyield不可

11.1 のとおり演算子は関数として扱われ、15.3 により関数は `yield^` できない。
**「yield 不可」は別の規則として書く必要がなく、帰結として従う。**

### 15.8 入れ子の yieldable［確定・旧 S21］

#### 問題

yieldable な手続きの中から、別の yieldable な手続きを使いたい。

```lhat
let^ a = p^{
    print("a start")
    yield^
    print("a finish")
}

let^ b = p^{
    a()                  # ここで何が起きるべきか
    print("b start")
    yield^
    print("b finish")
}
```

`b` のコルーチンを再開し続けたときに期待されるのは次である。

```text
a start
a finish
b start
b finish
```

**現行の 15.5 ではこうならない。** `a()` はコルーチンを作って返すだけであり、
それを捨てているので `a` の本体は一行も走らない。

委譲を明示すれば、期待どおりの並びになる。

```lhat
let^ b = p^{
    yieldall^ a()        # a の yield^ が b の再開側まで届く
    print("b start")
    yield^
    print("b finish")
}
```

```text
1回目  a start           # a の yield^ で中断（b 越しに届く）
2回目  a finish, b start # a が終わり、b が続いて b の yield^ で中断
3回目  b finish          # 完了
```

#### 15.5 が守っているもの

15.5 は利便性のためだけの規則ではない。

13.9 がコルーチンの型を3つ（受け取る型・出す型・返り値型）と定めている。
この3つを決めるには **境界まで届きうる `yield^` をすべて知る** 必要がある。

- **`yield^` が本体の中に閉じている** — 1つの本体を読めば3つとも決まる
- **呼び出しを跨いで届く** — 呼び出し先の先まで辿る全域解析か、
  呼ぶ側すべてへの印（＝色分け）が要る

したがって 15.5 は **13.9 を静的に決められるようにしている**。
03 の 5.7 が「コルーチンは1フレームだけを保存する」と決められたのも同じ理由による。

#### 使い道を3つ並べる

決めるべきは「入れ子が要るか」ではなく「**暗黙に届く必要があるか**」である。
実際の用途で確かめる。

##### (1) 反復子の合成

木を歩く反復子は、子の走査を下位の反復子に委ねたい。

```lhat
let^ walk = p^ node {
    yield^ node.value
    for^ child in^ node.children {
        yieldall^ walk(child)     # 子の出す値を、そのまま自分の出す値にする
    }
}
```

**各段が明示的に書いても不便ではない。**
委ねているのは書き手自身であり、その位置は本人が知っている。
Python が 3.3 で `yield from` を入れて以降、この形で足りている。

##### (2) 非同期の await 連鎖

15.4 が挙げた形である。

```lhat
let^ load = p^ url {
    let^ body = await^ fetch(url)     # await^ は委譲の糖衣になる
    return^ parse(body)
}
```

**そもそも各段に `await^` を書く。** 明示的な委譲は追加の負担にならない。
むしろ C# と Rust が `await` を明示にしたのは
「どこで中断しうるかが読んで分かること」を利点と見たためである。

##### (3) 入れ子のパーサ

入力が足りなければ中断し、続きを渡されて再開するパーサは、
下位のパーサを呼ぶ間もその性質を保たなければならない。

```lhat
let^ parseList = p^ {
    repeat^ {
        yieldall^ parseItem()     # parseItem も入力を待って中断しうる
        if^ done() { break^ }
    }
}
```

ここでも呼ぶ位置は書き手が知っている。

##### 明示が本当に困る場合

**深い補助手続きの奥から中断したい場合** である。
途中の段すべてに委譲を書くことになり、それは色分けそのものになる。

ただし (1)〜(3) はいずれもこの形を必要としていない。
中断しうる相手を呼ぶことは、設計上の意図であって偶然ではないためである。

#### 決定

> **(A) を採る。`yieldall^` を新設し、`yield^` の多重定義はしない。**

15.5・13.9・03 の 5.7 はそのまま残る。
以下は判断の材料として残す。

#### 残っている作業 → 15.2 改・13.9 改で解決

13.9 の3つの型のうち、「出す型」と「受け取る型」の推論は、
本体の `yield^`／`yieldall^`（委譲する先も含む）を集めて単一化することで
実装した（15.2 改）。`return^` から返り値型を推論する処理（03 の 3.4）と
似た形だが、複数箇所が食い違う場合は **合併ではなく型エラー** にする —
異種の `yield^` を型で見分けさせない方針を採ったためである（13.9 改）。
受け取る型は、`yield^` の値を直接受け取る `let^` 束縛の注釈から決まる。

##### `resume` の引数の個数が固定できていない → `start()` を新設して解決

最初の再開は値を送らない。本体がまだ `yield^` に達していないためである。
一方 13.4 は既定値を型に含めないと定めているので、
「1つ、または無し」を型で書く手段がない。

`resume` を2つに分ける（Python の `next` と `send` にあたる）案を採った。
コルーチンに `start()` を新設し、シグネチャを分けている。

- `start()` — 引数なし。まだ一度も始まっていないコルーチンだけに使え、
  先頭から本体を走らせる。返り値は resume と同じ union（出す型|返り値型）
- `resume(v)` — 受け取る型 `v` をちょうど1つ取る。始まっていないコルーチンに
  対する呼び出しは誤りとする

始まっていないコルーチンへの `resume` と、既に始まっているコルーチンへの
`start()` はどちらも実行時の誤りとする。
コルーチンが始まっているかどうかは動的にしか分からないため、
型検査ではなく実行時に検出する（12.6 と同じ位置づけ）。

呼ぶ前に確かめたい場合は `started()` を問う（15.6 改）。
誤りが残るのは、問わずに呼んだ場合を許さないためである。

```lhat
let^ c = gen()
c.start()      # 先頭から走らせる
c.resume(10)   # 続きを走らせ、10 を送る
c.resume(20)
```

#### 3つの案

##### (A) 明示的な委譲を足す［採用］

15.5・13.9・03 の 5.7 をそのまま保ち、記法を1つ増やす。

- **利点** — 型が静的に決まる。実行時は「コルーチンの鎖」で足り、独立スタックが要らない
- **欠点** — 各段に1語書く。深い補助手続きからの中断は書けない
- **費用** — 記法1語と、鎖をたどる再開

##### (B) Lua 方式に変える

コルーチンごとにスタックを持たせ、任意の深さの `p^` から `yield^` できるようにする。

- **利点** — 何も書かなくてよい。深い補助手続きからも中断できる
- **欠点** — 13.9 の3つの型が1つの本体から読めなくなる。
  **15.5 と 15.2 の書き直しが要る**（呼び出しがその場で走ってしまうため、
  コルーチンを作る別の記法が要る。Lua の `coroutine.create` にあたる）
- **費用** — コルーチンごとのヒープ上のスタック。03 の 5.7 の再決定

##### (C) 現状のまま（委譲なし）

入れ子は「外側が内側を回す」と書き下す。

```lhat
let^ b = p^{
    let^ inner = a()
    repeat^ while^ inner.running() { yield^ inner.resume() }
    …
}
```

- **利点** — 何も足さない
- **欠点** — (1)〜(3) のいずれでも毎回この定型を書く。
  内側の返り値と出す値の区別も手で書くことになる

#### 呼び忘れは誤りにできる［重要］

(A) と (C) には「委譲を書き忘れる」という失敗が残るように見える。
**静的に誤りにできる。新しい機構は要らない。**

C# の `IEnumerator`（および Unity のコルーチン）で最も刺さる不満がこれにあたる。
`a();` と書いても何も起きず、警告も出ない。

- 15.2 が yieldable かどうかをコンパイル時に決めている。
  したがって `a()` の型は `c^{R, Y, T}` と分かる
- 8.2 により裸の式は文ではなく、**呼び出しだけが単独で立てる**

> **値がコルーチンである呼び出し文は誤りとする。**

根拠が「書き忘れたのだろう」という推測でないことが要である。
15.5 により、その呼び出しは **本体を一行も走らせない**。
**その文に効果が全く存在しないことが型から分かる。**

`print("x")` のような呼び出し文が許されるのは、
手続きの効果がその時点で起きているためである。
yieldable な手続きの呼び出しには、その効果がない。

04 の 8.1 と同じ形の規則になる。
取りこぼしを捕まえる専用の機構ではなく、**型がそのまま検出になる**。

正しい書き方は次のいずれかで、診断はそれを示す。

```lhat
yieldall^ a()            # 委譲する
let^ c = a()             # コルーチンとして受け取る
with^ c := a() { … }     # 受け取り、抜けるときに破棄する（12.6）
```

```text
この呼び出しはコルーチンを作るだけで、本体を実行しません。
委譲するなら yieldall^ a()、コルーチンとして扱うなら let^ c = a() と書きます。
```

(B) を採っていれば呼び出しがその場で走るのでこの問いは消えたが、
(A) を採ったため **この規則を置く**。

##### 対話入力が答える文はこれに当たらない

根拠が「効果が全く存在しない」ことである以上、
**効果があるなら根拠のほうが成り立たない**。

03 の 4.3 は、対話入力の最後の文が式であるときその値を答えとする。
答えは表示されるので、その文には効果がある。

```lhat
> t.iterate()          # 誤りではない。歩きが答えとして表示される
> t.iterate()          # 最後でなければ、従来どおり誤り
> let^ k = 1
```

規則に穴を空けるのではなく、**規則が根拠にしている推論の適用範囲** の話である。

#### 記法の下位問題 — `yield^` の多重定義でよいか

(A) を採る場合、右辺がコルーチンなら委譲、そうでなければ従来どおり、
と `yield^` に多重定義させれば足りるようにも見える。

##### 逐次の `await^` は多重定義でも成立する

まずこれを潰しておく。`yield^ fetch(url)` が委譲になっても、
`fetch` の内部が最終的に **入出力要求**（コルーチンではない値）を出せば、
それがスケジューラまで届く。**逐次的な待ちは壊れない。**

Python のネイティブコルーチンがこの形である。`await` は委譲であり、
葉の awaitable が Future をイベントループへ出す。

##### 壊れるのは並行の原語

委譲は **逐次** である。並行にするには、
**コルーチンを走らせずに駆動側へ値として渡す** 必要がある。

```lhat
let^ worker = p^ {
    yield^ spawn(otherTask())   # 「これも並行に回して」。委譲されては困る
}
```

`gather`、`select`、構造化並行はいずれもこの形をとる。
多重定義するとこれが書けず、`yield^ { task := otherTask() }` のように
包んで渡す回避が要る。

> **逐次の `await^` は無事だが、並行の原語が潰れる。**

##### 型が右辺の型で決まる

- 右辺がコルーチンでない — 値は `R`（再開側が渡したもの）
- 右辺がコルーチン — 値は `T`（内側の返り値）

右辺が `c^{…}|nil^` や `any^` のとき決まらない。
13.7 が `any^` を「絞り込むまで何もできない」と定めているため、
**`yield^` する前に絞り込みを要求する** という筋の通らない規則になる。

##### 同じ一行が二つの意味を持つ

```lhat
let^ c = makeWorker()
yield^ c            # 出したつもりが委譲になる
```

読んで区別できない。局所で判断できない記法は 01 の 10.9 の原則に反する。

##### 前例

多重定義できる言語でも、いずれも分けている。

| 言語 | 出す | 委譲する |
| --- | --- | --- |
| Python | `yield x` | `yield from x` |
| JavaScript | `yield x` | `yield* x` |
| Kotlin | `yield(value)` | `yieldAll(sequence)` |

Kotlin は関数の多重定義を持つ言語であり、
`SequenceScope` の2つを1つの名前にまとめることもできたが、そうしていない。

16.6 のとおり **L^ ではキーワードの追加費用が低い**。
予約語がないため、語を1つ増やしても既存のコードは壊れない。

##### 委譲は値を持つ

```lhat
let^ r = yieldall^ a()
```

`a()` の型が `c^{R, Y, T}` のとき、

- **`yieldall^ a()` の値は `T`** — 内側の返り値である
- `Y` は外側の出す型に加わる
- `R` は外側の受け取る型と一致する必要がある。
  再開側が渡した値は、中断している内側まで届くためである

Python の PEP 380 が `yield from` の値をサブジェネレータの `return` 値と定め、
**そのためにジェネレータの `return` に意味を与えた** のと同じ構成になる。

**2つは型が違う。** 下の「記法の下位問題」がこれを前提にする。

| 記法 | 値 |
| --- | --- |
| `yield^ e` | 再開側が渡したもの（`R`） |
| `yieldall^ c` | 内側の返り値（`T`） |

13.9 の「再開の結果は出す型と返り値型の合併」との関係も整理しておく。
**内側の返り値は外側の再開側には届かない。`yieldall^` が吸収する。**
外側の再開側が見るのは、内側が出した値と、外側自身が出す値・返す値である。

##### 綴り

`yieldall^` を第一候補とする。`delegate^` は「何を委ねるのか」を語が言っておらず、
`yieldall^` は「内側が出すものを全部そのまま出す」という動作をそのまま述べている。

上の表の3言語がいずれも `yield` を語幹に残しているのと同じ判断による。
`yield^` との関係が綴りから読め、かつ別物であることも読める。

**Kotlin の `yieldAll` がそのままの前例になる。**

**`yieldall^` に確定する。**

### 15.9 継続とコルーチンを区別しない［確定］

Memo.md L61 は2階建てを構想していた。

> コルーチンはこれをラップして継続を隠蔽して返り値のみ扱えるようにする仕組み

**この区別は設けない。呼び出しが返すものをコルーチンと呼ぶ。**
`c^{ … }`（13.9）はその型である。

理由は、包む層に **言語が持つべき中身がない** ことによる。
Lua の `coroutine.wrap` がまさにこの層にあたるが、
その実体は `resume` を閉じ込めたクロージャであり、
L^ では普通の `p^` として誰でも書ける。組み込む理由がない。

反復子として扱いやすい形が要る場合も同じで、**ライブラリの層で書けばよい**。

語をひとつに保つことで、`typeof^` の答えと 13.9 の型と実行時の対象が同じ名前になる。

コルーチンの操作を取り込まずに使える件は [05-modules.md](05-modules.md) の 8.5 で定める。

### 15.10 `this^` — いま実行しているサブルーチン［確定］

> **`this^` は、それを含む最も内側のサブルーチンそのものを指す。**

Memo.md L561 の「擬似変数 this による自己再帰」にあたる。

```lhat
functorial := f^ x { if^ x = 0: 1 el^: x * this^(x - 1) ; }
```

#### 名前を持たない本体が自己再帰できる

名前で呼ぶ形は 8.7 の可視性で既に書ける。

```lhat
let^ fact = f^ n { if^ n <= 1 { return^ 1 } return^ n * fact(n - 1) }
```

`this^` が要るのは **束縛されていない本体** である。
その場で渡す本体に名前を付けさせないために置く。

```lhat
sort(items, f^ n { if^ n <= 1 { return^ 1 } return^ n + this^(n - 1) })
```

#### 3つの語が3つのものを指す［重要］

`this^` は **インスタンスではない**。Java・C#・JavaScript の `this` とは指すものが違う。

| 語 | 指すもの | 定める節 |
| --- | --- | --- |
| `self^` | インスタンス | 14.4 |
| `class^` | 定義 | 14.4 |
| `this^` | いま実行しているサブルーチン | 本節 |

メソッドの中の `this^` はそのメソッドであり、インスタンスでも定義でもない。
**1語1意味**（8.6 以来の原則）を保つために、語を分けている。

#### 最も内側を指す

入れ子の本体では内側のものを指す。外側に届ける手段は名前である。

#### 型は本体自身の署名

`this^` の型は、それが置かれている本体の署名になる。
したがって **引数の型と個数がその場で検査される**。

名前で呼ぶ場合、8.7 の事前収集がその名前を `unknown^` として束ねているため、
本体を読んでいる最中は引数の検査ができない。**`this^` のほうが強く検査される。**

#### 03 の 3.4 との関係

`this^` による呼び出しは、名前による自己呼び出しと同じく **再帰の脱出** として数える。
したがって返り値型の推論から外れ、脱出がすべて `this^` なら誤りになる。

#### サブルーチンの外では誤り

翻訳単位の直下に書いた `this^` は指すものを持たない。誤りとする。

### 15.11 `_yield^` — 中断しない `yield^`［確定］

> **`_yield^` は `yield^` とまったく同じに書け、まったく同じ型を言うが、
> 中断しない。**

#### 問題

「中断の必要がない `p^` でも、駆動側の設計上コルーチンを要求される」形がある。
15.2 は `yield^` の有無だけで yieldable を決めるので、
**署名を合わせるためだけの `yield^`** を到達不能な場所に書くことになる。

これが危うい。書き手は「`start()` で完走し、`resume` はされない」つもりでいるが、
その `yield^` に届く経路がうっかり残っていると **本当に中断する**。
壊れるのは駆動側であり、原因から遠い。

型を緩めて逃げることもできない。13.9 の3つの型は
[type.c の適合規則](../src/type.c) が R を反変、Y と T を共変に扱うので、
**Y と R の両方を正確に言えないと目的の型に届かない**。
L^ に底の型がない以上、`_yield^` は値を送れ、値を受け取れる形でなければならない。

#### 決定

`yield^` の書ける場所すべてに `_yield^` を書ける。**構文木は同じ節点** であり、
区別は印1つに載る。したがって:

- 15.2 の yieldable 判定は `_yield^` でも立つ
- 15.2改 の Y／R の単一化、13.9 の3つの型はまったく同じ経路を通る
- 15.8 の「作って捨てる呼び出しは誤り」も同じく効く

**型検査からは区別できない。それが要点である。**

```lhat
let^ real = p^ -> number^ {
    let^ got : string^ = yield^ 1
    return^ 9
}
let^ fake = p^ -> number^ {
    let^ got : string^ = _yield^ 1     # 同じ c^{string^, number^, number^}
    return^ 9
}
```

違うのは生成だけである。`_yield^` は
**送る値を計算したうえで、中断せずに次へ進む**。

- 送る式は評価する。副作用は `yield^` と同じく起きる
- 中断しないので、**再開する者がいない**。したがって値は返ってこない

#### 受け取る値は `nil^` になる

`let^ a : string^ = _yield^ 1` に到達した場合、`a` は `nil^` になる。
宣言は `string^` なので、**これは型の嘘である**。

嘘を残す。理由は、それが今より良い壊れ方であるためである。

- **到達不能な `yield^`（現状）** — 届くと中断する。
  `start()` が終了状態にならず、**駆動側**が原因から遠い場所で壊れる
- **`_yield^`** — 届いても中断しない。`a` が `nil^` になり、
  `a` を最初に使った時点で 03 の 5.1 の実行時型検査が捕まえる。**現場で落ちる**

専用の捕捉機構は置かない。汎用命令の実行時検査が既にその仕事をしている。
`_yield^` を書くことは「ここは走らない」という書き手の主張であり、
走ったならそれ自体が誤りである。

##### 13.12 の `_^` があれば嘘は消える

嘘を持つのは **名前** である。受け取る値に名前が要らないなら、
`_^`（13.12・未実装）で嘘を持つ入れ物そのものが無くなる。

```lhat
let^ _^ : string^ = _yield^ 1     # R は string^。読める名前はどこにもない
```

R を言うために名前を作る必要がないので、`_yield^` の定型はこの形になる。

#### `_yieldall^` は作らない

15.8 の委譲は、内側の本物のコルーチンの値を必要とする。消しようがない。

#### 残る欠点

署名を **死んだコードに書く** ことになる。
整理でその枝を消すと `p^` が黙ってコルーチンでなくなり、呼び出し側が全部壊れる。
到達不能な `yield^` でも同じであり、`_yield^` が悪化させるものではない。

### 15.12 本体が式1つの `f^` は `return^` を書かない［確定］

> **`f^` の本体が式1つだけであるとき、その式が返り値になる。**

```lhat
let^ square = f^ n:number^ -> number^ { n * n }
let^ sign   = f^ n:number^ -> number^ { if^ n < 0: 0 el^: 1 ; }
let^ wrap   = f^ -> number^ { inner() }        # 呼び出しも同じ
```

Ruby・Rust・Scala が同じ形を持つ。

#### 呼び出しも含む — 型は問わない［重要］

`inner()` が値を返すかどうかは **構文解析器には分からない**。分からなくてよい。

**13.2 により、本体が呼び出し1つだけの `f^` はいま必ず誤りである**
（関数は必ず答えるのに、呼び出し文は答えを捨てるため）。したがって `return^` に変えると:

- `inner()` が値を返す → **通るようになる**（以前は誤り）
- 返さない → `return^ inner()` が誤りになる。しかも
  「値を返さないものを返そうとしている」と、脱落より的確に言える

**どちらでも既存の意味は変わらない。** 判別は検査器が行う。

#### 狭く採る［重要］

**次はいずれも対象外である。**

| 書いたもの | 読み |
| --- | --- |
| `f^ -> number^ { let^ x = 1  x + 1 }` | 誤り。文が2つある |
| `f^ -> number^ { foo()  return^ 1 }` | `foo()` は従来どおり捨てる |
| `p^ -> number^ { 1 + 2 }` | 誤り。`p^` は答えないことがある |
| `f^ -> number^ { do^{ 1 + 2 } }` | 誤り。入れ子のブロックには及ばない |
| `p^ { foo() }` | 従来どおり。捨てる |

狭くする理由は2つある。

**8.1 の理由がまだ生きている。** 裸の式を文として広く認めると、
あらゆる二項演算子が文頭に立てるようになる。**本体が式1つなら前の文が無い**ので、
その曖昧さが生じる余地がない。

**既存の意味を1つも変えない。** 上はいずれも現在すでに誤りか、
すでに「捨てる」意味を持つ。

##### `f^` に限るのが安全の要である

`p^ { foo() }` は **いま正当であり「捨てる」意味を持つ**。
これを返り値にすれば意味が変わる。`f^` は元々誤りなので変わらない。

つまり「`f^` に限る」ことが、この規則を純粋な追加にしている。
`p^` に広げるなら **返り値型を宣言した `p^` に限る** といった条件が要る。未決とはしない。

#### 構文解析の段で `return^` にする

本体が文1つかどうかは **リストが終わって初めて分かる**ので、
裸の式はいったん式文として読み、本体を閉じた時点で `return^` に変換する。
文が2つ以上あれば、そこで 8.2 の誤りとして報告する。

**検査器と生成器は何も知らない。** 届くのは普通の `return^` である。

## 16. `for^` と `repeat^`［確定］

### 16.1 `for^` はループを意味しない［確定・最初に読むこと］

**`for^` は「いま注目している値が定義される場所」である。** 繰り返しの指示ではない。

```text
for^ <焦点> <駆動節> { … }
```

`for^` が値を導入し、**続く節がその値をどう使うかを決める**。

| 駆動節 | 意味 |
| --- | --- |
| `to^` / `downto^` | 数値として反復する |
| `in^` | 反復子から取り出して反復する（16.3） |
| `while^` / `until^` | 条件が続くあいだ反復する |
| `if^` | 反復せず、条件判定に1回だけ使う |
| `when^` 節群 | 値を分岐に掛ける（パターンマッチ。17 章） |

この理解がないと、`for^ x := 1 if^ c { … }` が例外にしか見えない。
実際には5つの形すべてが1つの原理から出ている。

**`for^` という語は他のどの言語でも「ループ」を意味する。**
読み手は必ずその予断を持って来るため、
本章の記述および利用者向けの文書は、いずれもこの再定義から始める必要がある。

### 16.2 焦点の既定の名前は `it^`［確定］

焦点に名前を付けるかどうかは任意である。付けなければ `it^` で参照する。

```lhat
for^ i := 1 to^ 10 { print(i) }     # 焦点に i と名付けた
for^ 1 to^ 10 { print(it^) }        # 名付けていないので it^
```

Memo.md L330 が既にこの形を用いている。

```text
for^i+t[3]: when^t[1] to^t[2]: it^ other^ nil^
```

ここでの `it^` は `for^` が導入した焦点そのものを指す。

名前を付ける場合、初期値を伴う束縛は `:=` で書く（16.3）。

### 16.3 `for^` の形［確定］

#### 数値の反復

```lhat
for^ i := 1 to^ 10 { … }
for^ i := 1 to^ 10 step^ 2 { … }
for^ i := 10 downto^ 1 { … }
for^ i := 10 downto^ 1 step^ 2 { … }
```

Memo.md L243–L247 の `from^` は **採らない**。
`i := 1` と書くことで、初期値を伴う束縛は `:=` という規則が言語全体で保たれる。

```lhat
for^ i from^ 1 to^ 10     # 採らない。i が := なしで生まれる唯一の場所になる
```

`in^` に `:=` がないのは初期値が存在しないためであり、例外ではない。

Pascal の `for i := 1 to 10` が同じ形をとる。

#### 反復子による反復

```lhat
for^ k, v in^ t { … }
```

カンマは分解の対象を並べる（13.10）。
`in^` が続くため多重定義と紛れず、`unpack^` を要しない。

##### `in^` の右は「反復子を答えられるもの」［確定］

> **`in^ e` は `e.iterate()` を呼び、返ってきたコルーチンを尽きるまで進める。**

13.9 が反復子をコルーチンと定めているので、
**歩く対象は常にコルーチンである**。違うのは、それをどこから得るかだけになる。

| `e` | `iterate()` が答えるもの |
| --- | --- |
| テーブル | 鍵と値の組を出すコルーチン（組込み） |
| コルーチン | 自分自身（組込み） |
| 利用者定義 | 書かれた `iterate` メンバ |

**組込みは、そのメンバが書かれていない場合にだけ答える。**
テーブルに `iterate` を書けば、そちらが使われる。

判定は 11.3 の構造的な規則そのままである。
「`iterate` を持つか」を問うだけで、特別な標識も継承関係も要らない。
`start`、`resume`、`dispose` を組込みで持つ扱い（12.6、05 の 8.5）と同じ位置づけになる。

##### 歩きは手で駆動できる［確定］

`iterate()` が答えるのはコルーチンであるから、
**`for^` に渡さず、`start()` と `resume()` で自分で進めてもよい**。

```lhat
let^ w = t.iterate()
let^ pair = w.start()        # 最初の組
let^ next = w.resume(nil^)   # 次の組
w.done()                     # 尽きたか
```

15.2 改の規則はテーブルの歩きにもそのまま効く。
本体を持たないことは、最初の再開が単独で意味を持つ理由にならない。

- `start()` — 最初の組。まだ始まっていない歩きにだけ使える
- `resume(v)` — 次の組。始まっていない歩きへの呼び出しは誤り
- 尽きたら `nil^` を答え、以後 `done()` が真になる
- `dispose()` — 歩きに保留中の後始末は無いので、終わらせるだけ（10.7）

送る値 `v` は捨てられる。歩きの受け取る型は `nil^` である（13.9 の3つの型は
`c^{nil^, t^{}, nil^}` になる。出す型がテーブルなのは 13.8 がタプルを持たないため）。

`for^ … in^` が吐く命令は `start()` を経ずに歩を進める低位のものだが、
**利用者が書く側の規則は 15.2 改のまま** であり、両者は一致している必要がある。

##### テーブルを歩く順序［確定］

**密な部分を添字順に先に歩き、残りは順序を定めない。**

14 章がテーブルを列と写像の両方にしているため、列の側には守る価値のある順序がある。
ハッシュ部の順序は実装の都合であり、約束しない。

##### 1つの名前は値をそのまま受ける［確定］

13.10 のとおり、**1つなら丸ごと、複数なら位置で分解**する。
`in^` がその印を兼ねるので `unpack^` は要らない。

```lhat
for^ v in^ gen()      # gen が出した値そのもの
for^ k, v in^ t       # 組を位置で分解する
```

テーブルを1つの名前で歩けば、`v` には組そのものが入る。

##### 焦点は読むのではなく束縛する［確定］

`in^` の焦点は **`for^` の見出しが名前を定義する唯一の位置** である。
`to^` や `while^` の焦点は初期値を伴う束縛文（`i := 1`）として書かれるが、
`in^` の焦点は名前だけであり、束縛であることが記法から見えない。

型は歩きが出す型から決まる。

- 1つの名前 → 出す型そのまま
- 複数の名前 → 位置で分解（13.10）。テーブルを歩く場合、
  **位置1が鍵、位置2が値** の型になる（14.10）
- 注釈を書いた場合（`for^ x:number^ in^ …`）→ 注釈が型になり、
  その位置の型がそれに収まることを要求する

鍵の型はテーブルのどちら半分を歩くかで決まる。
密な部分だけなら `number^`、名前つきだけなら `string^`、
両方あればその合併になる。

```lhat
let^ t = { 10, 20 }
for^ k, v in^ t { … }         # k: number^   v: number^

let^ u = { a := "x" }
for^ k, v in^ u { … }         # k: string^   v: string^
```

```lhat
for^ x in^ gen() { let^ n:number^ = x }   # gen が number^ を出すなら通る
for^ x in^ gen() { … }
let^ n = x                                 # 誤り。焦点は 16.7 のとおり
                                           # 繰り返しのスコープに属する
```

##### `in^` の右は静的にも問う［確定］

`iterate()` を答えられないものを `in^` に渡すのは誤りとする。
15.8 が `yieldall^` に課す要求と同じものであり、
**同じ診断**（「歩く／委譲するコルーチンが無い」）を使う。

書かれた `iterate` がコルーチンでないものを答える場合も同様に誤りとする。

```lhat
for^ x in^ 5 { … }                                      # 誤り
let^ t = { iterate := f^ -> number^ { return^ 1 } }
for^ x in^ t { … }                                      # 誤り
```

##### 反復子は状態を持つ

13.9 のコルーチンであるから、**2度歩けば2度目は尽きている**。
`in^` に同じコルーチンを2度渡した場合の動作はこれで決まっている。
毎回新しく歩きたければ、`iterate` を呼ぶたびに新しいコルーチンを返す側にする。

#### 条件つき反復

```lhat
for^ i := 1 while^ i < 10 next^ i := i + 1 { … }
for^ i := 1 until^ i ≧ 10 next^ i.inc() { … }
```

`next^` は毎回の反復の後に実行される文である。省略できる。
Memo.md L259 は `next^ i -> i + 1` と書いているが、
後置再代入は Q2 で撤回されたため `next^ i := i + 1` になる。

`next^` にはカンマで複数の文を並べられる（Memo.md L532）。

##### `next^` を取るのは `while^` と `until^` だけ［確定］

`next^` は **条件つき反復の更新** である。他の形は自分で焦点を進めるため、
`next^` に動かす対象がない。書けば構文の誤りとする。

```lhat
for^ i := 1 while^ i < 3 next^ i := i + 1 { … }   # これが next^ の場
for^ i := 1 to^ 3 next^ i := i + 1 { … }          # 誤り
for^ k, v in^ t next^ … { … }                     # 誤り
repeat^3 next^ … { … }                            # 誤り（16.5）
```

- `to^` / `downto^` — 16.4 のとおり `while^ … next^ …` への糖衣であり、
  展開が生成する `next^` と衝突する
- `in^` — 16.3 のとおり歩きのコルーチンが進める。焦点は再開のたびに束縛される
- `repeat^` — 焦点そのものを持たない（16.5）

#### 反復せず1回だけ使う

```lhat
for^ i := 1, j:int^ := 2 if^ i + j < 10 { … }
```

**これは繰り返しではない。** 次と等価である。

```lhat
do^{
    let^ i = 1
    let^ j:int^ = 2
    if^ i + j < 10 { … }
}
```

存在する理由は、**条件で使う値を一度だけ計算して名前を付けたいが、
その名前で外側のスコープを汚したくなく、入れ子も深くしたくない** という要求にある。

比較の連鎖（11.5 の (5)）は共有される被演算子を1度しか評価しないため
この要求をある程度緩和するが、`f(x) < g(y)` のように
別々の呼び出しが絡む場合には効かない。

複数の定義をカンマで並べられる。
`for^ k, v in^ t` のカンマとは役割が違うが、`:=` の有無で判別できる。

`elseif^` `else^` の節からも焦点が見える。

**繰り返しではないため、9 章の節（`prolog^` `main^` `epilog^` など）は付けられない。**

##### 式の形もある［確定］

5.1 と同じく、`{` が文の形を、`:` が式の形を開く。

```lhat
let^ i = for^ n := f(1) if^ n > 1: n el^: 0 ;
```

16.1 のとおり **`for^` は続く節の形をそのまま採る**。
`if^` に文と式の2つがある以上、`for^ if^` にも2つある。

**16.7 はこれを妨げない。** 式にしても **焦点の名前は外へ出ない**。
出るのはその名前から作った値であり、それが式というものである。
「名前を外に漏らさずに条件へ使う」という上記の目的はそのまま保たれている。

17 章のパターンマッチも同じ形を持つ。

#### パターンマッチ

```lhat
for^ expr { when^ 0: … other^: … }
```

17 章で定める。13.11 の絞り込みを先に決めたことで、その上の糖衣に収まった。

### 16.4 方向は推論しない［確定・重要］

Memo.md L245 は `for^i from^10 to^1` を降順（Lua の `for i=10,1,-1` 相当）としており、
**`from` と `to` の大小から方向を推論する**設計だった。これは採らない。

推論すると **空の範囲を表現できなくなる**。

```lhat
for^ i := 1 to^ n { … }
```

`n` が `0` のとき、推論する設計では `1 > 0` なので降順と解釈され、
**`1`, `0` の2回まわる**。求めているのは0回である。

「要素数だけ繰り返す」は最も頻出する用法であり、
そこで意図と逆の動作をする設計は採れない。

Lua が降順に `for i=10,1,-1` と明示を要求しているのは、これを避けるためである。

#### `step^` は正の量とする

符号は `to^` と `downto^` が決める。負の `step^` は誤りとする。

Memo.md L338–L341 が「10を返した後一回で終わってしまう」と混乱を記録していた
`10 to^1 step^2` は、この規則では単に0回になる。

#### 展開

数値の反復は条件つき反復への糖衣である。

```text
for^ i := A to^ B step^ S      →  for^ i := A while^ i ≦ B next^ i := i + S
for^ i := A downto^ B step^ S  →  for^ i := A while^ i ≧ B next^ i := i - S
```

原始的な形は **条件つき反復と `in^` の2つ** であり、
`to^` と `downto^` はその上の糖衣にあたる。

#### 上限と `step^` は1度だけ評価する［確定］

> **`to^` / `downto^` の上限と `step^` は、繰り返しに入る前に1度だけ評価する。**

```lhat
for^ i := 1 to^ t.size() { … }     # size() は1度だけ呼ばれる
```

上の展開をそのまま読むと毎回評価されることになるが、
**展開は意味を説明するための道具であって、評価回数まで規定しない**。

上限と `step^` は2つで **この繰り返しがどこまでどう進むか** を定めており、
繰り返しに入った後で動かせると、走っている最中に走り方が変わることになる。
Lua と Pascal が上限と歩幅を1度だけ評価するのも同じ理由による。

反復ごとに変えたい場合は、それを行う節が別にある。

```lhat
for^ i := 1 while^ i ≦ 9 next^ i := i + step { … }
```

`next^` は反復のたびに実行される **文** であり（16.3）、そこが可変な前進の置き場になる。
`to^` / `downto^` は「決まった範囲を決まった歩幅で」という形に閉じている。

`repeat^ n`（16.5）の `n` も1度だけ読む。
「`n` 回」が回数を指す以上、途中で変わってはならない。同じ理由である。

### 16.5 `repeat^` — ループ変数を持たない繰り返し［確定］

```lhat
repeat^ n { … }           # n 回
repeat^ { … }             # 無限。break^ で抜ける
repeat^ while^ c { … }    # 条件が成り立つあいだ
repeat^ until^ c { … }    # 条件が成り立たないあいだ
```

`for^` との違いは **焦点を導入しない** ことにある。
他の多くの言語の while ループにあたるものが `repeat^ while^` である。

`while^` を単独の文にしなかったのは、`for^` の中の `while^` 節と紛らわしいためである。

#### `next^` は取れない［確定］

更新の節は `for^` のものである。
`repeat^` が `next^` を取れると `for^` との境界がぼやけるため、認めない。

#### `until^` は `while^` の否定にすぎない［確定］

判定の時期は `while^` と同じで、本体の前である。
`repeat^ until^ c` は `repeat^ while^ !c` と同じ意味になる。

Memo.md L240 が後置表現を全廃しているため、**判定を後ろに書く記法は存在しない**。
判定が後に来る繰り返しそのものは 9.10 の `pre^` で書ける。
節の見出しで表すので、`while^` の位置は前のままである。

```lhat
repeat^while^ c {
    pre^:
        …            # 判定より前。c が最初から偽でも1回は走る
}
```

`pre^` を使わずに書き下すこともできる。

```lhat
repeat^{
    …
    if^ !c { break^ }
}
```

### 16.6 キーワードを増やす費用が低い［確定・設計原則］

`until^` は `while^` の否定でしかなく、`downto^` は `to^` と対をなすだけである。
どちらも表現力を増やさない。それでも用意するのは、**費用が低いためである**。

L^ には予約語が存在しない（01 の 2.1）。
キーワードは必ず `^` を伴うため、`until` や `downto` という名前の変数は
何の影響も受けない。**キーワードを追加しても既存のコードが壊れない。**

これは `^` サフィックスを採った設計の直接の帰結であり、
予約語を持つ言語では成り立たない自由度である。
自然言語として読みやすくなるという理由だけで制御構文を用意してよい。

### 16.7 焦点の寿命［確定］

`for^` が導入した焦点は、**繰り返し全体を通じて存在する**。

9.4 の区分では `prolog^` および `first^` で宣言した変数と同じ扱いになり、
`main^` で宣言した変数（寿命は1反復）とは異なる。

したがって次が成り立つ。

- `prolog^` は条件が一度も成立しない場合にも実行されるが、その時点で焦点は存在する
- `last^` は焦点を「条件が成立した最後の状態」で参照できる（9.7）
- `epilog^` および `finally^` からも参照できる

### 16.8 Lua の `repeat` との相違［注意］

**Lua の `repeat … until` は後判定である。** L^ の `repeat^ until^ c` は前判定であり、
同じ綴りで意味が反転している。

この設計は「馴染みのある綴りに別の意味を与える」ことを一貫して避けてきた
（Q8 の `or^`、Q3 の `?` と `!`、S11 の (3) の `|`）。
本項はその例外にあたる。

それでも `repeat^` を採るのは、L^ が Lua とは別の言語であり、
`repeat^` が「繰り返す」という語として自然に読めるためである。
Lua の経験がある読者が一度戸惑う点として、文書に明記しておく。

#### `overload^` — 呼び出し方を増やす

関数・手続きに限り、元の定義を残したまま呼び出し方を増やせる。

```lhat
let^ Foo = def^{
    self^{},
    foo := p^ { print("a") },
}

let^ Bar = Foo .. def^{
    overload^
    foo := p^x:string^ { print(x) },
    bar := f^ { 1 },
}
```

`Bar` のインスタンスは `foo()` と `foo("bbb")` の両方を受け付ける。

#### 多重定義の型は交差である［重要］

`Bar.foo` の型は次のとおり。

```text
p^; & p^string^;
```

**合併 `|` ではない。**
多重定義されたメンバは「引数なしでも文字列1個でも呼べる」のであり、
両方の性質を **同時に** 備える。14.5 の区別に照らせば交差である。

合併にすると「どちらか一方である」という意味になり、
`foo()` が呼べる保証が失われる。文字列を要求する側かもしれないためである。

TypeScript が多重定義を関数型の交差として扱うのも同じ理由による。

```lhat
print(typeof^(Bar.new^()).signature)
```

```text
t^{ bar : f^ -> number^;, foo : p^; & p^string^;, new : f^; }
```

多重定義された `foo` の型に交差が現れる。合成の表示にも `&` を用いる（14.5）ため、
記号が一貫する。

14.16 の実装は常に構造を開く（`label` を運用していないため、`Foo & …` の
ように名前を残す短縮形はまだ書けない）。

#### 多重定義の解決［確定］

##### 重なりを禁じる

`overload^` で加える署名は、**同名の既存の署名のどれとも重なってはならない**。

> **重なる** とは、ある呼び出しが両方に適合しうることをいう。

重なりは **`overload^` を書いた場所で** 報告する。14.12 の原則に従う。

##### 順位付けを採らない理由［重要］

C++ や Java は候補に順位を付け、最も特殊なものを選ぶ。**L^ はこれを採らない。**

**構造的型付けでは「より特殊」が定まらない** ためである。

```lhat
overload^ draw := p^ s:t^{radius : number^};
overload^ draw := p^ s:t^{width : number^, height : number^};
```

`{radius := 1, width := 2, height := 3}` は両方に適合する。
そしてどちらが「より特殊」かを言う根拠がない。両者は比較不能である。

公称型付けなら継承の木が順序を与えるので、この状況は稀にしか起きない。
構造的型付けでは **値が無関係な構造を同時に満たすことが普通に起きる** ため、
順位付けの規則を置いても決まらない場合が大量に残る。

順位付けを採ると、決まらなかったことは **呼び出し側で** 報告される。
定義から遠く離れた場所である。重なりを定義の時点で禁じれば、
報告は `overload^` を書いた行に戻る。

##### 重なりの判定

2つの署名が重なるのは、次を満たす引数の個数 `n` があるときである。

- `n` が **両方の署名で許される個数** であり、かつ
- **すべての位置 `i < n` で、両者の型が互いに素でない**

言い換えると、**1つでも互いに素な位置があれば重ならない**。
呼び出しは全位置を同時に満たす必要があるためである。

許される個数は、既定値（13.4）と可変長（13.7）から範囲として決まる。

```lhat
p^a:number^;                      # 1 個
p^a:number^, b:string^ = "x";     # 1〜2 個
p^...:any^;                       # 0 個以上
```

範囲が交わらなければ、型を見るまでもなく重ならない。
14.12 の診断が例に挙げた「引数の個数を増やす」用途はここで決着する。

**互いに素**（同時に満たす値が存在しない）は次のように定まる。

- 異なる組み込み型どうし — 互いに素（`number^` と `string^`）
- 組み込み型と構造 — 互いに素
- 構造どうし — **同名のメンバの型が互いに素であれば** 互いに素。
  共有するメンバ名がなければ **互いに素ではない**（両方を備えた値がありうる）
- 合併 `A|B` と `C` — `A` と `C`、`B` と `C` の **両方** が互いに素なら互いに素
- 交差 `A&B` と `C` — **どちらか** が `C` と互いに素なら互いに素
- `any^` — 何とも互いに素にならない（頂点型のため。13.7）

一般の条件は「両方に属する値が存在しない」であり、
判定には 14.12 の変性検査が要求するのと同じ部分型関係の機構を使う。
新たに作るものはない。

第一引数の `self^` は同じ定義の多重定義すべてで同じ型なので、
**位置を分ける役には立たない**。`self^` で多重定義することはできない。

##### 帰結 — 呼び出し側に選択は残らない［重要］

重なりを禁じた結果、次が成り立つ。

> **1つの呼び出しに適合する候補は高々1つである。**

したがって呼び出し側の解決は **選択ではなく検索** になる。
順位、変換の優先度、曖昧性の報告 — どれも要らない。

引数の型が合併であっても崩れない。

```lhat
overload^ show := p^ x:string^;
overload^ show := p^ x:number^;

v : string^|number^
show(v)     # 誤り。どちらの候補も v のすべての値を受けられない
```

候補は引数型の **すべての値** を受けられなければならない。
`v` はどちらの候補にも適合しないので、これは曖昧ではなく **適合なし** である。
書き手は先に絞り込む。

##### 返り値は解決に関与しない［確定］

候補の選択は引数だけで決まる。返り値の型は見ない。

引数が重なり返り値だけが違う2つは、そもそも重なりとして退けられる。
`f^` と `p^` の別（15 章）も同様で、引数が重なれば退けられる。

##### 多重定義されたメンバの型は交差である［確定］

`typeof^(x).signature`（14.10, 14.16）が多重定義をどう書き表すかは、
既にある記法で決まっている。

```lhat
t^{ show : p^string^; & p^number^; }
```

14.5 のとおり `&` は「すべての構造を備える」を意味する。
多重定義されたメンバは **どの署名でも呼べる** のだから、まさに交差である。
新しい記法は要らない。TypeScript が同じ対応を採っている。

この見方は重なりを禁じる理由も裏から説明する。
関数型の交差は、**どの腕が働くかを言えて初めて意味を持つ**。

さらに、14.4 が認めた「メソッドを値として取る」形も特別扱いを要さない。

```lhat
let^ show = foo2.show          # 型は p^self^, string^; & p^self^, number^;
show(foo2, "x")            # 解決の規則は呼び出しの位置によらない
```

多重定義されたメンバも **1つの型を持つ1つの値** である。
取り出した先で呼んでも、規則は同じ検索でよい。

##### 多重定義された名前を `override^` する［確定］

多重定義を経た名前は交差を担っている。そこへ `override^` を書いた場合、
**置き換わるのは重なった腕1つだけ** である。

```lhat
let^ Foo = def^{ self^{}, show := p^self^, n:number^ { } }
let^ Bar = Foo .. def^{ self^{}, overload^ show := p^self^, s:string^ { } }
                                          # show : p^number^; & p^string^;

let^ Baz = Bar .. def^{ self^{}, override^ show := p^self^, n:number^ { } }
                                          # number^ の腕だけが置き換わる
                                          # show : p^number^; & p^string^; のまま
```

判定は重なり（本節）で行う。置き換えた腕以外はそのまま残るので、
`Baz` のインスタンスは `show("x")` を呼べ続ける。

置換可能性（14.12）の検査は **重なった腕に対して** 行う。交差全体に対して
行ってはならない。交差の位置でそのまま使えるものは交差だけであり、
どの署名1つもそれを満たさないので、あらゆる置き換えが不正になってしまう。

重なりの数によって3つに分かれる。

- **ちょうど1つ** — その腕に対して置換可能性を検査し、その腕だけを差し替える
- **2つ以上** — 誤り。`override^` は引数を広げてよいため、広げた結果2つに
  届くことがある。どちらを置き換えたのかが決まらない
- **0個** — 誤り。その名前に置き換える相手がない。印だけを書いた場合と同じ扱い

```lhat
let^ Baz = Bar .. def^{
    self^{},
    override^ show := p^self^, ...:number^ { },   # 誤り。個数が両方の腕に届く
}
```

##### `override^` との組み合わせ［確定］

`override^` は、**新しい署名と重なる既存のメンバ** を置き換える。
既存の候補は互いに素なので、重なる相手は高々1つに定まる。
14.12 の置換可能性の検査はその相手に対して行う。

`override^` は引数を広げてよいため、広げた結果 **2つ以上と重なる** ことがある。

```lhat
# 既存: p^number^; と p^string^;
override^ foo := p^number^|string^;    # 誤り。どちらを置き換えるのか決まらない
```

これは誤りとする。個別に置き換えるか、構成を見直す。

##### 1つの `def^` の中でも同じ［確定］

同名のメンバを1つの `def^` の中に2つ書く場合も、`overload^` を要し、
重なりの規則は同じである。合成した場合と扱いを変える理由がない。

##### 形で振り分けたい場合

上の `draw` のように、重なる構造で振り分けたいことはある。
その用途は **多重定義ではなくパターンマッチ**（17 章）が引き受ける。

- **多重定義** — 静的に分離できる呼び出し方の違いを扱う
- **パターンマッチ** — 値の形を実行時に見て振り分ける

判別用のメンバを持たせて構造を互いに素にする手もある。
構造的型付けを採る言語で判別付き合併が使われるのはこのためである。

## 17. パターンマッチ［確定・旧 S19］

### 17.1 `is^` があるうえで何を足すのか

S19 を起票した時点では絞り込みがなかった。13.11 で `is^` が定まったいま、
型による振り分けは既に書けるうえに網羅性まで検査される（[04-errors.md](04-errors.md) の 7 章）。

```lhat
if^ r is^ ParseError.Syntax {
    report(r.line)
    elseif^ r is^ ParseError.Eof:
        recover()
    else^:
        use(r)
}
```

したがって `when^` が足すのは次の2つに絞られる。

- **主語を1度しか書かない**
- **値と範囲のパターン** — `is^` は型しか問えない

この2つだけを足す。**残りは 13.11 の上に載せる**（17.9）。

### 17.2 形［確定］

#### 文形

```lhat
for^ expr {
    when^ 0:
        stats
    when^ 1 to^ 3:
        stats
    other^:
        stats
}
```

#### 式形

```lhat
let^ r = for^ expr: when^ 0: e when^ 1 to^ 3: e other^: e ;
```

Memo.md L186–L199 の形である。綴りの差は 17.4 と 17.5 に記す。

#### 主語は一度だけ評価され、名前を持つ

`for^` は 16.1 のとおり **焦点が定義される場所** であり、パターンマッチでも同じである。
主語は一度評価され、16.2 により `it^` で参照できる。名前を付けてもよい。

```lhat
for^ parse(s) { when^ is^ ParseError.Syntax: report(it^.line) other^: recover() }
for^ r := parse(s) { when^ is^ ParseError.Syntax: report(r.line) other^: recover() }
```

**節の中では主語をこの名前で参照する。** 主語の式そのものを書き直すことはしない。
そうでないと呼び出しが節ごとに再評価される。

### 17.3 パターン［確定］

3種類とする。

| 形 | 意味 |
| --- | --- |
| `when^ V:` | 値が等しい |
| `when^ A to^ B:` | `A` 以上 `B` 以下 |
| `when^ is^ T:` | 型 `T` に適合する（13.11） |

`to^` は 16.4 と同じく **両端を含む**。空白は必須である（01 の 10.3）。
Memo.md L192 の `when^1to^3` は現在の字句規則では成立しない。

#### カンマで複数並べられる［確定］

```lhat
for^ c {
    when^ `a`, `e`, `i`, `o`, `u`:
        vowel()
    other^:
        consonant()
}
```

いずれか1つに合えば選ばれる。`or^` への糖衣であり、文法以上のものを要さない。

C の `case` のフォールスルーが担っていた用途を、**落ちる仕組みなしで** 賄う。

### 17.4 型のパターンには `is^` を書く［確定・重要］

型を問うパターンで `is^` を省き `when^ T:` と書けるようにする案は **採らない**。

**名前が値か型かを決められない。**

```lhat
when^ Foo:     # 変数 Foo の値と比べるのか、型 Foo への適合を問うのか
```

どちらも名前であり、真の曖昧性になる。`is^` を書けば決まる。

そして 13.11 が `is^` を「型への適合を問う」と定めている以上、
**同じ語が同じ意味で現れる**。新しい規則ではない。

### 17.5 既定の節は `other^`［確定］

```lhat
other^:     # 推奨形
el^:        # 同じ意味
else^:      # 同じ意味
```

5.3 が条件分岐で `el^` `else^` を認めているため、同じ語を同じ意味で使えることにする。
推奨形を `other^` とするのは、**分岐の条件ではなく「残り」を表す**ためであり、
Memo.md L195 の綴りでもある。

Memo.md は文形で `other^`、式形で `else^` と書いており食い違っていた。統一する。

#### `:` は省略できない［確定］

Memo.md L195 は「`:` は省略可能だが必須にするか？」と保留していた。**必須とする。**

6.3 の「`:` は開いた構造を導入する」に例外を作らない。

#### 文形では省略でき、式形では省略できない

文形は主語がどの節にも合わなければ何も起こらない。`other^` は省略できる。

式形は **値を返さなければならない** ため `other^` を要する。
すべての場合を尽くしたことを値のパターンについて示す手段がないためである。

### 17.6 `;` が閉じるのは `for^` の `:` だけ［確定］

式形は `:` を何度も使うが、**開くのは `for^ expr:` の `:` だけ** である。
`when^` と `other^` の `:` は開かない。

```lhat
let^ r = for^ expr: when^ 0: e when^ 1 to^ 3: e other^: e ;
```

5.1 の if 式が同じ構造を持つ。`if^` の `:` だけが開き、
`el^` の `:` は開かず、`;` が全体を閉じる。

したがって 6.3 の規則はそのまま成り立ち、閉じ忘れの位置も一意に決まる。

### 17.7 分解パターンは設けない［確定・重要］

`when^ {x, y}:` のように照合しながら中身を取り出す形は **設けない**。

#### 他言語で分解が中心的な理由

Rust の `Some(v)`、ML と Haskell の `(y:ys)`、Scala、Swift、Python 3.10、C# 8 以降、
Elixir はいずれも分解パターンを持つ。

**共通するのは、照合以外に中身へ届く手段がないことである。**
構成子の引数には名前がなく、判別子の裏に隠れている。
パターンが分解を担うほかない。

C、Go、Java（17 未満）、JavaScript の `switch` は値だけを見る。Lua には `switch` がない。

#### L^ では中身に名前がある

04 の 2.2 は誤りの種別に **名前付きのフィールド** を持たせている。

```lhat
errordef^ ParseError { Syntax { line : number^, column : number^ }, Eof }

for^ r := parse(s) {
    when^ is^ ParseError.Syntax:
        report(r.line, r.column)
    other^:
        recover()
}
```

テーブルのメンバも同じである。
そして 13.8 が多値返却を廃止したため、**位置指定の組が存在しない**。
分解が効く相手がそもそもない。

13.10 が `unpack^` の入れ子分解を「当面設けない」と保留しているのと同じ判断であり、
必要になれば **両方を同時に** 設計する。同じ問題だからである。

### 17.8 ガードは設けない［確定］

`when^ is^ number^ if^ it^ > 0:` のような追加条件は設けない。

`for^` には既に `if^` の形がある（16.3）。同じ語が1つの構文の中で別の役を持つと、
どちらの読みかを毎回決めなければならなくなる。

節の中に `if^` を書けば済む。

```lhat
for^ n {
    when^ is^ number^:
        if^ n > 0 {
            positive()
            else^:
                negative()
        }
    other^:
        fail()
}
```

節が括弧の内側に来るのは 5.2 のとおりであり、文の側で短縮形を使わないのも同じ節による。

### 17.9 展開 — `if^` の連鎖への糖衣［確定・重要］

パターンは次のように展開される。主語を `s` とする。

```text
when^ V:            →  s = V
when^ A to^ B:      →  s ≧ A and^ s ≦ B
when^ is^ T:        →  s is^ T
when^ P, Q:         →  展開(P) or^ 展開(Q)
other^:             →  else^
```

**残りは 13.11 と 04 の 7 章がそのまま担う。**

- **絞り込みが効く** — `when^ is^ ParseError.Syntax:` の節の中で主語は
  その種別に狭まり、宣言されたフィールドが見える（04 の 6.1）
- **網羅性が付く** — 型のパターンで合併を尽くせば、
  最後の節に残るのは成功時の型である。専用の機構は要らない
- **型検査に足すものがない** — 構文木を if の連鎖と同じ形に落とせば、
  既存の検査がそのまま走る

S19 を起票したときは「範囲が広いため別章を起こす」としていたが、
**13.11 を先に決めたことで範囲が縮んだ**。足したのは主語の共有と値のパターンだけである。

### 17.10 `for^` の5つ目の形について［確定］

`for^` はこれで5つの形を持つ。

| 駆動節 | 反復するか |
| --- | --- |
| `to^` `downto^` | する |
| `in^` | する |
| `while^` `until^` | する |
| `if^` | しない（16.3） |
| `when^` | しない（本章） |

16.1 のとおり `for^` は **焦点が定義される場所** であり、
何をするかは続く節が決める。この統一はここでも保たれる。

**実行時の費用は増えない。** 5つの形は構文解析の時点で分かれ、
それぞれ別のコードに落ちる。「どの `for^` か」を実行時に判定する場所はない。
