# 多言語化

L^ の処理系と道具が人に見せる文を、読み手の言語で出すための設計。
あわせて、L^ で書いたプログラムが自分の文を多言語化するときに、
言語の側が何を持ち、何を持たないかを定める。

言語そのものは変えない。語・綴り・型の書き方は一つであり、
訳の対象になるのは **人に向けて書かれた文** だけである。

## 1. 位置づけ

多言語化には2つの側がある。

- **処理系が人に見せる文** — 診断、トレースバック、CLI・言語サーバ・デバッガの文言。
  書いたのは処理系であり、訳すのも処理系の責務になる（§3〜§7）
- **L^ プログラム自身の文** — ゲームの画面の文言や、作者が書いた説明文。
  書いたのはプログラムの作者であり、処理系は訳さない（§8）

文字の扱いは既存の文書が決めている。ここでは引用するだけで、定め直さない。

- ソースの文字符号化は UTF-8 固定である（01 §1）
- 識別子の文字集合は UAX #31 に従うので、日本語の名前も書ける（01 §3.1）
- Unicode 正規化は行わず、識別子の同一性はコードポイント列で決まる（01 §1）
- 文字列の長さはコードポイント数であり、書記素クラスタではない（02 §14.18）

## 2. 原則

### 2.1 プログラムが観測できる文は言語設定で変わらない［重要］

> **L^ プログラムから読める文は、どの言語を選んでも同じバイト列である。**

対象は次のとおり。

- `tostring` の答え（02 §14.17）と、数の書き出し
- `typeof^` の綴り（02 §14.16）
- LTON の読み書き（08）

同じプログラムは誰が走らせても同じ結果を出さなければならない。
これらを比べる、保存する、ネットワークへ送るプログラムは、
走らせた人の言語設定で振る舞いが変わってはならない。

#### 人に読ませる説明は例外である

誤り値の `message`（04 §2.3）は人に見せるための説明であり、訳す。
訳せなければ、この欄を持つ意味が薄い。

> **プログラムは `message` の中身で分岐しない。何の誤りかは種別で判断する。**

- 標準ライブラリが埋める `message` も訳す。std.task と std.thread が
  失敗の説明に入れる実行時の状態とトレースバックは、§7.2 のとおり機械を作った program の言語で出る
- **std.debug.traceback の答えも訳す。** 人がログで読む文であり、`message` と同じく
  プログラムが中身で分岐する対象ではない。文の大半はファイル名・行・名前で、
  訳に変わるのは定型の4語（3.1）だけである。トレースバックの文を読み取る道具は無い
  — デバッガのスタック表示も Godot の表示も、構造化された API から組み立てている
- ［補足］`message` を比べるテストは、言語を固定して走らせる。CLI は既定で OS のロケールに従う（7.4）ので、
  固定しなければ走らせる環境によって期待値が変わる

### 2.2 英語が基準である

英語の文が基準であり、ほかの言語はその訳である。訳が無い文は英語で出す。

テストは文ではなく ID で比べる。検査器の単体テストが既にコードで比べている
（`CHECK_REPORTS`）ので、英語の文言を磨いても、訳を足してもテストは動かない。

### 2.3 言語の選択は大域に置かない

`setlocale` のようなプロセス全体の設定は使わない。

- std.task は機械ごとにワーカースレッドで走る。大域の設定はスレッド間で競合する
- 言語サーバは複数のワークスペースを抱え、それぞれに別の設定がありうる

言語は **program ごと** に持つ（§7）。

## 3. 対象

### 3.1 処理系が人に見せる文

| 対象 | 出どころ | 件数 | 入口 |
| --- | --- | --- | --- |
| 検査器 | `check` | 112（名前を伴う別の文 4 を含む） | `lhat_check_message_write` |
| 構文解析 | `parse` | 67（トークンの種類の句 8 と、期待したトークンを言う文 1 を含む） | `lhat_parse_message_write` |
| 字句解析 | `lex` | 18 | `lhat_lexer_error_message` |
| コンパイルの状態 | `compile` | 9（名前を伴う別の文 2 を含む） | `lhat_compile_message_write` |
| 実行時の状態 | `run` | 20 | `lhat_run_status_message` |
| program | `program` | 8（読み込みの失敗を言う文 1 を含む） | `lhat_program_error_message`・`lhat_program_load_failure` |
| ソースの読み込み | `source` | 3 | `lhat_source_init_from_file` |
| 報告の見出し | `report` | 2 | `lhat_report_write`（`error:`・`note:`） |
| トレースバックの定型 | `trace` | 4 | `lhat_machine_traceback`（`traceback:`・`in`・`at the top level`・`(coroutine)`。`f^` と `(finally^)` は訳さない） |
| CLI | `cli` | 25 | `cli/main.c` |
| デバッガ（DAP） | `dap` | 12 | `dap/adapter.c` |

言語サーバが自分で書く文は診断の文面だけである。ホバーが出す定義の行は
コードであり、説明文は作者が書いたものなので、どちらも訳の対象ではない（3.2）。

### 3.2 訳さないもの

- 型の綴り、名前、ハットの付いた語、コード片
- パス、トークンの綴り、数
- 章番号（`02 §14.15` など）
- 作者が書いた文 — 説明文（01 §6.4）、注釈の文字列引数（02 §18）。これは §8 の側である
- ［補足］道具が読み取る行とプロトコルの語 — デバッガが待ち受けを知らせる `lhat: dap listening on PORT`
  （エディタ拡張がこの綴りで探す）、DAP の `reason` の値

### 3.3 訳語［補足］

和訳は定訳に従い、和語を自製しない。reflection はリフレクション、
alternative は選択肢、walk は走査、label/tag はラベル・タグとする。

## 4. メッセージの同一性

### 4.1 安定した文字列 ID

> **人に見せる文は、文字列の ID で指す。**

列挙の番号は ID にならない。途中に1つ足せば後ろが全部ずれる。
英語の文をそのまま鍵にする方式（gettext 流）も採らない。文言を磨くたびに
すべての訳が外れる。

利用者に見せる短い番号（`TS2304` のようなもの）は別に持たない。
ID そのものを、検索と文書の鍵にする。

### 4.2 綴り

`出どころ.名前` とする。小文字の ASCII、語の区切りは `-`。

```text
check.lent-does-not-provide
parse.expected-found
run.not-a-subroutine
cli.no-type-errors
```

出どころは 3.1 の表のとおり、`check` `parse` `lex` `compile` `run` `program` `source` `report` `trace` `cli` `dap` である。
カタログの中ではこの出どころを書かない。ファイル名が与える（6.1）。

名前を伴っても伴わなくても報告されるコードは、名前を伴うときの文に別の ID を持つ。
元の ID に `.named` を足す（`check.no-member.named`）。名前を伴ってしか報告されないコードは、
その1つの文に穴を持ち、別の ID を持たない。

一度出した ID の意味は変えない。使わなくなった ID は再利用しない。

### 4.3 列挙は内部に残る

処理系の内部は今までどおり列挙で持ち、出どころごとに1つの表で ID へ対応させる。
公開 API に出るのは ID であって番号ではない。

［補足］現在、診断の番号は公開 API を越えていない。ホストは文面を受け取っている。
したがって ID を導入しても既存のホストは壊れない。

## 5. 文の組み立て

### 5.1 名前付きの穴

> **文は連結で作らない。引数は名前付きの穴に入れる。**

```text
check.no-member.named = this value has no such member: {member}
```

```text
check.no-member.named = この値にメンバ {member} は無い
```

英語で主題を末尾に置く文も、主題を足して作らず、末尾に穴を置く。
訳は穴を文の中ほどへ動かせる。

穴を埋める関数 `lhat_message_render` と引数の形 `LhatMessageArg` は公開する（`include/lhat/error.h`）。
内部の見出しを読まない道具（デバッガ）やホストも、自分の文を同じ規則で描ける。

### 5.2 穴の種類

| 種類 | 入るもの | 扱い |
| --- | --- | --- |
| `verbatim` | 名前、型の綴り、トークン、パス、数 | そのまま出す。訳さない |
| `phrase` | トークンの種類など、別の ID | その ID を同じ言語で引いて入れる |

> **種類はカタログに書かない。** 穴は名前だけで書き、種類は処理系が引数を渡すときに決まる。

```text
parse.expected-found = a '{expected}' was expected here, and this is {found}
parse.token.word = a word of the language
```

```text
parse.expected-found = ここには '{expected}' が要るが、あるのは{found}
parse.token.word = 言語の語
```

構文解析器はこの診断に、`expected` を verbatim の `}` として、`found` を phrase の
`parse.token.word` として渡す。描くときは、verbatim はそのまま入れ、phrase はその ID を
同じ言語のカタログで引いてから入れる。日本語では「ここには '}' が要るが、あるのは言語の語」になる。

種類を書かない理由は3つある。

- **訳す人に選ぶ余地が無い。** 名前やトークンは訳してはならず、句の ID はコードが選ぶ。
  ICU MessageFormat が `{count, number}` のように書式を文に書くのは、訳す人が書式を選べるからである
- **書けば食い違える。** 訳す人が種類を書き違えれば、句が引かれずに ID のまま出る
- **検査が単純なまま保てる。** 読み込み時に比べるのは穴の名前の集合だけで済む（6.4）

［補足］句の項目も verbatim の穴を持てるが、phrase の穴は持たない。句の中に句は入れない。
演算子の句 `parse.token.operator = '{operator}'` は、演算子を囲む引用符を訳に委ねるためにこの形をとる。

**句はその言語で1つの形だけを持つ。** 格で語形が変わる言語では、同じ句が
差し込む文によって別の形を要ることがある。これは 5.3 の複数形と同じ種類の問題なので、
同じく仕組みは持たない。句を差し込む位置を、その言語で形の変わらない位置に揃える文言で避ける。

### 5.3 複数形の仕組みは持たない

> **数に応じて語形を変える仕組みは持たない。数を含む文は、単複が問題にならない文言で書く。**

単数と複数だけに応じても、文法上の性や格で語形が変わる言語には応じられない。
一部の言語の一部の現象だけを扱う仕組みは中途半端になる。
多くのコンパイラも仕組みを持たず、文言で避けている。

```text
cli.no-type-errors = {path}: no type errors (units checked: {count})
```

```text
cli.no-type-errors = {path}: 型の誤りなし（検査した単位: {count}）
```

## 6. カタログ

### 6.1 書式は単純形式である

カタログは **出どころごとに1つのファイル** であり、`名前 = 文` を並べる単純な形式とし、
**注釈の行を持つ**。注釈は、訳していない英語の項目を参考として残すために使う（6.3）。

> **ファイル名が出どころを与える。ファイルの中では出どころを書かない。**

`ja/lex.txt` には `lex` の項目しか入らない。ID が `lex.string-unterminated` なら、
ファイルには `string-unterminated = …` と書く。ファイル名と中身が食い違いようがなく、
同じ出どころの訳は、どのビルドから書き出しても1つのファイルに集まる。

行の種類は、その行の1文字目で決まる。

- **`#`** — 注釈。読み飛ばす
- **空白またはタブ** — 直前の項目の続き。間の改行は文に残る
- **それ以外** — 新しい項目。`名前 = 文` と書く。名前は ID から出どころと `.` を除いたものである（4.2）

```text
# ja/check.txt
no-member.named = この値にメンバ {member} は無い
```

```text
# ja/cli.txt
usage = 使い方: lhat [オプション] <ファイル> [引数...]
    --run     プログラム全体を検査して走らせる
    --check   型を検査して報告する。走らせない
```

`usage` の文は3行になる。続きの行に共通する字下げは取り除く。

- 改行はこの形でだけ書く。エスケープで書く改行は持たない
- 注釈は1文字目が `#` の行だけである。字下げした行の `#` は文の一部になる
- 項目の最初の行の文は行末まで続き、`#` を含んでよい
- エスケープは `\\`（`\` そのもの）と、`\{` `\}`（波括弧そのもの）の3つだけである

注釈にした項目は、各行の頭の `# ` を消せば有効な項目に戻る。

読み手の決めごとは次のとおり。

- 文字符号化は UTF-8。先頭の BOM は捨てる（01 §1 のソース読み込みと同じ）
- 改行は CRLF と単独の CR を LF に直してから読む。引用符で囲む書き方が無く、
  文の中の改行は続きの行でしか書けないので、改行の揺れは文そのものを変えてしまう
- `=` の前後の空白と、行末の空白は除く
- 続きの行の目印は、行頭の空白またはタブである
- 空行は読み飛ばす。ただし後に同じ項目の続きの行があるなら、その空行は文の中の空行として残る
- 文が空の項目（`name =`）は採らない。訳し忘れの行が英語を消さないためである
- 名前が 4.2 の綴りでない行は採らない
- 言語は BCP 47 の言語タグで表し、ディレクトリ名にする（`ja/lex.txt`）。大小は区別しない
- ファイルの拡張子は `.txt` とする。特別な拡張子を持たせない方が、どのテキストエディタでもそのまま開ける
- 知らない出どころの名前のファイルは読み飛ばす

採らなかった行は、どれも `lhat --check-messages` が報告する（6.4）。

### 6.2 英語は処理系に焼き込み、ほかの言語は実行時に読む

> **英語の文は処理系の中に持つ。ほかの言語のカタログは、実行時にホストが渡す。**

- 英語は常に中にあるので、カタログが無くても必ず文が出る
- 訳の追加・修正に処理系のビルドは要らない
- 処理系はファイルの場所を決めない。ホストがバイト列を渡す（7.1）。
  ファイルシステムの無いホストや、Godot の `res://`、lhatove の仮想ファイルシステムからでも同じに渡せる

［提案］英語は C の表として持ち、ID の順に並べて二分探索で引く。
英語の原本を別ファイルに置いてビルド時に変換することはしない。
焼き込むのは英語だけなので変換器が要らず、書き出し（6.3）が原本の役を果たす。

［補足］前段を持たない実行時専用のビルド（05 §10.7）には、`compile` `run` `program` `source` `report` `trace` の英語が入り、
`check` `parse` `lex` は入らない。
カタログの読み手は前段に属さないので、そこでもほかの言語を読める。

### 6.3 英語を書き出す

> **処理系に入っている英語は、カタログの書式で書き出せる。**

訳はこれをもとに作る。書き出しは出どころごとに1つのファイルで、
**すべての項目を注釈にした形** とする。

```text
# check -- L^ 0.3.3, every entry commented out.
# To translate an entry, write it again below with the same name and the new text.

# no-member.named = this value has no such member: {member}
```

複数行の項目は、各行の頭に `# ` が付く。

訳す人は、訳した項目にだけ有効な項目を足す。英語の行は参考として注釈のまま残す。

```text
# no-member.named = this value has no such member: {member}
no-member.named = この値にメンバ {member} は無い
```

注釈のまま残った項目は、読み込むと英語で出る。訳の途中のカタログをそのまま使える。

注釈を外すときに `#` だけを消して空白を残すと、名前の行が字下げされた続きの行として読まれ、
前の項目の文に繋がってしまう。6.4 の検査がこれを報告する。

先頭の注釈には出どころと処理系の版を入れる。どの版の英語から訳したかが残り、
新しい版の書き出しと見比べれば、足された項目と変わった項目が分かる。

> **書き出すのは、その表を持っている側である。** ライブラリは自分の出どころを書き、
> 道具は自分の分を足す。リンクされている物だけが出るので、書き出したカタログが嘘をつかない。

書式は1か所にしか持たない。ライブラリが書式化の関数を公開し、道具は自分の表を渡す。
渡すのは ID と英語の文の組（`LhatMessageEntry`）の並びである。関数が ID から出どころを外して
書くので、ファイル名と中身の対応はそこで守られる。

以下の入口は［提案］である。

```c
const char *lhat_messages_source(size_t index);
size_t lhat_messages_write_english(const char *source, char *out,
                                   size_t capacity);
size_t lhat_messages_write_catalog(const char *source,
                                   const LhatMessageEntry *entries,
                                   size_t count, char *out, size_t capacity);
```

- CLI — `lhat --dump-messages DIR`。`DIR/<出どころ>.txt` を出どころの数だけ書く
- `lhat_messages_source` は、このビルドが持つ出どころを順に答える。
  前段を持たないビルドでは `check` `parse` `lex` が並ばない（6.2）
- `lhat_messages_write_english` は、ライブラリが持つ出どころ1つ分を書く
- `lhat_messages_write_catalog` は、道具が自分の表を同じ書式で書くためのものである。
  CLI は `cli` を、デバッガは `dap` を、ホストは自分の分をこれで書く
- どれも `lhat_report_write` の約束に従い、`(NULL, 0)` で必要な長さを答える

### 6.4 読み込み時の扱い［提案］

読み込みは出どころ1つ分ずつである。どの出どころかは呼び手が言う（7.1）。
ホストはファイル名から取ればよく、ファイルシステムを持たないホストでも渡せる。

- 知らない名前は無視する。別の版の処理系に向けたカタログでも読める
- 穴の名前の集合が英語と一致しない項目は無視する。その項目は英語で出る
- 同じ名前の項目が2つあれば、後の項目を採る
- 注釈の後に来た続きの行は、どの項目の続きでもない。無視する
- 読み込みは失敗しない。採った項目の数を答える。
  出どころを取り違えて渡せば、ひとつも採れずに 0 が返る
- 採らなかった項目とその理由は、`lhat --check-messages FILE` が報告する。訳す人のための入口である
- `lhat --check-messages` は、`名前 = 文` の形をした続きの行も警告する。
  注釈を外すときに空白を残した疑いがあるためである

### 6.5 ビルド時の検査［提案］

次のいずれかでビルド（またはテスト）を失敗させる。

- 内部の列挙に、ID と英語の文を持たないものがある
- リポジトリに置く訳のカタログ（`messages/ja/check.txt` など）に、英語に無い名前がある
- そのカタログの項目の穴の名前の集合が、英語と一致しない

後の2つは、英語の書き出しと突き合わせるテストで確かめる。

**訳が欠けていることは失敗にしない。** その項目は英語で出る。
一部だけ訳したカタログを出荷できるようにするためである。

## 7. 言語の選択と受け渡し

### 7.1 program ごとに持つ［提案］

```c
size_t lhat_program_load_language(LhatProgram *program, const char *tag,
                                  const char *source, const char *text,
                                  size_t length);
bool lhat_program_set_language(LhatProgram *program, const char *tag);
```

- `lhat_program_load_language` は、言語タグ `tag` の、出どころ `source` のカタログを
  program に持たせ、採った項目の数を答える。同じ組をもう一度読めば置き換える。
  ほかの出どころには触らない
- `lhat_program_set_language` の既定は `en`
- 言語タグは近いものへ寄せる。`ja-JP` のカタログが無ければ `ja`、それも無ければ英語
- 読み込みは program への書き込みなので、05 §8.11 の鍵の中で行う

### 7.2 機械［提案］

実行時の状態とトレースバックは、機械を作った program の言語で出す。
program を介さずに作った機械は英語で出す。

### 7.3 構造での受け渡し［提案］

文を描く前の形をホストへ渡す。ホストが自分で描いてもよい。

```c
const char *lhat_unit_diagnostic_id(const LhatUnit *unit, size_t index);
size_t lhat_unit_diagnostic_argument_count(const LhatUnit *unit, size_t index);
bool lhat_unit_diagnostic_argument(const LhatUnit *unit, size_t index,
                                   size_t which, const char **name,
                                   const char **value);
```

既存の `lhat_unit_diagnostic_message` は、program の言語で描いた文を答える。
言語が英語のとき、答える文は今と同じである。

### 7.4 各道具

> **CLI は既定で OS のロケールに従う。一致するカタログが無ければ英語で出す。**

言語タグの寄せ方は 7.1 による。

［補足］OS のロケールを読むのは CLI であり、読んだ言語タグを program に渡すだけである。
処理系は大域の設定を持たないので、2.3 に反しない。

- **CLI の明示** — `--language` で言語を明示すれば、OS のロケールより優先する。
  カタログは `--messages DIR` か、実行ファイルの隣の `messages/<言語タグ>/` から読む。
  そのディレクトリの `<出どころ>.txt` を順に読む
- **CLI が読む OS のロケール** — POSIX では `LC_ALL`、`LC_MESSAGES`、`LANG` の順に、
  最初に値のあるものを採る。`ja_JP.UTF-8` のような値は `ja-JP` に直す
  （`_` を `-` にし、`.` 以降と `@` 以降を除く）。`C` と `POSIX` は英語とする。
  Windows ではユーザーの表示言語（`GetUserPreferredUILanguages` の先頭）を採る
- **言語サーバ** — `initialize` の `locale` を program の言語にする（現状は読んでいない）。
  カタログの場所は言語サーバの設定で与える。診断の `code` に ID を入れる（現状は空）
- **デバッガ** — DAP の `initialize` の `locale` を使う
- **Godot バインディング** — エディタの言語と、バインディングが持つカタログを、
  ホストが `lhat_program_load_language` と `lhat_program_set_language` へ渡す

## 8. ［未決 I2］L^ プログラム自身の多言語化

処理系はプログラムの文を訳さない（2.1）。そのうえで、作者が自分の文を
多言語化するのを言語の側がどこまで支えるかは決めていない。

対象になりうるものは3つある。

- **説明文** — 定義に結び付いたコメント（01 §6.4）。言語サーバのホバーが出す（07 §4）
- **注釈の文字列引数** — ホストが宣言した注釈に作者が書く文（02 §18）
- **プログラムが表示する文言** — ゲームの画面の文字列など

Memo.md には、多言語化のための情報をソースから分離して持つメタデータ
`*.lhm` の構想がある。コメントに埋め込むこともでき、必須ではない。
説明文と注釈の訳はこれに載せられる。

プログラムが表示する文言は、道具ではなくライブラリの話になる。
LTON（08）のカタログを読む標準ライブラリにするか、Godot の TranslationServer の
ようなホストの仕組みに委ねるかも含めて決める。

決めることは次のとおり。

- `*.lhm` の書式と、訳を定義へ結び付ける鍵
- コメントの中に言語ごとの区画を書く綴りを持つか
- 説明文の書き分け記法（未決 L5、07）との関係
- 文言のカタログを標準ライブラリに持つか

## 9. 導入の段階

1. **番号の付いた表に ID を付ける** — 検査器・構文解析・字句解析・実行時の状態・program・コンパイルの状態の表。
   英語の出力は今と一字一句同じにする。変更の前後で全文を書き出して突き合わせ、
   退行が無いことを確かめる
2. **英語をテンプレートにする** — 引数を名前付きの穴にし（5.1、5.2）、穴の名前は文ごとに決める。
   名前を末尾に足す組み立て、構文解析の句、トレースバックの行、報告の見出し、
   読み込みの失敗を言う文もここで穴を持つ文にして ID を付ける。
   CLI とデバッガの人向けの文も洗い出し、同じくテンプレートにする。
   英語の文面が変わるのは、複数形を作っていた文を 5.3 のとおり直す所だけである
3. **英語の書き出し**（6.3）
4. **カタログの読み込みと言語の選択**（6.4、7.1）、最初の日本語カタログ
5. **言語サーバ・デバッガの `locale` と、診断の `code`**

1 と 2 は訳を1つも足さなくても価値がある。安定した ID が手に入り、
言語サーバが診断に `code` を付けられる。

句やトレースバックの断片に段階1で ID を付けないのは、段階2で1つの文に作り直すときに
捨てることになる ID を出さないためである（4.2）。

§8 は別に決める。
