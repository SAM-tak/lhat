# 特殊化と JIT — 確定した型で実行時の検査を消し静的にディスパッチする

**現状**: 多重定義の静的解決（2）、メンバ読みの記憶（3）、数の命令の特殊化（4）、
命令から命令への直接の跳び（5）、PGO（6）が入っている。JIT（7）は試作で、
既定では組み込まない。残りの特殊化命令は 8 に並べる。

この文書は、03（処理の構成）が定める命令の**意味**を変えずに、同じ答えを
速く出す工夫を扱う。命令が何を答えるかは 03 が正本であり、ここに書くものは
どれも、外せば 03 の汎用の道に戻るだけである。

## 1. 方針

03 の 5.1 は、型が確定した箇所向けの特殊化命令を最初から作らず、
まず全命令が実行時に型を確認する形で作ると決めている。特殊化は後から足す。
CPython 3.11 以降が採った順路であり、先に汎用命令の意味を固めてから、
確定した情報で特殊化命令に差し替える。

特殊化が消すものは2つある。

- **実行時の型の検査。** 値のタグを確かめる判定を、確定した箇所から省く
- **動的なディスパッチ。** 呼び先や答えの在りかを実行時に探さず、確定した
  ものへ直接向かう。多重定義の探索を消す（2）のも、メンバを探し直さない（3）
  のもこちらである

特殊化の材料は2種類ある。

- **検査器が確定させた型。** 引数の型が確定した多重定義の呼び出しは、
  どの選択肢かを焼く（2）。検査器は厳格度によらず意味解析を完全に行う
  （03 の 4.2）ので、確定した箇所なら relaxed でも効く
- **実行時に見えるもの。** 型検査が答えを持たなくても、値のタグや表の版番号は
  命令の中で安く確かめられる。メンバ読みの記憶（3）と数の命令（4）はこちらで、
  検査器を使わない

どちらの場合も、前提が外れたら汎用の道へ戻る（2 だけは例外で、検査器の答えを
確かめ直さない。その理由は 2 に書く）。安全性は 03 の 5.1 のとおり strict の
静的検査が担い、特殊化はそれを狭めも広げもしない。

測るときは 6 の PGO を通す。巨大な実行ループでは、命令の中身と同じくらい
「どこに書くか」がバイナリの配置を通じて速さを動かす。

## 2. 型の確定した呼び出しは選択肢を焼く［実装済み］

> **全引数の型が確定した多重定義の呼び出しは、どの候補を意味するかを
> コンパイル時に決め、バイトコードに焼く。実行時の探索は走らない。**

1 で述べた特殊化の最初の1つで、**タグ検査を丸ごと省く**形になっている
——探索の中身が引数ごとの `lhat_value_satisfies` である以上、
探索を消せば判定も消える。

### 経路は 03 の 5.11a と同じ形

`checked_arm`（`uint16_t`、選択肢の位置＋1。0 が「何も決まっていない」）を
節点に置く。

- **`LHAT_NODE_CALL`** — `infer_call` が当てた選択肢。**全引数の型が確定した
  ときだけ書く**（`any^`・未確定・型の穴を含めば書かない）。厳格度は見ない
- **`LHAT_NODE_TABLE_ENTRY`（`override^`）** — `override_one` が置き換えた選択肢。
  **常に書く**（すぐ下の理由による）

コンパイラは前者を `PICKARM A Bx`（群 R[A] の Bx 番で R[A] を置き換える）に
落とし、`CALL` の直前に置く。`CALL` は無改造でよい——
R[A] は既に素のサブルーチンなので、実行時解決の探索分岐を素通りする。
群でない値が来たら `PICKARM` は何もしない。書かれていなければ探索する。

### 選択肢の番号は両側で同じものを指す

検査器の選択肢の並びと実行時の群の並びは一致していなければならない。
`overload^` は両側とも末尾に足すので一致する。
`override^` は **実行時もその場差し替え** とする（`OVERRIDEARM`。
`lhat_overload_replacing`）——置き換えられた選択肢は残さず落とす。
**02 の 14.12改 の `super^` は書き込み前の `GETINDEX` で旧グループを捕捉している**ので、
新グループに残す必要が元から無い。

どの選択肢かは検査器が知っているので、`override^` のエントリに書いて渡す。
**これは特殊化ではなく群の形の正規化**であり、引数の型が確定したかどうかで
変えてはならない（群の選択肢は 02 の 14.16 の `typeof^` からも読まれる）。だから
呼び出し側注釈と違い、条件を付けずに書く。落とすほうが型に忠実でもある——
検査器の型は置き換えられた選択肢を持っていない。

`OVERRIDEARM` は `A B C` を選択肢の番号に使い切るので、値は `R[B+1]` から読む。
`compile_def` が鍵と値を隣り合う枠に置くのは 03 の 5.3 が呼び出しを置くのと同じ形。
隣り合っていなければ `OVERRIDEINDEX` に落ちる。

### 02 の 14.12 の非重複は選択肢ごとに問う

**新しい選択肢は、既にある選択肢のそれぞれと分離していなければならない**。
`overload^` も `override^` も、比較は選択肢1つずつ行う。
選択肢の集合（交差型）ごと `signatures_overlap` に渡すと、
署名でないものは「区別できない」＝重なり扱いになり、
明白に分離した選択肢まで拒否される。

### 実行時に確かめ直さない

`PICKARM` は番号で取り出すだけで、引数の型を一切見ない。
外れた場合に探索へ落とす安全網は**置かない**。置けば判定が残り、
特殊化が消そうとしているものがそのまま残る。1 の特殊化は
「型が確定した箇所から検査を省く」ものであり、これはその定義どおりの形である。

代わりに払うのは、**検査器が間違えれば誤った本体が呼ばれる**という賭けである。
静的型付けが元から張っている賭けと同じもので、新しく増える種類ではない。

### 演算子はまだ探索のまま

02 の 11.8 の `op^` も多重定義できるが、`PICKARM` はそこに載らない。
呼び出しと違い、**群がレジスタに載っていない** — 演算子の命令が持つのは
被演算子だけで、メンバの引き当ては `call_operator` が実行時に行う。
選択肢の番号を渡すには命令側に置き場所が要り、`ADD A B C` は既に埋まっている。
載せるなら別の形になるので、残りの特殊化（8）として起票する。

**検査器の側は揃っている。** `infer_operator` は右被演算子で選択肢を選ぶ
（02 の 14.4 が左を `self^` に置くので、選択肢への問いは `x.m(右)` と同じ形になる）。
どの選択肢も取らなければ、単一の選択肢が右被演算子を拒むときと同じ報告をする。
**静的な答えは揃っている。焼く先が無いだけである。**

## 3. メンバ読みは見つけた場所を覚える［実装済み］

> **`x.m` は、前回どこで見つけたかを呼び出し地点が覚える。当たれば
> 比較2回、外れれば今までどおり探して覚え直す。**

1 の2つ目の材料（実行時に見えるもの）を使う。2 と違い**検査器を
使わない**——答えは `GETINDEX` が返すものと同一なので、検査の答えにも
厳格度にも依らず同じだけ効く。

`bench/` が測ったのは「ホスト型のメンバ呼び出しのうち、受け手のメンバ
読みが占める分」で、入れる前は**4割前後**だった。入れると当たった地点で
それが消える。数は走らせた機械のものなので書かない。

### 覚えているのは呼び出し地点［重要］

チャンクには各地点のメンバ名を指す定数番号だけを置き、実行時には変更しない。
可変のキャッシュは**VMごと**に64件持ち、チャンクのアドレスと地点番号から
使用する枠を選ぶ。同じプログラムを複数ワーカーが実行してもキャッシュは共有しない。

枠が衝突しても、受け手・版番号・エントリの鍵を確認するため、誤った値にはならない。
衝突は命中率にだけ影響する。キャッシュは表の寿命を延ばさず、GCは回収対象の表への
参照をスイープ前に無効化する。`GETMEMBER` と `CALLMEMBER` は同じ方式を使う。

### 当たり判定は表の版番号

表は**並びが変わった回数**を持つ（`LhatTable.version`）。上がるのは
鍵が増えたとき・鍵が消えたとき・並べ替え（rehash）・列の側へ移ったとき。
**既にある鍵への上書きでは上がらない**——何も動かないからで、これが
`self^.x := 1` をループで回しても `self^.y` の読みが生き続ける理由である。

### インスタンスを跨いで当たる

`def^` のインスタンスは1つ1つ別のテーブルなので、表そのものを見比べる形
だと**インスタンスごとに外れる**。メンバは共有なのに当たらない、という
おかしなことになる。

見比べるのは表ではなく**「複製以来まだ構造を書かれていない」**という
事実（版番号が 0）である。03 の 5.10 がプロトタイプを封印しているので、
そのままの複製は**必ずプロトタイプと同じ鍵の集合**を持ち、定義側の
メンバを隠していない。だから:

```text
受け手の版が 0        — 自分は何も隠していない
受け手の定義が同じ    — 同じ def^
定義側の版が同じ      — 定義側も並びが変わっていない
```

自分の表へ鍵を足したインスタンスは版が 0 でなくなり、正しく外れる。

### 覚えるのは表の経路だけ

この命令が答えるもののうち、コルーチンの操作・ホスト値のフィールド・
どの値も持つ組込みは**その場で作られる**ものであって、表のどこかに
在るものではない。覚える場所が無いので、そこは今までどおり通る。

### 3.1 メンバ読みは呼び出しと組で走る［実装済み］

`x.m(…)` の `GETMEMBER` と `CALLMETHOD` の対は、引数がすべて何も走らせない
とき隣り合わせに置き、読みを `CALLMEMBER` に置き換える。

- **キャッシュに当たれば**、対の呼び出し命令をその場で読み取って呼び出しへ
  直進する。ディスパッチが1回減る
- **外れれば** `GETMEMBER` と一字一句同じに振る舞い、対の呼び出しは
  自分として走る

2命令はチャンクに残り、消えるのはディスパッチだけなので、符号化に新しい欄は
要らない。引数が何かを走らせる呼び出し、`?(`、`PICKARM` の立つ地点は
従来の並びのままである（読みが引数の後へ動くのは、間に何も走らないときだけ）。

## 4. 数の命令［実装済み］

`number^` は1型2表現（02 の 14.8）なので、整数か実数かは値のタグにしか無い。
この節の特殊化はどれも検査器の型ではなく、命令の中でタグを見て選ぶ。
前提が外れれば、汎用の `arithmetic()`／`ordering()` と演算子（02 の 11.3）へ
渡す。

### 4.1 オペランドはその場で読み、定数は命令に畳む

二項演算は、裸のローカルをオペランドとしてその場で読む。`MOVE` で一時領域へ
控えない。左辺をその場で読むのは、右辺が何も走らせないときだけである
——右辺の呼び出しが捕捉越しに左辺を書き換えうるからである。
検査器が両辺 `number^` と確かめた二項演算は印（`checked_numeric`）を持ち、
コンパイラはそれを「ローカルを書かない式」に数える。数同士なら演算子の本体が
走らないので、`s + i * 3` の `s` も控えずに読める。`..`・`cross`・`dot` は
数同士でも演算子へ行くので印を付けない。印は周回ごとに書き直し、形ごとの本体は
自前の木を持つ（03 の 3.4改4）ので、別の形の答えは混ざらない。

右が数値リテラルの演算は定数を命令に畳む。

- 算術: `ADDK`・`SUBK`・`MULK`・`DIVK`
- 比較: `LTK`〜`GEK`

演算子へ逃げるとき（02 の 11.3）は、機械が定数を `call_operator` まで運ぶ。
定数を取る型の `op^<=>` にもそのまま渡る。

`return^` と名前の読みも、裸の名前ならその場で読む。

### 4.2 同じ表現の数の組は命令の中で答える

`ADD`〜`MUL`・`ADDK`〜`MULK`・`LT`〜`GE`・`FORLOOP(D)` は、汎用の道へ渡す前に
タグ2つを見て、整数同士（算術は実数同士も）ならその場で答える。命令ごとに
ラベルを分け、演算子で `switch` しない。strict の型からは選べない——
表現は値のタグにしか無いからである。

整数同士の順序づけは整数で行う。double で比べると、2^53 を超える隣り合う
整数を等しいとしてしまう。

### 4.3 比較は自分を読む跳びを食う

`LT`〜`GE` と `=`・`≠` の組み込みの道は、答えを置いたあと次の命令を覗き、
それが自分の答えを読む `JUMP_FALSE` ならその場で消化する。対はチャンクに残り、
命令もオペコードも増えない。演算子へ逃げる道は覗かず、跳びは自分として走る。

### 4.4 数えるループの一周は1命令

02 の 16.4 の `to^`／`downto^` と `repeat^ n` は、焦点・境界・`step^` を
3連のレジスタに敷く。入口の `FORPREP` が3つが数であることを1回だけ問い、
周回は `FORLOOP`（`downto^` は `FORLOOPD`）が進めて試して跳ぶ。Lua の
`OP_FORLOOP` と同じ置き方である。形が合わないとき（既存の名前の焦点、`pre^`）は
比較・跳び・加算・後方跳びの綴り出しに戻り、答えは同じである。`repeat^ n` は
1起点・以下比較に組み替えて同じ命令対に乗る。

整数の `for^` の前進が溢れたら、そこでループを終える。全部が整数なら、溢れは
上限の先だからである。実数に広げると、上限と許容差の内で等しくなって
抜けられなくなる。

## 5. 命令から命令へ［実装済み］

ディスパッチの綴りは二つあり、どちらになるかはコンパイラが決める。

- **computed goto** — GCC と Clang はラベルのアドレスを取れる（`&&label` と
  `goto *`）。命令それぞれが自分の間接分岐で次へ跳ぶので、分岐予測器は
  「この命令の次はこれ」を命令ごとに憶えられる
- **`switch`** — MSVC にこの拡張は無い。間接分岐は一つに集約され、
  予測はプログラム全体で一つの履歴を共有する

同じ本体を両方の綴りで読ませる。`LHAT_VM_CGOTO` が判定し、ビルドから
`-DLHAT_VM_CGOTO=0/1` で上書きできる——二つを並べて測るのに要る。
判定は `__GNUC__` と `__clang__` の両方を見る。clang-cl は前者を定義しないので、
Lua の綴り（`LUA_USE_JUMPTABLE`）をそのまま写すと MSVC ABI 版の Clang が
`switch` 側へ落ちる。Luau は両方を見ており、そちらが正しい。

**取り分は 6 の PGO を通してからでないと読めない。** 配置くじはこの差より大きく、
符号ごと動かす。

**遅い道は一語に畳む。** 命令の合間に見るもの——collector が留めたコルーチン
（02 の 10.7）、drain、デバッガのフック——には機械の `traps` 一つが答える。
`switch` ならループの頭で一度払えば済むが、computed goto は命令ごとに払うので、
載せた数がそのまま費用になる。`traps` は両方の欄から毎回導出し、増減では持たない。
欄へ書くのは `machine.h` の二つの setter だけである。

**表に無い符号は型エラー。** `op` は1バイトで、命令は 79 しかない。表は 79 要素
だから範囲の検査を一つ置き、外れたら `switch` の `default` と同じ答えへ跳ばす。
`switch` は取りこぼしを黙って読み飛ばしていたので、これは二つの綴りの意味を
揃えたことでもある。

## 6. PGO — 配置くじの根治

`scripts/pgo.ps1` が計装→訓練（`bench/` の全ケースと `bench/train/` の
負荷、`sample/` の検査と実行）→プロファイル適用の再リンクまでを一括で行い、
`build/pgo/lhat.exe` が最適化済みバイナリになる。CMake 側は三値
`LHAT_PGO`（OFF/GENERATE/USE）で、GCC/Clang でも同じ器が使える。
絶対値は 8 の方針どおりここに書かない — 走らせた機械の `pgo.ps1` が
仕上げに bench を1周して数字を出す。

## 7. JIT（copy-and-patch）［試作］

> **命令ごとの処理を C で書いた「型紙」を、あらかじめ機械語にしておく。
> チャンクの機械語は、命令の型紙を並べて写し、オペランドや飛び先の
> 「穴」を埋めるだけで出来る。値はすべてインタプリタと同じスロットに置き、
> どの命令でもインタプリタへ戻れる。**

`LHAT_JIT`（既定 OFF）で組み込む。いまは x86-64 Windows（clang-cl）だけを持つ。

### 構成

- **型紙は C、抽出は Python。** `jit/stencils.c` を Clang でオブジェクトに落とし、
  `jit/gen_stencils.py` が型紙ごとの機械語と穴の位置を取り出して
  `jit/stencils_<target>.h` に書く。**生成物はリポジトリに置く**。Python が要るのは
  型紙を変える者だけで、lhat やバインディングを組む者にも、実行時にも要らない
- **外部のコード生成器は使わない。** Cranelift のような生成器は、JIT を入れた
  lhat を組む全員に別言語のツールチェーンを課す
- **呼び出しは JIT コードの中で扱う。** 呼び出しのたびにインタプリタへ出る形では、
  呼び出しを含むループがいつまでも速くならない

### 値はスロットに置く［補足］

型紙は命令をまたいで値をマシンレジスタに持ち越さない。値はインタプリタと同じ
スロット（03 の 2.2）にあるので、**型紙はどの命令でも、何も書かないうちに自分の pc を
答えて出られる**。インタプリタはその命令から続ける。前提の外れ（整数の溢れ、
演算子を持つ値、キャッシュの外れ）も、型紙の無い命令も、すべてこの出口になる。
出口が既存の命令処理そのものなので、意味の正本は常にインタプリタにある。

スライスによる中断、コルーチン、GC の根、トレースバックが JIT の有無で変わらないのも
同じ理由による。

### 型紙の契約［補足］

- **型紙が読むのは `jit/jit.h` と公開ヘッダの値・オブジェクトの配置だけ**
  （`lhat/value.h`・`lhat/object.h`）。機械（`machine.h`）は読まない。
  機械の配置を変えても生成物は古くならない
- **型紙はプラットフォームの通常の呼び出し規約で書く。** どの型紙も退避の要る
  レジスタを使わないので、JIT コードへの入口は普通の関数呼び出しで済み、
  MSVC で組んだホストからも呼べる
- **穴は命令の中の 32 ビットの欄**。型紙は ELF 向けに、位置独立でない小さい
  コードモデルでコンパイルする——そうするとレジスタの位置は読み書きの変位に、
  定数は即値に、次の型紙への継続は `jmp rel32` に畳み込まれる。関数は Windows の
  呼び出し規約を明示する。二つの対象で配置が同じであることは、生成物が持つ
  オフセットの静的検査が保証する。ヘルパのアドレスだけは届く距離が分からないので
  64 ビットの即値で持つ。次の型紙が隣に置かれるときは、末尾の継続を削って
  素通りにする。穴でないものへの参照（定数プール、ヘルパの直呼び）は生成時に拒む
- **生成物の鮮度は入力のハッシュで見る。** 生成物は入力（型紙のソースと、それが
  読む配置）のハッシュを持ち、`gen_stencils.py --check` はそれだけを比べる。
  機械語のバイト列は Clang の版で変わるので、再生成して比べる方式は取らない

### インタプリタとの出入り［補足］

- **入る地点:** 後方分岐でスライスを点検した直後、本体の入口、呼び出しから
  戻った地点。入れるかどうかは、チャンクの JIT コードの先頭にある入口表を
  インタプリタがその場で引いて決める。入れない地点では何も呼ばない
- **点検:** 後方分岐と本体の入口で、スライスの残りと `traps` を見る。
  スライスが尽きる手前やフックが待っているときは、インタプリタへ出て任せる
- **フレームが動いたとき:** JIT コードの中で呼び出しや戻りをしたら、その旨を返す。
  インタプリタはそのときだけフレームを読み直す
- 環境変数 `LHAT_JIT=0` で、同じバイナリのまま JIT を切れる

### 呼び出し［補足］

CALL・CALLMETHOD・CALLMEMBER（メンバのキャッシュに当たったとき）・TAILCALL・
TAILCALLMETHOD と RETURN は、C のヘルパがフレームを積み下ろしする。
型紙はその後、呼び先か呼び出し元の JIT コードへ末尾呼び出しで跳ぶ。
**C のスタックは積まない**——積めばコルーチンの中断もスライスも成り立たない。

- **速い道:** 呼び先が L^ の本体で、置かれた引数をちょうど受け取り、展開も
  可変長の残りも無く、コルーチンでもない呼び出し。片付け・コルーチン・
  演算子の答え（02 の 11.9）・タプル・ホスト値のどれも絡まない戻り。それ以外は出る
- **地点ごとの記憶:** 呼び出し地点は、前回速い道で呼んだ本体を覚えていて、
  同じ本体なら検査を省く。戻った後に続ける機械語の位置はチャンクを配置するときに
  決め、呼び先のフレームに持たせる（`Frame.jit_return`）
- **末尾呼び出し:** フレームを使い回せる条件と手順はインタプリタ（03 の 5.3）と同じ

### ステップ［補足］

型紙だけで書けない命令は、C の関数1つに任せる。済めば続き、済まなければ
何も書かずに出る。メンバ読み（キャッシュに当たったとき）、表への書き込み、
upvalue を閉じる処理、確保を伴う命令（クロージャ・表・インスタンス・
文字列の連結）がこれにあたる。確保する命令は、インタプリタの `LHAT_GC_POLL`
と同じ位置で GC を点検する。クロージャとインスタンスの組み立ては
インタプリタと関数を共有する（`vm_make_closure`・`vm_make_instance`）。

### 数値の表現の推定［構想］

> **`number^` の値に、静的に「実数（確定）」「整数（見込み）」「不明」の
> 3つの属性を追跡する。利用者に見える型は `number^` のままで、属性を読むのは
> コンパイラと JIT だけである。**

`number^` を整数と実数の型に分けない（02 の 14.8）のは、`1 / 3` が 0 にならず、
`i := 1 / 3` が型の違いで拒まれず、`.round()` や `0.0` を書かされない言語で
あるためである。その代わり、整数か実数かは値のタグにしか無く、JIT を含む
最適化はそれを実行時に確かめている。属性は、確かめる前に答えの見込みを与える。

- 型ではなく式に付く印として持つ。型検査の答え——適合、多重定義の選択、
  ホバー、診断——は属性によって変わらない
- 変数は流れに沿って追う。周回するループでは、合流で混ざったら「不明」に落ちる
- 使い道は JIT を含む後の最適化。「不明」は実行時の記録による推測に任せる

伝播の規則［補足］:

- **実数（確定）:** 実数リテラル、片側が実数の算術（02 の 14.8）、`/`（04 の 11.2）
- **整数（見込み）:** 整数リテラル、整数同士の `+ - *`、`//`・`%`、
  `round()`・`floor()`・`ceil()` の答え。どれも溢れや 0 での割り算、
  int64 に収まらない値で実数に広がりうるので、確定とは言えない。
  見込みを使うコードは、外れたらインタプリタへ出る（7 の出口）
- **整数（確定）の例外:** 整数リテラルと、整数で始まり整数の歩幅で進む for^ の
  カウンタ（本体の中）。後者は溢れた時点でループが終わる（4.4）ので、
  本体の中で整数でなくなることがない

## 8. 未決事項と材料

- 特殊化命令の設計。多重定義の静的解決（2）は済んでおり、
  残り（算術・索引などのタグ検査を省いた命令、演算子の選択肢の焼き込み）は手つかず

  **メンバ読みは 3 で入った**（`LHAT_BC_GETMEMBER`）。
  その取り分を測る道具が `bench/` にある。`-DLHAT_BUILD_BENCH=ON` で
  `lhat_bench` が建ち、同じループの本体だけを差し替えた数件を走らせて
  差を取る——受け手のメンバ読みは「ホスト型のメンバ呼び出し」から
  「局所に束ねた同じ C 関数の呼び出し」を引いた分である。
  **数は走らせた機械のものなので、ここには書かない。**

  測って分かった向きだけ記す。**ホスト境界は高い段ではない**——
  ホスト関数は枠もバイトコードも持たない C の呼び出しなので、
  L^ の閉包を呼ぶより**安い**。特殊化の取り分はメンバ読みの側にある。
  `def^` のインスタンス（02 の 14.7 が定義側も辿る）でも同程度なので、
  入れるならホスト型限定にする理由は無い

### 8.1 検査器が知っていて報告しないもの［参考］

型検査が確かめた事実のうち、**誤りとして報告しないが捨てるのも惜しいもの**は
この段の材料になる。現時点で分かっているのは次である。

- **左辺の型が答えを決めている `fits^`**（02 の 13.11）。
  右辺と互いに素なら常に偽、左辺全体が適合するなら常に真。
  到達しない側の枝を落とせる
- **絞り込みで選択肢が尽きた枝**（同）

02 の 13.11 がこれらを報告しないと決めているのは、
`fits^` が実行時に問うための記法であり、
**推論の結果を根拠に書き手を縛らない** ためである。
右辺だけで決まる `fits^ any^` はそこに当たらず、誤りとして報告される。

**報告しないことと、知らないことは別である。**
