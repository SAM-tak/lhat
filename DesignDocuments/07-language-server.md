# 言語サーバとエディタ統合

`L^` の言語サーバ `lhatls`（`lsp/`）と、それを利用する VSCode 拡張の設計。
拡張は別リポジトリ [lhat-vscode-extension](https://github.com/SAM-tak/lhat-vscode-extension)
にあり、本文で拡張側のファイルを指すパスはそのリポジトリのルートからの相対。

ビジュアルエディタは同じ拡張の中に載る。その設計は
[拡張リポジトリの 06-visual-editor.md](https://github.com/SAM-tak/lhat-vscode-extension/blob/main/devdocs/06-visual-editor.md)
に分けてある。
本文書はその土台にあたる部分を扱う。

節番号のない参照（`14.17` など）は [02-syntax.md](02-syntax.md) を指す。

## 1. 位置づけ

処理系本体の仕様ではなく、処理系を利用するツールの仕様。言語の意味論には影響しない。

ただし本文書が要求する情報のうち、字句解析器や構文木が持っていないものがある。
それらは本体側の設計文書に未決事項として起票し、そちらで決める。

## 2. 構成

```text
  VSCode
   └ lhat-vscode-extension (拡張、TypeScript、別リポジトリ)
      ├ 言語クライアント (vscode-languageclient) ──► lhatls (子プロセス、stdio)
      ├ 構文強調の文法定義 (syntaxes/lhat.tmLanguage.json)
      ├ ビジュアルエディタ (webview)             ──► lhatls (同じ接続)
      └ デバッグクライアント (DAP)               ──► lhat --dap=PORT (別プロセス、TCP)
```

言語サーバは `L^` の実装（`src/`）をそのまま組み込む。字句解析・構文解析・型検査を
サーバ側で二重に実装しない。ビジュアルエディタも同じ接続を使う（06 の 2 章）。
デバッグは別で、`lhat --dap` が担う（[09-debugger.md](09-debugger.md)）——`lhatls` とは別の
プロセスで、枠（Content-Length）だけを共有する。

## 3. 実装済みの機能

| 機能 | 方法 | 実装 |
| --- | --- | --- |
| 診断 | `textDocument/publishDiagnostics` | `lsp/diagnostics.c`、`lsp/worker.c` |
| 意味的な構文強調 | `textDocument/semanticTokens/full` | `lsp/handlers/semantic_tokens.c` |
| 文書の同期 | `textDocument/didOpen` / `didChange` / `didClose` | `lsp/handlers/text_document_sync.c` |
| ホバー | `textDocument/hover` | 4 章。`lsp/hover.c` |
| 定義へ移動 | `textDocument/definition` | 4 章の `LhatResolution` がそのまま答える。`lsp/definition.c` |
| 文書シンボル | `textDocument/documentSymbol` | 構文木だけから作る。`lsp/document_symbol.c` |
| 参照の検索 | `textDocument/references` | 5 章。解決の記録を定義位置で引く。`lsp/references.c` |
| 名前の変更 | `textDocument/rename`（`prepareRename` 付き） | 同じ答えをファイルごとに束ねる。`lsp/handlers/references.c` |
| 補完 | `textDocument/completion` | 4 章の「点の記録」「言語の語と、スコープにある名前」「まだ取り込んでいない名前」。`lsp/completion.c` |

検査はワーカースレッドで動く。プロジェクト内の `*.lh` はそれぞれが独立した根であり、
1つの編集は「その根」と「最後の検査でその文書を通過した根」だけを検査し直す
（`lsp/workspace.h`）。

新しい要求への対応は `lsp/dispatch_table.c` に1行と `lsp/handlers/*.c` を1つ足すだけでよく、
`dispatch.c` と `server.c` には手を入れない。

**文書シンボル（アウトライン）は検査を待たない。**列挙するのは `let^` / `var^` の束縛、
`def^` のメンバー（`self^{ }` 欄の項目はフィールド、関数値はメソッド）、テーブルリテラルの
名前付き項目、`errordef^` とその種類、`module^`、そして単位が `return^` で答えるテーブルの
項目 — LTON はこの最後の形（08 章）。いずれも名前は構文木に書かれていて、検査器の答えを
要しない。エディタはファイルを開いた瞬間にアウトラインを求めるので、受け口
（`lsp/handlers/document_symbol.c`）はワークスペースの検査済み単位を引かず、
文書ストアが持つその時点のテキストをその場で構文解析して答える。
ループの焦点・引数に渡したコールバックの中身は載せない。アウトラインはファイルの形であって、
名前の全列挙ではない。

## 4. ホバー

名前にホバーすると、**その名前が届いた定義**を示す（`textDocument/hover`、
`lsp/hover.c`）。示すのは次の3つ。

1. **定義の1行目** — その名前を導入した構文を、最初の改行まで。
   本体が何ページあっても1行に収まる
2. **推論された型** — 検査器が落ち着いた型（`lhat_type_write`）
3. **説明文** — その定義に結び付いたコメント（01 の 6.4）。`#` や `#[ ]#` は外す

```text
let^ twice = f^n:number^ -> number^ {
: f^number^ -> number^;

二倍にする
```

1 と 2 は**両方出す**。書かれたものと、そこから導かれたものは別の話であり、
注釈のない定義には 2 しかなく、注釈のある定義は書かれた形も見たい。

型は 13 章の記法で書き出す（`lhat_type_write`、`src/type.c`）。
`number^`、`t^{ sku : string^ }`、`f^number^ -> string^;` のように読める。
表示のための道具であって、往復できる表現ではない。

14 章はテーブルが自分自身を含むことを許すので、**深さと要素数で打ち切る**
（`LHAT_TYPE_WRITE_MAX_DEPTH`、`LHAT_TYPE_WRITE_MAX_ITEMS`）。
打ち切りも、バッファに収まらない場合も、末尾を `…` にする。

### 名前解決は検査器の答えを読む

どの定義に届いたかは、**検査器が解決したときに控えたものを読む**
（`check.h` の `LhatResolution` と `lhat_check_resolution_at`）。
`scope_find` が答えを出すその場所で、使用位置・定義位置・型を記録する。

8 章のスコープ規則をホバー側で解き直す道は採らない。
実装が二つになれば歩調を合わせ続ける必要が生じ、しかも**規則が難しい場所でこそ食い違う**。

記録は使用位置の順に並ぶので、位置からの検索は二分探索で済む。
この表は定義へ移動・参照の検索（5 章）の土台でもある。

### 点の記録 — メンバの補完が読むもの

`.` の後に何が書けるかは、**検査器が控えたレシーバの型**から答える
（`check.h` の `LhatMemberSite`、`lsp/completion.c`）。

構文解析器は末尾の `.` に**中身の無いメンバ**を残す（`parse_postfix`）。
8.2 が文の位置で拒む「裸の式」からもこの形だけは除いてある — 点は既に報せて
あり、節点こそが問いの対象だからである。
検査器はレシーバを推論した直後に、その点の位置と型を控える。

**拒んだ文でも木は捨てない。** 一打鍵後の `r.pe` は 8.2 が拒む — そこは
変えない — が、拒否は診断であって木の始末とは別の話である。`parser.c` の
`refused` は `LHAT_NODE_ERROR` の下に読み終えた走りを残し、検査器はそれを
**静かに歩く**（`chk_check_statement` の ERROR 腕、`c->rereading` を上げる）。
点と解決は控えられ、**診断は1つも増えない** — 誤りは既に一度報せてある。
`LHAT_NODE_ERROR` のままなので、診断で門を張っていないホストに対しても
コンパイル器は今までどおり `LHAT_COMPILE_UNSUPPORTED` で落ちる。

これで効くのは補完だけではない。弾かれた文の中でホバー・定義へ移動・
意味的強調・ビジュアルエディタの木が揃って答えるようになる。
弾かれた文が推論に寄与するようにはなるが、`BARE_EXPRESSION` を持つ単位は
決してコンパイルされない（CLI・LSP・load・reload すべてが診断で門を張る）ので、
動く番組の振る舞いは変わらない。

**サーバ側で式の型を出し直さない。** 解決の記録は名前で引く表なので、
`f().` なら「呼び出しは返り値を答える」を、`a[i].` なら添字の規則を、と
サーバに書き足していくことになる。それは 4 章が hover で既に拒否した
「二つ目の実装」であり、`(a + b).` に至っては直前の名前 `b` の型を引いて
**黙って間違う**。点に控えれば、どの形のレシーバも一つの機構で答える。

列挙の規則は**一つだけ**: その名前で `lhat_type_find_member` を引いて
同じメンバが返るものだけを出す。14.5 の合成で隠れたもの、14.7改2 の委譲が
貸さないもの（受け手を取らないもの）は、それだけで落ちる。**出す候補と
検査器が受ける候補が一致する**ことが、この一行で保証される。

**候補は二つの源から来る。** 型が持つメンバー一覧と、**検査器への問い合わせ**。
14.19 や 15.6改 の組み込みメンバー（`"text".length`、`t.push^`、コルーチンの `resume`）は
どの一覧にも載っていない —— 検査器が答えるものだからである。だから訊く:
`chk_infer_member` の連鎖を `chk_member_of` に切り出し、診断の立つ場所を NULL にすると
何も報せず何も控えずに答えだけ返る。補完は「試す綴り」の平坦な一覧を投げ、
`W` と `W^` の両方を訊いて答えた方を出す。

**適用条件はサーバ側に1行も無い。** どの受け手が裸の綴りを許すか（`plain_table_type`）、
どれがハット限定か、書かれたメンバーが先勝ちするか —— そこがこの機能で一番難しく、
写せば必ず食い違う。訊けば連鎖がそのまま答える。一覧に足し忘れれば候補が1つ出ないだけで、
**間違った候補は決して出ない**。

`number^` だけ形が違う。語であって値ではないので型から訊けず、点の記録が
`number_word` を立て、`lhat_check_number_constants` が定数だけを流す。

### 言語の語と、スコープにある名前

`l` と打ったところに `let^` と `counter` を出すのは、点の後の補完とは別の問いで
ある。レシーバが無いので、**そこに何が書けるかは位置だけが決める**。

位置がその問いであることは本文だけで判る — カーソルの左を語の字で遡り、その手前が
`.` なら（メンバの問いのものなので）答えず、行頭から見て註釈や文字列の中なら
答えない（`lsp_completion_word_prefix`）。答えは二つの源から来る。

一覧は `lsp/completion.c` の `WORDS[]` に置く。01 の 2.1 のとおり**字句層は
キーワード表を持たない** — ハットの付いた語は全て一つの字種で、どれが何かは
構文解析器が決める（`parser.c` の `is_statement_keyword` が、同じ理由で自分の
分の知識を抱えている）。だから読める一覧はどこにも無く、これが一覧である。

これは**候補の一覧であって典拠ではない**。何もこれと照合されず、これで何かが
拒まれることも無い。足し忘れれば候補が1つ出ないだけで、既に無い綴りが載って
いれば書いた瞬間に検査器が報せる。組み込みメンバーの `chk_builtin_words[]` と
同じ取引である。

**スコープにある名前は、スコープ自身が閉じるときに控える**
（`check.h` の `LhatBindingSite`、`chk_scope_close`）。8 章のスコープ規則をサーバ側で
解き直さないのは、ホバーが解決の記録を読むのと同じ理由である。控えるのは
スコープが覆った範囲と、閉じる時点でそれが持っていた束縛の全て — 8.7 が名前を
スコープ全体で見えるものとするので、範囲は `let^` より後ではなくスコープそのもの。

**並び順が唯一の仕組みである。** スコープは自分を囲むスコープより先に閉じるので、
記録は自然に内側から並ぶ。ある位置を含むものを順に流せば、**最初に来るのが
8 章の探索が見つけるはずのもの**で、以降は全て隠されたもの。だから
`lhat_check_bindings_at` は走査1つで済み、綴りごとに最初の1件を採るサーバ側も
シャドウイングを1行も書かない。

スコープの中には**位置を持たないもの**がある。`def^` のメンバー表、対話セッション
の一枚のスコープ、ホストが登録した名前。これらは範囲が空で、どの位置も含まないので
記録に載らない。逆に単位のスコープはファイル全体を覆う — 木の根の範囲は最後の文で
終わるが、書き手のカーソルはその先に立つ。

名前を先に、語を後に出す。名前の方が書き手にとって価値が高く、`self^` のように
両方に現れる綴りでは、**実際に持っている型が付いた方**が残る。

### まだ取り込んでいない名前 — 取り込む文も一緒に入れる

三つ目の源がある。**この単位がまだ取り込んでいない名前**を、それを届かせる
`import^` / `require^` の行と一緒に出す（LSP の `additionalTextEdits`）。

**束縛名を発明しない。** これが成り立つのは 05 の 5.5 のおかげである。
`let^`/`var^` を書かない `require^` は、その単位が `module^` で名乗ったパスの
下に入る —— `import^` が根を束ねて残りをメンバにするのと同じ形。だから
どちらも「名乗られたパス」を書くだけで済む。

| 打った語 | 挿す文 | 語の置き換え |
| --- | --- | --- |
| `print` | `import^ std.io` | `std.io.print` |
| `publicProc` | `require^ "lib/m1.lh"` | `namespace1.module1.publicProc` |

**`module^` を名乗っていない単位は候補にしない。** 5.5 が省略形をその場合に
誤りとしており、`let^ name = require^ ...` を書くなら名前を選ぶことになる。
それは書き手の選択であってサーバの領分ではない。

候補の出所は2つ。ホストのモジュールは `program->hosted` —— `import^` が
解決するのと同じ入れ子テーブルで、**この単位が `import^` を書いていなくても
中身が見える**（登録は検査より前に済んでいる）。他の単位は根が抱えている
検査済みプログラムから写し取る（`lsp_workspace_copy_exports`）。まだ一度も
検査していない根は答えない —— 古い答えを出すより、何も出さない方がよい。

**この源は最後に走る。** 既に出た綴りは落とすので、スコープにある名前や
言語の語と同じ綴りは自動的に消える —— 手が届く名前があるなら書き手はそれを
意図したのであり、行を足す価値があるのは届かないものだけである。

#### 行をどこに入れるか

ここが一番尖っている。

- **`module^` の上には入れられない。** 05 の 3 章がそれを先頭に置き、
  構文解析器が2つ目を拒む。上に書けば見た目が悪いのではなく、**ファイルが
  構文解析を通らなくなる**
- **先頭のコメント塊の中にも入れられない。** 01 の 6.4 では塊は直後に来る
  ものに属し、07 の 4 章はその塊を単位自身の説明としている。間に割り込めば
  説明文が新しい行のものになる

だから: `module^` があればその次の行、無ければ先頭のコメント塊の後、それも
無ければファイルの先頭。塊の判定はコメント表を読む —— `#[ ]#` は行を跨ぐので、
本文を見て「`#` で始まる行」を数えるだけでは足りない。

**既に届いているなら行を足さない。** `import^` は入れ子の登録簿なので
**親を取り込んでいれば子も届く**（`import^ std` は `std.io` を含む）。
`require^` は綴りが一致するときだけで、こちらは**二重に書けば誤りになる**
（5.5 と 8.8 の末尾の規則）ので、正しさが要る。名前自体は届いていても
出す価値があるので、落とすのは行だけである。

### 定義の文を見つける

`LhatResolution` が持つのは定義された**名前の位置**である。
そこから、その位置を含む最も内側の「名前を導入する構文」（`DEFINE`、`PARAM`、
`ERRORDEF`、`TABLE_ENTRY` など）を木から探し、その範囲の1行目を切り出す。

**`module^` に結び付いたコメントは、その単位そのものの説明**である。
`module^` は名前を宣言するもので使いはしないため解決の記録に載らない。
位置から直に探して答える。

**別の単位から来た名前は、モジュール名が見える。**追加の仕組みは要らない。
05 章では他の単位の名前に触れる道が `require^` と `import^` しかなく、
束縛の定義行に必ずモジュール名が現れるためである。

```text
let^ other = require^ "lib/util.lh"
```

**定義が別の単位にあるとき、定義の行と説明文はその単位から切る。** 記録の
`definition_path` が名指す単位を二段目に引く（定義へ移動と同じ形、
`lsp/handlers/hover.c`）。型と範囲は元の単位で決め（`lsp/hover.h` の `LspHoverPart`）、
ロックを越えるのは文字列とオフセットだけ。相手の単位に届かなければ型だけを出す。

**記録が付くのは名前だけではない。** `require^ "lib.lh"` の文字列はその単位の先頭（0）を、
型の位置に書いた `store.Held` は輸出したメンバーの宣言を、`E.Bad` / `Mode.Walk` は種の宣言を
指す。種は型（`type.h` の `v.error`）に書かれた場所を持つ — メンバーの `declared_at` と同じ。
先頭がコメントで始まる単位の 0 には何も立たないので、hover は最初の文（`module^`）を示す。

［未決］ **L5** — 説明文の中で返り値や引数への説明を書き分ける記法（`@Return` など）。
01 の 6.4 が後回しとしたもので、決めるときは 01 側に番号を起票する。
それまで説明文は一塊として扱う。

なお言語サーバは `LHAT_WITH_COMMENTS` を定義したビルドを使う（01 の 6.4）。
外れた構成では 2 が空になり、1 だけが出る。
ビジュアルエディタもノードのコメントとして同じものを使う（06 の 5.4）。

## 5. 参照の検索と名前の変更

**名前とは、それが宣言された場所である。** 綴りではない。二つのスコープの
`count` は二つの名前であり、三つのファイルから届く一つの名前は一つである。
これが、サーバが 8 章のスコープ規則を一行も読まずに安全な改名を出せる理由。

解決の記録（`check.h` の `LhatResolution`）を**逆から読む**だけである。定義へ
移動は一つの記録が指す先を読む。参照の検索は全部の記録を読んで、同じ場所を
指すものを残す。歩くのは検査器で、ここでは歩き直さない。

対象は `(単位のパス, 宣言の位置)` の対。カーソルがどちらに立っていても同じ
対に落ちる:

- **使用の上** — 記録がその場にある。記録が指す先が対
- **宣言の上** — 記録が無い。位置そのものが対（自分のファイルでは使われず、
  他のファイルからだけ使われる `public^` の名前がこれ）

**記録があって宣言位置が無いものは、何も答えない。** ホストが登録した名前
（05 の 8.7）、言語自身が答える組み込み（14.19）、素のテーブルリテラルの
メンバー —— どれも編集できる場所を持たない。ここを「自分自身が宣言」と
扱うと、**改名がその一箇所だけを書き換えて残りを置き去りにする**。
だから記録の有無と宣言位置の有無を分けて見る。

ほかに三つ拒む。

- **ハット付きの語** — 名前の直後が `^` なら拒む。01 の 2.3 でハットは名前の
  一部であり、そういう語は言語のもので、書き手が束ねた名前は決してそうならない
- **名前でないもの** — 数値は名前と同じ字で出来ているが、先頭が数字である
  （01 の 3.1）
- **新しい名前が名前でないとき** — 同じ規則で見る。空いているかどうかは見ない。
  8.7 の衝突は検査器が、起きた場所で一度だけ報せる

**綴りの一致も要る。** 記録が指す先にその名前が書かれていなければ、その記録は
この名前の話ではない —— `require^` の記録はファイルの先頭（0）を指し、そこには
その単位の最初の宣言が立っている。綴りを比べれば、どの種類の記録がそうするかを
数え上げずに弾ける。

範囲は**検査済みの根が抱える単位すべて**（`lsp_workspace_with_every_unit`）。
一つの単位が複数の根の木に立つので、パスを同一性として重複を除く。

`textDocument/rename` は同じ答えをファイルごとに束ねた `WorkspaceEdit`。
`prepareRename` は同じ問いを最初の一歩で止めたもので、**書き手が新しい名前を
打つ前に断る**ためにある。

## 8. VSCode 拡張

`contributes` は `languages` / `grammars` / `configuration` / `configurationDefaults` に加え、
ビジュアルエディタのために次を持つ。

- **カスタムエディタ** — `contributes.customEditors` に `CustomTextEditorProvider`
  として登録（`src/graphEditor.ts`）。文書はテキスト文書のままなので、
  保存・取り消し・未保存の印は VSCode が扱う
- **webview** — 写像（`src/webview/map.ts`）と描画（同 `render.ts`）。
  外部への通信は行わない

**webview は言語サーバに直接触らない。拡張本体が代行する。**
webview には言語クライアントも接続先も無いため、これは選択ではなく前提である。
webview → 拡張本体は `postMessage`、拡張本体 → `lhatls` は `sendRequest("lhat/ast", …)`。
往復は一段増えるが、6.5 の測定からしてレイアウトの方が桁違いに重く、問題にならない。

**カスタムエディタは既定にしない**（`"priority": "option"`）。
`*.lh` を開けばテキストエディタが出る。グラフは `L^: Open Graph View` で横に開く。
第1段階（06 の 3 章）が読み取り専用である以上、グラフだけが出る状態は行き止まりになる。

### 8.1 二つの半分と、その作り分け

拡張は性質の違う二つの半分でできている。

- **拡張本体**（`src/*.ts`）— Node の上で動き、`tsc` が CommonJS に出す
- **webview**（`src/webview/`）— ブラウザの上で動き、React Flow を使う（06 の 8.4）。
  JSX を含み、React とその依存ごと束ねる必要があるので **esbuild** が1つに固める

esbuild は型を見ないので、型検査は `tsconfig.rf.json`（`npm run check:rf`）が別に行う。
**束ねるものと検査するものを分けてある**ので、片方だけを走らせても意味がある。

写像（`src/webview/map.ts`）は描画層に依存しない。これは意図してそう書いたもので、
描画層を差し替えても写像は動いたことが 06 の 8.4 の検証で確かめられている。

## 9. 設定 — 二つのファイル

`*.lh` ごとに、その親ディレクトリから親へ探して最初に見つかった設定ディレクトリ
から読む。探索には、そのファイルを含む LSP の workspace folder を含めるが、そこより
上へは行かない。**書き手が違う**のが二枚に分かれている理由であって、話題の違いでは
ない。

| ファイル | 書き手 | 中身 |
| --- | --- | --- |
| `lhat-host.json` | 機械（`lhat --dump-host-api`） | ホストが登録するもの（05 の 8.7）。`strict` |
| `lhat-lsp.json` | 人（リポジトリに入れる） | この企画を道具がどう扱うか。`exclude`・`force_include_files`・`strict` |

ダンプはファイルを丸ごと置き換えるので、手で書いたものはそこに置けない。
そして `exclude` は生成器が原理的に知り得ないものである。だから二枚になる。
`strict` が両方にあるのは矛盾ではない — `lhat-host.json` のそれは
「このホストはこう走る」という陳述で、`lhat-lsp.json` のそれは
「エディタにはこう見せたい」であり、後者が勝つ。

片方だけがあるディレクトリもプロジェクト境界になる。その場合、もう片方を親から
継ぎ足して混ぜることはしない。二枚は一つのプロジェクト設定を別の書き手が持つための
分割であり、設定レイヤーではない。設定のないファイルは workspace folder 自身を境界
にした既定プロジェクトに属する。複数の workspace folder と、同じ folder 内の入れ子の
設定ディレクトリは、それぞれ独立したプロジェクトとして host 登録・設定・root 集合を
持つ。

`.vscode/settings.json` は採らない。「`build/` は生成物」は企画の事実であって
エディタの好みではなく、そこに置くと他のエディタの利用者が同じ事実を書き直す。
`.gitignore` も採らない。追跡するかどうかと検査するかどうかは別の問いで、
入れ子・否定・`.git/info/exclude` まで背負うことになる。

### 9.1 `exclude` — 何を根にしないか

3 章のとおり、プロジェクト内の `*.lh` はそれぞれが独立した根になる。
`exclude` はその**根の集合**を決める。パターンはプロジェクトルートからの相対
パスに `/` 区切りで照合する。

- `*` は `/` を跨がない。`**` は跨ぐ。`**/` は0段にも当たる
- パターンは名指したパスとその下すべてに当たる。ゆえに `build` と `build/` は
  同じもので、走査は同じ1回の照合でディレクトリを刈りファイルを弾く
- 残りはすべてそのままの文字。**`!` も `?` も `[]` も無い**

#### gitignore を真似ない

規模の問題ではない。完全に真似ても100行に届かない。

**否定 `!` は、ディレクトリを刈ることと両立しない。** gitignore(5) は
*"It is not possible to re-include a file if a parent directory of that file is
excluded."* と断っている。git がこの但し書きを持つのは性能のためで、`build/` を
除外したらそのディレクトリに降りない、ゆえに中の `!build/keep.lh` は評価される
機会が無い。走査は同じ理由で同じ壁にぶつかる。`!` を入れるなら、この紛らわしい
但し書きを再現するか、刈るのをやめて全部歩くかのどちらかになる。

`!` を持たないと決めると、**last-match-wins の順序規則も要らなくなる**。
どのパターンに先に当たったかで答えが変わらないので、照合は最初に当たった所で
止められる。ここは連鎖して効いている。

**アンカーの規則も採らない。** gitignore では「パターンに `/` が含まれるか」で
アンカーされるかが変わる — `build` は任意の深さに当たり、`src/build` はルート
相対になる。同じつもりで書いて挙動が変わる暗黙の条件分岐なので、ここでは
「常にルート相対、深さを跨ぐなら `**/` と書く」の1規則にした
（VSCode の `files.exclude` も同じ流儀）。**この差は実利用に出る**: gitignore の
頭で `build/` と書くと `src/build/` にも当たると思うが、ここでは当たらない。

入れ子の `.gitignore` も採らない。ディレクトリごとに規則を積む機構は、ルートの
生成物を外すという用途に対して過剰である。

そして**中途半端に似ていると、似ている分だけ悪い**。構文が gitignore に見えれば
読む側は gitignore の頭で読み、そこからのズレは設計ではなくバグに見える。
明らかに小さい構文なら、そもそも持ち込まれない。

決めたこと2つ:

- **除外されたものは根にならない。**探索でも didOpen でも。根は今のところ
  取り除かれる道が無いので、「開いている間だけ根」にすると一度開いたファイルの
  赤が閉じた後も残る — 元の苦情がそのまま戻る
- **根にならないだけである。**他の根が `require^` した先は今までどおり読まれ、
  そこにある誤りは報告される。05 の 5 章の辿りは言語のもので、サーバが検査器に
  「そのファイルは無い」と嘘をつく話ではない。`exclude` は根の集合を決める
  道具であって、診断を黙らせる道具ではない

### 9.2 `force_include_files` — 除外の中の、名指しした数本

除外したディレクトリの中に本物のソースが混ざることはある。`force_include_files`
がそれを戻す。

```json
{
  "exclude": ["build/"],
  "force_include_files": ["build/generated/api.lh"]
}
```

**これはパターンではなく名指しである。**その一点が、gitignore の `!` が抱えた
問題を丸ごと消している。パターンなら「走査が見つけたものから戻す」ことになり、
戻す対象を見つけるには除外したディレクトリを歩かねばならない — `!` の但し書きは
まさにそれで生じている。名指しなら探す必要が無い。走査は今までどおり自由に刈り、
**その後で、書かれた名前をそのまま根に足す**。二つの機構が出会わない。

順序も要らない。`!` は除外と同じ列に混ざるので last-match-wins が要ったが、
これは別の欄なので集合の差で定まる — `除外 = exclude に当たる かつ
force_include_files に無い`。どのパターンに先に当たったかで答えが変わらない。

規則:

- プロジェクトルートからの相対パスで、**ルートの中に留まる**。絶対パスは
  1台の機械のものでこのファイルごとコミットできず、`..` は畳まれないまま届いて
  1つのファイルが2つの根になる（`scan_dir` の注釈が警告している罠）。`..` を
  含む項目は読み捨てる
- 書いた文字がそのまま名前である。`*` を書けば `*` という字を含むファイルを指す
- 名指したファイルは、そこから先は**普通のファイルとして振る舞う**。走査が残し、
  掃き出しが落とさず、開けば検査される（判定が `path_excluded` の1箇所に
  集まっているため、4つの経路が自動で揃う）
- 名前が指すファイルが無ければ、起動時に**そのパスを名指して警告する**。
  名指しは「検査してほしい」の表明であり、綴り間違いが黙って落ちてはいけない

編集すると読み直し、根の集合を作り直し、全体を検査し直す（`lsp/worker.c`）。
消えた根の古い診断は空の配列で消える（既存の `published_paths`）。
