# L^ 字句構造仕様

字句解析器（lexer / scanner）が扱う範囲、すなわちソース文字列からトークン列を得るまでを定義する。

構文解析（トークン列から構文木を得る段階）以降の話題は扱わない。
ブロックとテーブルリテラルの区別、if 文と if 式の区別、型検査などは
すべて構文解析以降の責務であり、本文書の対象外である。

記法ラベル（［確定］／［提案］／［未決］）の意味は [README.md](README.md) を参照。

---

## 1. ソースファイル

- **文字符号化: UTF-8 固定**［提案］

  `≠` `≦` `≧` を演算子として採用する（Memo.md L34）以上、ソースは非 ASCII を含む。
  また識別子のローカライズを将来的な課題として挙げている（Memo.md L397–L399）。
  符号化を UTF-8 に固定し、それ以外は受け付けない。

- **BOM**［提案］

  先頭の U+FEFF は読み飛ばす。ファイル先頭以外に現れた場合はエラー。

- **改行**［提案］

  `LF` / `CRLF` / `CR` を改行として認識し、内部的にはすべて `LF` として扱う。
  文字列リテラル内部の改行も同様に正規化する。
  これをしないと、同じソースが改行コードによって異なる文字列値を生む。

- **Unicode 正規化**［提案］

  行わない。識別子の同一性はコードポイント列の一致で判定する。
  正規化はエディタ／フォーマッタの責務とする。

## 2. 字句構造の中核 — `^` サフィックス

L^ の字句構造で最も特徴的な点であり、他のあらゆる規則がここから派生する。

**呼称**: `^` は「ハット」と呼ぶ。「キャレット」とは呼ばない。
言語名 `L^` を「エルハット」と読ませるため、文書・識別子・診断メッセージのすべてで
`hat` / ハットに統一する。トークン種別も `HAT_IDENT` である。

### 2.1 予約語が存在しない［確定］

Memo.md L395 に「とにかく予約語がないし名前の制限が緩い」とある。
キーワードは常に `^` を伴う。

- `if` — ただの識別子。変数名に使える
- `if^` — キーワード

したがって字句解析器はキーワードを認識しない。
`^` が付いた識別子を **一律に同じトークン種別として返し**、
それがキーワードなのか型名なのかメタプロパティなのかの判定は構文解析器に委ねる。

これは単なる実装上の都合ではなく、「予約語がない」という言語設計の直接の帰結である。
字句解析器にキーワード表を持たせると、キーワードを増やすたびに既存コードの識別子が壊れる
――まさにこの設計が避けようとしている事態――を字句レベルで再導入してしまう。

### 2.2 `^` の用途は一つに統一されている［確定］

Memo.md 全体を通じて、`^` は算術（べき乗）にも論理（XOR）にも使われていない。
`^` はサフィックス専用の記号である。この一貫性が字句解析を単純にしている。

`^` が付く語の実例を Memo.md から分類すると、以下のすべてが同じ字句形をとる。

- 制御構文: `if^` `else^` `elseif^` `elsif^` `elif^` `ei^` `el^` `or^` `for^` `when^`
  `other^` `from^` `to^` `downto^` `step^` `in^` `while^` `until^` `next^` `repeat^`
  `do^` `break^` `return^` `yield^` `yieldall^` `defer^` `with^`
- 定義子: `f^` `p^` `op^` `def^` `self^` `enum^`
- 型・修飾: `number^` `string^` `int^` `nil^` `true^` `false^` `as^` `is^`
- メタプロパティ: `.class^` `.super^` `.keys^` `.values^` `this^` `it^`
- テーブル制御: `width^` `autowidth^`
- 繰り返しの節: `prolog^` `main^` `epilog^` `first^` `last^`

字句解析器から見ればこれらはすべて同一種別であり、区別する必要がない。

上は **Memo.md の語彙の分類** であって、言語の語彙一覧ではない。
その後に決まった `finally^`（02 の 10 章）、`override^` `overload^`（02 の 14.12）、
`errordef^` `try^` `catch^`（[04-errors.md](04-errors.md)）、
`var^` `let^`（02 の 8.6、8.9）、
`module^` `public^` `require^`（[05-modules.md](05-modules.md)）、
`isa^`（02 の 13.11、11.6改で `is^` から適合の判定を引き継いだ）も同じ字句形をとる。
`enum^` は撤回された（04 の 12.3）。

Memo.md L28–L29 の `mutable^` は **退役させる**。「引数は既定で immutable、
書き換えたければ `mutable^` を書く」という構想は、実際には
02 の 15.1改 の「本体が作ったテーブルだけを変更できる」という出自の規則に
置き換わった。可変性の側は 02 の 8.9 が `var^` と `let^` で担う。
綴りとしての `mutable^` はどこにも実装されておらず、上の分類から外した。

このうち **名前ではなく構文であるもの** は取り込みを要さない。
`try^` `catch^` `pack^` `require^` `typeof^` がそれにあたる（05 の 8.4）。
`rawsignature^` は提案されたが実装されず撤回した（02 の 14.16）。

**語が増減しても字句解析器は変わらない。** それが 2.1 の決定の効果である。

### 2.3 `^` の連続［確定・S34で名前の解釈を訂正］

Memo.md L358–L362 に `super^` `super^^` `super^^^` が現れ、
L688 には `$^^^^a` がある。`^` は反復しうる。

したがってトークンは **`^` の個数を保持する**。

- `this^` → 識別子 `this^`、ハット数 1
- `this^^^` → 識別子 `this^`、ハット数 3

ハット数1がハット識別子そのものであり、2つ目以降が段数を言う。
`this^^^` は「2つ外の `this^`」であって、`this` という名前ではない。

ハット数を持たせず「識別子＋`^`」トークンの後ろに裸の `^` トークンを並べる設計でもよいが、
構文解析器側で毎回数え直す手間が生じる。字句側で数えてしまうほうが素直。

#### ハットは名前の一部である［確定・S34で訂正］

> **ハット識別子の名前は「語＋ハット1つ」である。
> `self^` と `self` は別の名前であり、決して混ざらない。**

かつて実装は「ハットは名前の一部ではない」と解釈しており、
`self^` を `self` として引き、`P.new^` と `P.new` を同じキーにしていた。
**誤りだった。** この解釈では、処理系の語（`self^` `class^` `it^` `tostring^`）が
書き手の裸の名前（`self` `class` `it` `tostring`）と衝突する
——ハットを付けて避けたはずの汚染が、名前解決の層で復活していた。

正しくは:

```lhat
var^ self = 10        # 書き手の名前。self^ とは無関係
var^ class = 30       # 同上。def^ の class^ と衝突しない
let^ t = { tostring^ = f^self^ -> string^ { return^ "mine" } }
t.tostring^           # 上で書いたもの
t.tostring            # 別の名前。何も入っていない
```

正準形は **語＋ハット1つ** である。2つ以上のハットは同じ名前を外へ数える段数であり
（`this^^^` = 2つ外の `this^`、`break^^^` = 3段抜け、01 の 8 章 の `$^^`）、
名前の同一性には入らない。

この規則は **キーにも束縛にも一様に** 適用される。
メンバのキー `tostring^` は9文字のキーであり、
局所名 `self^` は5文字の名前である。例外はない。

#### どの語が段を数えるか［確定・S35。同日実装済み］

2つ目以降のハットは段数だが、**段を数えられるのは数える構造を持つ語だけ**である。
（S35 の時点では4語だった。S37 で `Self^` を加えて5語になっている。）

- **スコープ・ループの段数** — `$^^…`（8 章）、`break^^^`（02 の 9.8）
- **同名束縛の段数**（内側の同名束縛を数えて飛ばす）
  - `it^^` — 外側のループ（または `catch^`）の焦点
  - `self^^` / `class^^` — 外側の `def^` の受け手・定義。`$^self^` の短縮形
- **`Self^^`**［S37で追加］ — **書かれた型リテラルの段数**。`Self^` は自身を囲む
  `t^{ … }` / `def^{ … }` を指し、2つ目以降のハットは1つ外の型リテラルを数える。
  数える対象が束縛でもループでもなく **ソースに書かれた型リテラル** である点だけが
  他の語と違う。`self^` とは別の名前（大文字 S）であり、値ではなく型である。
  詳細は 02 の 13.13
- **`this^^`** — 入れ子定義の外側の関数・手続き。**レキシカル**であり、
  実行時の呼び出しスタックを辿るものではない——内側の閉包が**作られる瞬間**に、
  作り手（＝字句上の外側の本体を走らせている閉包）が自分自身を捕捉する。
  無名のまま外側の本体を呼ぶ再帰を書くための手段である。
  `$^` の外向きの読みと同じ意味だが、this^ は束縛でなく命令なので
  `$` の機構（束縛の解決）では書けず、捕捉の1種として実装される
- **誤り**（構文エラー） — 上記以外のすべて。キーワード（`if^^` `var^^`）、
  値語（`true^^` `nil^^` `L^^`）、型名（`number^^`）、書き手の名前（`foo^^`）、
  メンバのキー・型名・宣言の位置に書かれた多段全般

##### `super^^` は誤りとする［確定・S35］

「基底の基底の実装に届く」という読みを検討し、**退けた**。

- **合成順に脆い。** 14.15改の mixin は自分が何に積まれるか知らないのが設計であり、
  段数で層を飛ばす書き方は `A..B..def^` に C を挟んだ瞬間、黙って別物を指す
- **指す先がキーの上書き履歴に依存する。** `super^` はキー単位の「直前の値」であり、
  途中の部品がそのキーを override していなければ「2つ前」は存在しない。
  使用箇所からこの履歴は見えない
- **明示形が既にある。** 14.5改が「側を名指して届く」と定めており、
  `A.a` と書けば挿入にも履歴にも壊されない

Java/C++ が `super.super` を禁じ、Python が明示クラス名で書かせるのと同じ方向である。

### 2.4 隣接規則［提案］

識別子と `^` の間に空白・コメントを挟むことを禁じる。

```text
if^     -- キーワード
if ^    -- 識別子 if と、裸の ^
```

Memo.md L684–L685 はスコープ指定子 `$` について
「空白文字無しでくっつけて書かないとスコープ指定子とみなされない」と述べており、
同じ原則を `^` にも適用する。

### 2.5 裸の `^`［確定］

`^` が識別子に続かない位置に単独で現れる用法はない。
旧層のブロック開始子 `{^`（Memo.md L416, L704 ほか）は不採用が決定している（10.7）。

したがって `^` は常に識別子の直後にのみ現れる。
識別子を伴わない `^` を検出したらエラーとしてよい。

## 3. 識別子

### 3.1 構成文字［提案］

Unicode 標準附属書 #31 (UAX #31) の `XID_Start` / `XID_Continue` に従う。
加えて `_` を開始文字・継続文字の両方として許可する。

ASCII のみに限定しない理由は、識別子のローカライズを将来課題として明示していること
（Memo.md L397–L399）と、日本語圏の利用を想定していることによる。

**実装の現状**: UAX #31 の表は未搭載。
非 ASCII のコードポイントのうち、空白でも予約記号（7.2）でもないものをすべて
識別子構成文字として受け付けている。仕様より緩い。
`src/lexer.c` の `is_ident_start()` に該当箇所を注記してある。

### 3.2 `?` と `!` は識別子に使えない［確定・旧 Q3 で変更］

`?` は `?` 族の演算子（`?.` `?(` `?[`、`??`、後置の `?`）に、
`!` は論理否定演算子に、それぞれ予約されている。どちらも識別子の構成文字にならない。

`?` 単体はかつて専用の字句誤りだった（「`?.` `?(` `?[` の一部としてしか書けない」）。
02 の 11.7改2 が後置演算子として与えたので、その誤りは無くなった。

Memo.md L139–L142 は当初、逆の割り当てを提案していた。

> boolを返す関数に?で終わる名前付けを許すために、!のほうをnilプロパゲーションに使う？
> （中略）なので、!はシンボル名に使えない。?も末尾のみ、値がboolである場合のみ許可

この案は **撤回された**（12章 Q3 参照）。役割は入れ替わり、
`?` 末尾による bool 命名規約は通常の識別子では採用しない。

ただし bool を返す関数を `?` で終わる名前にしたい場合は、
3.4 の名前リテラルを用いて `` `foo?` `` と書ける。

字句解析器への影響として、以前の版にあった
「`?` は識別子の最終文字としてのみ出現できる」という規則は不要になった。
識別子の走査中に `?` や `!` に出会ったら、そこで識別子を終端する。

なお、この変更により `foo?()` の意味が反転している。
旧案では「`foo?` という名前の関数の呼び出し」だったが、
現在は「`foo` を nil 伝播つきで呼び出す」になる。

### 3.3 `id^` による識別子リテラル［旧仕様・3.4 に置換］

Memo.md L76–L79 は `id^` に文字列リテラルを続ける形を挙げていた。

```lhat
id^foobar
id^"foobar"
id^'foobar'
```

この形は 3.4 のバッククォート記法に置き換える。経緯は 3.4 を参照。

### 3.4 名前リテラル［確定］

バッククォートで囲むと、通常の識別子規則に収まらない名前を書ける。

```lhat
`foo?`
`is empty? (yes/no)`
`空か?`
```

囲みの中は一切解釈しない。演算子・コメント記号・`^` サフィックスを含む文字列も、
そのまま名前の一部になる。

- **区切り記号は名前に含まれない。** `` `ab` `` の名前は `ab`
- **バッククォート2つで、バッククォート1文字を表す。** `` `a``b` `` の名前は ``a`b``。
  生文字列の `''`（5.2）と同じ規約
- **改行をまたげない。** 閉じ忘れが行末で止まるため、
  5.5 に述べた「未終端の引用符がファイル末尾まで飲み込む」問題が起きない
- **空の名前リテラル `` `` `` はエラー**

#### 独立したトークン種別である［確定・重要］

名前リテラルは `IDENT` とは **別のトークン種別** として返す。同一にしてはならない。

Memo.md L81–L83 は、識別子を **値として** 扱う用法を挙げている。

```lhat
let^ foo = {a := f^{} b := f^{} c := f^{}}
foo[for^bar { when^1: id^a when^2: id^b when^3: id^c }]()
```

ここの `id^a` は変数 `a` の値ではなく **名前 `a` そのもの** であり、
`for^when` 式が返した名前が `foo` のキーになる。

名前リテラルが `IDENT` を返す実装だと、`` `a` `` と `a` が
**字句的に同一のトークンになり、この用法が表現できなくなる**。
別種別にすることで、名前を書く用途と名前を値として扱う用途の両方を担える。

#### `id^` を置き換える理由

- **1トークンで済む。** `id^'foo?'` は「`^` 付き識別子」と「文字列リテラル」の
  2トークンであり、構文解析器が対にして解釈する必要がある。
  名前リテラルは字句解析器が1個のトークンとして返す
- **短い。** 名前の自由度を高めることは Memo.md L395–L399 が挙げる将来目標であり、
  例外的な記法ではなく日常的に使われうる
- **3.2 で失われた `?` 終わりの命名規約を取り戻せる。**
  Q3 で `?` を識別子構成文字から外したが、`` `empty?` `` と書けば同じ意図を表せる

実行時の文字列から名前を得る操作は、この記法（リテラル）では表現できない。
必要になった場合は Q3 の方針に倣い、構文ではなく標準ライブラリ関数として提供する。

#### バッククォートを選んだ理由

`` ` `` は現行の設計で未使用のまま残っていた。
Memo.md L391–L392 はサフィックス記号の候補として `^` とバッククォートを比較し
（日本語キーボードでは `^` がシフト不要、US キーボードでは逆）、
`^` を採用した。L419 の `//#grave off` もバッククォート用の指令の名残である。
つまり **旧構想で候補から外れた結果として空いていた** 記号を再利用する形になる。

ASCII 1バイトであるため、全角チルダ（U+FF5E）と波ダッシュ（U+301C）の
使い分けのような、環境によってコードポイントが変わる問題も生じない。

Kotlin・Scala・F#・MySQL が同じ記法を採っている。

## 4. 数値リテラル

Memo.md には具体的な数値リテラルの実例（`1` `10` `1.234` `2.4` `-1` `0`）しかなく、
書式の定義がない。以下はすべて［提案］。

### 4.1 整数と浮動小数点数を別の型とする［提案］

Lua 5.3 以降と同様に整数型と浮動小数点型を区別する。
字句解析器は小数点・指数部の有無で `INT` と `FLOAT` を区別して返す。

### 4.2 基数プレフィックス［提案］

- `0x` / `0X` — 16 進整数
- `0b` / `0B` — 2 進整数
- `0o` / `0O` — 8 進整数

C の `0777` 形式の 8 進数は採用しない。先頭 `0` の事故が多いため。

### 4.3 桁区切り［提案］

`_` を数字の区切りとして許可する（`1_000_000`）。
先頭・末尾、および小数点に隣接する位置には置けない。

### 4.4 小数点の規則［提案・重要］

以下の2つは字句的曖昧性の解決に直結するため、単なる書式の好みではない。
詳細は [10. 字句的曖昧性](#10-字句的曖昧性と解決規則) を参照。

- **先頭の小数点を認めない** — `.5` は不正。`0.5` と書く
- **末尾の小数点を認めない** — `1.` は不正。`1.0` と書く

すなわち小数部は **小数点の直後に数字が続く場合にのみ** 成立する。

### 4.5 指数表記［提案］

`1.0e10` `1.0E-3` `2.5e+8` を認める。

`e` / `E` を読んだ後、続く文字が数字でも符号付き数字でもなければ **エラー**とする。
読み戻しは行わない。Q7 の決定（10.3）により、
数値リテラルの直後に識別子開始文字が続くことがそもそも許されないため、
`1e` に見える並びを `1` と `e^…` に分解して救済する必要がない。

## 5. 文字列リテラル

Memo.md L67–L72 に4種類が挙げられている。

### 5.1 `"…"` — エスケープあり、複数行可［確定］

改行を含められる（Memo.md L68）。

エスケープ列は Memo.md に定義がない。以下を［提案］する。

| 記法 | 意味 |
| --- | --- |
| `\n` `\r` `\t` `\0` | 改行・復帰・タブ・NUL |
| `\\` | `\` 自身 |
| `\"` | `"` |
| `\xHH` | 16 進バイト |
| `\u{…}` | Unicode コードポイント |
| `\` + 改行 | 行継続（改行を出力しない） |

未定義のエスケープ列はエラーとする（黙って `\` を落とさない）。

### 5.2 `'…'` — エスケープなし、複数行可［確定］

Memo.md L69。`'` 自身は `''` と2つ重ねて表す。

`\` は何も特別な意味を持たない。Windows のパスや正規表現をそのまま書ける。

なお空文字列 `''` と「`'` 1文字を含む文字列」`''''` は字句的に区別される。

### 5.3 `"""` — 行末までの文字列リテラル［確定］

Memo.md L72「`"""` は行末まで文字列リテラル」。
開始の `"""` から、その行の改行の直前までが文字列の内容になる。終了記号は不要。

これは実質的に行コメントとして機能する（[6. コメント](#6-コメント)参照）。

**エスケープは処理しない**［提案］。`"` で始まるがエスケープありの `"…"` とは異なる。
コメント代わりに使われる以上、文中の `\` 1個でエラーになる挙動は望ましくないため。

### 5.4 文字列補間［確定］

Memo.md L70–L71。

```lhat
$"string interpolation {foo} {bar:2.4}"
```

- `$` と引用符の間に空白を置けない［提案］
- 補間対象は `{` … `}` で囲む［確定］
- 穴の中は `{式}` または `{式:書式指定子}`［確定・旧 Q4］

Memo.md L70 の `{2.4:bar}` は前後が逆になった誤記であり、正しくは `{bar:2.4}`。
`bar` が評価される式、`2.4` が書式指定子である。C# および Python の f 文字列と同じ順序。

#### 書式指定子は式ではない［提案］

`:` 以降は評価される式ではなく、書式のミニ言語をそのまま書いた文字列として扱う。
したがって字句解析器は `:` を読んだ時点で **穴を閉じる `}` までを生の文字列として取り込む**。
内部を通常のトークンに分解してはならない。

#### 書式指定子を開始する `:` の決定規則［提案］

L^ は `:` を多用する（`id : type = value`、`when^0:`、`if^expr:expr`、`else^:`）。
穴の中に置かれた式そのものが `:` を含みうるため、どの `:` が書式指定子の開始かを決める必要がある。

> 穴の中で、`(` `)` / `[` `]` / `{` `}` のいずれにも囲まれていない **最初の `:`** が
> 式を終端し、書式指定子を開始する。

この規則の帰結として、`:` を最上位に含む式（if 式や型注釈）は括弧で囲む必要がある。
C# が条件演算子 `?:` に対して同じ制約を課しているのと同型である。

```lhat
$"{ (if^x: a el^: b ;) :2.4 }"   # 括弧が必要
$"{ foo.bar }"                    # : がないので書式指定子なし
```

#### 穴は `tostring` を呼ぶ［確定］

> **`$"…{式}…"` は、断片と、各穴の `式.tostring()` とを
> 02 の 11.2 の `..` でつないだものと同じである。**

書式指定子を書いた穴は `式.tostring(書式)` になる。
02 の 14.17 がその第2署名を `number^` だけに与えているため、
書式を書けるのは数を埋める穴に限られる。

```lhat
$"n = {a}"        # "n = " .. a.tostring()
$"{a:%04d}"       # a.tostring("%04d")
```

したがって **補間は新しい文字列の作り方を持ち込まない**。
手で書き下せるものの綴りを短くしているだけである。
14.17 のとおり利用者の型が自分の `tostring` を書いていればそれが答えるので、
補間もその綴りに従う。

穴の中は普通の式なので、評価されるのは **その式が書かれた場所ではなく、
文字列が作られる時点** である。

#### 波括弧そのものを書く［提案］

`{{` と `}}` でそれぞれ `{` と `}` を表す。C# および Python の f 文字列に同じ。

テキスト断片の中では、閉じるべき穴が開いていないため、
単独の `}` も文字としての `}` を意味する（エラーにしない）。

#### `$'…'` は存在しない［確定・旧 Q11］

Memo.md L71 の注記「文字列補間したいなら `""` 必須」に従い、
補間は `$"…"` のみとする。`$'…'` は専用の診断で拒否する。

#### 実際に生成されるトークン列［確定］

```text
BEGIN ( TEXT | EXPR_BEGIN <通常のトークン列> [FORMAT] EXPR_END )* END
```

`TEXT` は断片が空でない場合にのみ生成する。
`$"{a}{b}"` のように穴が連続する場合、間に空の `TEXT` は挟まらない。

穴の内部は通常の規則で走査されるため、
テーブルリテラルや文字列リテラル、さらに別の補間文字列を含められる。
穴の中で開かれた `{` の深さを数えることで、
テーブルリテラルの `}` を穴の終端と取り違えない。

入れ子の深さには上限を設ける（実装では 32）。これを超えたら診断を出す。

字句解析器の実装方針［提案］として、補間文字列を1個の巨大なトークンとして
返して後段で再解析する方式は採らない。`{` … `}` の内部には任意の式が入り、
その式はさらに文字列リテラルを含みうる（`$"{ f("x") }"`）ため、
再解析器が字句解析器の完全な複製になってしまう。

代わりに、字句解析器に小さなモードスタックを持たせ、
補間文字列を次のトークン列に分解して返す。

- 補間開始（`$"`）
- 文字列断片
- 補間式の開始（`{`）
- 内部の式のトークン列（通常どおり字句解析する）
- 補間式の終了（`}`）
- 文字列断片
- 補間終了（`"`）

`{` `}` の対応をモードスタックで数えることで、
式の内部に現れるテーブルリテラルの `}` と補間の終端 `}` を取り違えずに済む。

### 5.5 複数行文字列の危険性［注意］

`"…"` と `'…'` がどちらも複数行を許すため、閉じ忘れた引用符は
**ファイル末尾までを飲み込む**。エラーは実際の誤りから遠く離れた位置で報告される。

診断品質のための緩和策［提案］として、未終端の文字列を検出した際に、
文字列の開始位置と、その後に現れた最初の空行またはインデントが戻る位置を
併せて報告する。これは字句解析器の責務ではなくエラー報告器の責務だが、
そのための位置情報を字句解析器が保持しておく必要がある。

## 6. コメント

### 6.1 行コメントは `#`［確定・旧 Q5］

`#` から行末までがコメントである。C 風の `//` は採用しない。

Memo.md L88–L89 は当初、専用のコメント構文を設けず
「使用しない文字列リテラル」で代用する案を挙げていた。

> コメント構文は特に用意しない。使用しない文字列リテラルがその代わり
> // だけはコメント専用にする？

この案は採らない。理由は 5.5 に述べた複数行文字列の危険性である。
`"…"` と `'…'` がどちらも複数行を許す以上、
コメント内に引用符が1個混入した時点で文字列の入れ子構造が崩壊し、
そこから先のファイル全体の字句解析が破綻する。
コメントは専用の構文を持つべきである。

なお Memo.md 自身のコード例は `//` と `/* */` を全面的に使用している
（L99, L119, L278, L296–L298, L347–L362, L480–L489 ほか多数）が、
これらは表記を `#` に読み替える。

#### `#` を選んだ理由

- **`//` を切り捨て除算に空けられる。** Python・Lua 5.3 以降が持つ演算子であり、
  コメントに使ってしまうと表現できなくなる（7.1 に追加済み）
- **シバン行がそのままコメントとして通る。** `#!/usr/bin/env lhat` を
  特別扱いなしに読み飛ばせる。L^ はグルー言語を標榜しており、
  スクリプトとして直接実行される場面が想定される。
  Lua は同じ目的のために「1 行目が `#` で始まる場合は読み飛ばす」という
  専用処理を処理系側に持っている
- **`#` は他のどの用途とも衝突しない。** Lua では長さ演算子だが、
  L^ は Q3 で長さを関数に移したため完全に空いている
- Python・Ruby・シェル・Perl・R・YAML・TOML・Makefile・PowerShell と同じ記法であり、
  グルー言語の利用者にとって馴染みが深い

### 6.2 ブロックコメント［提案］

`#[` から `]#` まで。**入れ子を許可する。**

```lhat
#[ これはコメント
   #[ 入れ子にできる ]#
   ここもまだコメント ]#
```

行コメントと同じ `#` を基調とすることで記法が揃う。Nim が同じ組み合わせを採っている。

`/* */` を残す案もある。`//` を切り捨て除算にしても `/*` とは最長一致で区別できるため
共存は可能だが、行コメントが `#` である言語に C 風のブロックコメントだけが残るのは
一貫性を欠く。また `a //* b */` のような並びが
「切り捨て除算のあとに `*`」と読まれる紛らわしさも生じる。

入れ子を許可するのは、コメントアウトした範囲をさらにコメントアウトする操作が実務上必要になるため。
字句解析器は `#[` の深さを数える。

### 6.3 `"""` 行末文字列との併存［確定］

`"""` から行末までの文字列リテラル（5.3）は、
値を捨てれば行コメントとしても機能する。これは禁止しない。
ただしコメントの主たる手段は `#` である。

### 6.4 コメントの保持［確定・旧 Q13］

字句解析器は当初、コメントを空白と同じ trivia として読み飛ばしていた
（`src/lexer.c` の `skip_block_comment`）。構文木にもコメントは残らなかった。

これを改め、**字句解析器はコメントの位置と本文を保持し、構文木のノードに結び付ける**。

理由は説明表示（07 の 4 章）だけではない。**ビジュアルエディタでの編集**（06）が本命である。
構文木がコメントを持たなければ、グラフ上で書けるコメントはテキスト編集で書けるものより
ずっと貧しくなる。テキストと同じ自由度でコメントを書けることが要る。

#### 説明文の記法は設けない

説明文かどうかを字句の段階で区別する専用の記法（`##` など）は**採らない**。
コメントはすべて等しく保持し、**定義の直前に置かれたコメント塊を説明文とみなす**。
Go が同じ形をとる。

追加の字句規則が要らず、既存のコードがそのまま説明を持つようになる。

`@Return` のように、説明文の中で返り値や引数への説明を書き分ける記法は、
別途整備する余地がある。**当分は後回し**とし、記法を決めるまでは説明文を一塊として扱う。

#### 保持の形［案 E・実装済み］

トークン列に `COMMENT` トークンとして混ぜる形は採らない。
構文解析器が全ての読み取り位置でこれを読み飛ばす必要があり、既存の解析器に手が入る。

**字句解析器がトークン列とは別に `(開始, 終端, 行, 桁, 種別)` の表を積み、
構文木との対応は位置で取る**（`LhatComment`、`src/token.h`）。構文解析器は無変更でよい。
範囲はコメント全体を覆う（`#`・`#[`・`]#` を含む）ので、本文はソースの部分列として取れる。

閉じられなかったブロックコメント（6.2）も表に載せる。書かれたものはコメントであり、
編集の途中だからといってツールがそれを失ってよい理由はない。

#### ノードへの結び付け

構文木への結び付けは、**単位を解析し終えた後の1パス**で行う（`parser.c` の `attach_comments`）。
表も木もソース順なので、表に対するカーソル1つで足りる。解析中ではなく解析後に行うのは、
その時点で表の成長が止まっており、ノードが持つポインタが無効にならないため。

規則は2つ。

- **直後に来るものに属する。** あるノードの部分木の開始位置より前にあるコメントは、
  そのノードに属する。部分木の開始位置を使うのは、中置・後置のノードが演算子の位置から
  始まるため（06 の 4.2）。`a + b` の `a` の前に書かれたコメントは和に属してほしい
- **ただし直前のコードと同じ行にあるなら、そちらに属する。** 行末コメントは、
  その行に書かれたものに対して書かれている。判定は行番号ではなくソース本文で行う
  （ノードは開始位置しか記録せず、文は複数行にわたりうるため）

どの子より後にあり、まだそのノードの範囲内にあるコメントは、そのノードの最後の子に属する。
木全体より後にあるコメント（ファイル末尾の行）は根に属する。

結び付けは **`next_for_node` による連結**とし、表の区間としては持たない。
ノードは「上に書かれたコメント」と「最終行の末尾コメント」を2回に分けて受け取ることがあり、
その間に別のノードのコメントが挟まりうるため、区間では隣のノードのものを飲み込んでしまう。

`tests/test_parser.c` の `test_comments` が、**走査したコメント数と木に付いたコメント数の一致**を
検査する。落としても二重に付けても数が合わなくなる。

#### 条件コンパイルで外せる

コメントの保持は言語の意味論に一切関与せず、必要とするのは言語サーバと
ビジュアルエディタだけである。組み込み用途では表も走査も無駄になる。

したがって **`LHAT_WITH_COMMENTS` が定義されているときだけ有効**とする。
未定義のビルドでは表も、それを積む処理も、構文木側のフィールドも消える。

CMake の `option(LHAT_WITH_COMMENTS ... ON)` から `lhat` ライブラリに `PUBLIC` で与える。
`LhatLexer` と `LhatNode` の形が変わるため、これらのヘッダに対してコンパイルされるものは
すべて同じ設定で揃っていなければならない。
既定は ON（`LHAT_BUILD_LSP` が既定 ON であるため）。組み込み向けの構成が OFF にする。

OFF のビルドでは、表・それを積む処理・`LhatNode` のフィールド・結び付けのパスがすべて消える。

［確定］ コメントを保持する。専用記法は設けない。`LHAT_WITH_COMMENTS` で外せる。

なお `LhatNode` の終端位置（06 の 4.2）は同じようには外さない。
コストは 8 バイト/ノード（`sizeof(LhatNode)` が 96、外すと 88）で、
コメントの表と違ってソースの内容によらず一定である。
それより、外すと `test_spans` も外れ、**OFF の構成で構文解析器の正しさが検証されなくなる**。
終端位置は「どこまで読んだか」の記録であり、構成によって消える種類のものではない。

**`=` が代入ではなく比較である点**は、C 系言語の経験がある実装者が
最も間違えやすい箇所なので強調しておく。`==` は存在しない。

この点は言語の設計動機に直結している。
`i = i + 1` のような記述は、数学の等式と同じ見た目でありながら意味が全く異なる。
L^ ではこの乖離を排し、**数学的な見た目をした記法には数学的な意味だけを与える**。
`=` を比較に割り当てたのも、再代入に `=` を使わず `:=` を用いるのも（7.3）、
同じ原則の帰結である。

なお 02 の 8.6 により、`var^ x = 0` のように
**式が現れえない位置に限って** `=` が初期値の記号になる。
`=` が比較でなくなる位置はそこだけであり、文の `x = 1` は依然として比較式である。

### 7.2 `≠` `≦` `≧` の扱い［確定］

これらは複数バイトの UTF-8 として符号化される。
演算子照合をバイト単位の `switch` で書くと扱えないため、
演算子表は UTF-8 バイト列として保持し、最長一致で照合する。

対応する ASCII 表記（`!=` `<=` `>=` および `=/`）は同一のトークン種別に落とす。
どちらの表記で書かれたかはフォーマッタが必要とするので、
トークンは元の表記の位置と長さを保持する（Memo.md L34「フォーマッタが書き換える」）。

#### `≤`（U+2264）と `≥`（U+2265）も受け付ける［確定・旧 Q10］

比較演算子には2系統の Unicode 表記がある。**4つすべてを受け付ける。**

| 字句 | コードポイント | 意味 |
| --- | --- | --- |
| `≤` | U+2264 LESS-THAN OR EQUAL TO | 以下 |
| `≦` | U+2266 LESS-THAN OVER EQUAL TO | 以下 |
| `≥` | U+2265 GREATER-THAN OR EQUAL TO | 以上 |
| `≧` | U+2267 GREATER-THAN OVER EQUAL TO | 以上 |

`≦` `≧` は日本語圏で一般的な字形、`≤` `≥` は国際的に一般的な字形であり、
利用者がどちらを入力するかは環境と習慣による。両方を同一のトークン種別に落とす。

いずれも **識別子構成文字から除外する** ことが重要である。
これを怠ると `a ≤ b` が「`a`」と「`≤b` という識別子」に分解され、
極めて発見しにくい誤りを生む。

### 7.3 再代入は前置形［確定・旧 Q2］

```lhat
i := i + 1
```

本節は当初この綴りを `<<` と定めていた。
02 の 8.6 で定義が `var^` に移り `:=` が空いたため綴りは変わったが、
**本節が問題を消している理由は綴りではなく位置にある**。以下はそのまま成り立つ。

**`=` は使わない。** `<-`、`:->`、`i.set^(i+1)`、`set^i i+1`、
および後置形 `i + 1 -> i` も採用しない。

#### 決定理由

7.1 に述べた設計動機による。
`i = i + 1` は数学の等式と同じ見た目でありながら意味が異なり、
初学者を混乱させる。混乱の原因は **`=` という字面** にあるため、
再代入には等式に見えない専用の記号を与える。

`:=` は等式に見えない。`=` との差が1文字であるため、
02 の 8.6 は `x = 1` を文として認めず、診断で両方の意図を示す。

#### 後置形からの変更

当初は後置形 `expr -> var` を採った。
「左辺と右辺という等式の構図を持たない」ことを根拠としたが、
これは動機が要求する以上に強い条件だった。
混乱の原因は `=` であって左右の配置ではない。

後置形をやめた決定的な理由は別にある。
後置形は **文が任意の式で始まることを許す**ため、
`-1 -> counter` のように文が `-` で始まりうる。
改行に意味がない以上、前の行の式に吸い込まれる誤読が生じる。
詳細は [02-syntax.md](02-syntax.md) の 8.4 を参照。

前置形は文が対象（識別子・名前リテラル・`$` 指定子）で始まるため、
この問題が構造的に発生しない。
**改行に意味を持つ規則を `(` のひとつに保てる**（9.2）。

#### `<-` を採らない理由

Memo.md L39 が指摘するとおり `a<-2` が
「`a` に 2 を代入」なのか「`a` が `-2` より小さい」なのか決まらない。

`:=` にはこの問題がない。`-` が絡まないためである。

#### 字句解析上の扱い

- `:=` は1トークン。`:` とは最長一致で区別する
- `<<` はトークンとして残す。撤回された記法を指摘するため（02 の 8.6）
- `<-` はトークンではない。`<` と `-` に分解する。`a<-2` は常に `a < -2`
- **`->` はトークンとして残す。** ~~言語の一部ではないが、~~ 現在は関数・手続きシグネチャの
  返り値節の開始を意味するトークンとして使用されている。
  Memo.md にも本文書の旧版にも後置形の記述が残っているため、
  構文解析器が「後置形は廃止された。`target << value` と書く」と
  指摘できるようにしておく。`-` と `>` に分解すると的確な診断が出せない

### 7.4 存在しないもの［確定・複合代入は 7.4改で撤回］

Memo.md L45「`++` `+=` などの演算子はなし」。
インクリメント（`++` `--`）は字句として存在しない。
数値オブジェクトのメソッド `inc()` `dec()` を使う（L46）。

複合代入（`+=` など）も当初ここに含めていたが、7.4改で撤回した。
`add(a)` `sub(a)` のようなメソッド名での代替は、演算子ごとに
別の名前を覚える必要があり、`op^`（02 の 11.4）が各演算子に与える
綴りとも揃わないため使い勝手が悪かった。

### 7.4改 複合代入は演算子ごとに用意する［確定］

`+=` `-=` `*=` `/=` `%=` `//=` `**=` `..=` の8つを、次と同義とする。

```lhat
a += b   # a := a + b
a -= b   # a := a - b
a *= b   # a := a * b
a /= b   # a := a / b
a %= b   # a := a % b
a //= b  # a := a // b
a **= b  # a := a ** b
a ..= b  # a := a .. b
```

**ただし `a` の評価は1度だけ。** 展開をそのまま読むと `a` が
テーブルの添字・メンバのとき2度評価されるように見えるが、
実際には現在値を1度だけ読み、演算し、同じ場所へ書き戻す。

```lhat
t[f()] += 1   # f() は1度しか呼ばれない
```

書き先は複数書ける（02 の 8.6改2）。`a, b += 1, 2` は位置で対にし、
`a := a + 1` と `b := b + 2` を行う。個数は一致しなければならない。
右辺をすべて読んでから書き込む点も多重代入と同じである（02 の 8.6改3）。

`??=` は設けない。`a ??= b` は「`a` が `nil^` でなければ `b` を
評価せず `a` にも変化がない」ことになり、複合代入として存在意義がない。

### 7.5 追加で確定した演算子［確定・旧 Q3］

Memo.md に記述がなかったものを以下のとおり決定した。

- **剰余: `%`**
- **べき乗: `**`** — `^` がサフィックス専用のため二重アスタリスクを採る
- **論理否定: `!`（前置）** — nil プロパゲーションを `?` 側に移したことで空いた
- **ビット演算・長さ: 演算子として提供しない** — 組み込み関数または標準ライブラリ関数とする

最後の決定は演算子表を小さく保つほかに、`#` を空ける効果があった。
Q5 で行コメントに割り当てられたのはこれによる（6.1）。
Lua では `#` は長さ演算子であり、関数化の決定がなければ使えなかった。

空いた記号のうち `|` はその後、型の合併演算子に割り当てられた
（[02-syntax.md](02-syntax.md) の 11.5）。
`&`、`~`、`>>` は未使用のまま残り、将来の用途に開けておける。
`<<` は Q2 で再代入に割り当てたが、02 の 8.6 で撤回された。

字句解析上の注意。

- `**` は最長一致で1トークン。`a * *b` に相当する構文がないため曖昧性はない
- `!` は前置演算子。`!=`（非等値）とは最長一致で区別する。
  `a != b` は常に非等値であり、「`a` と `!` と `=`」には分解されない
- `//`（切り捨て除算、Q5）と `/` は最長一致で区別する
- `...`（可変長引数）は `..`（連結）より先に照合する。
  順序を誤ると `..` と `.` に分解される
- 複合代入の各綴り（`//=` `**=` `..=` など）は、それぞれの元になる演算子
  （`//` `**` `..`）より先に照合する（7.4改）。順序を誤ると `=` が孤立する
- `<=>`（三方比較、02 の 11.9）は `<=` と `<` より先に照合する。
  順序を誤ると `>` が孤立する

### 7.6 型に関する記法［確定・旧 Q9］

引数と返り値の区切りは **`->` に一本化する**。
Memo.md L314–L316 が併記していた記法のうち `->` を採り、`::` は採らない。
型のシグネチャで `:` を用いる記法（Memo.md L304–L308）も採らない
（[02-syntax.md](02-syntax.md) の 13.6 の (1)）。

```lhat
let^ f = f^a:number^, b:number^=2 -> string^ { a+b }
```

#### `::` から `->` へ変更した経緯

Q9 の当時、`->` は再代入に使われていたため、
同じ記号が「メモリの書き換え」と「型注釈」を兼ねる状態を避ける必要があり、`::` を採った。

その後 Q2 の変更で再代入が前置形になり、**`->` を避ける理由が消えた**。

改めて比較すると `::` には難点がある。
L^ は `:` を多用する（引数の注釈、構造的な型の構成要素、`when^0:`、`elseif^expr:`、
if 式の各節）。その中で `::` は視覚的に埋没し、区切りとして目に留まりにくい。

`->` は「引数から返り値を produce する」という意味を字面が示し、
Rust・Haskell・Python・Swift がいずれも同じ位置で用いている。

`::` はトークンとしては残す。
本文書の旧版および会話上の記述に `::` が多く残っているため、
構文解析器が「`::` は廃止された。`->` を使う」と指摘できるようにしておく。

型に関わる記法は次の3つに整理される。いずれも役割が異なる。

- **`:` — 名前と型を結びつける。** 定義における型注釈（`id : type = value`、Memo.md L36）、
  引数の注釈、構造的な型における構成要素の注釈
- **`->` — 引数と返り値を区切る。** 定義でも型のシグネチャでも同じ
  （[02-syntax.md](02-syntax.md) の 13.1）
- **`as^` — 式に対する型指定。** Memo.md L304–L311

`as^` が `:` ではなく `^` 付き語である理由は Memo.md L311 に記されている。
`elseif^expr:` のような節記法が `:` を占有しているため、後置の型指定に `:` を使いにくい。

### 7.7 `>>` は演算子ではない［確定］

Memo.md L116–L117 の記述を、当初は `>>` という演算子の定義として読んでいた。

```text
コマンド形式手続き呼び出し
>> foo 1 2 3
```

**これは誤読である。** ここでの `>>` は **コマンドプロンプトを表す表記** であり、
L^ の構文の一部ではない。Memo.md L318–L323 の `>> print f.parameters.length`
なども同じくプロンプト付きの実行例として書かれている。

したがってソース中の実際のコマンド形式は、括弧を伴わない並置呼び出しである。

```text
foo 1 2 3
```

#### コマンドインタプリタモードはホストが決める［確定］

コマンド形式を受け付けるかどうかは **動作モード** であり、
**L^ ランタイムを生成する時点でホストアプリケーションが指定する**。

ソースコード中からこのモードへの遷移を指示する構文は存在しない。
`>>` を書けばそれ以降がコマンドモードになる、という規則ではない。

#### 通常モードでの並置呼び出し［確定］

通常モードにおいて `foo 1 2 3` は **構文エラー** とする。
並置呼び出しはコマンドインタプリタモードでのみ有効。

この決定には設計上の利点がある。
2つのモードの差が **文レベルの解析規則1箇所に閉じる** ことになり、
式の解析にも字句解析にもモードが波及しない。
モードフラグを文法全体に引き回す必要がなくなる。

診断品質の観点から、この構文エラーは汎用のメッセージではなく
「`foo(1, 2, 3)` の誤りではないか」と示唆すべきである［提案］。
コマンドモードに慣れた利用者が通常モードで書いてしまう典型例になる。

並置呼び出しの成立条件、および REPL に通常形式のコードを貼り付けた場合の扱いは
[02-syntax.md](02-syntax.md) の 2 章と 3 章で扱う。

#### 字句解析器への影響

- **`>>` はトークンではない。** `a >> b` は `>` と `>` の2トークンに分解される
- 演算子表から `>>` を削除済み。未使用のまま将来に開けてある
- **字句解析器はモードを持たない。**
  `foo 1 2 3` はどちらのモードでも `IDENT INT INT INT` として同じく走査され、
  受理するか拒否するかは構文解析器が決める
- 将来コマンドモードが字句規則そのものを変える必要が出た場合に限り、
  ソース由来ではなく **初期化時のフラグ** として渡す

ビット演算の右シフトに `>>` を割り当てる予定は今のところない（7.5）。

## 8. スコープ指定子

Memo.md L91–L93［確定］。

**数え方が2つある。記号がどちらかを言う。**

| 字句 | 数え方 | 意味 |
| --- | --- | --- |
| `$symbol` | 絶対 | コンパイル単位の先頭（一番外側） |
| `$$symbol` | 絶対 | その1つ内側のスコープ |
| `$$$symbol` | 絶対 | さらに1つ内側 |
| `$^symbol` | 相対 | 現在のリテラルスコープの親 |
| `$^^symbol` | 相対 | その親 |

`$` の反復は **外側から内向き**、`^` の反復は **内側から外向き** に数える。
同じ場所を両方の綴りで指せる（Memo.md L676–L695 がこの対応表そのもの）。

```lhat
let^ x = 1           # 単位の先頭
do^{ let^ x = 2
    do^{ let^ x = 3
        $x           # 1   絶対 0 段目
        $$x          # 2   絶対 1 段目
        $$$x         # 3   絶対 2 段目（＝ここ）
        $^x          # 2   相対 1 段外
        $^^x         # 1   相対 2 段外
    }
}
```

［提案］字句解析器は接頭辞全体を1トークンとして返し、種別と深さを保持する。

- `$` × (n+1) → 絶対、深さ n
- `$` + `^` × n → 相対、深さ n

Memo.md L676–L695 は絶対の段を **グローバルから** 数えていた
（`$a` が 0＝グローバル、`$$a` が 1＝ファイル）。
**グローバル変数を持たないことに決めたため（8.3）、段が1つずつ前に詰まった。**
`$` が単位、`$$` がその1つ内側になる。相対の `$^` は変わらない。

［確定］記号と識別子の間に空白を置けない（Memo.md L684–L685）。

**間に置けないのは空白だけではない。** 記号の次は識別子の開始文字でなければ
ならず、`$.x` も `$ x` も同じ誤りとして拒否する。合法な形は `$x` だけであり、
`$` を単体で書いてメンバを辿る綴りは無い。

なお旧層には `$1a` `$-3a` `$3^a` といった数値添字形式があるが（L643–L698）、
記号の反復（`$` と `^`）で同じことが書けるため採用しない。
`$1a` は `$$a`、`$-1a` は `$^a` にあたる。

### 8.1 何を1段と数えるか［確定］

> **名前が見えるようになるスコープを開く `{` を数える。**

`^` の数はこの `{` の数であり、それ以外の何でもない。

| 形 | 1段か |
| --- | --- |
| `do^{ … }`、ループ本体、`if^ c { … }` | ✓ |
| サブルーチンの本体 `f^ n { … }` | ✓（引数は**この中**にある） |
| `def^{ … }` | ✓（14.4 の `self^` と `class^` がここの名前） |
| `{ a := 1 }`（テーブルリテラル） | ✗ |
| `self^{ … }`、`error^ K { … }` | ✗ |
| `$"{ 式 }"`（補間の穴） | ✗ |
| `catch^`、`with^` | ✗（そもそも `{` を書かない） |

右列が ✗ のものは、中身が **要素や式であって束縛ではない**。
名前が増えないので、数える対象にならない。

サブルーチンの引数が本体の中にあるのは `{` がひとつだからである。
`f^ x:string^ { $^x }` の `$^x` は本体の外を指す。

### 8.2 意味論［確定］

> **指定子は「どこから探し始めるか」を言う。どこで止まるかは言わない。**

指し示したスコープにその名前が無ければ、通常どおりさらに外へ辿る。

```lhat
let^ x = 1
do^{
    do^{ let^ y = 2
        $^x            # ひとつ外に x は無いので、さらに外の 1 に届く
    }
}
```

- `$` は **コンパイル単位の先頭**。03 の 4.3 の対話セッションでは
  セッションのトップレベル全体を指す
- 開いているスコープの外を指したら誤りとする。相対の `$^^^^`（外へ行き過ぎ）も、
  絶対の `$$$`（書いた場所より内側を名指し）も同じ扱いになる。
  端で止める寄せ方はしない（02 の 9.8 の多段 `break^` と同じ理由）

#### 読み書きは同じ束縛を指す［確定］

`$^x` は再代入の左辺にも書ける。読みと書きは同じ解決を通るため、
`$^x := 9` が書き込む先は `$^x` が読む先と必ず一致する。

```lhat
var^ x = 1
do^{ var^ x = 2
    $^x := 9        # 外の x が 9 になる。内側の x は 2 のまま
}
```

`var^` には書けない。8.7 のとおり `var^` は **書かれた場所に名前を作る** 文であり、
他のスコープを指す余地がない。既にある束縛へ書くのは `:=` の仕事である。

### 8.3 グローバル変数は持たない［確定］

Memo.md L91–L93 の `$symbol`（グローバル）は **採らない**。
そのぶん `$` が単位を指す綴りになった（8 章の表）。

理由は 05 の 8.1「取り込まないものは何も見えない」の系である。

- 静的型検査を持つ以上、共有される名前は **どこかに宣言されていなければ
  型が付かない**。宣言を書いた時点で、それは実質モジュールになる
- `require^` / `import^` / `module^`（05 の 3–6 章）が揃った今、
  この形のグローバルが埋める隙間が無い
- 単位ごとに検査する以上、ある単位が書いたグローバルを別の単位が読むには
  型を単位間で共有する配管が要る。そして **どちらが先に検査されるかで
  見えたり見えなかったりする** ——共有された可変の名前空間に型を付ける限り
  避けにくい

JavaScript が辿った道が同じ結論を示している。暗黙のグローバルを ES5 strict で
封じ、ES6 の `let`/`const` はトップレベルでも `globalThis` のプロパティに
ならず、ES モジュールで各ファイルが閉じた。残ったのは `globalThis.x` という
明示的な綴りだけである。TypeScript で `globalThis.x` に型を付けるには
`declare global` を **どこかに書く** 必要があり、上の一点目そのものにあたる。

雑な置き場が要るなら 05 の 8.6 の `L^` に直接生やせる。
ただし 8.6 は「載せるのはプログラムが自分では用意できないものに限る」と
定めているので、そこに置く筋も薄い。

本節が 05 の 4 章で `public^ var^` を認めない理由でもある（02 の 8.9）。
単位をまたいで見える名前が、その単位の与り知らぬところで変わるなら、
それは綴りを替えたグローバル変数にほかならない。

## 9. 空白と改行

### 9.1 空白［確定］

空白・水平タブはトークンの区切りとしてのみ意味を持ち、読み飛ばす。

### 9.2 改行［確定・旧 Q1］

**改行は文法的に意味を持たない。ただし1点だけ例外がある。**

字句解析器は `NEWLINE` トークンを出力しない。
代わりに、**全トークンに「直前に改行があったか」の真偽値を持たせる**。
この値を参照する規則は **10.9 の呼び出し括弧の規則ただ一つ** である。

一時は「文が始まりうる位置では改行直後の `-` を単項とする」という
2つめの規則を要したが、Q2 で再代入を前置形に変更したことで不要になった。
経緯は [02-syntax.md](02-syntax.md) の 8.5 を参照。

#### 自動セミコロン挿入は採らない

Go・JavaScript・Swift・Kotlin・Julia などが採る
「改行が文を終端し、継続規則で例外を設ける」方式は採用しない。
文の区切りを改行に依存させると、
`.` によるメソッド連鎖や行頭に二項演算子を置く整形が、
すべて継続規則の対象になり、規則が増え続ける。

#### 文脈自由性との関係

「改行に意味を持たせない」ことと「文法が文脈自由である」ことは別の性質であり、
両者を混同しないほうがよい。

- Python のインデントは、字句解析器が `INDENT` / `DEDENT` を生成する。文法は文脈自由のまま
- Go の自動セミコロン挿入も字句解析器の規則である。文法は文脈自由のまま

10.9 で導入する規則も同様に字句側で処理される。
形式的には終端記号が2種に分裂するだけなので、文法の文脈自由性は保たれる。

なお、真に文脈自由でなくなる代表例は C の typedef（いわゆる lexer hack）であり、
`(a)*b` がキャストか乗算かを字句解析器が型情報なしに決められない。
**L^ は型名が `number^` のように `^` で標識されるため、この問題を構造的に回避している。**

#### 字句レベルで改行が終端になるもの

次の2つは字句解析器の内部規則であり、文法には波及しない。

- `#` 行コメント（6.1）
- `"""` 行末文字列リテラル（5.3）

#### `;` は別問題として残る

Memo.md L148–L151, L180, L199 が `;` を要求しているのは文の区切りのためではなく、
`:` で導入される開放的な構文の終端を決めるためである。

```text
foo(f^:x, y)
    → foo(f^{return^x, y})   なのか
    → foo(f^{return^x}, y)   なのか
```

これはカンマ区切りリストがどこで閉じるかの問題であり、
1行に書いても同じく決まらない。改行方針とは独立に `;` が必要になる。
構文仕様の側で扱う。

## 10. 字句的曖昧性と解決規則

本文書で最も実装に直結する部分。
いずれも「素朴な最長一致で書くと誤る」ものばかりである。

### 10.1 `a.1.1` — 整数キーの連鎖

Memo.md L29 は `a.1.1` を「C で言う所の `a[0][0]`」としている。
期待されるトークン列は次のとおり。

```text
IDENT(a) DOT INT(1) DOT INT(1)
```

しかし素朴な最長一致では、`.` の後の `1.1` が浮動小数点数として読まれてしまう。

```text
IDENT(a) DOT FLOAT(1.1)     -- 誤り
```

**解決規則［提案］: `.` トークンの直後に現れる数字列は、整数リテラルとしてのみ解釈し、
小数点を消費しない。**

この規則は Memo.md の設計意図と一致している。L28 は
「`a.(1.234)` 実数で引く場合は `()` 必須」と述べており、
実数キーには括弧（あるいは L28 の結論に従えば `[]`）を要求する設計だからである。
すなわち `.` の直後に実数が来ることは、言語仕様上そもそもない。

4.4 で先頭の小数点を禁じたのは、この規則と表裏一体である。

### 10.2 `1..2` — 連結演算子と小数点

`..` は連結演算子（Memo.md L357）である。`1..2` は次のように読まれなければならない。

```text
INT(1) CONCAT INT(2)
```

素朴な実装では `1.` を浮動小数点数として読んでしまう。

**解決規則［提案］: 小数部は、小数点の直後に数字が続く場合にのみ成立する。**
`1.` の時点で次が `.` であれば、小数点を消費せず整数として確定する。

これは 4.4「末尾の小数点を認めない」と同じ規則である。

### 10.3 数値の直後に識別子は置けない［確定・旧 Q7］

> 数値リテラルの直後に識別子開始文字が続いたらエラーとする。

Memo.md には空白ありの `when^1 to^3:`（L192）と、
空白なしの `when^1to^3:expr`（L199）の両方が現れる。
**後者を不正とし、空白を必須とする。**

```text
when^1 to^3:      # 正
when^1to^3:       # 誤。エラー
```

Memo.md L199 の記述はこの決定により無効となる。

隣接を許せば `1to^3` は読めるが、その代償として
`123abc` のような打ち間違いを字句段階で捕捉できなくなる。
空白1個を要求するほうが得るものが大きい。

`to^` のような限られた語に対してのみ隣接を許す折衷案は採らない。
それは字句解析器にキーワード表を持ち込むことを意味し、2.1 の方針と衝突する。

#### この決定が波及して単純化されるもの

- **指数表記の後戻りが不要になる**（4.5）。
  `1e^3` を「整数 1 と `e^` と整数 3」に分解して救済する必要がなくなり、
  `e` の後に数字がなければ単にエラーでよい。字句解析器から巻き戻し機構が消える
- `0x1g` のような不正な基数リテラルも同じ規則で捕捉できる

#### 影響しないもの

`.` や `..` は識別子開始文字ではないため、10.1 と 10.2 の規則は影響を受けない。

```text
a.1.1     # 10.1 のとおり。エラーにならない
1..2      # 10.2 のとおり。エラーにならない
```

### 10.4 指数表記の後戻り［10.3 に統合］

旧版では `1e5` と `1e^3` の衝突を読み戻しで解決していたが、
Q7 の決定により後戻り機構そのものが不要になった。10.3 を参照。

節番号は他節からの参照を保つため欠番にしていない。

### 10.5 `"""` と `""` の衝突

`"""` は行末までの文字列（5.3）である。
一方 `""` は空文字列であり、その直後に別の文字列リテラルが続く並び `""` + `"abc"` は
`"""abc"` と書かれると `"""` として読まれる。

**解決規則［提案］: 最長一致を優先し、`"""` を行末文字列として扱う。**
空文字列を連結したい場合は間に空白を置く（`"" "abc"`）。

実害はほぼないが、規則として明示しておく。

### 10.6 `$` の直後による分岐

`$` は後続文字によって役割が変わる［提案］。

- `$` + `"` または `'` → 補間文字列の開始（5.4）
- `$` + `$` / `^` / 識別子開始文字 → スコープ指定子（8）

いずれも空白を挟めないため、1文字先読みで決定できる。

### 10.7 `{^` は採用しない［決定済み・旧 Q6］

Memo.md 内では正面から矛盾していた箇所だが、方針が決定した。

**決定内容:**

- データ構造リテラルは `{}`
- ブロックは必ずキーワードとセットで現れる（`for^… {}`, `if^… {}`, `while^… {}` など）
- 制御構文を伴わない素のブロックは `do^{}` で書く
- `{^` は **採用しない**

これは Memo.md 末尾追記 L704–L713 の案 1)（すべてのブロックを `{^ … }` とする）を退け、
最新層 L48–L50 を採る決定である。L50「テーブルリテラルなのかブロックなのかは
キーワードの有り無しでわかる」および L49「空のブロックは書けない、`do^{}` とする」が
そのまま生きる。

**字句解析器への影響: `{^` はトークンとして存在しない。**
`{` と `}` を単独のトークンとして返すだけでよい。

**構文解析器への波及（参考）:**

この決定は 2.1 の「キーワードは必ず `^` を伴う」という設計と噛み合っている。
`{` が現れたとき、それがブロックかテーブルリテラルかは
**直前のトークンが `HAT_IDENT` かどうかを見るだけで判定できる**。
キーワードが字句レベルで `^` により標識されているため、
構文解析器は1トークンの後方参照だけで済み、意味解析を待つ必要がない。

予約語を廃して `^` を導入した設計判断が、ここで曖昧性の解消として効いている。

### 10.8 `[]` の役割［字句的には影響なし］

10.7 でデータ構造リテラルが `{}` に確定したことにより、
Memo.md L18「`[]`はテーブルリテラルのみ」は撤回されたものとして扱う。
L28「これ良くないので`[]`復活」および L30 の `a[1, 1]` に従い、
`[]` はインデックス／キーアクセスに用いる。

いずれにせよ字句解析器は `[` と `]` を返すだけなので影響を受けない。

### 10.9 呼び出し括弧は呼び出し先と同じ行に置く［確定・旧 Q1］

区切り子を必須とせず、かつ改行にも意味を持たせない文法では、
**継続にもなれ文頭にもなれるトークン**が改行直後に現れたときに、
人間の知覚する境界と構文解析器の決定する境界が食い違う。

Lua がこの問題の実例であり、マニュアルが明示的に警告している。

```lua
a = b + c
(print or io.write)('done')
```

これは `a = b + c(print or io.write)('done')` と解釈される。
誤った解釈が構文的に妥当であるため **構文エラーが出ず**、
実行時に原因から離れた位置で失敗する。エラー局所性が失われるこの性質は、
開発の反復速度がいくら上がっても改善しない。

#### 規則

> 呼び出しおよび添字の `(` は、呼び出し先と同じ行になければならない。
> すなわち、直前に改行がある `(` は後置演算子として解釈されない。

```text
(t1 or t2)["key"] << value      -- 行頭の ( は継続になれない → 文頭として解釈 ✓

let^ a = b + c
(f or g)()                      -- 人間の直感どおり2文に分かれる ✓

foo(
  a, b                          -- ( は foo と同じ行 → 呼び出し ✓
)
```

#### 対象は `(` だけでよい

継続と文頭の両方になれるトークンを数え上げると、規則が必要なのは `(` のみである。

- `[` — 10.8 で添字専用に確定。文頭になれないため曖昧性がない
- `{` — 10.7 でブロックがキーワード必須になった。文頭のテーブルリテラルを
  文として認めない限り曖昧性がない
- `-` — 文頭になれない。単項マイナスだけの文は意味を持たず、
  再代入は対象から始まる（`counter << -1`）ため、文が `-` で始まらない。
  一時は後置形 `-1 -> counter` のために例外を要したが、
  Q2 の変更により解消した（[02-syntax.md](02-syntax.md) の 8.5）

**`{}` と `[]` の役割を確定させた 10.7・10.8 の決定が、ここで2件の曖昧性を先に潰している。**

#### 脱出の被演算子にも同じ規則が要る［確定］

> **`return^` `yield^` `break^` の被演算子は、その語と同じ行になければならない。**

被演算子は省略できる（02 の 13.2、15.4）。省略された場合、次の行の文が
被演算子として読まれてはならない。

```text
yield^
x := 1          -- 2文。yield^ は何も出さない ✓
```

**ここでは「継続にも文頭にもなれるトークン」を数え上げても足りない。**
`x` は普通の識別子であり、式の先頭にも文の先頭にもなれる。
区別できるのは行の情報だけである。

同じ行に置けば被演算子になる。

```text
return^ x
y := 1          -- return^ は x を返し、y := 1 は別の文 ✓
```

コマンド形式手続き呼び出し（7.7）は文頭に識別子を置く形であり、
`(` のような二重の役割を持たないため、この規則の対象にならない。

#### 失うもの

`(` を次の行に落とす整形ができなくなる。

```text
foo
(a, b)          -- 呼び出しにならない。2文として解釈される
```

実務でこの整形を採る例はほとんどない。
引数リストを複数行に割る場合は `(` を呼び出し先と同じ行に置く通常の整形で書ける。

#### 検討して採らなかった案

- **文頭の `(` を禁止する** — `(t1 or t2)["key"] << value` のような
  計算された対象への操作が書けなくなり、制限が強すぎる
- **`do^(f or g)()` のような明示マーカーを要求する** — 文法的には成立し、
  10.7 の `do^{}` を一般規則の特殊例として統合できる利点もあるが、
  Lua の先頭 `;` と同型であり、書き忘れを検出できない。
  脱出口であって検出機構ではないため、上記の問題を解決しない

字句解析器が返すトークンの種別。

| 種別 | 内容 | 保持する情報 |
| --- | --- | --- |
| `IDENT` | 識別子 | 文字列 |
| `HAT_IDENT` | `^` 付き識別子 | 文字列、ハット数 |
| `NAME_LITERAL` | バッククォート囲みの名前（3.4） | 展開後の名前 |
| `INT` | 整数リテラル | 値、基数 |
| `FLOAT` | 浮動小数点リテラル | 値 |
| `STRING` | `"…"` `'…'` `"""…` | 展開後の文字列、種別 |
| `INTERP_BEGIN` | `$"` | — |
| `INTERP_TEXT` | 穴と穴の間のテキスト断片 | 展開後の文字列 |
| `INTERP_EXPR_BEGIN` | 穴の `{` | — |
| `INTERP_FORMAT` | `:` 以降の書式指定子 | 生の文字列 |
| `INTERP_EXPR_END` | 穴の `}` | — |
| `INTERP_END` | 閉じる `"` | — |
| `SCOPE` | `$` `$^…` | 種別、深さ |
| `OP` | 演算子・区切り子 | 種別、原表記（7.2） |
| `EOF` | 入力終端 | — |

`NEWLINE` は存在しない（9.2）。

全トークンが共通で保持する情報。

- **直前に改行があったかの真偽値**［確定］ — 10.9 の規則が参照する
- ファイル内バイトオフセット（開始・終了）［提案］
- 行番号・桁番号［提案］（桁は UTF-8 バイトではなくコードポイント単位で数える）

桁をバイトで数えると、日本語コメントを含む行のエラー表示位置がずれる。
このプロジェクトでは設計メモが日本語である以上、実際に踏む。

`IDENT` から「末尾 `?` の有無」が消えているのは 3.2 の変更による。

## 12. 決定済み事項

いったん未決として起票し、その後に決定したもの。
番号は安定させるため欠番にせず、決定内容を記録して残す。

- **Q1 — 改行はトークンとして意味を持つか → 持たない（9.2, 10.9）**

  `NEWLINE` トークンは出力しない。全トークンに「直前に改行があったか」の
  真偽値を持たせ、参照するのは 10.9 の呼び出し括弧の規則ただ一つとする。
  自動セミコロン挿入は採らない。
  検討の末に採らなかった案（文頭 `(` の禁止、`do^` 明示マーカー）は 10.9 に記録。

- **Q2 — 再代入演算子の記法 → 前置形（7.3）。綴りは 02 の 8.6 で `:=`**

  `i << i + 1` と書く。`=` `<-` `:->` `i.set^(i+1)`、
  および一度採用した後置形 `i + 1 -> i` はいずれも不採用。
  設計動機は 7.1 に記録。後置形を撤回した理由は
  [02-syntax.md](02-syntax.md) の 8.4 と 8.5 に記録。

- **Q3 — 未定義の演算子 → `%` `**` `!`。ビット演算と長さは関数（7.5）**

  剰余 `%`、べき乗 `**`、論理否定 `!`（前置）。
  ビット演算子一式と長さ演算子は言語に入れず、組み込み関数または
  標準ライブラリ関数として提供する。
  併せて nil プロパゲーションを `!.` から `?.` `?(` `?[` に変更し、
  識別子末尾の `?` を廃止した（3.2）。

- **Q4 — 文字列補間の書式指定 → `{式:書式指定子}`（5.4）**

  Memo.md L70 の `{2.4:bar}` は前後が逆の誤記。正しくは `{bar:2.4}`。
  書式指定子は式ではなく生の文字列として取り込む。
  穴の中で括弧類に囲まれていない最初の `:` が境界となるため、
  `:` を最上位に含む式は括弧で囲む必要がある。

- **Q5 — `//` をコメントとするか → しない。行コメントは `#`（6.1）**

  `//` は切り捨て除算に割り当てる。
  ブロックコメントは `#[ … ]#`（入れ子可）を提案。
  副次的にシバン行 `#!/usr/bin/env lhat` が特別扱いなしで読み飛ばせる。

- **Q6 — `{^` を採用するか → 不採用（10.7）**

  データ構造リテラルは `{}`。ブロックは必ずキーワードとセット。
  素のブロックは `do^{}`。`{^` はトークンとして存在しない。
  併せて `[]` はインデックス／キーアクセスに確定（10.8）。

- **Q8 — `or^` を `else^` の代わりに使えるか → 使えない**

  `or^` は論理和専用とする。
  Memo.md L171–L174 の `or^expr:` / `or^:` という節記法、および
  L182 の推奨形 `if^expr: or^expr: or^: ;` は撤回する。

  撤回の理由は字句・構文上の衝突である。`or^` を節マーカーにすると、
  次の並びで `b or^ y` という論理和の式なのか、
  `a := b` の後に `or^` 節が始まるのかが決まらない。

  ```text
  if^x {
      a := b or^ y: ...
  }
  ```

  この曖昧性は改行の有無に関係なく、1行に書いても生じる。
  Q1 でどの方針を採っても解消しないため、記法そのものを廃した。

  条件分岐の節は `elseif^` `else^if^` `elsif^` `elif^` `ei^` `else^` `el^` で書く。
  if 式の推奨形は構文仕様の側で決め直す必要がある。

- **Q7 — 数値リテラル直後の識別子 → 不許可。空白必須（10.3）**

  `1to^3` はエラー。`1 to^3` と書く。Memo.md L199 の記述は無効。
  `123abc` を字句段階で捕捉できる利点を取った。
  副作用として指数表記の読み戻し機構が不要になり、字句解析器が単純化された（4.5, 10.4）。

- **Q9 — 引数と返り値の区切り → `->` に一本化（7.6）**

  当初は `::` を採った。当時 `->` が後置再代入に使われており、
  同じ記号が「メモリの書き換え」と「型注釈」を兼ねるのを避ける必要があったため。

  その後 Q2 で再代入が前置形になり `->` が空いたこと、
  および `:` を多用する中で `::` が視覚的に埋没することから、`->` へ変更した。
  `::` はトークンとしては残し、診断で `->` を示せるようにする。

  型に関わる記法は `:`（名前と型の結びつけ）、`->`（引数と返り値の区切り）、
  `as^`（式の型指定）の3つに整理される。

- **Q10 — `≤` と `≥` を受け付けるか → 受け付ける（7.2）**

  `≤`（U+2264）を「以下」、`≥`（U+2265）を「以上」として
  `≦`（U+2266）`≧`（U+2267）と同じトークン種別に落とす。
  日本語圏の字形と国際的な字形の両方に対応する。
  4文字とも識別子構成文字からは除外する。

- **Q11 — `$'…'` は存在するか → しない（5.4）**

  補間は `$"…"` のみ。Memo.md L71 の注記「文字列補間したいなら `""` 必須」に従う。
  `$'…'` は専用の診断で拒否し、スコープ指定子の誤りとして報告しない。

- **Q12 — 名前リテラルの記法 → バッククォート囲み（3.4）**

  `` `foo?` `` のように書く。`id^` による記法（3.3）を置き換える。
  `IDENT` とは別のトークン種別とし、名前を値として扱う用法を残す。
  実行時の文字列から名前を得る操作は標準ライブラリ関数とする。

- **Q13 — コメントを保持するか、説明文をどう区別するか → 保持する。区別しない（6.4）**

  字句解析器がコメントの位置と本文を保持し、構文木のノードに結び付ける。
  説明文を区別する専用の記法は設けず、定義の直前のコメント塊を説明文とみなす。
  保持はトークン列とは別の表で行い、構文木との対応は位置で取る。
  `LHAT_WITH_COMMENTS` が未定義のビルドでは丸ごと外れる。
